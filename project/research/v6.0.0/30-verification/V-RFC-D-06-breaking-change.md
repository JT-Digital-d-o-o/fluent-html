# Verdict: RFC-D-06 — breaking-change lens

> ADVERSARY brief: kill RFC-D-06 by finding hidden breakage mislabeled as additive.

## Attack

RFC-D-06 stamps itself `breaking: additive`, claims "Additive / behavior-preserving — nothing breaks," and explicitly states `breaking-changes.md`: **no entry**. That claim is false for one bundled item, and the falseness is exactly the failure mode this lens exists to catch: a behavioral change to a **public symbol** smuggled in under an "internal cleanup" label.

- **Breaking failure mode 1 — `escapeAttr` is public surface, and its output changes.** The RFC repeatedly frames `escapeAttr` as "internal-renderer surface that app code never calls directly" (lines 177, 234) and rests its compat argument on "the renderer always emits double-quoted attributes, so rendered HTML is byte-identical" (line 171). But `escapeAttr` is **exported from `src/render/index.ts:3`** and reachable by consumers via the `./render` subpath export declared in `package.json` (`"./render": { "default": "./dist/src/render/index.js" }`). It is not internal. The compat reasoning ("byte-identical *inside the renderer*") is irrelevant to a third party who imports `escapeAttr` from `fluent-html/render` and calls it on a value destined for a single-quoted attribute, an unquoted attribute, RCDATA, or a `<textarea>` — all contexts where dropping `>`/`'` escaping is **not** output-equivalent and is a latent XSS/correctness change. The RFC's own escape.ts docstring warns: "If unquoted or single-quoted attributes are ever supported, this would need to also escape..." — the RFC removes the safety that docstring is guarding, for a public function whose callers it does not control.

- **Breaking failure mode 2 — an existing test encodes the old contract and will fail.** `test/escape.ts:72-75` asserts `escapeAttr('<"test">') === '&lt;&quot;test&quot;&gt;'` under the title `"delegates to escapeHtml"`. Under the proposed body (escape only `&` and `"`; drop `>` and `'`; `<` is an open question) the `>` is no longer escaped, so the assertion breaks regardless of how the `<` open question resolves. A test that must be edited to make a change pass is, by definition, a behavioral/contract change — not "behavior-preserving." The RFC lists no test churn for F-D-051 and asserts "no output change" (line 172), which is contradicted by the repository's own locked-in assertion.

- **Breaking failure mode 3 — three serializers must move in lockstep or diverge.** F-D-093/F-D-052 touch `render.ts:213/225` and `stream.ts:151/163`, but the **fold** `renderAlgebra` (`src/fold/algebras/render.ts:18,29,36-38`) independently calls `escapeAttr(String(value))`. The RFC does not enumerate it. If `escapeAttr` changes semantics under all three but the `String()`/non-string skips land in only two, the three render paths produce different attribute bytes for the same tree — a silent regression the RFC's "byte-identical" claim would mask. This is the same render/stream/fold divergence class flagged in the recon seed backlog (§10, Track A "HTMX serialization duplicated across render/stream/fold, diverging").

What survives the attack cleanly: **F-D-021** (prototype-default `_variantPrefix`) and **F-D-022** (try/finally) are genuinely behavior-preserving for app code — `addClass` reads `this._variantPrefix` truthily (`tag.ts:103`), so own-prop-`null` and prototype-`null` are indistinguishable; `delete` restoring to a prototype `null` is correct. **Context `push`/`pop`** and **`foldViewScalar`** are true additive new exports; `scope()`/`foldView()` callers are untouched. No symbol is renamed or removed. So the breakage is narrow — it is confined to `escapeAttr` — but it is real, it is public, and it is mislabeled.

## Does it survive?

**survives-with-changes.** Sixteen of the seventeen findings are honestly additive or internal. The single defect is material because it violates guardrail §11.5 (backward-compat) and §11.7-adjacent honesty: a public exported function's observable contract changes under a `breaking: additive` banner with "no `breaking-changes.md` entry." That is precisely the "breaking API sneaks in under a minor/additive label" failure (ALGORITHM §13, "Guardrail drift"). It is not a reject, because the fix is mechanical and the rest of the cluster is sound — but it must not ship as written.

The cleanest resolution is the additive one (required change #3, option A): keep the **public** `escapeAttr` byte-for-byte as `= escapeHtml` and route the renderer's hot path through a new **internal** `escapeQuotedAttr`. That preserves the public contract, keeps the perf win, needs no `breaking-changes.md` entry, and leaves `test/escape.ts:74` green. If instead the team wants `escapeAttr` itself narrowed, it must be reclassified `breaking`, bundled into `breaking-changes.md`, the open `<` question resolved first, and the existing test rewritten (required changes #1, #2). Either path is acceptable; the status quo (silent public-symbol semantic change labeled additive) is not.

## Guardrail check (breaking-change owns §11.5)

- **§11.5 backward-compat:** FAIL as written for F-D-051. `escapeAttr` is a published export (`./render` subpath); narrowing its body is an observable change to a public symbol, not internal. Frontmatter `breaking: additive` and "no `breaking-changes.md` entry" are incorrect for this item. Must move to additive-via-rename or be reclassified breaking + bundled. All other 16 items pass §11.5 (additive exports / shape-only internal changes with app-invisible behavior).
- Cross-check with security/escape lens REQUIRED before merge: dropping `>`/`'` (and the `<` open question) for a public escaper is exactly the kind of change that lens must sign off on; the breaking-change verdict does not substitute for it.
