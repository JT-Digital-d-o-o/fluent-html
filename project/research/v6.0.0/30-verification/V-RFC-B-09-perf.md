# Verdict: RFC-B-09 — perf lens

> I am an ADVERSARY. My job is to KILL this RFC through the perf lens.
> The synchronous SSR render is the product's hot path. Any async must be opt-in and must not touch the sync path. Default to reject under uncertainty.

## Attack

The RFC's §11.2 self-check asserts the no-options overloads are "byte-identical to today (no per-render cost when unused)." That assertion is **false as designed**, and the falsity is structural, not incidental.

- **perf failure mode 1 — the overload dispatch tax on the 100%-common path.** `View = Tag | string | RawString | View[]` (`src/core/types.ts:6`). `RenderOptions = { contexts?, nonce? }` is a plain object with no discriminant. TypeScript overloads are *erased at runtime*: `render(opts, ...views)` and `render(...views)` compile to one JS function that must inspect `arguments[0]` to decide which it got. Today the body is a single line — `renderImpl(views.length === 1 ? views[0]! : views, false)` (`render.ts:34`) — zero branches, zero property reads on the view. The overloaded version must, on **every** call, run something like `isRenderOptions(arg0)` → which means a `typeof === 'object'` + absence-of-`_t` check + a property probe (`'contexts' in arg0`). A bare `Tag` *is* a `typeof === 'object'`, so the cheap `_t` discriminant the codebase relies on (`guards.ts`) doesn't cleanly separate "options" from "a single Tag view passed positionally" without an extra read. That added branch + megamorphic arg0 shape lands on the millions of `render(SomePage())` calls that will never use `contexts`. This is exactly the "common case pays for a rare feature" pattern guardrail §11.2 forbids, and the RFC's claim of byte-identity is unverified hand-waving — no bench accompanies it.

- **perf failure mode 2 — `seedContext` moves context-entry onto the always-hot chrome path, and the Disposable alloc is already a known cost.** The whole point of `seedContext` is that *every authenticated request* in *every app* now enters its chrome contexts (nav counts + sidebar + i18n translation + locale + timeZone = 3-5 contexts is the RFC's own worked-example count). Each `scope()` allocates a fresh closure-bearing Disposable object (`context.ts:77-85`) — and the v6 perf backlog *already* lists "Cheaper context `scope()` — per-call Disposable alloc" as an open Track-D defect (ALGORITHM.md:409). RFC-B-09 takes that not-yet-fixed cost and multiplies it by every request × every seeded context, turning a "rare scope() call" cost into a per-request baseline. `render({ contexts })` running `scope(e0) ∘ scope(e1) ∘ …` (RFC §2) means N Disposable allocations + N stack pushes + N pops *per render*, on the hottest authenticated path. The RFC never quantifies this and never depends on the Track-D fix.

- **perf failure mode 3 — new unconditional per-request allocation (`request[kContexts]`).** §3 says `seedContext` "collects each seeded `(ctx, value)` into a per-request bag (`request[kContexts]`)". If that bag is allocated for every request (the natural decorateRequest default), then routes that seed *nothing* still pay an array/Map allocation + a property write per request — a regression for the many partial-swap / health-check / static routes that render without any chrome context. The RFC is silent on laziness.

- **perf failure mode 4 — stream path context-leak under throw, and per-chunk re-entry ambiguity.** `renderToStream` (`stream.ts:111-118`) walks the entire tree synchronously inside `read()` and `push`es. The RFC says disposal is "owned by the `render({ contexts })` `finally`" — but the stream path is a *different* function (`streamImpl`), and the RFC's §2 only spells out the wrapping for the string `render`. If a component throws mid-walk (e.g. `AuthCtx.current` throwing per `createRequiredContext`, `context.ts:115`), an unguarded `stack.push` without the matching `pop` **leaks the context stack into the next request** sharing that module-level `stack` array (`context.ts:70`). That's not just perf — it's a correctness-leak — but it's caused by the perf-shaped decision to keep contexts as a process-global stack rather than ALS. The RFC must state the stream try/finally contract explicitly.

## Does it survive?

**survives-with-changes.** The architecture (explicit `contexts` on render, no ALS) is the *correct* perf call — it keeps the data path synchronous and ALS-free, which is genuinely the cheap option for sync SSR. The async work is properly confined to the app's preHandler. So the core decision is perf-sound and I cannot land a clean kill on the primitive itself.

But the **packaging** as a polymorphic-first-arg overload on the hottest function is a real, specific regression to the sync hot path, and the RFC ships zero benchmark to back its "byte-identical" claim — under §11.2 ("Track D owns the proof") and the default-reject rule, an unproven hot-path claim does not get the benefit of the doubt. The five required changes (in frontmatter) fold the fix back in: split the entry point so the no-options path is provably untouched (or prove < 1% with a bench), make the per-request bag lazy, fix/avoid the per-scope Disposable multiplication, and pin down the stream try/finally so the global stack can't leak. With those, it survives; without the bench + the entry-point split, the overload is a reject.

## Guardrail check (§11.2 — sync hot path)

NOT satisfied as written. The RFC asserts byte-identity but the overloaded signature provably adds an arg-discrimination branch to every `render` call, `seedContext` adds N per-request Disposable allocations on the always-on chrome path (compounding an already-open Track-D allocation defect), and `request[kContexts]` adds an unconditional per-request allocation unless made lazy. §11.2 requires the proof to live with the change; it does not. Conditionally clears the guardrail only after the required changes + an accompanying microbench (no-options path 1k/10k nodes, < 1% delta) are folded in.
