# Verdict: RFC-B-05 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC stamps `breaking: additive` and asserts "Additive — nothing breaks … no signature changes, no removals." At the *public TypeScript surface* that is true, and I verified it: no export-name collisions in `src/index.ts`; none of `Icon`/`Stop`/`Mask`/`Filter`/`LinearGradient`/`RadialGradient`/`ClipPath`/`FeGaussianBlur` exist in source today; and a grep across rideshare/mngmt/jt-cut/ttl found no local `Icon`/`Filter`/`Mask`/`Stop` symbols a new barrel export would shadow. The headline additivity holds. But "additive" is being used to wave away three hazards this lens exists to catch.

- **breaking-change failure mode 1 — silent behavioral regression masquerading as additive (the killer).** The render path is schema-gated. `render.ts:208-216` and `stream.ts:146` serialize only attributes whose keys appear in the prototype's `_sk` array (`SvgTag._sk` at media.ts:351 = `['width','height','viewBox','xmlns','fill','stroke','stroke-width']`; `SHAPE_SK` at svg.ts:66 ends at `'transform'`). The existing typed-field setters render *only because* their key is in `_sk` — e.g. `setStrokeLinecap` writes `this['stroke-linecap']` (svg.ts:31) and `'stroke-linecap'` is in `SHAPE_SK`. The RFC adds `setStrokeOpacity`/`setStrokeDashoffset` to `SvgShapeTag` and five stroke setters to `SvgTag` in the identical typed-field style (§2), but the proposed code never touches the `_sk` arrays. Consequence: `Path().setStrokeOpacity("0.5")` — the RFC's own worked example D (line 264) — compiles, type-checks, chains, and emits **no `stroke-opacity` attribute**. The "before" used `.addAttribute("stroke-opacity","0.5")`, which routes through `tag.attributes` (render.ts:218-228) and *does* serialize; the "after" routes through a `_sk`-gated field that is *not registered*, so it is dropped. That is a behavioral change from the migration the RFC literally prints, invisible at compile time, surfacing only as a wrong render (a chart line that should be faded renders solid). A reviewer trusting `breaking: additive` will not hunt for it. This is §13 "Guardrail drift": internal coupling sneaking in under an additive banner.

- **breaking-change failure mode 2 — the "shared mixin" is a refactor of shipped public methods, mislabeled as new surface.** §2 and Alternatives §3 propose extracting the stroke setters into a mixin "so both expose the same setters." But `setStrokeLinecap`/`setStrokeLinejoin`/`setStrokeDasharray`/`setTransform`/`setFill`/`setStroke`/`setStrokeWidth` are *already public* on `SvgShapeTag` (svg.ts:16-58) and inherited by every shape tag (svg.ts:73-294). Moving them into a mixin touches the inheritance and `_sk` wiring of `Circle`/`Rect`/`Path`/… If the mixin doesn't reproduce the exact signatures and `_sk` membership, existing `Circle().setStroke(…)` behavior changes. The RFC frames this purely as additive and never flags the refactor risk, so the `breaking` field under-reports.

- **breaking-change failure mode 3 — guideline/surface desync re-teaching a deprecated name.** Not a code break but a §11.8 defect: the RFC's replacement `fluent-html.md` text (line 333) presents `setSvgOpacity()` as the live API, while svg.ts:50-53 has deprecated it in favor of `setOpacity`. Shipping this guideline edit resurrects a name the library is retiring — the prose mirror of a §11.7 vocabulary desync.

## Does it survive?

**survives-with-changes.** I could not find a hard public-API break — no removed/renamed exports, no app collisions — so an outright `reject` isn't warranted. But failure mode 1 means the RFC as written ships setters that *don't work*, mislabels an internal refactor (mode 2), and mis-teaches a deprecated name (mode 3). These are exactly the "additive-on-paper, breaking-in-practice" defects this lens forces back into the design. All fixes are mechanical and fold into the RFC: enumerate the exact per-class `_sk` deltas and require the `_sk` mutation alongside each typed-field setter; reframe the SvgShapeTag delta and the mixin as a behavior-preserving refactor with a test obligation; and correct the guideline text. With those, the `additive` label becomes honest and migration stays a no-op for existing callers.

## Guardrail check (breaking-change owns §11.5)

§11.5 backward-compat: **conditionally pass.** No removals or renames of public symbols (verified against `src/index.ts` and all four apps). The `breaking: additive` frontmatter is defensible but under-specified: it omits (a) the `_sk` coupling that makes the new setters functional and (b) the SvgShapeTag mixin extraction touching shipped inheritance. Both must be spelled out before Wave-4 `breaking-changes.md` can correctly classify this RFC as a true no-migration addition. §11.7 class-string contract: confirm-and-state that the new raw SVG attrs are not Tailwind utilities and need no extractor/eslint entry — the RFC argues this only for Icon sizing.
