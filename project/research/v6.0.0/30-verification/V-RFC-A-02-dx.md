# Verdict: RFC-A-02 — dx lens

> ADVERSARY. Killing RFC-A-02 through the dx failure mode: API surface justification, discoverability, idiom-consistency, misuse-resistance, naming, and the §11.8 guideline edit.

## Attack

I tried to kill this on three dx axes: (1) is the surface worth it, (2) is it misuse-resistant, (3) is the guideline edit correct, minimal, house-style, and complete. It largely holds, but two real traps and three house-style defects survive my read.

- **dx failure mode 1 — the lowercase-vs-camelCase landmine, taught by the README (killer).** The shipped `setAria` impl (tag.ts:298-305) does `key.replace(/[A-Z]/g, l => "-"+l.toLowerCase())` so a camelCase key `hasPopup` renders `aria-has-popup` — which is **not a real ARIA attribute** (correct is `aria-haspopup`, one word), and `labelledBy` renders the broken `aria-labelled-by`. This is not merely latent: the README's canonical setAria example (`README.md:1799-1804`) **teaches exactly this broken form** — `hasPopup: true // → aria-has-popup`. The RFC's new `AriaAttributeName` union is **all-lowercase** (`haspopup`, `labelledby`, `describedby`, `valuenow`) — the *correct* WAI-ARIA spelling, matching the only real multi-word usage in the survey (`rideshare/.../tooltip.view.ts:74` uses `{ describedby }`, and apps use `describedby` lowercase consistently). But the RFC never reconciles the union with the kebab runtime or the README. Net effect after this RFC ships: a developer following the README writes `hasPopup`, it is NOT in the union, flows through `(string & {})`, compiles green, and renders the silently-broken `aria-has-popup` — the precise failure the RFC claims to fix ("`.setAria({ lable })` compiles and silently breaks AT"). The headline value (typed keys catch typos) does not catch the most common multi-word miss, because the trap is casing, not single-word spelling. An author who *does* write the correct `labelledBy` instinct gets a cryptic union-mismatch error with no hint the fix is lowercasing. The conversion machinery, the new type, and the canonical doc now point in three directions. This is a misuse-resistance regression hiding inside an "additive" change.

- **dx failure mode 2 — the guideline re-teaches the boilerplate it's killing.** The RFC's whole premise (F-A-054) is that apps hand-write `checked: on ? "true" : "false"` and should pass `checked: on`. Good. But the proposed `fluent-html.md` block shows the negative case as `.setAria({ disabled: isReady ? "false" : "true" }) // ✗ pass the boolean instead` **without showing the boolean**. The naive fix a reader (human or LLM) derives is `disabled: isReady` — which is the **wrong polarity** (the original maps ready→"false"). The correct answer is `disabled: !isReady`. Shipping a ✗ whose obvious ✓ is a bug is worse than not teaching it. The index block has the same shape but happens to use a non-inverted example, so it's only the topic ref that's actively dangerous.

- **dx failure mode 3 — house-style defects in the index edit.** Guardrail §11.8 demands the `CLAUDE.md` index rule be a clean, copy-pasteable ✓/✗ block matching the surrounding voice. The proposed block degrades into receiver-less fragments (`.setAria({ checked: on })`, `A(icon).setTitle(...)`) where the rest of that index section ("Specialized tag methods", `formFor`) uses complete expressions. An LLM splicing these lines will emit dangling-dot code. Minor, but it's exactly the "confusing guideline edit → adoption failure" the lens is told to flag.

- **Naming — `setTitle` collision.** `setTitle` vs the `Title()` element is a real discoverability trap (the index already lists `Title` as an element elsewhere). The RFC handles it with one parenthetical in the topic ref, but the index — the LLM's primary read — gets no warning. Given the model often reads only `CLAUDE.md`, the disambiguation belongs there.

- **Surface justification — passes (independently verified).** `setRole`/`setTabindex`/`setTitle` retire a large `addAttribute` category — I counted **187** `addAttribute("role"|"tabindex"|"title")` sites across the apps (`grep -rEn 'addAttribute\("(role|tabindex|title)"'`), plus **46** `setAria({ label })` sites for the typed-key win. The `(string & {})` escape-hatch idiom is already load-bearing in `tailwind-types.ts` and `BooleanAttribute`, so this is squarely in-idiom; an app author already reaching for `.setType`/`.toggle` will reach for these. Number-valued `valuenow` is a real gap. No surface inflation: the "Alternatives considered" section correctly rejects `setAriaState` and `setAttrs` batch. This is not idea-inflation trivia. (Note: the RFC's "~300 sites" headline is looser than my verified 187+46; not load-bearing, but the RFC should cite the verifiable split.)

- **§11.8 completeness — one gap.** Every method symbol is taught, but `AriaAttributeName` is exported in `api_surface` yet never appears in any signature or example (only `AriaRole` and `AriaAttrs` do). That's an untaught public symbol — either internalize it or give it a one-line use.

## Does it survive?

**survives-with-changes.** The API *shape* is sound, in-idiom, and well-justified (187+46 verified sites), so default-reject is not warranted — it would be a bad cut to kill a 233-site ergonomics fix over text-level defects. But the killer objection is real and it lives where the dx lens has authority: the typed union, the kebab runtime, and the canonical README example contradict each other, so the RFC's headline misuse-resistance claim does not hold for the most common multi-word key (`hasPopup`→`aria-has-popup`), and the README actively teaches the broken form. That is an adoption failure, not a nitpick. It survives only because the fix is surgical — resolve the casing contract, fix README.md:1799, add one ✗ guideline line — with no API redesign. Alongside it the guideline edit also has a polarity bug (`disabled` ✗ with a buggy implied ✓ — the correct ✓ is `disabled: !isReady`), house-style fragments in the index, an undocumented `setTitle`/`Title()` collision in the index, and one untaught exported symbol (`AriaAttributeName`). Each folds back cleanly. Required changes are in frontmatter.

## Guardrail check (§11.8 guideline-sync — this lens owns it)

Fails as-written on three counts: (a) the topic-ref tristate example teaches a polarity bug, (b) the index block isn't copy-pasteable house style, (c) `AriaAttributeName` is exported but untaught — §11.8 requires every `api_surface` symbol be covered. With the five required changes applied, §11.8 is satisfied: index rule + topic-ref deep section, code-snippet-first, ✓/✗, LLM-reader-correct, every symbol taught.
