# Verdict: RFC-C-03 — breaking-change lens

> Adversary brief: KILL this RFC through the breaking-change failure mode. Hunt hidden breakage, mis-marked breaks, non-codemod-able behavioral changes. Default reject under uncertainty.

## Attack

I verified the RFC's premises against source: `tailwind-methods.ts:568` (`p.outline = outline-${value}`), `:576` (`p.gradientTo = bg-gradient-${direction}`), and the v3 type tables at `tailwind-types.ts:77,81,139,144,165,197,205` all match the RFC's "before" exactly. The recon is honest. The problem is in how the *fix* distributes breakage, and which breaks it declares benign.

- **breaking-change failure mode 1 — the "automatic, no migration" remap is the new silent break, and it is provably incomplete.** The RFC's own table (line 216) marks `shadow/rounded/blur scale → ✓ automatic (remapped to preserve v3 look) → none`. The remap is `{ "": "shadow-sm", sm: "shadow-xs", /* others 1:1 */ }` with fallback `?? \`shadow-${value}\`` (lines 123–126). **The `/* others 1:1 */` claim is false for a value the type still advertises:** `TailwindShadow` keeps `"inner"` (verified, `tailwind-types.ts`), but v4 renamed `shadow-inner` → `inset-shadow-sm`. So `.shadow("inner")` under target:v4 falls through to `shadow-${value}` and emits **`shadow-inner` — a dead class, no CSS, no error** — the exact F-C-001 failure the RFC's Problem section opens with, now inside the row labeled "no migration action." A consumer has every reason to call `.shadow("inner")` because the type permits it. Beyond enumerated values, the remap is also value-correct **only if the consumer uses Tailwind's stock scale.** fluent-html is a class-string generator with no knowledge of the installed `@theme`; an app that customizes its shadow ramp in `@theme` (a first-class TW4 workflow the RFC itself leans on in its escape-hatch note, line 205) gets `shadow-sm → shadow-xs` pointing at the *wrong custom slot* — silently, no type error, no lint flag, under a line promising zero migration. This is precisely the silent-render-wrong class the RFC condemns ("no type error, no build error — the page just renders wrong," line 20), reintroduced one abstraction down. The honest cases (`outline`, `ring`, `border`, `transition`) are ESLint-flagged; the *most* invisible cases (the auto-remaps) are marked as needing no attention. That inversion is the killer.

- **breaking-change failure mode 1b — the codemod introduces its own behavioral change.** Migration table line 217 marks `.outline("none")` → `.outlineHidden()` as an ESLint **autofix**. But `.outline("none")` is a legitimate call expressing real `outline-style:none`. A blanket `--fix` rewrites every occurrence to `outlineHidden()` (→ `outline-hidden`), silently flipping any intentional real-`none` site. A codemod that mutates sites it cannot prove are focus-suppression is itself an unbundled breaking change; it must be a flag, not an autofix. (The RFC's own line 202 calls `.outline("none")` "a semantic trap" — the argument for flagging it for a human, not auto-rewriting it.)

- **breaking-change failure mode 2 — `gradientRadial()/gradientConic()` are hidden no-ops under the default target.** Default target is `"v3"` (line 209) for all of v6.x (open question 3). The new `gradientRadial()`/`gradientConic()` are "(no-op-warns on v3)" per line 75, but the emit sketch (line 131) only shows the warn pattern for `outlineHidden`, not the gradient methods. A developer who adds `.gradientRadial()` in a v6 app that hasn't flipped the global target gets *no gradient and no diagnostic*. A new method that silently emits nothing in the default configuration is a breaking-shaped trap, not an additive win — and it isn't in the migration table at all.

- **breaking-change failure mode 3 — `setTailwindTarget` is a process-global mutable singleton, and the RFC under-weights the blast radius.** Open question 1 acknowledges the global assumption but frames it as a monorepo-only edge case. The sharper breaking-change risk is *within one app*: last-write-wins with no per-render guard means a single test that calls `setTailwindTarget("v4")` without resetting, or an import-order accident, leaks v4 vocabulary into every subsequent render in the process — including v3 renders that then emit `shadow-xs`/`bg-linear-*` and break. There is no freeze-after-first-render, no assertion. The guardrail §11.2 check ("a module var read") is correct about *cost* but blind to the *mutability hazard*.

- **breaking-change failure mode 4 — "ESLint-flagged" is sold as if it were "ESLint-enforced."** The migration table marks `ring`, `border`, `transition`, button-cursor as "✗ needs call change → ESLint flag." But flipping `setTailwindTarget("v4")` is a runtime act independent of whether the consumer runs lint. An app that flips the target and ships without a clean lint pass gets bare `.ring()` at 1px/currentColor (was 3px/blue) and bare `.border()` at currentColor (was gray-200) across 64+ sites in `ttl` — a silent visual regression. The break is real the instant the flag flips; the lint rule only *helps you find it*. The migration guide must say the flip is unsafe absent a clean lint pass, not imply the lint rule neutralizes the break.

## Does it survive?

It survives — **with changes.** The architecture is sound and genuinely defensible against the hard-major alternative: defaulting to `"v3"` means installing v6 breaks nothing (verified: 26 `.outline("none")` sites in `ttl`+`rideshare` keep working untouched until a deliberate flip), and bundling with RFC-C-01/02 honors guardrail §11.5's "one migration." The break is opt-in and staged, which is correct. The `outlineHidden()` dedicated method is the right call and is honestly marked.

What stops a clean `survives` is the **mis-classification of the auto-remap as migration-free**. The RFC's central value claim — "remap preserves your v3 appearance" — holds only for the default theme scale, but is stated unconditionally. That is a breaking change marketed as a non-event, and it is not codemod-able or even detectable by the tooling the RFC ships. Under the lens mandate (hidden breakage must be honestly marked and surfaced), this is a required correction, not a nitpick. The five required changes above fold the dishonestly-quiet breaks back into the visible migration surface without changing the architecture. With them, the breakage is honestly marked and bundled into one migration; without the first one in particular, this should not ship.
