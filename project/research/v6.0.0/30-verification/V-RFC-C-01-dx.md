# Verdict: RFC-C-01 — dx lens

> You are an ADVERSARY. Your job is to KILL this RFC through the dx lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The core repurpose (content-extractor callback → safelist emitter + plugin) is the right move and the surface is justified — v4 genuinely removed `content.extract`, fluent classes are genuinely invisible to Oxide, and the two apps genuinely cargo-culted divergent regexes. I cannot kill the *concept*. But the RFC ships with concrete DX defects that, left in, produce exactly the silent-failure and copy-paste-divergence pathologies it claims to fix.

- **dx failure mode 1 — the headline `onWarning` break is mislabeled as additive (the killer).** `ExtractorOptions` is not a new type; it exists today (`extractor/src/index.ts:11`) with `onWarning?: (message: string) => void`. The RFC's `ExtractorOptions` (lines 84-96) replaces that with `onWarning?: (info: { file?; method; argText }) => void`. This is a source-breaking signature change to a shipped public field, yet frontmatter says `breaking: additive` and the Migration section asserts "No existing symbol changes shape… The only addition is an *optional* second argument that already existed." That is false. Every consumer who passes `onWarning: (m) => console.warn(m)` gets a type error on upgrade. An RFC whose own type-safety story (a selling point) rests on a misstatement of its own breaking surface is a DX-honesty failure: the reader can't trust the compat table. Under default-reject this alone would justify rejection; I hold at survives-with-changes only because the fix is mechanical (rename the structured callback) and the rest of the design is sound.

- **dx failure mode 2 — the polymorphic `fluentHtmlPlugin` is a type lie (OQ1 shipped unresolved).** `fluentHtmlPlugin(options?): import('vite').Plugin` advertised as "also valid as a PostCSS plugin via the same factory" cannot be true: a Vite `Plugin` and a PostCSS plugin are structurally different objects. A dev reading the api_surface line `// @tailwindcss/vite + PostCSS` will drop the Vite-typed return into `postcss.config.js` and get a runtime failure with no compile signal — the precise hard-to-misuse criterion this lens enforces, violated. Open questions about the *exported shape of the primary API* are not "open questions," they are blockers; the RFC must commit before merge.

- **dx failure mode 3 — the guideline edits are written against text that doesn't exist.** §11.8 makes the guideline edit part of the deliverable, and the `dx` lens owns auditing it. The RFC quotes the `## Tailwind CSS` bullet as "Prefer literal fluent calls; when a token must come from a variable…" — but the real file (`CLAUDE.md:54`) says "Always use full class names." The proposed replacement therefore won't apply cleanly and misdescribes the current rule to whoever applies it. Likewise "after line 105" in fluent-html.md points at a single blockquote, not the structured block the example assumes. A guideline patch that misquotes its own target is an adoption failure by the algorithm's own §0.7 standard.

- **dx failure mode 4 — `onUnresolved`'s three-value union is undertaught, and `themeManifest` is imported as if it exists.** The guideline snippets show only `onUnresolved: "error"` and import `themeManifest` from RFC-C-02 (unmerged) in four places. An LLM reader copying the canonical example gets an unresolved import on day one and never learns when to pick `warn`/`silent`. §11.8 requires coverage of every api_surface symbol; `UnresolvedPolicy` and the `staticManifest`-omitted baseline are missing.

## Does it survive?

**survives-with-changes.** The naming is right (`generateFluentSafelist`, `extractDefaultClasses` mirror what apps hand-rolled; `target`/`onUnresolved` literal unions are greppable and type-safe; `defineX`/option-object idioms match the library voice). An app author would reach for `fluentHtmlPlugin` — one-line Vite wiring is strictly better than the cargo-culted `combinedExtractor`. Exporting the previously-internal `extractDefaultClasses` (confirmed non-exported at `extractor/src/index.ts:688`) directly retires the F-C-054 copy-paste. The surface is worth it.

But three of the six required changes are correctness-of-claim defects (the `onWarning` mislabel, the polymorphic-plugin type lie, the misquoted guideline targets) that would mislead an adopter, and the guideline edit — the adoption vehicle — is not yet applicable or complete. Per the lens mandate ("a great API with a missing or confusing guideline edit is an adoption failure → at least survives-with-changes"), it cannot pass clean. Fold the six changes back into the RFC and it ships.

## Guardrail check (§11.8 guideline-sync, owned by this lens)

Fails as written. The edit names both target files in `guideline_updates` (good) and attempts ✓/✗ house style (good), but: (a) it misquotes the existing `## Tailwind CSS` bullet, so the patch won't apply; (b) it undertaught the `UnresolvedPolicy` union (only `error` shown); (c) its canonical example imports an unmerged-dependency symbol, so the first copy fails. §11.8 requires every api_surface symbol taught with an applicable edit — not met until required changes 2, 5, and 6 land. The §11.5 backward-compat self-grade ("Pass. Additive") is also incorrect given the `onWarning` collision and must be corrected to additive-with-a-typed-break (required change 1).
