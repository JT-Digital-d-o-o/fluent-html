# Verdict: RFC-B-04 — breaking-change lens

> ADVERSARY brief: kill RFC-B-04 through hidden/under-marked breaking changes. Default to reject under uncertainty.

## Attack

The RFC stamps itself `breaking: additive` and devotes its compat section to proving "nothing breaks" because every new symbol is a new export and the two prototype methods are additions. That framing passes a *symbol-level* audit and fails a *system-level* one. The library does not ship alone — guardrail §11.7 names a three-package contract (lib + extractor + eslint) that shares the generated class vocabulary. I attacked the seams between them.

- **Breaking-change failure mode 1 — `.container()` silently breaks CSS generation under TW v4 (the killer).** Verified in `fluent-html-tailwind-extractor/src/index.ts`: the extractor resolves fluent methods to classes via a hardcoded `MethodPattern[]` keyed on `methodName` (`w`, `h`, `padding`, `margin`, `maxW`, …). It is the *only* mechanism that tells Tailwind which classes a fluent-method-built page uses — and Track-C recon (`03-tailwind4` B-1) flags TW v4's removal of `content.extract` as "existential," i.e. this extractor IS the content source. A brand-new `.container()` method emits `max-w-7xl mx-auto px-4 sm:px-6 lg:px-8` with **no string literal in source** and **no entry in `MethodPattern[]`**. The extractor doesn't recognize it, emits zero classes for it, and doesn't even warn (the `onWarning` path at line 727 fires only for *known* methods whose args are variables). Result: HTML references utilities Tailwind never compiles → the centered container renders unstyled in prod. That is a real, shipped-app-visible regression. The RFC's §11.7 self-check ("`.container()` reuses existing utilities … no new classes for Track-C tooling") is reasoning about the wrong layer: the utilities already existing is irrelevant when the *extractor keys on method names*. This breakage is not codemod-able and is not honestly marked.

- **Breaking-change failure mode 2 — `og` object silently narrows emitted markup.** The before/after worked example replaces ~12 `<meta>` lines (og:type, og:site_name, og:title, og:image*, twitter:card) with `og: { siteName, image }`. But `DocumentProps.og` defaults to `false`/none, and the object form's emission rules aren't specified beyond "fully typed." If the object doesn't auto-emit `og:type=website` and `twitter:card=summary_large_image`, the migration *drops* meta tags storysell ships today — a behavioral change to rendered output disguised as a clean refactor. Unspecified emission semantics on a "before→after" migration is a breaking-change smell.

- **Breaking-change failure mode 3 — `lang` precedence is ambiguous and can change rendered output.** Today: hardcoded `lang="en"` everywhere. The RFC says `Document()` "defaults `lang` from `createLayoutContext` if seeded, else `\"en\"`." If an app seeds a layout context (for `user`/`navCounts`, per F-B-035) the auto-read coupling could silently flip the `lang` attribute for SEO/SR. The intended fix (locale-aware lang) is good, but the *default behavior* of a no-arg `Document()` in a context-seeded app must be pinned, or adopters get a surprise attribute change.

- **Breaking-change failure mode 4 — eslint plugin half-addressed.** The §11.7 contract is three packages. The RFC names only the extractor whitelist for `htmx-indicator`. The eslint plugin (`fluent-html-eslint-plugin`, 20+ setClass-vocabulary rules) is the third party and is unmentioned for both `htmx-indicator` and `.container()`.

## Does it survive?

**survives-with-changes.** None of these are fatal to the *idea* — the API shape is sound, additive at the symbol level, and the failures are all in under-specified seams that fold back cleanly. But failure mode 1 is a genuine hidden breakage that the RFC mismarks; left as written, `.container()` ships broken under the very Tailwind version Track C is targeting. That is exactly the "breaking API sneaks in" guardrail-drift failure mode (§13). It survives only because the fix is mechanical and bundle-able: add the method to the extractor map in the same migration. The five required changes above are exact and fold into the RFC's Migration & §11.7 sections.

I withhold a full `reject` because the breakage is contained, locatable, and codemod-adjacent (a map entry, not an architectural flaw), and the RFC already half-flags the class-string contract — it under-scoped the flag rather than ignored it. Confidence 0.72: I'm highly confident in failure mode 1 (verified against extractor source); modes 2/3 depend on emission details the RFC left unspecified, which is itself the defect.

## Guardrail check (breaking-change owns §11.5 + the §11.7 seam)

- **§11.5 backward-compat:** the `breaking: additive` frontmatter is *symbol-accurate* but *system-inaccurate*. No removals, true; but a new class-emitting fluent method is a breaking change to the extractor's output contract until the extractor is updated in lockstep. Must be reclassified from a deferred Wave-4 flag to a same-migration dependency.
- **§11.7 class-string contract:** FAILED as self-assessed. The RFC marks `.htmxIndicator()` as needs-mitigation but marks `.container()` as pass — backwards. `htmx-indicator` is a static literal an extractor can whitelist; `.container()` is a dynamic method emission the extractor must learn. The harder case is the one marked pass.
