# Verdict: RFC-B-07 — dx lens

> Adversary brief: kill this RFC through the dx failure mode. Is it worth the surface area, discoverable, idiomatic, hard to misuse, correctly named, and fully taught?

## Attack

This RFC bundles four genuinely separable surfaces (render plugin, auth factory, error handlers, auth views) behind one `fluent-html/fastify` entry point. The *problem* is real and well-evidenced — 261 `request.user!`, 6-fork drift, returnTo silently dropped in 3 apps. The render-plugin and `requireUser`/`createAuthPlugin` core is the strongest part of the v6 backlog and I cannot kill it on value: an app author building app #7 absolutely reaches for `server.register(fastifyFluentHtml())` over re-copying a `decorateReply`. But there are concrete, shippable-as-written defects:

- **dx failure mode 1 — `requireRole` is a type-safety *regression* dressed as a fix.** The apps already ship `requireRole(role: UserRole)` (`rideshare/src/auth/auth.guards.ts:55`), a typed enum where `requireRole("ADMNI")` is a compile error. The RFC proposes `requireRole: (...roles: string[]) => FastifyPreHandler` — bare `string`. So the *single most consequential* call in an authz system (the one whose typo silently grants/denies admin) goes from compile-checked to stringly-typed. The const generic `TUser` threads the user type but knows nothing about roles. This directly violates the type-safety story the RFC sells (§11.4) and is the killer: a library API that is *less* safe than the copy-paste it replaces is a net DX loss on the exact axis the RFC claims to win. Easy fix (second const generic `TRole`), but it must land.

- **dx failure mode 2 — the Guidelines impact teaches 6 of 11 api_surface symbols; the missing one is the headline anti-pattern's partner.** §11.8 says every api_surface symbol must be taught or it's an orphaned API (the `Match` 18:1 failure). The edit covers `fastifyFluentHtml`, `renderView`, `renderStreamView`, `renderHx`, `createAuthPlugin`, `requireUser`, `registerErrorHandlers`, `AuthShell`, `OAuthButtons`. It *never shows* `signIn`/`signOut` — yet `reply.signIn(user)` after a credential check is the one line every single login controller must write, and `signOut()` every logout. An LLM reading these guidelines to build a login flow gets `requireUser`/`createAuthPlugin` but no taught path to *establish* the session. Also dropped: `ErrorPage` (rendered directly for custom error pages), `safeReturnTo` (the open-redirect guard, a security-relevant symbol apps reach for in OAuth callbacks), `requireRole`, and `DEFAULT_SKIP_PREFIXES`. A great API with an incomplete guideline is an adoption failure — exactly the §11.8 / §13 "orphaned API" trap.

- **dx failure mode 3 — the auth factory hides its hardest dependency; the "after" example won't run.** The shipped plugin opens with `fastify.register(cookie, { secret })` from `@fastify/cookie` (a real `dependencies` entry, rideshare/package.json:56) wrapped in `fastify-plugin` (package.json:75), and uses `reply.setCookie`/`request.unsignCookie`. `createAuthPlugin` *must* set/clear/unsign signed cookies — the entire returnTo+session story — yet it can neither import @fastify/cookie (§11.1 zero-deps) nor exposes a seam for the app to provide it. Worked example C's "after" (`server.register(auth.plugin)`) has no cookie registration and throws `reply.setCookie is not a function` at first sign-in. The library's "owns the wiring" claim collides with its own zero-deps guardrail. Compounding it: the default `cookieName: "__sid"` silently rotates the shipped `userId` cookie → every user logged out on deploy, a change the "Additive, nothing breaks" compat section denies.

- **dx failure mode 4 — hidden coupling between `requireUser` and `registerErrorHandlers`, left as an open question.** `requireUser` "throws a typed 401." But a thrown `Error & { statusCode: 401 }` only becomes a 401 *page* if `registerErrorHandlers` (or an equivalent handler) is installed; absent it, Fastify's default surfaces a 500/JSON. The RFC's own open question admits the error type is undecided. An app author who adopts `requireUser` incrementally (the RFC explicitly sells incremental adoption) but not yet `registerErrorHandlers` gets a worse failure than `request.user!`'s `undefined.id` (which at least 500s loudly with a stack). This cross-symbol contract must be stated, not deferred.

## Does it survive?

**survives-with-changes.** I tried to reject on "not worth the surface area" and failed — the evidence (6-fork drift, security fixes that must be applied 4–6×, the misteaching `fastify.md:94`) makes the render+auth core clearly worth it, and the API is idiomatic (variadic `renderView` mirrors core `render(...views)`; `renderHx(hxResponse(...))` collapses a verified 3-step; `.resolve()` route refs honored; no inline JS). Naming is right (`fastifyFluentHtml`, `requireUser`, `createAuthPlugin` read correctly and are discoverable from the entry point).

But it does **not** survive as written: the `requireRole` bare-string signature is a concrete type-safety regression against shipped app code, and the Guidelines impact — which the dx lens specifically owns — drops the one symbol (`signIn`) without which the auth story is unusable, plus four others. These are folded into the required_changes above and are mechanical, not architectural; none requires re-scoping the RFC. The auth-views slice (`AuthShell`/`OAuthButtons`) is the weakest-value member but the RFC's "moves with the OAuth `.resolve()` fix" justification in Alternatives is adequate; I do not require splitting it.

## Guideline-sync check (this lens owns §11.8)

FAIL as written → forces at least survives-with-changes. The edit is in house style (✓/✗, code-snippet-first, LLM-reader, succinct) and correctly targets `CLAUDE.md` index + `fastify.md` topic ref, and it does correct the two misteaching lines (`fastify.md:62` wiring gap, `fastify.md:94` `request.user!`). Verified those two lines exist exactly as cited. But coverage is incomplete: 6/11 api_surface symbols taught, with `signIn`/`signOut` (load-bearing) and `safeReturnTo` (security-relevant) among the omissions. The RFC's own §11.8 self-assessment claims "covers every api_surface symbol" — that claim is false and must be reconciled (either teach them or trim api_surface). The `renderView(view?: View)` → `renderView(...views: View[])` arity widening must also be made explicit as a *replacement* of the old `declare module` line, or apps double-augment.
