# shadow/rounded/blur scale-shift causes broad silent visual regressions on Tailwind v4

## Problem

In Tailwind v4 the shadow, blur, drop-shadow, backdrop-blur, and rounded scales shifted by one slot:

| v3 class | v4 class (same visual) |
|---|---|
| `shadow-sm` | `shadow-xs` |
| `shadow` (bare) | `shadow-sm` |
| `rounded-sm` | `rounded-xs` |
| `rounded` (bare) | `rounded-sm` |
| `blur-sm` | `blur-xs` |
| `blur` (bare) | `blur-sm` |

The same **class name still exists in v4** but now maps to a **different CSS value**. There is no compile error, no runtime error, and no linter warning — the visual simply changes across the entire app. `.shadow("sm")` emits `shadow-sm`, which on v3 was a subtle shadow; on v4 `shadow-sm` is visually identical to v3's bare `shadow` (medium shadow). Apps migrating to v4 will render every card, panel, and button with a heavier shadow than intended.

The type tables encode the v3 scale without the `xs` slot:

```ts
// fluent-html/src/core/tailwind-types.ts:77
export type TailwindRounded = "none" | "sm" | "md" | "lg" | "xl" | "2xl" | "3xl" | "full" | `[${string}]`;

// fluent-html/src/core/tailwind-types.ts:81
export type TailwindShadow = "sm" | "md" | "lg" | "xl" | "2xl" | "inner" | "none" | (string & {});

// fluent-html/src/core/tailwind-types.ts:205
export type TailwindBlur = "none" | "sm" | "md" | "lg" | "xl" | "2xl" | "3xl" | `[${string}]`;
```

None include `"xs"`, which is the correct v4 small variant. Users who want the v4 `xs` slot must fall back to `(string & {})` with no type safety.

The extractor mirrors this faithfully:

```ts
// fluent-html-tailwind-extractor/src/index.ts:265-270
{
  methodName: "rounded",
  generateClass: (args) => {
    if (args.length === 0) return ["rounded"];
    if (args.length === 1) return [`rounded-${args[0]}`];
    if (args.length === 2) return [`rounded-${args[0]}-${args[1]}`];
    return [];
  },
},

// fluent-html-tailwind-extractor/src/index.ts:288-290
{
  methodName: "shadow",
  generateClass: (args) => args.length === 0 ? ["shadow"] : [`shadow-${args[0]}`],
},

// fluent-html-tailwind-extractor/src/index.ts:414-416
{
  methodName: "blur",
  generateClass: (args) => args.length === 0 ? ["blur"] : [`blur-${args[0]}`],
},
```

## Evidence

The rideshare app uses `.shadow("sm")` and `.rounded("lg")` / `.rounded("xl")` extensively in its card/panel components:

```ts
// rideshare/src/settings/settings.view.ts:56-57
.rounded("xl")
.shadow("sm")

// rideshare/src/settings/settings.view.ts:78-79
.rounded("xl")
.shadow("sm")

// rideshare/src/settings/settings.view.ts:497
.shadow("sm")
```

Approximately 10 distinct call sites in rideshare alone. Any app upgraded to Tailwind v4 will see every `.shadow("sm")` become visually one step heavier, with no indication that anything is wrong.

## Why it matters

This is the nastiest category of v4 breakage: the **same method call produces a valid class name that resolves in v4 but to a different CSS value**. No error surfaces. Visual QA must catch it. Pervasive utilities (`rounded`, `shadow`) appear on nearly every UI element — cards, buttons, inputs, modals — so the regression is app-wide, not isolated.

## Rough idea (not a design)

The core question is whether to (a) silently remap v3 scale names to the v4 name that preserves the visual (`.shadow("sm")` → emit `shadow-xs` under the v4 target) so existing calls keep their appearance, or (b) emit the literal name and let users update their calls to match the new v4 scale. Option (a) is least-surprise for migrators; option (b) is transparent. Either requires a v3/v4 target flag threaded through all three packages (methods, extractor, ESLint map). Type tables must gain the `"xs"` slot under the v4 target, and the `no-known-modifiers-in-setclass` auto-fix must update shadow/rounded/blur suggestions.
