# `[${string}]` bracket escape-hatch types reject v4's CSS-variable paren syntax `(--var)`

## Problem

Tailwind v4 changed the arbitrary syntax for CSS variable references from square brackets to parentheses:

| v3 syntax | v4 syntax |
|---|---|
| `bg-[--brand]` | `bg-(--brand)` |
| `text-[--color-heading]` | `text-(--color-heading)` |
| `p-[--spacing-card]` | `p-(--spacing-card)` |

In v3 you could reference a CSS variable using the bracket arbitrary-value syntax (`[--var]`). In v4, the preferred form is parentheses (`(--var)`). Both syntaxes are understood by Tailwind v4, but the parenthesis form is the canonical one documented in v4.

fluent-html's type tables use `[${string}]` as the bracket-only escape hatch for arbitrary CSS values. The relevant types:

```ts
// fluent-html/src/core/tailwind-types.ts:65
export type TailwindTextSize = "xs" | "sm" | ... | `[${string}]`;
//                                                   ^^^^^^^^^^^^ rejects "(--heading-size)"

// fluent-html/src/core/tailwind-types.ts:77
export type TailwindRounded = "none" | "sm" | ... | `[${string}]`;
//                                                   ^^^^^^^^^^^^ rejects "(--radius-card)"

// fluent-html/src/core/tailwind-types.ts:84
export type TailwindBorderWidth = 0 | 2 | 4 | 8 | ... | `[${string}]`;

// fluent-html/src/core/tailwind-types.ts:91
export type TailwindOpacity = 0 | 5 | ... | `[${string}]`;
```

The comment in the file (lines 11–13) acknowledges only the bracket form:

```ts
// fluent-html/src/core/tailwind-types.ts:11-13
//   `[${string}]`   — bracket-only escape hatch for arbitrary CSS values.
//                      Stricter: forces explicit bracket syntax like "[13px]".
```

A user writing `.textSize("(--heading-size)")` or `.rounded("(--radius-sm)")` to use v4 CSS-variable tokens via the parenthesis syntax will get a TypeScript error even though the resulting Tailwind class (`text-(--heading-size)`, `rounded-(--radius-sm)`) is perfectly valid on v4. They must fall back to `addClass("text-(--heading-size)")` — bypassing the typed method entirely.

## Evidence

- `fluent-html/src/core/tailwind-types.ts:11` — comment explicitly says "bracket-only escape hatch"
- `fluent-html/src/core/tailwind-types.ts:65` — `TailwindTextSize` uses `[${string}]`
- `fluent-html/src/core/tailwind-types.ts:77` — `TailwindRounded` uses `[${string}]`
- `fluent-html/src/core/tailwind-types.ts:84` — `TailwindBorderWidth` uses `[${string}]`
- `fluent-html/src/core/tailwind-types.ts:91` — `TailwindOpacity` uses `[${string}]`

The recon doc (§2.2, minor m-2) notes: *"Escape-hatch types accept `[${string}]` brackets only; a user wanting `bg-(--brand)` can't express it via brackets. Minor type-table gap."* This finding confirms the concrete scope of that gap (multiple types affected, not just colors).

## Why it matters

This is lower pain than the renamed/removed classes — both syntaxes work in v4, so there is no runtime breakage. However, v4 docs and examples use the paren form extensively, especially when introducing `@theme` CSS-variable tokens. As apps adopt `@theme { --color-brand: oklch(...) }` for type-safe custom tokens, they will naturally try `.background("(--color-brand)")` and hit a type error. The (string & {}) color/spacing types are unaffected (they accept any string); the stricter `[${string}]` types are the problem.

## Rough idea (not a design)

Widen the bracket escape hatches to also accept parens: change `[${string}]` to `[${string}] | (${string})` — or simply `\`[\${string}]\` | \`(\${string})\`` — in every affected type alias. The change is purely additive (no existing valid values become invalid). Alternatively, relax to `\`[\${string}]\` | \`(\${string})\`` only in types where CSS-variable tokens are realistic (sizes, spacing, colors) and leave filter/transform types as bracket-only. Update the explanatory comment to document both forms.
