# ESLint `no-known-modifiers-in-setclass` map missing `bg-linear-` entry

## Problem

The ESLint auto-fix rule `no-known-modifiers-in-setclass` steers users away from raw `setClass("bg-gradient-to-r")` toward `.gradientTo("to-r")`. The `FIXABLE_PATTERNS` array (line 19) has an entry for the v3 class name `bg-gradient-` (line 384) but **no entry for the v4 class name `bg-linear-`**:

```ts
// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384
{ pattern: "bg-gradient-", methodName: "gradientTo" },
// "bg-linear-" is completely absent from FIXABLE_PATTERNS
```

On Tailwind v4, the class is `bg-linear-to-r` (not `bg-gradient-to-r`). A v4 user who writes `setClass("bg-linear-to-r")` — whether through muscle memory, copy-paste from v4 docs, or `@source inline()` in a CSS file — gets no ESLint warning and no auto-fix suggestion to use `.gradientTo("to-r")`.

## Evidence

The `FIXABLE_PATTERNS` array at line 19 drives the entire auto-fix map. The gradient block at line 383-387 only encodes the v3 prefix:

```ts
// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:383-387
// Gradients
{ pattern: "bg-gradient-", methodName: "gradientTo" },
{ pattern: "from-", methodName: "from" },
{ pattern: "via-", methodName: "via" },
{ pattern: "to-", methodName: "to" },
```

The companion method in the library (tailwind-methods.ts:576) still emits `bg-gradient-` on v3. Once F-C-001 lands (renaming the emitted prefix to `bg-linear-` on v4), the ESLint map must also be updated or the plugin will have zero guidance for v4 gradient class strings.

No entries exist for the new v4 gradient families either: `bg-radial-at-*` and `bg-conic-*`.

## Why it matters

The whole purpose of `no-known-modifiers-in-setclass` is to catch raw Tailwind strings and redirect users to fluent methods. On v4, the most commonly migrated utility (`bg-gradient-` → `bg-linear-`) becomes a blind spot: users writing raw v4 gradient strings lose the lint guidance that would steer them to type-safe fluent methods. This is a DX regression relative to v3 that silently widens after the v4 upgrade.

Frequency is low currently (v4 not yet adopted), but becomes medium the moment any project migrates — every `setClass("bg-linear-*")` usage is an unguided escape hatch.

## Rough idea (not a design)

Add `{ pattern: "bg-linear-", methodName: "gradientTo" }` to `FIXABLE_PATTERNS` immediately after the `bg-gradient-` entry. Keep both entries so the plugin handles v3 source during a migration period. Once `bg-radial-` and `bg-conic-` methods exist in the library, add their patterns too. This change is purely additive and can ship before the library itself is updated.
