# ESLint conflict-rule PREFIX_CONFLICTS list includes v3-removed utilities; auto-fix map has no v4 opacity-modifier suggestions

## Problem

The ESLint `no-conflicting-classes-in-setclass` rule maintains a `PREFIX_CONFLICTS` array encoding Tailwind utility prefix groups whose members conflict. Line 128 includes `backdrop-opacity-` — a utility family that was **removed entirely in Tailwind v4** (replaced by the color-modifier syntax `backdrop-{color}/{opacity}`). Keeping removed prefixes in the conflict list is not itself breaking, but it:

1. Flags a class like `backdrop-opacity-50` as a "conflict" rather than a "removed utility" — giving the user the wrong mental model.
2. Does not flag `backdrop-blur-` + `backdrop-opacity-` conflicts correctly for v4 (since `backdrop-opacity-` no longer exists, the relevant v4 conflict groups around `backdrop-{filter}` are different).

```ts
// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:128
"backdrop-blur-", "backdrop-brightness-", "backdrop-contrast-", "backdrop-grayscale-",
"backdrop-hue-rotate-", "backdrop-invert-", "backdrop-opacity-", "backdrop-saturate-", "backdrop-sepia-",
//                                                                ^^^^^^^^^^^^^^^^^^^ removed in v4
```

Additionally, the auto-fix map (`no-known-modifiers-in-setclass.ts`) encodes `bg-gradient-` → `gradientTo` (L384) but has no entries for the removed opacity utilities (`bg-opacity-*`, `text-opacity-*`, `border-opacity-*`, etc.). On v4 a user who writes `bg-opacity-50` in `setClass` gets no auto-fix suggestion at all — the rule stays silent — even though the correct v4 replacement is `bg-{color}/50` via color modifier syntax.

The `CONFLICT_GROUPS` array also has no entry for the new v4 gradient prefixes (`bg-linear-`, `bg-radial-`, `bg-conic-`) that conflict with each other. A user who accidentally writes both `bg-linear-to-r` and `bg-radial-at-center` will not be warned.

## Evidence

```ts
// no-conflicting-classes-in-setclass.ts:128 (PREFIX_CONFLICTS)
"backdrop-opacity-",   // v3-removed; should not appear as a live conflict prefix on v4
```

No evidence of `bg-opacity-*` in the auto-fix map (confirmed: grep returns zero hits for `bg-opacity` in `no-known-modifiers-in-setclass.ts`).

No `bg-linear-` / `bg-radial-` / `bg-conic-` entries in `CONFLICT_GROUPS` (L4-99).

## Why it matters

The ESLint plugin is the tooling surface apps interact with every day. Stale conflict groups produce misleading lint messages (wrong reason for the error). Missing auto-fix suggestions for removed utilities leave users without guidance when they hit a v4 upgrade. Missing new gradient conflict groups produce no lint warning when users accidentally combine incompatible gradient utilities.

Frequency is across all apps that use the ESLint plugin (both ttl and rideshare have it enabled).

## Rough idea (not a design)

Remove `backdrop-opacity-` from `PREFIX_CONFLICTS`. Add `bg-linear-`, `bg-radial-`, `bg-conic-` as a new CONFLICT_GROUP entry. Add comment-only notes (or a separate lint rule for v4) flagging `bg-opacity-*`, `text-opacity-*`, `border-opacity-*`, `ring-opacity-*`, `divide-opacity-*` as "removed in v4 — use color/opacity modifier" with no auto-fix (since the correct fix requires knowing the companion color class).
