# Unit-overloads partially adopted — `addClass('max-w-[Npx]')` / `addClass('min-h-[Nvh]')` used for arbitrary sizing values

## Problem

`fluent-html` provides unit-based overloads for all sizing and spacing methods (`w`, `h`, `minW`, `maxW`, `minH`, `maxH`, `padding`, `margin`, `gap`, `top`, `right`, `bottom`, `left`, `inset`). The overloads accept a unit string and a number and emit the correct Tailwind arbitrary-value class: `.maxW("px", 300)` → `max-w-[300px]`, `.minH("vh", 80)` → `min-h-[80vh]`.

Despite this, 15 call-sites across 5+ apps use `addClass("max-w-[300px]")` or `addClass("min-h-[80vh]")` in standalone single-class form — cases where the unit overload is a direct, zero-friction replacement. The same files often use fluent unit calls for `padding()` and `w()` on adjacent lines, proving that the developer is aware of the pattern but has not applied it to `maxW` and `minH`.

The root cause is that `guidelines/web-development/CLAUDE.md` shows only `w("px", 180)` and `minH("px", 180)` as examples, with a bare comment `// Methods: w, h, minW, maxW, minH, maxH, padding, margin, gap, top, right, bottom, left, inset`. `fluent-html.md` shows only `w("px", 180)` and `h("rem", 2.5)` — neither file demonstrates `maxW`, the viewport units (`vh`, `dvh`, `svh`, `lvh`), or shows a ✗ counterexample of `addClass("max-w-[300px]")` being the wrong form.

## Evidence

Clear standalone cases (the only class in the `addClass` call, directly replaceable):

```ts
// pokemon/src/shared/components/error.view.ts:31
Div(...).addClass("min-h-[80vh]")         // ✗ → .minH("vh", 80)

// idea-hub/src/ideas/ideas.view.ts:122
Div(...).addClass("min-h-[200px]")        // ✗ → .minH("px", 200)

// vabilo30/src/auth/auth.view.ts:156 (+3 more in same file)
Div(...).addClass("min-h-[80vh]")         // ✗ → .minH("vh", 80)

// storysell-ai/src/brand/brand.identity.view.ts:117
Div(...).addClass("max-w-[150px]")        // ✗ → .maxW("px", 150)

// jtdigital-landing-page/src/admin/views/analytics-wizard.ts:180
Div(...).padding("y", "2").padding("r", "3").addClass("max-w-[300px]")
// ✗ maxW: → .padding("y","2").padding("r","3").maxW("px", 300)
// Note: padding() is used correctly on the SAME chain, but maxW reverts to addClass
```

The correct forms:

```ts
// ✓ unit overloads — typed, no raw class string
Div(...).minH("vh", 80)
Div(...).minH("px", 200)
Div(...).maxW("px", 150)
Div(...).padding("y", "2").padding("r", "3").maxW("px", 300)
```

The guideline reference:

- `CLAUDE.md:127-132` — mentions `w` and `minH` in examples; lists all 13 methods in a comment but shows zero examples for `maxW`, `maxH`, or any viewport unit.
- `fluent-html.md:109-113` — shows only `w("px", 180)` and `h("rem", 2.5)`; no `maxW`, no `vh`/`dvh`, no ✗ counterexample.

## Why it matters

15 standalone violations confirm the pattern is not about "unavoidable mixed-class strings" — these are replaceable one-to-one. The "partial adoption" evidence (same file chains use `padding()` fluently but `maxW` via `addClass`) shows a knowledge gap about which methods have overloads, not a decision to use `addClass`.

The broader number is larger: 43 `addClass("max-w-[Npx]")` and 35 `addClass("min-h-[Npx]")` total, though most mix arbitrary values with other non-fluent classes in one string (an acceptable pattern; the setClass is needed for the other classes). The 15 standalone cases are the clean fix target.

## Rough idea (not a design)

Extend the arbitrary-value section in both `CLAUDE.md` and `fluent-html.md`:

```ts
// ✓ unit overloads — all sizing/spacing/position methods support them
Div().w("px", 180)          // → w-[180px]
Div().minH("vh", 80)        // → min-h-[80vh]    ← viewport unit
Div().maxW("px", 300)       // → max-w-[300px]
Div().padding("px", 12)     // → p-[12px]
// Units: px | rem | em | % | vh | vw | dvh | svh | lvh

// ✗ don't reach for addClass for standalone arbitrary sizing
.addClass("min-h-[80vh]")   // ✗ → .minH("vh", 80)
.addClass("max-w-[300px]")  // ✗ → .maxW("px", 300)
```
