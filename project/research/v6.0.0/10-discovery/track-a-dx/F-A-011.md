# Boolean typed setters in `_sk` render `attr="true"` / `attr="false"` — not idiomatic HTML boolean attributes

## Problem

Every typed subclass (`InputTag`, `ButtonTag`, `TextareaTag`, `SelectTag`, `VideoTag`, `AudioTag`, `ScriptTag`, `DetailsTag`, `DialogTag`, `IframeTag`, `TrackTag`, …) exposes `setDisabled(true)` / `setChecked(true)` / `setAsync(true)` / `setDefer(true)` / `setControls(true)` / `setMuted(true)` / `setLoop(true)` / `setOpen(true)` / `setAllowfullscreen(true)` / `setNomodule(true)` and stores the JS boolean in the `_sk`-backed field.

The render path at `render.ts:213` serializes every `_sk` field value with `String(value)`:

```ts
// fluent-html/src/render/render.ts:213
attrs += ' ' + sk[i]! + '="' + escapeAttr(typeof value === 'string' ? value : String(value)) + '"';
```

`String(true)` → `"true"`, so the output is `defer="true"` instead of the correct bare `defer`. Worse, `setDisabled(false)` produces `disabled="false"` — which **still disables the element in HTML** (any non-absent value of `disabled` is truthy; the only way to remove the attribute is absence). This is a real correctness bug, not just a style issue.

## Evidence

```ts
// fluent-html/test/elements.test.ts:488
it("Script external", () =>
  assert.strictEqual(
    render(Script().setSrc("app.js").setDefer()),
    `<script src="app.js" defer="true"></script>`,  // ✗ should be `defer`
  ));

// fluent-html/test/elements.test.ts:271
it("Video with controls", () =>
  assert.strictEqual(
    render(Video().setSrc("video.mp4").setControls().setWidth(640).setHeight(360)),
    `<video src="video.mp4" controls="true" width="640" height="360"></video>`,  // ✗
  ));

// fluent-html/test/elements.test.ts:292
`<video src="video.mp4" controls="true" autoplay="true" loop="true" muted="true" ...>`  // ✗
// fluent-html/test/elements.test.ts:315
`<track ... default="true">`   // ✗
// fluent-html/test/elements.test.ts:438
`<iframe ... allowfullscreen="true">` // ✗
```

The existing canonical path — `.toggle("disabled", cond)` — renders correctly as a bare `disabled`, because `toggles` are serialized as `tag.toggles.join(' ')` (no `=` at all). Two parallel mechanisms exist for setting boolean attributes, and the `_sk`-backed one is subtly wrong.

## Why it matters

- Any browser-consuming code that checks for `disabled="false"` as "not disabled" (e.g., form serializers, Playwright selectors) will be misled.
- The pattern `Input().setDisabled(false)` is a footgun: it looks conditional but has no effect.
- The test suite normalizes this incorrect output as expected, masking the bug.
- The idiomatic `.toggle("disabled", cond)` is the correct path, but typed subclasses offer both — the wrong one first, since `setDisabled` is a member completion suggestion.
- Frequency: every typed element with boolean attributes is affected — `ScriptTag`, `VideoTag`, `AudioTag`, `TrackTag`, `DetailsTag`, `DialogTag`, `IframeTag`, `InputTag`, `ButtonTag`, `TextareaTag`, `SelectTag`, `FieldsetTag`, `FormTag` — i.e., essentially all typed elements.

## Rough idea (not a design)

Option A: Fix the `_sk` render loop to detect `true` → emit bare attribute name; `false` → skip. This is backward-compat for `true` cases and a breaking fix for the `false` case (which was already broken, so acceptable in a major). Option B: Remove the `setBoolean()` typed setters entirely and let `.toggle(name, cond)` be the only boolean path — consistent with the documented idiom. Option A is less disruptive and can be done with a single `if` branch in `render.ts:213`.
