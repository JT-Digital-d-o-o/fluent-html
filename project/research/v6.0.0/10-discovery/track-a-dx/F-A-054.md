# `setAria()` accepts JS `boolean` but ARIA state attributes require string `"true" | "false" | "mixed"` — apps avoid the boolean path and manually write string literals

## Problem

`setAria(attrs: Record<string, string | boolean>)` accepts `boolean` values (they are coerced with `String(value)` — so `true` → `"true"`, `false` → `"false"`). However, apps uniformly avoid passing JS booleans and instead manually write `"true"` / `"false"` string literals — because:

1. ARIA state attributes have a tristate model in WAI-ARIA (`"true" | "false" | "mixed"` for `aria-checked`, `aria-expanded`). A JS boolean collapses this to two states and doesn't hint at the `"mixed"` option.
2. Some aria attributes are NOT boolean states — `aria-label`, `aria-labelledby`, `aria-describedby`, `aria-live`, etc. accept arbitrary strings, not booleans. The `boolean` type in the union looks applicable to all keys but only makes sense for a subset.
3. There is no documentation or type hint telling developers "pass `true`/`false` for state attributes."

## Evidence

```typescript
// glimm/src/shared/components/huluma/control.components.ts:99
.setAria({ checked: on ? "true" : "false", label: on ? "On" : "Off" });
//                  ^^^^^^^^^^^^^^^^^^^ manual ternary — could be boolean but isn't
```

```typescript
// planet-positive-sport/src/loc/events/views/event-overview/submit-button.component.ts:54
.setAria({ disabled: isReady ? "false" : "true" })
//                   ^^^^^^^^^^^^^^^^^^^^^^^^^^ inverted boolean → string manually
```

```typescript
// planet-positive-sport/src/shared/components/display/display.ts:262
return label ? el.setAria({ label }) : el.setAria({ hidden: "true" });
//                                                   ^^^^^^^^^^^^^^^ "true" as string, not boolean
```

The `setAria` implementation in `tag.ts:298-306`:
```typescript
setAria(attrs: Record<string, string | boolean>): this {
  ...
  this.attributes[`aria-${kebabKey}`] = String(value);  // boolean → "true"/"false"
}
```

The boolean coercion works but is invisible to consumers. There is no guideline or JSDoc example showing the boolean path.

## Why it matters

- The boolean path is there (`string | boolean`) but is de-facto unused by all app code.
- Apps write `on ? "true" : "false"` as boilerplate that could be `on` (a boolean), if the API made the intent clear.
- The API misleads: `{ aria-label: true }` would render `aria-label="true"` which is semantically wrong — the boolean path should only apply to state attributes.
- For `aria-checked` specifically, the tristate `"mixed"` value (for partially checked checkboxes / tree items) is unreachable through the boolean path.

## Rough idea

Two options:
1. **Narrowed types per key** (if F-A-053 adds typed keys): for known state keys, type their value as `boolean | "true" | "false" | "mixed"`; for non-state keys, type as `string`. Auto-convert `true`→`"true"`, `false`→`"false"` in the implementation.
2. **Separate `.setAriaState(key, value: boolean | "true" | "false" | "mixed")` method** alongside `setAria` for semantic clarity — `setAria` keeps the string-only object API, `setAriaState` handles binary/tristate.

Option 1 is cleaner if F-A-053 is implemented; option 2 is viable standalone.
