# `setToggles()` removed in v5.9.0 but 11 apps (186 call-sites) never migrated to `.toggle()`

## Problem

`setToggles(toggles?: string[])` was the pre-v5.9.0 API for adding boolean HTML attributes. In v5.9.0 it was removed as a breaking change and replaced by `.toggle(name, condition?)`:

```
# fluent-html/CHANGELOG.md:138
`setToggles()` has been replaced by `.toggle()`:
  Input().toggle("required").toggle("disabled")
  Input().toggle("required", isRequired)  // conditional
```

However, **no ESLint rule or codemod was provided** to assist migration. 11 apps pinned to pre-5.9.0 versions of the library (one as old as `lambda.html`, the pre-rename package) still use the removed API extensively.

## Evidence

**Confirmed dead API on the current library** — no `setToggles` anywhere in `fluent-html/src/**/*.ts`. The old v5.7.1 packages installed in apps still expose it:

```ts
// gzs/inovacije/node_modules/lambda.html/dist/src/core/tag.d.ts:31
setToggles(toggles?: string[]): this;
```

**186 call-sites across 11 apps** — sample patterns:

```ts
// gzs/inovacije/src/views/admin/admin-evaluation.view.ts:484
Option("—").setValue("").setToggles(["disabled", "selected"]),

// gzs/inovacije/src/views/admin/admin-helpers.view.ts:54
.setToggles(checked ? ["checked"] : undefined)

// gzs/inovacije/src/views/library/library.view.ts:288
.setToggles(currentPage === 1 ? ["disabled"] : undefined)

// pregled-nepremicnin-dashboard/src/views/components/ui.view.ts:160
.setToggles(selectedValue === opt.value ? ["selected"] : [])
```

**Apps affected**: buzzin, excel-gym-crm, filmplast-landing-page, gym-crm, gzs (inovacije), idea-hub, jt-chess, movies, pregled-nepremicnin-dashboard, tela, vabilo30.

These 11 apps cannot upgrade to v5.9.0+ without breaking (TypeScript compile error plus missing prototype method). The migration mapping is straightforward but tedious at 186 sites:

| Old | New |
|-----|-----|
| `.setToggles(["disabled"])` | `.toggle("disabled")` |
| `.setToggles(["a", "b"])` | `.toggle("a").toggle("b")` |
| `.setToggles(cond ? ["x"] : undefined)` | `.toggle("x", cond)` |
| `.setToggles(["a", "b", "c"])` | `.toggle("a").toggle("b").toggle("c")` |

## Why it matters

11 apps on outdated library versions miss all post-5.9.0 improvements (typed routes, required context, performance gains, strict types). The migration blocker is purely mechanical — there is no conceptual difficulty — but without tooling, 186 hand-edits are too high a friction to justify the upgrade.

This also reveals a process gap: prior breaking changes shipped without a paired ESLint codemod, leaving a long tail of frozen apps. Every future breaking change risks the same fate.

## Rough idea (not a design)

1. Add `no-set-toggles` auto-fix rule to `fluent-html-eslint-plugin`. Pattern: detect `.setToggles(expr)` call and rewrite based on argument shape.
2. Add a migration note in the guidelines (`web-development/fluent-html.md`) explaining the mapping.
3. Establish a policy: every breaking change in `fluent-html` ships with a paired ESLint auto-fix rule.
