# Pagination + sort: callers manually reconstruct full filter `vals` to preserve active filters

## Problem

When a table has both pagination and sortable columns (or inline filters), every page-change link and every sort-change link must carry the current values of all *other* parameters. There is no library primitive for this. Each view manually builds a `Record<string, string>` vals object by conditionally copying each active filter into it, then passes the whole thing into `setHtmx(route({ vals }))`. This 5–10 line block is repeated at every `renderPageLink` callback and every sort-header `buildHtmx` call in every app.

## Evidence

### glimm — two separate vals builders for the same table

```ts
// glimm/src/analytics/views/event-log.view.ts:65
// Sort HTMX builder — must forward active filter params
const buildSortHtmx = (vals: { sort: string; dir: SortDirection }) => {
  const extraVals: Record<string, string> = {};
  if (props.filters.event)    extraVals.event    = props.filters.event;
  if (props.filters.category) extraVals.category = props.filters.category;
  if (props.filters.userId)   extraVals.userId   = props.filters.userId;
  return analyticsRoutes.events({
    target: layoutIds.mainContent,
    swap: "outerMorph scroll:top",
    vals: { ...extraVals, sort: vals.sort, dir: vals.dir },
    pushUrl: true,
    indicator: layoutIds.globalLoading,
  });
};
```

```ts
// glimm/src/analytics/views/event-log.view.ts:169
// Pagination renderPageLink — must ALSO forward filter + sort params
renderPageLink: (page, label) => {
  const vals: Record<string, string> = { page: String(page) };
  if (props.filters.event)    vals.event    = props.filters.event;
  if (props.filters.category) vals.category = props.filters.category;
  if (props.filters.userId)   vals.userId   = props.filters.userId;
  if (props.filters.sort)     vals.sort     = props.filters.sort;
  if (props.filters.dir)      vals.dir      = props.filters.dir;
  return A(label)
    .setHtmx(analyticsRoutes.events({ target: layoutIds.mainContent, swap: "outerMorph scroll:top", vals, pushUrl: true, indicator: layoutIds.globalLoading }))
    .textColor("primary").textSize("sm").on("hover", t => t.underline()).cursor("pointer");
},
```

The same pattern appears in storysell and jt-cut for their event-log views with the same structure: one builder for sort, one builder for pagination, each manually copying the other's params.

### storysell-ai — identical pattern

```ts
// storysell-ai/src/analytics/views/event-log.view.ts:168
renderPageLink: (page, label) => {
  const vals: Record<string, string> = { page: String(page) };
  if (props.filters.event)    vals.event    = props.filters.event;
  if (props.filters.category) vals.category = props.filters.category;
  if (props.filters.userId)   vals.userId   = props.filters.userId;
  if (props.filters.sort)     vals.sort     = props.filters.sort;
  if (props.filters.dir)      vals.dir      = props.filters.dir;
  // ... same A(label).setHtmx(...) link
},
```

## Why it matters

This boilerplate appears in at least 4 apps, typically twice per paginated+sorted table (once for the sort builder, once for the pagination link builder). The risk is correctness: if a developer adds a new filter param to the query schema and forgets to add it to one of the two manual forwarding blocks, that filter silently resets on the next page turn or sort click. The code duplication is also a maintenance burden: glimm, storysell, and jt-cut have **identical** `event-log.view.ts` structures, and any change to the filter params must be applied in three separate repositories.

## Rough idea

A `TableState<T extends object>({ page, sort?, dir?, filters: T })` abstraction that: (1) serializes all active, non-empty fields into the `vals` object automatically; (2) is passed once to both `Pagination` and `SortHeader`-style columns so they can read from it and emit updated versions without manually copying each field. When integrated with `Pagination({ route, state, extraVals? })` and a typed `SortHeader({ field, state })`, the manual `Record<string, string>` builders disappear entirely.
