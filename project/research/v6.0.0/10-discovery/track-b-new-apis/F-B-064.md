# Gradient badges/highlights forced to use addClass("bg-gradient-to-r ...") because no gradient fluent method exists

## Problem

Several apps feature "highlight" badges, pricing cards, and CTA buttons with gradient backgrounds. These are a legitimate use of Tailwind's gradient utilities (`bg-gradient-to-{dir}`, `from-{color}`, `to-{color}`). However, fluent-html has no `.gradient()` method, so every gradient expression escapes to `addClass("bg-gradient-to-r from-brand-500 to-brand-600")`. This is the single most common multi-class `addClass` pattern in storysell-ai (the app with the highest `addClass` count at 327).

The problem is acute in the badge/alert angle because the "highlight badge" variant (e.g. "Most Popular", "Best Value" on pricing cards) is a distinct component class that every mature app independently invents, and its only styling mechanism is the string escape hatch.

## Evidence

storysell-ai `HighlightBadge` — forced to `addClass` for the gradient:
```ts
// storysell-ai/src/shared/components/brand/ui.brand.badges.ts:108-119
export function HighlightBadge({ label }: HighlightBadgeProps) {
  return Span(label)
    .display("inline-block")
    .padding("x", "3")
    .padding("y", "1")
    .textSize("xs")
    .fontWeight("bold")
    .textColor("white")
    .addClass("bg-gradient-to-r from-brand-500 to-brand-600")  // ← escape hatch
    .rounded("full")
    .shadow("sm");
}
```

The same gradient string appears 4 more times in storysell-ai for buttons and indicators:
```ts
// storysell-ai/src/shared/components/brand/ui.brand.indicators.ts:67
.addClass("bg-gradient-to-r from-brand-400 to-brand-500")

// storysell-ai/src/shared/components/brand/ui.brand.indicators.ts:128
.addClass("bg-gradient-to-br from-brand-400 to-brand-600")

// storysell-ai/src/shared/components/brand/ui.brand.buttons.ts:40
.addClass("bg-gradient-to-r from-brand-500 to-brand-600")

// storysell-ai/src/shared/components/organisms/ui.organisms.reports.ts:55
.addClass(`bg-gradient-to-br ${gradient}`)  // dynamic direction via template literal
```

jt-cut extracted gradient style-fns but the body still calls `.background("gradient-to-r")` combined with `.from()` / `.to()` — indicating partial gradient support exists in the fluent layer but the convenience method for the most common case is absent:
```ts
// jt-cut/src/shared/components/ui.components.ts:24-29
export const coralGradientR = <T extends Tag>(t: T): T =>
  t.background("gradient-to-r").from("coral").to("coral-orange") as T;

export const coralGradientBr = <T extends Tag>(t: T): T =>
  t.background("gradient-to-br").from("coral").to("coral-orange") as T;
```

The jt-cut evidence is particularly revealing: `.background("gradient-to-r").from(…).to(…)` already works via fluent calls, so the underlying vocab is there — but it requires 3 chained calls with non-obvious semantics. Apps that don't know the trick fall back to `addClass`.

## Why it matters

Gradient backgrounds are not a rare use case — they are standard in pricing highlights, CTA badges, and hero sections across every mature app in the fleet. The escape to `addClass` is a Tailwind v4 risk (purge must see the class strings in source) and a DX regression (breaks the "fluent methods only" discipline from CLAUDE.md). With ~8 `addClass` hits for gradient strings in storysell-ai alone and 2 helper fns in jt-cut, this is one of the top 3 `addClass` categories.

## Rough idea (not a design)

Add `.gradient(from, to, dir?)` convenience method on `Tag` that emits `bg-gradient-to-{dir} from-{from} to-{to}`. Direction defaults to `"r"` (left to right). Both `from` and `to` accept the same `TailwindColor` type as `.background()`. This collapses the 3-call jt-cut pattern and kills the `addClass` escape in storysell-ai's HighlightBadge and similar components.
