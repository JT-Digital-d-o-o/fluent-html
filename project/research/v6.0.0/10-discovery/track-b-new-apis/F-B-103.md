# Translation keys are bare `string` — typos silently return the key at runtime

## Problem

In the context-based i18n architecture (pps, projects-template), the `TranslationFn` signature is:

```ts
type TranslationFn = (key: string, params?: Record<string, string | number>) => string;
```

The `key` parameter is typed as `string`, meaning any string is accepted. When a key doesn't exist in the translation map, the function silently returns the key itself (the fallback behaviour). A typo in a view renders the raw key to the user (`"settings.delet.wraning"`) with no compile error and no runtime warning.

The pps codebase has ~2874 `t("...")` call sites. Any of those strings can silently drift from the actual JSON keys when keys are renamed or files are refactored.

## Evidence

```ts
// planet-positive-sport/src/core/i18n/i18n.ts:4
export type TranslationFn = (key: string, params?: Record<string, string | number>) => string;
```

```ts
// planet-positive-sport/src/core/i18n/i18n.ts:73-78 (fallback behavior)
return (key: string, params?: Record<string, string | number>): string => {
  const value = localeTranslations?.[key] ?? fallbackTranslations?.[key] ?? key;
  // ^^^^ silently returns `key` if not found
  if (params) return interpolate(value, params);
  return value;
};
```

Call sites in the controller pass translated strings as view props:

```ts
// planet-positive-sport/src/settings/settings.controller.ts:105
{ success: request.t("settings.success.profileUpdated") }
```

And view functions call the module-level `t()` directly:

```ts
// planet-positive-sport/src/settings/views/delete-account.view.ts:27
P(t("settings.delete.warning"))
```

In contrast, jt-cut's typed-object approach (`t.settings.delete.warning`) makes the same typo a compile error — but at the cost of prop-drilling (see F-B-102).

## Why it matters

With ~2874 `t("...")` calls in pps alone, key-drift is inevitable as translation files evolve. The silent fallback means regressions surface only in QA or production (when a user sees a raw key string), not during development. The fix (typed keys) is well-established in the TypeScript ecosystem (e.g. `i18next` + `i18next-resources-to-backend` generates `TFunction` with typed keys) and aligns with the library's "narrowest type by default" TypeScript guideline.

## Rough idea (not a design)

At server startup (or as a build step), flatten all locale JSON files into a union type:

```ts
// generated/translation-keys.d.ts
export type TranslationKey =
  | "settings.delete.title"
  | "settings.delete.warning"
  | "settings.success.profileUpdated"
  // ... (all keys from the en locale as the source of truth)
```

Then type the `TranslationFn`:

```ts
type TranslationFn = (key: TranslationKey, params?: Record<string, string | number>) => string;
```

A typo is now a compile error. The union can be generated by the `i18n.loader` at startup and written to a `.d.ts` file, or by a separate build script.
