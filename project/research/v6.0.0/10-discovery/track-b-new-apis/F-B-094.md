# Guidelines say "never inline JS; use .behavior()" but list no HTMX lifecycle behaviors, leaving devs no alternative to addAttribute for after:request/after:swap

## Problem

The CLAUDE.md guideline is unambiguous:

```
// guidelines/web-development/CLAUDE.md:201-208
**`.behavior()` for client-side interactions** — never raw inline JS:
Button("Toggle").behavior("toggle", { target: ids.filterPanel })
Button("Copy").behavior("clipboard", { value: apiKey })
Button("Submit").behavior("disable")
A("Back").behavior("back").cursor("pointer")
Built-in: `toggle`, `toggleClass`, `remove`, `clipboard`, `disable`, `focus`, `scrollTo`, `selectAll`, `back`.
```

But the list ends with DOM-interaction behaviors only. It says nothing about HTMX lifecycle events (`htmx:after:request`, `htmx:after:swap`, `htmx:before:request`, etc.) — the second most common use case for inline JS in these apps. When a dev needs to reset a form on successful submission, they cannot satisfy the "never raw inline JS" rule because no behavior covers HTMX events.

The result is that app code explicitly acknowledges the guideline conflict:

```ts
// planet-positive-sport/src/admin/emission-factors/emission-factors.utils.ts:78-80
// Client-side filter helpers — inline `hx-on:*` strings. Pattern mirrors
// Modal's `addAttribute("hx-on:click", ...)`. Kept here so the list view
// stays declarative.
```

```ts
// planet-positive-sport/src/admin/pre-approved-emails/views/pre-approved-emails.list.view.ts:101-107
// Morph preserves dirty input values across the redirect+swap, so a fresh
// value="" doesn't visually clear them. Reset the form when the request
// succeeds (HTTP < 300) so Email/Note clear after add but the user's input
// is preserved on a 422 (duplicate) re-render. htmx 4 alpha 7 syntax:
// `hx-on:<eventName>` (no `::` shorthand), event `htmx:after:request`,
// detail shape `{ctx: {response: {status, ...}, ...}}`.
.addAttribute("hx-on:htmx:after:request", "if (event.detail.ctx.response?.status < 300) this.reset()"),
```

The long explanatory comment shows the dev discovered the HTMX 4 API shape change independently. If there were a guideline-blessed behavior for this case, the explanation would be unnecessary.

The `htmx.md` reference file has no section on `.behavior()` at all — the entire behavior API is only documented in CLAUDE.md's index. `htmx.md` covers routes, ids, swaps, anchors, inheritance, and config — but not behaviors.

## Evidence

- `guidelines/web-development/CLAUDE.md:201-208` — the list of built-ins stops at DOM-click behaviors; no mention of lifecycle events
- `guidelines/web-development/htmx.md` — no mention of `.behavior()` anywhere (grep shows 0 hits for "behavior" except "behavior:" in a code comment about htmx 2)
- `planet-positive-sport/src/admin/pre-approved-emails/views/pre-approved-emails.list.view.ts:101-107` — 7-line explanatory comment forced by the gap
- `planet-positive-sport/src/admin/events/events.view.ts:358-363` — similar explanatory comment
- `planet-positive-sport/src/admin/emission-factors/emission-factors.utils.ts:78-80` — developer comment acknowledging the pattern mirrors the known anti-pattern
- Rideshare uses `hx-on:htmx:after:swap` instead of `after:request` — two apps using different lifecycle events for the same logical operation, suggesting no canonical guidance

## Why it matters

The guideline creates a rule with no viable alternative for a common case. Developers who follow the rule hit a dead end; developers who read the behavior list and don't see their use case fall back to `addAttribute`. The result is not just adoption-gap but active guideline confusion: the htmx.md reference never mentions `.behavior()` at all, so a dev reading that file has no reason to know the behavior system exists.

This is both a code gap (the behaviors don't exist) and a guideline gap (the teaching is incomplete). Even if the new behaviors are added (F-B-091, F-B-092), the guidelines need to be updated to show the before/after — otherwise apps won't adopt the new behaviors any more than they adopted the existing ones.

## Rough idea (not a design)

Two parallel fixes: (1) add the missing lifecycle behaviors to the code (`resetOnSuccess`, `openModal`, `closeModal` — see F-B-091 and F-B-092 for specifics); (2) update CLAUDE.md to list the new behaviors and add a ✗/✓ do-don't block for the form-reset case; update htmx.md with a "Behaviors" section that covers both DOM and lifecycle behaviors with examples, cross-referencing the index. The guideline fix is needed even before the code ships so devs know the direction.
