# No fluent-html Fastify plugin — `decorateReply("renderView")` copy-pasted verbatim into every app

## Problem

Every fluent-html app must hand-write the same `server.decorateReply("renderView", …)` call (and a matching TypeScript `declare module "fastify"` augmentation) before it can call `reply.renderView()`. There is no first-party Fastify integration plugin in the library. The result is verbatim copy-paste across the entire app fleet.

## Evidence

All six apps contain identical or near-identical blocks:

```ts
// rideshare/src/core/server.ts:86-91
server.decorateReply(
  "renderView",
  function (this: FastifyReply, ...views: View[]) {
    this.type("text/html").send(render(...views));
  }
);
```

```ts
// mngmt/src/core/server.ts:83-88  (identical)
server.decorateReply(
  "renderView",
  function (this: FastifyReply, ...views: View[]) {
    this.type("text/html").send(render(...views));
  }
);
```

```ts
// glimm/src/core/server.ts:115-120 / 122-127  (adds renderStreamView too)
server.decorateReply(
  "renderView",
  function (this: FastifyReply, ...views: View[]) {
    this.type("text/html").send(render(...views));
  }
);
server.decorateReply(
  "renderStreamView",
  function (this: FastifyReply, view: View) {
    this.type("text/html").send(renderToStream(view));
  }
);
```

Every app also contains a corresponding `declare module "fastify" { interface FastifyReply { renderView(...views: View[]): void } }` block (rideshare `server.ts:35-37`, mngmt `server.ts:~24`, pps `server.ts:~28`). This augmentation drifts between apps — mngmt omits `renderStreamView`, glimm and storysell add it. There is no single source of truth.

## Why it matters

Six active apps copy this code. Every new project must rediscover and re-copy it. The TypeScript augmentation drifts (some apps have `renderStreamView`, some don't). A future change to the rendering signature (e.g. adding async rendering) must be applied in 6+ places. This is the entry-point boilerplate for the entire library — arguably the most impactful place to provide a first-party helper.

The guideline (`fastify.md`) documents `reply.renderView()` as if it were a built-in, but doesn't explain how it is wired up — a new developer reading the guidelines would not know to add the `decorateReply` block.

## Rough idea (not a design)

A `fastifyFluentHtml` Fastify plugin (exported from `fluent-html/fastify` or a thin `fluent-html-fastify` package if the zero-deps guardrail requires separation) that:
- registers `reply.renderView(...views)` and `reply.renderStreamView(view)` via `decorateReply`
- exports the TypeScript module-augmentation types (import-side-effect pattern)
- optionally accepts a config for `setErrorHandler`/`setNotFoundHandler` hooks (see F-B-122)

Zero-deps guardrail risk: Fastify is a peer dep in apps, not in the library. The plugin could live in a `fluent-html/plugins/fastify.js` entry point that only imports from `fluent-html` itself and uses duck-typed Fastify APIs, keeping the library dep-free. Alternatively it ships as a separate `fluent-html-fastify` package under the monorepo.
