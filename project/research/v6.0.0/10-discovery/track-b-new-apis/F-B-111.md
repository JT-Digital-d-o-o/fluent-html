# `gradientTo()`/`from()`/`via()`/`to()` exist but are invisible

## Problem

fluent-html exports typed `gradientTo(direction)`, `from(color)`, `via(color)`, and `to(color)` methods on every `Tag` (declared in `fluent-html/src/core/tailwind-methods.ts:262-265`). Despite this, jt-cut never calls them. Instead it defines two helper apply-fns using `background("gradient-to-r")` — treating `"gradient-to-r"` as an argument to the *background* method — and other views in the same project hard-code the same workaround inline. storysell-ai falls back even further, using `addClass("bg-gradient-to-r from-brand-500 to-brand-600")` raw strings.

The existing finding F-B-064 characterises this as "no gradient fluent method exists." In fact the API exists; the problem is that the guidelines never show it with a code example, never contrast it with the wrong patterns, and the method name `gradientTo` (not `background(gradient)`) is non-obvious.

## Evidence

jt-cut defines helper apply-fns but uses the wrong call site:
```ts
// jt-cut/src/shared/components/ui.components.ts:24-29
export const coralGradientR = <T extends Tag>(t: T): T =>
  t.background("gradient-to-r").from("coral").to("coral-orange") as T;   // ← background() not gradientTo()

export const coralGradientBr = <T extends Tag>(t: T): T =>
  t.background("gradient-to-br").from("coral").to("coral-orange") as T;
```

Both helpers are used ~55 times across jt-cut. The same `background("gradient-to-br")` pattern appears inline in `v2.studio.view.ts:228`, `v2.export.view.ts:200`, `home.hero.view.ts:391`, `v2.style.view.ts:78`, and more.

In `jt-cut/src/auth/auth.view.ts:38-41`, two more gradient helpers are defined, duplicating the same workaround in a second module within the same app.

storysell-ai goes a step further with `addClass`:
```ts
// storysell-ai/src/shared/components/brand/ui.brand.badges.ts:116
.addClass("bg-gradient-to-r from-brand-500 to-brand-600")

// storysell-ai/src/shared/components/brand/ui.brand.indicators.ts:67
.addClass("bg-gradient-to-r from-brand-400 to-brand-500")
```

The correct pattern already exists and works:
```ts
// fluent-html/src/core/tailwind-methods.ts:262-265
gradientTo(direction: TailwindGradientDirection): this;
from(color: TailwindGradientStop): this;
via(color: TailwindGradientStop): this;
to(color: TailwindGradientStop): this;
// Usage:
Div().gradientTo("br").from("coral").to("coral-orange")  // ← never used in jt-cut
```

The guidelines mention gradients in a single dense sentence at line 107 of `fluent-html.md`:
> "gradients (`gradientTo`, `from`, `via`, `to`)"

There is no ✓/✗ example and no contrast with the workarounds.

## Why it matters

jt-cut has ~55 gradient call sites using the wrong or partial pattern. The `background("gradient-to-r")` form is technically functional but bypasses the typed `TailwindGradientDirection` parameter (passing a freeform string), losing compile-time safety. The `addClass` form breaks the Tailwind v4 extractor. storysell-ai alone has 4+ `addClass` gradient hits — these are the exact strings that will break under TW v4's new purge model (Track C). The fix is a guideline edit, not a code change.

## Rough idea (not a design)

Add a dedicated **Gradients** subsection to `guidelines/web-development/fluent-html.md` with ✓/✗ examples:

```ts
// ✓ fluent gradient chain
Div().gradientTo("br").from("coral").to("coral-orange")
Div().gradientTo("r").from("brand-500").via("brand-400").to("brand-300")

// ✗ background() does not accept gradient direction
Div().background("gradient-to-r").from("coral").to("coral-orange")

// ✗ addClass leaks raw strings (breaks TW v4 extractor)
Div().addClass("bg-gradient-to-r from-brand-500 to-brand-600")
```
