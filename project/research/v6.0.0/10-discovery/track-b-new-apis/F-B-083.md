# No built-in Tooltip component — implementations range from full accessible (200 LOC) to native `title=`

## Problem

There is no built-in `Tooltip` component. Apps deal with the gap in three wildly different ways:

1. **Full accessible implementation** (rideshare): CSS group modifiers + `behavior("toggleClass")` for mobile tap + `role="tooltip"` + `aria-describedby`. 200 LOC, 77 lines of component code. Works well but is far too much to write per app.
2. **Simpler but fragile hack** (jt-cut `InfoTooltip`): uses raw `addClass` with Tailwind arbitrary modifier strings (`group-hover/info:opacity-100`) and inline SVG via `Raw()` for the "ⓘ" icon. Ignores accessibility.
3. **Native `title=` attribute** (mngmt): `addAttribute("title", ...)` on the triggering element — zero JS, no hover styling, no mobile support.

The divergence means accessibility quality depends on which app you're in, and the only "correct" path requires 200 lines of app-level code for a primitive that every UI library ships.

## Evidence

**rideshare** — full accessible `Tooltip` component in shared:

```ts
// rideshare/src/shared/components/tooltip.view.ts:28-76
export function Tooltip({ id, label, content, side = "bottom", align = "right" }: TooltipProps): Tag {
  const bubble = Div(...contentItems)
    .setId(id)
    .addAttribute("role", "tooltip")       // ← correct ARIA role
    .opacity("0").pointerEvents("none")
    .on("group-hover", (t) => t.opacity("100"))
    .on("group-focus", (t) => t.opacity("100"));
  // position logic for top/bottom, left/right …
  return Div(...labelItems, bubble)
    .group()
    .position("relative").display("inline-block").cursor("help")
    .addAttribute("tabindex", "0")
    .setAria({ describedby: id.id })       // ← correct aria-describedby
    .behavior("toggleClass", { target: id, class: VISIBLE_CLASS }); // ← mobile tap
}
```

**jt-cut** — `InfoTooltip` using `addClass` escape-hatch for group-hover:

```ts
// jt-cut/src/shared/components/ui.components.ts:352-370
export function InfoTooltip(text: string) {
  return Span(
    Raw(`<svg class="w-3.5 h-3.5" …/>`),    // ← Raw() for icon
    Div(text)
      .opacity("0").addClass("invisible")
      .addClass("group-hover/info:opacity-100 group-hover/info:visible")  // ← addClass escape
      .transition("all").duration("200")
      .addClass("pointer-events-none").zIndex("10"),
  )
    .position("relative").addClass("group/info").cursor("help");  // ← named group via addClass
}
```

No `aria-describedby`, no keyboard-focus reveal, no mobile tap. 

**mngmt** — falls back to native `title` attribute (no hover styling at all):

```ts
// mngmt/src/assignments/assignments.components.ts:49
.addAttribute("title", userName);

// mngmt/src/changelog/changelog.view.ts:340
.addAttribute("title", entry.timestamp)
```

## Why it matters

Three different apps, three different quality levels. The rideshare implementation is correct but requires a developer to build it from scratch. The jt-cut approach needs `addClass` escape hatches because `.on()` doesn't support named groups (`group/info`). mngmt gives up on hover styling entirely. A single built-in `Tooltip` would raise the floor to the rideshare level across all apps — and the rideshare implementation itself points to missing fluent-html primitives: named groups (`group/{name}`) and an `addRole()` / `aria()` fluent helper are both needed to implement it idiomatically.

Note: the jt-cut `InfoTooltip` also uses `Raw()` for the inline SVG info icon — the icon-registry gap (F-B-020) independently contributes to this.

## Rough idea (not a design)

`Tooltip({ id, label, content, side?, align? })` built-in, matching rideshare's interface. Internally uses `.group()`, `.on("group-hover", ...)`, `.on("group-focus", ...)`, `behavior("toggleClass")`, and `.setAria({ describedby })`. No JS injected — pure CSS reveal for hover/focus with optional mobile-tap toggle via behavior. Requires the named-group modifier gap (Track-A or as a dependency of this RFC) to avoid `addClass("group/name")`.
