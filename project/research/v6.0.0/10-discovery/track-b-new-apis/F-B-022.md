# No built-in Drawer/slide-over component; pps rolled its own and no other app has one

## Problem

Planet-positive-sport needed a right-side slide-over panel (drawer) and built one in `src/shared/components/display/drawer.ts`. No other fluent-html app has a drawer, almost certainly because the effort of building the backing component + JS-string close/open helpers from scratch is high. The component mirrors `Modal` structurally but uses different CSS (absolute position on the right, no centering) and a different show/hide model (no `flex` dance — just `classList.add('hidden')`/`remove('hidden')`). Yet it also exposes `openDrawerExpr(id)` and `closeDrawerExpr(id)` string helpers for callers to embed in `addAttribute("hx-on:click", ...)`.

## Evidence

The pps `Drawer` is 76 LOC:

```ts
// planet-positive-sport/src/shared/components/display/drawer.ts:20-76
export function Drawer({ id, title, body, footer }: DrawerProps) {
  return Div(
    Div()
      .position("absolute")
      .inset("0")
      .addAttribute("hx-on:click", closeDrawerExpr(id)),
    ...
  )
    .setId(id)
    .position("fixed").inset("0")
    .background("[rgba(0,0,0,0.5)]").zIndex("50");
}

export function openDrawerExpr(id: string): string {
  return `document.getElementById('${id}').classList.remove('hidden');`;
}
export function closeDrawerExpr(id: string): string {
  return `document.getElementById('${id}').classList.add('hidden');`;
}
```

The `EmissionFactor` feature extends the pattern further: it uses the drawer body to host a confirm-delete sub-panel, toggling multiple inner elements with JS-string expressions built from a `setHiddenExpr` helper:

```ts
// planet-positive-sport/src/admin/emission-factors/emission-factors.utils.ts:236-239
function setHiddenExpr(idValue: string, hidden: boolean): string {
  const method = hidden ? "add" : "remove";
  return `document.getElementById('${idValue}').classList.${method}('hidden');`;
}

// lines 287-297
export const SHOW_DELETE_CONFIRM_EXPR =
  setHiddenExpr(ids.efDrawerForm.id, true) +
  setHiddenExpr(ids.efDrawerFooterEdit.id, true) +
  setHiddenExpr(ids.efDrawerConfirmDelete.id, false) +
  setHiddenExpr(ids.efDrawerFooterConfirm.id, false);
```

This is a second JS-string helper factory invented locally — a sign that the behavior system's `toggle` granularity is insufficient for multi-element drawer transitions.

## Why it matters

Drawers (slide-over panels) are a standard UX pattern used in admin interfaces and mobile-friendly layouts. The fact that only one app has one — despite all apps being admin-heavy — suggests the implementation cost is a barrier. A built-in `Drawer` paired with `Modal` would close that gap and prevent each new app from reimplementing the 76 LOC + JS-string helpers pattern.

## Rough idea (not a design)

A `Drawer({ id, title, body, footer, side?: "right" | "left" })` component ships alongside `Modal`. Add `behavior("openDrawer", { target: Id })` and `behavior("closeDrawer", { target: Id })` to `BehaviorMap`. Internal state uses only `hidden` (not the `hidden+flex` dance Modal uses), so the behavior is simpler — compatible with the existing `toggle` semantic but named semantically so the CSS mechanism can change.
