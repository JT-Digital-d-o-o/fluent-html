# Two incompatible i18n architectures co-exist with no library guidance

## Problem

Apps that need i18n have invented two structurally different approaches, each with distinct trade-offs. There is no library guidance on which to use, so each new app picks arbitrarily. The two approaches are not composable — a shared component written for one approach cannot be dropped into an app using the other.

**Architecture A — typed-object prop-drilling (jt-cut):**  
`request.t` is a `Translations` object (a deeply-typed TypeScript interface). Views receive it as a prop and access keys with dot notation: `t.auth.login.pageTitle`. Type safety is excellent (typos are compile errors), but `t` must be threaded through every component that needs a string.

**Architecture B — string-key context lookup (pps, projects-template):**  
`createContext<TranslationFn>` holds a `(key: string, params?) => string` function. Views import a module-level `t()` function that reads from the context — no prop drilling. But keys are bare strings; typos silently fall back to the key itself.

## Evidence

**jt-cut — Architecture A (typed object, prop-drilled):**

```ts
// jt-cut/src/i18n/types.ts:1-10 (excerpt — 251 LOC total)
export type Translations = {
  nav: { home: string; login: string; projects: string; ... };
  auth: { login: { pageTitle: string; cardTitle: string; emailLabel: string; ... }; ... };
  // ...
};
```

```ts
// jt-cut/src/home/home.view.ts:16,22,25,30,32
type HomePageProps = { ...; t: Translations; locale: SupportedLocale };
function HomePage({ user, t, locale, demo }: HomePageProps) {
  return Layout({ ..., children: [
    HeroSection({ t, locale, demo }),
    EarlyAccessSection({ t, locale }),
    BottomCtaSection({ t, locale }),
  ], t, locale });
}
```

```ts
// jt-cut/src/auth/auth.view.ts:221
function GoogleButton({ t, locale }: { t: Translations; locale: SupportedLocale }) { ... }
```

Every component that displays text must declare `t: Translations` in its props.

**pps / projects-template — Architecture B (string key, context):**

```ts
// planet-positive-sport/src/core/i18n/i18n.ts:8-11
export const i18nTranslation = createContext<TranslationFn>(fallbackT);
export const i18nLocale = createContext("en");
```

```ts
// planet-positive-sport/src/settings/views/delete-account.view.ts:15,27,45
import { t } from "../../core/i18n/i18n.js";
// ...
P(t("settings.delete.warning"))
return DangerCard({ title: t("settings.delete.title"), ... })
```

No prop drilling, but keys are bare strings. `t("settings.delet.wraning")` compiles and silently returns the key at runtime.

## Why it matters

A new app joining the fleet — or a developer extracting a shared component into a library — must choose one approach and cannot reuse components from the other approach without refactoring. The guideline says "use `createContext` for locale" but gives no concrete i18n pattern, so developers consult whichever existing app they look at first.

The trade-off is real: Architecture A catches typos at compile time but pays in prop-drilling verbosity (jt-cut threads `{ t, locale }` through at least 10 component boundaries in the home page alone). Architecture B is ergonomic but sacrifices key safety. A hybrid — typed keys extracted from the JSON files at build time — is possible but requires tooling no app has attempted.

## Rough idea (not a design)

Guidelines endorsement of Architecture B (context) as the standard for fluent-html apps — it is more consistent with the "context over prop-drilling" principle already in `fluent-html.md`. Add a code snippet showing the `t(key)` pattern and how to wire it via the Fastify plugin. Track the type-safety gap as a separate RFC (typed key extraction via `keyof FlatTranslations` at build time).
