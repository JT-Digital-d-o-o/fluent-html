# No official Fastify plugin — reply.renderView() and hxResponse integration re-implemented in every app

## Problem

`fluent-html` has no Fastify plugin. Every app that wants `reply.renderView(view)` — the idiomatic SSR reply method shown throughout `fastify.md` — must add the Fastify `decorateReply` call itself. The decorator is identical across all apps: render the view tree, set content-type to `text/html`, call `reply.send()`.

A second related gap: `hxResponse()` returns an `HxResponse` builder with `.trigger()`, `.pushUrl()` etc., but `reply.renderView()` only accepts a `View` — it cannot consume an `HxResponse`. So controllers that need to set HTMX response headers must call the 3-step `{ html, headers } = hxResponse(...).build(); reply.headers(headers); reply.renderView(html)` sequence. This sequence is copy-pasted verbatim in at least 4 apps (rideshare, mngmt, jt-cut, storysell).

## Evidence

**renderView decorator — copy-pasted verbatim in rideshare and mngmt (and likely jt-cut/storysell):**

```ts
// rideshare/src/core/server.ts:84   (identical in mngmt/src/core/server.ts:83)
server.decorateReply(
  "renderView",
  function (this: FastifyReply, ...views: View[]) {
    this.type("text/html").send(render(...views));
  }
);
```

**3-step hxResponse boilerplate — copy-pasted in rideshare, mngmt, jt-cut, storysell:**

```ts
// rideshare/src/files/files.controller.ts:62  (identical pattern in 3 other apps)
const { html, headers } = hxResponse(Empty())
  .trigger("showToast", { message: "File uploaded successfully" })
  .build();

reply.headers(headers);
return reply.renderView(html);
```

This 3-step pattern appears at least 8 times across 4 apps (2 in rideshare, 2 in mngmt, 2 in jt-cut, 2 in storysell — every app has a files controller with this exact shape).

## Why it matters

The ALREADY-SEEN list records `auth.plugin.ts` copy-pasted across 4 apps. The `renderView` decorator is a smaller but more universal boilerplate: **every** fluent-html + Fastify app needs it, whereas auth plugins are optional. The `hxResponse` 3-step is the only way to set HTMX headers with the current API — there is no `reply.renderHx(hxResponse)` or `reply.renderView(hxResponse(...).trigger(...))` overload. Apps can't avoid it.

Frequency: approx 6 active consumer apps all copy the same decorator. The `hxResponse.build()` pattern appears 8 times across 4 apps (not counting SVG path builders that also call `.build()`).

Pain: medium — it works correctly, but it is boilerplate the library should own.

## Rough idea (not a design)

Export a `createFluentHtmlPlugin()` (or `fluentHtmlPlugin`) from a `fluent-html/fastify` sub-path (zero runtime deps — just wraps the same `render()` call). The plugin registers:
- `reply.renderView(...views: View[]): void` — current idiom
- `reply.renderHx(response: HxResponse): void` — sets headers + renders in one call

This eliminates all `decorateReply` copy-paste and the `hxResponse.build()` 3-step.
