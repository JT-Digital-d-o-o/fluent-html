# foldView and paraView allocate a new intermediate array for every array-type child node, even when the algebra discards it

## Problem

`foldView` and `paraView` dispatch array-type View children with `.map()`, creating a fresh `A[]` intermediate array for every array node in the tree. The array is then passed to `alg.list(children)`, which may immediately discard it (e.g. `countAlgebra.list` reduces it to a single number; `textAlgebra.list` joins it to a string). The intermediate array exists solely to satisfy the call to `list()` and is GC pressure with no benefit.

The existing SEEN entry for `countAlgebra.list uses reduce with a closure` identifies the downstream waste; this finding is the upstream cause — the per-array-node allocation in `foldView` itself.

## Evidence

```ts
// src/fold/fold.ts:75
if (Array.isArray(view)) {
  const foldedItems = view.map(item => foldView(alg, item));  // ← always allocates new A[]
  return alg.list(foldedItems);
}
```

```ts
// src/fold/para.ts:63
if (Array.isArray(view)) {
  const foldedItems = view.map(item => paraView(alg, item));  // ← same pattern
  return alg.list(foldedItems);
}
```

```ts
// src/fold/algebras/count.ts:14
list: (counts) => counts.reduce((a, b) => a + b, 0),
// counts is a number[] that was just allocated to be immediately summed and discarded
```

For a realistic page (~200 tags), every array of sibling elements allocates an intermediate result-array. The recon bench confirms that `foldView count (realistic page)` runs at 25K ops/s — essentially the same throughput as `render()` at 23.6K ops/s, even though counting does no string work. The `.map()` allocation overhead accounts for most of this gap.

## Why it matters

Every fold traversal — count, text extraction, link collection, accessibility description — pays this per-array-node allocation. Pages with many sibling elements (long lists, tables with rows) are hit proportionally harder. With frequency = every `foldView`/`paraView` call on a multi-child view, this is the dominant allocation in the fold layer.

## Rough idea (not a design)

For the common single-value algebras (count, text, links), an alternative entry point `foldViewScalar` could iterate the array in-place with a loop and pass results to `list()` one at a time via a mutable accumulator pattern. Alternatively, the `ViewAlgebra` type could carry an optional `listAccum` method that receives items one by one and avoids the array entirely. The main `foldView` stays unchanged for backward compat; the fast path is opt-in.
