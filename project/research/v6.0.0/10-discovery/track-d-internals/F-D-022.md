# `withVariant` is not exception-safe: a throw inside `.on()/.at()` corrupts `_variantPrefix`

## Problem

`withVariant` mutates `tag._variantPrefix`, calls the user callback `fn`, then restores the original value:

```ts
// src/core/tailwind-methods.ts:86-91
function withVariant(tag: Tag, prefix: string, fn: (tag: Tag) => Tag): Tag {
  const outer = tag._variantPrefix;
  tag._variantPrefix = outer ? `${outer}:${prefix}` : prefix;
  fn(tag);             // ← if this throws, the restore below never runs
  tag._variantPrefix = outer;
  return tag;
}
```

If `fn(tag)` throws — for example, an invalid Tailwind class is constructed at runtime, or any method in the chain raises — `_variantPrefix` is left set to the variant prefix string rather than restored to its outer value (usually `null`). Because `Tag` instances are mutable and shared in the view tree, a partially-built tag that escapes with a non-null `_variantPrefix` will incorrectly prefix every subsequent `addClass` call with the leaked variant string. The error surfaces as silently-wrong rendered HTML, not a thrown exception.

## Evidence

The pattern used by both `p.on` and `p.at`:

```ts
// src/core/tailwind-methods.ts:326-331
p.on = function (state: string, fn: (tag: Tag) => Tag) {
  return withVariant(this, state, fn);
};

p.at = function (breakpoint: string, fn: (tag: Tag) => Tag) {
  return withVariant(this, breakpoint, fn);
};
```

A call like:

```ts
Button("Save")
  .on("hover", t => {
    t.background("blue-600");
    throw new Error("oops");   // any error inside the callback
  })
  .textColor("white")          // ← now prefixed with "hover:" if error was caught upstream
```

The standard JavaScript fix is a `try/finally`, which V8 optimizes well for the non-throwing (common) path.

## Why it matters

The bug is silent: the tag does not re-throw; it continues building with a corrupted `_variantPrefix`. Affected classes are rendered with the wrong (stale) variant prefix, producing incorrect CSS output like `hover:text-white` for a class that should be `text-white`. Since view construction errors are commonly caught at the request-handler level and a 500 response is returned, the *next* render in the same process is unaffected (the Tag is not reused across requests). However, if a Tag is reused across requests (e.g., a partially-constructed shared component), the bug becomes persistent and cross-request — a latent correctness hazard for any future static-subtree hoisting feature (seed opportunity #3).

## Rough idea (not a design)

Replace the bare call with `try/finally`:

```ts
function withVariant(tag: Tag, prefix: string, fn: (tag: Tag) => Tag): Tag {
  const outer = tag._variantPrefix;
  tag._variantPrefix = outer ? `${outer}:${prefix}` : prefix;
  try {
    fn(tag);
  } finally {
    tag._variantPrefix = outer;
  }
  return tag;
}
```

V8's try/finally has negligible overhead on the non-throwing path after JIT compilation.
