# 54 scattered `as any` casts for prototype writes — no typed helper

## Problem

The library must write to class prototypes at module-init time for two patterns: setting the `_t` type discriminant on `Tag` and `RawString`, and setting `_sk` (schema-key arrays) on every specialized element subclass. Both operations are genuinely unavoidable as prototype writes — but each is repeated as a raw `(Ctor.prototype as any).field = value` cast, scattered across 10+ files.

```ts
// src/core/tag.ts:314
(Tag.prototype as any)._t = 1;

// src/core/raw-string.ts:13
(RawString.prototype as any)._t = 2;

// src/core/behavior-methods.ts:91
(Tag.prototype as any).behavior = function (name: string, options?: Record<string, unknown>) { ... }

// src/elements/forms.ts:125
(InputTag.prototype as any)._sk = ['type', 'name', 'placeholder', 'value', ...];

// src/elements/forms.ts:234
(TextareaTag.prototype as any)._sk = ['name', 'placeholder', 'rows', ...];

// src/elements/forms.ts:288
(ButtonTag.prototype as any)._sk = ['type', 'name', 'value', 'disabled', ...];

// src/elements/data.ts:16
(TimeTag.prototype as any)._sk = ['datetime'];
```

Running `grep -rn "as any" src/ --include="*.ts"` counts **54 occurrences** — 51 of them are `_sk` assignments in `src/elements/*.ts`, 3 are in `src/core/`.

Each file suppresses the `@typescript-eslint/no-explicit-any` eslint rule with a comment (e.g. `// eslint-disable-next-line @typescript-eslint/no-explicit-any -- intentional prototype manipulation`). This means the rule fires only on accidental casts, not structural ones — acceptable only if the cast count is small and stable. 54 casts across 10 files, with more added each time a new element class is introduced, is large and growing.

## Why it matters

Every new element class silently introduces a new `as any`. The pattern is unguided: a contributor writing a new element subclass must know to write the cast, know the `_sk` naming convention, and know to match the field names to the actual setters. A typed helper both enforces the convention and eliminates the casts at the call sites.

The tri-typed `isRawContext: boolean | string` flag in `renderImpl` (`render.ts:184`) is a related quality issue: three distinct meanings on one `boolean | string` parameter, requiring every call site to remember the encoding convention.

## Rough idea (not a design)

```ts
// internal helper — one cast, used N times
function defineSchemaKeys<T extends Tag>(ctor: new (...args: never[]) => T, keys: readonly string[]): void {
  (ctor.prototype as Record<string, unknown>)['_sk'] = keys;
}

// call site — no cast, type-checked
defineSchemaKeys(InputTag, ['type', 'name', 'placeholder', 'value', ...] as const);
```

Similarly a `setDiscriminant(ctor, n)` for the `_t` writes. Replace the `boolean | string` raw-context flag with a small union type `type RawCtx = false | true | 'script' | 'style'` to make the dispatch self-documenting.
