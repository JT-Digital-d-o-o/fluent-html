# No static-subtree precompilation API — headers, footers, navs, and icon SVGs are re-rendered from Tag trees every request

## Problem

`render()` has no mechanism to short-circuit rendering for subtrees that are identical every request. Every call re-walks the entire Tag tree from root, re-allocates attribute strings, re-escapes every value, and re-joins children — even for a 200-tag static navigation bar or an SVG icon that never changes.

The bench pre-builds views at module level (simulating the SSR pattern where a component function returns a new tree on every request), then calls `render(flatPage)` / `render(realisticPage)` repeatedly — confirming that render cost is paid in full on every call, with no caching path:

```ts
// bench/render.ts:191-204
const flatPage = benchFlatPage();        // built once
printResult("Flat page (1000 divs)", measure("flat", () => render(flatPage), ITERATIONS));
// → 6.4K ops/sec, 0.156 ms/op even though the view tree never changes

const realisticPage = benchRealisticPage();
printResult("Realistic page (~200 tags)", measure("realistic", () => render(realisticPage), ITERATIONS));
// → 23.6K ops/sec, 0.043 ms/op
```

There is no `Frozen`/`Static`/`prerender` concept anywhere in the codebase:

```ts
// src/core/types.ts:6
export type View = Tag | string | RawString | View[];
// No CachedView, FrozenView, or PrerenderedView variant
```

```ts
// src/render/render.ts:33-35 — no short-circuit on any cache field
export function render(...views: View[]): string {
  return renderImpl(views.length === 1 ? views[0]! : views, false);
}
```

## Evidence

`benchRealisticPage()` (bench/render.ts:97-161) constructs a 200-tag page including a static header, nav (4 links), footer, and product grid. On an SSR server, the nav and footer are identical every request yet are rebuilt and re-rendered each time. At 23.6K ops/sec the render is already fast, but the static chrome accounts for roughly half the tag count. Precompiling just the header+footer would halve their render cost.

The memory bench shows construction allocates ~65 KB per realistic page render (bench/render.ts:232):

```ts
// bench/render.ts:231-232
measureMemory("Realistic page construction", () => benchRealisticPage(), 100);
// → ~65 KB heap / 100 iters ≈ 650 bytes per construction
```

If the static parts (header, nav, footer) were pre-compiled to a `RawString`, their construction + render cost would drop to zero after the first call — a memcpy of the cached string.

A `Frozen` wrapper integrates naturally at the existing dispatch point:

```ts
// src/render/render.ts:196 — where Tag is handled
if (isTag(view)) { ... }
// A FrozenView check would go here (or a new _t discriminant)
```

## Why it matters

Large SSR pages typically have 40-60% static chrome (nav, sidebar, footer, icon sprites). Re-rendering this chrome on every request is pure waste. At 1000 req/s, a 200-tag page re-renders 200,000 tags/sec that could be 1 cached-string copy each. The opportunity is proportional to the static-to-dynamic ratio of the page — which is high for typical apps.

No API workaround exists: users can manually call `Raw(render(myNav))` but this (a) bypasses fluent construction, (b) requires manual cache management, and (c) is not documented.

## Rough idea (not a design)

Add `Frozen(view: View): View` (or `Static`, `prerender`) that wraps a View in a sentinel that, on first `render()`, renders the subtree to a string and stores it as a `RawString`; subsequent renders return that cached `RawString` directly. The cache lives on the wrapper object (request-scope safety: the frozen object itself must not be mutated between requests). No new runtime dependency. `renderToStream` gets the same short-circuit.
