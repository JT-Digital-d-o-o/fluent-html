# renderToStream re-walks the entire view tree on every read() call — idempotency broken in paused-mode consumption

## Problem

The `Readable` created by `renderToStream` has no guard against `read()` being called more than once:

```ts
// src/render/stream.ts:112-118
export function renderToStream(view: View): Readable {
  return new Readable({
    read() {
      streamImpl(this, view, false);  // full tree walk — no guard
      this.push(null);               // EOF pushed every call
    },
  });
}
```

Node.js calls `read()` each time the consumer needs more data. In the current implementation the first `read()` call pushes the entire rendered output plus `null` (EOF), so subsequent `read()` calls from the internal machinery are effectively a no-op only because `push(null)` has already closed the stream. In practice, for the simple happy-path consumer (`stream.on('data', ...)` or `stream.pipe()`) this does not double-render.

However, in paused-mode consumption (`stream.read(n)` with a byte count, or piping to a slow writable with a tiny highWaterMark that hasn't triggered EOF yet), Node.js may call `read()` again before the stream has been marked ended. In that scenario `streamImpl` re-traverses the entire view tree and re-pushes all HTML chunks, producing **duplicate output**. The second `push(null)` then ends the stream — but only after the duplicate content is already in the buffer.

More critically, this is the correct architecture for real backpressure: `read()` should push _one unit of work_ and return, not the entire tree. The current design conflates "one unit" with "everything," making it structurally incompatible with demand-driven streaming.

## Evidence

```ts
// src/render/stream.ts:112-118 — no started/done flag, no generator state
export function renderToStream(view: View): Readable {
  return new Readable({
    read() {
      streamImpl(this, view, false);
      this.push(null);
    },
  });
}
```

Compare the Node.js documentation for `Readable._read()`: _"When data is available, put it into the read queue by calling `readable.push(chunk)`. If `push()` returns `false`, the stream should stop producing data. When `_read` is called again, it should resume pushing data."_ The current implementation never resumes; it always restarts.

The recon (`04-performance.md:§1.4`) acknowledges: _"The entire tree is walked synchronously inside one `read()` call — every chunk is `push`ed in one tick, then EOF. So this is not backpressure-aware streaming and not incremental: it materializes all chunks eagerly into the stream's internal buffer."_

## Why it matters

The `read()` re-entry bug is latent today because the eager-push pattern causes the stream to end on the first `read()` call in all common consumption patterns. But it is a correctness trap: any refactor that attempts to make `renderToStream` actually incremental (F-D-011) must add the started-guard or switch to a generator — if the guard is forgotten, incremental streaming will double-render in paused mode. Documenting it as a discrete finding ensures the RFC for backpressure streaming addresses it explicitly.

## Rough idea (not a design)

Add a `let started = false` closure variable in the `Readable` options object. `read()` checks `if (started) return; started = true;` before calling `streamImpl`. This is the minimum fix for the double-render bug. The proper fix (F-D-011) replaces the single-call body with a generator-driven incremental approach that naturally avoids re-entry because the generator maintains its own position in the tree.
