# renderImpl is unboundedly recursive — stack overflow at ~3468–3500 nesting depth

## Problem

`renderImpl` descends into child views by calling itself at every Tag and every array element. There is no iteration budget or trampoline — the call stack grows one frame per DOM depth. Measured binary search confirms `render(deep(3500))` raises `Maximum call stack size exceeded` while `render(deep(3468))` succeeds.

## Evidence

```ts
// src/render/render.ts:240
return '<' + el + attrs + '>' + renderImpl(tag.child, childCtx) + '</' + el + '>';

// src/render/render.ts:246-250 (array path)
if (len === 1) return renderImpl(view[0]!, isRawContext);
let result = renderImpl(view[0]!, isRawContext);
for (let i = 1; i < len; i++) {
  result += '\n' + renderImpl(view[i]!, isRawContext);  // still recursive
}
```

The two recursion points are:
1. Tag → `renderImpl(tag.child, childCtx)` at line 240 — one frame per nesting level.
2. Array → `renderImpl(view[i]!, isRawContext)` at line 250 — for sibling arrays the loop is iterative, but for a single-child array it also recurses at line 246.

The recon measured the precise threshold: between depth 3468 and 3500 `render()` throws. 1000-level nesting is safe; 5000 throws.

Real-world apps producing recursive comment threads, deeply nested menus, or programmatically generated trees (via `unfoldView`) can reach this limit. The fold layer (`foldView`, `paraView`, `hyloView`) shares the same unbounded-recursion profile.

## Why it matters

This is a **correctness** bug, not a perf concern. A single app rendering a comment thread with 3500+ ancestors silently crashes the process. The limit is not documented anywhere. No test catches it (the deepest bench tree is 100 levels; the deepest stream test is 4 levels).

## Rough idea (not a design)

Replace the recursive descent in `renderImpl` with an explicit work-stack: push `(view, isRawContext, continuation)` frames, iterating until the stack is empty. The recon identifies `render.ts:240,248-251` as the two mutation points; the mirror fix in `stream.ts:182,187-191` must be done simultaneously so both renderers share the same safe core.
