# extractAttrs duplicated verbatim in fold.ts and para.ts — allocation-heavy per node

## Problem

`extractAttrs` is defined identically in two files with zero diff:

```ts
// src/fold/fold.ts:9-27  (identical copy in src/fold/para.ts:9-26)
function extractAttrs(tag: Tag): TagAttrs {
  const attrs: TagAttrs = {
    id: tag.id,
    class: tag.class,
    style: tag.style,
    attributes: { ...tag.attributes },   // ← spreads the whole attributes map
    htmx: tag.htmx,
    toggles: tag.toggles,
  };

  for (const key of Object.keys(tag)) {   // ← iterates all own-enumerable keys
    if (!(key in attrs) && key !== '_t' && key !== 'el' && key !== 'child') {
      (attrs as Record<string, unknown>)[key] = (tag as unknown as Record<string, unknown>)[key];
    }
  }

  return attrs;
}
```

Every call to `foldView` or `paraView` on any `Tag` node creates a fresh `TagAttrs` object, spreads the attributes map (even the shared frozen `EMPTY_ATTRS` sentinel — the identity check happens in `render.ts` but not here), and iterates `Object.keys(tag)` to copy element-specific fields.

The recon benchmark confirms the cost: `foldView(countAlgebra, realisticPage)` at 25K ops/sec matches the throughput of `render(realisticPage)` at 23.6K — even though counting does nothing but add integers. The allocation in `extractAttrs` erases the algebra's no-work advantage.

## Why it matters

Two files drift: a bug fix or performance improvement to `extractAttrs` must be applied twice. Any new field added to `Tag` must be handled in two places. This is the exact scenario that produced the `renderAlgebra` drift (F-D-003) in the algebras layer.

For read-only algebras (count, text, links) the `TagAttrs` clone is wasted allocation — the algebra never mutates attrs, so passing the live `Tag` (or a read-only view of it) would be sufficient and allocation-free.

## Rough idea (not a design)

1. Move `extractAttrs` to `src/fold/shared.ts` and import it in both `fold.ts` and `para.ts`.
2. Add a fast path: if `tag.attributes === EMPTY_ATTRS`, skip the spread (reuse `EMPTY_ATTRS` in the result).
3. Consider a `ReadonlyTagAttrs` variant where `extractAttrs` returns the live `Tag` fields directly (no spread, no `Object.keys` loop) for algebras that declare themselves read-only. This matches the "pay-as-you-go" framing from the recon.
