# bench/render.ts pre-builds all view trees outside the measure loop — ops/sec numbers exclude construction cost, understating real per-request workload

## Problem

All ops/sec benchmarks in `bench/render.ts` build the view tree ONCE before calling `measure()`, then repeatedly call `render(prebuiltView)` inside the loop. In the real SSR workload, every request builds a new tree AND renders it. The bench therefore measures only the render half, reporting 6.4K ops/s for "Flat page (1000 divs)" when the real per-request throughput is lower.

This is a separate issue from "bench not wired into CI" (which is about catching regressions). This finding is about the bench measuring the wrong thing: it gives a systematically optimistic picture that drives poor prioritisation decisions.

## Evidence

```ts
// bench/render.ts:190-191
const flatPage = benchFlatPage();   // built once
printResult("Flat page (1000 divs)", measure("flat", () => render(flatPage), ITERATIONS));
//                                                       ^^^^^^^^^^^^^^^^^^^^
//          same pre-built object passed every iteration — construction cost excluded
```

All seven render benchmarks follow this pattern:
```ts
// bench/render.ts:193-209
const deepTree    = benchDeepTree(100);
const escapePage  = benchHeavyEscaping();
const htmxPage    = benchHtmxAttributes();
const realisticPage = benchRealisticPage();
const variantPage = benchVariantHeavy();
const largeForEach = benchLargeForEach();
// All are pre-built; measure() only sees render()
```

The recon's own memory table reveals the true cost:
```
// product/research/v6/00-recon/04-performance.md:77-81
Flat page construction (1000 divs)  → 14.5 KB heap / render
Flat page render       (1000 divs)  → 104  KB heap / render
```

Construction allocates 14.5 KB per request just to build the tree — a cost the 6.4K ops/s figure never sees. Because construction and render are both paid every SSR request, any investment in construction-allocation reduction (opportunity #4 in the recon) cannot be validated by the current bench.

The ONLY benchmarks that DO include construction are the memory measurements (lines 231-232):
```ts
measureMemory("Flat page construction (1000 divs)", () => benchFlatPage(), 100);  // ✓ includes construction
measureMemory("Flat page render (1000 divs)",        () => render(flatPage), 100); // ✗ render-only
```
These measure KB/iteration but not ops/sec, so throughput with construction included is unquantified.

## Why it matters

Decisions about whether to invest in construction-allocation reduction, lazy field initialisation, or monomorphic Tag shapes cannot be evidence-based because there is no benchmark measuring total per-request cost. An optimisation that cuts construction time by 30% and render time by 0% would appear as zero improvement in the current numbers. This actively misleads v6 prioritisation.

## Rough idea (not a design)

Add a `"Full request (build + render)"` variant for each scenario:
```ts
// proposed addition
printResult("Full request: flat page (1000 divs)",
  measure("full-flat", () => render(benchFlatPage()), ITERATIONS));
```
Rename the existing runs to `"Render-only: flat page (1000 divs)"` to preserve their signal as an isolated render-path measurement. Both numbers are useful; the problem is that only one exists today.
