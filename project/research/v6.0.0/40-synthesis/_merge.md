## 2. Single-owner assignments for contested infrastructure

Four "infrastructure spines" are touched by many RFCs. One owner is named; all others consume the owner's symbol and must not re-declare it.

### 2.1 The `render(...)` / `renderToStream(...)` signature spine — **owner: D-01 (shape) + D-04 (options)**
Six RFCs rewrite or overload the top-level render entry points. They MUST be serialized, not merged independently:
- **D-01** de-recurses `render`/`renderToStream`/the four fold drivers (behavior-identical) — the structural foundation.
- **D-03** dedups render+stream into one emitter (`emit`/`Sink`) — lands **on top of D-01**, never before.
- **D-02** adds true backpressure `renderToStream`/`renderToIterable` — **hard `depends_on` D-01** (its own breaking verdict makes this a blocking gate).
- **D-04** adds `render(view, opts)` / `RenderOptions.nonce` — the **options-object** owner.
- **B-08** adds `reply.renderView(view, opts)` / `Deferred()` — `Deferred` Part 3's streaming benefit is **gated on D-02**; until then `Deferred()` works under plain `renderView` (B-08-perf).
- **B-09** adds `render(opts, ...views)` / `renderView(view, { contexts })` — the **request-context** overload owner.

**Resolution:** exactly ONE options-bearing render overload. D-04 defines `RenderOptions` with `nonce`; B-09 extends the SAME `RenderOptions` with `contexts`. Neither ships a second `*WithNonce`-style sibling (D-04-dx cuts `renderToStreamWithNonce`; B-09 threads `nonce` through the shared `RenderOptions`). B-09 must NOT overload `render`/`renderToStream` on a polymorphic arg0 — it adds separate `renderWith(opts, …)`/`renderToStreamWith(opts, view)` so the zero-options path is byte-untouched (B-09-perf). The variadic `render(...views)` vs `render(opts, ...views)` is reconciled via B-09-breaking change #1 (single `render(view?: View|View[], opts?)` decorator shape).

### 2.2 The Tailwind target mechanism — **owner: C-03 (runtime switch) + C-01 (extractor) + C-05 (codegen source)**
`TailwindTarget`, `TW_TARGET`/`setTailwindTarget`, `ExtractorOptions.target`, and the ESLint `target` setting appear across **C-01, C-02, C-03, C-04, C-05, C-06, A-07, A-09, B-03, B-04**. Cycle and duplication resolved:
- **C-05** is the leaf: canonical `TailwindTarget` type + `classVocab` source of truth (`@fluent-html/class-vocab`). Everyone imports the type from here.
- **C-03** owns the runtime switch (`setTailwindTarget`/`getTailwindTarget`) and the renamed/remapped methods.
- **C-01** owns `ExtractorOptions` (incl. `.target`) and the safelist emitter. **C-02's `emitSafelistCss()` is dropped** in favor of C-01's `generateFluentSafelist` (C-02-dx #1). C-02 keeps the pipeline/config-migration + `CLASS_VOCAB`/`@theme` token-migration story only.
- **C-04** consumes the `target` type for rule options; does not re-declare it.
- **C-06's** extractor changes (`onPointerHover`/`containerQuery` scanning) fold into **C-01**'s extractor; its type-table regen is its own.
- **C-01↔C-02 cycle broken**: C-05 → C-03 → C-01; C-02 depends on C-03 for the target (C-02-dx #3).
- **Default target = `v3` day one** (additive/byte-identical); the `v4` flip is the bundled breaking migration owned by C-03 + the C-01..C-04 breaking-changes entries (C-02-bc #1, C-05-bc #5).

### 2.3 `BehaviorMap` + `escapeJs` — **owner: B-02 (BehaviorMap) + D-05 (escapeJs/validateAttributeKey)**
- `behavior('resetOnSuccess')` is declared by **A-08, B-01, and B-02**. **B-02 owns the `BehaviorMap` extension** (overlay/lifecycle cluster). B-01/A-08 reference it; both verdicts flag the triple-declaration. A-08's `formResetOnSwap`/`dismissOnEscape` live alongside B-02's set, never redefine `resetOnSuccess`.
- **`escapeJs` and `validateAttributeKey` have ONE hardened impl, owned by D-05.** A-08's `escapeJs fix`, B-02's `el()`/`escapeJs` hardening, A-G4's cross-ref, D-03's escaping all consume it. Per D-05-dx, both stay **internal** (not on the public barrel). The hardened charset (`\ ' " \n \r U+2028 U+2029`, `<`→`\x3C` only where a script sink is reachable) is pinned by D-05-security; A-08-security's objection that `\x3C` is dead on the `hx-on:*` attr path is reconciled by D-05 owning the single escaper and documenting per-sink scope.

### 2.4 The Fastify reply decorator — **owner: B-07**
`reply.renderView`, `renderHx`, `renderStreamView`, and the `FastifyReply`/`FastifyRequest` augmentations are touched by **B-07, B-08, B-09, A-05, A-G3, A-G5, D-04**. **B-07 owns the decorator + plugin.** B-08 extends `renderView` with `opts`, B-09 with `{ contexts }` — both extend B-07's single augmented signature (`renderView(view?, opts?): FastifyReply`), never re-augment. Per B-07/B-08/B-09 breaking verdicts: **the library MUST NOT ship a `declare module "fastify"` augmentation as a side-effect**; apps own their `user`/`renderView` augmentations (B-07-bc #1–#2, B-08-bc #1, B-09-bc #1). A-G3's `applyTo(reply)` and A-05/A-G5's context wiring are app-side helpers that consume, not redefine, the decorator.

## 3. Cross-track conflict list with resolutions

### C-1 — `Document()` / `DocumentTag` declared by BOTH A-06 and B-04
**Overlap:** identical `api_surface` symbols `Document()` + `DocumentTag`.
**Resolution:** **A-06 is MERGE-OWNER** (it owns the DOCTYPE-render branch + SEO head helpers — the lower-level concern). B-04 must drop its own `Document()`/`DocumentProps` declaration and build on A-06's `Document(...children): DocumentTag`. **A-06's variadic-children form is canonical; B-04's props-shell becomes `Shell(props)`/`Page(props)` layered on top.** Both must patch the same multi-render-path gap (render + stream + fold) — see C-7.

### C-2 — `createLayoutContext()` (B-04) vs `createRequiredContext` (A-05) vs context bridge (B-09)
**Overlap:** B-04's `createLayoutContext<T>` is admitted (B-04-dx #3) to be a thin alias for `createRequiredContext`.
**Resolution:** **drop `createLayoutContext`**; B-04 teaches `createRequiredContext` (A-05) directly; per-request seeding uses B-09's `seedContext`/`renderView({contexts})`. A-05 owns context lifecycle; B-09 owns the request-scoped bridge.

### C-3 — `setAria` / `AriaAttrs` / ARIA types declared by BOTH A-02 and A-G2
**Overlap:** both declare `Tag.prototype.setAria(attrs: AriaAttrs)` + `AriaAttrs`.
**Resolution:** **A-02 is MERGE-OWNER** of `setAria`/`AriaAttrs`/`AriaRole`/`AriaAttributeName`. **A-G2 FOLDS its `setAria` type INTO A-02** and retains only the `addAttribute` retirement teaching, `setDataAttrs` key-validation, and the `prefer-set-method` eslint extension. Both converge on the SAME fix: the `AriaAttrs` key type is a **closed** union (drop the `(string & {})` key hatch; use a template-literal `aria-${string}` escape arm) so `setAria({ lable })` is a compile error (A-02-ts #1, A-G2-ts #1). A-02 also owns `setAria` key-validation (`validateAttributeKey` on the derived `aria-*` key).

### C-4 — `HxResponse.applyTo(reply)` declared by BOTH A-G3 and B-08
**Overlap:** identical `HxResponse.prototype.applyTo` + `HxReplyLike`.
**Resolution:** **B-08 is MERGE-OWNER** (broader `renderView(opts)` + HTMX-response surface). **A-G3 consumes B-08's `applyTo`** and contributes the discoverability teaching + the `depends_on A-03` note. Both require the SAME hardening: `applyTo` does NOT call the app's `renderView` decorator (document the bypass; recommend `getHeaders()`+`renderView` when the host decorates), and `applyTo` CRLF-validates header values (A-G3-sec, B-08-sec).

### C-5 — Track-A `setCrossorigin` rename collides with Track-C eslint `prefer-set-method` map
**Overlap (Track-A rename vs Track-C tooling):** A-03 renames `setCrossorigin`→`setCrossOrigin` / `setReferrerpolicy`→`setReferrerPolicy` and adds the bare `setCrossorigin("")` overload. The eslint `prefer-set-method` autofix map targets the OLD lowercase names — so the autofix would emit a now-nonexistent method (A-03-corr #2–#3).
**Resolution:** **A-03 is MERGE-OWNER** of the rename + bare-crossorigin overload. The eslint map update is a **lockstep Track-C deliverable bundled with A-03** (reconciled inside the C-04/C-05 eslint regen). A-03 must ALSO rename Img (`ImgTag.setCrossorigin`) and Anchor (`AnchorTag.setReferrerpolicy`), not just Link/Script/Iframe, or the eslint map fixes to a method that doesn't exist on those elements.

### C-6 — Track-A `.translate()`/`.rotate()`/`.neg()`/`Overlay` emit classes the Track-C extractor+eslint can't see
**Overlap (Track-A new vocabulary vs Track-C extractor/eslint) — the largest cross-track conflict, spanning A-07, A-09, B-03, B-04:**
- **A-07** relocates the negative sign (`translate-y--1`→`-translate-y-1`) and adds 11 zero-arg display/position shortcuts + `.neg()`. The extractor has NO handler; the eslint patterns don't match negative forms. A-07 falsely claims "no Track-C change" (A-07-bc #1–#3).
- **A-09** rewrites `Overlay` to emit classes (`relative`, `-translate-x-1/2`, `top-1/2`) instead of inline styles; fractional translate/inset vocab is unverified (A-09-bc #5, A-09-corr #4).
- **B-03** `.gradient()` emits v4 `bg-linear-to-*` + status-palette classes net-new to the extractor (B-03-bc #3).
- **B-04** `.container()` and `htmx-indicator` break the extractor's method-name allowlist (B-04-bc #1, #5).
**Resolution:** every NEW class-emitting fluent method is a **hard dependency on the Track-C extractor + eslint vocab landing in the SAME milestone**, not a Wave-4 "confirm later". The shared `@fluent-html/class-vocab` codegen (**C-05**) is the single source the lib, extractor, and eslint consume — so A-07/A-09/B-03/B-04's new utilities are added as `UtilityDef` rows in C-05's vocab, auto-propagating to extractor (C-01) + eslint (C-04). A-07 must also widen `TailwindRotate`/`TailwindSkew` to admit negative literals (`.rotate("-45")` is a compile error today — the core fix is otherwise dead code; A-07-ts #1). **Sequencing: C-05 vocab rows → A-07/A-09/B-03/B-04 methods; day-one default `v3` keeps output byte-identical.**

### C-7 — Multi-render-path divergence (render.ts / stream.ts / fold/algebras/render.ts) hit by many RFCs
**Overlap (shared internal surface):** **A-01, A-02, A-03, A-06, B-05, D-01, D-03, D-04, D-05, D-06, D-07** each touch attribute/doctype/nonce serialization, and EACH verdict independently discovered the codebase has **three+ emit paths** (`render.ts`, `stream.ts`, `fold/algebras/render.ts` via `extractAttrs` in `fold.ts`/`para.ts`) — and that RFCs frequently patch only one or two. The fold path renders attrs **generically by JS key** (not via `_sk`), so `_sk`-order/tuple fixes are invisible there unless `extractAttrs` learns the prop→attr mapping.
**Resolution:** **D-03 is MERGE-OWNER of emitter unification** — it dedups render+stream into one `emit`/`Sink` and makes `renderAlgebra` a thin wrapper, the structural fix that makes "patch one path" correct. **All attribute/serialization RFCs (A-01, A-02, A-03, A-06, B-05, D-04, D-06) land their per-attribute logic INTO D-03's single emitter, or ship a three-path parity test** asserting byte-identical output across `render`, `stream`, and `foldView(renderAlgebra)` (every one of those verdicts requires this exact test). D-03 must preserve `_sk` ordering through `TagAttrs` (D-03-ts #2) or "byte-identical" claims fail. **Sequencing: D-01 (de-recursion) → D-03 (dedup) → attribute RFCs fold in.**

### C-8 — `escapeAttr` semantic narrowing (D-06) vs the three emitters (D-03/D-05)
**Overlap:** D-06 narrows `escapeAttr` to stop escaping `>`/`'`/`<` (inert inside double-quoted attrs) for a fast path; D-03/D-05 route attrs through `escapeAttr`.
**Resolution:** introduce the fast path under a **new internal name** (`escapeQuotedAttr`) used only by render.ts/stream.ts/fold-render, keeping public `escapeAttr === escapeHtml` additive (D-06-bc #3). The `<`-handling open question resolves BEFORE merge (D-06-corr #3). All three serializers stay byte-identical (D-06-bc #4) — folds into C-7's parity test.

### C-9 — `Overlay` variadic rewrite (A-09) vs `Overlay` variadic (D-07)
**Overlap:** both A-09 and D-07 list "variadic Overlay" in `api_surface`.
**Resolution:** **single rewrite, owned by A-09** (it owns the type-only-exports + Overlay change). D-07's "variadic Overlay" is the SAME change — dedup to one. The class-output change (inline-style → Tailwind classes) is reclassified `breaking` (A-09-bc #1) and depends on C-6's vocab confirmation for `-translate-x-1/2`/`top-1/2`.

### C-10 — `Frozen()` (D-01) vs nonce (D-04) vs fold drivers (D-03/D-05)
**Overlap:** `Frozen()`'s opaque cached string is invisible to `applyNonce` (D-04), to fold analysis algebras (D-05), and renders in the wrong escape context for script/style.
**Resolution:** D-01 owns `Frozen`; per D-01-security/type, `applyNonce` (D-04) + fold drivers must throw on a `FrozenView` containing script/style or descend into `node.view`. The `frozen` algebra arm is added to the public `ViewAlgebra`/`ParaAlgebra` interfaces (D-01-bc #1, reclassified `breaking`). Sequencing: D-01 lands the work-stack + `Frozen`; D-04's nonce single-pass consumes it.

### C-11 — `gradientTo`/`bg-gradient` vs `.gradient()`/`bg-linear` fork (B-03 vs C-03 vs C-04)
**Overlap:** existing `gradientTo()` emits v3 `bg-gradient-*`; B-03's `.gradient()` emits v4 `bg-linear-to-*`; C-03 owns the target-aware gradient methods; C-04's eslint gradient-conflict rule must recognize all four engine prefixes.
**Resolution:** **C-03 owns the target-aware gradient emit** (`gradientTo`/`gradientRadial`/`gradientConic` → `bg-gradient-*` on v3, `bg-linear-*`/`bg-radial-*`/`bg-conic-*` on v4). **B-03's `.gradient()` defers to C-03's target** (B-03-bc #2 adds the `depends_on` + target-aware emit). C-04's eslint gradient conflict group keys all four prefixes to ONE shared key and excludes `from-`/`via-`/`to-` color stops (C-04-corr #3–#4). The guideline teaches ONE gradient idiom (see G-3).
