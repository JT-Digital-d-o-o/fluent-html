# The C-02 union-closure skipped the sizing family

## Problem
C-02 (documented in the header of `tailwind-types.ts`) closed the five themeable
families (colors, spacing, fontSize, radius, shadow) by removing `(string & {})`
so that a typo like `.background("brnad")` becomes a compile error. The same
reasoning applies verbatim to the **sizing** family — but those six types were
left open:

```ts
// src/core/tailwind-types.ts:39-64
export type TailwindWidth =
  | TailwindSpacing | "auto" | "full" | "screen" | ... | "11/12"
  | (string & {});                 // ← re-opens what TailwindSpacing closed

export type TailwindHeight   = | TailwindSpacing | ... | (string & {});
export type TailwindMaxWidth = | "0" | "none" | "xs" | ... | (string & {});
export type TailwindMinWidth = "0" | "full" | "min" | "max" | "fit" | (string & {});
export type TailwindMaxHeight= TailwindSpacing | ... | (string & {});
export type TailwindMinHeight= "0" | "full" | ... | (string & {});
```

Unlike the genuinely-JIT scales (`TailwindGridCols`, `TailwindColSpan`,
`TailwindDuration`, `TailwindRingWidth`, `TailwindScale` — whose comments justify
the open tail for "JIT bare numbers beyond 12"), the sizing family has **no such
justification and two redundant escape routes already**:

1. `TailwindWidth`/`Height`/`MaxHeight` embed `TailwindSpacing`, which carries the
   `` `[${string}]` `` arbitrary arm — so `.w("[37px]")` already type-checks.
2. Every sizing method ships a second `(unit, amount)` overload
   (`tailwind-methods.ts:141-151`) — `.minH("px", 180)` → `min-h-[180px]`.

So the open tail buys nothing except silent typos. `.w("brnad")` compiles, and the
runtime faithfully emits a dead class:

```ts
// src/core/tailwind-methods.ts:404-406 (representative; minW shown at :415)
p.w = function (unitOrValue: string, amount?: number) {
  if (amount !== undefined) return this.addClass(`w-[${amount}${unitOrValue}]`);
  return this.addClass(`w-${unitOrValue}`);   // `.w("brnad")` → class="w-brnad"
};
```

## Evidence
- `tailwind-types.ts:43,49,55,58,61,64` — six sizing unions each end in `(string & {})`.
- The C-02 note at `tailwind-types.ts:12-16` states the rationale for closing
  ("An open tail can't typo-check") and lists exactly five families — the sizing
  family is conspicuously absent despite meeting the same criteria.
- `tailwind-methods.ts:415` (and siblings 404-425) — the impl blindly interpolates
  the value into the class string, so a typo emits an invalid Tailwind class that
  the tailwind-extractor will copy verbatim into the safelist, producing dead CSS
  with no warning.

## Why it matters
Sizing methods (`w`, `h`, `maxW`, `minW`, `maxH`, `minH`) are among the most-called
fluent methods in any layout-heavy view — frequency is high across every app in
the workspace. A typo'd width silently produces a class that matches nothing, so
the element collapses to its intrinsic size and the bug surfaces only as a visual
glitch at runtime, never at compile time. This is the precise failure mode C-02
set out to kill; it was simply not finished. It also makes the type surface
internally inconsistent: a developer who learns "fluent methods catch typos"
(per the CLAUDE.md styling guidance) is wrong for exactly this family.

## Rough idea (not a design)
Delete the `(string & {})` tail from the six sizing unions and rely on the existing
`` `[${string}]` `` arm (already reachable via `TailwindSpacing`) plus the
`(unit, amount)` overload for arbitrary values — for `MaxWidth`/`MinWidth`/`MinHeight`
that don't embed `TailwindSpacing`, add the `` `[${string}]` `` arm explicitly, mirroring
how C-02 restated the arbitrary arm on the closed color/shadow types. This is a
type-narrowing change: code that previously compiled `.w("typo")` now errors, so it
is a **breaking change → parked-major**, shipped alongside any future re-tightening
of the remaining JIT-justified scales. The class-vocab/extractor contract is
unaffected (the emitted prefixes don't change), but the eslint-plugin's value
vocab should be reviewed for these prefixes in lockstep.
