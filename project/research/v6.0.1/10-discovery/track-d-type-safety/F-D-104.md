# The schema-key tuple/string isn't tied to the class it describes

## Problem
`defineSchemaKeys(ImgTag, ['src', 'alt', ...])` is the single source of truth for which fields the renderer emits as attributes — but `SchemaKey` is just `string | [string, string]`, with no link to the target class's instance type. So a key that doesn't exist on the class (a typo, or a field that was renamed/removed) compiles cleanly, and the renderer silently never emits that attribute (or emits a dead one). This is the `_sk` tuple-value typing hole called out for this angle: the `prop` half of `[prop, attr]` is unconstrained bare `string`.

## Evidence
```ts
// src/core/proto.ts:18
export type SchemaKey = string | readonly [prop: string, attr: string];
// src/core/proto.ts:29
export function defineSchemaKeys(ctor: abstract new (...args: never[]) => Tag, keys: readonly SchemaKey[]): void {
```
Every call site is unchecked against its class, e.g.:
```ts
// src/elements/media.ts:70
defineSchemaKeys(ImgTag, ['src', 'alt', 'width', 'height', 'loading', 'decoding', 'srcset', 'sizes', 'crossorigin']);
// src/elements/document.ts:95 — the tuple's `prop` ('httpEquiv') is also unconstrained
defineSchemaKeys(MetaTag, ['name', 'charset', ['httpEquiv', 'http-equiv'], 'property', 'content']);
```
Nothing forces `'srcset'`/`'httpEquiv'` to actually be a field of `ImgTag`/`MetaTag`. `defineSchemaKeys(ImgTag, ['srcset', 'nonexistent'])` type-checks today.

## Why it matters
This list is hand-maintained for ~25 element classes and is the contract that turns a class field into emitted HTML. A drift between the field set and the `_sk` array is invisible to the compiler and only catches in a render snapshot test (if one exists for that attribute). Binding it to `keyof T` makes the whole element layer self-checking — exactly Track D's "tighten types, remove the hole" mandate.

## Rough idea (not a design)
6.1.0 (additive, source-internal): parameterize `defineSchemaKeys` and `SchemaKey` over `keyof T & string`. It's `@internal`, so no public shape changes; the only risk is surfacing a pre-existing latent typo (which is the point — fix any it flags in the same patch). Keep the `[prop, attr]` decoupling for camel→kebab/colon cases.
