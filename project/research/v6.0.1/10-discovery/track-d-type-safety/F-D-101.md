# `<link>` and `<base>` setters are untyped strings where enums fit

## Problem
`<link>` is one of the most enum-heavy elements on the platform, yet `LinkTag` types `rel`, `as`, and `type` as bare `string`, and `BaseTag.target` is bare `string`. `LinkRel` and `BrowsingContext` open unions already exist in `html-types.ts` and are used elsewhere (anchor/area/form). `rel` on `<link>` (`stylesheet | preconnect | preload | modulepreload | icon | manifest | dns-prefetch | apple-touch-icon | …`) and `as` (`script | style | font | image | fetch | document | …`) are well-defined finite sets; today `.setRel("styleshet")` and `.setAs("fnt")` compile silently.

## Evidence
```ts
// src/elements/document.ts:102, 109  (LinkTag)
rel?: string;
...
as?: string;
// src/elements/document.ts:188  (BaseTag)
target?: string;
```
while these unions already exist and are reused elsewhere:
```ts
// src/elements/html-types.ts:28
export type BrowsingContext = '_self' | '_blank' | '_parent' | '_top' | (string & {});
// src/elements/html-types.ts:30
export type LinkRel = 'noopener' | 'noreferrer' | ... | (string & {});
```

## Why it matters
`<link rel=…>` typos are a classic silent-failure class (a misspelled `preconnect`/`preload` just does nothing — no runtime error, degraded perf). Four setters across the two head elements. Adding open unions keeps the `(string & {})` escape hatch so no valid value is lost.

## Rough idea (not a design)
6.1.0 (additive): introduce `LinkAs` (open union) and a `LinkType` hint; re-type `LinkTag.rel` to a link-specific open rel union (the document `<link>` rel set differs from anchor's), `LinkTag.as`→`LinkAs`, `BaseTag.target`→`BrowsingContext`. Open unions = autocomplete with escape hatch, so additive not breaking. No class emission → no vocab lockstep.
