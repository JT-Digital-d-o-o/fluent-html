# Context module-global value stack corrupts across concurrent requests under interleaved async

## Problem
`createContext` / `createRequiredContext` back the scope by a **single module-level
array** that lives for the whole process. The value is read at *build time* (component
functions run eagerly and read `.current` while constructing the Tag tree), and the
scope is popped when the caller's `using` block exits. This is correct only if nothing
yields the event loop between `scope(value)` and the point where every component that
reads `.current` has finished running.

In a Fastify SSR handler that is exactly what happens routinely:

```ts
async function getDashboard(req, reply) {
  using _ = AuthCtx.scope(req.user);     // pushes onto the SHARED global stack
  const data = await db.load();          // <-- event loop yields here
  return reply.renderView(Page(data));   // Page() reads AuthCtx.current
}
```

While this handler is awaiting `db.load()`, a **second concurrent request** runs its own
`AuthCtx.scope(otherUser)` and pushes onto the same global array. When request 1 resumes
and `Page()` reads `AuthCtx.current`, it reads the **top of the shared stack** —
request 2's user. Cross-request data bleed (auth/user/nonce/locale), a classic
SSR isolation bug, and silent: no throw, just the wrong user rendered.

## Evidence

```ts
// src/control/context.ts:69
export function createContext<T>(defaultValue: T): Context<T> {
  const stack: T[] = [defaultValue];          // ONE array per context, per process
  return {
    get current(): T { return stack[stack.length - 1]!; },
    scope(value: T): Disposable {
      stack.push(value);
      return { [Symbol.dispose]() { stack.pop(); } };
    },
  };
}
```

The memory note "Never use AsyncLocalStorage — context is sufficient for synchronous
rendering" is the intended constraint, but nothing in the shipped JSDoc or the
guidelines (`web-development/fluent-html.md:283`) states the actual rule the design
demands: **there must be no `await` between `scope()` and the synchronous render of the
scoped subtree.** The examples even encourage `using _ = AuthCtx.scope(user)` at the top
of a handler that is typically `async`. The render path itself
(`emitChunks`/`emit`, `src/render/serialize.ts:312`) reads nothing from context — by
then the tree is already built — so the hazard window is entirely in app-land handler
code, which is precisely where the docs point people.

## Why it matters
Auth/user context bleeding between concurrent requests is a security-grade correctness
bug, and the guideline pattern actively steers toward it (scope at the top of an async
handler). Frequency is "every app that scopes request data and awaits before render,"
i.e. nearly all of them. It is undocumented, so a careful reader cannot avoid it.

## Rough idea (not a design)
6.0.1 patch: tighten the JSDoc on `createContext`/`createRequiredContext` and
`web-development/fluent-html.md` to state the invariant explicitly — build the scoped
subtree synchronously, do all `await`s *before* `scope()`, and never hold a scope across
an `await`. (A structural fix — request-isolated storage — is a P5/@fluent-html/fastify
concern and out of scope here.)
