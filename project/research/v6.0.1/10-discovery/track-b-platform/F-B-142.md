# Microdata global attributes have no typed surface

## Problem
`itemscope` is the only microdata attribute reachable typed (it's in the boolean union). The other four — `itemtype`, `itemprop`, `itemref`, `itemid` — have no setter at all, so structured-data markup (schema.org Product/Article/BreadcrumbList for SEO/rich-results) requires `.addAttribute("itemprop", …)` raw strings on every annotated element.

## Evidence
```ts
// src/elements/html-types.ts:61
  | 'hidden' | 'inert' | 'ismap' | 'itemscope' | 'loop' | 'multiple'
```
`itemscope` is present; grepping the whole `src/` tree for `itemprop|itemtype|itemref|itemid` returns only this single `itemscope` hit — none of the value-bearing microdata attributes are modeled.

```ts
// src/core/tag.ts:305
setDataAttrs(attrs: Record<string, string>): this { ... }
```
The codebase already has the right shape for a multi-attribute global combinator (`setDataAttrs`, `setAria`), but microdata never got one.

## Why it matters
For an SSR-first HTML library aimed at content/marketing pages (the project ships marketing guidelines), schema.org microdata is a core SEO primitive. Today it's all untyped escape-hatch, with `itemprop` repeated on potentially dozens of elements per page — exactly the "no bare string for standard props" rule the guidelines enforce.

## Rough idea (not a design)
Additive (6.1.0): a `.microdata({ type?: string; prop?: string; ref?: string; id?: string })` combinator on `Tag` that emits `itemtype`/`itemprop`/`itemref`/`itemid` (paired with the existing `itemscope` toggle). `itemtype` values are URLs (open string); `itemprop` is content-author-defined (open string) — type-safety here is shape, not value-union.
