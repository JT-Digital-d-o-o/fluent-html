# Declarative Shadow DOM (`<template shadowrootmode>`) has no typed surface

## Problem
`Template()` returns a bare `El("template")` with no element-specific class. Declarative Shadow DOM — `<template shadowrootmode="open">…</template>` — is the *SSR* mechanism for shadow DOM (it's the only way to ship shadow roots without client JS), plus its companions `shadowrootdelegatesfocus`, `shadowrootclonable`, `shadowrootserializable`. None are reachable typed; they require raw `.addAttribute("shadowrootmode", "open")`.

## Evidence
```ts
// src/elements/document.ts:211
export function Template(...children: View[]): Tag {
  return El("template", ...children);
}
```
A bare factory — no `TemplateTag`, no setters. Contrast `SlotTag` in webcomponents.ts which *does* model its one attribute:
```ts
// src/elements/webcomponents.ts:6
export class SlotTag extends Tag {
  name?: string;
  setName(name?: string): this { this.name = name; return this; }
}
```
The library already supports web-component surfaces (`Slot`), but the declarative-shadow-DOM half of that story is unmodeled.

## Why it matters
Low frequency (declarative shadow DOM is niche for most apps) but it is a genuine SSR-only platform capability — precisely this library's wheelhouse — that is reachable only via the untyped escape hatch. For component-library authors rendering encapsulated widgets server-side, this is the primitive.

## Rough idea (not a design)
Additive (6.1.0): a `TemplateTag` with `setShadowRootMode(mode: "open" | "closed")` and boolean toggles for `shadowrootdelegatesfocus`/`shadowrootclonable`/`shadowrootserializable` (add those three to the boolean union). Mirrors the SlotTag pattern.
