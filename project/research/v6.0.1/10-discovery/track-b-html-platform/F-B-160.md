# No typed `fetchpriority` setter

## Problem
`fetchpriority` is the canonical Core-Web-Vitals lever for nudging the loading order of the LCP image, a critical preload, or a render-blocking script. It is a baseline platform attribute on `<img>`, `<link>`, `<script>` and `<iframe>`. None of those shipped tags expose it — there is no `setFetchPriority` anywhere in `src/`. The only way to emit it today is the untyped `addAttribute("fetchpriority", "high")` escape hatch, which is exactly what Track B exists to eliminate.

## Evidence
`ImgTag` declares `loading`, `decoding`, `srcset`, `sizes`, `crossorigin` — but no `fetchpriority`:

```ts
// src/elements/media.ts:13
export class ImgTag extends Tag {
  src?: string;
  alt?: string;
  width?: string;
  height?: string;
  loading?: 'lazy' | 'eager';
  decoding?: 'sync' | 'async' | 'auto';
  srcset?: string;
  sizes?: string;
  crossorigin?: CrossOrigin | '';
  // no fetchpriority
}
```

`LinkTag` (src/elements/document.ts:101) and `ScriptTag` (src/elements/document.ts:215) likewise carry `crossorigin`/`integrity`/`as` but no `fetchpriority`. `IframeTag` (src/elements/embedded.ts:5) has `loading` but not `fetchpriority`. A grep for `fetchpriority`/`fetchPriority` across `src/` returns zero hits.

## Why it matters
The single most common performance recommendation Lighthouse emits for an SSR app — `fetchpriority="high"` on the hero/LCP image and on the critical `<link rel=preload>` — cannot be written with a typed setter. Every app that cares about LCP (all of them) drops to `addAttribute`, losing the closed-union typo guard that Track B promises. High frequency (one of the most-cited perf attributes), high pain (directly tied to the perf guardrail and the marketing/landing-page work).

## Rough idea (not a design)
Additive (6.1.0): a shared `export type FetchPriority = 'high' | 'low' | 'auto';` in html-types.ts, plus `setFetchPriority` + schema key on the four tags. Pairs naturally with the resource-hint typing in [[F-B-161]].
