# `AutocompleteHint` is half a union

## Problem
The autofill token list is sparse — it omits the most-used checkout/profile tokens — and falls back to a bare `(string & {})`, so a typo like `'crrent-password'` or `'cc-numbr'` compiles silently. Guardrail #4 ("no bare `string` where a literal union fits") is only half-honored: the WHATWG autofill field-name list is a finite, well-known set; the open tail is needed only for the composable prefix grammar, not for the field names themselves.

## Evidence
```ts
// src/elements/html-types.ts:20
export type AutocompleteHint =
  | 'on' | 'off' | 'name' | 'email' | 'username' | 'new-password'
  | 'current-password' | 'organization' | 'street-address' | 'country'
  | 'postal-code' | 'tel' | 'url' | 'one-time-code'
  | (string & {});
```

Missing from a payment/profile form: `given-name`, `family-name`, `additional-name`, `honorific-prefix`, `nickname`, `address-line1/2/3`, `address-level1..4`, `country-name`, `cc-name`, `cc-number`, `cc-exp`, `cc-exp-month`, `cc-exp-year`, `cc-csc`, `cc-type`, `bday`, `bday-day/month/year`, `sex`, `tel-national`, `tel-country-code`, `email` is there but `impp`/`photo` are not, `transaction-amount`, `language`, `webauthn`. The `(string & {})` tail means none of these omissions is caught.

## Why it matters
Checkout and sign-up forms are the highest-value forms in any SaaS, and correct `autocomplete` tokens are what unlock browser/password-manager autofill (measurable conversion impact). A developer wiring a 14-field address form gets zero autocomplete on every token not in the short list, with no compile-time nudge toward the correct spelling.

## Rough idea (not a design)
Additive (6.1.0): enumerate the full WHATWG field-name set as the union body; keep `(string & {})` (or, better, a documented template-literal type for `section-*`/`shipping`/`billing`) only for the prefix grammar. Pure type widening of accepted literals — no runtime change, no shape break.
