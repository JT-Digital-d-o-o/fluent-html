# No typed `form=""` association attribute

## Problem
The HTML `form` content attribute lets a control, button, `<fieldset>`, or `<output>` live anywhere in the DOM yet still submit with a specific `<form id>` — the canonical "submit button in a sticky footer / modal action bar outside the `<form>`" pattern, which is extremely common in HTMX SSR layouts where the form body and its action bar are in different layout regions. None of the form element classes expose it; only the *sub*-attributes `formaction`/`formmethod` exist on `ButtonTag`.

## Evidence
`InputTag` (src/elements/forms.ts:13), `ButtonTag` (src/elements/forms.ts:215), `SelectTag`, `TextareaTag`, `OutputTag`, and `FieldsetTag` (src/elements/forms.ts:457) declare typed fields but none is `form`:

```ts
// src/elements/forms.ts:215 — ButtonTag has formaction/formmethod but NOT form
export class ButtonTag extends Tag {
  type?: 'submit' | 'reset' | 'button';
  name?: string; value?: string;
  formaction?: string;
  formmethod?: 'get' | 'post';
  // no `form?: string`
}
```

Today the only path is `Button("Save").addAttribute("form", "signup-form")`, untyped and not `Id`-aware (so it can't reference a `defineIds` value cleanly).

## Why it matters
Decoupling a submit button from the form element is the standard solution for app-shell layouts and `<dialog>` footers. In an HTMX full-layout swap app (the documented default pattern), the action bar is routinely a sibling of the form. The capability is unreachable type-safely and silently loses the benefit of `Id` typing.

## Rough idea (not a design)
Additive (6.1.0): a shared `setForm(id?: string | Id)` on the form-associated element classes. No class-string emission → no extractor/eslint change. Guideline note in views.md on the decoupled-action-bar pattern.
