# Inline-style setters are a silent off-ramp from the typed styling layer

## Problem
The whole v6 styling story is "fluent methods, not raw strings — for type-safety, IDE autocomplete, and a scannable class contract." But `setStyle("color: red; font-size: 16px")` and `setStyles({ color: "red" })` let an author re-enter raw CSS with zero type-checking, zero autocomplete, and — crucially — zero visibility to the extractor/eslint that police the *class* surface. There is a lint rule (`no-known-modifiers-in-setclass`) that catches Tailwind tokens smuggled into `setClass`, but nothing catches the much wider hole of expressing the same thing as inline CSS, which converges *away* from the one-way-to-do-it principle the release is built on.

## Evidence
The setters accept arbitrary CSS text/object with no validation against the vocab:

```ts
// src/core/tag.ts:142
setStyle(style?: string): this { this.style = style; return this; }
// src/core/tag.ts:283
setStyles(styles: Record<string, string | number>): this { … this.style = styleString; return this; }
```

At render time the value is HTML-escaped (XSS-safe) but never analyzed — it is an opaque attribute:

```ts
// src/render/serialize.ts:242
const tsty = tag.style;
if (tsty !== undefined) attrs += ' style="' + escapeAttr(tsty) + '"';
```

Meanwhile the class surface gets a dedicated guard the style surface lacks:

```ts
// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts
// flags `.setClass("p-4 …")` — but `.setStyle("padding: 16px")` sails through
```

## Why it matters
This is the convergence leak that quietly erodes the design system: a developer who can't find a fluent method reaches for `setStyle`, the value escapes the safelist/theme entirely, and the codebase drifts back to ad-hoc CSS — invisibly, because no tool complains. Pain is low per-instance but it is the path of least resistance under deadline pressure, so it compounds.

## Rough idea (not a design)
Additive tooling (6.1.0): an eslint rule `prefer-fluent-over-inline-style` that recognizes inline-style declarations with a 1:1 fluent/Tailwind equivalent and suggests the typed method, leaving genuinely-dynamic CSS (custom properties, computed values) untouched. No core shape change — `setStyle`/`setStyles` stay as the sanctioned dynamic-CSS escape hatch, just no longer the *silent* default.
