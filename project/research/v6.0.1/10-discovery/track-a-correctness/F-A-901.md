# buildAttrs emits duplicate `id`/`class`/`style` attributes — silent collision

## Problem
`buildAttrs` serializes the three dedicated tag fields first, then walks the generic
`attributes` bag and appends every key blindly — with no check that the bag already
collides with a dedicated field:

```ts
// src/render/serialize.ts:238-272 (abridged)
const tid = tag.id;
if (tid !== undefined) attrs += ' id="' + escapeAttr(tid) + '"';
const tcls = tag.class;
if (tcls !== undefined) attrs += ' class="' + escapeAttr(tcls) + '"';
const tsty = tag.style;
if (tsty !== undefined) attrs += ' style="' + escapeAttr(tsty) + '"';
...
const extraAttrs = tag.attributes;
if (extraAttrs !== EMPTY_ATTRS) {
  for (... key of Object.keys(extraAttrs)) {
    attrs += ' ' + key + '="' + escapeAttr(String(value)) + '"';   // no id/class/style guard
  }
}
```

`addAttribute("id", …)` / `("class", …)` / `("style", …)` are NOT blocked —
`validateAttributeKey` (`src/core/tag.ts:30`) only rejects proto keys, `on*` handlers,
and malformed names; `id`/`class`/`style` all pass — so they land in the `attributes`
bag and emit a *second* attribute of the same name.

Observed (built `dist`):

```
render(Div().setId("a").addAttribute("id", "b"))
=> <div id="a" id="b"></div>

render(Div().setClass("a").addAttribute("class", "b"))
=> <div class="a" class="b"></div>

render(Div().setStyle("color:red").addAttribute("style", "color:blue"))
=> <div style="color:red" style="color:blue"></div>
```

Browsers keep the **first** `id`/`class`/`style` and silently drop the second, so the
author's second write is lost with no error — and the markup is invalid (duplicate
attribute). This mirrors the already-recorded `.toggle()` duplicate-attribute bug but
is a wholly separate code path (the core `id`/`class`/`style` fields vs. the generic
`attributes` bag, not the `toggles` array).

## Evidence
- `src/render/serialize.ts:238-243` — dedicated `id`/`class`/`style` emitted unconditionally.
- `src/render/serialize.ts:262-272` — generic bag appended with no reserved-name collision check.
- `src/core/tag.ts:30-40,159` — `validateAttributeKey` (called by `addAttribute`) does not reserve `id`/`class`/`style`, so they reach the bag.

## Why it matters
Mixed-source styling is common: a base component sets `class`/`style` via the fluent
API while a wrapper or untyped escape-hatch passes `addAttribute("class", …)`; or a
component does `.setId(ids.x)` and a generic prop-spreader re-adds `id`. The result is
invalid HTML and a silently-dropped write — hard to debug because the rendered string
"looks" like it has the value. Medium pain, recurs anywhere the dedicated setters and
the generic escape hatch coexist.

## Rough idea (not a design)
Patch (6.0.1, no public-shape change): make `id`/`class`/`style` reserved in the
generic bag. Simplest: in `buildAttrs`, skip bag keys equal to `id`/`class`/`style`
when the dedicated field is set (dedicated wins), or have `addAttribute` route those
three names into the dedicated fields. Add an attribute-name dedup assertion to the
serializer tests.
