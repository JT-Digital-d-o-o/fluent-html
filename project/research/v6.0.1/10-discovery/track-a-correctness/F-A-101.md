# The emit/emitChunks drift guard does not exist as described

## Problem
`serialize.ts` ships TWO hand-maintained copies of the work-stack traversal:
`emitChunks()` (generator, used by all streaming paths) and `emit()` (eager,
used by `render()`). The duplication is justified in a comment that promises a
fuzz test pins the two together:

```ts
// src/render/serialize.ts:386-387
// ... only the low-churn traversal skeleton is repeated, and the `render` ≡
// `renderToIterable` fuzz test guards against drift. @internal
```

No such fuzz test exists. `test/fuzz.ts` only fuzzes `render()` output
(escaping + deep-nesting); it never invokes `renderToIterable`/`emitChunks` and
never compares the two serializers. The only `render ≡ renderToIterable`
assertion is a SINGLE hand-picked example:

```ts
// test/stream.test.ts:409
it("renderToIterable joins to the render output", () => {
  ...
  assert.equal([...renderToIterable(v)].join(""), render(v));
});
```

## Evidence
- `test/fuzz.ts:22` — `describe("Property-based fuzz: text content escaping")`
  and friends call only `render(Div(s))` / `render(Div().addAttribute(...))`.
  Grep confirms `renderToIterable`/`emitChunks` appear nowhere in `fuzz.ts`.
- `test/stream.test.ts` has example-based parity (`streamToString(v) === render(v)`)
  for a fixed handful of trees, plus the one `renderToIterable` line above. None
  of it is randomized, and none stresses the drift-prone branches together
  (nonce stamping on script/style, `_doc` DOCTYPE prefix, array `\n` separators,
  void elements, script/style sanitization, deep nesting).

The two loops have already diverged structurally (e.g. `emit` early-`continue`s
on void elements at serialize.ts:425; `emitChunks` uses an `if (!VOID...)` block
at serialize.ts:347) — exactly the kind of skeleton edit the comment claims is
caught automatically but isn't.

## Why it matters
The whole architectural bet of v6's render spine is "one serializer, two thin
drivers, so they cannot drift" — that's the headline in the file banner
(serialize.ts:9-17). Keeping two physical copies is defensible ONLY if a strong
test pins them. Today a future edit to one loop (a new context kind, an escaping
tweak, a separator change) can ship a `render` vs `renderToStream` output split
that example tests miss. This is a correctness landmine for a "Correctness &
Polish" patch line.

## Rough idea (not a design)
6.0.1: add a property test that builds random trees (mixing text, RawString,
nested arrays, void elements, script/style with/without author nonce, Document,
deep nesting) and asserts `render(t, opts) === [...renderToIterable(t, opts)].join("")`
for random `nonce`/`chunkSize`. Then the serialize.ts comment is accurate.
Optionally tighten the comment to point at the actual test.
