# HTMX.ignore serializes to a non-existent hx-ignore="true" attribute (intended the boolean hx-disable)

## Problem
The `HTMX.ignore` field is documented as "Ignore htmx processing (was disable)" — i.e. it is meant to render the htmx attribute that disables htmx processing on a subtree. But it is registered in `HTMX_ATTRS` via `boolVal('ignore')`, which emits `hx-ignore="${v}"`. htmx has no `hx-ignore` attribute, and the disable-processing attribute is a **bare boolean** (`hx-disable`), not a `"true"`-valued one. So `{ ignore: true }` ships a dead `hx-ignore="true"` that htmx ignores entirely — the element is **not** opted out of processing.

## Evidence

```ts
// src/htmx.ts:242-243
// Ignore htmx processing (was disable)
ignore?: boolean;
```

```ts
// src/render/serialize.ts:125-128 — boolVal renders the literal value
const boolVal = (key: string): AttrConfig => ({
  key,
  serialize: (v) => ` hx-${key}="${v}"`,
});
```

```ts
// src/render/serialize.ts:161
boolVal('ignore'),     // → hx-ignore="true"   (no such htmx attribute)
```

Output: `hx(... ).ignore = true` → `hx-ignore="true"`. There is no `hx-ignore` in htmx; the author's intent to disable htmx processing on the element silently does nothing.

## Why it matters
The whole point of the field is a safety opt-out (mark a subtree htmx must not touch — e.g. user-generated HTML, a third-party widget). Shipping an attribute htmx does not recognise means the opt-out fails open: htmx still processes the element. That's the dangerous direction for a "disable processing" control. No test exercises `ignore`, so it slipped through green CI.

## Rough idea (not a design)
Patch (6.0.1): confirm the htmx 4 attribute name + value form for disabling processing, then special-case `ignore` in `buildHtmx` to emit that exact attribute (bare boolean if that's the contract) rather than the generic `boolVal` `hx-ignore="true"`. Update the htmx.md guideline and JSDoc to name the real attribute. No public-shape change (the field stays `ignore?: boolean`).
