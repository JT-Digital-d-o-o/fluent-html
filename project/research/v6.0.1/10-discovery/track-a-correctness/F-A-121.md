# hx-status object config corrupts itself when swap/target/select carry spaces

## Problem
`buildStatusConfig` serializes an `HxStatusConfig` object into a single space-delimited
`key:value` string:

```ts
// src/render/serialize.ts:211-220
function buildStatusConfig(cfg: HxStatusConfig): string {
  const parts: string[] = [];
  if (cfg.swap) parts.push('swap:' + cfg.swap);
  if (cfg.target) parts.push('target:' + cfg.target);
  ...
  return parts.join(' ');
}
```

But `cfg.swap` has type `HxSwap`, which legitimately contains spaces — e.g.
`"outerHTML scroll:top"` (src/htmx.ts:66, `SwapWithModifier`). The modifier's space collides
with the `' '` that separates config entries, so the emitted attribute fuses the swap modifier
with the following entry and htmx misparses it.

## Evidence
Reproduction with a fully type-valid input:

```
Div().setHtmx(hx("/page", { status: { "200": { swap: "outerHTML scroll:top", target: "#x" } } }))
=> <div hx-get="/page" hx-status:200="swap:outerHTML scroll:top target:#x"></div>
```

htmx reads `hx-status:200` as space-separated `key:value` tokens, so it sees three entries:
`swap:outerHTML`, `scroll:top`, and `target:#x`. The intended `scroll:top` swap modifier is
lost (or reinterpreted) and the config no longer means what the author wrote. The `escapeAttr`
wrapping at serialize.ts:204 protects against `"`-injection, but does nothing for this
delimiter-collision because spaces are valid attribute characters.

The same class hits any `target`/`select`/`push`/`replace` value that contains a space
(`target: "closest tr"` style selectors), since those are bare `string`/`HxTarget` (which
includes `closest ${string}`, `find ${string}`, etc.).

## Why it matters
The status-config object form is presented as the typed, safe alternative to a raw string, yet
the most natural typed value — a swap *with a modifier* — silently produces a malformed
attribute. It is a correctness footgun that type-checks, with no error and no obviously-wrong
local output (the bug is in how htmx later parses it).

## Rough idea (not a design)
Patch (6.0.1): the htmx status-config mini-grammar can't express multi-token values via plain
space joins. Options to scope in Wave 2: (a) reject (throw) on a `swap`/`target` value
containing a space in this context, surfacing the conflict; or (b) confirm htmx's actual
`hx-status` parsing and, if it has no escaping, document the limitation and constrain the type
so a spaced swap can't be passed here. No public-shape change either way.
