# ESLint prefer-unit-overload hardcodes the CSS unit list — UNIT_METHODS is drift-guarded, the units aren't

## Problem
The plugin went to real lengths to keep the method↔class vocabulary in lockstep
with the lib: `vocab.generated.ts` is codegen'd by `gen-vocab.mjs` and pinned by
`vocab-drift.mjs`, which asserts both `VOCAB_METHODS` and `UNIT_METHODS` match
`classVocab`. But the **set of accepted CSS units** — the other half of the unit
overload — is hand-copied into a regex in the rule and is NOT generated or drift-
guarded:

```ts
// fluent-html-eslint-plugin/src/rules/prefer-unit-overload.ts:11
const BRACKET_UNIT_RE = /^\[(-?\d+(?:\.\d+)?)(px|rem|em|%|vh|vw|dvh|svh|lvh)\]$/;
```

The lib's source of truth:

```ts
// fluent-html/src/class-vocab/types.ts:19
export const UNITS: ReadonlySet<string> = new Set([
  "px", "rem", "em", "%", "vh", "vw", "dvh", "svh", "lvh",
]);
```

Today they happen to agree. The drift guard does not cover them — `gen-vocab.mjs`
derives `unitMethods` but never reads `UNITS`, and `vocab-drift.mjs` asserts only
methods.

## Why it matters
v6 is explicitly v4-native and greenfield; container-query units (`cqw`/`cqh`) or
new viewport units are a plausible next addition to `UNITS`. The moment the lib
adds one, this regex silently stops suggesting `.minH("cqw", 50)` for
`.minH("[50cqw]")` — and nothing fails. It's the exact "tooling drifts from the
class-string contract" failure mode the rest of the vocab pipeline was built to
prevent (guardrail #7), left with one unguarded copy.

## Rough idea (not a design)
Have `gen-vocab.mjs` import `UNITS` and emit `export const UNITS` into
`vocab.generated.ts`; build `BRACKET_UNIT_RE` from `[...UNITS]`; add a `UNITS`
assertion to `vocab-drift.mjs`. Pure tooling change, no public surface — 6.0.1.
