# The set*/add* convention is only honored for classes

## Problem
The library teaches a `set*` = replace / `add*` = accumulate convention (it is documented inline in `tag.ts` and is a recorded API rule). Classes implement both sides: `setClass`/`setClasses` (replace) and `addClass` (append). Styles and attributes implement only one side, breaking the symmetry the convention promises.

## Evidence
The convention is stated in the source itself:
```ts
// src/core/tag.ts (setStyle JSDoc)
// "(Class names are the opposite: `setClass` replaces, `addClass` appends.)"
```
But:
```ts
// src/core/tag.ts:142  setStyle  — replace
// src/core/tag.ts:283  setStyles — replace (object form)
// → no addStyle / addStyles to append a single declaration
```
For attributes there is `addAttribute` (single) but no `setAttributes`/`addAttributes` bulk form, while for styles there is the bulk `setStyles` but no single-append. The axes are filled in asymmetrically: classes have {set, setMany, add}, styles have {set, setMany}, attributes have {addOne}. A user who learns "add* appends" on classes reasonably expects `addStyle` and is surprised it doesn't exist.

## Why it matters
Low individual pain but it directly contradicts a stated, recorded naming convention — exactly the consistency the v6 convergence goal targets. Composition helpers (`.apply(card)`) frequently want to append one declaration without clobbering an existing inline style.

## Rough idea (not a design)
Add the missing accumulating counterparts — at minimum `addStyle(decl: string)` / `addStyles(obj)` mirroring `addClass`. Purely additive (6.1.0). No class-vocab impact (style strings are outside the Tailwind class contract).
