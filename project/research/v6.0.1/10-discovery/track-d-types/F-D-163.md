# DialogTag is an empty exported class

## Problem
`DialogTag` is a named public export with no methods at all — it adds nothing over `Tag` except the element name. Every dialog attribute (and the `open` boolean) is reachable only through generic `.toggle()`/`addAttribute`, so the dedicated class buys the user zero type-safety while still appearing in the public `.d.ts` as a distinct type.

## Evidence
```ts
// src/elements/interactive.ts:25
export class DialogTag extends Tag {
}

defineSchemaKeys(DialogTag, []);
```
Compare to `DetailsTag` right above it, which earns its class with `setName` for the `<details name>` accordion grouping. `DialogTag` has no such payload — yet the lib invests heavily in dialog ergonomics elsewhere (`openDialog`/`closeDialog`/`dismissOnEscape` behaviors in `behavior-methods.ts`). The boolean `open` is in the closed `BooleanAttribute` union (`html-types.ts:55`) and set via `.toggle("open")`, so the class itself contributes nothing.

## Why it matters
An empty exported class is API-surface noise (it implies typed methods exist when none do) and a convergence smell for a greenfield release. Either it should carry the dialog-specific typed surface that warrants its existence, or its existence as a distinct exported type should be justified.

## Rough idea (not a design)
Audit the stable `<dialog>` attribute surface and give `DialogTag` the typed setters that pull their weight; if there are none beyond what `.toggle()` covers, document why the class exists. Additive (6.1.0) — adding methods is non-breaking; removing the export would be parked-major and is the weaker option given the export is already shipped.
