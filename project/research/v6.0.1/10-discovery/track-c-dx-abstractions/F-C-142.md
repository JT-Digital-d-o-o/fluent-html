# No typed field-array / repeated-fieldset binding

## Problem
`Form<T>` binds *scalar* top-level fields only. There is no way to bind a repeated group — line items on an invoice, multiple phone numbers, a list of permissions per row — where the conventional wire format is `name="items[0].sku"`, `name="items[1].sku"`, etc. The author must hand-concatenate the index into the name string (`f.input(\`items[${i}].sku\`)` doesn't even type-check, since the index-bracketed string isn't `keyof T`), which both defeats the binding and is exactly the kind of string-arithmetic the library elsewhere refuses (`defineRoutes`/`defineIds`).

## Evidence
```ts
// src/elements/forms.ts:327
export interface FormBinding<T> {
  input(name: keyof T & string, type?: InputType): InputTag;
  ...
}
```
`createFormBinding` (forms.ts:336) only ever reads `values[name]` for a flat `name`. `ForEach` (iteration.ts:26) renders the rows fine, but there is no scoped binding to give each row, so each repeated input's `name` and prefilled `value`/`error` must be wired by hand with interpolated indices.

## Why it matters
Any form with an editable collection (order lines, address book, role assignments, key/value settings) hits this. It is the largest single category of forms that `Form<T>` cannot express at all, so authors silently fall back to raw tags + manual index strings — the most error-prone wiring in the whole forms surface (off-by-one indices, mismatched name/value, lost errors). Medium frequency, but high blast radius per occurrence.

## Rough idea (not a design)
Additive (6.1.0): `f.array(name, items, (row, i) => View)` where `name` is a `keyof T` whose value is an array type; `row` is a child `FormBinding` of the element type whose factories prefix `name[i].` onto field names and read `state.values[name]?.[i]` / `state.errors` for that row. Composes with `ForEach` rather than replacing it. Pure naming/wiring primitive — no add/remove-row UI (that is HTMX user-land).
