# Tag.when() uses JS truthiness, diverging from IfThen/whenElse null-narrowing — 0 and "" silently skip

## Problem
`IfThen`, `IfThenElse`, and `Tag.whenElse` all branch on **`!= null`** (nullable narrowing): a present-but-falsy value like `0` or `""` takes the then/non-null branch and is narrowed to `NonNullable<T>`. `Tag.when` — documented in the same breath as `whenElse` and accepting the same `T | null | undefined` value form — instead branches on plain JS truthiness:

```ts
// src/core/tag.ts:216
when<T>(condition: T | null | undefined | boolean, fn: (tag: this, value: NonNullable<T>) => this): this {
  return condition ? fn(this, condition as NonNullable<T>) : this;   // <- truthiness, not != null
}
```

Compare its own two-branch sibling, ten lines down, which is `!= null`:

```ts
// src/core/tag.ts:231
whenElse<T>(condition: T | null | undefined | boolean, thenFn, elseFn): this {
  if (typeof condition === "boolean") return condition ? thenFn(this) : elseFn(this);
  return condition != null ? thenFn(this, condition as NonNullable<T>) : elseFn(this);
}
```

and the canonical `IfThen`:

```ts
// src/control/conditionals.ts:59
if (conditionOrValue != null) { return then(conditionOrValue); }
```

## Evidence
`when(value, fn)` with a value of `0`, `""`, or `NaN` silently takes the skip branch even though the value is *present and non-null*. The `NonNullable<T>` callback signature actively advertises null-narrowing semantics (why else narrow?), so a developer reasonably writes `Span().when(count, (t, n) => t.setTitle(\`${n}\`))` expecting the IfThen contract — and gets a silent no-op when `count === 0`. The doc comment for `whenElse` even calls out this exact distinction ("Falsy-but-present values (`\"\"`, `0`) take the `thenFn` branch"), which `when` then contradicts. 30 `.when()` call sites exist across the apps; today they happen to pass only `is*/has*` booleans, so the latent footgun hasn't fired — but the contract is wrong.

## Why it matters
This is a behavior/correctness divergence within a single conceptual family (`when`/`whenElse`/`IfThen`). It is a no-shape-change fix: the public signature already promises `NonNullable<T>` narrowing, so aligning the runtime to `!= null` is a behavior fix, not an API break — it can ship in 6.0.1. The current truthiness path is a silent-wrong-output trap exactly where the type signature says it should narrow.

## Rough idea (not a design)
Patch (6.0.1). Change the value branch to `condition != null ? fn(this, condition as NonNullable<T>) : this`; keep the boolean overload behaving as truthiness. No signature change. Add a test asserting `when(0, ...)` runs the modifier. Confirms parity with `whenElse`/`IfThen`.
