# Juxtaposition: RFC-A-003 verdicts vs shipped code

RFC-A-003 (eliminate duplicate-attribute emission) shipped to `src/render/serialize.ts`
(`buildAttrs`, `RESERVED_BAG_KEYS`), `src/core/tag.ts` (`toggle` unchanged), and
`test/attributes.test.ts` ("Duplicate-attribute emission (A-003)"). The three Wave-3
verdicts (breaking-change `survives-with-changes` 0.78, correctness `survives-with-changes`
0.86, type-safety `survives` 0.82) carried 6 `required_changes`; none carried a
`killer_objection`. The headline finding: **the correctness lens's required-change #1 was
NOT honored** — the shipped `buildAttrs` does an unconditional `RESERVED_BAG_KEYS.has(key)
continue` (serialize.ts:277), so a non-colliding `addAttribute("id"/"class"/"style")` with
no dedicated setter is silently deleted. Verified empirically:
`render(Div().addAttribute("id","b"))` → `<div></div>` (v6.0.0 baseline: `<div id="b"></div>`).
This is a shipped correctness regression / silent data-loss defect that breaks the RFC's own
byte-identical-on-non-duplicate invariant.

## Cross-lens defect (not from a verdict, surfaced by reconciliation)

The correctness lens predicted the unconditional-skip regression and made it required-change #1.
The shipped code did NOT apply the fix — it ships the exact buggy form the verdict flagged
(`if (RESERVED_BAG_KEYS.has(key)) continue;`). This is the single high-severity item: a benign,
non-duplicate `addAttribute("id"/"class"/"style")` is silently swallowed on any tag that did not
also call the dedicated setter. Real-world reach: any author who used `addAttribute("class", …)`
on a tag without fluent class methods (a documented-discouraged but compiling and previously-working
pattern) now renders NO class at all. The fix is a one-line-per-key presence gate; the three
no-setter test cases (correctness required-change #3, case a/b) are the regression detectors and
must be added at the same time.
