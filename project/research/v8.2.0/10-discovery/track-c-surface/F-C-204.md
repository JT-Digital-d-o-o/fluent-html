# Palette literals: frequent, recurring, and redirected to nothing

## Problem
The prior colors with Tailwind palette shades (`text-slate-500`, `bg-indigo-600`, `border-slate-200`, `ring-emerald-600/20`, ...). In the template and in 13 of the 14 canonical 8.1.0 app repos (all except home-page), `interface FluentColorConfig { defaultPalette: false }` makes them compile errors. The `no-tailwind-in-raw-class` autofix emits them verbatim (`Replace with: .text("slate-500")`), and tsc's first message does not name a replacement:
- `.bg("slate-50")` -> `TS2345: Argument of type '"slate-50"' is not assignable to parameter of type 'TailwindColor'.` (alias only)
- `.text("slate-900")` -> `... parameter of type '"info" | "warning" | "sm" | "lg" | "xl" | "2xl" | ... | "white" | ... 53 more ... | "pretty"'.` (the merged size/align/color union; the text roles are inside the hidden 53)
- `.border("slate-200")` -> a 5-line TS2769 about overloads and border directions.

## Evidence (executed)
- AST inventory of both runs: 43 and 40 palette occurrences (recon 02 audit reproduced), 28 and 24 distinct, 20 in both runs, 32 in the union.
- Each of the 32 distinct tokens probed in the template (`Div().addClass(tok)` -> `eslint --fix` -> tsc): 36 diagnostics. Role-token names visible in them: none in 14; `info`, `warning` in 12; `primary`, `primary-700`, `warning`, `info` (+`on-accent`) in 10. None shows `text`, `text-dim`, `text-faint`, `bg`, `surface`, `line` or `line-strong`, the roles the prior's slate shades correspond to.
- Fleet: `grep defaultPalette` over the canonical 8.1.0 repos' `src/app/theme.ts`: `false` in studio, stojnica, everyframe-composer, gzs/stem-50, sportoawards, na-cent, fl-um, competify, fluent-html-home-page, everyframe, competition, popri, website-sales-funnel-automation-system and the template; absent in home-page.
- Mapping availability (from theme.ts, not executed as code): each prior hue has a role in the template theme: slate -> `text`/`text-dim`/`text-faint` (text-*), `bg`/`surface` (bg-*), `line`/`line-strong` (border/divide/ring-*); indigo -> `primary`/`primary-700`; red -> `danger`; emerald -> `success`; amber -> `warning`.

## Why it matters
43/40 occurrences per run make palette the most frequent divergence after the `addClass` call itself, recurring in both runs. The blind in-repo agents avoided it only by copying exemplars (0 palette literals in 4/4 runs, recon 02). Autofix -> an error that names nothing is the whole redirect path. Reach 3, pain 3.

## Rough idea (not a design)
Type layer first: under the opt-out, route `${Hue}-${Shade}` literals to an arm whose parameter is a branded message naming the fix ("palette literals are off in this project: use a role token from src/app/theme.ts"), the technique the template's render-stance error already uses (recon 02 probe #29: fix at char 225). Lint second, type-aware through `parserServices` (as `match-subset-default` does): withhold the autofix when the replacement does not type-check, and list the role tokens for the property family. The "never write a palette literal" paragraph then only restates what the compiler says.
