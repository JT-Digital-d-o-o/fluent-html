# Prune is free on the prior axis; the post-prune redirect is not ready

## Problem
Seed: 108 methods at 0 call sites, re-measured by recon 01 at 92 (0 fleet, 0 canonical-era; 361 -> 269 callables). Through the prior lens the question is whether pruning removes anything the model reaches for, and what a model that does reach for a pruned utility meets afterwards.

## Evidence (executed)
1. Prior reach. The pure prior's 107 distinct class tokens map (via the lint's own `Replace with` text) to 46 distinct methods and variant keys: 0 are in the 92. Its `addAttribute` sites map to 13 typed alternatives (setAutocomplete, setSrc, setAria, toggle, setCharset, setContent, setName, setScope, setRole, setMethod, setAction, setFor, setLang): 0 in the 92. The 4 in-repo runs (blind1/2, guided1/2 feature patches): 73, 63, 73, 66 distinct `.method(` names, 0 in the 92.
2. What 8.0.0's prune left behind, by lint outcome over the pinned Tailwind class list (see [[F-C-201]] harness):
   - silent: 378 `mask-*` classes (family pruned 8.0.0, `vocab-coverage.test.ts:42`) get no report from `no-tailwind-in-raw-class`; `addClass("mask-b-from-50%")` passes lint and tsc.
   - mis-routed: 591 classes of pruned or uncovered families are rewritten into a surviving merged prefix and then fail tsc: `rotate-x-45` -> `Replace with: .rotate("x-45")` -> `TS2345 ... 'TailwindRotate'` (residue prefix `rotate-`, `derive-fixable.ts:112`), `scroll-mb-60` -> `.scroll("mb-60")`, `scale-x-105` -> `.scale("x-105")`, `perspective-origin-top` -> `.perspective("origin-top")`.
   - redirected: `place-items-center`, `snap-x`, `hyphens-auto`, `backdrop-grayscale` -> "is a Tailwind 'place-items-center-*' utility with no fluent method. Use .cssProp() ..." (`no-tailwind-in-raw-class.ts:28`; the printed root is the whole token plus `-*`). `.cssProp("place-items", "center")` renders `[place-items:center]`, which the pinned oracle compiles.

## Why it matters
On this task, pruning the 92 costs no prior-alignment: nothing the model or the exemplar-driven agents wrote touches them (context-economy gain without prior loss). But a prune today yields three different behaviors for the same situation, and two of them are wrong (silent pass, or an error naming a surviving method that cannot take the value). Reach 2, impact 2, pain 2.

## Rough idea (not a design)
Ship the prune in the 9.0.0 bundle together with a lint-side "pruned roots" table derived from the coverage watch's `pruned` IGNORED_ROOTS rows (re-derived, never hand-edited, guardrail 9), so every removed root gets the cssProp redirect with the correct root, and the prefix residue can no longer capture it. The plugin CI contract from [[F-C-201]] then covers pruned roots by construction.
