# The extractor safelists without checking the classes compile

## Problem
The extractor is the one layer that runs in the app, beside the app's installed Tailwind and its `@theme` tokens, on every `npm run css`. It already fails the build on non-literal arguments (`onUnresolved: "error"` in the template). It never asks Tailwind whether the literal classes it safelists produce CSS. The lib's own oracle checks a stock theme at one pinned version in the lib's CI. So an app gets no signal for a class its Tailwind version or theme cannot compile: open-arm values (F-D-201), floor violations (F-D-206), or a `staticManifest` token with no theme entry.

## Evidence (executed)
- Scaffold copy (template 3.7.0 scaffold from wave0-2, fluent-html 8.1.0, plugin 4.1.0, extractor 3.0.0-unreleased, tailwindcss 4.3.3). With `invalid-arms.ts` plus 5 controls:
  - `tsx scripts/build-safelist.ts` exit 0; `fluent-safelist.css` contains 18/18 probe classes.
  - `postcss public/css/styles.css`: 0/19 probe selectors have a rule, 5/5 controls do.
  - tsc exit 0, eslint 0 messages.
- Cost and yield of the missing check (`safelist-audit.mjs`). For each of the 16 canonical apps, the script loads Tailwind 4.3.3's design system with the app's own `fluent-safelist.css` `@theme` block and its `styles.css` `@theme`/`@utility`/`@custom-variant` blocks, then compiles every safelisted class. 16,851 classes, 2 dead (0.012%). All 16 apps took 0.39 s wall; the largest (website-sales-funnel, 1,502 classes) took 13 ms to load and 37 ms to check. Both dead classes come from fluent-html-home-page, where the extractor scanned `.text("centre")` and `.hover({ bg: "blue-60" })` inside doc-label template strings as real calls: harmless junk entries, and a second extractor gap (strings scanned as code).
- Release state. Extractor HEAD is 83e81d2 (2026-08-03, "rebuild stale dist"). fluent-html shipped 8.0.0 (2026-08-14) and 8.1.0 since. The template consumes the extractor by git sha in `pnpm-lock.yaml:197`, and its peer range (`tailwindcss >=4.0.0`) is below the measured 4.2.0 floor.

## Why it matters
impact 2 × pain 2 × reach 1 / M = 2. Today's live safelists are 99.99% clean, so reach is 1. That is the typed surface and the raw-class lint doing their job on existing code. The check is preventive, and it is the only one that runs against each app's actual Tailwind version and theme. It would hold across the next bump, where the lib's oracle, pinned at one version, cannot.

## Rough idea (not a design)
Build layer (boot/ci-class enforcement in the app). When the optional `tailwindcss` peer resolves, have `generateFluentSafelist` load the app's design system from its CSS entry and run `candidatesToCss` over the safelist. Add `onInvalidClass: "error" | "warn" | "ignore"`, set to `"error"` in the template like `onUnresolved`, reporting file:line and the class. Ship it in the 3.0.0 release with the F-D-206 peer floor. The unreleased state has also let the extractor suite fall to 55/56 against lib 8.1 (recon 03). No prose to delete. It lets the template's `DYNAMIC_SAFELIST` comment stop being the only guidance on dead classes.
