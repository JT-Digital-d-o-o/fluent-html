# setPopovertarget, setPopovertargetaction and setForm are typed on every Tag, but only work on specific elements

`$D3` = `<scratch>/wave1/D3`

## Problem

RFC-B-010 (6.1.0) put the Popover invoker setters on `Tag`, on the premise "any element can be a popover or an invoker" (`RFC-B-010.md:66`). That premise holds for `popover` and not for `popovertarget`. HTML defines `popovertarget`/`popovertargetaction` only on `<button>` and `<input type=button|submit|reset|image>`, and `form=` only on form-associated elements.

The same release scoped the sibling invoker API correctly: `setCommand`/`setCommandfor` live on `ButtonTag`, so `A("x").setCommand(...)` is TS2339.

The result is an inert invoker that compiles, lints and renders. The teaching points straight at it:
- **d.ts JSDoc**: "Wire this element (any invoker — `<button>`/`<a>`/…)" (`dist/src/core/tag.d.ts:325`). Blind agents read `dist/src` d.ts/src 36 and 39 times per run (recon 02 §2.2).
- **CHANGELOG example**: `A("Account").setPopovertarget(ids.menu).anchorName(ids.menu)` (`CHANGELOG.md:527`).
- **Lib test**: `test/native-interactivity.test.ts:97` pins `<a style="anchor-name: --user-menu" popovertarget="user-menu">Account</a>` as the expected output.

## Evidence (executed)

**tsc 5.9.3** (`probe/scope.ts`):
- `A("Menu").setPopovertarget(ids.menu).setPopovertargetaction("show")`: clean.
- `Div("x").setForm(ids.f)`: clean.
- `A("x").setCommand("show-modal")`: `TS2339: Property 'setCommand' does not exist on type 'AnchorTag'.`

**Browser** (`invoker-scope.mjs`). Lib-rendered invoker `#inv` plus `<div id="menu" popover="auto">`; click `#inv`, then read `:popover-open`:

| Invoker (rendered) | Chromium 149 | Firefox 151 |
|---|---|---|
| `<button popovertarget="menu">` | open | open |
| `<a popovertarget="menu">` | **not open** | **not open** |
| `<div popovertarget="menu">` | **not open** | **not open** |
| `<span popovertarget="menu">` | **not open** | **not open** |
| `<li popovertarget="menu">` | **not open** | **not open** |

`Div("x").setForm(ids.f)`: `div.form` is `null` and `form.elements.length` is 1 (only the real `<input form=…>`) in 2/2 engines. The attribute is emitted and ignored.

**Fleet.** The 15 `setPopovertarget` sites are all on buttons (manual receiver audit of each chain), and there are 0 `.setForm(` sites. The hazard is latent; nothing in the fleet depends on the wide typing.

## Why it matters

- **reach 1**: 0 misuses today, exposure across 132 non-button factories.
- **impact 2**: a menu or tooltip trigger that never opens, with no error on any layer.
- **pain 3**: the shipped JSDoc names `<a>` as an invoker, and anchors are a plausible prior for menu triggers.

Dimensions:
- **silent-failure**.
- **invariant-safety**: an element-scoped platform attribute is typed as global.
- **prior-alignment**: the doc steers the guess into the dead form.

## Rough idea (not a design)

**Type layer.** Declare `setPopovertarget`/`setPopovertargetaction` on `ButtonTag` and `InputTag`, and `setForm` on the form-associated classes. `A(…).setPopovertarget` then fails as TS2339, the same shape the correctly scoped `setCommand` already gives.

Also:
- Fix the JSDoc at `tag.ts:542`.
- Fix the CHANGELOG example at `:527`.
- Re-pin the anchor test at `:97` on a `Button`.

Removing a `Tag` method is a type break, so the lane is 9.0.0. Codemod: none (0/15 fleet sites and 1 lib test move).
