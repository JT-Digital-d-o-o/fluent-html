# `preload` was deleted as a phantom; it was live under the extension

`$S` = `<scratch>/wave1/D1`.

## Problem

7.2.0 deleted the `preload`/`optimistic` options because "Neither attribute exists in the htmx 4.0.0-beta4 runtime, so anything built on them silently did nothing" (`CHANGELOG.md:166-169`). The type test and unit test repeat "they never existed in the htmx 4 runtime" (`type-surface.test-d.ts:440`, `htmx.test.ts:155`), as do `CLAUDE.md:276` and `guidelines/web-development/htmx.md:412`. Meanwhile the lib's own `HtmxConfig` JSDoc example (`patterns.ts:117-121`, copied at `htmx.md:499`) enables `extensions: "sse, preload"`. htmx 4 ships `hx-preload` as an extension in every tarball from beta4 to 4.0.0. The diagnosis grepped the core bundle and missed the extension layer, the same oracle failure recon 03 §2.4 found for the `Partial()` root cause.

## Evidence (executed)

| Emission (with `ext/hx-preload.js` or `ext/hx-optimistic.js` loaded) | beta4 | beta6 | 4.0.0 |
|---|---|---|---|
| bare `hx-preload` on `hx-get` (the exact pre-7.2.0 `preload: true` bytes) | mousedown -> 1 prefetch; click -> 0 further requests, content swapped | same | (extension present; valued form below) |
| `hx-preload="mouseover"` (pre-7.2.0 `preload: "mouseover"`) | hover -> 1 prefetch; click served from it | same | same |
| same, with the lib's `HtmxConfig({ extensions: "sse, preload" })` in head | same | same | same |
| bare `hx-optimistic` (pre-7.2.0 `optimistic: true`) | inert: needs a selector value | inert | extension removed, renamed `hx-pending` (valued form works) |

So the deletion was right for `optimistic` (the boolean shape never worked, and the name changed at 4.0.0) and wrong for `preload`. Demand is 0 either way: the 58-repo census finds 23 `preload: true` hits, all HSTS config, and 0 htmx `preload`/`optimistic`/`extensions:` sites.

## Why it matters

impact 1 × pain 1 × reach 1. Decision-closure: 6 teaching and test lines state a runtime fact that is false, so a later decision (L-217 rejected the prefetch verb on this premise; L-325, L-344 rest on it) inherits it. Evolvability: the runtime-grammar contract (guardrail 10) does not say whether extension grammar is in scope, and the lib both enables an extension in its example and denies it in its tests.

## Rough idea (not a design)

Layer: prose-only correction (no public shape change). Reword the two test descriptions and `CLAUDE.md:276` / `htmx.md:412` to "not in htmx core; extension attributes are outside fluent's typed grammar", add an erratum line under the 7.2.0 entry, and drop the extension names from the `HtmxConfig` example (or scope the contract to include extensions, which would be a decision-gated reopening of the instruction-set boundary). No re-add: 0 demand.
