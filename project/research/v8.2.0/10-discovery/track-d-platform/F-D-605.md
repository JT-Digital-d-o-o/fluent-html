# Release records omit the platform-contract changes and keep stale labels

## Problem

A CHANGELOG is where a consumer, or an agent upgrading a repo on demand, learns what a release was verified against. Across the three packages:

**fluent-html.**
- The htmx pin moved twice: 258621a (2026-07-21) added `4.0.0-beta5`, recorded at `CHANGELOG.md:369`; c60a484 (2026-08-14) moved to `4.0.0-beta6`, with **0** mentions of `beta6`. The newest htmx target the CHANGELOG states is beta5, 48 days stale, while the template and 13/16 apps serve 4.0.0.
- The 7.2.0 deletion of `preload`/`optimistic` cites "the htmx 4.0.0-beta4 runtime" (`:168`) while the pin was beta5.
- The `[Unreleased, 7.0.0]` header (`:230`) sits below 6 released headers (7.0.1, 7.1.0, 7.2.0, 8.0.0, 8.1.0-a, 8.1.0).
- `@playwright/test` 1.61.1 and `typescript` ^5: 0 mentions.

**eslint plugin.** `CHANGELOG.md:52` (the 4.0.0 entry) says the rewritten README teaches "variants are `.on()`/`.at()`". The shipped README and USAGE have 0 `.on(`/`.at(` mentions, so the record contradicts the artifact.

**extractor.** 83e81d2 (2026-08-03, "rebuild stale dist: 3.0.0 variant-object scanning never shipped; add dist-parity guard") has 0 CHANGELOG lines, and the header is still `[Unreleased, 3.0.0]`. Anyone who installed between 43409f4 and 83e81d2 got a dist without object-variant scanning, and the record does not say so.

**Correction to recon 04 side-finding 4.** 11 of the plugin's 32 rules (incl. `prefer-htmx-api` and `no-superfluous-view-return-type`) have 0 CHANGELOG lines, but all 11 were added 2026-03-07..11, before the CHANGELOG began (1.7.0, 2026-06-24). That part is a missing rule index, not an unlogged change.

None of the 3 repos runs anything over its CHANGELOG. The plugin and the extractor have no workflows at all (F-D-503).

## Evidence (executed)

- **Pin history.** `git log -G` over `package.json` for the four pins: 258621a, f840c9f (tailwindcss 4.3.3, recorded at `:337`), c60a484. `git show 258621a:package.json` gives `htmx.org: 4.0.0-beta5`, and so does `c60a484^`.
- **Mention counts** (`grep -c` in the lib CHANGELOG): `beta6` 0, `beta4` 2, `4.0.0-beta` 4, `htmx.org` 0, `4.3.3` 1, `1.61` 0.
- **Header order** (`grep -n "^## "`): the Unreleased 7.0.0 header at :230 follows :5, :43, :87, :148, :171 and :188.
- **Plugin.** `grep -n "\.on(\|\.at(" README.md USAGE.md` gives 0. For each of the 11 rules, `git log --diff-filter=A` dates fall before c111bb2 ("release: v1.7.0 ... + CHANGELOG", 2026-06-24).
- **Extractor.** `grep -n "83e81d2\|stale dist\|dist-parity" CHANGELOG.md` gives 0.

## Why it matters

impact 1 x pain 1 x reach 2 (every on-demand upgrade of the 46 consumer repos starts from these files).

- **evolvability**: the htmx target an upgrade must match is not recorded where upgrades look.
- **context-economy**: a stale record costs the reader a probe to discover the truth.

## Rough idea (not a design)

ci layer (8.1.x). A small CHANGELOG check in each repo:
- no `Unreleased` header below a released one;
- the package.json version has a header;
- a diff that changes the `htmx.org`, `tailwindcss` or `@playwright/test` pin must touch the CHANGELOG.

One line per pin in the current release header closes the beta6 gap.
