# Dev checks latch NODE_ENV before dotenv

## Problem
`devChecks` is computed once, at module evaluation: `export let devChecks: boolean = readDefault()` (`src/core/dev-checks.ts:45`), `readDefault` returning `process.env.NODE_ENV !== "production"`. The template's server entry imports `fluent-html` at `server.ts:5` and the config module at `:8`; config imports `env.ts`, whose `dotenv.config()` (`:28`) is what sets `NODE_ENV` when the shell did not, a case `env.ts:13-17` supports explicitly. ESM evaluates imports in order, so fluent-html reads `NODE_ENV` before dotenv writes it. Any launch where `NODE_ENV=production` lives only in `.env` (e.g. `npm start`, `package.json:10`, on a host other than the cPanel app) runs production with the guards on: the process reports production (`isProdEnv()` true) while fluent-html behaves as development.

## Evidence (executed)
- `esm-order/server.mjs` imports `dist/src/index.js` first, then `env.mjs` (sets `process.env.NODE_ENV ??= "production"`, the dotenv stand-in), renders `Div("x").p("4")`, then calls `.bg("red-500")`:
  - `env -u NODE_ENV node server.mjs` -> `NODE_ENV=production loaded=true -> mutate-after-render THROWS (dev checks ON): <div>.addClass() mutates a tag that has already been rendered…`
  - `NODE_ENV=production node server.mjs` -> `mutate-after-render: no throw (dev checks OFF)`
- Cost of the guards on 8.1.0, dev vs prod paired medians on "Build+render realistic (per req)": x0.872, x0.894, x0.921, x0.920 (4 independent runs of 5-7 reps; 7.0.1: x0.901); on pre-built renders x0.95-1.00. So the latched state costs 8-13% of per-request build+render and turns a drifting-markup bug into a thrown 500 in production.
- The template's own cPanel deploy is safe: `write-server-config.sh:112` writes `PassengerEnvVar NODE_ENV`, so the shell carries it before import. Reach is the other launch paths (npm start with a production `.env`, containers or hosts configured through `.env` only).

## Why it matters
impact 2 x pain 2 x reach 1 / S. The CHANGELOG (7.0.1, "Production (`NODE_ENV=production`) is unchanged") and `setDevChecks` JSDoc promise the guards are off in production; with dotenv-based config the promise depends on import order, which no layer checks. A host change (the template already supports `.env`-only NODE_ENV) silently flips production to guarded mode. Dimensions: silent-failure, evolvability.

## Rough idea (not a design)
Runtime layer in the lib: resolve the default on first use (first render epoch or first `Tag` construction) instead of at module evaluation, keeping `setDevChecks` as the explicit override. Alternative one layer up: the template calls `setDevChecks(!isProdEnv())` right after `dotenv.config()` in `env.ts`. No prose to delete.
