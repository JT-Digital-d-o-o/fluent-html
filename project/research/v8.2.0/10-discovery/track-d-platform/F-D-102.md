# Beta-pinned apps lose keystrokes in `.search`, and no layer knows the runtime is wrong

`$S` = `<scratch>/wave1/D1`.

## Problem

The template's `.search` verb debounces, then morphs `#main-content`, which contains the input the user is typing in. On htmx 4.0.0-beta4..beta6 a morph copies the server's `value` onto the input even while it has focus; 4.0.0 stopped doing that. A search response that lands between keystrokes therefore rewrites the input to the older query, and the `changed` modifier then sees no change, so the user's latest keystroke is gone and the results stay stale. fl-um and na-cent (fluent-html 8.1 @ 9d86871, htmx beta6) and workshop-toni (7.0.0, beta4) run exactly those runtimes. Each app's own provenance test (`served bundle == package.json pin`) passes, because the pin itself is the stale part, and neither fluent-html nor the template states which htmx their grammar is verified against.

## Evidence (executed)

Probe: a lib-rendered filter form whose input carries the `.search` attribute set (`trigger: "input changed delay:300ms"`, `sync: "replace"`, `target: "#main-content"`, `swap: "outerMorph"`, `include: "closest form"`); the server echoes `q` into the input and filters a list, 300 ms latency. Playwright focuses the input, types `ab`, waits 450 ms (debounce fired, request in flight), types `c`, waits 1.5 s.

| Bundle | Final input value (5 trials) | Results | Requests sent |
|---|---|---|---|
| 4.0.0-beta4 | ab, ab, ab, ab, ab | `abacus,abc-co` (for "ab") | `ab\|ab` × 5 |
| 4.0.0-beta6 | ab, ab, ab, ab, ab | `abacus,abc-co` | `ab\|ab` × 5 |
| 4.0.0 | abc, abc, abc, abc, abc | `abc-co` | `ab\|abc` × 5 |

Root cause is the same delta as F-D-101 row 4 (4.0.0 htmx.js:2194, release note #3985). Live exposure: `.search(` app-authored sites in beta-runtime canonical apps: na-cent 3 (imenik.components.ts:244, projects.components.ts:153, transactions.components.ts:695), workshop-toni 2 (payments.admin-list.view.ts:82, event-log.view.ts:51), fl-um 0. `busyWhileRequesting` (swap-verbs.ts:219-224) disables only buttons and forms, so the input stays typeable during the request.

What declares the runtime today: fluent-html README 0 version statements (7 htmx mentions), no `peerDependencies`; the behaviors runtime's skew handshake (runtime.ts:476-481) compares its own asset stamp only; the template's provenance test (`htmx-grammar-contract.test.ts:167-176`) checks `public/js/htmx.min.js` byte-equals the app's pin, which fl-um and na-cent satisfy with beta6. A compatibility source already exists: `require("fluent-html/package.json").devDependencies["htmx.org"]` resolves from the template (`./package.json` is exported) and returns `4.0.0-beta6` today, which would also have flagged the lib's own lag (F-D-101) on 2026-08-28.

Install-time alternative, executed: an optional peer `htmx.org: "4.0.0"` on a packed fluent-html makes `npm install` fail with `ERESOLVE could not resolve ... peerOptional htmx.org@"4.0.0" from fluent-html@8.1.0` for an app pinning `4.0.0-beta6`, and installs clean with 4.0.0. All 16 canonical repos use npm lockfiles, so that variant is install-breaking.

## Why it matters

impact 2 × pain 2 × reach 2. Silent-failure: the user loses input with no console message, no failing test, and a green provenance check. Reach: 2/16 canonical apps (5 sites) plus 12 pre-7 apps on beta4 if they adopt the verbs on upgrade. Evolvability: an app scaffolded before a bump keeps the old runtime indefinitely, because nothing compares its pin with what the grammar targets.

## Rough idea (not a design)

Layer: boot/ci in the template (no lib API): the provenance test gains one assertion, app pin == fluent-html's verified htmx, message naming `npm i htmx.org@<x> && npm run htmx:vendor`. Depends on F-D-101 so the lib's pin is the GA the template serves. The fleet fix for na-cent/fl-um/workshop-toni is a re-vendor. Prose deletable: none today (the doctrine never mentions runtime versions), which is the gap.
