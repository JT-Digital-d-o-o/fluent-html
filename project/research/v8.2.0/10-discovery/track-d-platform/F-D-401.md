# Object variants made variant-styled construction 2.4x slower than the lambdas they replaced

## Problem
7.0.0 (commit 7f52506) replaced `.on("hover", t => t.bg(...))` lambdas with typed variant objects (`.hover({ bg: ... })`). The runtime path behind every tier-1 variant method and `.variant()` is `applyVariantObject` (`src/core/variant-object.ts:65-90`): per call it allocates `Object.entries(obj)` pairs, a `try/finally`, and per key a spread `[...spec.pre, ...valueArgs(value)]` plus the `emitClasses` output array, iterated with `for...of`. The object-variants design measured only TypeScript check cost (`project/pm/llm-styling/object-variants/design.md:34`, "object 0.16-0.17s vs lambda 0.12-0.13s"); runtime construction was never measured, and `bench/render.ts:219-220` times the variant-heavy page as `render(variantPage)` on a tree built once, so construction cost is invisible to the bench. Comparing 8.1.0 against the 7.0.1 numbers cannot see it either: 7.0.1 already contains the regression.

## Evidence (executed)
`node variant-xver.mjs <dist> lambda|object`, the bench's own variant-heavy page (100 buttons, 5 variant groups) built per op, same `measure()` method as `bench/render.ts` (200 ms warm-up, median of 7 samples), `NODE_ENV=production`, 5 interleaved rounds, load1 3.64-4.31 on a 10-core M1 Pro with other agents running:

| build | build ops/s | build+render ops/s | render-only ops/s |
|---|---|---|---|
| pre-7.0 lambdas (ce7768e = 7f52506^, canonical names) | 16,243 (spread 18.2%) | 8,908 (13.4%) | 51,650 |
| 7.0.1 objects (bd04a2d) | 4,574 (3.8%) | 3,656 (4.9%) | 50,022 |
| 8.1.0 objects (lib dist, not rebuilt) | 4,570 (10.9%) | 3,639 (9.6%) | 49,179 |
| 8.1.0 + scratch applyVariantObject rewrite | 8,831 (1.9%) | 5,796 (6.1%) | 48,985 |

- Emitted class lists: 1 distinct output across all 4 builds (sorted `class` of the first button identical), so the pages are the same bytes.
- Per call, `node single-variant.mjs` (100 elements, one `.hover({ bg: "gray-100" })` each): lambda +67 to +82 ns per element, object +191 to +207 ns, rewrite +117 to +123 ns (3 runs each).
- `node --cpu-prof prof/obj.mjs` (3 s, 13,297 builds): self time `applyVariantObject` 49.4%, the tier-1 wrapper closure 19.1%, `addClass` 11.7%, `valueArgs` 3.6%, `emitClasses` 3.2%.
- The rewrite (for-in over the object, `[value]` instead of the double spread when `spec.pre` is empty, indexed loop over the emitted classes) renders byte-identical output for nested variants and `.variant("data-[state=open]", …)` (checked by string equality).
- Reach: app-authored canonical-era variant-method sites (`hover focus focusVisible focusWithin active disabled checked dark first last odd even groupHover peerChecked before after sm md lg xl xl2 variant`) = 2,780 in 16/16 canonical repos (`01-census-perrepo.json`, `app_authored_dedup`); dedup canonical-era 2,887 (3.5% of 81,635 sites).

## Why it matters
impact 2 x pain 2 x reach 3 / S. Every interactive element in a canonical app carries one or more variant groups, and that construction runs per request (SSR rebuilds the tree). The page shape the bench already carries went from 112 us to 275 us per build+render. The loss is silent: guardrail 2 (sync render hot path stays fast) had no scenario that builds variants, so the 7.0.0 API change shipped a 2.4x construction regression that every later release inherited. Dimension: silent-failure (perf), verification-loop (no measurement could catch it).

## Rough idea (not a design)
Runtime layer, no public-shape change, output byte-identical: rewrite the `applyVariantObject` loop (the scratch version recovers x1.93 build / x1.59 build+render; precomputing a per-key emitter closure could close the rest of the gap to 16K). Pair it with a ci-layer guard: a build+render variant scenario in `bench/render.ts` (see F-D-403). No guideline prose involved; nothing to delete.
