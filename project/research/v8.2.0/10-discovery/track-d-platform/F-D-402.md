# Route param substitution builds a new RegExp per param per call

## Problem
Every call of a param'd route callable (`routes.detail({ id })`, which the template's swap verbs call per link and button) and every `.resolve({ id })` runs `substituteParams` (`src/routes.ts:387-411`), which for each param builds `escapeRegExp(key)`, a template literal and `new RegExp(..., "g")` (`:397`), runs `replace`, then `assertNoUnresolvedParams` runs a second regex over the result (`:348-352`). Nothing about the pattern depends on the call: the template is fixed at `defineRoutes` time. List pages resolve one or more routes per row, so this cost scales with row count.

## Evidence (executed)
`NODE_ENV=production node micro-route.mjs` (1e6 calls, median of 7):

| call | 8.1.0 dist | precompiled prototype (ropt2) |
|---|---|---|
| `routes.list.resolve()` (no params) | 3 ns | 5 ns |
| `routes.detail.resolve({ id })` | 498 ns | 98 ns |
| `routes.deep.resolve({ org, team, id })` | 1,382 ns | 257 ns |
| `routes.detail({ id })` -> HTMX | 466 ns | 102 ns |
| `hx(routes.detail({ id }), { target, swap, pushUrl })` | 592 ns | 225 ns |

`node route-page.mjs <dist>`: 50-row member list, each row a detail link (`setHref(routes.detail.resolve({ id }))`) and an edit button (`setHtmx(hx(routes.edit({ id }), …))`), build+render per op; control = the same rows with URLs resolved once up front (rendered bytes asserted equal). 3 runs each:
- 8.1.0: 7,797 / 7,887 / 7,912 ops/s live vs 13,178 / 13,191 / 13,221 pre-resolved: route substitution is 40% of the request's build+render time (126 us vs 76 us).
- Caching the compiled RegExp per key (3-line change, `ropt/`): 9,382-9,626 ops/s (+18%).
- Precompiled parts + keys at `defineRoutes` with a fallback to the current path for extra, missing or splat params (`ropt2/`): 10,838-12,344 ops/s (+49%), within 7-10% of the pre-resolved ceiling.
- Parity: `node --test dist/test/routes.js dist/test/routes-ids-parity.test.js dist/test/htmx.test.js` = 214/214 on both 8.1.0 and ropt2. `node route-parity.mjs`: 1,950 cases (numbers, negatives, decimals, NaN, 1e21, strings with `/ ? # : % *`, empty, undefined; repeated keys; `:idCard` vs `:id`; extra and missing keys; splat) on `.resolve` and the callable: 0 differences in results or error messages.
- Reach: 640 app-authored canonical-era `.resolve` sites in 16/16 canonical repos (`01-census-perrepo.json`); 269 of 823 route defs in the 16 canonical repos' 272 `*.routes.ts` files put a `:param` in the path (same-line heuristic, lower bound). Swap-verb calls on param'd callables come on top.

## Why it matters
impact 2 x pain 2 x reach 3 / S. The cost lands on the pages that scale (lists, tables, dashboards), grows linearly with params and rows, and is invisible to the bench: its realistic page uses `assetUrl(...)` for every URL (`bench/render.ts`), so no scenario resolves a param'd route. Dimension: silent-failure (perf regression that no layer reports).

## Rough idea (not a design)
Runtime layer, no public-shape change, byte-identical output: compile each param'd template once at `defineRoutes` (literal parts + key list) and substitute by concatenation; route anything irregular (extra keys, missing keys, splat) through today's `substituteParams` + `assertNoUnresolvedParams` so every error message stays as it is. Add a param'd-route list scenario to the bench (F-D-403). No prose to delete.
