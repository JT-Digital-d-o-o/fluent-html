# The documented npm install resolves fluent-html 5.7.0, three majors behind, and the extractor's documented install returns 404

## Problem
All three packages document a registry install. The registry holds a February snapshot of two of them and nothing for the third, while every consumer installs from GitHub. Whoever follows `README.md:10` (`npm install fluent-html`) gets the 5.7.0 API: pre-7 names (`.background`, `.padding`), no `defineTheme`, no object variants, no `defineRoutes`. The npmjs.com page for `fluent-html` renders the 5.7.0 README, which teaches `.setClass(...)` 37 times.

## Evidence (executed)
- `npm view fluent-html`: 5 versions (`... 5.4.2, 5.4.3, 5.7.0`), `dist-tags.latest` 5.7.0, modified 2026-02-13, `deprecated` empty. The lib's git tags stop at `v5.7.0`.
- `npm install fluent-html` in an empty scratch project -> `5.7.0`. `typeof` on the installed API: `defineTheme`, `defineRoutes`, `Tag.prototype.bg`, `.hover`, `.variant`, `.on` are all `undefined`; `.background` and `.setClass` are functions.
- The 8.1 README's ```ts blocks use 31 method names that exist in 8.1.0; 17 are absent from 5.7.0 (`text font px py bg p list whenElse whenMatch transition hover focus md variant cssProp cssClass neg`). They call 17 functions that exist in 8.1.0; 5 are absent (`defineRoutes Partial MatchValue ForEachKeyed defineTheme`).
- The 5.7.0 README (1,951 lines, the npmjs.com page): `.setClass(` 37, `.padding(` 24, `.background(` 11, `.textColor(` 8, `.addClass(` 8, `.bg(` 0.
- `npm install --save-dev eslint-plugin-fluent-html` -> 1.4.0 with 13 rules (4.1.0 has 32). `npm install --save-dev fluent-html-tailwind-extractor` -> `E404 Not Found`.
- Fleet: 93 lockfiles under the org root; 0 resolve `fluent-html` from registry.npmjs.org; 1 (jt-chess, pre-7) resolves `eslint-plugin-fluent-html-1.4.0.tgz`. The 55 fluent-html dependency specs in the dedup corpus are all `github:`, git URLs, `file:` or workspace `*`.

## Why it matters
Prior alignment: the registry page is the public artifact a model or a web search meets first, and it documents an API the current lib rejects with anonymous TS2339s (recon 02 probes #22-23: `.textColor`, `.on`). Reach 2: the fleet is unaffected (0/93 lockfiles), but the install line is the first code line of the README that 2/2 blind runs opened in recon 02 (2 reads each), and any project outside the template scaffold follows it. Pain 3: the failure is a wholesale wrong API, not a single error.

## Rough idea (not a design)
Either publish 8.1.0 / 4.1.0 / 3.0.0 (which also unblocks L-292's semver ranges) or, at minimum, `npm deprecate` the published lines with a pointer to the git spec and change the three README install lines to the spec consumers actually use. No guideline prose involved.
