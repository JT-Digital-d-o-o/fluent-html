# hxResponse(view).build() returns rendered HTML as a plain string that every View sink re-escapes

## Problem
`HxResponse.build()` (src/patterns.ts:343-346) returns `{ html: render(this._content), headers }` with `html: string`. In the template world the only way to send it is a View sink (`reply.renderView`, `renderPage`, `Partial`, children), and a `string` View is text, so the already-rendered markup is escaped a second time and the browser shows the page source. `build()` also calls `render()` without options, so any `<script>`/`<style>` in the content never receives the request's CSP nonce. tsc accepts it (`string` is a `View`), no lint rule looks at it, and a substring assertion in a test passes on the escaped body.

The guidelines assemble the bug from two taught snippets: fastify.md:201-203 / htmx.md:519-525 teach `const { html, headers } = ...build(); reply.renderView(html)`, htmx.md:538-541 teaches `hxResponse(view)...build()` with a real view, and guidelines/CLAUDE.md:468 whitelists "pre-rendered strings" as legitimate renderView input.

## Evidence (executed)
- Reproduction against the fleet repo's own installed library (workshop-toni pins 7.0.0; the escape path is unchanged in 8.1.0):
  ```
  node -e: hxResponse(Div(H1("Family")).setId("main-content")).pushUrl("/family").build()
  build().html:            <div id="main-content"><h1>Family</h1></div>
  renderView(html) body:   &lt;div id=&quot;main-content&quot;&gt;&lt;h1&gt;Family&lt;/h1&gt;&lt;/div&gt;
  ```
- Live site: workshop-toni/src/app/family/family.controller.ts:50-54 answers every successful htmx create/update of a storyteller with `reply.renderView(html)` where `html = hxResponse(FamilyListPage({...})).pushUrl(...).build().html`. The integration test at tests/integration/family.test.ts:90-100 asserts only `toContain("joined the family")` and `hx-push-url`, both true of the escaped body.
- Census (`build-census.mjs`, TS AST, 58-repo dedup corpus, non-test files): 68 `hxResponse(...).build()` sites; 64 destructure `html`; 67 pass `Empty()` (so `html` is always "" and the only purpose is the headers); 1 passes a real view, and that 1 hands `html` to `renderView` (escaped). 0 sites wrap it in `Raw()`.
- The template itself no longer uses `build()`: its 2 call sites use `.getHeaders()` (templates/full-stack/src/core/behaviors/runtime.ts:89, app/payments/payments.controller.ts:224).

## Why it matters
impact 2 (a whole page renders as source text after a successful mutation) x pain 3 (tsc, lint and the repo's own integration test are all green) x reach 2 (the build() shape sits in 68 sites across the fleet; 1/1 non-empty use is broken) / effort M. Hurts silent-failure and verification-loop: the escaped body satisfies substring assertions, so the test layer certifies the bug.

## Rough idea (not a design)
The `html` half of `build()` has one real consumer in the fleet and it is broken, so converge on `getHeaders()` (the template's pattern): drop `html` from `build()` in 9.0.0 with a codemod (`const { headers } = x.build()` to `const headers = x.getHeaders()`, `renderView(html)` with Empty content deleted, the non-empty case to `renderView(view)`). Strongest layer: type (the removed field fails to compile). Prose deleted: guidelines/CLAUDE.md:468 "pre-rendered strings", fastify.md:201-203, htmx.md:519-525 can be deleted today regardless of the lane.
