# drawer trapFocus escapes on WebKit

## Problem

`trapTab` steps in only at the ends of the drawer's focusables list. For any Tab in the middle of the list it returns `false` (`runtime.ts:175`) and leaves the move to the browser's native order. WebKit's default keyboard navigation skips links and buttons (Safari's "Press Tab to highlight each item" is off by default). A drawer of links therefore sends the first Tab to the next text field outside the drawer, behind the backdrop.

The library's acceptance matrix has a WebKit column, behind `ACCEPT_ENGINES=all`. Before this run that column had never executed: WebKit was not installed locally (recon 03 §5), and 0 CI workflows run the matrix. Run now, it fails.

## Evidence (executed)

WebKit 26.5 (playwright webkit-2311, installed under the scratch `PLAYWRIGHT_BROWSERS_PATH`) was run on a scratch copy of `test/acceptance` that changes only the port and engine selection:

```
✘ [webkit] rows.spec.mjs:205 row 15: focus trap cycles within the open drawer
  expect(locator('#drawer-btn')).toBeFocused()  Received: inactive
68 passed, 1 failed
```

`trap.mjs` tests 2 drawer shapes (link + button; 3 links), each with a text input outside the drawer. It opens the drawer with `focusFirst` and presses Tab 4 times:

```
chromium shipped T1  l1 > b1 > l1 > b1 > l1        escaped: false
firefox  shipped T1  l1 > b1 > l1 > b1 > l1        escaped: false
webkit   shipped T1  l1 > search > l1 > search > l1  escaped: true
webkit   shipped T2  l1 > search > l1 > search > l1  escaped: true
```

The trap lets focus alternate between the drawer and the page's search field. Text typed then lands in an input under the overlay.

Prototype (scratch copy of the lib): `trapTab` always calls `preventDefault()` and moves to `items[(at ± 1) mod n]`, or to the first/last item when focus is outside the drawer.
- Probe: 6/6 shape-engine pairs hold.
- Matrix: webkit 69/69, chromium 69/69, firefox 68/69. The Firefox failure is the pre-existing row-28 charset console error.
- Unit tests: 2159/2159.
- Asset size: 6108 B min, within the 6144 B budget (combined with the F-A-601 change).

Fleet: there is 1 `trapFocus: true` drawer, the mobile sidebar in `na-cent/src/shared/views/app-shell.ts:395-399`.

The same WebKit run re-executed 9 earlier Chromium-only DOM probes (F-A-205/401 colspan, F-A-302, F-A-402, F-A-401 inert, F-A-403, F-A-406, F-A-407, F-A-503, F-A-504). Outcomes were identical on WebKit and Firefox, so the trap is the only engine-dependent defect found.

## Why it matters

- impact 2: a broken a11y guarantee on Safari's default settings; focus and typed input go behind a modal-looking overlay.
- pain 2: invisible in Chromium-only development and CI.
- reach 1: 1 fleet site.

It hurts silent-failure, and verification-loop: the contract's third engine was declared, never run, and red.

## Rough idea (not a design)

The enforcement layer is runtime, plus CI.
- Runtime: while the trap is armed, own every Tab press. Cycle within `focusables(drawer)` instead of deferring to native order.
- CI: run the WebKit and Firefox columns at least on `publish.yml`. F-D-503 owns the CI half.

No prose changes.
