# htmx 4 evaluates js:/javascript: values in five fluent sinks

## Problem
htmx 4 treats a value that starts with `js:` or `javascript:` as code in several places: the request action (the `hx-get`/`hx-post` value), `hx-confirm`, `hx-vals`, and it navigates `location.href` to `HX-Redirect` and issues an ajax call (whose action is then evaluated) for `HX-Location`. fluent-html has a runtime URL sanitizer (`sanitizeUrl`, S-03 "URL setters scheme-sanitize"), but it runs only for the typed `_sk` URL attributes; the htmx endpoint (serialize.ts:140), `confirm`, string `vals`, and the `HxResponse` URL headers bypass it, and `sanitizeUrl` does not know htmx's `js:` scheme at all. The `ResolvedRoute`/`ExternalHref` brand on `hx()` is a type-level cast (`externalUrl`, `assetUrl`), so the same value that `A().setHref(externalUrl(x))` neutralizes to `about:blank` runs as code in `setHtmx(hx(externalUrl(x)))`. The `HxResponse` URL setters take bare `string` with no brand.

This is also a gap in the runtime-grammar contract (seed: "no test asserts emitted htmx names exist in the pinned bundle"): a names-only contract passes all of these, because the attribute names are valid; the value grammar is what the bundle executes.

## Evidence (executed)
`js-sink-probe.mjs`, payload `window.__pwned++`, click the trigger, both bundles, with and without the template CSP:
```
                                         beta6/none  beta6/template  4.0.0/none  4.0.0/template
hx endpoint externalUrl('javascript:..')     1            0               1            0
hx endpoint assetUrl('js:..')                1            0               1            0
hx confirm 'js:..'                           1            0               1            0
hxResponse.redirect('javascript:..')         1            0               1            0
hxResponse.location('js:..')                 1            0               1            0
hxResponse.location('javascript:..')         1            0               1            0
hxResponse.location({path:'js:..'})          1            0               1            0
control: setHref(externalUrl('javascript:..'))  0         0               0            0
setHref('js:..') / setAction('js:..') under hx-boost  0 (htmx boosts same-origin URLs only)
```
`vals-probe.mjs` (4.0.0): `hx(assetUrl("/ok"), { method: "post", vals: "js:{a: (...)}" })` emits `hx-vals="js:{a: ...}"` and executes (1).
Under the template CSP every case is blocked, by `'unsafe-eval'` absence ("Evaluating a string as JavaScript violates...") or by the javascript: URL rule. `sanitizeUrl` in node: `"js:alert(1)" -> "js:alert(1)"`, `" js:alert(1)" -> unchanged`, `"javascript:alert(1)" -> "about:blank"`.
Reach: 51/58 fleet repos and 16/16 canonical-era repos configure a CSP (grep contentSecurityPolicy); the 7 without are pre-7 (buzzin, cms, gzs/inovacije, jtdigital-landing-page, pm-gui, pregled-nepremicnin-dashboard, tela). 9 canonical hxResponse URL-header sites all take route-resolved or provider URLs today; 0 user-controlled values found.

## Why it matters
impact 3 (script execution from a value the API types as a URL or a message) x pain 2 (nothing errors; the typed setter path is protected, so the protection looks uniform) x reach 1 (the template CSP blocks every case; exposure is apps without it and any future CSP that adds 'unsafe-eval') / effort S. Hurts silent-failure resistance and invariant safety (the brand promises what only one of two runtime paths enforces).

## Rough idea (not a design)
Runtime layer, 8.1.x-eligible (bytes change only for values that execute today): add `js:` to the blocked schemes in `sanitizeUrl`, apply it to the endpoint in `buildHtmx` and to `HxResponse.redirect/location/pushUrl/replaceUrl` (including `HxLocationConfig.path`); dev-throw when `confirm` or a string `vals` starts with `js:`/`javascript:` (behaviors v4 already forbids inline JS, S-21). Type layer in 9.0.0: brand the `HxResponse` URL setters `ResolvedRoute | ExternalHref` like `hx()`. Pin all five sinks in test/security.test.ts.
