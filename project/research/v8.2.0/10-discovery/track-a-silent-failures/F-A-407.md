# setPopovertarget on `<a>` compiles and does nothing

## Problem
The HTML popover invoker attributes (`popovertarget`, `popovertargetaction`) work only on `<button>` and `<input type=button|submit|reset|image>`. fluent-html defines `setPopovertarget`/`setPopovertargetaction` on the `Tag` base, so they compile on all 133 factories. Its own JSDoc names `<a>` as an invoker (`tag.ts:542`), and the 6.1.1 CHANGELOG example uses `A("Account").setPopovertarget(...)` (`CHANGELOG.md:527`). An `<a popovertarget>` renders the attribute and the browser ignores it. `setForm` on the base has the same shape: it renders `form=` on a `<div>`.

## Evidence (executed)
- **Browser (Chromium).** `A(...).setPopovertarget(m1)` then click leaves `:popover-open` false. The same wiring on a `Button` sets it true.
- **Setter audit.** 421 setter slots were rendered and checked against the element's spec attribute list. Only the Tag-base setters emit attributes the element does not define:
  - `setPopovertarget`/`setPopovertargetaction`/`setForm` on `div`
  - `title`, `popover`, `dir`, `translate` and others on SVG shapes
- **Static layers.** tsc and eslint accept `A(...).setPopovertarget(id)`.
- **Fleet.** 15 sites, all on `Button`. Reach is 0 live instances; the teaching carries the hazard.

## Why it matters
impact 2 × pain 2 × reach 1 / effort S = 4. The surface the library ships and the example it teaches both admit an invoker that the platform ignores. The popover never opens and every layer is clean.

## Rough idea (not a design)
Type layer, 9.0.0:
- Move the two invoker setters to `ButtonTag`/`InputTag`, so an `<a>` receiver gets TS2339.
- Move `setForm` to the form-associated classes.
- The measured codemod dry run is 0 of 15 fleet sites.

Now, as a doc-only fix: correct the `tag.ts:542` JSDoc and the `CHANGELOG.md:527` example.
