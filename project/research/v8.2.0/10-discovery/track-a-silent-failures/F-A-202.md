# The lint-prescribed named variant object is silently dropped by the extractor

## Problem

An agent that extracts a variant style object gets this **error** from the template's lint config
(verbatim, eslint 4.1.0):

> `'pressed' is passed to .hover() without \`satisfies VariantStyleObject\` on its declaration — key
> typos in it are not compile-checked (they throw at render time). Declare it as \`const pressed = {
> ... } satisfies VariantStyleObject\`.`

Following it produces:

```ts
const pressed = { bg: "warning-700" } satisfies VariantStyleObject;
Button("Retry").bg("warning").hover(pressed);                 // renders class="... hover:bg-warning-700"
Div("Panel").variant("aria-expanded", expanded);              // renders class="aria-expanded:bg-surface-3"
```

The extractor's tier-1 and `.variant` scanners accept only an inline `{…}` argument and treat
anything else as "a same-named non-fluent call" (`extract.ts:277`, `:291`): no class, no ledger
row, so the default `onUnresolved: "error"` never fires. The hover/aria state ships unstyled.
The spread form of the same object (`.hover({ ...pressed })`) does produce a ledger row and fails
the build, so the loud path and the lint-endorsed path disagree.

## Why it matters

impact 3 (a whole interaction state never styles) x pain 3 (passes tsc, eslint, css build and dev

## Rough idea (not a design)

CI/build layer: a style argument that is not an object literal on a tier-1 or `.variant` call becomes
an unresolved ledger row (so the default policy fails the build and names the site), or the
extractor resolves a same-file `const x = {…} satisfies VariantStyleObject` and emits its classes.
Pin both in `extract.test.ts`. No guideline prose needed.
