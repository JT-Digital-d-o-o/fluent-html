# Form<T>.textarea drops one leading newline per render

## Problem
The HTML parser discards a single LF that immediately follows the `<textarea>` (and `<pre>`/`<listing>`) start tag. A renderer that wants the text content to round-trip has to emit one extra LF when the content itself begins with LF. fluent-html emits the content verbatim, so a value that starts with a newline loses it at parse time. The typed form binding hits this on the path the guidelines advertise for 422 re-renders ("typed values kept"): `FormBinding.textarea` (forms.ts:492) renders `Textarea(String(v))`, so each failed submit or edit-save cycle eats one leading newline of the user's text.

This is a separate mechanism from the sibling-separator issue (L-030): no separator is involved; a single-child textarea loses data.

## Evidence (executed)
`ws-probe.mjs` (dist 8.1.0, Chromium):
```
Textarea("\nHello")                  html <textarea>\nHello</textarea>          value "Hello"
Textarea("\n\nHello")                html <textarea>\n\nHello</textarea>        value "\nHello"
Form<T> values {body:"\nHello"}      html <textarea id="body" name="body">\nHello</textarea>   value "Hello"
Pre("\nline1\nline2")                pre.textContent "line1\nline2"
round trip (value fed back from the DOM each cycle):  "\n\n\nNotes" -> "\n\nNotes" -> "\nNotes" -> "Notes"
```
The second row doubles as the fix check: one extra leading LF restores the value exactly.

Reach: 71 `.textarea(` / `Textarea(` construction sites in non-test files across 14 canonical-era repos (grep; website-sales-funnel-automation-system 24, competify 10, everyframe-composer 9, gzs/stem-50 8, competition 5, others 1-2). 0 lib tests cover a textarea value that starts with a newline (grep over test/).

## Why it matters
impact 2 (silent user-data loss that compounds per save) x pain 2 (only values that start with a newline; nothing errors) x reach 2 (every prefilled textarea in 14 repos, through the lib's own binding) / effort S. Hurts silent-failure resistance.

## Rough idea (not a design)
Runtime layer in the serializer: when the first text descendant of a `<textarea>` starts with `\n`, emit one extra `\n` after the open tag. Bytes change only for content that currently loses data, so 8.1.x-eligible. `<pre>` needs a decision (authors of `Pre(`\n...`)` template literals may rely on the strip); keep it textarea-only unless decided otherwise. Pin with a Playwright acceptance row that round-trips a textarea value through Form<T>.
