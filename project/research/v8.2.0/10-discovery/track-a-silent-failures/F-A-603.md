# Form<T>.checkbox groups re-render all-checked

## Problem

`f.checkbox(name, value?)` accepts a submitted value, which is how a checkbox group is written:

```ts
Form<{ tags: string[] }>({ values: { tags: saved } }, (f) =>
  Div(ForEach(["a", "b", "c"], (o) => Label(f.checkbox("tags", o), Span(o)))))
```

The binding sets `checked` from `Boolean(values[name])` (`forms.ts:508`) and never compares it with `value`. Any non-empty field value checks every box. So do `[]`, which is truthy, and a single urlencoded `"b"` from a 422 re-render. Every box also gets `id="tags"`, because `controlId(name)` takes no value. `radio` (`:510-514`) already solves both problems. `select` compares `String(selected) === o.value`, so a `string[]` field marks no option selected.

## Evidence (executed)

`group.mjs`: render, then load into each engine, then read `checked`, `FormData` and the id count.

```
chromium | saved ['a'] (edit form)        checked a,b,c  submitted tags=a&tags=b&tags=c  idCount 3
chromium | saved [] (edit form)           checked a,b,c  submitted tags=a&tags=b&tags=c  idCount 3
chromium | 422 re-render, body tags='b'   checked a,b,c  submitted tags=a&tags=b&tags=c  idCount 3
chromium | no values                      checked (none) submitted (empty)                idCount 3
```

Firefox 151 and WebKit 26.5 give identical rows. `label[for=tags]` resolves to the first box only.

The corruption path: a user opens an edit form with 1 saved tag and saves it untouched. The server receives all 3 tags.

`form.mjs` also measures `select` with `.toggle("multiple")` and `['a','c']`, which selects 0/2. A boolean field given the string `"false"` renders checked.

Checks: tsc 5.9.3 exits 0, and eslint with all 32 rules at error reports 0 diagnostics on the group and select-multiple lines (`$R/tsprobe/probe.ts:23-24`).

The fleet census (`checkbox-census.mjs`, TS AST, dedup corpus) counts 45 one-argument boolean `checkbox` calls and 16 two-argument calls. 14 of the 16 are groups (the value is not `"on"`), in 7 repos. 9 of those are canonical-era, in 4 repos: competition 3, fl-um 1, na-cent 2, website-sales-funnel 3.
- 9/14 append a hand-written `.toggle("checked", selected.includes(v))` that overrides the binding. For example, `na-cent/src/app/imenik/views/imenik.form.view.ts:114` and `website-sales-funnel-automation-system/src/app/funnels/views/funnels.form.view.ts:131`.
- 7/14 append `.setId(...)` to break the duplicate id.
- 7/14 still emit duplicate ids. Examples: `competition/src/app/competition/screening/views/screening.views.ts:87`, `:89` render `id="missing"` and `id="sections"` once per option.

The lib's 4 checkbox tests (`test/form-for.test.ts:123-141`) bind boolean fields only, and 0 tests bind a group.

## Why it matters

- impact 3: a silent data-changing round trip. Edit forms re-save every option, and 422 re-renders show every option chosen.
- pain 2: invisible until stored data is wrong, and the fix is a per-site override authors must discover.
- reach 2: 14 group sites in 7 repos, and 9/14 already carry the workaround.

It hurts silent-failure (all layers green) and invariant-safety (duplicate ids from a binding whose purpose is to own ids).

## Rough idea (not a design)

The enforcement layer is runtime, in the binding itself.
- When `value` is passed, `checked` becomes membership: `Array.isArray(v) ? v.map(String).includes(value) : String(v) === value`. Without a value it keeps today's `Boolean(v)`.
- When `value` is passed, the id becomes `${controlId(name)}-${value}`, as `radio` already does.
- `select` uses the same membership for arrays.
- Pin the change with group tests in `test/form-for.test.ts`.

This lane is 8.1.x, because the emitted bytes change only for shapes that never worked. The 9 hand-written `.toggle("checked", …)` overrides keep working and become deletable.
