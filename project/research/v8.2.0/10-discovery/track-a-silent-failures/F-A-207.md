# The opacity-modifier arm is wider than Tailwind's modifier grammar

## Problem

Tints are taught as `bg("success/10")`. The type is `${CustomColor}/${number}`, so an author thinking in
CSS alpha (`/0.1`) or in thirds (`/33.3`) compiles clean, is safelisted, and gets no CSS: Tailwind 4.3.3
accepts only multiples of 0.25. Values above 100 compile to `color-mix(... 150%, transparent)`, which
Chromium resolves to transparent.

## Evidence (executed)

`$A2 = <scratch>/wave1/A2`.

- Oracle (`candidatesToCss`, 4.3.3, `--color-danger`): NULL for `bg-danger/0.1`, `/0.2`, `/0.3`,
  `/33.3`, `/66.6`; CSS for `/0.25 /0.5 /0.75 /1 /2.5 /5 /7 /12.5 /33 /99 /100 /101 /150`.
- Real build (`npx postcss` with the app's `@tailwindcss/postcss`, `@source inline("bg-danger/0.1 … bg-danger/150 …")`):
  `bg-danger/0.1` absent; `bg-danger/150` present as `background-color:#dc2626` + `@supports`
  `color-mix(in oklab, var(--color-danger) 150%, transparent)`.
- Chromium with that build: `bg-danger/0.1 => rgba(0, 0, 0, 0)`, `bg-danger/150 => rgba(0, 0, 0, 0)`,
  `bg-danger/10 => oklab(0.577107 0.191166 0.0987778 / 0.1)`.
- Probe app: `.bg("danger/0.1")`, `.bg("warning/150")` -> tsc exit 0, eslint exit 0; both in
  `fluent-safelist.css`; compiled CSS has no `bg-danger/0.1` rule.
- Fleet (16 canonical apps, extractor classes): 537 opacity-modified color classes, 28 distinct
  modifiers, all integers 5-95; 0 affected.

## Why it matters

impact 2 (the tint or badge background vanishes) x pain 2 (clean on tsc/eslint/extractor; the oracle
never sees the open arm, since vocab-validity samples literals) x reach 1 / effort S.

## Rough idea (not a design)

Type layer: generate the modifier arm from the pinned oracle (0-100 integers plus the 0.25 grid, or
a template that excludes other fractions), so `/0.1` fails with the valid set in the message.
