# Container confirm: the lint's fix makes Cancel a no-op

## Problem

htmx 4 does not inherit attributes unless they carry `:inherited`. `src/**` emits 0 `:inherited`/`:append` names (recon 03 §1), so the typed API cannot express inheritance. The only path is the untyped `addAttribute("hx-confirm:inherited", …)` taught at `htmx.md:487`.

The pure-prior htmx-2 form, `Div(…buttons).addAttribute("hx-confirm", "Sure?")`, gets a warn from `prefer-htmx-api`: "Use the HTMX API (hxGet, hxPost, setHtmx) instead". Following that advice puts `.setHtmx(hx(route, { confirm }))` on the container. The container then becomes a requester itself. Its confirm guards only its own spurious GET, while the child's DELETE has already left. The user sees "Sure?" and clicks Cancel, and the item is deleted anyway.

The correct `:inherited` form passes all 32 rules, and so does the wrong typed form.

## Evidence (executed)

`inherit.mjs` and `inherit-dismiss.mjs`: two child DELETE buttons, served with each of alpha7, beta4, beta6 and 4.0.0; click child 1, then accept or dismiss the confirm.

| Shape | Dialogs | Requests on Cancel | Requests on OK | Bundles |
|---|---|---|---|---|
| S1 container `addAttribute("hx-confirm")` (htmx-2 prior) | 0 | `DELETE /items/1` | `DELETE /items/1` | 4/4 |
| S2 container `addAttribute("hx-confirm:inherited")` (guideline) | 1 | none | `DELETE /items/1` | 4/4 |
| S3 container `.setHtmx(hx(route, { confirm }))` (the lint's suggestion) | 1 | `DELETE /items/1` | `DELETE /items/1` + `GET /items`; the container swaps and button #b1 is gone | 4/4 |
| S4 S1 + `HtmxConfig({ implicitInheritance: true })` | 1 | none | `DELETE /items/1` | 4/4 |

Headers (`headers.mjs`, beta6 and 4.0.0): the page carries the template's `<html hx-headers:inherited='{"X-Fluent-Behaviors":…}'>`. A button with a typed `headers: { "X-Own": "1" }` bag sends `X-Own` and stamp `null` (2/2). With no bag it sends the stamp (2/2). In `htmx.js:306-307` the element's own attribute wins, and fluent emits no `:append`. The template's refresh-on-mismatch hook (`runtime.ts:85-90`) only fires when the header is present. So every request carrying a typed `headers` bag silently opts out of deploy-skew protection.

Lint (`ALL=1`, 32 rules, `$R/tsprobe/probe.ts`):
- `:29` (S1) gets 1 `prefer-htmx-api`.
- `:30` (S3) gets 0.
- `:31` (S2) gets 0.

Fleet: `container-hx.mjs` (TS AST over the 45 repos that serve an htmx 4 build, `src/core` excluded) finds 5 candidate container writes and 52 on requesting chains. All 5 candidates are false positives on manual read: rideshare `detail.view.ts:198` is inside a `.when` on an `.hxPost` chain, and corina/storysell's 4 sit on a `page` that also receives `hx-get`. Measured container reliance is 0. The template's own inheritance (`runtime.ts:124`) is the only `:inherited` writer: 93 fleet lines, all vendored copies of it.

## Why it matters

- impact 3: a destructive request goes through after the user declined it, in the shape the lint recommends.
- pain 2: the dialog appears, so manual testing passes.
- reach 1: 0 live fleet container sites today. The shape is the htmx-2 prior, and 16 fleet repos still serve htmx 4.0.0-alpha7.

It hurts silent-failure and error-quality: the only diagnostic names the wrong fix.

## Rough idea (not a design)

The cheapest layer is lint, at 8.2.0, additive. `prefer-htmx-api` keeps its warning, but for the inheritable names (`hx-confirm`, `hx-target`, `hx-swap`, `hx-headers`, `hx-indicator`, `hx-include`, `hx-sync`, `hx-disable`) on a chain that makes no request, the message says `addAttribute("hx-<name>:inherited", …)` or the typed path. The typed path (L-102's `inherited` bag) should also offer `:append` for `headers`, so a typed bag can no longer drop the template's stamp. Once the typed path exists, the untyped example at `htmx.md:480-491` becomes deletable.
