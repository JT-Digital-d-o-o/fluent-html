# El(name) element names are unvalidated

## Problem

Every attribute-name sink validates its key and throws in production:
- `addAttribute`, `setDataAttrs` and `setAria` go through `validateAttributeKey` (`tag.ts:31-40`), which also blocks `on*` handlers.
- `toggle` names are validated at `serialize.ts:274`.

Element names have no validation. `El(name)` (`utils.ts:8-10`) and `new Tag(name)` (`tag.ts:89-93`) write the name verbatim into both the open and the close tag. A name is therefore a markup breakout that also bypasses the `on*` block the library enforces everywhere else.

## Evidence (executed)

`names.mjs`, run with `NODE_ENV` set to production and to development (identical output):

```
El("img src=x onerror=alert(1)", "hi")   -> <img src=x onerror=alert(1)>hi</img src=x onerror=alert(1)>
El("b><script>alert(1)</script><b", "hi") -> <b><script>alert(1)</script><b>hi</b><script>alert(1)</script><b>
addAttribute("x onmouseover=alert(1) y") -> THROWS Invalid attribute key
addAttribute('x"><img src=x onerror=…>') -> THROWS Invalid attribute key
setDataAttrs({evil}) / ({quote-breakout})  -> THROWS (2/2)
setAria({evil})                          -> THROWS
toggle(evil)                             -> THROWS Invalid boolean attribute name
```

In Chromium (`el-browser.mjs`), all 3 element-name payloads execute: `img onerror` sets `__hit` to 1, the script breakout to 2, and `div onclick` to 1 after a click.

Fleet: the 58-repo dedup corpus has 1 non-literal `El(` site and 0 `new Tag(<non-literal>)` sites. That site is `tela/src/views/editor/panels/canvas-panel.ts:64` (pre-7, fluent-html 5.7.0), `El(tag, …)` with `tag = el.tag` from the stored design document. The tag reaches storage through `GET /tela/:projectId/add/:tag`, which casts the URL parameter `as ElementTag` and saves it with no allow-list check (`element.controller.ts:42-76`). Any editor of a project can reach it with a GET.

Rendering tela's own `CanvasPanel` with that stored tag (`tela-render.ts`, tela's tsx) outputs:

```
<img src=x onerror=alert(document.domain) id="canvas-e1" class="canvas-element p-2  " data-element-id="e1" hx-get="/tela/p1/select/e1" ...>
```

tela sets no CSP: 0 matches for content-security-policy/helmet in `src/` and `package.json`.

Checks: tsc exits 0 and eslint (32/32 rules) reports 0 diagnostics for `El(tagFromData, "hi")` (`$R/tsprobe/probe.ts:37`). The lib's El tests are 3 literal custom-element cases (`test/attributes.test.ts:59`, `test/composition.test.ts:211`, `test/elements.ts:230`).

## Why it matters

- impact 3: script execution through a sink that looks like data, past the library's own `on*` block. Guardrail 3, escape by default, holds for every other name.
- pain 2: invisible until exploited. Once the sink is known, the fix is 1 line.
- reach 1: 1 live non-literal site, which is reachable, in 1 of 58 repos.

It hurts silent-failure and invariant-safety.

## Rough idea (not a design)

The enforcement layer is runtime: a throw, the same stance as `validateAttributeKey`. Validate in `El()`: an ASCII letter first, then letters, digits, `-`, `.` or `_`, which admits valid custom elements and the SVG camelCase names. Run the same check in the `Tag` constructor under `devChecks`, so the hot path stays untouched (guardrail 2). Pin a breakout probe next to the attribute-key probes in `test/security.test.ts`.

The lane is 8.1.x: the only bytes that change are invalid element names, which never produced well-formed HTML. No prose is needed.
