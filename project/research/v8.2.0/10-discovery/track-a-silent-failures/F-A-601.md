# onClickOutside on the panel hides it on the opening click

## Problem

The natural composition, and the one the JSDoc default (`target` = `@self`) points at, is:

```ts
Div(
  Button("open").setType("button").behavior("toggle", { target: ids.menu }),
  Div("items").setId(ids.menu).hidden().behavior("onClickOutside", { action: "hide" }),
)
```

It compiles (tsc 0) and lints clean (0 diagnostics with all 32 plugin rules at error, `$R/tsprobe/probe.ts:6-9`). At runtime the menu never opens. `dispatch` (`runtime.ts:415-424`) runs the ancestor walk first. The walk runs the trigger's `toggle`, which removes `hidden` from the panel. Then `outsideScan(start)` (`:422`) runs on the same click. The panel does not contain the trigger and is no longer class-hidden, so it gets re-hidden in the same tick.

Carriers hidden natively are worse. A closed `<dialog>` or `popover` carrier is never class-hidden, so `outsideScan` adds `hidden` to it on any click anywhere. That includes the click on its own `command="show-modal"` invoker. The modal then opens with `display: none`: it is invisible, and it makes the rest of the page inert.

## Evidence (executed)

The harness is `outside.mjs`: 5 shapes, shipped `dist/fluent-behaviors.8.1.0.js` vs a patched asset, on Chromium 149.0.7827.55, Firefox 151.0 and WebKit 26.5. The sequence is: initial, trigger click, outside click, trigger click, trigger click. A correct panel is visible in states 2 and 4.

| Shape | Shipped (all 3 engines) | Patched (all 3 engines) |
|---|---|---|
| A: panel carrier, default `@self` target | `false,false,false,false,false` (0/5) | `false,true,false,true,false` |
| B: panel carrier, explicit target = panel | `false,false,false,false,false` (0/5) | `false,true,false,true,false` |
| C: wrapper carrier (the fleet workaround) | `false,true,false,true,false` | `false,true,false,true,false` |
| D: `popover=manual` panel carrier, native `popovertarget` invoker | `:popover-open` true but visible false in 5/5 | opens (true), then outside click leaves `:popover-open` with class `hidden` (desync) |
| E: `<dialog>` carrier, `command=show-modal` invoker | `open:true`, visible false | `open:true`, visible true; backdrop click lands on the dialog, so it is never dismissed |

The inert-modal check is `inert.mjs`, run on 3/3 engines. With the behavior, the dialog reports `{"open":true,"cls":"hidden","display":"none"}`, 0 clicks reach a page button, and focus cannot land on it. The control without the behavior reports the same blocking with `display: block`, so there the user can at least see the dialog.

Fleet: `grep.mjs 'onClickOutside|clickOutside'` over the 58-repo dedup corpus finds 2 app sites in 2 canonical repos. Both declare the dismissal on a wrapper, and both explain why:
- everyframe-composer `studio.components.ts:724-730` (commit 8c6382a, 2026-09-27): "on the menu the trigger's own press counted as outside and shut what it had just opened (27. 09. 26, the dropdown does nothing)".
- competify `app-shell.ts:206-211` (commit 4439268, 2026-09-12): "one click could never open it at all". Its test `tests/view/app-shell.view.test.ts:45-53` pins the wrapper shape.

The lib's own matrix cannot see it. The onClickOutside fixture carrier starts visible and has no opener (`test/acceptance/app.mjs:76-78`). The generated rows (initial/swap/morph) and row 22 only click inside, then outside.

Prototype (scratch copy of the lib):
- The change is in `outsideScan`/`dispatch`. Outside candidates are collected before `walk()`: carriers that do not contain the click and are shown (`!hidden && checkVisibility()`). After the walk, only those that are still shown are dismissed.
- Measured results:
  - `npm run build` gives 6108 B min / 2737 B gz against the 6144 B budget (shipped 5977 B; this includes the F-A-602 trap change).
  - Unit tests: 2159/2159.
  - Acceptance with `ACCEPT_ENGINES=all`: chromium 69/69, webkit 69/69, firefox 68/69. The one Firefox failure is row 28's undeclared-charset harness error, which also fails unpatched (recon 03 §5).
  - With the patched asset, shapes A, B and C behave correctly on 3/3 engines.
- Of the critic's targets, the 2 fleet shapes moved back onto the panel pass. The D3 `<dialog>` shape now opens visibly, but outside clicks still do not dismiss it, because the backdrop click targets the dialog. Native `setClosedby("any")` remains the tool for that shape.

## Why it matters

- impact 3: the control never opens, and the dialog variant freezes the page behind an invisible modal.
- pain 3: both fleet authors hit it, and finding the fix required reading the runtime's dispatch order. One of them dates a production incident.
- reach 2: 2/2 fleet uses, 100% of real usage.

It hurts silent-failure (tsc, lint, extractor and the matrix are all green) and verification-loop (the matrix fixture cannot express the opener composition).

## Rough idea (not a design)

The enforcement layer is runtime. Collect the outside candidates before the dispatch walk and dismiss only those still shown after it, at about +131 B within budget, and keep grammar frozen per S-21. Add an acceptance row: a toggle outside a panel carrier opens it, then an outside click closes it. This makes the competify and everyframe-composer wrapper comments, and their pinning test, deletable. No guideline prose needs adding: the carrier rule disappears instead of being taught.
