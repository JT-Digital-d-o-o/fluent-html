# Bracket arms are an unencoded, untyped hatch

## Problem

The typed bracket arm accepts any string, and the runtime appends it as written.

1. Whitespace. Tailwind needs `_` for spaces inside `[...]`; the lib already encodes that for
   `.cssProp` (`cssPropValue`) but not for bracket arms:
   `Div().w("[calc(100% - 2rem)]")` -> `class="w-[calc(100% - 2rem)]"`, which the browser reads as 3
   classes (`w-[calc(100%`, `-`, `2rem)]`), none valid.
2. Merged prefixes. `.text("[var(--step-2)]")` compiles to `color: var(--step-2)` although the only
   reason to pass a var to `.text` in a size slot is a fluid font size; the working spelling
   `[length:var(--step-2)]` is admitted by the same `[${string}]` arm but nothing steers to it.

## Why it matters

impact 2 (the style silently does not apply, or applies to the wrong property) x pain 2 (the css
build prints one warning line an agent never reads, 0/4 agents ran the css build in recon 02; the
var() case prints nothing) x reach 1 / effort S.

## Rough idea (not a design)

Runtime/emit: apply `cssPropValue`'s whitespace encoding to every `[${string}]` arm in the lib emitter
and the vocab row together (8.1.x: bytes change only for classes that never worked). Type layer for
the var() case: on the 6 merged prefixes, accept `[var(…)]` only with a `length:`/`color:` hint.
