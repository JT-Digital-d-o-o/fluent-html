# No structural view inspection: tests verify rendered markup by substring and hand-written regex

## Problem

The only way to look at a View is `render()` to a string. Every test in the fleet, and every agent run, then checks that substrings occur somewhere in that string. A substring cannot say which element carries it, so structure is unverified. The template's FormGroup suite:

```ts
// tests/view/components.test.ts:34-38
expect(html).toContain("Email");
expect(html).toContain('type="email"');
expect(html).toContain('name="email"');
expect(html).toContain('for="email"');
expect(html).toContain('id="email"');
```

Where a test needs an element it hand-writes a regex coupled to the serializer's attribute order (`/<link[^>]*rel="preload"[^>]*href=.../`, competify tests/view/layout.test.ts), and the template states the trade-off: "Deterministic SSR output from our own renderer: anchored extraction, no HTML parser dependency" (tests/integration/seo.test.ts:8).

## Evidence (executed)

- Fleet scan of 1,512 canonical-era test files (`tests.mjs`): 20,610 string-argument `toContain`/`toMatch` assertions in 856 files, 16/16 repos; 3,559 `.not.toContain`; 555 `toContain('...id=...')`; 2,701 hx-attribute contains.
- Subject split over 20,597 `expect(x).toContain|toMatch` calls: 13,701 whose subject is named as rendered markup (html, markup, view, a render() call), 2,321 an HTTP `.body`/`.payload`, 4,575 other. The in-memory `inspect(view)` covers the first group; HTTP-body tests stay a template concern.
- 440 tag-extraction regex literals in 97 files (16 repos); 57 regexes and 202 contains strings encode two attributes in serializer order (259 order-coupled assertions, 16 repos).
- Agent runs (recon 02, phase 2): 4/4 runs verify by string: 225 toContain, 24 toMatch, 5 tag regexes over 20 test files and 73 render() calls.
- Mutation experiment (`inspect-exp.mjs`): FormGroup with the id moved from the input to the wrapper div (the label now points at a div) passes the template's 5 string assertions; the tree suite (`byId("email").tag === "input"`, label `for` equals that id) fails.
- Parity: `serialize(inspect(v)) === render(v)` for 300/300 random trees (escaping, Raw, toggles, aria, ForEach), and byte-identical on a real app page: fl-um 8.1.0 HomePage, full-document and htmx arms (`inspect-flum.mjs`). Cost on that page: inspect 119 us vs render 22 us, test-only.
- Library support: `import("fluent-html/dist/src/render/serialize.js")` from fl-um fails with ERR_PACKAGE_PATH_NOT_EXPORTED; `fluent-html/render` exports 9 names, none of them buildAttrs.
- Typed sketch (`tsprobe/testing.d.ts`, `use.ts`): compiles with 0 errors; `byId("email")` and `all("lable")` fail as `@ts-expect-error` expects.
- Known incident class: F-A-501 (workshop-toni family.test.ts:90-100) passed `toContain("joined the family")` on escaped markup; a tree query finds no element there.

## Why it matters

impact 3 x pain 2 x reach 3 / M = 9. The verification loop is where an agent learns its view is wrong; today it learns only that a substring exists. The order-coupled assertions also tax evolvability: any serializer attribute-order change (C-63) breaks 259 assertions in 16 repos without a behavior change. Dims: verification-loop, silent-failure, evolvability.

## Rough idea (not a design)

A `fluent-html/testing` subpath whose `inspect()` reuses the serializer walk (shared buildAttrs and contexts, guarded by the existing render/iterable fuzz parity test) and returns plain nodes with Id-typed lookups whose error lists the ids present. Enforcement: type for the lookups; the template then teaches tree assertions in its view tests and can delete its regex helpers. It verifies structure, not htmx runtime behavior: the bundle oracle (RFC-A-03) and Playwright stay the runtime check (L-421).
