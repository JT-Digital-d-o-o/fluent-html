# Layout chrome variants are re-invented per app

## Problem

The template Layout offers `width` but no way to drop or swap the nav and footer, so apps with a landing page, an auth screen or a full-viewport workspace each add their own prop. The result is one idea under five vocabularies: `"app" | "bare"` (competify, fluent-html-home-page), `"site" | "app"` (na-cent, everyframe-composer), `"app" | "marketing" | "minimal"` (popri), `"app" | "none"` (studio), and a boolean `hideNav` (website-sales-funnel-automation-system).

## Evidence (executed)

- LayoutProps keys extracted from src/core/layout/layout.view.ts in the 15 canonical apps that have one: `chrome` in 6, `hideNav` in 1, `preloadImage` in 4 (already a template prop).
- `chrome:` call sites outside core/layout: everyframe-composer 34, popri 9, studio 9, competify 8, na-cent 8, fluent-html-home-page 3 (71).
- All 6 render the chrome inside MainContent (the #main-content root), which is what lets `.nav` between variants swap the nav correctly; the template seam can fix that placement for every future app.

## Why it matters

impact 1 x pain 1 x reach 2 / S = 2. An agent adding a bare page must discover each app's private vocabulary first, and an app that puts the variant outside #main-content would leave stale chrome after a `.nav`. Dims: decision-closure, context-economy.

## Rough idea (not a design)

Add `chrome?: LayoutChrome` with `"app" | "bare"` to the template layout, Matched inside MainContent; apps widen the union. Enforcement: type (closed union).
