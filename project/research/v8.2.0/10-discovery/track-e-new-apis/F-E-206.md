# Request-scoped render data has no app-owned seam: 3 apps edit core render-context.ts, and nav state is threaded by prop

## Problem

`withRenderContext` binds a fixed chain (SEO, htmx flag, i18n). An app that needs more request-scoped data in its views or layout has to edit core and nest another `.run(...)` by hand. Examples are the current org, a family selection, and the current path for nav highlighting.

The one recurring piece is "which nav section is current", and the template ships nothing for it:

- popri forked a `currentPath` context into core.
- wsfas threads an `activePath` string through every admin page, 15 times as a raw path literal.
- The template's own `TabItem`/`tabItem` styles an active state but never sets `aria-current`.

## Evidence (executed)

- **Per-file divergence** (blob match against template history, setup-generated hash groups separated): `render-context.ts` differs in 15 of 15 apps, but 11 are the setup tool's module-stripped variants.
  - The 4 genuine edits: na-cent nests 3 app contexts (render-context.ts:21-23), workshop-toni adds `requestFamily` (:20), popri adds `currentPath` (:17), and competify replaces the i18n binding with a deployment locale (:37).
  - That is 3 apps adding 5 app contexts.
- **Nav-state census:**
  - wsfas has 89 `activePath` lines: 15 raw `"/admin/..."` literals, 31 read from the request or props, and 20 from `xRoutes.y.path` or a PATH const. Matching is `===` or `startsWith` (admin-layout.view.ts:137-138), with no `aria-current`.
  - popri matches on a route pattern's static head (`sectionRoot` + `inSection`, layout.view.ts:417-438) and does set `aria-current`.
- **Sketch** (`verbs/render-contexts.ts`): `renderBinding` + `withBindings` + `currentPath` + `isCurrent` over fluent-html route callables.
  - `tsc` clean.
  - For `/canvas/42/board?tab=x`, `isCurrent(canvasRoutes.show)` is true and the app's org binding resolves (output `[ true, 'org_1' ]`).

## Why it matters

impact 2 x pain 2 x reach 2 / S = 8.

- Every app context is a core edit that the template update path never carries back.
- The nav-state workaround puts raw path strings into views. Type-checked routes exist to remove those (`defineRoutes`, `.resolve`).
- Template nav components miss `aria-current`.

Dimensions: evolvability, decision-closure.

## Rough idea (not a design)

The template's `withRenderContext` folds an app-owned `src/app/render-bindings.ts` list, so core is never edited for app data. Ship `currentPath` + `isCurrent(...routes)` as its first built-in binding, and have `TabItem`/`NavLink` take `current` and set `aria-current="page"` from it. Framework layer only. fluent-html already exposes `route.path`.
