# No error exit for handlers: app-rendered ErrorPage answers nest a second #main-content inside fragment targets

## Problem

The template knows that an ErrorPage is a page (Layout-rooted, carrying #main-content) and that morphing it into a fragment slot nests a second #main-content and breaks every later swap (server.ts:375-384). Its global error and 404 handlers therefore send HX-Retarget: #main-content first. That rule lives in `retargetErrorAwayFromFragments` (server.ts:402), which is module-private, and the exported `sendErrorPage` (server.ts:421) does not apply it. App code that answers an error itself has no sanctioned call, so it writes `reply.code(404).renderView(ErrorPage({ status: 404, ... }))` by hand, inside fragment routes too:

```ts
// everyframe-composer/src/app/captions/captions.controller.ts:59-62, reached from routes with render: captionIds.captionsWorkspace
function notFound(reply: FastifyReply): FastifyReply {
  reply.code(404).renderView(ErrorPage({ status: 404, message: "Project not found" }));
  return reply;
}
```

htmx 4 swaps 4xx bodies by default (noSwap: [204, 304], htmx.js:219), so the 404 page lands in #captions-workspace.

## Evidence (executed)

- AST join of route stances to handlers over the 16 canonical repos (`fragerr.mjs`): 285 fragment-stance route keys; 28 of their handlers answer ErrorPage (directly or through a local helper), 43 ErrorPage answers, 0 with HX-Retarget. everyframe-composer 23 handlers, gzs/stem-50 5.
- Playwright probe (`errswap.mjs`) against the lib's htmx 4.0.0-beta6 and the template's served 4.0.0: a button with hx-target="#captions-workspace" hx-swap="outerMorph" receives the Layout htmx arm (`<title>` + `#main-content`) at status 404. Both bundles: `#main-content` count 2, nested, nav count 2, `#captions-workspace` gone. Same response with `HX-Retarget: #main-content`: count 1, nav 1.
- `errpage2.mjs`: 222 ErrorPage answers in canonical-era code state the status twice (55 inline `.code(X).render*`, 167 preceded by `reply.status(X)`), 16/16 repos, 0 disagreements; 1 site without a status (the template's not-found handler, where Fastify sets 404).
- Helper scan: `notFound` 10 sites in 4 repos, `unknownProvider` in 6 (vendored), plus `renderNotFound`, `deny`, `refuse`, `conflict`, `answerDetail`, `renderPaymentError`, `withErrorPage`.
- `sendErrorPage(`: 0 app call sites in 58 repos.
- Hand copies of the private rule: competify/src/app/demo/demo.plugin.ts:52-61 and na-cent/src/app/demo/demo.plugin.ts:80-89 (its comment names server.ts "where it is module-private"); workshop-toni/src/app/family/family.plugin.ts:19-23 parses HX-Target a third way.
- Sketch compiled with fastify types (`errsketch/sketch.ts`, tsc exit 0): `reply.renderError(404, ...)` is assignable to both `FragmentAnswer<"captions-workspace">` and `PageAnswer`; `renderError(200, ...)` is rejected by the closed `ErrorStatus`.

## Why it matters

impact 2 x pain 3 x reach 2 / S = 12. The bug class is the one the template already fixed for itself: a page in a fragment slot leaves duplicate ids and points every later swap at the wrong node, with a clean compile and a 404 that looks handled. Reach is 2 repos for the live corruption and 16/16 for the double-stated status that the same call removes. Dims: silent-failure, invariant-safety, context-economy.

## Rough idea (not a design)

Template core exports `hxTargetId`/`rendersShell` from htmx-request.ts and decorates `reply.renderError(status, message)` that runs the existing retarget rule and renders ErrorPage at that status; `sendErrorPage` becomes its implementation. Enforcement: type (closed ErrorStatus) plus a template lint that flags `ErrorPage(` outside renderError, which turns 222 sites into one spelling. No library change.
