# Server code re-derives htmx 4's HX-Target header to ask whether a swap aims at #x

## Problem

A response can depend on where the swap lands: an error page must be retargeted away from a fragment slot, a layout plugin skips work for fragment requests. The answer lives in the `HX-Target` request header, whose format changed between htmx generations. The template parses it correctly (`core/server/server.ts:394`, `hxTargetId`, with a comment documenting `${tagName}#${encodeURI(id)}`), but the function is module-private, so apps re-derive it:

- competify `demo.plugin.ts:52-61` and na-cent `demo.plugin.ts:80-89`: the same 8-line parser, copied ("where it is module-private", the na-cent comment says).
- workshop-toni `family.plugin.ts:19-23`: `target.endsWith(layoutIds.mainContent.selector)`.
- storysell-ai shipped two wrong guesses: `a2d2911` replaced `=== String(scraperIds.scrapeProgress)` (renders `#scrapeProgress`) with `=== scraperIds.scrapeProgress.id`, then `fb7f780` found htmx sends `div#main-content` and fell back to `.includes(id)` (a substring match).
- jt-vault (htmx 2.0.7) treats `!!request.headers["hx-target"]` as "a filter request" in 5 controllers, a test htmx 4 makes true for every htmx request.

## Evidence (executed)

`node hxtarget-probe.mjs`: Chromium, both pinned bundles, three buttons (target `#mainContent`, target `#scrapeProgress`, no target):

```
lib:4.0.0-beta6 ["div#mainContent","div#scrapeProgress","button"] | String(id)= #scrapeProgress | id.id= scrapeProgress | equality hits: 0
template:4.0.0  ["div#mainContent","div#scrapeProgress","button"] | String(id)= #scrapeProgress | id.id= scrapeProgress | equality hits: 0
```

Both storysell guesses match 0 of 6 header values; an untargeted trigger still sends a header (`button`). Census: `function hxTargetId` in `core/server/server.ts` of 13 of 16 canonical repos (vendored, private); app-code `headers["hx-target"]` reads in 3 of 16 (competify, na-cent, workshop-toni); pre-7 reads in storysell-ai, jt-draw core and 5 jt-vault controllers.

## Why it matters

impact 2 × pain 2 × reach 2 / S = 8. A wrong guess silently disables the branch it guards (the poll never short-circuits, the error page nests a second `#main-content`), and the format is version-dependent knowledge each app re-learns. Dimensions: invariant-safety, evolvability (one place to update on the next htmx header change).

## Rough idea (not a design)

Framework layer: move `hxTargetId` into `core/htmx/htmx-request.ts` next to `isHtmxRequest` and export it with an `Id`-typed predicate, so a selector string or `String(id)` cannot be passed (type enforcement). The vendored server.ts and the two demo plugins call it. A template unit test pins the htmx 4 format against the served bundle.
