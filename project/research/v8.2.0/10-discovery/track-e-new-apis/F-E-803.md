# Template emails ship an HTML part only

## Problem

The template's `createEmail` (email.template.ts:23) returns one HTML string and every vendored caller sends `sendMail({ to, subject, html })` (verification-email.ts:46, email-change.ts:29, reset.service.ts:36). One app noticed and fixed it by parsing its own output back:

```ts
// gzs/stem-50/src/infra/email/email.template.ts:25-32
// a text/html part with no text/plain sibling is among the strongest spam signals there is ...
// Derived from the rendered HTML rather than from sections, because a section is an opaque View
export function toPlainText(html: string): string { return html.replace(/<style[\s\S]*?<\/style>/gi, "") ... }
```

## Evidence (executed)

- AST scan of canonical non-test code (`mailtext.mjs`): 44 `sendMail({...})` calls with `html` and no `text` across 13 repos; 3 with `text` (competify, competition: hand-written internal notifications, not view-derived); 6 spread `...createEmail()` in gzs/stem-50, the only repo whose text part comes from the view.
- `email-text.mjs`: the template email shape (head + style, heading, paragraph with Strong, button link whose URL carries `&`, a name with `<` and an apostrophe) rendered once; stem-50's `toPlainText(render(view))` and a 12-line walk over `inspect(view)` (F-E-801) produce identical text. The walk needs no entity decoding, because it reads strings from the tree.

## Why it matters

impact 2 x pain 1 x reach 3 / S = 6. Verification, reset and invite mail is what a new user must receive; an html-only message carries a spam signal the one fixing repo names, and nothing in a test or a log shows the loss. Dims: silent-failure, context-economy.

## Rough idea (not a design)

Template `createEmail` returns `{ html, text }`; callers spread it. Ship the stem-50 regex now and switch to the tree walk when F-E-801 lands. Enforcement: type (callers that pass `html` alone stop compiling once the return type changes).
