# Grouped lists are hand-rolled because the template's lib hides Map.groupBy

## Capability
Grouped sections need no fluent-html API: `Map.groupBy` (ES2024) returns a Map, `ForEach` accepts any `Iterable<T>` (src/control/iteration.ts:36-39), and a Map iterates `[key, items]` entries that destructure in the callback. Rendered on fluent-html 8.1.0 under Node v26.0.0:
```
Div(ForEach(Map.groupBy(events, (e) => e.day), ([day, items]) => Section(H3(day), Ul(ForEach(items, (e) => Li(e.title))))))
-> <div><section><h3>Mon</h3><ul><li>a</li><li>b</li></ul></section><section><h3>Tue</h3><ul><li>c</li></ul></section></div>
```

## Problem
The template pins `"target": "ES2022", "lib": ["ES2022"]` (templates/full-stack/tsconfig.json:3-4, templates/web/tsconfig.json:3-4) and all 15 canonical apps inherit it, so the one-liner does not type-check:
```
sketch.ts(4,19): error TS2550: Property 'groupBy' does not exist on type 'MapConstructor'. Do you need to change your target library? Try changing the 'lib' compiler option to 'es2024' or later.
sketch.ts(4,36): error TS7006: Parameter 'e' implicitly has an 'any' type.
sketch.ts(4,50): error TS2769: No overload matches this call.
sketch.ts(4,113): error TS18046: 'e' is of type 'unknown'.
```
Apps and agents therefore hand-roll grouping, and the parked core idea (ForEachGroup, L-149) would add a second way next to the platform's.

## Evidence (executed)
- Compile: `$E6/proto/group/sketch.ts` with lib ES2022: 4 errors above; with lib ES2024: 0 errors.
- Bump safety (`$E6/libcheck.mjs`, each app's TS 6.0.3): lib ES2022 vs ES2024 over 15 canonical apps, 4,890 files: 0 diagnostics added, 0 removed.
- Demand, all app-authored files (`$E6/scan6.mjs`): 29 named group*By helpers in 15/58 fleet repos (6 in 5/16 canonical: gzs/stem-50/src/shared/faculty-picker.ts:32, na-cent/src/app/vat/vat.utils.ts:55, popri/src/app/canvas/canvas.utils.ts:15, popri/src/app/canvas/evaluation/evaluation.report.ts:172, sportoawards/src/app/archive/archive.service.ts:33, website-sales-funnel-automation-system/src/shared/ui/timeline.components.ts:334); accumulation idioms `map.get(k)!.push` 13 fleet / 4 canonical, `if (!m.has(k)) m.set(k, [])` 11 / 3, `(acc[k] ??= []).push` 3 / 1; native `Map.groupBy`/`Object.groupBy` 0 sites. In view files alone the demand is small (18 helper calls fleet / 2 canonical), which is why a view-layer combinator is not proposed.
- Agents (`$E6/agent/`, 3 blind runs): EventsByDay 3/3 wrote their own `groupByDay` (9, 12 and 12 lines) and then nested ForEach; 2/3 returned `[H3(...), Ul(...)]` arrays from the ForEach callback.
- Runtime constraint: Map.groupBy needs Node 21+. The template declares `engines.node >=20` (projects-template/package.json:40); deploy scripts default to Node 24 (scripts/create-cpanel-nodejs-app.sh:12, scripts/write-server-config.sh:13) but document a Node 20 example (scripts/setup-server-dirs.sh:13).

## Why it matters
impact 1 x pain 1 x reach 2 / effort S(1) = 2. Low, but it is the cheapest closure of a modality item: one config line removes a hand-rolled helper class and keeps ForEachGroup out of core (guardrails 5 and 7). Dims: prior-alignment (the platform primitive an agent knows), context-economy (no helper, no new name to teach).

## Rough idea (not a design)
Template: target/lib ES2024 in both templates, engines `node >=22` in generated apps plus a boot or CI check of the runtime major, so a Node 20 host fails at deploy rather than at the first grouped page (`Map.groupBy is not a function`). One compiling exemplar replaces any grouping prose. ForEachGroup (L-149) is closed as served by the platform.
