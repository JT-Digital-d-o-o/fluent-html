# No accessible progress bar in the template; 44 hand-rolled width bars in 11 apps, 1 announced to assistive tech

## Problem

The template's only bar is the `Meter` in chart.figures.ts. It is a div track with a div fill whose width rides `setStyle(`width: ${pct}%`)`, and it has no role or value attributes. Apps copy that shape every time they need a ratio:

- judges scored
- upload or render progress
- funnel stages
- thesis completion

The result is invisible to assistive tech.

fluent-html already ships the native `Progress()`/`Meter()` factories with typed `setValue`/`setMax`, but nothing in the fleet imports them. The template also exports a component named `Meter` that shadows the library factory of the same name, so the native path stays out of sight.

## Evidence (executed)

- **Census** (app-authored lines, template-origin lines excluded):
  - 44 runtime width bars in 36 files across 11 apps (strict match on `width:` driven by a variable inside setStyle/setStyles).
  - The looser property census counts 47: composer 23, wsfas 11, popri 3, competify 2, home-page 2, and 1 each in competition, fl-um, stem-50, na-cent, sportoawards and stojnica.
  - 4 apps define a component literally named `ProgressBar`, and popri defines a `Meter`. All of them use the same div + setStyle shape.
- **Accessibility:** grep for `progressbar|aria-valuenow` over all 15 apps and the template finds 2 lines, both in composer studio.review.view.ts:152-153. That is 1 of 44 bars.
- **Native factories:** `grep import ... (Progress|Meter) ... from "fluent-html"` across every repo under <org-root> (lib excluded) returns 0 files.
- **Chromium AX tree** (`a11y-bars.mjs`, Playwright):
  - The fleet's div bar does not appear in the ARIA snapshot at all.
  - `<progress value=43 max=100>` yields `progressbar: 43%` with valuemin=0 and valuemax=100.
- **Tailwind oracle** (`tw-progress.mjs`, tailwindcss 4.3.3 compile): `appearance-none`, `[&::-webkit-progress-bar]:bg-*`, `[&::-webkit-progress-value]:bg-*`, `[&::-moz-progress-bar]:bg-*` and the two meter pseudo-elements all emit (5/5 plus appearance).
- **Sketch** (`lib/progressbar-sketch.ts`):
  - `tsc` clean with role tokens declared through defineTheme.
  - Renders `<progress class="appearance-none block w-full h-2 rounded-full ... [&::-webkit-progress-value]:bg-primary [&::-moz-progress-bar]:bg-primary" value="7" max="12" aria-label="Entries scored">58%</progress>`.

## Why it matters

impact 2 x pain 2 x reach 3 / S = 12.

- 43 of 44 bars carry information that sighted users get and screen-reader users do not.
- The template component teaches that shape.
- 47 of the fleet's 111 app-authored setStyle sites (42%) exist only to move a bar's width. The native element removes the inline style.

Dimensions: silent-failure, decision-closure.

## Rough idea (not a design)

Add `ProgressBar` to src/shared/ui on the native element, and let `Meter` (and any chart bar that is a single ratio) render it. A view test that asserts `role` or `<progress>` on the template's Meter holds the a11y half. No library change and no prose added. The views.md line on runtime widths can point at the component instead of at setStyle.
