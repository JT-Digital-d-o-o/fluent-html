# IDREF sinks accept a selector where an id is required

`$B3` = `<scratch>/wave1/B3`.

## Problem

An `Id` exposes three strings: `.id` (`email`), `.selector` (`#email`), and `toString()` (also `#email`). IDREF attributes (`for`, `list`, `form`, `headers`, `aria-controls`, ...) need the first. The sinks disagree on what they accept and none rejects the other two:

| Sink | Type | `ids.email` | `ids.email.selector` | `` `${ids.email}` `` |
|---|---|---|---|---|
| `LabelTag.setFor`, `InputTag.setList`, `Tag.setForm` | `string \| Id` | `for="email"` | compiles, `for="#email"` | compiles, `for="#email"` |
| `setAria({ controls })` (8 IDREF keys) | `string` | TS2322 `Type 'Id<"team-list">' is not assignable to type 'string'.` | compiles, `aria-controls="#team-list"` | compiles, same |
| `setPopovertarget`, `setCommandfor` | `Id` | ok | TS2345 | TS2345 |

## Evidence (executed)

- `v14-idref.ts` on the scaffolded template: tsc errors only on `setAria({ controls: ids.teamList })` and `setPopovertarget("team-list")`; renders `<label for="#email">` (x2), `<button aria-controls="#team-list">` (x2), `<input list="#email">`. eslint: 0 findings.
- Live instance: `projects-template/templates/web/src/pages/contact.ts:105,132,159,182`. Rendered with fluent-html 8.1.0 and the template's real `siteConfig` (`$B3/web/render-contact.mts`): labels `for` = `#name`, `#email`, `#subject`, `#message`; controls `id` = `name`, `email`, `subject`, `message`. Chromium (`$B3/label-probe.mjs`): `label.control` is `null` for 4/4; clicking the first label leaves focus on `BODY`; `document.getElementById("name").labels.length` = 0, so the inputs have no label-derived accessible name.
- Fleet (TS AST, dedup corpus): those 4 are the only selector-into-IDREF sites; 8.x `setCommandfor` 39 sites and `setPopovertarget` 7 sites are Id-only and compile with 0 string arms, so the Id-only shape is already adopted where it exists. 0 of 1,848 `setId` sites use a `#`-prefixed id, so treating a leading `#` in an IDREF as a mistake has 0 measured collateral.
- Type prototype (`$B3/hint/idref.ts`, tsc --strict against dist): `setFor<const S extends string | Id>(forId?: S extends `#${string}` ? { readonly ["for= takes an element id, not a selector: pass ids.email (or ids.email.id), not ids.email.selector"]: never } : S)`. `ids.email.selector` and `"#email"` fail with the fix in line 1; `ids.email`, `ids.email.id`, `"email"`, a `string` variable and no argument compile. The `${ids.email}` template literal is typed `string` and is not caught by the type; a runtime strip or warn covers it.

## Why it matters

impact 2 (form labels and ARIA relations silently broken: an a11y failure no visual check shows), pain 2 (compiles, lints, renders; only an accessibility audit or a click on the label reveals it), reach 2 (the template's web starter ships it to every site cut from it).

## Rough idea (not a design)

The strongest layer is type (the prototype above, also for `setList`/`setForm`/`setHeaders`, and `Id` accepted on the 8 aria IDREF keys, emitting `.id`). Backstop that fits 8.1.x (bytes change only for values that never worked): `extractId` strips a leading `#` in IDREF sinks, with a dev warning. Template lockstep: fix `contact.ts` to `setFor(ids.x)`.
