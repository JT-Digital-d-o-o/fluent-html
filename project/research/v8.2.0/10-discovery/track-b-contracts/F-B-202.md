# Match errors route through a 2-candidate TS2769 and NoExtraCases reports 'not assignable to never'

## Problem

A 3-argument keyed call `Match(s, "status", {...})` passes the arity check of two overloads: keyed-exhaustive and value-with-default `(value, cases, defaultView)`. TypeScript lists every candidate when 2-3 survive arity (typescript.js:81271), so every keyed error opens with a detour through the value overload (`Argument of type 'State' is not assignable to parameter of type 'string | number'`). Separately, `NoExtraCases` maps a stray key to `never`, so a typo'd case reads `Type '() => Tag' is not assignable to type 'never'` and names neither the key nor the rule.

## Evidence (executed)

`$B2 = <scratch>/wave1/B2`. Six shapes, before (8.1.0) and after (prototype `guard-msg`):

|---|---|---|
| m1 keyed, missing `success` (= recon p02) | TS2769, 7 lines / 1368 chars, `Property 'success' is missing` at char 1035 (line 7) | TS2345, 2 lines / 672 chars, at char 353 (line 2) |
| m2 value, missing case | TS2345, 2 lines / 311 chars | unchanged |

Verbatim after:

```
m.ts(5,52): error TS2345: Argument of type '{ loading: () => Tag; error: (e: { status: "error"; message: string; }) => Tag; }' is not assignable to parameter of type '{ loading: (value: { status: "loading"; }) => View; ... } & NoExtraCases<...>'.
  Property 'success' is missing in type '{ loading: () => Tag; error: (e: { status: "error"; message: string; }) => Tag; }' but required in type '{ ... }'.
m.ts(22,3): error TS2322: Type '() => Tag' is not assignable to type '"'sucess' is not a case of this Match: remove it or fix its spelling"'.
m.ts(29,42): error TS2345: Argument of type '"state"' is not assignable to parameter of type '"status"'.
```

Mechanism (d.ts only): the value-with-default overload becomes `Match<V, C, D>(value: V, ...rest: [V] extends [string | number] ? [cases: C, defaultView: Thunk<D>] : [never, never, never, never, never])`. For an object value the rest instantiates to 5 elements, the candidate fails arity after inference (typescript.js:81454) and leaves the TS2769 list, so the keyed overload reports alone. `NoExtraCases` maps `K` to `` `'${K}' is not a case of this Match: remove it or fix its spelling` ``.

Alternatives measured:
- Overload reorder only: m1's case moves to line 4 but m3 gets worse (the keyed overload's 48-member `Record<"toString" | ...>` print comes first).
- A 3-tuple guard regressed m5 (arity 4 collided with keyed+default): the 5-tuple fixes it.
- Putting the missing case on line 1 via a `MissingCases<Exclude<T, keyof C>>` key works for the value form (m2 line 1 names `"missing case: invited"`) but breaks keyed narrowing (valid.ts:18 fails: context-sensitive handlers defer `C`), a dead end.

Regression checks: valid.ts (exhaustive, subset+default, widened string, numeric, keyed narrowing, keyed+default, return-type equality) 0 errors; lib type-surface.test-d.ts 0 diagnostics; scaffold 9 Match sites and fl-um/na-cent/competify 26 Match sites: 0 new errors.

## Why it matters

impact 2 x pain 2 x reach 3 / effort M. Match is in 19/19 canonical repos, keyed form 104 of 162 canonical-era sites; a missing case renders `""` at runtime (recon 02 #2), so the compile error is the only signal.

## Rough idea (not a design)

Type layer, d.ts-only, additive (every valid call resolves as before). Needs a type-safety lens: the conditional rest tuple is less readable in d.ts and prints `rest_0: never` in the rare residual m3 listing. Residual left open: m3 (value+default typo) stays TS2769 because keyed overloads still pass 3-argument arity.
