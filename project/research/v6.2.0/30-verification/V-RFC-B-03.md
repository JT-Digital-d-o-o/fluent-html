# V-RFC-B-03 — Iframe & embedded security (typed sandbox tokens, Permissions-Policy allow)

## Attack

I attacked through security-escape, type-safety, dx, and breaking-change, defaulting to reject under uncertainty. Every load-bearing claim was checked against source and CHANGELOG.

**(1) Already shipped in 6.1.x? — NO.** Grepped `setSandbox|setAllow|SandboxToken|PermissionsPolicy` across `src/`. `src/elements/embedded.ts:39,49` confirm both setters still take bare `string` (`setAllow(allow?: string)`, `setSandbox(sandbox?: string)`); the stored fields `allow?: string` / `sandbox?: string` are at `:12,:14`. `SandboxToken` and `PermissionsPolicyDirective` do not exist in `html-types.ts` (only `ReferrerPolicy` at :35 and `FetchPriority` at :57). CHANGELOG 6.0.0→6.1.1: `sandbox` appears only as an *initial bare attribute* (6.0.0 "New embedded elements: Iframe (with sandbox…)"); the 6.1.1 iframe retype covered `referrerpolicy`→`ReferrerPolicy` (CHANGELOG:81) and 6.1.0 added `setFetchPriority` (CHANGELOG:115) — neither touched `sandbox`/`allow`. The gap is real and the draft's framing is accurate.

**(2) §11.7 lockstep holes — NONE; correctly N/A.** `sandbox`/`allow` are HTML attributes routed through `defineSchemaKeys` (embedded.ts:71) and serialized at `src/render/serialize.ts:270`, not Tailwind classes. Zero `src/class-vocab/vocab.ts` rows, zero extractor/eslint vocab regen. The draft's §11.7 N/A is correct.

**(3) Naming collisions — NONE.** `setSandbox`/`setAllow` already exist on `IframeTag` (the RFC narrows them in place, no new method name). No `SandboxToken`/`PermissionsPolicyDirective` symbol exists in `html-types.ts`. The eslint `prefer-set-method` map (`sandbox: \"setSandbox\"`, `allow: \"setAllow\"`) is unaffected because the method names don't change — the RFC's 'no eslint change' claim holds.

**(4) Escape / security regression — NONE.** `src/render/serialize.ts:270` `escapeAttr`s every `_sk` field value, including `sandbox`/`allow`. Sandbox tokens are literal (no injection surface); `allow` record values are author strings that ride the existing escaping — a `\"`/`<` in a value cannot break out. The setters do pure synchronous `Array.join`/`Object.entries` string work — §11.1 zero-deps and §11.2 ssr-only/sync hold. The empty-string emission guard at serialize.ts:269 (`value !== undefined && value !== null`) means `sandbox=\"\"` and `allow=\"\"` DO emit (empty string passes), so the 'fully locked' / 'deny all' behaviors are real on the current render path. (Required-change 3 pins this so a future edit can't break it.)

**(5) Breaking-change honesty — PARTIALLY WRONG.** `setSandbox` breaking is correctly marked. But `setAllow` is marked additive on a FALSE premise (see killer objection): if the raw arm is correctly dropped for CONVERGE, `setAllow` becomes breaking too. Even if the RFC stubbornly kept the raw arm, the in-repo test at `test/elements.test.ts:470` (`setSandbox(\"allow-scripts allow-same-origin\")`) breaks and is NOT listed in `guideline_updates` — the migration section only addresses the landing-page raw string. Unowned in-repo breakage.

**(6) Type holes.** `SandboxToken` fully closed (13 WHATWG tokens, no tail) — correct and matches `FetchPriority`'s closed rationale (html-types.ts:52-57). `PermissionsPolicyDirective` open tail is consistent with `LinkRel`/`HttpEquiv` precedent (html-types.ts:30-33,48-50) for growing registries — defensible, but the RFC's security framing makes the open tail's silent-typo admission worth disclosing honestly (required-change 4). No `any`. Stored fields stay `string` legitimately (serialized lists). Overload resolution claim verified sound: `{}` is assignable to `Partial<Record<…>>` but not to `string | undefined`, so `setAllow({})` picks the record arm and `setAllow()` picks the optional arm — though required-change 1 collapses this to a single record overload, removing the resolution subtlety entirely.

## Does it survive?

Yes, with changes. The core thesis — `sandbox` is a fixed 13-token spec enum and belongs in a fully-closed `SandboxToken` union, eliminating a silent security-weakening typo — is a genuine CORE primitive gap, correctly scoped (it's an instruction-set attribute narrowing, not an opinionated component), and the implementation is a byte-identical-render-path setter narrowing. It is not killable: the gap is real, not shipped, lockstep-clean, escape-clean.

What it cannot ship as-drafted: (a) the `setAllow` raw-arm is convergence debt defended by an incorrect claim that the record can't express multi-origin allowlists (it can — the value is a freeform string); (b) `setAllow` is mis-marked additive; (c) the in-repo `test/elements.test.ts` breakage is unowned. All three are mechanical, in-RFC fixes. None reaches reject. → **survives-with-changes**, confidence 0.74 (docked for the false Alternatives premise the author shipped as a settled rejection, which signals the convergence analysis wasn't done).
