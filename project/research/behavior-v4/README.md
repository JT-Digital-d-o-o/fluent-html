# Behavior System v4 — Research & Design

**Problem:** the behavior system was redesigned twice and forked once (v1 data-behavior+runtime -> v2 inline hx-on:* -> v3 template monkey-patch back to data-attributes for CSP), oscillating because the constraint set was never written down or made executable.

**Process:** 14-agent workflow — 4 evidence agents (design archaeology, template dispatcher spec, call-site inventory, htmx 4 stability), 3 precedent agents (LiveView.JS, Stimulus, CSP dispatcher patterns), 3 competing designs (minimal/UPSTREAM, registry-first/fx, platform-native/Bedrock), 3 adversarial attack lenses (CSP+security, morph+lifecycle, DX+extensibility-abuse), 1 synthesis.

**Outcome:** UPSTREAM won (2 of 3 attack lenses), with grafts from fx and Bedrock. See [design.md](design.md).

## Constraint charter (all must hold simultaneously)

- **C1** Strict CSP: per-request nonce + strict-dynamic, no unsafe-eval, no inline JS, no scripts inside swap targets
- **C2** Survives outerMorph and plain swaps; idempotent binding across any number of swaps
- **C3** Typed closed-union call sites; extension via registration + declaration-merged BehaviorMap — amended 2026-07-20: registration is framework-layer-only, apps never extend (ADR-07 amendment)
- **C4** Independent of htmx scripting internals; htmx churn cannot force redesign; htmx-optional where feasible
- **C5** One emission format, no per-app overrides, template fork gets deleted
- **C6** Extensibility cannot rebuild an ad-hoc framework: data-only registration, DOM-as-state, no client store
- **C7** Verifiable by a browser-level acceptance matrix: behavior x {load, swap, outerMorph} x strict CSP

## Competing designs & attack rankings

- **UPSTREAM — the v3 dispatcher, library-owned, contracted, opened one notch** — The v3 fork already survives production under strict CSP; what is wrong with it is only that it lives in the wrong repo, has no contract, and cannot be extended. v4 is the smallest delta that fixes exactly the defects the charter and call-site inventory prove: upstream the delegated dispatcher into fluent-html as a versioned nonce'd head script, replace the flat colliding attribute encoding with per-verb namespacing (restoring multi-behavior), re-cut the vocabulary strictly against 4-repo demand (13 verbs to 10: add drawer, clipboard-feedback, onEscape, onClickOutside, resetOnSuccess; delete the 5 superseded), and open the registry through one narrow spec-driven hook. No JSON command chains, no sticky-op store, no custom elements, no lifecycle API — every feature is paid for by a named call site.
- **fx — Open Verb Registry (extensibility-first v4)** — The registry IS the product: one frozen JSON wire format (`data-fx` = ordered [event-descriptor, steps] bindings, LiveView-style tuples + Stimulus descriptor grammar) executed by one versioned, eval-free, capture-phase-delegated runtime that fluent-html both emits for and ships. Apps extend the vocabulary with `defineBehavior()` — a declaration-merged BehaviorMap entry plus a constrained client handler compiled into a content-hashed runtime asset at boot — so the library never needs a new built-in for an app-specific need again, and the typed surface is generated from the registry, making "it type-checks" and "it fires" the same fact (killing the v2/v3 silent-no-op class).
- **Bedrock — platform-first verbs, residual data-fx dispatcher** — Delete verbs into the platform before implementing them: dialogs, popovers, light-dismiss, focus-trap, scroll-lock and open/close buttons become native `command`/`commandfor` + `<dialog closedby>` / `popover` + CSS — zero behavior-system involvement, morph-safe by element identity, zero owned code in 2027. Everything the platform cannot do collapses into ONE attribute (`data-fx`, a LiveView-style JSON array of [event, verb, opts] tuples) executed by one versioned, capture-phase, document-delegated dispatcher (~2KB) shipped as a static asset from the fluent-html npm package. The bet: the residual vocabulary is small enough (10 verbs) that platform deletion + one wire format ends the A→B→A oscillation, because neither forcing function (runtime-ownership burden, execution-context legality) has anything left to push on.

- *attack-csp-security*: On the CSP + security + C7 lens specifically, rank: A (Upstream) > C (Bedrock) > B (fx). None has a LIVE injection exploit — I verified fluent-html's escapeAttr escapes all five chars including both quotes (escape.ts:6-7,20-30) and Script() bodies pass through sanitizeRawContent's </script guard (serialize.ts:211-219), so the JSON-program-in-attribute breakout I expected to land against B/C does NOT land (JSON.stringify backslash-escapes inner quotes, escapeAttr entity-encodes, browser decode + JSON.parse is structurally sound). Given that shared safety floor, ranking is by residual reopened-door surface and C7 fidelity. A wins: it genuinely deletes the escapeJs class from the behavior path (attributes only), ships ONE guarded inline nonce'd script, and its C7 matrix enumerates mechanically from the registry so it faithfully tests what ships. C has the strongest raw C1 posture (Tier-0 verbs are pure HTML/zero-JS via command/commandfor/popover — nothing to attack) BUT the weakest C7 fidelity: its flagship behavior is browser-divergent (dialog open-state-across-morph depends on moveBefore, Chrome-only; light-dismiss/command Baseline gaps on Safari<26.2), so a Playwright-on-Chromium strict-CSP acceptance run passes GREEN while Safari/Firefox silently diverge — false confidence in the exact matrix meant to prevent silent regressions, plus a JS command-polyfill branch that dilutes the zero-JS story. B ranks last on THIS lens: it is the only design that generates its runtime by fn.toString()-concatenating app-authored function objects into a served .js asset at boot — the closest thing to reopening a code-generation door (minify/closure divergence makes the shipped runtime differ from the fixture-validated source form → silent no-op invisible to C7), and it uniquely ships a `fire` verb (arbitrary app: CustomEvent with attacker-influenceable JSON detail) that is an XSS-gadget amplifier against any unsafe app listener. B's one genuine C7 win — mandatory per-verb fixtures in the defineBehavior type — is not enough to offset the codegen surface. CROSS-CUTTING (dominates all three): the deploy-window skew silent no-op (long-lived pre-deploy page swaps post-deploy HTML carrying a newer verb → unknown verb skipped with console.warn/error) is the precise failure class that caused BOTH prior regressions — silent, production-only, invisible to tests — and C7 as specified in ALL THREE pins a single package+htmx version, so it structurally CANNOT catch skew. That is the scenario most likely to force redesign #5, and none of the three makes it executable.
- *attack-morph-lifecycle*: On the MORPH + LIFECYCLE lens: 1) fx, 2) Bedrock, 3) UPSTREAM. fx ranks first because it is the only design whose stateful pieces (focus trap, scroll-lock, overlay-open) are guarded by DOM predicates recomputed at event time — there is no client-held authority to dangle, so every finding against it is a patchable spec hole (once-semantics, sweep predicate, transient-restore guard, nested-carrier consumption) rather than an architectural liability. Bedrock ranks second: it has the genuinely best teardown story of the three (native dialog close-on-removal, self-reconciling :has() scroll-lock, zero owned lifecycle for Tier 0), but its flagship morph claim is factually wrong — idiomorph attribute-sync strips `open` on node-PRESERVING morphs, closing the modal without the close algorithm (no close event, no focus restore) — and its dialog-vs-popover attribute-reflection asymmetry means the same widget behaves oppositely under the same background morph depending on which platform primitive was chosen; the fixes (hx-preserve emission, containment-gated closeOnNav, per-element-type matrix rows) are real spec surgery, not wording. UPSTREAM ranks last because its one piece of runtime state, the activeDrawer slot, concentrates every classic lifecycle failure: unconditional slot-clear on htmx:after:swap closes the drawer on unrelated polls (upstreaming the exact bug rideshare's main.js has today, verified in source), slot-clear is not specified as a full close (leaked body scroll-lock, stranded focus), a dangling slot after history-restore or non-htmx removal turns the capture-phase focus trap into a document-wide Tab-killer, and the keyup member sitting in BehaviorEvent with no corresponding delegated listener demonstrates — inside the proposal itself — that the hand-maintained union/listener sync that produced the v3 'type-checks but never fires' class is still the process. All three share two lens-wide defects that must be fixed wherever v4 lands: transient-feedback timers that restore pre-morph snapshots over fresh server renders, and undefined nested-carrier Escape semantics (UPSTREAM silently drops the outer behavior; fx/Bedrock double-fire).
- *attack-dx-abuse*: On the DX + extensibility-abuse lens: 1) UPSTREAM, 2) fx, 3) Bedrock. UPSTREAM wins because the call-site surface is unchanged and fully closed-union, the composite drawer is atomic (one verb = whole bundle, so the gap-list interaction cannot be half-assembled), and its worst defects — unfenced string handlers (C6), unspecified registry lifecycle, the same-verb-once grammar ceiling, single-slot drawer — are all fixable without touching the wire format or architecture. fx is second: it has the best end-to-end typing story on paper (typed handler bodies, Wire<T>, registry-generated event unions, mandatory fixtures, dev render-throw), but fn.toString serialization reintroduces the works-in-dev/dead-in-prod failure class the library exists to kill, its documented bundler fallback institutionalizes a second wiring mode (C5), and slots+exec+trigger+fire+custom-verbs is the most capable ad-hoc-framework kit of the three designs (C6 breached by machinery, not just policy) — heavy but survivable fixes. Bedrock fails the lens outright: the #1 demand item (drawer) decomposes into five silently-omittable pieces, the real-world responsive-sidebar shape fits neither dialog nor popover and has no residual verb, closedby/anchor-positioning aren't cross-browser in 2026, and registering one custom behavior requires standing up a client build toolchain the SSR stack doesn't have — the strongest defect-to-public/js pressure, which is precisely the scenario that forces redesign #5.

## Evidence packets

### design-archaeology

The behavior system went through three eras. v1 (5530b19, Mar 14 2026): pure typed plumbing — empty user-augmented BehaviorMap emitting data-behavior + data-{name}-{key} attributes, explicitly shipping NO client JS and NO built-ins, which pushed the init-runtime boilerplate onto every app. v2 (590045b, Mar 15 2026, one day later): inverted both decisions — closed built-in BehaviorMap (8 verbs, grown to 13) whose renderers emit inline JS via hx-on:* attributes, "eliminating the client runtime" by delegating execution to htmx; subsequent commits patched injection holes (9224eff escapeJs everywhere), widened options (3ccbc07 event?/force?/animateOut? + attribute-name-injection guard), and fixed a silently-dead htmx-4 event name (07e4c1b). v3 (projects-template b9d1eef, Jul 3 2026): strict per-request-nonce CSP killed v2 wholesale — htmx compiles hx-on:* via AsyncFunction, requiring 'unsafe-eval', so ALL 13 behaviors silently no-op'd in production apps; the template monkey-patches Tag.prototype.behavior back to data-behavior-* emission plus a ~55-line nonce'd document-delegated dispatcher — i.e. v1's architecture rebuilt in user-land, but with v2's closed vocabulary and typed options kept. Each era's "fix" was the previous era's discarded tradeoff: v1 had CSP-safe emission but no runtime ownership; v2 had runtime ownership but CSP-fatal emission; v3 recombined them outside the library, forking emission semantics (C5 violation) and losing library-owned tests/typing coupling.

### dispatcher-spec

The v3 fork lives in projects-template/templates/full-stack as two small pieces: a Tag.prototype.behavior override (~45 LOC) that re-emits the documented .behavior(name, opts) API as flat data-behavior-* string attributes, and a ~40-line minified, nonce-stamped, document-delegated dispatcher inlined in the layout <head> that implements all 13 library behaviors eval-free. It covers the full built-in vocabulary (nothing missing vs the library's 13) but only a 6-key static option surface, a closed switch (no registry), one behavior per element, a fixed 10-event delegation list, and getElementById-only target resolution. templates/web ships NO htmx runtime and NO dispatcher yet calls .behavior("toggle") in its header — that mobile-menu toggle is dead code today, proving the C4 "htmx-optional" requirement is real.

### callsite-inventory

Exhaustive demand-side inventory across projects-template, ttl, rideshare, and fluent-html-demos found only 4 production `.behavior()` call sites (toggle x2, toggleClass x1, clipboard x1), 3 raw `hx-on` escapes, 1 raw `onclick`, and two hand-rolled public/js runtimes (rideshare 358-line main.js, ttl 20-line data-action dispatcher) that both independently converge on the same delegated-listener architecture the template's v3 dispatcher upstreams. The dominant unmet demand is (1) a composite drawer/overlay verb (4 independent implementations), (2) clipboard-with-transient-feedback (6 call sites, all bypassing the feedback-less built-in), and (3) success-conditioned form reset after swap (2 sites). Roughly half of the 13 current built-ins (focus, scrollTo, selectAll, openDialog, closeDialog, formResetOnSwap, dismissOnEscape, disable) have zero production call sites; `disable` has already been superseded by the htmx-native `disable: "find button"` route option.

### htmx4-stability

htmx 4 (latest: 4.0.0-beta5, June 26 2026; GA targeted late-summer 2026, 'latest' tag early 2027) offers a stable, delegation-friendly event surface for the v4 behavior dispatcher: colon-namespaced lifecycle events dispatched as bubbling+composed+cancelable CustomEvents with a detail.ctx that includes response.status, plus idempotent htmx.process() and explicit cleanup events. hx-on is confirmed eval-based (new Function/AsyncFunction in beta5 source) and officially unusable under no-unsafe-eval CSP, validating the v3 fork's diagnosis. The extension API (registerExtension, hook-per-event) and the hx-csp/inlineScriptNonce script-nonce machinery are the churn-heavy/CSP-incompatible surfaces to avoid; morphs fire no per-node events, so re-init must key off the ordinary swap/process lifecycle, not morph internals.

### liveview-js

Phoenix LiveView.JS is the closest proven precedent for typed, server-composed client commands: ~20 declarative verbs authored in the host language, serialized as a JSON array of [kind, args] tuples inside an ordinary attribute, and executed by a small first-party client engine (no eval — each kind maps to a hand-written exec_* function). Its two killer mechanisms are (a) the sticky store: every class/attribute mutation is recorded as a re-applicable operation in per-element private state (DOM.putSticky) and re-applied during morph patching, so client-side changes survive server patches; and (b) exec/attribute-storage: command lists stored in any attribute can be re-triggered from elsewhere (JS.exec), enabling reuse without duplication. Its escape hatches are dispatch (fire a CustomEvent that user JS listens for) and lifecycle hooks (phx-hook + mounted/updated/destroyed on uniquely-id'd elements). Known limits: purely declarative (no conditionals, can't read state, can't set input.value), verbosity for composite widgets, and hooks requiring unique DOM ids.

### stimulus-api

Stimulus's binding model is a four-part attribute grammar (data-controller / data-action / data-[controller]-target / data-[controller]-[name]-value) driven by a chained MutationObserver architecture that gives idempotent connect/disconnect lifecycle — but its state-in-attributes design is corrupted by morphing (turbo #1210/#1224), and its TypeScript story requires per-property `declare readonly` boilerplate that only community wrappers fix. For fluent-html v4, the most valuable imports are the action-descriptor grammar (event->verb with :prevent/:stop/:self modifiers and keydown.esc-style filters), the typed value serialization table (JSON for objects/arrays, exact boolean/number coercion rules), and default-event-per-element shorthand — all of which a server-side typed builder can emit correctly by construction, eliminating both the runtime type-casting and the declare-boilerplate problems Stimulus has client-side.

### dispatcher-patterns

Researched four architecture areas for the v4 dispatcher. (1) Document-level capture-phase delegation is the proven CSP-safe pattern: non-bubbling events (focus/blur/mouseenter/scroll) are handled via capture phase or bubbling twins (focusin/focusout/mouseover); shadow-root retargeting is the one structural blind spot. (2) Custom elements give free connectedCallback/disconnectedCallback lifecycle but interact badly with morphing (idiomorph historically skipped lifecycle expectations; fixed-ish via moveBefore/two-pass in v0.4+, and connectedMoveCallback only helps in Chrome 133+), and Safari still refuses is=/customized built-ins — so autonomous wrapper elements would force markup changes; attribute-driven delegation avoids all of this. (3) Native invoker commands (command/commandfor) hit Baseline in Dec 2025 (Chrome 135/Firefox 144/Safari 26.2) and can replace dialog/popover open-close verbs with zero JS; dialog closedby is an Interop 2026 focus area. (4) The standard runtime-shipping pattern is a version-stamped self-hosted static file served from the same npm package that renders the attributes (Phoenix LiveView precedent), loaded via one nonce'd script tag in the initial head under strict-dynamic — never scripts inside swap targets, since htmx duplicates/re-executes swapped scripts and stale nonces get blocked (and htmx's own inlineScriptNonce auto-nonce feature is a documented CSP bypass).
