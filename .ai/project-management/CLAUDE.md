# Project Management Guidelines

Markdown files are the PM system. No external tools required to use it; CLI scripts (`npm run focus`, `hill`, `tree`, `pm:lint`) derive status and enforce hygiene from the files plus git history.

**These rules apply only if `project/pm/` exists in the repo.**

## Liveness

PM dies from being born dead or going dark, not from bad structure. Three obligations:

1. **Born lazy.** Create a file the session its work starts, never before. `npm run pm:init` creates only `roadmap.md` plus an empty `INDEX.md`. A scope's `prd.md`/`todo.md`/`qa.md` are created the session work on that scope begins, never as an upfront grid. Smell: a `prd.md` with no sibling `todo.md` and no code committed in the same week is a backlog. `todo.md` is never a backlog.
2. **Kept live.** `roadmap.md` is read first and updated last every session. `npm run focus` warns when `roadmap.md`'s last git-touch predates the last product-code commit; fix that before continuing.
3. **Close, don't delete.** Finished or killed work is archived with an Outcome line, never deleted in place or left frozen.

Hand-write only intent the tools cannot derive (focus, decisions, the worked-out approach). Everything derivable (counts, status, progress) is computed, never typed.

## `roadmap.md` (session brain)

One hand-written file at `project/pm/roadmap.md`. Read first, updated last. Holds only what the tools cannot derive: what we're focused on and why, what's next in what order and why, what's blocked on a human decision, what just shipped. `npm run focus` derives the executable task list; the roadmap supplies the intent ranking can't.

It opens with a generated `## Product Development` checklist: one box per phase of the [Product Development roadmap](../product-development/roadmap.md) (JTBD, research, validate, name, shape, build, ship), each linking to that phase. `pm:init` and the project scaffold seed it from the vendored roadmap; that roadmap is the method, this checklist tracks where the project sits in it. Keep it even at the ~40-line budget; it is a reference, not derived data. The visible text is the phase name (never "Phase N"), so `pm:lint`'s phased-plan rule stays quiet.

```markdown
# Roadmap

<!-- Session brain. Read first, update last. Intent only — no task lists,
     no counts, no dated phase plans. ~40 lines; prune as you go. -->

## Product Development
<!-- One checkbox per phase of ../../.ai/product-development/roadmap.md; generated by pm:init. Check a step when its gate is cleared. -->
- [ ] [Protect the bet](../../.ai/product-development/roadmap.md#phase-0--protect-the-bet--loonshots)
- [ ] [Anchor on the Job](../../.ai/product-development/roadmap.md#phase-1--anchor-on-the-job--competing-against-luck)
- [ ] … (one per phase, through Ship & learn)

## Current Focus
One or two sentences: what this cycle/week is about and why.

## Next Up
- <thing> — why it's next / what it unblocks
- <thing> — why

## Blocked on a Decision
- <question that needs a human call> — who/what it's waiting on

## Just Shipped
- <one line per recent session; collapse older ones to a range; git holds the detail>
```

**Hard limits** (lint-enforced):
- No phased, date-ranged plans (`Phase 1: Mar 17–30 …`). Sequencing lives in `Next Up` as intent, not dates.
- No derived data: counts, percentages, velocity, changelogs.
- ~40-line budget. Collapse old `Just Shipped` entries to a one-line range; git is the changelog.

## File Structure

Fractal: every directory is a scope. Scopes nest recursively; a scope can contain child scopes, and every scope draws from the same file vocabulary. "Project", "epic", "feature" is just depth, not a different concept.

```
/project/pm/
├── roadmap.md            ← session brain (root only) — intent, read-first/update-last
├── INDEX.md              ← scope overview + child links (link-only, no status/counts)
├── inbox.md             ← optional: raw untriaged input (client feedback, meeting notes)
├── decisions.md          ← cross-cutting decisions
│
├── archive/             ← terminal home for closed scopes (see Lifecycle); tools skip it
│   └── [closed-scope]/   ← moved here on ship/supersede/kill, with an Outcome line
│
└── [scope]/              ← live child scope (same vocabulary, recursively)
    ├── INDEX.md          ← only when the scope has children
    ├── prd.md            ← problem, appetite, solution, rabbit holes, no-gos
    ├── design.md        ← optional: the worked-out HOW (approach/algorithm/spike)
    ├── todo.md           ← tasks grouped by user story
    ├── qa.md             ← bugs scoped to this level
    ├── decisions.md      ← scope-level decisions (created on first decision)
    ├── cooldown.md      ← optional: tech debt / cleanup parking lot
    └── [scope]/          ← deeper scope (discovered during the build)
```

| File | When it exists | Holds |
|------|----------------|-------|
| `roadmap.md` | always (root only) | non-derivable intent: focus, next-up, blockers, just-shipped |
| `INDEX.md` | a scope has children | title + links to children. Link-only: never status, counts, or prose state. |
| `prd.md` | a scope is committed to | Problem, Appetite, Solution, Rabbit Holes, No-Gos |
| `design.md` | an uphill story needs a worked-out approach | the HOW: algorithm, spike result, investigation, refactor recipe |
| `todo.md` | work on a scope begins | user stories with tasks + hill markers |
| `qa.md` | a bug is found in this scope | one section per bug |
| `decisions.md` | a decision is made | append-only architecture decisions |
| `inbox.md` | raw external input arrives | untriaged feedback/notes before they become tasks/bugs |
| `cooldown.md` | optional | tech-debt / cleanup parking lot |

Files appear when needed. A scope with just `INDEX.md` plus one child is valid; a leaf with just `prd.md` plus `todo.md` is valid.

**Anti-patterns:** parallel trees (`prd/auth/`, `todo/auth/`); `status.md`/`changelog.md`/`velocity-report.md` files; `## Status:` headings or `> State (date):` blocks inside `INDEX.md`/`todo.md`; hand-written counts/percentages; `TASK-001`/`BUG-003`/`Pattern-A` IDs; binaries (`.docx`, `.png`, `.html`) committed under `pm/` (link from the repo's asset area instead).

### Scoping

Tasks, bugs, and decisions go at the most specific scope they belong to. Parent-level files are for cross-cutting work that spans multiple children (e.g. a root `todo.md` task "Set up CI").

### Depth = Decision History

The tree encodes how scope evolved: outer scopes are older and foundational, inner scopes are newer discoveries made during the build. `git log --diff-filter=A` gives each scope's birth date. This signal survives only under lazy birth (a mass-birth in one commit destroys it). Moving a scope into `archive/` is terminal; its history stays in git.

## Shared Definitions

**No IDs.** File path plus text is the identifier. Cross-reference, don't duplicate:

```markdown
- [ ] [P1] Update shared auth middleware
  - Note: also referenced in auth/login/todo.md
```

**Status marks** (todo.md tasks and qa.md bug headings):

| `[ ]` todo | `[>]` in progress | `[r]` review (code done, **not yet verified**) | `[x]` done | `[-]` cancelled |

`[r]` is not done; verification must close it (see [Verification Loop](#qa-and-the-verification-loop)). `npm run focus` surfaces aged `[r]` so it can't become a holding pen.

**Priority / severity:**

| Level | Task | Bug |
|-------|------|-----|
| P0 | Blocker | App crash, data loss, blocked flow |
| P1 | High | Feature broken, workaround exists |
| P2 | Mid | Visual/minor UX |
| P3 | Low | Polish, nice-to-have |

**Nice-to-haves:** prefix with `~` to mark cuttable scope (`- [ ] [P2] ~Show "link expired" page`). When time is tight, `~` goes first; non-`~` defines the must-have.

## Hill (uphill = blocked on a decision)

Mark a story uphill only when it is genuinely blocked on a human decision: an open question that needs a call before code can proceed. Everything else is unmarked and executable. No mandatory per-story marker, no downhill bookkeeping.

```markdown
<!-- hill: uphill -->
### As a user I want to reset my password so that I can regain access
- [ ] [P1] DECISION NEEDED: reuse magic-link infra, or separate reset tokens?
```

- Only `<!-- hill: uphill -->` is valid. No `downhill`, no invented values.
- `npm run focus` and `npm run hill` list uphill stories as the decisions queue and flag stuck ones (uphill + untouched for days).
- Stuck means make the call, split the story, or spike it, not wait.
- Resolve the decision, delete the marker, and it's executable.
- Dropping a story means [archive with `Outcome: killed`](#lifecycle-archive), not uphill forever.

## Lifecycle: `archive/`

Live scopes stay flat at the pm root; "what's live" is derived by the tools, which keeps the depth=history tree intact. When a scope is fully closed (shipped, superseded, or killed), move it into `project/pm/archive/` with an outcome line at the top of its `INDEX.md` (or `prd.md`):

```markdown
> **Outcome:** shipped — 2026-06-19. <one line: what landed.>
> **Outcome:** superseded by [new-approach](../../new-approach/INDEX.md) — <why>.
> **Outcome:** killed — <why we dropped this bet>.
```

- One terminal dir, three outcomes. Not separate `done/`/`superseded/` trees.
- `killed` is a first-class outcome.
- Tools skip `archive/` by default (`--archived` to include). A scope with open `[r]` work is not closed; don't archive to escape the verification nag.
- Archive is deliberate, typically at cycle end (product) or delivery (client). Git preserves full history regardless.

## Shape Up Mapping

The PM system implements Shape Up's build track. Two flows share the same files; they differ in how scope enters and ends.

| Shape Up concept | PM equivalent |
|---|---|
| Scope (integrated slice) | user-story heading in `todo.md` |
| Shaping / open question | `<!-- hill: uphill -->` + `design.md` |
| Task discovery | tasks added to stories as work reveals them |
| Scope hammering | `~`-prefixed cuttable tasks |
| Circuit breaker | unfinished → `[-]`; scope → `archive/` `Outcome: killed` |
| Cool-down | `cooldown.md` |

**Product flow (SaaS).** Continuous cycles; you choose what to build. Enter scope only through the betting table: create the scope dir plus `prd.md` from the pitch, then `todo.md` with the first story. Only committed bets get files. Appetite = fixed time, variable scope (1–2 day small batch / 1-week big batch). Circuit breaker at cycle end: if must-haves remain, archive the scope `Outcome: killed`; don't carry scraps forward. If it matters it returns as a reshaped pitch.

**Client flow (agency).** Scope comes from a brief/SOW; delivery is the commitment. Enter scope from the brief into `prd.md` (requirements, constraints, deliverables, out-of-scope). Budget = appetite. Negotiate `~` cuts with the client, never drop agreed scope silently. No circuit breaker: you deliver. If over budget, scope-hammer `~` with agreement, renegotiate, or simplify. Mid-project change requests enter via [`inbox.md`](#inboxmd-external-intake), then get triaged into `prd.md` plus new stories, never squeezed in silently.

## Todo Format

Tasks grouped by user story in `todo.md`. Format: `- [status] [priority] Title`, atomic, imperative, one sentence. Every story ends with two mandatory tasks: write tests and check for bugs.

New stories go at the bottom. New features get their own story. A bug-fix task may join a completed story if directly related (prefix `BUG:`).

**Execution order:** decisions-blocked (uphill) stories first; scariest/riskiest work first within a story; top-to-bottom within a story; update status immediately, never batch; break down broad tasks before starting; a task that reveals a bug gets fixed or filed in `qa.md` before moving on.

## `design.md` (the HOW)

Optional, per scope. The worked-out approach for a story whose how isn't obvious: the algorithm, spike result, investigation, refactor recipe, or agent-orchestration plan. This is the artifact for the uphill phase.

- `prd.md` = what and why. `design.md` = how. `todo.md` = the task list that falls out of the how.
- When the design produces a decision, record it in `decisions.md` and link; don't duplicate.
- Keep it to the worked-out approach; delete or fold it once the story is built and the decisions are captured. Budget-capped.

## QA and the Verification Loop

Each bug is a section in the relevant scope's `qa.md`; the heading is the summary (status + severity). `qa.md` is the sole bug ledger: no `bugs.md` inbox, no IDs, no silent code-only fixes.

```markdown
## [ ] [P1] Login fails with special characters in password
**Date:** 10. 03. 26
**Linked:** auth/login/todo.md — Implement auth endpoint
**Repro:**
1. Go to login page
2. Enter a password containing `&` or `<`
3. Submit
**Expected:** Login succeeds
**Actual:** 500 error
**Resolution:**
```

The loop must close. A fix is not done until its bug reaches `[x]` with a Resolution: found `[ ]`, fixing `[>]`, verified fixed `[x]` + Resolution. A fix commit that never moved its `qa.md` entry is incomplete; the same holds for `[r]` review tasks in `todo.md`. `npm run focus` lists aged `[r]` tasks and bugs as loudly as P0s.

## `inbox.md` (external intake)

Optional landing zone for raw, untriaged external input (client feedback, meeting action-points, bug dumps, stakeholder notes, often not in English) before it becomes structured tasks/bugs.

- Triage promptly: each item becomes a `qa.md` bug, a `todo.md` task, a `prd.md` change request, or a decision, then is struck from the inbox.
- Keep source binaries (decks, `.docx`, screenshots) out of `pm/`; link to them in the repo's asset area.
- A small root-level `inbox.md` (or a `## Incoming` section in `roadmap.md`) is enough; don't build a parallel tracker.

## Cooldown

`cooldown.md`: optional parking lot for tech debt, cleanup, or exploration that isn't committed scope. Categories as `##` headings, items as checkboxes. No priorities, no stories. When picked up, remove the item and create proper scope files. Prune between cycles.

## Decisions Format

Scope-level goes in `[scope]/decisions.md`; cross-cutting goes in the parent's. Record before writing code.

```markdown
## Use Resend instead of SendGrid for transactional email
**Date:** 10. 03. 26
**Context:** Need transactional email for password reset and verification.
**Decision:** Resend over SendGrid — simpler API, better DX, sufficient for our volume.
**Reasoning:** SendGrid needs more config and has a steeper learning curve for basic use.
**Consequences:** Locked into Resend pricing; migration would mean rewriting templates.
```

Append-only. Never edit a past decision; add a new one that supersedes it and note the supersession in both. No `## Resolved`/`## Open` buckets: one section per decision, newest at the bottom.

## Writing Discipline

- Terse. Link, don't duplicate. Omit anything derivable.
- `INDEX.md` is link-only: title plus child links, no status, counts, or prose state. (Lint-enforced; the most common breach.)
- Length budgets, self-pruned: `roadmap.md` ~40 lines; `prd.md`/`design.md` stay focused; collapse old `Just Shipped`/session detail to ranges.
- No derived data, no binaries under `pm/`. `pm:lint` flags `## Status:` headings, `State (date):`/count/percentage blocks, `velocity`/`changelog`-style files, and committed binaries.

## Tooling

CLI scripts in `project/scripts/` derive everything from the files plus git; never hand-maintain what they compute.

| Command | Purpose |
|---|---|
| `npm run focus` | **Start here.** The startup dashboard (see Session Start). Warns if `roadmap.md` is stale vs code. |
| `npm run hill` | Uphill (blocked-on-decision) stories; flags stuck ones. |
| `npm run tree` | Scope tree with task counts + progress. |
| `npm run pm:init` | Bootstrap a `roadmap.md` + empty `INDEX.md`, and nothing else (enforces lazy birth). |
| `npm run pm:lint` | Fail on derived-data leakage, non-link INDEX, committed binaries, budget breaches. |

`npm run roadmap` is removed; `focus` supersedes it, and the hand-written `roadmap.md` is the real roadmap.

## File Update Rules

| Event | Action |
|-------|--------|
| Session start | Read `roadmap.md`; run `npm run focus` (heed the staleness + aged-`[r]` warnings) |
| Starting a task | Mark `[>]` in the scope's `todo.md` |
| Task done | Mark `[x]` immediately (never batch) |
| Decision needed | Mark the story `<!-- hill: uphill -->`; resolve, log in `decisions.md`, delete the marker |
| New scope begins | Create the scope dir + `prd.md` now (not before work starts) |
| Bug found | Add a `qa.md` entry in the right scope before continuing |
| Bug verified fixed | Move it to `[x]` + Resolution (the loop must close) |
| Architecture decision | Log to the most specific `decisions.md`, before the code |
| Scope shipped / killed | Move to `archive/` with an `Outcome:` line |
| Session end | Update `roadmap.md` (Current Focus, Just Shipped, Blocked) |

## Session Start

1. Read `roadmap.md`: focus, what's next and why, what's blocked.
2. `npm run focus`, then heed in order: stale-roadmap warning, critical bugs, aged `[r]`, decisions queue (uphill), ready-to-execute.
3. Make the open decisions before writing code; uphill is for thinking, not coding.
