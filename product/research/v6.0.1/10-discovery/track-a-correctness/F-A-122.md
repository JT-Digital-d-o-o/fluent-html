# setDataAttrs skips key validation — attribute-name injection through dynamic data-* keys

## Problem
`buildAttrs` writes the keys of the `attributes` bag into the markup **verbatim** — only the
*value* is escaped, never the key:

```ts
// src/render/serialize.ts:268-270
const value = extraAttrs[key];
if (value !== undefined && value !== null) {
  attrs += ' ' + key + '="' + escapeAttr(String(value)) + '"';   // key is raw
}
```

This is safe only because every writer into `attributes` is supposed to validate its key.
`addAttribute` does (`validateAttributeKey`, tag.ts:159) and `setAria` validates its *computed*
key (tag.ts:365). But `setDataAttrs` writes the computed `data-…` key with **no validation**:

```ts
// src/core/tag.ts:305-310
setDataAttrs(attrs: Record<string, string>): this {
  if (this.attributes === EMPTY_ATTRS) this.attributes = Object.create(null) as Record<string, string>;
  for (const [key, value] of Object.entries(attrs)) {
    this.attributes[`data-${kebabCase(key)}`] = value;   // <-- no validateAttributeKey
  }
  return this;
}
```

`kebabCase` only lower-cases/hyphenates; it does not strip quotes, spaces, or `=`. The
`Record<string, string>` type cannot constrain key *contents*, so a dynamic key (the common
case — keys often come from a data record) injects directly into the attribute name.

## Evidence
Reproduction (built from the shipped tree):

```
Button("x").setDataAttrs({ 'foo"onx=y z': "v" })
=> <button data-foo"onx=y z="v">x</button>
```

The `"` closes the `data-…` attribute name and `onx=y` becomes a live attribute on the
button — attribute-name injection, the exact threat the `validateAttributeKey` choke point and
the `hx-status` / boolean-toggle / `hx-on` regex guards exist to stop. `setDataAttrs` is the one
key-writing setter that bypasses all of them.

## Why it matters
Data attributes are the single most likely setter to receive dynamic keys (an object built from
a record, a config map, i18n keys). `addAttribute` and `setAria` are hardened; `setDataAttrs`
silently is not, so the same untrusted-key input is safe through one API and exploitable through
another. High pain because it's an escape-by-default hole reachable with fully type-valid input.

## Rough idea (not a design)
Patch (6.0.1): call `validateAttributeKey(`data-${kebabCase(key)}`)` before the assignment,
mirroring `setAria` exactly. Add a security.test.ts case asserting a key with a quote/space
throws. No public-shape change.
