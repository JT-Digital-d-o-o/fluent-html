# hx-preload string value is emitted UNescaped — attribute breakout / XSS hole

## Problem
Every HTMX string attribute is run through `escapeAttr` before being written into its
double-quoted attribute value — except `hx-preload`. The `preload` special-case writes the
raw string straight into the markup:

```ts
// src/render/serialize.ts:186-191
if (htmx.optimistic !== undefined) result += ' hx-optimistic';
if (htmx.preload !== undefined) {
  result += typeof htmx.preload === 'string'
    ? ' hx-preload="' + htmx.preload + '"'   // <-- htmx.preload is NOT escaped
    : ' hx-preload';
}
```

A `"` in the value closes the attribute and lets the rest be parsed as new markup —
i.e. attribute-name injection / XSS, the exact class the rest of the serializer guards.

## Evidence
Reproduction (built from the shipped tree):

```
A("x").setHtmx("/p", { preload: 'mouseover" onclick="alert(1)' })
=> <a hx-get="/p" hx-preload="mouseover" onclick="alert(1)">x</a>
```

The injected `onclick="alert(1)"` is now a live attribute on the anchor.

The type `preload?: 'mousedown' | 'mouseover' | boolean` (src/htmx.ts:252) *usually* blocks a
bad string at compile time, but the value flows through `HxOptions`/`RouteHxOptions` and any
untyped caller, an `as string`, a value read from config/i18n, or a JS consumer reaches the
unescaped branch. The escape-by-default invariant must hold at the renderer, not rely on the
caller's type. Note the existing tests (test/htmx.test.ts:158/160) only assert the two happy
union values; the unescaped path is untested.

## Why it matters
This is a true XSS regression in a security-first SSR library: a single dynamic `preload`
value (e.g. a feature-flagged preload strategy) produces injectable HTML. Every other htmx
string attr (target, swap, trigger, confirm, include, …) is escaped; `preload` and the bare
specials are the lone exception, so this is also an internal inconsistency that hides the risk.

## Rough idea (not a design)
Patch (6.0.1): in the string branch wrap with `escapeAttr(htmx.preload)`. Mirror the
existing `str()`/`boolOrStr()` helpers so it can't drift again, and add a security.test.ts
case asserting a `"`-bearing preload is `&quot;`-escaped.
