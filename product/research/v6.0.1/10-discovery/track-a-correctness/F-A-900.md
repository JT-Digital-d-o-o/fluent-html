# sanitizeRawContent only guards bare `</script` — the `<!--<script` "double-escaped" state defeats the break-out guard

## Problem
`sanitizeRawContent` is the sole XSS guard for content placed inside a raw-text
`<script>` (the only escaping a `Script(userData)` call gets). It escapes the
ASCII close tag `</script` and nothing else:

```ts
// src/render/serialize.ts:223,227-232
const SCRIPT_CLOSE_RE = /<\/script/gi;
const STYLE_CLOSE_RE = /<\/style/gi;

export function sanitizeRawContent(content: string, element: 'script' | 'style'): string {
  if (element === 'script') {
    return content.replace(SCRIPT_CLOSE_RE, '<\\/script');
  }
  return content.replace(STYLE_CLOSE_RE, '<\\/style');
}
```

That is necessary but **not sufficient** for `<script>`. Per the HTML tokenizer,
inside script raw text the sequence `<!--` switches the parser to *script data
escaped* state, and a subsequent **`<script`** *start* tag (note: no slash, so the
`</script` regex never fires) switches it to *script data double escaped* state. In
that state the **next `</script>` does not close the element** — the parser keeps
consuming. So an author who interpolates attacker-controlled data containing
`<!--<script>` neutralizes the legit closing tag that follows, and everything up to a
*later* `</script>` is swallowed as script — re-enabling the very break-out the guard
exists to stop.

Observed (built `dist`, `render(Script("<!--<script> </sCrIpT > alert(1)"))`):

```
<script><!--<script> <\/script > alert(1)</script>
```

The `</sCrIpT` got escaped to `<\/script`, but the `<!--<script>` opener passed
through untouched. A browser parsing this enters double-escaped state at `<script>`
and will not treat the library's own trailing `</script>` as the end — the guard is
bypassed.

## Evidence
- `src/render/serialize.ts:223` — `SCRIPT_CLOSE_RE = /<\/script/gi` is the only pattern; no `<!--` / `<script`-opener handling.
- `src/render/serialize.ts:229` — the replace covers solely the close tag.
- `test/stream.test.ts:226-230` — the *only* script-sanitization test is `Script("document.write('</script>')")`; the `<!--<script>` double-escaped vector is never exercised, so coverage masks the hole.

## Why it matters
`Script()` is the sanctioned way to emit inline JS, and the comment is explicit that
`sanitizeRawContent` is the break-out guard authors rely on. Any app that pipes
user-influenced data into a `<script>` body (analytics payloads, JSON bootstrap,
config blobs) is exposed to script injection despite the guard appearing to fire.
High pain (XSS), low frequency of call-site but catastrophic per occurrence.

## Rough idea (not a design)
Patch (6.0.1, no shape change): in the `script` branch also escape the state-opening
sequences — e.g. rewrite `<!--` and any `<script` *start* tag the same way (`<\!--`,
`<\script`) so attacker data can never drive the parser into escaped/double-escaped
state. Add the `<!--<script>...</script>` vector to `security.test.ts` and the stream
fuzz leaves. (`<style>` does not have an analogous double-escaped state, so its guard
is fine.)
