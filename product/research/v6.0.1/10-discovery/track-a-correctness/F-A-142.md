# HxResponse.trigger merge corrupts/loses triggers when a prior bare event name parses as JSON

## Problem
`HxResponse.trigger` stores the first detail-less event as the **bare string** `event` in the `HX-Trigger` header, but stores subsequent merges as a JSON object. To merge, it `JSON.parse(existing)`s the header. When the previously-stored bare event name itself parses as valid JSON of a non-object type (a number, `true`/`false`/`null`, or an array/object-looking string), `JSON.parse` succeeds, the code mutates a primitive/array, and the subsequent `JSON.stringify` silently drops the new trigger.

## Evidence

```ts
// src/patterns.ts:202-226
trigger(event: string, detail?: Record<string, unknown>): this {
  const existing = this._headers["HX-Trigger"];
  if (existing) {
    try {
      const parsed = JSON.parse(existing);          // existing may be a BARE event name
      if (detail) { parsed[event] = detail; }       // no-op on number; mutates array
      else        { parsed[event] = {}; }
      this._headers["HX-Trigger"] = JSON.stringify(parsed);
    } catch { /* treat existing as a bare string */ }
  } else {
    if (detail) this._headers["HX-Trigger"] = JSON.stringify({ [event]: detail });
    else        this._headers["HX-Trigger"] = event;   // <-- stored bare
  }
  return this;
}
```

Reproduction (first event name happens to be JSON-parseable):

```
hxResponse(v).trigger("[1,2]").trigger("showToast", { msg: "hi" })
// after 1st: HX-Trigger = "[1,2]"
// 2nd: JSON.parse("[1,2]") → [1,2]; [1,2]["showToast"] = {...}; JSON.stringify → "[1,2]"
// RESULT: HX-Trigger = "[1,2]"  — showToast is LOST, original corrupted
```

`"true"`, `"null"`, `"42"` event names parse to non-objects and assign onto a boxed primitive (no-op), so the second trigger is dropped while the header becomes `{"true":{}, …}` only by luck of re-stringification.

## Why it matters
The dual representation (bare string vs JSON object) for the same header is the root flaw; the `JSON.parse(existing)` round-trip cannot distinguish "the header is a JSON object I wrote" from "the header is a bare event name that coincidentally parses". Event names are author-controlled and usually safe, but the merge is silently lossy at the exact moment a server emits multiple triggers — a data-loss bug with no error surfaced.

## Rough idea (not a design)
Patch (6.0.1): keep an internal structured accumulator (e.g. `string | Record<string, unknown>`) on the builder; append to it directly and only `JSON.stringify` (or leave bare) once in `build()`/`getHeaders()`. Never parse the serialized header back. No public-shape change.
