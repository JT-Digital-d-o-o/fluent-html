# AriaAttrs value type is a blanket string — the closed *name* union has no matching closed *value* unions

## Problem
The aria attribute *names* are a closed union (good), but every value is `string | number | boolean`. So while `setAria({ labeledby: … })` is correctly a compile error, `setAria({ checked: "mixde" })`, `setAria({ haspopup: "menyu" })`, `setAria({ current: "stpe" })`, and `setAria({ live: "asertive" })` all type-check and silently emit garbage. The JSDoc promises the tristate `"mixed"` is supported, but nothing constrains it to that value.

## Evidence
```ts
// src/core/aria-types.ts:52
export type AriaValue = string | number | boolean;
```
```ts
// src/core/aria-types.ts:59
export type AriaAttrs =
  & Partial<Record<AriaAttributeName, AriaValue>>
  & Record<`aria-${string}`, string>;
```
```ts
// src/core/tag.ts:360
setAria(attrs: AriaAttrs): this { ... this.attributes[attrKey] = String(value); }
```
Every standard key maps to the same widened `AriaValue`. The enumerated ARIA states/properties — `aria-current` (`page|step|location|date|time|true|false`), `aria-haspopup` (`menu|listbox|tree|grid|dialog|true|false`), `aria-sort`, `aria-live`, `aria-orientation`, the tristates `aria-checked`/`aria-pressed` (`boolean | "mixed"`) — have no per-key value type.

## Why it matters
Low pain individually but it's a real type-hole in the one API whose stated purpose is typo-proof ARIA. The name half is closed; the value half is wide open. Inconsistent and surprising — a user reasonably expects `current: "stpe"` to fail like a bad name does.

## Rough idea (not a design)
Additive (6.1.0): replace the flat `Partial<Record<AriaAttributeName, AriaValue>>` with a mapped type keyed per attribute, giving tristate and token states their real enumerations while leaving free-text states (`label`, `valuetext`) as `string`. Non-breaking for all valid existing values.
