# ID-referencing form attributes ignore the `Id` type

## Problem
`setId` already accepts `string | Id` (the `defineIds` branded token), but the attributes that *reference* an id — `<input list>`, `<label for>`, `<output for>` — are typed as bare `string`. So a developer who created a `<datalist id={ids.cities}>` must hand-stringify the same token to wire the input's `list`, defeating the typed-id machinery and inviting drift between the two strings.

## Evidence
```ts
// src/elements/forms.ts:101
setList(list?: string): this { this.list = list; return this; }
// src/elements/forms.ts:258
setFor(forId?: string): this { this.for = forId; return this; }   // LabelTag
// src/elements/forms.ts:480
setFor(forId?: string): this { this.for = forId; return this; }   // OutputTag
```

Compare `setId` (src/core/tag.ts:87) which is `setId(id?: string | Id)`. The reference side was never widened, so `Input().setList(ids.cities)` doesn't type-check even though `Datalist().setId(ids.cities)` does.

## Why it matters
Datalist autocomplete, every `<label for>`, and `<output for>` are core accessible-form plumbing. Letting the *reference* attributes accept the same `Id` token closes the loop on the `defineIds` contract and removes a stringly-typed seam that is easy to typo (a wrong `for` silently breaks label/control association — an a11y regression with no compile error).

## Rough idea (not a design)
Additive (6.1.0): widen the three setter signatures to `string | Id` (and coerce in the body, as `setId` does). Pure signature widening — no runtime behavior change, no break. Pairs naturally with F-B-122's `setForm(string | Id)`.
