# Invoker Commands (command/commandfor) absent

## Problem
The Invoker Commands API (`command` + `commandfor` on `<button>`) is the declarative, JS-free way to drive a `<dialog>` or popover from a button: `command="show-modal"`, `command="close"`, `command="request-close"`, `command="toggle-popover"`, etc. fluent-html v6.0.0 has no surface for it. Worse, the library currently solves the *same problem* by shipping hand-written JavaScript inside the behavior system:

```ts
// src/core/behavior-methods.ts:133
openDialog: (opts) => [
  "click",
  `${el(opts.target)}.showModal()`,
],
closeDialog: (opts) => [
  "click",
  `${el(opts.target)}.close()`,        // src/core/behavior-methods.ts:137
],
```

These emit `hx-on:click="...showModal()"` — runtime JS the library owns — when the platform now offers a fully declarative equivalent with no script at all and built-in `request-close` (fires `cancel`, respects `closedby`). `ButtonTag` (src/elements/forms.ts:215) has no `command`/`commandfor` setters, so the typed/declarative path doesn't exist.

## Why it matters
This is the strongest instruction-set fit in the whole interactivity angle: invoker commands are a *primitive*, not a component, and they let the library stop generating imperative `showModal()`/`close()` strings. Every dialog/popover trigger in an SSR app is a call-site. The declarative form is also more robust (works without the behavior plumbing, gets `request-close` semantics for free).

## Rough idea (not a design)
Additive (6.1.0): on `ButtonTag`, `.setCommandfor(id: Id)` + `.setCommand(cmd)` where `cmd` is a union of the built-in commands (`"show-modal" | "close" | "request-close" | "toggle-popover" | "show-popover" | "hide-popover"`) plus a `--custom` escape. Keep `openDialog`/`closeDialog` behaviors for HTMX-driven targets but document the command path as preferred. No class strings → no vocab sync; carries guidelines + JSDoc.
