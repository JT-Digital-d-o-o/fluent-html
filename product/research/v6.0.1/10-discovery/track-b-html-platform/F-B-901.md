# SourceTag lacks width/height — responsive <picture> sources can't declare dimensions

## Problem
The HTML spec gained `width` and `height` content attributes on `<source>` (inside
`<picture>`) specifically so art-directed responsive images can reserve layout space and
avoid Cumulative Layout Shift — each candidate crop has a different aspect ratio, so a
single `<img width/height>` is not enough. `ImgTag` exposes `setWidth`/`setHeight`, but
`SourceTag` does not:

```ts
// src/elements/media.ts:81 — SourceTag: no width/height fields or setters
export class SourceTag extends Tag {
  src?: string;
  srcset?: string;
  sizes?: string;
  type?: string;
  media?: string;
  // (no width / height)
}

// src/elements/media.ts:114 — and they're absent from the schema keys
defineSchemaKeys(SourceTag, ['src', 'srcset', 'media', 'sizes', 'type']);
```

Compare `ImgTag`, which has them:

```ts
// src/elements/media.ts:16 — ImgTag carries width/height
width?: string;
height?: string;
```

So the recommended CLS-safe `<picture>` pattern is unreachable typed:

```ts
Picture(
  Source().setSrcset("/hero-wide.avif").setMedia("(min-width:1024px)")
    .addAttribute("width", "1600").addAttribute("height", "600"),  // ✗ untyped
  Source().setSrcset("/hero-square.avif").setMedia("(max-width:1023px)")
    .addAttribute("width", "800").addAttribute("height", "800"),   // ✗ untyped
  Img().setSrc("/hero.jpg").setWidth("800").setHeight("800"),
)
```

## Evidence
- `src/elements/media.ts:81` — `SourceTag` class declares `src/srcset/sizes/type/media` only; no `width`/`height`.
- `src/elements/media.ts:114` — `defineSchemaKeys(SourceTag, ...)` omits `width`/`height`, so even form/schema wiring can't see them.
- `src/elements/media.ts:16` — `ImgTag` has the very setters `SourceTag` is missing, proving the inconsistency is unintentional rather than a deliberate cut.

## Why it matters
Core Web Vitals (CLS) is a ranking + UX signal. Art-directed `<picture>` (different
crops per breakpoint) is the canonical case where per-`<source>` dimensions matter, and
it's exactly when a single `<img>`'s width/height can't cover all candidates. Any
marketing/landing surface doing responsive hero images hits this and is forced into the
untyped escape hatch — inconsistent with the `<img>` API right next to it.

## Rough idea (not a design)
Add `setWidth`/`setHeight` to `SourceTag` mirroring `ImgTag` (string-typed for
consistency) and append both to its `defineSchemaKeys`. Purely additive (6.1.0); no
class string, so only JSDoc + the responsive-images guideline section need updating.
