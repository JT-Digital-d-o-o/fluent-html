# MetaTag.name is an unconstrained string

## Problem
The standard `<meta name=…>` registry — `theme-color`, `color-scheme`, `viewport`, `description`, `referrer`, `robots`, `application-name`, `color-scheme` — drives the browser UI (address-bar tint, light/dark form-control rendering, mobile scaling) and SEO. `MetaTag.name` is a bare `string`. There is no union and no helper, so `name="theme-colour"` or `name="color-sheme"` compiles and silently does nothing. `http-equiv` got a typed `HttpEquiv` union (html-types.ts:48) but the far more frequently used `name` axis did not.

## Evidence
```ts
// src/elements/document.ts:62, 68
export class MetaTag extends Tag {
  name?: string;            // bare string — no MetaName union
  content?: string;
  ...
}
setName(name?: string): this { this.name = name; return this; }
```

Contrast with the sibling pragma axis which *is* typed:

```ts
// src/elements/document.ts:84
setHttpEquiv(httpEquiv?: HttpEquiv): this { ... }   // HttpEquiv union exists
```

`content` is necessarily free-form, but `name` is a closed-ish registry and is the one users actually fat-finger.

## Why it matters
`theme-color` and `color-scheme` are the two metas every modern dark-mode-aware SSR app sets, and `viewport` is mandatory on every page. A typo is invisible until someone notices the address bar is the wrong color in production. Medium frequency (several per layout), medium pain (silent UI/SEO regressions). This is squarely the "bare `string` where a literal union fits" guardrail.

## Rough idea (not a design)
Additive (6.1.0): a `MetaName` union (with a `(string & {})` tail for OG/custom metas, mirroring `LinkRel`) typing `setName`; optionally thin combinators `ThemeColor(color)`, `ColorScheme("light dark")`, `Viewport(...)` that pre-fill `name`+`content`. Pairs with the loading-media perf cluster ([[F-B-160]], [[F-B-161]]).
