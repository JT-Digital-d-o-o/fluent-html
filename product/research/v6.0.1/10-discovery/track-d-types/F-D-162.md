# The `form` attribute has no typed setter on any control

## Problem
HTML's `form` attribute lets a labelable control live anywhere in the document and still belong to a form by id (the standard pattern for footer-pinned submit bars, modal forms whose buttons are in the `<dialog>` footer, etc.). Every form-associated tag in the lib (`InputTag`, `SelectTag`, `TextareaTag`, `ButtonTag`, `OutputTag`, `FieldsetTag`) is missing a `setForm`. `grep -rn "setForm" src/` returns nothing; there is no `form?` field on any element class.

## Evidence
```ts
// src/elements/forms.ts:457 — FieldsetTag has name but no form
export class FieldsetTag extends Tag {
  name?: string;
  setName(name?: string): this { ... }
}

// src/elements/forms.ts:476 — OutputTag has for + name but no form
export class OutputTag extends Tag {
  for?: string;
  name?: string;
  ...
}
```
The only escape is the untyped, convention-violating path the CLAUDE.md guidelines explicitly discourage:
```ts
// src/core/tag.ts:158 — "Prefer typed setter methods … over this."
addAttribute(key: string, value: string): this { ... }
Input().addAttribute("form", "checkout")   // ✗ untyped string id, no Id support
```

## Why it matters
6 element classes, and the pattern is common precisely in the SSR + native-`<dialog>` workflows this lib targets (submit button physically outside the `<form>`). Today it silently falls back to `addAttribute`, losing the `Id`-object type-safety the rest of the library enforces via `defineIds`.

## Rough idea (not a design)
Add `setForm(formId?: string | Id)` (normalize `Id` the way `setId` does) to the form-associated tags and register the schema key. Net-new additive surface → 6.1.0; no breaking change, no class-vocab impact.
