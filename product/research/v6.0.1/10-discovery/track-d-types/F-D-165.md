# Born-deprecated helpers in a greenfield release

## Problem
`OOB` and `withOOB` are exported from the public barrel AND marked `@deprecated` in the same v6.0.0 release. v6 is explicitly greenfield-only with no v5 back-compat (recorded constraint), so there is no existing caller these aliases exist to support — they are deprecated on arrival, which is a convergence contradiction ("ship one way to do each thing").

## Evidence
```ts
// src/patterns.ts:23
/** @deprecated Use `Partial()` instead for htmx 4+. OOB swaps are replaced by `<hx-partial>`. */
export function OOB(target: string | Id, content: View, swap?: HxSwapStyle): Tag { ... }

// src/patterns.ts:53
/** @deprecated Use `Partial()` instead for htmx 4+. */
export function withOOB(main: View, ...oob: View[]): View[] { ... }
```
And they are re-exported as first-class public surface:
```ts
// src/index.ts
export {
  // OOB helpers (deprecated — use Partial)
  OOB,
  withOOB,
  Partial,
  ...
}
```
A greenfield user reading the docs/`.d.ts` sees two deprecated functions next to their replacement and must ask "why are these here?" — the answer (v5 migration) does not apply, because v5 callers don't exist in v6 projects.

## Why it matters
Two public exports, every consumer of the htmx patterns barrel sees them. Born-deprecated surface is dead weight that confuses the "use Partial" message htmx 4 wants to send, and it widens the public `.d.ts` for no migration benefit.

## Rough idea (not a design)
Decide explicitly: since there is no back-compat obligation, cut OOB/withOOB. Removal is a public-shape change → parked-major. For 6.0.x, at minimum the CHANGELOG must name the removal version so the deprecation isn't open-ended. (Keeping them indefinitely is the wrong default for a converge release.)
