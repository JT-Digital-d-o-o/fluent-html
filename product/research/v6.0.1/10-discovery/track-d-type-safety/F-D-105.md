# The typed-form binding casts away Input's own overload signatures

## Problem
`Form<T>`'s field binding is the lib's flagship type-safety feature, yet its `input()` factory reaches past the very overloads it ships by force-casting the `Input` function:

```ts
// src/elements/forms.ts:342
const tag = type ? (Input as (t: InputType) => InputTag)(type) : Input();
```
The cast exists because `Input` is overloaded into `NumericInputTag`/`DateTimeInputTag`/`NoMinMaxInputTag` (forms.ts:128-137) and the binding wants the plain `InputTag` regardless. So the one place that most advertises type safety opts out of it with a function-type assertion — if the overload set drifts, this cast hides the mismatch.

## Evidence
```ts
// src/elements/forms.ts:128-133  — the overloads the cast routes around
export function Input(): InputTag;
export function Input(type: NumericInputType): NumericInputTag;
export function Input(type: DateTimeInputType): DateTimeInputTag;
export function Input(type: NoMinMaxInputType): NoMinMaxInputTag;
// src/elements/forms.ts:342  — the binding casts past all of them
const tag = type ? (Input as (t: InputType) => InputTag)(type) : Input();
```

## Why it matters
Low frequency (one call site) but high symbolic value: Track D is "remove unsafe casts." This is a removable one — the cast only exists because the un-overloaded implementation body isn't exposed internally. Extracting it deletes the assertion entirely with no behavior change.

## Rough idea (not a design)
6.1.0 / 6.0.1 (no public shape change): factor the current implementation body into an internal `makeInput(type?: InputType): InputTag`; the public overloads delegate to it, and `createFormBinding.input` calls `makeInput` directly. The `as`-cast disappears. Pure refactor, byte-identical output — could even land as 6.0.1.
