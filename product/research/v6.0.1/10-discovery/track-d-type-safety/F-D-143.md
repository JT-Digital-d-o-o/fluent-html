# Form<T> select/hidden values aren't bound to the field's type

## Problem
`Form<T>` constrains every field *name* to `keyof T` (the headline feature), but the
*values* it wires for `select` and `hidden` are plain `string`. For a field whose
type is a literal union — the canonical `role: "admin" | "viewer"` from CLAUDE.md —
the option set and the hidden value are unchecked against that union.

## Evidence
```ts
// src/elements/forms.ts:320
export type SelectOption = { value: string; label: string };

// src/elements/forms.ts:330-331
select(name: keyof T & string, options: readonly SelectOption[]): SelectTag;
hidden(name: keyof T & string, value: string): InputTag;
```
So this compiles despite being wrong against the schema:
```ts
Form<{ role: "admin" | "viewer" }>((f) => [
  f.select("role", [{ value: "amdin", label: "Admin" }]),  // typo — no error
  f.hidden("role", "superuser"),                           // off-union — no error
])
```
The name `"role"` is type-checked; the values that will actually be submitted for
that field are not — which is the part that reaches the server.

## Why it matters
Selects and hidden fields are precisely where literal-union fields live (roles,
statuses, visibility). Binding the name but not the value catches the cheap typo
(field name) and misses the expensive one (a value the server's enum rejects at
runtime). It's a half-delivered guarantee in the form primitive that the whole track
is about.

## Rough idea (not a design)
Additive (6.1.0): make `select`/`hidden` generic over the picked name —
`select<N extends keyof T & string>(name: N, options: readonly { value: T[N] & string; label: string }[])`
and `hidden<N>(name: N, value: T[N] & string)`. When `T[N]` is `string` it degrades
gracefully to today's behavior; when it's a union it's enforced. Runtime unchanged.
