# defineIds returns a single un-parameterized `Id` brand

## Problem
Every id produced by `createId`/`defineIds` has the identical type `Id`. The brand
prevents *structural spoofing* (a raw object can't masquerade as an `Id`) but does
nothing to keep ids from *different registries* apart. An id meant for one feature's
layout is freely assignable as an `hx-target` for another's.

## Evidence
```ts
// src/ids.ts:23
export interface Id {
  readonly [__idBrand]: true;
  readonly id: string;
  readonly selector: string;
  toString(): string;
}

// src/ids.ts:63
type IdRegistry<T extends readonly string[]> = {
  readonly [K in T[number] as KebabToCamel<K>]: Id;   // every entry is the SAME Id
};
```
And the consumer side erases provenance entirely — `target?: HxTarget | Id`
(src/routes.ts:105) accepts any `Id`. So:
```ts
const userIds = defineIds(["user-list"] as const);
const adminIds = defineIds(["admin-panel"] as const);
userRoutes.list({ target: adminIds.adminPanel })  // compiles — wrong target, no error
```

## Why it matters
The whole pitch of `defineIds` is "hx-target selectors always reference valid element
IDs." It guarantees the id *exists somewhere*, not that it exists *in the document
this swap targets*. In multi-feature SSR apps that's the realistic mixup, and it's
exactly the class of bug branded IDs are supposed to kill (cf. the CLAUDE.md
`UserId`/`PostId` rule).

## Rough idea (not a design)
Parametrize the brand: `Id<Tag = unknown>` with a phantom carried from the defining
registry (`IdRegistry` stamps a unique tag, or at minimum carries the names union).
This is a public-shape change to `Id`, so park for a major — but flag it now because
it's the headline branded-ID gap for Track D.
