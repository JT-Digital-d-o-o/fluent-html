# defineRoutes `params` map keys are unchecked against the path

## Problem
`RouteDef.params` is `Readonly<Record<string, ParamTypeName>>` — its keys are an
unconstrained `string`, not the set of `:param` names actually present in `path`.
So a typo'd or stale key is accepted and silently does nothing: the intended param
keeps the default `string` type, the bogus key contributes nothing.

## Evidence
```ts
// src/routes.ts:73
export type RouteDef = {
  readonly method: HxHttpMethod;
  readonly path: `/${string}`;
  readonly params?: Readonly<Record<string, ParamTypeName>>;   // keys NOT tied to path
};
```
Given `{ path: "/users/:id", params: { ic: "number" } }` (typo `ic` for `id`),
`ResolveParamTypes` (src/routes.ts:57) walks `ExtractParams<"/users/:id"> = "id"`,
finds `"id"` is *not* `keyof params`, and falls back to `string`. The `"ic"` entry
is dead. No diagnostic — the developer believes `id` is a `number` and it isn't.
`ExtractParams` (src/routes.ts:27) already computes the exact valid key set, so the
information needed to reject the bad key is on hand.

## Why it matters
This is the silent-failure flavor of a type hole: the feature (typed params) appears
to be in use but isn't, and the mistake survives refactors (rename `:id`→`:userId`
in the path, forget the `params` map → param silently re-widens to `string`).

## Rough idea (not a design)
Additive (6.1.0): make the params slot generic over the path so
`params?: Partial<Record<ExtractParams<Path>, ParamTypeName>>`. Excess/typo keys
become an object-literal excess-property error; renames surface immediately. Runtime
unchanged.
