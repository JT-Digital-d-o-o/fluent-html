# LLM guidelines teach an uppercase route method that fails to type-check

## Problem
The shipped route type accepts **lowercase HTTP methods only**:

```ts
// src/htmx.ts:10
export type HxHttpMethod = "get" | "post" | "put" | "patch" | "delete";

// src/routes.ts:74
export type RouteDef = {
  readonly method: HxHttpMethod;   // lowercase union
  readonly path: `/${string}`;
  ...
};
```

But the LLM-facing guidelines and the project `CLAUDE.md` `defineRoutes` examples use
**uppercase**:

```ts
// guidelines/web-development/CLAUDE.md:214-216
list:   { method: "GET",  path: "/" },
create: { method: "POST", path: "/" },
detail: { method: "GET",  path: "/:id", params: { id: "number" } as const },
// guidelines/web-development/fastify.md:140
method: "POST",
```

`{ method: "GET" } as const` is **not assignable** to `RouteDef` (`"GET"` is not in
`"get" | "post" | ...`). The canonical instruction set teaches a value that produces a
compile error, and an LLM following the guidelines will emit non-building code on the
very first `defineRoutes` it writes.

## Evidence
See the four citations above. The README and the `routes.ts` JSDoc correctly use
lowercase (16 lowercase / 0 uppercase in README), so the shipped code and its own docs
agree — the drift is isolated to the guidelines/CLAUDE.md surface, which is exactly the
surface that drives generated code.

## Why it matters
Every feature scaffolded from the guidelines defines routes; this is the first thing an
agent writes per feature, so the mis-teach has high blast radius. It is also a
guideline-sync guardrail violation: the LLM-facing docs disagree with the shipped
literal union.

## Rough idea (not a design)
6.0.1: lowercase the method literals in `guidelines/web-development/CLAUDE.md`,
`guidelines/web-development/fastify.md`, and the project `CLAUDE.md` to match
`HxHttpMethod`. Docs-only; the shipped type is correct and must not change (uppercasing
the union would be a breaking change and is the wrong direction).
