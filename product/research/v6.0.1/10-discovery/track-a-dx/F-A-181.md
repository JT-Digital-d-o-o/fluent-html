# context.test.ts exists but never runs in CI

## Problem
`test/context.test.ts` is a full, real test suite (19 cases across `createContext`
and `createRequiredContext`, including render integration). It is **not listed** in the
`npm test` (or `npm run test:coverage`) file enumeration, so it is never executed —
neither locally via `npm test` nor in CI/`prepack`. A shipped public surface
(`createContext`, `createRequiredContext`) has zero executed coverage.

## Evidence

```jsonc
// package.json:7 — the explicit, hand-maintained file list. context.test is absent.
"test": "npm run build && node --test dist/test/elements.test.js ... dist/test/define-theme.test.js"
```

```sh
$ grep -c "context.test" package.json
0
```

```ts
// test/context.test.ts:1 — a real suite that nothing invokes
import { describe, it } from "node:test";
...
describe("Context — createContext", () => { /* 13 it() */ });
describe("Context — createRequiredContext", () => { /* 6 it() */ });
```

The recon already noted four orphaned test files; `context.test.ts` is the one that
guards an actual shipped runtime behavior (the other three are styling demos/lint
fixtures). Because the script is an explicit allowlist rather than a glob, any
newly-added `*.test.ts` is silently excluded — the same trap will recur.

## Why it matters
The context system (see [[F-A-180]]) has subtle scope/dispose lifecycle behavior; its
only regression guard is dead. A future refactor of the stack/dispose logic would pass
CI with the context contract broken. Wiring it in is a one-line, zero-risk patch with
high leverage.

## Rough idea (not a design)
6.0.1: append `dist/test/context.test.js` to both the `test` and `test:coverage` script
lists. Separately worth considering switching the runner to a glob
(`node --test dist/test/**/*.test.js`) so orphaning can't recur — but that is a larger
change; the minimal patch is the one-file add.
