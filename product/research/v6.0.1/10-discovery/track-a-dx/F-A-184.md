# Streaming + context interaction is untested

## Problem
`renderToStream`/`renderToIterable` suspend the serializer generator across event-loop
turns. The library is *correct* here only because all control flow is eager and context
is read at **build time** — by the time the generator yields its first chunk, the Tag
tree is fully built and reads nothing from `context.ts`. That is a load-bearing
invariant, and it is **completely untested**: `test/stream.test.ts` has 64 cases (error
mid-stream, backpressure, nonce, chunking) but **none** combine a scoped context with a
streamed render.

This is the gap that makes the recon's "context is gone by the time the stream resumes"
smell *plausible*. It happens not to bite today (eager build), but nothing pins that. If
control flow ever became lazy (a deferred thunk evaluated during traversal), context
reads would move into the suspended generator and the global stack would already be
popped — silently rendering defaults. A regression test is the cheap guard.

## Why it matters
The single most-cited streaming concern in the recon (context lifetime across
suspend/resume) has no characterization test asserting the actual behavior. Pinning it
both documents the contract ("context is read at build time; streaming is safe because
the tree is built before the first chunk") and guards against a future laziness change
silently breaking it. Frequency is low today but pain is high if it regresses (silent
wrong output under streaming).

## Rough idea (not a design)
6.0.1: add a `stream.test.ts` case — `using _ = Ctx.scope("dark"); const out = [...renderToIterable(BoxThatReadsCtx())].join(""); assert(out.includes("bg-gray-900"))`
— plus a negative case proving that a context read *deferred* past the scope (if any
lazy path is ever introduced) is caught. Pure test addition; no public-shape change.
Also worth a one-line note in `web-development/fluent-html.md` that context is
build-time and therefore streaming-safe.
