# ForEachElse covers the empty *row*, but the dominant app pattern is the empty *container*

## Problem
`ForEachElse` (shipped in `src/control/iteration.ts:93`) returns the per-item views or a fallback **in the same slot**:

```ts
// src/control/iteration.ts:93-104
export function ForEachElse<T>(
  items: readonly T[],
  renderItem: (item: T, index: number) => View,
  emptyView: View | (() => View),
): View {
  if (items.length === 0) {
    return typeof emptyView === "function" ? (emptyView as () => View)() : emptyView;
  }
  ...
}
```

That shape only fits when the rows and the empty message live **inside the same parent** — e.g. `Ul(ForEachElse(users, u => Li(u.name), () => Li("None")))`. But the overwhelmingly common real shape is the opposite: a **whole container** (`<table>`, a card grid, a `<section>`) is rendered when the list is non-empty, and a **different sibling element** (a full empty state) replaces it entirely when the list is empty. `ForEachElse` cannot express that — you can't put a `<table>` in the "item" slot and a centered empty-state `<div>` in the "else" slot, because the item slot renders once per item.

So app authors fall back to two coordinated `IfThen`s on `.length`, which is verbose, repeats the predicate, and (critically) is **not exhaustive** — nothing stops both predicates from drifting out of sync:

```ts
// ttl/src/admin/views/projects-list.view.ts:157-161 (real app code)
IfThen(projects.length > 0, () =>
  ProjectsTable({ projects }),
),
IfThen(projects.length === 0, () =>
  EmptyState(),
),
```

## Evidence
`grep` for `IfThen(... .length === 0 | .length > 0 ...)` across the two reference apps (rideshare, ttl) returns **58 call sites**. The pattern is the canonical list-vs-emptystate branch: `browse.view.ts` alone has six (`events.length === 0`, `rides.length === 0`, `events.length > 0` ×3, …), and every admin table view pairs a `length > 0` table branch with a `length === 0` empty branch.

`ForEachElse` (`src/control/iteration.ts:93`) is the closest primitive, but it only branches at the **row** level — `items.length === 0` is checked to swap the *children*, never the container. There is no combinator that branches a whole subtree on emptiness while handing the non-empty array (typed as proven-non-empty) to the container arm.

## Why it matters
Frequency is high (58 sites in two apps; every list/table/grid view hits it) and the pain is real: the two-`IfThen` idiom duplicates the predicate, reads as two unrelated statements, and silently allows a both-true / both-false bug. This is a **control-flow primitive gap**, not a component gap — it sits exactly alongside `IfThenElse` and `ForEachElse` in `src/control/`. The output is the user's own container and the user's own empty state; the library only owns the branch.

## Pre-empting the instruction-set objection (guardrail #6)
This is **not** EmptyState (the cut visual helper). EmptyState was cut because it bakes in an icon + heading + message + styling opinion — pure user-land. The proposal here is the *control combinator* that the cut helper was being used to express: "render A from the proven-non-empty list, else render B." It ships zero markup, zero classes, zero visual opinion — same category as `IfThenElse`/`Match`/`ForEachElse`. The leverage is exhaustiveness (one predicate, two arms, can't drift) and narrowing the non-empty array, which a user cannot get from composing two `IfThen`s.

## Rough idea (not a design)
Add a two-arm list combinator in `src/control/iteration.ts`, e.g. `ListOr(items, (nonEmpty) => View, (/* empty */) => View)` — branches on `items.length`, passes the array (optionally a branded non-empty array) to the first arm and renders the second arm when empty. Additive → 6.1.0. Teach it in `views.md` as the replacement for the paired-`IfThen` idiom.
