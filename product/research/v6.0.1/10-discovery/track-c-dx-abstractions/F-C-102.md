# No keyed iteration — ForEach gives morph no stable identity for list reorder/insert/delete

## Problem
The whole HTMX story in this stack is built on morphing — `outerMorph`/`innerMorph` are the default swaps, sold as "preserves focus, scroll, animations." Idiomorph matches old and new nodes; when nodes carry stable `id`s it matches by id, otherwise it matches by **position**. `ForEach` (the list primitive, 149 call sites) emits children with no identity hook at all:

```ts
// src/control/iteration.ts:26
export function ForEach<T>(
  views: Iterable<T>,
  renderItem: (item: T, index: number) => View
): View;
```

There is no key/id parameter and no convention. So when a morph re-renders a reordered or filtered list, idiomorph falls back to positional matching: row identity, in-progress CSS transitions, and focus on a row's input can all be lost or mis-attributed to the wrong item.

## Evidence
`ForEach` is the dominant list tool (149 uses across ttl/rideshare/landing) and the swap vocabulary leads with morph:

```ts
// src/htmx.ts:31
  | 'innerMorph'     // Morph target's children
  | 'outerMorph'     // Morph target element itself
```

Nothing in `iteration.ts` ever calls `.setId(...)` or emits a `data-key`, and the renderItem callback only receives `(item, index)` — index being precisely the unstable key that defeats morph on reorder. To get stable morphing today a developer must remember, by hand, to `.setId(\`row-${item.id}\`)` on every list-item root — undocumented tribal knowledge, easily forgotten, and invisible until a reorder visibly glitches.

## Why it matters
High call-site frequency (149) intersecting the framework's headline feature (morph). The failure mode is subtle — lists *look* fine on first paint and only misbehave on reorder/insert/delete during a morph swap — so it ships silently. A keyed iterator turns "remember to id every row or your morphs are positional" into a typed, hard-to-forget primitive.

## Rough idea (not a design)
Additive (6.1.0). Either a dedicated `ForEachKeyed(items, keyOf, renderItem)` or a `ForEach` overload with a key extractor; it stamps each item's root tag with a stable id/`data-key` derived from `keyOf(item)` so idiomorph matches by key. Pure combinator, zero deps, no break to existing `ForEach`. Pairs with an htmx.md note on why morph needs keys.
