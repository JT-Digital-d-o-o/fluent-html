# No view-level When/Unless — IfThen(cond, () => …) thunk ceremony drives the 18:1 IfThen:Match gap and naked && leaks

## Problem
The only conditional-view primitives are `IfThen`/`IfThenElse`, and **both require a thunk** for the then-branch:

```ts
// src/control/conditionals.ts:57
export function IfThen(condition: boolean, then: Thunk<View>): View;
```

For the dominant case — "show this already-built view when a boolean is true," with no nullable value to narrow — the `() =>` is pure ceremony on all 228 `IfThen` call sites. There is no eager `When(cond, view)` and no `Unless(cond, view)` for the inverted case, so `Unless` is always spelled as `IfThen(!cond, () => …)` (double negation + thunk). There is also no positive-condition mirror of `whenElse`'s ergonomics at the view level. The result: developers either pay the thunk tax everywhere or quietly drop to naked `cond && View(...)` in children — which leaks `false`/`undefined` into the child list and sidesteps the escape-safe `Empty()` contract.

## Evidence
`IfThen` is used 228 times vs `Match` 11 times (≈18:1 in the surveyed apps) — the under-use of `Match` mirrors a broader pattern: the conditional surface is heavyweight, so the cheapest tool wins regardless of fit. `IfThenElse` (71 uses) is likewise thunk-only on both arms:

```ts
// src/control/conditionals.ts:23
export function IfThenElse(condition: boolean, thenBranch: Thunk<View>, elseBranch: Thunk<View>): View;
```

The control index exports exactly three conditionals — `IfThen`, `IfThenElse`, `Match` — with no `When`/`Unless`:

```ts
// src/control/index.ts:2
export { IfThen, IfThenElse, Match } from "./conditionals.js";
```

A thunk is genuinely needed only when the branch must be lazily evaluated to narrow a nullable (the `IfThen<T>(value, then)` overload). For the plain-boolean case the view is already constructed by the time the call is made, so the thunk buys nothing.

## Why it matters
228 call sites pay syntactic overhead for the most common conditional in the codebase, and the absence of an eager/Unless form is a standing invitation to naked `&&` — the one pattern the library's escape-by-default and `Empty()` contract exist to prevent. Closing this is the highest-leverage ergonomics win on the control-flow surface.

## Rough idea (not a design)
Additive (6.1.0). `When(cond: boolean, view: View): View` and `Unless(cond: boolean, view: View): View`, eager (View, not thunk), returning `Empty()` when skipped — for the no-narrow boolean case. Keep `IfThen`'s thunk overload as the narrowing path. Pure combinators, zero deps. Pairs with a views.md note steering people off naked `&&`.
