# Match has no value-mapping form — value→string/value lookups fall back to chained ternaries or switch

## Problem
`Match` only maps a discriminant to a **`View`**, and every case is a `Thunk<View>` — a function. The overwhelming real-world need is mapping a literal value to *another literal value* (a Tailwind class fragment, a label, an icon glyph). Today that is impossible without wrapping each value in a `() => ...` thunk and relying on the fact that `View` happens to include `string`. So app code abandons `Match` entirely and reaches for chained ternaries or `switch`.

The exhaustive overload signature forces thunks:

```ts
// src/control/conditionals.ts:118
export function Match<T extends string | number>(
  value: T,
  cases: { [K in T]: Thunk<View> }   // <- Thunk, never a plain value
): View;
```

## Evidence
Real apps map values with chained ternaries because `Match` can't return a non-View value ergonomically:

```ts
// ttl/src/shared/components/ui.components.ts:333
const bgColor = color === "green" ? "green-500" : color === "red" ? "red-500" : "accent";

// jtdigital-landing-page/src/admin/views/analytics-chart.ts:119
const yAxisLabel = scale === "linear" ? "Views" : scale === "log" ? "log₁₀(views)" : "ln(views)";
```

And where developers *do* try to use `Match` for a value, they smuggle a string through the View slot with a noise thunk per arm:

```ts
// rideshare/src/analytics/views/dashboard.view.ts:67
const trendArrow = Match(omtm.trend, { up: () => "↑", down: () => "↓" }, () => "→");
```

This relies on `View ⊇ string`; the `() =>` on each arm is pure ceremony, and the result is typed `View` (not `string`), so it can't feed a setter that wants a string (`.background(...)`, `.setTitle(...)`). 15 chained-value-ternary sites were found across ttl/rideshare/landing.

## Why it matters
Value→value mapping (status → badge color, size → width class, role → label) is one of the single most common UI chores. Because `Match` is View-only and thunk-only, none of it can be exhaustively checked — a chained ternary with a missed variant compiles silently, defeating the whole point of the discriminant-exhaustiveness `Match` was built to provide. This is a direct contributor to the 18:1 IfThen:Match adoption gap.

## Rough idea (not a design)
Additive (6.1.0). A value-returning sibling whose cases are *values* not thunks, exhaustive by default, returning the value's own type: `pick(status, { active: "green-500", error: "red-500" })` → `"green-500" | "red-500"`. Optional default makes it partial. No break to `Match`. Keeps the instruction-set spirit (a combinator, not a component) and gives exhaustiveness to the most common mapping in the codebase.
