# `.addAttribute("style", ...)` bypasses typed `.setStyle()` / `.setStyles()`

## Problem

`Tag` has two dedicated methods for inline CSS:

```ts
// fluent-html/src/core/tag.ts:125
setStyle(style?: string): this        // arbitrary string
setStyles(styles: Record<string, string | number>): this  // object, camelCase → kebab-case
```

Both are documented in `guidelines/web-development/fluent-html.md` line 40–41. Yet 14 call-sites across 2 apps reach for `addAttribute("style", ...)` instead:

```ts
// storysell-ai/src/brand/brand.identity.view.ts:146
Span("").addClass("w-4 h-4 rounded-md border border-slate-200 shrink-0")
  .addAttribute("style", "background:" + c.hex)

// storysell-ai/src/brand/brand.identity.view.ts:403
Div("").setDataAttrs({ biBar: "" })
  .addAttribute("style", `width:${completeness}%`)

// storysell-ai/src/shared/components/charts.components.ts:365
.addAttribute("style", `background-color: ${color}`)

// storysell-ai/src/shared/components/molecules/ui.molecules.progress.ts:96
.addAttribute("style", `height: ${percent}%`)

// storysell-ai/src/shared/components/molecules/ui.molecules.nav.ts:131
.addAttribute("style", `width: ${widthPercent}%; transform: translateX(${activeIndex * 100}%)`)

// storysell-ai/src/shared/components/brand/ui.brand.indicators.ts:72
.addAttribute("style", `width: ${clamped}%`)

// storysell-ai/src/product/views/product.list.view.ts:302
.position("relative").h("32").addAttribute("style", `background: ${gradient}`)

// jt-cut/src/analytics/views/users.view.ts:250
Div().h("2").rounded("full").background("primary")
  .addAttribute("style", `width: ${pct}%`)
```

The correct typed equivalents:

```ts
// ✓ setStyle — for simple string
.setStyle(`background: ${c.hex}`)

// ✓ setStyles — for object (camelCase → kebab-case)
.setStyles({ width: `${completeness}%` })
.setStyles({ backgroundColor: color, width: `${pct}%` })
```

`addAttribute("style", ...)` achieves the same result and is not wrong in practice, but it:
1. Loses the `setStyles` camelCase-to-kebab convenience
2. Conflicts with any `setStyle/setStyles` call on the same element (they write to `this.style`, while `addAttribute` writes to `this.attributes["style"]` — rendering both)
3. Is inconsistent with the library's "typed methods over addAttribute" principle

## Why it matters

14 call-sites is a narrow footprint (2 apps, mostly in one codebase), but the pattern indicates that `.setStyle()` is not top-of-mind for dynamic CSS values. Developers reach for `addAttribute` because it feels like the escape hatch when the style is computed. The guideline shows `.setStyle("color: red")` as a static example only — there's no example with a template literal or variable, which is the dynamic-style use case that actually triggers the escape hatch.

## Rough idea (not a design)

Guidelines-only fix. Extend the `.setStyle` entry in `fluent-html.md` with a dynamic example:

```typescript
// ✓ typed inline style — works with dynamic values
Div().setStyle(`width: ${pct}%`)
Div().setStyles({ backgroundColor: color, width: `${width}px` })

// ✗ addAttribute("style") — conflicts with setStyle and loses camelCase conversion
Div().addAttribute("style", `background-color: ${color}`)
```
