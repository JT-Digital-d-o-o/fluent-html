# `setAria()` adoption gap — apps still use `addAttribute("aria-*", ...)` despite the typed helper existing

## Problem

`Tag.setAria()` exists and is well-adopted in planet-positive-sport (~30 call sites), glimm, rideshare (1 site), fivb, cms, and filmplast-v2. But in rideshare and jt-draw, `addAttribute("aria-*", ...)` is still used for individual aria attributes — even in files that have other fluent methods nearby. The guideline teaches `setAria` in a single-line example but never says "never use `addAttribute` for aria attributes."

```typescript
// rideshare/src/shared/components/layout.view.ts:463-465
Div(...)
  .addAttribute("role", "dialog")
  .addAttribute("aria-modal", "true")   // ✗ should be .setAria({ modal: "true" })
  .addAttribute("aria-label", "Navigation menu")  // ✗ should be .setAria({ label: "Navigation menu" })
```

```typescript
// rideshare/src/shared/components/layout.view.ts:544-545
Button(...)
  .addAttribute("aria-label", "Toggle menu")   // ✗ .setAria({ label: "Toggle menu" })
  .addAttribute("aria-expanded", "false")      // ✗ .setAria({ expanded: "false" })
```

```typescript
// jt-draw/src/auth/auth.components.ts:93
Span(...).addAttribute("aria-hidden", "true");  // ✗ .setAria({ hidden: "true" })

// jt-draw/src/home/views/landing.pricing.view.ts:188
Button(...).addAttribute("aria-pressed", "false")  // ✗ .setAria({ pressed: "false" })
```

## Evidence

The offending guideline text (`guidelines/web-development/fluent-html.md:42`):
```
  .addAttribute("data-x", "val")   // custom attributes only
  .setDataAttrs({ userId: "123" }) // data-user-id="123" (auto kebab-case)
  .setAria({ label: "Close" })     // aria-label="Close"
```

The `// custom attributes only` comment on line 42 implies `addAttribute` is for non-standard attributes, but does not explicitly say "not for aria-*" — aria attributes look like custom attributes (they have a prefix) to developers unfamiliar with the fluent API.

In contrast, the `setAria` example is a single-line mention without any ✗ anti-pattern. The guideline also does not mention that passing multiple aria attrs in one `setAria({})` call (batch object) is preferred over multiple `addAttribute` calls.

## Why it matters

- 9 `addAttribute("aria-*")` calls remain in 2 apps that otherwise follow fluent conventions.
- `setAria` provides the camelCase→kebab-case conversion and groups all aria attrs in one call; `addAttribute` is purely raw string, no conversion, no grouping, higher cognitive load.
- Each `addAttribute("aria-*")` call is a missed opportunity to validate the key (though current `setAria` itself doesn't type-check keys — see F-A-053).
- The fix is a guideline edit, not a code change.

## Rough idea

In `guidelines/web-development/fluent-html.md`, under the "Universal methods" block, add an explicit ✗ anti-pattern for aria and data attributes:

```typescript
// ✗ never addAttribute for aria or data-* attributes
.addAttribute("aria-label", "Close")  // ✗
.addAttribute("data-user-id", "123")  // ✗

// ✓ use the typed helpers
.setAria({ label: "Close", expanded: "false" })
.setDataAttrs({ userId: "123" })
```
