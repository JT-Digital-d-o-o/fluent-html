# `hxGet(route.resolve({params}))` bypasses the typed HTMX route object

## Problem

`defineRoutes` routes are callable: `route({ param: value })` returns a typed `HTMX` object that carries the method, path, and options in a fully-typed bundle. `setHtmx(route({...}))` uses this object directly.

`hxGet(endpoint: string)` and `hxPost(endpoint: string)` accept only a **string** URL. When apps need to call a parameterized route, they use `route.resolve({...})` to get the URL string, then pass it to `hxGet` / `hxPost`:

```ts
// rideshare/src/rides/views/browse.view.ts:122
.hxGet(
  rideRoutes.browse.resolve({ event: event.id }),
  { target: layoutIds.page, swap: "outerMorph scroll:top", replaceUrl: true }
)

// rideshare/src/rides/rides.components.ts:246
.hxPost(
  reservationRoutes.createSubmit.resolve({ rideId: ride.id }),
  { target: layoutIds.page, swap: "outerMorph" }
)

// ttl/src/settings/settings.view.ts:388
.hxGet(settingsRoutes.page.path, {
  target: settingsIds.settingsContent,
  swap: "outerMorph",
})
```

The typed equivalent would be:

```ts
// ✓ fully typed — method is part of the route definition
.setHtmx(rideRoutes.browse({ event: event.id }, { target: layoutIds.page, swap: "outerMorph scroll:top", replaceUrl: true }))
.setHtmx(reservationRoutes.createSubmit({ rideId: ride.id }, { target: layoutIds.page, swap: "outerMorph" }))
.setHtmx(settingsRoutes.page({ target: settingsIds.settingsContent, swap: "outerMorph" }))
```

The `hxGet(route.resolve({...}))` pattern is valid TypeScript — `route.resolve()` still validates param types — but it decouples the HTTP method from the route definition. If the route definition changes method (e.g. from GET to POST), the `setHtmx(route(...))` form catches it; the `hxGet(route.resolve(...))` form silently sends the wrong method.

## Evidence

41 callsites across at least 3 projects:

```ts

  { target: layoutIds.page, swap: "outerMorph scroll:top", replaceUrl: true, include: "[name='time']" }

// rideshare/src/reservations/reservations.view.ts:105

// rideshare/src/admin/rides/views/admin-rides.view.ts:56

```

## Root cause: guideline is ambiguous

`guidelines/web-development/htmx.md:83-94` defines the split as "simple requests → hxGet, complex → setHtmx(hx())":

```
## Shorthand vs setHtmx
**Shorthand methods** for simple requests, **setHtmx(hx())** for complex:
Button("Load").hxGet("/api/items")
Button("Save").hxPost("/api/save", { target: ids.result })
Form(/* fields */).setHtmx(hx("/search", { method: "post", ... }))
```

The guideline illustrates `hxGet` with hardcoded strings only. It never shows what to do for parameterized routes — the gap between "simple" and "complex" — so apps fill it with `hxGet(route.resolve({...}))`. That looks like the typed-route pattern but isn't: it collapses the route call to a plain string at the point of use.

## Why it matters

`defineRoutes` is the library's typed-route system. Its primary value is **method safety** — the HTTP method lives in the route definition, not scattered across call sites. Using `hxGet(route.resolve({...}))` re-scatters the method, defeating that guarantee. 41 callsites currently carry this silent coupling fragility. The fix is a guideline addition, not a code change.

## Rough idea (not a design)

Add to `htmx.md` under "Shorthand vs setHtmx":

```
// ✗ DON'T — method is now implicit; route method changes won't be caught
.hxGet(rideRoutes.browse.resolve({ event: id }), { target: ids.page })

// ✓ DO — method stays with the route definition
.setHtmx(rideRoutes.browse({ event: id }, { target: ids.page }))
```

Rule: **`hxGet`/`hxPost` are for literal string endpoints only.** Once `defineRoutes` is in play, always use `setHtmx(route({...}))`.
