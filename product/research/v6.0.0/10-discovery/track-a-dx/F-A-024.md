# createContext adoption gap — auth/user prop-drilled through 5+ layers

## Problem

`createContext` / `createRequiredContext` are documented as the solution to prop drilling for cross-cutting values. The guidelines explicitly list auth as the primary use case: _"use for cross-cutting values (theme, auth, locale, nonce) instead of prop drilling."_ Yet in production apps — rideshare, ttl — auth user is prop-drilled through every layer of the layout.

## Evidence

`rideshare/src/shared/components/layout.view.ts` passes `user: AuthUser` as a prop through four nested component levels:

```ts
// rideshare/src/shared/components/layout.view.ts:65
type LayoutProps = {
  user?: AuthUser | null;
  // ...
};

// layout.view.ts:78 → Layout calls Sidebar
function Layout({ title, children, user, … }: LayoutProps) {
  // ...
  Sidebar({ user: user!, navCounts, activePage }),   // line 127
  MobileSidebarOverlay({ user: user!, … })           // line 152
}

// layout.view.ts:399-404 → SidebarProps duplicates user
type SidebarProps = { user: AuthUser; … };
function Sidebar({ user, navCounts, activePage }: SidebarProps) {   // line 404
  SidebarNavSections({ user, navCounts, activePage }),              // line 421
  SidebarFooter({ user }),                                          // line 424
}

// layout.view.ts:374 → yet another level
function SidebarNavSections({ user, navCounts, activePage }: { user: AuthUser; … }) {
  const isAdmin = user.role === "ADMIN";   // the actual consumer
}

// layout.view.ts:313 → leaf consumer
function SidebarFooter({ user }: { user: AuthUser }) {
  Avatar({ user, size: "sm" }),
  Div(user.name ?? "User"),
}
```

The chain is: `Layout → Sidebar → SidebarNavSections → SidebarFooter` — four levels deep. `createRequiredContext<AuthUser>("AuthCtx")` set once in the request handler would let all four consumers call `AuthCtx.current` with zero prop threading.

The same pattern appears in ttl/src/shared/components/layout.view.ts, and in the rideshare admin dashboard which re-threads `user` through its own component chain.

The guideline's own example uses `ThemeCtx` — a colour theme — which is too abstract. Developers copy the pattern but don't realize it applies to auth. The missing piece is a concrete example showing:
1. context defined at module level
2. scope set in the Fastify handler (where `request.user` lives)
3. leaf components reading it without any prop

## Why it matters

3+ production apps affected. Adding `user` to every intermediate component type is noise: it couples layout component signatures to the auth type, makes adding new layout sections require threading a new prop, and is exactly the friction `createRequiredContext` was built to remove. Since none of the apps use this for auth, the API exists but the teaching gap prevents adoption.

## Rough idea (not a design)

Replace the current abstract `ThemeCtx`/`LocaleCtx` guideline example with a concrete auth example in the `fluent-html.md` "Scoped Context" section:

```ts
// ✓ auth context — defined once, consumed anywhere
const AuthCtx = createRequiredContext<AuthUser>("AuthCtx");

// In the Fastify preHandler or handler:
using _ = AuthCtx.scope(request.user);
return reply.renderView(Layout({ title, children }));

// In Layout (no user prop needed):
function Layout({ title, children }) { … }
function Sidebar() { … }  // no user prop

// In the leaf component:
function SidebarFooter() {
  const user = AuthCtx.current;  // directly available
  return Div(user.name);
}
```

Add a ✗ counterexample showing the prop-drilling chain.
