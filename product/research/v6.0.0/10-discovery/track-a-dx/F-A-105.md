# `IfThen(!!x, () => Component(x!))` bypasses the narrowing callback — 14 call-sites

## Problem

`IfThen(value, (v) => ...)` is specifically designed to narrow `value`'s type in the callback parameter: if `value` is `string | null | undefined`, then `v` inside the callback is `string`. The whole point is that the consumer never needs a non-null assertion.

However, 14 call-sites across 6+ apps wrap the condition in `!!` (boolean coercion), which converts the value from `string | null | undefined` to `boolean` before `IfThen` sees it. At that point the original nullable value is gone, so inside the callback the developer must use `x!` (non-null assertion) to recover the value — exactly the cast `IfThen` was meant to prevent.

`guidelines/web-development/CLAUDE.md` teaches the ✓ form (`IfThen(user.avatar, (avatar) => Img().setSrc(avatar))`) and even shows the ✗ form (`IfThen(user.avatar, () => Img().setSrc(user.avatar!)) // ✗ don't re-check/cast`). But the ✗ rule only covers the missing-parameter variant. It does not mention the `!!x` double-negation variant, which is a distinct (and more common) error pattern: developers think `!!x` makes the truthiness check more explicit, not realising it destroys the type information.

## Evidence

```ts
// jtdigital-landing-page/src/shared/seo.ts:293-294
IfThen(!!props.canonical, () => Canonical(props.canonical!)),
IfThen(!!props.structuredData, () => StructuredData(props.structuredData!)),
```

```ts
// website-sales-funnel-automation-system/src/admin/jobs/views/jobs.view.ts:102-103
IfThen(!!props.success, () => Alert({ message: props.success!, type: "success" })),
IfThen(!!props.error, () => Alert({ message: props.error! })),
```

```ts
// buzzin/src/views/quiz/sponsor-exposition.view.ts:203
IfThen(!!sponsorBannerUrl, () => SponsorBanner(sponsorBannerUrl!))
```

```ts
// pregled-nepremicnin-dashboard/src/views/admin/pricing.view.ts:148
IfThen(data.quote != null, () => QuoteResultCard(data.quote!))
// ← `!= null` variant: same effect — truthy check outside IfThen, ! inside callback
```

The correct forms:

```ts
// ✓ narrowing callback — no !! and no !
IfThen(props.canonical, (url) => Canonical(url)),
IfThen(props.structuredData, (data) => StructuredData(data)),
IfThen(props.success, (msg) => Alert({ message: msg, type: "success" })),
IfThen(sponsorBannerUrl, (url) => SponsorBanner(url))
IfThen(data.quote, (quote) => QuoteResultCard(quote))
```

Variants observed:
- `IfThen(!!x, () => C(x!))` — double negation + non-null assertion (12 of 14 instances)
- `IfThen(x != null, () => C(x!))` — explicit null-check + non-null assertion (2 of 14 instances)

Both variants share the same root cause: the truthy guard is evaluated outside `IfThen`, converting to `boolean`, so the narrowed type is lost inside the callback.

## Why it matters

The `!` non-null assertion is a runtime trust assertion — TypeScript will not warn if `x` is somehow falsy in an async context or after a refactor changes the type. The `IfThen` narrowing callback eliminates this footgun entirely by making the narrowed value the callback argument. The `!!x` pattern actively defeats the type safety `IfThen` provides, while appearing to be equivalent, making it a subtle but widespread correctness risk.

14 instances across 6+ apps shows the existing ✗ rule is insufficient — it guards against one variant of the anti-pattern but leaves the more common `!!x` variant undocumented.

## Rough idea (not a design)

Extend the existing ✗ list in `CLAUDE.md` under the `IfThen narrows nullable values` heading:

```ts
IfThen(user.avatar, (avatar) => Img().setSrc(avatar))           // ✓ avatar: string
IfThen(user.avatar, () => Img().setSrc(user.avatar!))            // ✗ don't re-check/cast
IfThen(!!user.avatar, () => Img().setSrc(user.avatar!))          // ✗ !! destroys the type; forces !
IfThen(user.avatar != null, () => Img().setSrc(user.avatar!))    // ✗ same problem via != null
```

This is a two-line addition to an existing block — zero cost, direct benefit.
