# `hxGet`/`hxPost`/`hxPut`/`hxPatch`/`hxDelete` break the `set*` naming convention

## Problem

Every method on `Tag` that configures an attribute uses the `set*` prefix:

| Method | Sets |
|---|---|
| `setId()` | `id` attribute |
| `setClass()` | `class` attribute |
| `setStyle()` | `style` attribute |
| `setNonce()` | nonce on script/style |
| `setHtmx()` | HTMX configuration |
| `toggle()` | boolean attributes |
| `addClass()` | appends to class |
| `addAttribute()` | arbitrary attributes |

Then there are five shorthand methods that break this pattern:

```ts
// fluent-html/src/core/htmx-methods.ts:18-22
hxGet(endpoint: string, options?: Omit<HxOptions, "method">): this;
hxPost(endpoint: string, options?: Omit<HxOptions, "method">): this;
hxPut(endpoint: string, options?: Omit<HxOptions, "method">): this;
hxPatch(endpoint: string, options?: Omit<HxOptions, "method">): this;
hxDelete(endpoint: string, options?: Omit<HxOptions, "method">): this;
```

These are `hx*`-prefixed — not `set*` — and they do exactly what `setHtmx()` does, just with an implicit method baked in. Functionally: `Button().hxGet("/api")` ≡ `Button().setHtmx("/api", { method: "get" })`.

## Evidence

The implementation confirms these are thin wrappers over `setHtmx`'s internal logic:

```ts
// fluent-html/src/core/htmx-methods.ts:37-40
p.hxGet = function (endpoint: string, options?: Omit<HxOptions, "method">) {
  this.htmx = hx(endpoint, { ...options, method: "get" });
  return this;
};
```

Usage in apps: 109 `hxGet` + 41 `hxPost` calls — a combined 150 callsites. These are on `Tag.prototype`, side-by-side with `setId`, `setClass`, `setStyle`, and `setHtmx`.

The resulting mental model has two naming zones with no documented rule for which zone a new method belongs to:
- `set*` — for everything that sets an attribute or property
- `hx*` — for five specific HTMX-method shortcuts

A new contributor adding a `DELETE` shorthand would be uncertain: `hxDelete` (existing pattern) or `setHxDelete` (set* pattern)?

## Why it matters

The inconsistency is low pain in isolation — the methods work correctly and the names are readable. The cost is cognitive: the `set*` prefix is a reliable namespace signal throughout the library. These five methods punch a hole in it. The hole matters more when introducing new contributors, when autocomplete surfaces methods, and when the guidelines section "Shorthand vs setHtmx" fails to explain the naming rationale (it only says when to use which, not why they're named differently).

Secondary issue: the `htmx.md` guideline frames this as "simple requests → hxGet, complex → setHtmx" but provides no guidance for the common mixed case: a request that is GET/POST but also has typed route params (see F-A-074).

## Rough idea (not a design)

Two options:
1. **Rename to `set*`** (breaking): `hxGet → setHxGet`, `hxPost → setHxPost`, etc. Uniform, but a breaking change and longer names.
2. **Formalize the two-zone rule** (non-breaking): document in `fluent-html.md` that `hx*` is the HTMX verb-shorthand namespace distinct from the attribute-setter `set*` namespace; add a note in the `htmx.md` section on the design intent. No code change.

Option 2 resolves the confusion without a break and is the minimal path.
