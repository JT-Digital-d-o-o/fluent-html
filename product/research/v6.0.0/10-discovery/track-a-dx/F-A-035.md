# Auth user prop-drilled through view trees in 3 apps (102 call sites) instead of using createRequiredContext

## Problem

The guidelines identify auth/user as the canonical use case for `createRequiredContext` ("use for auth, request data"), yet three apps — rideshare, mngmt, and ttl — thread `user: AuthUser` as an explicit prop through every view, layout, and sub-component:

```ts
// ttl/src/shared/components/layout.view.ts:42-45
type LayoutProps = {
  title: string;
  description?: string;
  children: View;
  user?: AuthUser | null;   // ← threaded through layout
  activePage?: ActivePage;
};
```

```ts
// mngmt/src/dashboard/views/epic-detail.view.ts:63
user: props.user,   // ← passed down through intermediate view
```

```ts
// ttl/src/time-entry/views/time-entry.view.ts:28
user: AuthUser;   // ← repeated in every view's Props type
```

## Evidence

Measured call-site counts (grep `user: request\.user\|user: request\.user!`):

| App | Prop-drilling sites |
|-----|-------------------|
| rideshare | 59 |
| mngmt | 27 |
| ttl | 16 |
| **Total** | **102** |

In contrast, `planet-positive-sport` — the most mature app — uses `createContext<AuthUser | null>(null)` in `src/auth/current-user.context.ts` and exposes `useCurrentUser()`:

```ts
// planet-positive-sport/src/auth/current-user.context.ts
const CurrentUserCtx = createContext<AuthUser | null>(null);
export const provideCurrentUser = (user: AuthUser | null): Disposable =>
  CurrentUserCtx.scope(user);
export const useCurrentUser = (): AuthUser | null => CurrentUserCtx.current;
```

Layout components in planet-positive-sport read `useCurrentUser()` directly with zero prop threading.

## Why it matters

102 call sites that could be eliminated. Prop-drilling `user` means:
- Every intermediate view must declare and forward the prop even if it never uses it
- Adding a new layout-level consumer of the user (e.g. a debug panel) requires threading through every ancestor
- The `user: null` vs `user: AuthUser` ambiguity is re-encoded in every Props type

The fix exists in the library and is demonstrated in one app. The other three apps don't use it because `fastify.md` shows how to populate `request.user` but never says "here's how to make it available to views without prop-drilling."

## Guideline gap

`guidelines/web-development/fastify.md` section "Auth Guards" explains `request.user` but stops there. It never connects `request.user` to `createRequiredContext` or shows the provider/consumer pattern. The fluent-html.md context example uses a generic `User` type without any Fastify glue.

## Rough idea (not a design)

Guideline-only fix: add a "Providing auth to views" pattern to `fastify.md`:

```ts
// ✓ Scope in renderView so components can read user without prop drilling
const AuthCtx = createRequiredContext<AuthUser>("AuthCtx");

server.decorateReply("renderView", function (...views: View[]) {
  using _ = AuthCtx.scope(this.request.user!);
  this.type("text/html").send(render(...views));
});

// In any view — no prop needed:
function UserAvatar() {
  const user = AuthCtx.current;
  return Img().setSrc(user.avatarUrl).setAlt(user.name);
}
```
