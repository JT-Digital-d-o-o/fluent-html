# README legitimises `.addClass("hover:bg-red-600")` as "Traditional Tailwind" — contradicts the `.on()` rule

## Problem

`CLAUDE.md` line 112 is unambiguous:

> **Fluent methods** — not `setClass` with Tailwind strings. **`.on()` for pseudo-classes, `.at()` for breakpoints** — **not** `addClass`.

`guidelines/web-development/fluent-html.md` (line 105) echoes this:

> Use fluent methods (not `setClass`) … `.on()` for pseudo-classes, `.at()` for breakpoints.

Yet the README "Mixing APIs" section (around line 1108) presents `addClass` with a raw variant-prefixed class as equally valid:

```ts
// fluent-html/README.md:1108–1111
Div()
  .padding("4")                  // Fluent API
  .background("red-500")         // Fluent API
  .addClass("hover:bg-red-600")  // Traditional Tailwind   ← shown as valid
  .setClass("custom-class");     // Replace all classes
```

The comment `// Traditional Tailwind` frames `addClass("hover:bg-red-600")` as an acceptable alternative style — not as an escape hatch to avoid. A developer (or LLM) reading this section reasonably concludes that both approaches are idiomatic and interchangeable.

A second site appears in the README at line 1252:

```ts
// fluent-html/README.md:1252
.addClass("hover:shadow-xl")
```

Again with no ✗ marker or "avoid this" note.

## Evidence

Source of the rule (`CLAUDE.md:112`):

```
**Fluent methods** — not `setClass` with Tailwind strings (fluent methods provide type safety + IDE autocomplete).
**`.on()` for pseudo-classes, `.at()` for breakpoints** — not `addClass`:
```

The contradicting README snippet (`README.md:1108`):

```ts
Div()
  .padding("4")
  .background("red-500")
  .addClass("hover:bg-red-600")  // Traditional Tailwind
  .setClass("custom-class");
```

The fluent-html.md guideline has it right at line 117–120:

```ts
  .transition("colors")
  .on("hover", t => t.background("blue-600").scale("105"))
  .on("focus", t => t.ring("2").ringColor("blue-300").outline("none"))
```

The README and the guidelines are in direct conflict on the same topic. Since the README is the longer and more detailed document, developers often treat it as more authoritative.

## Why it matters

The LLM agent (Claude Code) reads `CLAUDE.md` as the high-priority rule source, but also reads the project's README.md in context when generating code. When the README presents `addClass("hover:...")` as "Traditional Tailwind" without a ✗ marker, the LLM can reasonably generate that pattern in app code — bypassing type safety and IDE autocomplete on variants. This finding is distinct from F-A-084 (which is about the `.apply()` JSDoc) because it is about **variant-prefixed strings in `addClass`** specifically, which is the most common form of guideline violation in apps.

## Rough idea (not a design)

Replace the "Mixing APIs" example in the README with a ✗/✓ pair:

```typescript
// ✗ Traditional Tailwind — avoid in fluent-html; loses type safety on variants:
Div().addClass("hover:bg-red-600")

// ✓ Fluent variant — typed, autocompleted, extractable:
Div().on("hover", t => t.background("red-600"))
```

And change the README line 1252 from a bare `addClass` call to `.on("hover", ...)`. No library code changes needed.
