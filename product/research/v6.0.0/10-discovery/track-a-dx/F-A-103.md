# TypeScript discriminated-union prop types rendered without `Match` — per-branch narrowing lost

## Problem

Multiple apps define component props as TypeScript discriminated unions — the idiomatic pattern for multi-state components — but then render them with extracted boolean flags and ternary chains instead of `Match(props, discriminantKey, {...})`. The discriminated-union overload of `Match` exists precisely to provide per-branch type narrowing; when bypassed, accessing variant-specific fields requires manual type casts or double-narrowing.

The `guidelines/web-development/fluent-html.md` and `CLAUDE.md` teach `Match` with discriminated unions (CLAUDE.md line 153), but only with free values like `Match(state, "status", {...})`. Neither file shows the pattern where the entire component **props argument** is itself a discriminated union and the top-level `Match` should be the first statement in the render function.

## Evidence

`test/aaa/src/auth/views/auth.verify-email.view.ts` (mirrored in `glimm`, `ttl`):

```ts
// test/aaa/src/auth/views/auth.verify-email.view.ts:58
type VerifyEmailResultPageProps =
  | { state: "success" }
  | { state: "error"; message: string };

export function VerifyEmailResultPage(props: VerifyEmailResultPageProps) {
  const isSuccess = props.state === "success";   // ← boolean flag loses the union

  return Layout({ title: isSuccess ? "Email Verified" : "Verification Failed", children:
    CenteredPage({ content:
      AuthCard({
        title: isSuccess ? "Email verified" : "Verification failed",
        subtitle: isSuccess
          ? "Your email has been verified successfully"
          : props.message,  // ← safe only because TS can narrow ternary else-branch
        content: Div(
          IfThenElse(
            isSuccess,
            () => PrimaryBlockLink({ label: "Continue to app" })…,
            () => PrimaryBlockLink({ label: "Back to login" })…,
          ),
        ),
      }),
    })
  });
}
```

`ttl/src/auth/auth.view.ts:218` — same pattern for a 3-variant DU:

```ts
// ttl/src/auth/auth.view.ts:218
type ForgotPasswordPageProps =
  | { state: "idle" }
  | { state: "error"; message: string }
  | { state: "success"; message: string };

function ForgotPasswordForm(props: ForgotPasswordPageProps = { state: "idle" }) {
  return Div(
    IfThen(props.state !== "idle" ? props.message : null, (msg) =>
      Alert({ message: msg, type: props.state === "success" ? "success" : "danger" })
    ),
    ...
  );
}
```

Here `props.state === "success" ? "success" : "danger"` inside the `IfThen` callback has to re-check `props.state` because the original `props` type was not narrowed. With `Match` the variant-specific `message` field would be automatically available.

The correct pattern:

```ts
// ✓ Match on the entire prop value — per-branch narrowing
function VerifyEmailResultPage(props: VerifyEmailResultPageProps) {
  return Layout({ title: "Email Verification", children:
    CenteredPage({ content:
      Match(props, "state", {
        success: () => AuthCard({ title: "Verified", subtitle: "Your email has been verified successfully",
          content: PrimaryBlockLink({ label: "Continue" })… }),
        error: (s) => AuthCard({ title: "Failed", subtitle: s.message,  // s: { state:"error"; message: string }
          content: PrimaryBlockLink({ label: "Back to login" })… }),
      }),
    })
  });
}
```

The 8 instances found span `test/aaa`, `glimm`, and `ttl` — all three use the same template pattern with DU props but none apply `Match` at the component top-level.

## Why it matters

Beyond the minor verbosity cost, the manual approach has two concrete defects:

1. **Variant-specific fields require re-narrowing.** `s.message` is only accessible after a second `props.state === "error"` check inside each ternary branch. With `Match`, the branch callback receives `s` already narrowed to the correct variant, eliminating the re-check.

2. **Adding a new variant is non-exhaustive.** A new `| { state: "loading" }` variant is silently ignored by the boolean flag pattern; `Match` would cause a compile error at every call site if the `"loading"` case is missing (when using the non-default overload).

The guideline fix is a single ✓/✗ example added to `fluent-html.md`; no code change is needed.

## Rough idea (not a design)

Add to `guidelines/web-development/fluent-html.md` under the `Match` section:

```ts
// ✗ boolean flag — variant-specific fields need re-narrowing; non-exhaustive on new variants
type Props = { state: "success" } | { state: "error"; message: string };
function Page(props: Props) {
  const isSuccess = props.state === "success";
  return Div(
    P(isSuccess ? "Done" : props.message),       // ← re-narrow ternary
    IfThenElse(isSuccess, () => Button("OK"), () => Button("Retry")),
  );
}

// ✓ Match on props — per-branch narrowing, exhaustive
function Page(props: Props) {
  return Match(props, "state", {
    success: ()  => Div(P("Done"), Button("OK")),
    error:   (s) => Div(P(s.message), Button("Retry")),  // s typed as error variant
  });
}
```
