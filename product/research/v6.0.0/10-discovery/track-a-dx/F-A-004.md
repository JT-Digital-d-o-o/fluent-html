# ESLint `prefer-set-method` misses `data-*` and `aria-*` attributes; 396 call-sites use `addAttribute` instead of `setDataAttrs`/`setAria`

## Problem

`Tag` has two ergonomic bulk-setter methods for the most common `addAttribute` use-cases:

- `setDataAttrs(attrs: Record<string, string>)` — sets all `data-*` attributes from an object, converting camelCase keys to kebab-case automatically (`tag.ts:275`).
- `setAria(attrs: Record<string, string | boolean>)` — sets all `aria-*` attributes from an object (`tag.ts:298`).

These methods are typed, concise, and kebab-convert keys automatically. Yet the ESLint `prefer-set-method` rule has **zero entries for `data-*` or `aria-*` prefixes** (`prefer-set-method.ts` maps only exact attribute names, not prefix patterns). The result: 396 `addAttribute("data-*", ...)` call-sites and 45 `addAttribute("aria-*", ...)` call-sites across 14+ apps go un-flagged and uncorrected.

## Evidence

**`setDataAttrs` and `setAria` exist and are documented** (`fluent-html/src/core/tag.ts:275,298`):

```ts
// tag.ts:275
setDataAttrs(attrs: Record<string, string>): this { ... }

// tag.ts:298
setAria(attrs: Record<string, string | boolean>): this { ... }
```

**`prefer-set-method` covers only exact attribute names** — no prefix matching logic. `data-testid`, `data-user-id`, `aria-label`, `aria-expanded` are all invisible to the rule.

**351 `addAttribute("data-*")` call-sites in apps** (sample):

```ts
// gzs/inovacije/src/views/auth/auth.view.ts:82
.addAttribute("required", "true")

// tela/src/views/editor/panels/attributes-panel.ts (multiple data- usages)
.addAttribute("data-element-id", elem.id)
.addAttribute("data-panel", "attributes")

// buzzin/src/views/components/forms.ts
.addAttribute("data-controller", "form")
.addAttribute("data-action", "submit->form#handle")
```

**45 `addAttribute("aria-*")` call-sites**, e.g.:

```ts
Button("Menu").addAttribute("aria-expanded", "false").addAttribute("aria-controls", "nav")
// vs. idiomatic:
Button("Menu").setAria({ expanded: "false", controls: "nav" })
```

**`setAria` used only 55 times** (ratio: 45 `addAttribute` vs 55 `setAria` — roughly 1:1 instead of the idiomatic near-zero for `addAttribute`).

**`setDataAttrs` used 115 times** (ratio: 351 `addAttribute` vs 115 `setDataAttrs` — 3:1 against the idiomatic path).

The guidelines (`web-development/fluent-html.md:43`) list `.setDataAttrs()` and `.setAria()` as universal methods, but without ESLint enforcement, the escape hatch (`addAttribute`) is the path of least resistance.

## Why it matters

`addAttribute` requires writing the full `data-` / `aria-` prefix manually (error-prone for complex kebab keys like `data-hx-on-click`), bypasses kebab-conversion, and accepts any string key without validation. `setDataAttrs`/`setAria` are safer and more concise. 396 sites using the escape hatch when the idiomatic API exists is a direct guideline-adoption failure caused by missing tooling.

## Rough idea (not a design)

Add prefix-match cases to `prefer-set-method` (or create separate rules `prefer-data-attrs` / `prefer-aria-attrs`). For single-attribute calls, suggest the individual `setDataAttrs`/`setAria` with a one-key object. For clusters of consecutive `addAttribute("data-*")` calls on the same tag, offer a multi-key object fix. The auto-fixer can concatenate consecutive calls into a single `setDataAttrs({...})` invocation.
