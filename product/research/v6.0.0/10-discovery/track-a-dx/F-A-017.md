# `setAria()` and `setDataAttrs()` exist but 30+ app call-sites use `addAttribute('aria-*')` / `addAttribute('data-*')` instead

## Problem

The library provides two bulk typed setters for the two most common non-standard attribute patterns:

```ts
// fluent-html/src/core/tag.ts:275
setDataAttrs(attrs: Record<string, string>): this  // data-user-id="123" (auto kebab-case)

// fluent-html/src/core/tag.ts:298
setAria(attrs: Record<string, string | boolean>): this  // aria-label="Close"
```

Despite both existing and being documented in `fluent-html.md`, apps consistently use `addAttribute("aria-*", ...)` and `addAttribute("data-*", ...)` instead:

```ts
// rideshare/src/shared/components/layout.view.ts:464  — three one-liners instead of one setAria call
.addAttribute("role", "dialog")           // ✗ (missing setRole, see F-A-014)
.addAttribute("aria-modal", "true")       // ✗ should be setAria({ modal: "true" })
.addAttribute("aria-label", "Navigation menu")  // ✗ should be setAria({ label: "Navigation menu" })

// rideshare/src/rides/rides.components.ts:183
.addAttribute("aria-label", `View ride from ${from} to ${to}`)  // ✗

// rideshare/src/shared/components/autocomplete.view.ts:158
.addAttribute("data-value", item.value)   // ✗ should be setDataAttrs({ value: item.value })
.addAttribute("data-label", item.label)   // ✗ should be setDataAttrs({ value: item.value, label: item.label })

// ttl/src/admin/views/add-project.view.ts:57
.addAttribute("data-action", "remove-member")    // ✗
.addAttribute("data-user-id", user.id)           // ✗ both writable as setDataAttrs

// ttl/src/shared/components/layout.view.ts:131
.addAttribute("data-action", "close-sidebar")    // ✗
```

Tallied counts across rideshare and ttl:
- `addAttribute("aria-*", ...)`: 6 calls — all replaceable with `setAria({...})`
- `addAttribute("data-*", ...)`: 22+ calls — most replaceable with `setDataAttrs({...})`

## Evidence

The guidelines do mention both methods, but they appear at the bottom of a long code block after `addAttribute`:

```ts
// guidelines/web-development/fluent-html.md:42
.addAttribute("data-x", "val")   // custom attributes only
.setDataAttrs({ userId: "123" }) // data-user-id="123" (auto kebab-case)
.setAria({ label: "Close" })     // aria-label="Close"
```

The presentation order implies `addAttribute` is the primary path and `setDataAttrs`/`setAria` are alternatives. There is no ✗ anti-pattern example showing that `addAttribute("aria-label", ...)` is wrong. The existing apps were likely written before or without reading past the `addAttribute` example.

Additionally, `setAria` accepts `string | boolean` values, but the correct value for `aria-expanded` is the string `"false"` (not boolean), which the method handles via `String(value)`. This is subtle and not shown in the docs.

## Why it matters

- `setDataAttrs({...})` is strictly better than multiple `addAttribute("data-*")` calls: it batches writes, handles camelCase→kebab conversion automatically, and reads as a typed object.
- `setAria({...})` similarly ensures correct `aria-` prefix and handles both string and boolean values.
- The pattern matters for LLMs (Claude Code) which generate code by following guidelines: if the first example in a block is `addAttribute`, that's what gets generated. The fix is a guideline reorder + anti-pattern annotation, not a code change.

## Rough idea (not a design)

Reorder `fluent-html.md`'s "Universal methods" example block: lead with `setDataAttrs` and `setAria`, follow with `addAttribute` as the "when none of the above fit" escape. Add ✗/✓ pairs:

```ts
// ✓
.setDataAttrs({ action: "remove-member", userId: user.id })
.setAria({ label: "Navigation menu", modal: "true", expanded: "false" })

// ✗ — use setDataAttrs for data-* and setAria for aria-*
.addAttribute("data-action", "remove-member")
.addAttribute("aria-label", "Navigation menu")
```
