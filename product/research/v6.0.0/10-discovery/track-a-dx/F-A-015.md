# `SvgShapeTag.setOpacity()` and `setFilter()` route through `addAttribute` instead of `_sk` — inconsistent with every other setter

## Problem

All other `SvgShapeTag` setters (`setFill`, `setStroke`, `setStrokeWidth`, `setTransform`, etc.) write to a typed field and declare that field in `SHAPE_SK`, so the renderer serializes them in the normal data-driven path. But `setOpacity` and `setFilter` bypass this and call `addAttribute`, writing into the `attributes` bag instead:

```ts
// fluent-html/src/elements/svg.ts:46
setOpacity(opacity: string): this {
  return this.addAttribute('opacity', opacity);   // ✗ wrong path
}

// fluent-html/src/elements/svg.ts:61
setFilter(filter: string): this {
  return this.addAttribute('filter', filter);     // ✗ wrong path
}

// fluent-html/src/elements/svg.ts:66
const SHAPE_SK = [
  'fill', 'stroke', 'stroke-width', 'stroke-linecap', 'stroke-linejoin',
  'stroke-dasharray', 'transform'
  // ← no 'opacity', no 'filter'
] as const;
```

## Evidence

The `setFilter` method even carries a JSDoc `@deprecated` marker on its alias `setSvgOpacity`, but `setOpacity` itself still routes through `addAttribute` rather than the `_sk` schema.

The consequences:
1. **Fold layer loses opacity and filter**: `extractAttrs` in `fold/fold.ts` iterates `tag.attributes` for the general bag but SVG presentation attributes tracked via `_sk` go through a different branch. Anything that reconstructs a `SvgShapeTag` via `createTransformAlgebra` will preserve `fill`/`stroke` (because they are in `_sk`) but drop `opacity`/`filter` (in the `attributes` bag, which IS copied, but inconsistently).
2. **Serialization order**: `attributes` entries are serialized after `_sk` entries. For SVG, presentation attribute order shouldn't matter for browsers, but it creates a different canonical rendering than the rest of the shape attributes.
3. **API inconsistency**: a consumer subclassing `SvgShapeTag` expecting all shared attributes to be in `_sk` will be surprised that these two are not.

## Why it matters

While the functional impact is minor (browsers accept both orderings; `addAttribute` still escapes correctly), the inconsistency is a maintenance trap: the pattern "all SVG presentation attributes go in `_sk`" is broken by two methods, which will confuse anyone extending the SVG layer or writing a fold algebra over SVG trees. The fix is trivially small.

## Rough idea (not a design)

Add `opacity?: string` and `filter?: string` to `SvgShapeTag` class fields, add `'opacity'` and `'filter'` to `SHAPE_SK`, and change the setter bodies to `this.opacity = opacity; return this;` (matching every other setter in the class).
