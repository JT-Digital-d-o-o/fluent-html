# No `defineTheme()` API — no way to generate a type-safe `@theme {}` block from TypeScript

## Problem

Tailwind v4 is CSS-first: custom design tokens are defined in CSS via `@theme { --color-accent: …; }`,
not in `tailwind.config.js`. fluent-html has no API to help apps bridge this change. Today apps
define tokens entirely in JS config (v3 style) and reference them in fluent methods using
`(string & {})` widening — which accepts any string, including typos, with zero compile-time
checking.

In v4 the JS config is no longer auto-loaded. Apps will need to hand-write an `@theme` CSS block
**and separately** manually widen the TypeScript types. The library offers no coordinated path.

## Evidence

`rideshare/tailwind.config.js` defines 11 custom color tokens in JS:

```js
// rideshare/tailwind.config.js:23-37
colors: {
  forest: "#0d1f0f",
  moss: "#3faf5a",
  leaf: "#74d680",
  sage: "#DDF3E2",
  cream: "#DDF3E2",
  sand: "#D8D1CA",
  mist: "#DDF3E2",
  "site-bg": "#f2f4f2",
  "site-border": "#e4e8e4",
  charcoal: "#1e1e1e",
  body: "#555555",
  muted: "#707070",
}
```

These 11 colors are used in **456** call-sites across the rideshare app (grep: `"charcoal"\|"leaf"\|"forest"\|"muted"\|"body"\|"sage"\|"mist"\|"moss"`). Every call-site goes through `TailwindColor`'s `(string & {})` escape hatch:

```ts
// fluent-html/src/core/tailwind-types.ts:57-62
// Full color type — includes (string & {}) so custom theme colors
// (e.g. "accent", "brand-500", "accent-dark") work with fluent methods.
export type TailwindColor =
  | "inherit" | "current" | "transparent" | "black" | "white"
  | `${TailwindColorName}-${TailwindShade}`
  | (string & {});   // ← accepts "muted" but also accepts "muteed" silently
```

`ttl/tailwind.config.js` defines a custom `accent` color family:

```js
// ttl/tailwind.config.js:24-29
colors: {
  accent: {
    DEFAULT: "#F59E0B",
    dark: "#D97706",
    light: "#FBBF24",
  },
},
```

Used in **92** call-sites (`.background("accent")`, `.textColor("accent")`, etc.).

Additionally, `rideshare` defines custom `fontSize` tokens (`display-lg`, `display-md`, `display-sm`)
that require explicit `as TailwindTextSize` casts because `TailwindTextSize` is a closed union with
no escape hatch:

```ts
// rideshare/src/landing/views/landing.view.ts:100
.textSize("display-lg" as TailwindTextSize)
// rideshare/src/landing/landing.components.ts:91
.at("md", t => t.textSize("display-md" as TailwindTextSize))
```

8 separate call-sites across rideshare require this forced cast.

## Why it matters

**Frequency × pain:** Two production apps, 500+ call-sites. In v3 this is a tolerable ergonomic
tradeoff. In v4 it becomes a migration blocker: apps must hand-write `@theme { --color-forest: #0d1f0f; … }`
**and** update TypeScript types manually, with no coordination between the two. There is no
compile-time check that the `@theme` CSS and the TypeScript widening stay in sync.

The `as TailwindTextSize` casts are the most egregious evidence: `TailwindTextSize` is a strict
closed union, so custom font-size tokens require a type assertion that silences the compiler
entirely — a typo like `"display-lgg"` passes TypeScript silently.

## Rough idea (not a design)

Add a `defineTheme(tokens)` function exported by `fluent-html` (or a companion) that accepts a
typed token object and returns:
1. A CSS string (`@theme { --color-accent: …; --font-size-display-lg: …; }`) for the user's CSS file.
2. A narrowed union type (`type AppColor = TailwindColor | "accent" | "accent-dark"`) usable as a
   drop-in replacement for `TailwindColor` in the app's own component signatures.

The const-generic approach — `defineTheme({ colors: { accent: "#F59E0B" } as const })` — lets
TypeScript infer exact token names. The v4 migration story becomes: run `defineTheme`, paste the
CSS output into `@theme {}`, import the narrowed types, remove all `as TailwindX` casts.
