# ESLint `no-known-modifiers-in-setclass` auto-fix map references stale v3 gradient and shadow class names

## Problem

The ESLint plugin's `no-known-modifiers-in-setclass` rule (778 lines, 36 KB) is a hand-maintained map from Tailwind class-name patterns to fluent method calls. It powers auto-fix: when a user writes `.setClass("bg-gradient-to-r")` the rule suggests (and can auto-apply) `.gradientTo("to-r")`. Under Tailwind v4, several of these auto-fix suggestions produce **wrong output**:

1. **Gradient pattern** (line 384): `{ pattern: "bg-gradient-", methodName: "gradientTo" }` — the rule correctly recognizes `bg-gradient-*` and fixes to `.gradientTo()`, but `.gradientTo()` then emits `bg-gradient-*` back out (a v3-renamed class). On v4 that class is dead. The fix leads the user from one broken state to another.

2. **Shadow-sm** (line 223): `{ pattern: "shadow-sm", methodName: "shadow", exactMatch: true, fixedValue: "sm" }` — suggests `.shadow("sm")` which emits `shadow-sm`. On v4, `shadow-sm` is one step heavier than on v3. The suggestion is semantically misleading; the correct v4 analog would be `.shadow("xs")` (not yet in the type table).

3. **Rounded-sm** (line 213): `{ pattern: "rounded-sm", methodName: "rounded", exactMatch: true, fixedValue: "sm" }` — same problem as shadow-sm.

The `no-conflicting-classes-in-setclass` rule's `PREFIX_CONFLICTS` list includes `"backdrop-opacity-"` (line 128), which was a legitimate v3 prefix for `backdrop-opacity-50` etc. In v4, `backdrop-opacity-*` is **removed** — the slash-opacity modifier (`backdrop-blur-sm/50`) replaces it. The rule will still flag legitimate v4 user code (e.g., if the user added `backdrop-blur/50`) without recognizing the replacement, and the `backdrop-opacity-` prefix entry in PREFIX_CONFLICTS is a stale false-positive generator.

```ts
// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:213
{ pattern: "rounded-sm", methodName: "rounded", exactMatch: true, fixedValue: "sm" },

// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:223
{ pattern: "shadow-sm", methodName: "shadow", exactMatch: true, fixedValue: "sm" },

// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384
{ pattern: "bg-gradient-", methodName: "gradientTo" },

// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:128
"backdrop-opacity-",
```

## Evidence

The map entries are confirmed at the lines above. The rule file is 778 lines; the `KNOWN_MODIFIERS` array starts at line ~1 and runs the full length. The gradient entry at L384 directly ties to the `bg-gradient-*` → `bg-linear-*` rename established in the recon (03-tailwind4.md, M-1, M-7). The shadow/rounded entries tie to the scale-shift in F-C-021.

Under a v4 migration, a developer who runs the ESLint auto-fix receives:
- `.setClass("bg-gradient-to-r")` → auto-fixed to `.gradientTo("to-r")` → still emits dead `bg-gradient-to-r` class
- `.setClass("shadow-sm")` → auto-fixed to `.shadow("sm")` → emits `shadow-sm`, visually heavier on v4 than intended
- `backdrop-opacity-` in PREFIX_CONFLICTS fires on any class with that prefix, which v4 users writing `/opacity` modifiers would never use; the conflict list becomes noisy

## Why it matters

The ESLint plugin is the lint-time guardrail for class correctness. Stale auto-fix suggestions actively mislead developers during migration: the fix appears to succeed (no more lint error) but the underlying v3 class name is still emitted. This undermines the primary value of the plugin. The `PREFIX_CONFLICTS` stale entry is lower pain (a false-positive conflict warning) but adds noise to v4 migrations.

## Rough idea (not a design)

Coordinate the ESLint map update with the v3/v4 target flag decision (also needed by extractor and methods). Under v4 target:
- Replace `bg-gradient-` entry with `bg-linear-` to suggest `.gradientTo()` for the v4 name (or add a separate `gradientLinear` method)
- Update `shadow-sm` and `rounded-sm` entries to map to `"xs"` value once the `xs` slot is added to the type tables
- Remove `backdrop-opacity-` from PREFIX_CONFLICTS; document the `/opacity` slash-modifier approach instead
- Add entries for new v4 gradient patterns (`bg-linear-`, `bg-radial-`, `bg-conic-`)
