# Bare `.ring()` changes from 3px blue ring to 1px currentColor ring in Tailwind v4

## Problem

In Tailwind v3, bare `ring` (no width argument) creates a **3px** ring in **blue-500**. In Tailwind v4, the same bare `ring` creates a **1px** ring in **currentColor**. This is a semantic change on an unchanged class name — the class still exists and compiles, but renders differently.

fluent-html's type for `.ring()` does not surface this distinction, and neither does the guideline pattern that teaches `.ring("2")` as the canonical focus-ring:

```ts
// fluent-html/src/core/tailwind-types.ts:144
export type TailwindRingWidth = 0 | 1 | 2 | 4 | 8 | Stringified<0 | 1 | 2 | 4 | 8> | (string & {});
// The bare .ring() call (undefined) is valid and maps to the v3 "3px" default — gone in v4
```

```ts
// fluent-html/src/core/tailwind-methods.ts:533-535
p.ring = function (value?: string | number) {
  return value === undefined ? this.addClass("ring") : this.addClass(`ring-${value}`);
};
// Bare .ring() emits "ring" — v3 = 3px blue; v4 = 1px currentColor
```

```ts
// fluent-html-tailwind-extractor/src/index.ts:297
generateClass: (args) => args.length === 0 ? ["ring"] : [`ring-${args[0]}`],
// Extractor faithfully emits "ring" — CSS will be generated but with v4 rendering
```

## Evidence

The apps use `.ring("2")` (explicit width) in the majority of focus-ring patterns, which is safe — `ring-2` is unchanged in v4 (still 2px). However some call-sites use bare `.ring()` or implicit ring defaults via the `ringColor` companion:

```ts
// ttl/src/shared/components/ui.components.ts:85
.on("focus", t => t.ring("2").ringColor("accent")),
// ✓ explicit ring-2, safe on v4

// rideshare/src/rides/views/browse.view.ts:184 (select element)
.outline("none").cursor("pointer")
// No explicit ring — relies on browser default or previously set ring state
```

The concern is broader than just counted call-sites: any user who writes `.ring()` without a width today expects the v3 3px blue ring. On v4 they get 1px in text color. There is no compile-time signal that the semantics changed.

Additionally, `TailwindRingWidth` as a type does not include `3` (the value that would replicate the old v3 bare-ring look on v4: `.ring("3").ringColor("blue-500")`). Apps that want to preserve the old look have no type-safe way to express it — they must reach for the `(string & {})` escape hatch.

The CLAUDE.md project guidelines show `.on("focus", t => t.ring("2").ringColor("blue-300")` as the canonical focus-ring pattern — which is fine. But neither CLAUDE.md nor `fluent-html.md` mentions the bare `.ring()` semantic change or warns against it on v4.

## Why it matters

Focus rings are everywhere in accessibility-correct apps. The `ring` → `ring-3` migration is the v4 upgrade guide's recommendation for preserving the old default look. Without this being documented as a known breaking change (in guidelines and in a migration note), users who rely on bare `.ring()` will silently get hairline rings after a v4 upgrade.

The fix is partly documentation (the guideline must say "never use bare `.ring()`; always pass an explicit width") and partly type-table (add `3` to `TailwindRingWidth`).

## Rough idea (not a design)

Add `3` to `TailwindRingWidth` so `.ring("3")` is type-safe (it replicates the old v3 bare-ring width). Add a `✗ .ring() → ✓ .ring("3")` do-don't rule to `fluent-html.md` guidelines for v4 migration. Include in the migration/compat section of the Track C RFC.
