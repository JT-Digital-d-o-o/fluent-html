# ESLint conflict rule `PREFIX_CONFLICTS` still lists `backdrop-opacity-` — a v4-removed utility

## Problem

The `no-conflicting-classes-in-setclass` rule maintains a `PREFIX_CONFLICTS` array (line 102) that lists class prefixes whose values conflict with each other (e.g. `opacity-50` vs `opacity-75` in the same `setClass()`). Line 128 includes `backdrop-opacity-`:

```ts
// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:128
"backdrop-blur-", "backdrop-brightness-", "backdrop-contrast-", "backdrop-grayscale-",
"backdrop-hue-rotate-", "backdrop-invert-", "backdrop-opacity-", "backdrop-saturate-", "backdrop-sepia-",
```

**Tailwind v4 removed the entire `*-opacity-*` utility family.** `backdrop-opacity-25`, `backdrop-opacity-50`, etc. no longer exist in v4. The correct v4 pattern is the opacity modifier on the color: `backdrop-blur-md/50` style, or separate properties.

The same issue applies to the other opacity utility families that v4 removed:
- `bg-opacity-*` — removed (use `bg-color/opacity`)
- `text-opacity-*` — removed
- `border-opacity-*` — removed
- `ring-opacity-*` — removed
- `placeholder-opacity-*` — removed

Of these, only `backdrop-opacity-` appears in `PREFIX_CONFLICTS`. The rest were apparently never added to the conflict list, so that's consistent but incomplete.

## Evidence

```ts
// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:102-140
const PREFIX_CONFLICTS: string[] = [
  ...
  "backdrop-blur-", "backdrop-brightness-", "backdrop-contrast-", "backdrop-grayscale-",
  "backdrop-hue-rotate-", "backdrop-invert-", "backdrop-opacity-", "backdrop-saturate-", "backdrop-sepia-",
  ...
];
```

On Tailwind v4:
- `backdrop-opacity-50` does not exist → no CSS is generated
- The ESLint rule will still flag `setClass("backdrop-opacity-25 backdrop-opacity-50")` as a conflict, which is technically accurate (two same-prefix classes) but misleading on v4 where both classes are dead

The core problem is the inverse: a v4 project that has `backdrop-opacity-50` (perhaps left over from a v3 migration) gets a conflict warning if it appears twice, but no warning that the utility itself is dead. The ESLint plugin lacks any "deprecated/removed utility" detection category — it only knows fluent-method mapping and value conflict.

## Why it matters

This is a low-pain finding because the conflict detection still fires correctly in a narrow sense. However it creates a misleading signal: a developer on v4 sees "conflicting classes" for something that's actually "both classes are dead in v4." A future "removed utilities" ESLint rule (or an extension of `no-known-modifiers-in-setclass` to also cover removed classes) would be a cleaner fix, but the minimum change is to remove the dead prefix from `PREFIX_CONFLICTS` to avoid false positives on v4 projects.

## Rough idea (not a design)

Remove `backdrop-opacity-` from `PREFIX_CONFLICTS`. Consider adding a new `REMOVED_IN_V4` constant listing removed utility prefixes (`bg-opacity-`, `text-opacity-`, `border-opacity-`, `ring-opacity-`, `backdrop-opacity-`) and a new `no-removed-v4-utilities` rule (or extend the existing modifier rule) that flags usage of these with a message like "This utility was removed in Tailwind v4; use the opacity modifier `/NN` on the color instead."
