# No v3/v4 dual-target mechanism: three packages must agree on class vocabulary with no coordination point

## Problem

Supporting both Tailwind v3 and v4 requires the same class names to differ across three independent packages (`fluent-html`, `fluent-html-tailwind-extractor`, `fluent-html-eslint-plugin`) with **no shared constant, flag, or config object** tying them together. Today:

- `fluent-html/src/core/tailwind-methods.ts:576` emits `bg-gradient-${dir}` (v3)
- `fluent-html-tailwind-extractor/src/index.ts:391` in `METHOD_PATTERNS` also emits `bg-gradient-${dir}` (v3)
- `fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384` matches and fixes `bg-gradient-` (v3)
- `fluent-html-tailwind-extractor/package.json:40` pins `peerDependencies: { tailwindcss: ">=3.0.0" }` (v3 only)

When the gradient rename (F-C-001), scale shift (F-C-021), and outline split (F-C-022) are fixed, each of the three packages must be updated independently, with **no mechanism to enforce they remain in sync**. A developer who updates the methods package but forgets to update the extractor's `METHOD_PATTERNS` will get correct class names in the browser but wrong CSS generated (the extractor still extracts the old class name, which no longer matches the updated method output). Similarly, if the ESLint plugin is on a different v3/v4 assumption from the methods package, its auto-fix suggestions will contradict the method output.

There is currently no:
- Shared `TW_TARGET: "v3" | "v4"` constant
- Extractor `options.target` parameter
- ESLint plugin `settings.tailwindTarget` config
- Automated test asserting all three packages agree on the class string for the same method call

## Evidence

The three affected files all hard-code the same v3 string independently:

```ts
// fluent-html/src/core/tailwind-methods.ts:576
p.gradientTo = function (direction: string) { return this.addClass(`bg-gradient-${direction}`); };

// fluent-html-tailwind-extractor/src/index.ts:390-392
{
  methodName: "gradientTo",
  generateClass: (args) => args.length === 1 ? [`bg-gradient-${args[0]}`] : [],
},

// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384
{ pattern: "bg-gradient-", methodName: "gradientTo" },
```

The extractor's `package.json` pins v3:

```json
// fluent-html-tailwind-extractor/package.json:40
"peerDependencies": { "tailwindcss": ">=3.0.0" }
```

There is no test that does:
```ts
// assert method output ↔ extractor output ↔ eslint map are consistent
```

## Why it matters

The three packages form an implicit contract (method → class name → extractor → CSS). Divergence between them is a latent bug: the app compiles, the lint passes, but either the CSS is not generated (extractor has old name) or the lint auto-fixes to a dead class (ESLint map has old name). A v3→v4 migration performed by updating only one or two of the three packages — which is the likely scenario without a shared coordination point — produces a subtly broken state.

This is also a maintenance burden: any future Tailwind version bump (v4.1, v5) requires the same triple-update pattern with no mechanism to catch mismatches.

## Rough idea (not a design)

Introduce a lightweight coordination mechanism:
- A `tailwindTarget: "v3" | "v4"` option at each package boundary (extractor `ExtractorOptions`, ESLint plugin `settings.fluentHtml.tailwindTarget`)
- A shared cross-package integration test (likely in a monorepo test package) that calls `method → extractedClass → eslintAutoFix` and asserts all three are consistent for a given target
- Bump extractor `peerDependencies` to `">=3.0.0 || >=4.0.0"` under the v4 flag
- The target flag gates the class-name generation branches introduced by F-C-001, F-C-021, F-C-022 fixes
