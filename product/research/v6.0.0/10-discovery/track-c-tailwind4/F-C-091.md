# group-hover/peer-* states exist in TailwindState but guidelines never teach them

## Problem

`TailwindState` already includes `"group-hover"`, `"group-focus"`, `"group-active"`, `"group-disabled"`, `"peer-hover"`, `"peer-focus"`, `"peer-checked"`, and `"peer-invalid"` (line 188–189 of `tailwind-types.ts`). These are fully functional via `.on("group-hover", t => ...)` — the `withVariant` function correctly prefixes the enclosed classes. But neither `guidelines/web-development/fluent-html.md` nor the project `CLAUDE.md` ever shows a `group-hover` example using `.on()`. The only documented use of `.on()` is `"hover"`, `"focus"`, `"disabled"`, and `"dark"`.

The result: every developer (human or LLM) who needs `group-hover:` on a child element reaches for `addClass("group-hover:opacity-100")` — the raw-string escape hatch — rather than the type-safe fluent path. Seven such call-sites exist across the ttl app alone.

## Evidence

```ts
// fluent-html/src/core/tailwind-types.ts:188 — the types DO include group/peer states
export type TailwindState =
  | "hover" | "focus" | "focus-within" | "focus-visible"
  | "active" | "visited"
  | "disabled" | "enabled" | "checked" | "indeterminate" | "required" | "invalid" | "valid"
  | "first" | "last" | "odd" | "even" | "empty"
  | "first-of-type" | "last-of-type" | "only-child"
  | "placeholder" | "selection" | "marker" | "file"
  | "before" | "after"
  | "dark"
  | "group-hover" | "group-focus" | "group-active" | "group-disabled"   // ← exists
  | "peer-hover" | "peer-focus" | "peer-checked" | "peer-invalid";      // ← exists
```

```ts
// ttl/src/time-entry/views/time-entry.view.ts:466 — escape hatch used instead
.addClass("group-hover:opacity-100")   // ✗ raw string, bypasses type safety

// The correct fluent form (undocumented, but works):
.on("group-hover", t => t.opacity("100"))   // ✓ type-safe, uses TailwindState
```

```ts
// ttl/src/shared/components/ui.components.ts:375,390 — more complex cases also escape
.addClass("group-hover:bg-amber-500/20")   // ✗
.addClass("group-hover:text-amber-500")    // ✗
// Fluent equivalents:
.on("group-hover", t => t.background("amber-500/20"))   // ✓
.on("group-hover", t => t.textColor("amber-500"))        // ✓
```

All 7 occurrences are in the same `ttl` codebase, clustered in table/list-row interactive UI components where child elements react to parent hover. Zero occurrences in rideshare, but rideshare has very few list-row interactions.

## Why it matters

The guideline is what an LLM reads when generating code. When the guideline only shows `.on("hover", ...)`, `.on("focus", ...)`, and `.on("disabled", ...)`, both LLMs and human developers naturally reach for `addClass()` for any state that doesn't appear in the examples — even though the type system supports it. This is the same dynamic that caused `Match` to be used 18:1 vs `IfThen`.

In the context of Tailwind v4, this gap matters additionally because:
- v4 introduces `group-*` and `peer-*` variant naming changes (the `/name` syntax for named groups is unchanged, but the underlying mechanism is part of the variant system that's being re-audited).
- Users migrating to v4 who add new `group-hover` interactions will go straight to `addClass` strings if the guideline never shows the fluent path.

Frequency: 7 call-sites in one app with no fluent equivalent shown anywhere in the guidelines.

## Rough idea (not a design)

Add a `## Group and peer variants` section to `guidelines/web-development/fluent-html.md` with a ✓/✗ do-don't pair showing `.on("group-hover", ...)` and `.group()` used together. Also add `peer-checked` / `peer-invalid` examples since they're needed for checkbox-driven UI patterns. No code change needed — only a guideline edit.

```ts
// ✓ type-safe group variants
Div().group()                                              // marks parent
  .append(
    Button("Edit").on("group-hover", t => t.opacity("100").scale("105"))
  )

// ✗ raw string escape hatch — loses type safety
Button("Edit").addClass("group-hover:opacity-100")
```
