# Guidelines reference Alert, Badge, and Spinner as built-in imports in code examples, but none are exported by the library

## Problem

The guidelines (both `fluent-html.md` and `CLAUDE.md`) use `Alert`, `Badge`, and `Spinner` in code examples illustrating `Match` control-flow:

```typescript
// guidelines/web-development/fluent-html.md:123-127
Match(status, {
  active: () => Badge("Active"),
  error:  () => Badge("Error"),
}, () => Badge("Unknown"))

// guidelines/web-development/fluent-html.md:129-133
Match(state, "status", {
  loading: ()  => Spinner(),
  error:   (s) => Alert(s.message),
  success: (s) => UserList(s.data),
})
```

None of `Alert`, `Badge`, or `Spinner` is exported from the `fluent-html` package (confirmed: `grep` over `src/index.ts` returns zero matches). They exist only as per-app helper functions.

The CLAUDE.md copy of the Match example at line 107 repeats the `Alert` usage:
```typescript
// guidelines/web-development/CLAUDE.md:107
error:   (s) => Alert(s.message),   // s narrowed to { status: "error"; message: string }
```

Because the primary consumer of these guidelines is an LLM (Claude Code), not a human, this is not merely a documentation inaccuracy. When Claude Code scaffolds a new view it will import `Alert` from `fluent-html` — and get a compile error. Alternatively it will define a local `Alert` inline, bypassing the shared component and contributing to the per-app proliferation documented in F-B-061.

## Evidence

`fluent-html/src/index.ts` exports: no `Alert`, `Badge`, `Callout`, or `Spinner`. Full grep output: empty.

Guidelines `fluent-html.md:119-138` shows four distinct usages of `Badge(...)` and two of `Alert(...)` in the control-flow reference section. These are placed in context-free code blocks with no import statement, implying they are library exports on par with `Match`, `ForEach`, and `IfThen`.

`CLAUDE.md:107` (the CLAUDE.md that is inlined into every project context) repeats the `Alert(s.message)` usage in the discriminated-union Match example.

## Why it matters

This is a guidelines-vs-reality drift in the most frequently read document (CLAUDE.md is injected into every session). An LLM reading these guidelines will model `Alert` and `Badge` as fluent-html primitives, leading it to: (a) write incorrect imports, (b) generate code that fails to compile, or (c) silently define local one-off helpers when the import fails — perpetuating the duplication problem these findings document. Pain is **high** because it gates correct code generation for every new view that uses status feedback.

## Rough idea (not a design)

Two options (mutually exclusive — Wave 2 decides):

1. **Ship the APIs** — implement `Alert` / `Badge` / `Spinner` as built-ins (see F-B-061, F-B-062). The guideline examples then become correct as-is. This is the preferred path.
2. **Fix the guidelines now** — replace the placeholder names with imports from a hypothetical `@project/ui` or mark them explicitly as "app-defined helpers, not library exports." Add an import comment to every example that uses them.

If option 1 is chosen, the guidelines gain accuracy without any edits. If option 2, the guideline_gap is `web-development/fluent-html.md` (Match section examples) and `web-development/CLAUDE.md` (Match discriminant example).
