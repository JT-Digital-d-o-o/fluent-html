# No first-class Badge component; StatusBadge re-implemented 5+ times per app with per-app color maps

## Problem

Every app that displays status-driven colored labels (payment status, project status, subscription status, render status, event status) re-implements the same `StatusBadge` helper. Within a single app (jt-cut, storysell-ai) this helper is even duplicated 2–4 times across features because there is no canonical one to import. The implementations share the same pill shape (rounded-full, xs text, padding x/y) but differ in how the `value → color` mapping is expressed, ranging from:

- Parallel `statusBg()` + `statusTextColor()` utility functions (jt-cut payments)
- A local `const statusStyles = { … } satisfies Record<Status, …>` record (jt-cut ui.components, pps composite)
- A `STATUS_COLORS` record with raw Tailwind class strings passed to `.setClasses()` or `.addClass()` (mngmt)
- A `statusConfig` record with bg/text/dot properties (storysell-ai brand badges, jt-cut ui.components)

The mixing of fluent `.background()`/`.textColor()` calls with raw `.addClass("bg-…")` / `.setClasses(["bg-…", "text-…"])` is particularly notable in mngmt and parts of jt-cut, where the semantic intent is clear but there is no type-safe bridge from "enum value" to "fluent color pair."

## Evidence

jt-cut defines `StatusBadge` at least 4 times in different features:
```ts
// jt-cut/src/shared/components/ui.components.ts:33-56 — shared, fluent bg/text
type StatusBadgeProps = { status: string; label?: string };
const statusStyles = {
  completed: { bg: "emerald-50" as const, text: "emerald-700" as const, dot: "bg-emerald-500" },
  rendering: { bg: "coral-50" as const, text: "coral-dark" as const, dot: "bg-coral" },
  …
};
export function StatusBadge({ status, label }: StatusBadgeProps) { … }

// jt-cut/src/payments/payments.view.ts:50-61 — local copy using statusBg()/statusTextColor() helpers
function StatusBadge({ status }: StatusBadgeProps) {
  return Span(statusLabel(status))
    .background(statusBg(status))
    .textColor(statusTextColor(status));
}

// jt-cut/src/projects/views/projects.components.ts:30-48 — third local copy, bare string status
export function StatusBadge(props: { status: string }) { … }

// jt-cut/src/analytics/views/analytics.badges.ts:11-19 — fourth, takes raw string
export function StatusBadge(status: string) { … }
```

mngmt uses raw class strings via `.setClasses()` / `.addClass()` because no fluent API maps enum → color:
```ts
// mngmt/src/dashboard/dashboard.components.ts:36-48
const STATUS_COLORS: Record<ProjectStatus, { bg: string; text: string }> = {
  "On track": { bg: "bg-emerald-500/10", text: "text-emerald-400" },
  "At risk":  { bg: "bg-amber-500/10",   text: "text-amber-400"   },
  "Blocked":  { bg: "bg-red-500/10",     text: "text-red-400"     },
};
export function StatusBadge({ status }: { status: ProjectStatus }) {
  const colors = STATUS_COLORS[status] ?? STATUS_COLORS["On track"];
  return Span(status)
    .setClasses([colors.bg, colors.text])  // raw class strings, defeats fluent type-safety
    .textSize("xs").fontWeight("medium").padding("x","3").padding("y","1").rounded("full");
}
```

storysell-ai has a sophisticated 5-badge family in `ui.brand.badges.ts` (StatusBadge, CountBadge, TypeBadge, HighlightBadge, PercentBadge) but each is hand-wired individually with its own color record. It also has a *separate* `StatusBadge` inline in `payments.components.ts:7` that uses a different shape. planet-positive-sport has two `StatusBadge` variants: one generic (in `display.ts`) and one domain-specific workflow-state one (`composite.ts:86`).

## Why it matters

Across jt-cut, storysell-ai, glimm, mngmt, planet-positive-sport, and vabilo30 the recon counted ~21 + 19 + 8 + 6 + 34 = ~88 `StatusBadge` call sites and 15+ independent definitions. The raw-class-string workaround in mngmt defeats fluent's type-safe color lookup, meaning Tailwind v4 renames would silently break those badges. The per-app duplication also makes it impossible to enforce a consistent pill shape (some have a dot indicator, some don't; sizes vary from `xs` to `sm`).

## Rough idea (not a design)

`Badge(label, { variant })` with a standard semantic palette (`success | warning | danger | info | neutral`) for the common case. `Badge.of(value, colorMap)` where `colorMap: Record<Value, { variant: BadgeVariant }>` (or `{ bg, text }` fluent pairs) for the enum-driven case — this replaces the `STATUS_COLORS` record + `.setClasses()` pattern and keeps everything in fluent. Optional `dot` prop for the status-dot indicator shape seen in storysell-ai's brand badges.
