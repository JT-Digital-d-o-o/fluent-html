# `renderToStream` declared in 2 apps but never called — streaming render adoption is zero

## Problem

`renderToStream` is imported from `fluent-html` and wired as a Fastify reply decorator (`renderStreamView`) in both storysell-ai and glimm. In neither app is `renderStreamView` ever called from a controller or view — the declaration is dead code. The library ships a streaming render primitive that no real app uses.

## Evidence

```ts
// storysell-ai/src/core/server.ts:7
import { render, renderToStream, View, defineRoutes } from "fluent-html";

// storysell-ai/src/core/server.ts:149-153
server.decorateReply(
  "renderStreamView",
  function (this: FastifyReply, view: View) {
    this.type("text/html").send(renderToStream(view));
  }
);
```

```ts
// glimm/src/core/server.ts:11
import { render, renderToStream, View, defineRoutes } from "fluent-html";

// glimm/src/core/server.ts:123-126
server.decorateReply(
  "renderStreamView",
  function (this: FastifyReply, view: View) {
    this.type("text/html").send(renderToStream(view));
  }
);
```

A full-text search of `renderStreamView` across both apps returns zero results outside these two declaration sites. `rideshare`, `mngmt`, `planet-positive-sport`, and `jt-cut` don't import `renderToStream` at all.

## Why it matters

The root cause appears to be architectural: all data fetching in fluent-html apps happens synchronously before `renderView` is called. The controller awaits all DB queries, then calls `reply.renderView(Page({ data }))`. There is no concept of a "deferred slot" — a placeholder that the stream can resolve later with the result of a concurrent async call. Without that, `renderToStream` provides no benefit over `render` for the typical controller pattern:

```ts
// every controller follows this shape:
const data = await prisma.thing.findMany(...);   // all data loaded first
reply.renderView(Page({ data }));                // then render synchronously
```

Streaming is only beneficial when you can begin sending HTML immediately and fill slots asynchronously. The library lacks the `Deferred(route, placeholder)` or `Suspense(promise, fallback)` primitive that would make the two-phase pattern ergonomic. Without it, streaming render is a dead export.

The guidelines (`fluent-html.md`) mention `renderToStream` but provide no guidance on when to use it, how to structure controllers for it, or what the "deferred slot" pattern would look like.

## Rough idea (not a design)

Two complementary things: (1) A `Deferred(routeRef, placeholder)` or `LazyFragment(routeRef, fallback)` component that emits an htmx-powered placeholder (`hx-get + hx-trigger=load`) so the stream can deliver the shell immediately while the slow data fetches in a second round-trip — this is the HTMX-native approach to "suspense." (2) Guidelines update to explain when `renderToStream` is useful (large pages where the `<head>` / above-the-fold content can be flushed before slow queries finish) versus when it isn't (typical CRUD endpoints that await everything before rendering). The guideline gap is that devs can't tell the difference, so they copy the `renderStreamView` decorator from a starter template and never use it.
