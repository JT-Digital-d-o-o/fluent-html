# No built-in inline per-field validation error component — `FieldError` re-derived in every form view

## Problem

Showing a per-field error message below an input requires every view to either (a) define a private `FieldError` helper or (b) repeat an `IfThen(errors?.fieldName, msg => P(msg).textSize("xs").textColor("red-600").margin("t","1.5"))` pattern inline. Neither is taught by the guidelines; apps converge on the pattern organically but duplicate the micro-component everywhere.

A related issue: the boundary between a form-level `Alert` (whole-form error) and a field-level `FieldError` (per-input error) is left entirely to convention. Some views use Alert for what should be a FieldError (the whole-form Alert in mngmt `PasswordSection` fires for a field-specific error like "passwords do not match").

## Evidence

**rideshare** defines `FieldError` twice in the same feature:

```ts
// rideshare/src/rides/views/create.view.ts:117-119
function FieldError(message: string) {
  return P(message).textSize("xs").textColor("red-600").margin("t", "1.5");
}

// rideshare/src/shared/components/phone-input.view.ts:31-32
/** Inline field error — mirrors the FieldError style used on the ride form. */
function FieldError(message: string) {
  return P(message).textSize("xs").textColor("red-600").margin("t", "1");
}
```

The comment in `phone-input.view.ts:30` ("mirrors the FieldError style used on the ride form") confirms the author knew they were duplicating code but had no shared built-in to reach for.

**planet-positive-sport** achieves field-level error highlighting via arbitrary child-selector escape hatch, not a component:

```ts
// planet-positive-sport/src/shared/components/forms/form.ts:21-40
.when(!!error, t =>
  t.addClass("[&>input]:border-red-300 [&>textarea]:border-red-300 [&>select]:border-red-300 ..."))
```

This side-steps the error-text display problem entirely by styling the child element from the parent — because there is no first-class way to pass an error down to the styled input and have it render error state.

**rideshare create.view.ts** shows the resulting call-site boilerplate:

```ts
// rideshare/src/rides/views/create.view.ts:218
IfThen(errors?.departureCity, (msg) => FieldError(msg)),
// … repeated at :271, :278, :289, :324
```

Five manual `IfThen(errors?.field, msg => FieldError(msg))` invocations in a single view file.

## Why it matters

Every form with per-field validation repeats `IfThen(errors?.X, msg => <error-markup>)` for each field. The markup is nearly identical across all apps (small red text below the input). A built-in removes the boilerplate and standardises the visual treatment; it also enables the `FormField` (F-B-001) to wire it automatically. The `[&>input]:border-red-300` workaround in pps is the worst outcome: it relies on arbitrary Tailwind child selectors to style the input's border from the parent, which breaks if the input is wrapped in an extra element.

The guideline at `web-development/views.md:136-148` shows a `FormField` that accepts `error?` but `FormField` is not a real built-in — it is a code snippet for users to copy into their own project. The gap between "here is an example" and "this ships in the library" is exactly where the boilerplate lives.

## Rough idea (not a design)

A built-in `FieldError(message)` component with standardized styling (small, red, top-margin), and a `FieldHint(message)` for non-error help text. Integrate both into a `FormField` component (F-B-001) so the error appears automatically when the `error` prop is set, with appropriate `aria-describedby` linking. This eliminates the per-view `IfThen(errors?.field, ...)` pattern.
