# Multiple layout variants (app/landing/auth) per app share no shell abstraction; layout props fan-out to every view call site

## Problem

Every mature app grows 2–5 layout variants (app-with-sidebar, landing/marketing, auth/unauthenticated, public, admin) that share the same `<head>` boilerplate but differ in chrome. Each variant is a separate top-level function. Because there's no shell context, every view function must thread layout-specific data as props (`user`, `title`, `activePage`, `navCounts`, `navActions`, etc.) even though those values are request-scoped constants, not component-specific data.

## Evidence

rideshare's `Layout` function signature already requires 7 props, many of which exist purely to pass down to the nav:

```ts
// rideshare/src/shared/components/layout.view.ts:71-78
type LayoutProps = {
  title: string;
  children: View;
  variant?: LayoutVariant;
  description?: string;
} & NavProps;  // adds user, authPage, navCounts, activePage

export function Layout({ title, children, user, authPage, variant = "app", description, navCounts, activePage }: LayoutProps) {
```

Every view function then re-declares and passes these fields:
```ts
// rideshare/src/reservations/reservations.view.ts:207
return Layout({ title: "My Reservations", user, activePage: "reservations", navCounts, children: ... });
// rideshare/src/rides/views/browse.view.ts:54
return Layout({ title: "Browse Rides", user, activePage, navCounts, children: ... });
```

planet-positive-sport went further and split into separate layout files to cope with the variants:

```ts
// planet-positive-sport/src/shared/components/layouts/ (3 files)
//   app-layout.view.ts:91  — authenticated app shell
//   auth-layout.view.ts:70 — sign-in/register pages
//   public-layout.view.ts:71 — public/marketing pages
```

Each of the 3 files starts with `Raw("<!DOCTYPE html>")` and assembles its own `Head(...)`. storysell-ai uses a single `Layout()` with a `chrome?: boolean` flag that conditionally renders the sidebar or navigation, making the function body a large conditional tree.

## Why it matters

The prop-threading anti-pattern forces every view function signature to carry layout-specific fields (6+ props in rideshare) that don't belong to the view's own data model. This is precisely the use case that `createContext` was designed for: request-scoped data (the authenticated user, notification counts, the active-page key) known at request entry that multiple components read. But the guidelines don't teach "seed layout context in a Fastify preHandler," so apps resort to prop drilling instead. Additionally, having 2–5 independent layout files per app repeats all the `<head>` / DOCTYPE boilerplate (covered in F-B-031) and makes variant-switching fragile.

## Rough idea (not a design)

Two complementary directions: (1) a `LayoutContext` (via `createContext`) holding `{ user, title, activePage, navCounts }` seeded once in a Fastify preHandler, letting layout components read from context rather than receiving props; and (2) a `Shell({ variant, head?, chrome?, children })` built-in that composes the document shell and delegates chrome selection (sidebar/topnav/none) to the `variant` discriminant rather than a boolean flag. These together would cut layout view signatures from 7+ props to 1–2 (just `children` + page-specific data).
