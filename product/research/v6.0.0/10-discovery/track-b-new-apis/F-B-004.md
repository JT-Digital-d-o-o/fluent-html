# `formFor<T>()` adoption gap — mngmt uses 0 formFor calls with 52 raw `.setName()` despite guideline mandate

## Problem

The guideline at `web-development/CLAUDE.md:91` says: "**`formFor<T>()`** — use for type-safe form fields; never untyped `.setName()` when a schema exists." Despite this, the `mngmt` app makes 0 uses of `formFor` and 52 raw `.setName()` calls across its forms, including on forms that have well-defined schema types (settings page forms all have corresponding Fastify JSON schema bodies). The guideline is clear but the gap remains — suggesting the current teaching is insufficient.

## Evidence

**mngmt** settings view — 52 raw `.setName()` calls, no `formFor`:

```ts
// mngmt/src/settings/settings.view.ts:120
StyledInput().setType("text").setName("name").setValue(user.name || "")
// :163
StyledInput().setType("password").setName("currentPassword")
// :172
StyledInput().setType("password").setName("newPassword")
// :429
StyledInput().setType("text").setName("name").setPlaceholder("Space name (e.g. rideshare)").toggle("required")
// :486
StyledInput().setType("text").setName("repoName").setPlaceholder("GitHub repo name (e.g. rideshare)").toggle("required")
```

All of these correspond to schema types defined in `mngmt/src/settings/settings.schema.ts` (Fastify JSON schema for the body). The type information exists — it is simply not being used for the form field names.

**storysell-ai** demo view — 40 raw `.setName()` calls alongside 27 `formFor` uses in the same app:

```ts
// storysell-ai/src/demo/views/demo.view.ts:49
Input().setName(name).setValue(value).setPlaceholder(placeholder).addClass(INPUT_CLASS),
```

The demo view bypasses `formFor` even though it renders named fields for a specific request schema.

**rideshare** shows the correct pattern with `formFor` (28 uses) but also retains 27 raw `.setName()` calls for cases where `formFor` seemed inconvenient (file inputs, hidden fields, multi-word date/time splits).

## Why it matters

`formFor<T>()` provides compile-time protection against field name typos that submit the wrong key to the server — a silent data bug. When `.setName("nmae")` compiles fine but submits nothing to the server's `name` field, the error only surfaces at runtime. With `formFor<T>().input("nmae", "text")` the typo is a compile error.

Three apps (mngmt, parts of storysell-ai, parts of rideshare) continue to use raw `.setName()` on forms with typed schemas. The guideline says "never untyped `.setName()` when a schema exists" but does not show a concrete ✗ example with a real typo scenario, nor does it note that `formFor` output is a normal `InputTag` with full chaining — a common misconception seems to be that using `formFor` sacrifices the ability to chain `.setPlaceholder()`, `.toggle("required")`, etc.

## Rough idea (not a design)

Edit `web-development/views.md` (section "Type-safe form fields with `formFor`") to add: (1) a ✗ example explicitly showing raw `.setName("nmae")` compiling but submitting the wrong key; (2) a concrete chaining example showing `f.input("email", "email").setPlaceholder("you@example.com").toggle("required")` — demonstrating that `InputTag` chaining is unaffected; (3) a note covering the legitimate exception cases (file inputs, hidden fields, meta tags). No code change required.
