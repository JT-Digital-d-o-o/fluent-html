# No behavior for form-reset-on-success; 5+ apps hand-write hx-on:htmx:after:request/swap with status guard

## Problem

After an HTMX form submission, apps routinely want to reset the form on success (HTTP < 300) while preserving user input on validation errors (422). This is a standard pattern in HTMX apps — but the `.behavior()` system covers only DOM interactions triggered by `click` or `focus`, not HTMX lifecycle events. Devs are forced to hand-write `hx-on:htmx:after:request` or `hx-on:htmx:after:swap` expressions via `addAttribute`.

The expressions are not trivial: they need to guard on the response status (to avoid resetting on 422), and in HTMX 4 the event shape changed from `event.detail.xhr.status` to `event.detail.ctx.response?.status` — a detail that apps frequently comment on:

```ts
// planet-positive-sport/src/admin/pre-approved-emails/views/pre-approved-emails.list.view.ts:101-107
// Morph preserves dirty input values across the redirect+swap, so a fresh
// value="" doesn't visually clear them. Reset the form when the request
// succeeds (HTTP < 300) so Email/Note clear after add but the user's input
// is preserved on a 422 (duplicate) re-render. htmx 4 alpha 7 syntax:
// `hx-on:<eventName>` (no `::` shorthand), event `htmx:after:request`,
// detail shape `{ctx: {response: {status, ...}, ...}}`.
.addAttribute("hx-on:htmx:after:request", "if (event.detail.ctx.response?.status < 300) this.reset()"),
```

The same file has a second identical addAttribute at line 139, and a third variant in `events.view.ts`:

```ts
// planet-positive-sport/src/admin/events/events.view.ts:364-367
.addAttribute(
  "hx-on:htmx:after:request",
  "if (event.target === this && event.detail.ctx.response?.status < 300) this.reset()",
)
```

(The `event.target === this` guard was added to prevent child htmx requests from also triggering the reset — a subtle correctness issue not present in the simpler variants.)

In the assessment component:

```ts
// planet-positive-sport/src/loc/assessment/assessment.components.ts:717
.addAttribute("hx-on:htmx:after:request", "if (event.detail.ctx.response?.status < 300) this.reset()"),
```

In rideshare, a different lifecycle event is used (`after:swap` instead of `after:request`) with an element-existence check:

```ts
// rideshare/src/settings/settings.view.ts:260
.addAttribute("hx-on:htmx:after:swap", `if(!document.getElementById('${ids.passwordError.id}'))this.reset()`),
// rideshare/src/settings/settings.view.ts:337
.addAttribute("hx-on:htmx:after:swap", `if(!document.getElementById('${ids.emailError.id}'))this.reset()`),
```

## Evidence

Six distinct call sites across two apps, each requiring developer knowledge of:
- The correct HTMX 4 event name and attribute format (`hx-on:htmx:after:request`, no `::` shorthand)
- The changed event detail shape (`event.detail.ctx.response?.status` vs the HTMX 2 `event.detail.xhr.status`)
- The status-guard pattern to preserve 422 input state
- An optional self-guard (`event.target === this`) to prevent child request pollution

Every call site has a multi-line comment explaining the HTMX 4 syntax — a clear signal this is non-obvious and friction-heavy.

## Why it matters

Form reset after successful submission is one of the most common post-submission UX interactions in HTMX apps. The `.behavior()` system's complete silence on HTMX lifecycle events forces every app to re-discover the correct incantation independently. The comments show devs are actively debugging the HTMX 4 API shape change — this is a correctness footgun (wrong event name or detail shape → silent failure).

Frequency: 6 confirmed sites across rideshare and pps, likely more in storysell/glimm (not fully grepped). The pattern is universal wherever forms use outerMorph (which preserves dirty values on 422 re-render).

## Rough idea (not a design)

Add `behavior("resetOnSuccess")` that emits `hx-on:htmx:after:request` with the correct HTMX 4 guard expression, and optionally a `selfOnly: true` flag to add the `event.target === this` guard. This is the single most-commented workaround in app code, making it a high-ROI addition to the behavior registry.
