# No request-scoped context that survives `await`; apps resort to AsyncLocalStorage despite guideline ban

## Problem

The CLAUDE.md guideline says "**Never use `AsyncLocalStorage`** for render-time data — context is sufficient." Yet storysell-ai uses `AsyncLocalStorage` deliberately, with a comment explaining exactly why fluent-html's `createContext` fell short: data loaded in an async `preHandler` hook must still be visible to a synchronous render later in the same request — including after mutations.

`createContext` requires an explicitly entered synchronous scope around the render call. There is no "seed at request start, mutate after await, read at render" story. The guideline says the right answer is `createContext`, but `createContext` cannot carry data across awaits into a later render call.

## Evidence

```ts
// storysell-ai/src/core/view-context.ts:20-39
export const sidebarContext = new AsyncLocalStorage<SidebarContext>();

/**
 * Update the request's sidebar context after a mutation (create / switch brand)
 * that then renders a chrome page in the same request.
 *
 * Mutates the store seeded at the start of the request rather than calling
 * `enterWith` again: `AsyncLocalStorage.enterWith` does NOT reliably propagate
 * when called after an `await`, so a fresh store set here (post-DB-query) would
 * be invisible to the synchronous render. The seeded store object is shared by
 * reference for the whole request, so mutating it is always visible.
 */
export function setSidebarContext(ctx: Partial<SidebarContext>): void {
  const store = sidebarContext.getStore();
  if (store) Object.assign(store, ctx);
  else sidebarContext.enterWith({ brands: [], activeId: null, ...ctx });
}
```

```ts
// storysell-ai/src/core/server.ts:164-194
// IMPORTANT: `enterWith` only propagates to the handler when called BEFORE the
// first `await`. So we seed a mutable store synchronously, then mutate it with
// the brands after the DB query.
server.addHook("preHandler", async (request) => {
  const store: SidebarContext = { brands: [], activeId: null, mode: "default" };
  sidebarContext.enterWith(store);

  const user = request.user;
  if (!user) return;
  // ... hx-target check ...
  try {
    const brands = await server.prisma.brand.findMany(...);
    store.brands = brands;         // mutate the already-seeded store
    store.activeId = pickActiveBrand(brands, user.activeBrandId)?.id ?? null;
  } catch (err) {
    request.log.error(err, "failed to load sidebar brands");
  }
```

The second ALS call site (`brand.active.ts:50`) shows the same object-mutation workaround after a DB query.

## Why it matters

This is a documented guideline violation that the developer was forced into by the library's limitations. The comment in the source code is a precise bug report: `createContext` scopes only cover synchronous call stacks, so the common pattern of loading chrome data asynchronously in a preHandler and reading it in a synchronous view render simply doesn't work with the existing API.

The same need recurs in any app with an authenticated shell that pre-fetches shared data (navigation badges, org context, feature flags, active subscription) and hands it to a layout component. rideshare solves the same problem by threading `navCounts` through every controller's `Layout()` call (50+ explicit `navCounts: request.navCounts` prop-drill sites in settings.controller.ts alone), which is the boilerplate ALS was meant to eliminate.

Pain: high — the developer who hit this was careful and skilled; they left a comment explaining the ALS semantics in detail. Less experienced developers will either get broken views (empty picker) or introduce a harder-to-debug bug.

## Rough idea (not a design)

Two complementary directions: (1) A Fastify-integration helper `decorateRequestContext(server, MyContext, loadFn)` that seeds a fluent-html context value per-request in a preHandler hook (leveraging the fact that `enterWith` propagates within the hook's own call stack, so the context survives into the synchronous render the hook eventually leads to). (2) An overload on `reply.renderView(view, { contexts: [[MyContext, value], ...] })` that temporarily enters context scopes around the render call — letting controllers pass values explicitly without prop-drilling.
