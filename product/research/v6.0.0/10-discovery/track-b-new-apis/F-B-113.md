# No `Button().variant()` / `.size()` API — button wrappers reimplemented in 5 apps

## Problem

Every app that reaches a two-button interface (primary + secondary) or a delete action (danger) independently writes `PrimaryButton`, `SecondaryButton`, `DangerButton` wrapper functions. Each encodes its own radius, padding, font-weight, shadow, and hover-color choices in 10–15 lines of fluent chain. The result is 5 incompatible button families that share the same semantic structure but diverge on every token.

## Evidence

glimm has **two** separate button families: a generic one in `ui.button.components.ts` and a brand-specific huluma layer in `huluma/button.components.ts`:

Generic layer (rounded `"lg"`, no shadow, `fontWeight("extrabold")`):
```ts
// glimm/src/shared/components/ui.button.components.ts:10-20
export function PrimaryButton({ label }: PrimaryButtonProps) {
  return Button(label)
    .background("primary").textColor("deep").padding("x","6").padding("y","3")
    .rounded("full").fontWeight("extrabold").shadow("soft")
    .transition("colors").on("hover", t => t.background("primary-700"));
}
```

Huluma brand layer (rounded `"full"`, shadow `"lit"`, tracking `"[0.01em]"`, min-tap-44px, focus ring):
```ts
// glimm/src/shared/components/huluma/button.components.ts:10-27
export function PrimaryPill(label: string) {
  return Button(label)
    .setType("button").rounded("full").background("coral").textColor("deep")
    .fontWeight("extrabold").textSize("[15px]").tracking("[0.01em]")
    .padding("x","8").padding("y","3.5").shadow("lit").transition("colors").cursor("pointer")
    .on("hover", t => t.background("coral-deep"))
    .on("focus", t => t.outline("none").ring("2").ringColor("coral"))
    .on("disabled", t => t.opacity("50").cursor("not-allowed"));
}
```

glimm thus has **two** primary button variants in production. The second layer (`PrimaryPill`) coexists with the first (`PrimaryButton`) because there was no library mechanism to reconfigure the existing one.

storysell-ai (rounded `"lg"`, `fontWeight("medium")`, no shadow):
```ts
// storysell-ai/src/shared/components/ui.button.components.ts:10-18
export function PrimaryButton({ label }: PrimaryButtonProps) {
  return Button(label)
    .background("primary").textColor("white").padding("x","6").padding("y","3")
    .rounded("lg").fontWeight("medium")
    .transition("colors").on("hover", t => t.background("primary-700"));
}
```

planet-positive-sport defines 5 button types (PrimaryButton, DangerButton, SecondaryButton, IconButton, ButtonGroup) in `forms/buttons.ts:7-111`, plus `PrimaryBlockLink`. pps SecondaryButton uses `background("white").textColor("gray-700").border().borderColor("gray-300")` while glimm's equivalent uses `.background("foam").borderColor("sand-2")` — semantically identical, diverging in every token.

The divergence is most visible across three dimensions:
- **Border radius**: `"full"` (pill, glimm-huluma), `"lg"` (storysell/pps), none (a few CTA links)
- **Font weight**: `"extrabold"` (glimm), `"medium"` (storysell, pps)
- **Shadow**: `"soft"`/`"lit"` (glimm), none (storysell, pps)

## Why it matters

Five apps, one semantic concept (primary CTA button), five incompatible implementations. Every app developer writes the same 12-line wrapper from memory. The glimm double-layer (two separate button families in one app) shows what happens when there's no reconfigurable variant system — the second team created a new set of wrappers rather than configuring the existing one.

A `Button(label).variant("primary")` API with a context-configurable theme (border-radius token, color roles, weight, shadow) would let apps define their brand tokens once and retire all the wrapper functions.

## Rough idea (not a design)

Add `Button(label).variant("primary"|"secondary"|"danger"|"ghost")` and `.size("sm"|"md"|"lg")` to the base Tag surface. Variant styles resolve via a `ButtonThemeCtx` context (or a `configureButtonTheme(tokens)` factory), allowing each app to supply `{ radius, padding, font, shadow }` per variant and receive correctly typed fluent Tag output. The Wave-2 RFC should compare this against the `.apply(style)` approach (which already works but lacks semantic names and IDE discoverability).
