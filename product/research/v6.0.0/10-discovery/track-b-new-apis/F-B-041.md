# No Icon registry — every app maintains its own per-file SVG dump

## Problem

There is no `Icon("name")` or similar helper in fluent-html, so every app independently accumulates a collection of hand-authored per-icon wrapper functions or raw SVG string constants. The two strategies used are both worse than a registry:

**Strategy A — individual icon wrapper functions backed by `Raw()`:**

```ts
// rideshare/src/shared/components/layout.view.ts:171-216
function SearchIcon() {
  return Raw(`<svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><circle cx="11" cy="11" r="8"/><path d="m21 21-4.35-4.35"/></svg>`);
}
function BookmarkIcon() { return Raw(`<svg …`); }
function PlusCircleIcon() { return Raw(`<svg …`); }
// … 14 such functions in one file
```

**Strategy B — `SvgIcon(d)` helper that builds from a path `d` string:**

```ts
// jt-cut/src/projects/v2/views/v2.components.ts:34-37
function SvgIcon16(d: string) {
  return Svg(
    Path().setD(d).setFill("none").setStroke("currentColor").setStrokeWidth("2").setStrokeLinecap("round").setStrokeLinejoin("round"),
  ).w("4").h("4").setViewBox("0 0 24 24");
}
// 12 named exports follow: ChevronLeftIcon, CheckIcon, PlusIcon, CloseIcon, PlayIcon…
```

Also in `jt-cut/src/shared/components/ui.components.ts:374-380`:
```ts
export function SvgIcon(d: string) {
  return Svg(
    Path().setD(d).setFill("none").setStroke("currentColor").setStrokeWidth("1.8").setStrokeLinecap("round").setStrokeLinejoin("round"),
  ).w("5").h("5").setViewBox("0 0 24 24");
}
```

**Strategy C — raw SVG string constants stored in a Record, consumed via `Raw(icon)`:**

```ts
// mngmt/src/dashboard/dashboard.components.ts:25-33
const ICON_CHECK_CIRCLE = '<svg class="w-4 h-4 text-accent shrink-0" fill="none" stroke="currentColor" stroke-width="2" viewBox="0 0 24 24"><path stroke-linecap="round" stroke-linejoin="round" d="M9 12.75L11.25 15 15 9.75M21 12a9 9 0 11-18 0 9 9 0 0118 0z"/></svg>';
const ICON_CLOCK = '<svg class="w-4 h-4 text-accent/60 shrink-0" …>';
// … 8 more constants
const TASK_STATUS_ICONS: Record<TaskStatus, string> = { done: ICON_CHECK_CIRCLE, … };
export function TaskStatusIcon({ status }: { status: TaskStatus }) {
  return Raw(TASK_STATUS_ICONS[status]);
}
```

And in `mngmt/src/changelog/changelog.view.ts:293-300`, same pattern for `ChangeType` → SVG string mapping (6 icon strings).

## Evidence

- `rideshare/src/shared/components/layout.view.ts:171-216` — 14 named icon functions (`SearchIcon`, `BookmarkIcon`, `PlusCircleIcon`, `UsersIcon`, `LogoutIcon`, `DashboardIcon`, `CalendarIcon`, `UserIcon`, `CarIcon`, `LeafIcon`, `ChartIcon`, `GearIcon`) all returning `Raw("<svg>…")` strings.
- `jt-cut/src/projects/v2/views/v2.components.ts:34-116` — `SvgIcon16(d)` helper + 12 named icon exports.
- `jt-cut/src/shared/components/ui.components.ts:372-380` — second `SvgIcon(d)` helper (different size, different stroke width) in the same codebase.
- `mngmt/src/shared/icons.ts:14-49` — 6 icon functions (`IconGrid`, `IconTable`, `IconClipboard`, `IconDocumentText`, `IconChartBar`, `IconGear`) using fluent `Svg(Path(…)).apply(icon)`, requiring an eslint-disable for `setStrokeWidth`.
- `mngmt/src/dashboard/dashboard.components.ts:25-33` — 8 raw SVG string constants, consumed via `Raw(string)`.
- `mngmt/src/changelog/changelog.view.ts:293-300` — 6 more SVG string constants keyed by change type.
- Recon (`02-app-patterns.md:§5.4`) counts 72 `Raw()` in jt-cut, 31 in rideshare, 30 in mngmt.

## Why it matters

Five apps independently reinvent icon delivery, producing three incompatible strategies: raw HTML strings, `Raw("<svg>…")` wrappers, and path-string helpers. None are resizable or thenable without string manipulation. The `Raw()` paths bypass the fluent-html escape/safety layer and embed Tailwind class strings (`class="w-4 h-4"`) inside untyped strings, silently breaking Tailwind extraction and the ESLint plugin. Path-string helpers improve on this but still require each team to copy-paste SVG `d` attributes from design tools and write their own sizing boilerplate.

## Rough idea

`Icon("name", { size?, stroke?, fill?, className? })` backed by a bundled minimal set (Heroicons outline, ~24 common icons) plus a user-level `registerIcon(name, svgPaths)` API that avoids bundling a full icon lib as a runtime dependency (guardrail: zero-deps). The fluent `Svg`/`Path` API already exists and is the correct implementation layer — the gap is just a named registry and a standard call site. Tailwind sizing would use fluent `.w()`/`.h()` on the returned `SvgTag`, not embedded `class=` strings.
