# `.behavior('toggle')` loses the flex/hidden dual-class dance needed by modals and drawers

## Problem

The built-in `toggle` behavior emits:

```ts
// fluent-html/src/core/behavior-methods.ts:47-49
toggle: (opts) => [
  "click",
  `${el(opts.target)}.classList.toggle('hidden')`,
],
```

It only toggles `hidden`. Modals and drawers built with Tailwind require **two simultaneous class changes**: removing `hidden` AND adding `flex` to make the backdrop center its content (`display: flex; align-items: center; justify-content: center`). If only `hidden` is toggled, the flex layout is stranded or absent.

Because `.behavior("toggle")` cannot express this two-step, pps re-invented the operation as raw JS string helpers — **and exported them as part of the public display API**:

```ts
// planet-positive-sport/src/shared/components/display/modal.ts:41-51
export function closeModalJs(id: string): string {
  return `document.getElementById('${id}').classList.add('hidden'); document.getElementById('${id}').classList.remove('flex')`;
}

export function showModalJs(id: string): string {
  return `document.getElementById('${id}').classList.remove('hidden'); document.getElementById('${id}').classList.add('flex')`;
}
```

The same pattern re-appears independently in **four more source locations** — each is a standalone re-derivation of the same string, not imported from modal.ts:

```ts
// planet-positive-sport/src/loc/assessment/assessment.components.ts:478
return `document.getElementById('${id}').classList.add('hidden'); document.getElementById('${id}').classList.remove('flex')`;

// planet-positive-sport/src/loc/events/views/event-overview/collaborators-strip.component.ts:21-22
function showModal(id: string) {
  return `document.getElementById('${id}').classList.remove('hidden'); document.getElementById('${id}').classList.add('flex')`;
}

// planet-positive-sport/src/expert/views/pending-assignment.card.ts:21-26
function showModal(id: string) { ... }
function closeModal(id: string) { ... }
```

The Drawer component has the same problem with `openDrawerExpr`/`closeDrawerExpr`:

```ts
// planet-positive-sport/src/shared/components/display/drawer.ts:70-76
export function openDrawerExpr(id: string): string {
  return `document.getElementById('${id}').classList.remove('hidden');`;
}
export function closeDrawerExpr(id: string): string {
  return `document.getElementById('${id}').classList.add('hidden');`;
}
```

The pps `Modal` component's own doc comment says "toggle visibility via HTMX or `.behavior('toggle')`" (`modal.ts:56`) — but every single actual call site uses `closeModalJs`/`showModalJs` strings because `toggle` is wrong for this case.

## Evidence

- `planet-positive-sport/src/shared/components/display/modal.ts:41-51` — `closeModalJs`/`showModalJs` as exported string helpers, used instead of `.behavior("toggle")`
- `planet-positive-sport/src/shared/components/display/modal.ts:56` — misleading comment still suggests `.behavior("toggle")` is viable
- `planet-positive-sport/src/shared/components/display/modal.ts:67, 80` — two `addAttribute("hx-on:click", closeJs)` inside the Modal component itself
- `planet-positive-sport/src/loc/assessment/assessment.components.ts:478, 816` — re-derived `closeModal`/`showModal` strings
- `planet-positive-sport/src/loc/events/views/event-overview/collaborators-strip.component.ts:21-22` — yet another local `showModal` string function
- `planet-positive-sport/src/expert/views/pending-assignment.card.ts:21-26` — another independent pair
- `planet-positive-sport/src/admin/organizations/organizations.detail.view.ts:66` — `toggleHidden` (single-class only, same root cause)
- `planet-positive-sport/src/admin/organizations/organizations.view.ts:72` — `toggleHidden` again

## Why it matters

This is the most concrete proof that `.behavior()` falls short for the #3 seed item (Modal). Every modal call site in the largest app uses raw JS instead of `.behavior()` — not from ignorance, but because the library's toggle is semantically wrong. The guideline says "never raw inline JS; use `.behavior()`" but the built-in behavior cannot do what modals need. The mismatch makes the guideline unenforceable.

Five independent re-derivations across one codebase, plus a comment in the library-level `Modal` component that actively mis-states the recommended approach — this is a high-frequency, high-pain gap.

## Rough idea (not a design)

Add `behavior("openModal", { target: Id })` and `behavior("closeModal", { target: Id })` that emit the correct two-class swap atomically. The `toggle` behavior should be extended or replaced with a multi-class variant. A separate `behavior("openDrawer"/"closeDrawer")` may or may not be needed if a generic "swap classes" behavior can be parameterized. The `Modal` component in the library should accept an `Id` and wire its own close buttons internally.
