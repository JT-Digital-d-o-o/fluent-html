# Icons stored as raw SVG HTML strings — type erosion and silent Tailwind breakage

## Problem

In `mngmt`, icons are stored as raw `string` SVG literals and injected via `Raw()`. This is a more severe anti-pattern than the per-function `Raw("<svg>")` approach because it creates a **`string` type that is silently accepted everywhere a `string` is valid**, making it impossible to distinguish SVG icon strings from other strings at the type level. Tailwind classes embedded inside those strings (`class="w-4 h-4 text-accent shrink-0"`) are invisible to the fluent-html Tailwind extractor, producing dead CSS or missing classes.

```ts
// mngmt/src/dashboard/dashboard.components.ts:25-33
const ICON_CHECK_CIRCLE = '<svg class="w-4 h-4 text-accent shrink-0" fill="none" stroke="currentColor" stroke-width="2" viewBox="0 0 24 24">…</svg>';
const ICON_CLOCK        = '<svg class="w-4 h-4 text-accent/60 shrink-0" …>';
const ICON_REVIEW       = '<svg class="w-4 h-4 text-purple-400 shrink-0" …>';
const ICON_CANCELLED    = '<svg class="w-4 h-4 text-slate-500 shrink-0" …>';
const ICON_REFRESH      = '<svg class="w-4 h-4" …>';
const ICON_BACK         = '<svg class="w-5 h-5" …>';
```

These are typed `string` and consumed:

```ts
// mngmt/src/dashboard/dashboard.components.ts:68-78
const TASK_STATUS_ICONS: Record<TaskStatus, string> = {
  done: ICON_CHECK_CIRCLE,
  in_progress: ICON_CLOCK,
  review: ICON_REVIEW,
  todo: ICON_EMPTY_CIRCLE,
  cancelled: ICON_CANCELLED,
};

export function TaskStatusIcon({ status }: { status: TaskStatus }) {
  return Raw(TASK_STATUS_ICONS[status]);   // ← unescaped raw HTML injection
}
```

The changelog uses the same pattern with a `Partial<Record<ChangeType, string>>` map:

```ts
// mngmt/src/changelog/changelog.view.ts:293-308
const SECTION_ICONS: Partial<Record<ChangeType, string>> = {
  task_completed: '<svg class="w-4 h-4 text-emerald-400" …>',
  task_started:   '<svg class="w-4 h-4 text-blue-400" …>',
  // …
};
// later:
IfThen(icon, (i) => Raw(i)),    // icon: string — no type narrowing possible
```

And in a button helper:
```ts
// mngmt/src/dashboard/dashboard.components.ts:137-139
export function GhostButton({ label, icon }: { label: string; icon?: string }): View {
  …
  IfThen(icon, (i) => Raw(i)),
```

## Evidence

- `mngmt/src/dashboard/dashboard.components.ts:25-33` — 8 SVG string constants, typed `string`.
- `mngmt/src/changelog/changelog.view.ts:293-300` — 6 SVG string constants in a `Partial<Record<ChangeType, string>>`.
- `mngmt/src/dashboard/dashboard.components.ts:68-78` — `TaskStatusIcon` accepts `status: TaskStatus` and does `Raw(string)`.
- `mngmt/src/dashboard/dashboard.components.ts:137-139` — `GhostButton` accepts `icon?: string` and does `Raw(i)`.

## Why it matters

The `icon?: string` prop signature in `GhostButton` is the most pernicious manifestation: any caller passing an arbitrary string (including user content) would trigger `Raw()` injection. The correct type for an icon slot is `View`, not `string`. Additionally, the Tailwind classes embedded in the SVG literal strings (`w-4 h-4 text-accent shrink-0`, `text-purple-400`, etc.) are invisible to the fluent-html extractor, meaning they must be safelisted separately — a maintenance burden that will silently break when classes are renamed. This is a distinct problem from F-B-041 (the missing registry): even with a registry, the `icon?: string` API surface would be a bug that the library should prevent.

## Rough idea

The library (or its ESLint plugin) should reject `icon: string` as an icon prop type and enforce `icon: View`. The existing `prefer-set-method` ESLint rule already flags adjacent `addAttribute` misuse — a companion rule `no-raw-icon-string` could flag `Raw(stringVariable)` when the variable matches an SVG-literal pattern. Separately, a typed `IconView` branded type would make icon slots statically distinct from plain strings.
