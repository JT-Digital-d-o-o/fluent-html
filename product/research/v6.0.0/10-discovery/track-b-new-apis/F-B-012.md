# `Pagination` helper reimplemented in 5 apps; caller must always provide a full `renderPageLink` callback

## Problem

A `Pagination` helper is independently defined in at least five apps (jt-cut, glimm, storysell-ai, rideshare, mngmt). The component surface is always the same — `{ page, totalPages, renderPageLink }` — but the caller must supply a `renderPageLink: (page, label) => View` callback that manually constructs an HTMX-aware anchor. Because the library has no built-in pagination primitive, each app's `renderPageLink` body is near-identical boilerplate building a `setHtmx(route(...))` anchor with the same options.

## Evidence

Every app's `Pagination` component requires a `renderPageLink` callback:

```ts
// storysell-ai/src/shared/components/ui.data.components.ts:104-125
type PaginationProps = {
  page: number;
  totalPages: number;
  renderPageLink: (page: number, label: string) => View;
};
export function Pagination({ page, totalPages, renderPageLink }: PaginationProps) {
  return IfThen(totalPages > 1, () =>
    Div(
      IfThen(page > 1, () => renderPageLink(page - 1, "← Previous")),
      Span(`Page ${page} of ${totalPages}`).textSize("sm").textColor("gray-600"),
      IfThen(page < totalPages, () => renderPageLink(page + 1, "Next →")),
    ).flex().justifyContent("center").alignItems("center").gap("4").margin("t", "6")
  );
}
```

This same function body is copy-pasted verbatim across glimm, jt-cut, and storysell. The rideshare app doesn't even bother extracting a `Pagination` helper — it inlines the three-part `Div(IfThen..., Span..., IfThen...)` pattern directly in the view:

```ts
// rideshare/src/analytics/views/events.view.ts:153-183
IfThen(totalPages > 1, () =>
  Div(
    IfThen(props.filters.page > 1, () =>
      A("← Previous")
        .setHtmx(analyticsRoutes.events({ query: { page: String(props.filters.page - 1) }, ... }))
        ...
    ),
    Span(`Page ${props.filters.page} of ${totalPages}`).textSize("sm").textColor("body"),
    IfThen(props.filters.page < totalPages, () =>
      A("Next →")
        .setHtmx(analyticsRoutes.events({ query: { page: String(props.filters.page + 1) }, ... }))
        ...
    ),
  )...
)
```

The `renderPageLink` callback approach also forces every call site to re-pass the HTMX route ref, target, swap options, and indicator id — making the callback expand to 5–10 lines at each usage (see [[F-B-013]] for the sort/filter param forwarding complication that happens in the same callbacks).

## Why it matters

Five separate re-implementations of the same 20-line component. The existing helper interface (`renderPageLink` callback) leaks the link-construction concern back to the caller, preventing the helper from being a clean primitive. Any app that needs to preserve sort/filter params alongside page changes must manually reconstruct the full `vals` object inside the callback. The result is 5–10 lines of boilerplate per paginated table (see F-B-013 for details). Total frequency across all 5 apps: approx 20 `Pagination(...)` call sites.

## Rough idea

A built-in `Pagination({ route, page, totalPages, extraVals? })` that accepts a route ref directly and internally sets `vals: { ...extraVals, page: String(n) }`, removing the `renderPageLink` callback entirely. The HTMX anchor style (target, swap, indicator) could be configured via a context (e.g. a `PaginationContext`) or per call-site option. This maps naturally to `defineRoutes` — the same route used to render the page is passed to `Pagination` to build its links.
