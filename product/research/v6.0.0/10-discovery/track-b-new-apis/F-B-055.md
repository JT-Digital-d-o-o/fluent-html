# requireAuth guard loses the intended URL in 3 of 4 apps

## Problem

When an unauthenticated user visits a protected route, the `requireAuth` preHandler guard should redirect to login while preserving the intended destination so the user is returned there after sign-in. Only rideshare does this; glimm, mngmt, and storysell-ai all redirect to a bare `/auth/login` with no returnTo, silently discarding the URL.

```ts
// rideshare/src/auth/auth.guards.ts:8  — CORRECT: preserves returnTo
function redirectToLogin(request: FastifyRequest, reply: FastifyReply) {
  return reply.redirect(authRoutes.login.resolve({ returnTo: request.url }));
}
export async function requireAuth(request: FastifyRequest, reply: FastifyReply) {
  if (!request.user) return redirectToLogin(request, reply);
}
```

```ts
// glimm/src/auth/auth.guards.ts:21  — WRONG: drops the URL
export async function requireAuth(request: FastifyRequest, reply: FastifyReply) {
  if (!request.user) return reply.redirect("/auth/login");
}

// mngmt/src/auth/auth.guards.ts:9  — WRONG: same
export async function requireAuth(request: FastifyRequest, reply: FastifyReply) {
  if (!request.user) return reply.redirect("/auth/login");
}

// storysell-ai/src/auth/auth.guards.ts:11  — WRONG: same
export async function requireAuth(request: FastifyRequest, reply: FastifyReply) {
  if (!request.user) return reply.redirect("/auth/login");
}
```

Additionally, rideshare ships a `safeReturnTo()` validator (`auth.return-to.ts:9-13`) that guards against open-redirect attacks by accepting only same-origin absolute paths. The other three apps have no such utility even if someone tried to add returnTo manually.

```ts
// rideshare/src/auth/auth.return-to.ts:9 — open-redirect guard (absent in glimm/mngmt/storysell)
export function safeReturnTo(raw: unknown): string | null {
  if (typeof raw !== "string" || raw.length === 0) return null;
  if (!raw.startsWith("/")) return null;
  if (raw.startsWith("//") || raw.startsWith("/\\")) return null;
  return raw;
}
```

## Evidence

- `rideshare/src/auth/auth.guards.ts:8-10`: `redirectToLogin` preserves `request.url` via `authRoutes.login.resolve({ returnTo: request.url })`
- `glimm/src/auth/auth.guards.ts:21`: `reply.redirect("/auth/login")` — no returnTo
- `mngmt/src/auth/auth.guards.ts:9`: `reply.redirect("/auth/login")` — no returnTo
- `storysell-ai/src/auth/auth.guards.ts:11`: `reply.redirect("/auth/login")` — no returnTo
- `rideshare/src/auth/auth.return-to.ts:9-13`: `safeReturnTo()` open-redirect guard, not present in other apps
- `rideshare/src/auth/auth.return-to.ts:37-43`: `consumeReturnTo()` that clears the cookie after use — also absent elsewhere

## Why it matters

This is a UX regression that happens silently because each app clones the guard without the returnTo logic (which lives separately in `auth.return-to.ts` — easy to miss). Users deep-linking to a protected page (e.g., from an email) land on the dashboard after login instead of their intended destination. The `safeReturnTo` guard is also a security requirement — without it, an app that tries to add returnTo manually could be vulnerable to open-redirect if the query param isn't validated.

## Rough idea (not a design)

Include `returnTo` preservation and `safeReturnTo` validation in the `createAuthPlugin` factory proposed by [[F-B-051]]. The guard emits `reply.redirect(loginPath + "?returnTo=" + encodeURIComponent(safeUrl))` by default, and `consumeReturnTo` is exported from the same factory result so controllers can redirect after login without hand-rolling the validation.
