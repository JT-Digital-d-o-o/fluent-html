# `TagAttrs` index signature `[key: string]: unknown` forces unsafe `as string` casts in every algebra

## Problem

`TagAttrs` carries an open index signature to hold element-specific attributes (`href`, `src`, `alt`, `type`, etc.) that were copied from the `Tag` instance by `extractAttrs`:

```ts
// src/fold/types.ts:7-15
export interface TagAttrs {
  id?: string;
  class?: string;
  style?: string;
  attributes: Record<string, string>;
  htmx?: HTMX;
  toggles?: string[];
  [key: string]: unknown;   // ← element-specific attrs (src, href, etc.)
}
```

Because `[key: string]: unknown` is the only mechanism for accessing element-specific fields, every algebra that reads them must cast unsafely:

```ts
// src/fold/algebras/links.ts:28-32
tag: (element, attrs: TagAttrs, childLinks) => {
  if (element === 'a' && attrs.href) {
    const linkInfo: LinkInfo = {
      href: attrs.href as string,    // ← `as string` cast — type unsafe
    };
    if (attrs.target) linkInfo.target = attrs.target as string;   // ← same
    if (attrs.rel)    linkInfo.rel    = attrs.rel    as string;   // ← same
```

```ts
// src/fold/algebras/aria-describe.ts:26-41
if (element === 'a' && attrs.href) {
  // attrs.href is `unknown` — must cast
  return `link '${text}' (href: ${attrs.href})`;  // toString() coercion, not a cast, but still unsafe
}
if (element === 'img') {
  const alt = attrs.alt ?? attrs.attributes?.alt;  // ← `attrs.alt` is `unknown`
  return alt ? `image '${alt}'` : "image (no alt)";
}
if (element === 'input') {
  const type = attrs.type ?? attrs.attributes?.type ?? "text";  // ← `attrs.type` is `unknown`
```

TypeScript cannot enforce that `attrs.href` is a string when accessed via an index signature — it is `unknown`. The casts silence the type checker but do not prevent a runtime error if `extractAttrs` ever copies a non-string value under `href`.

## Evidence

`src/fold/types.ts:14` — `[key: string]: unknown` is the only way to access `href`, `src`, `alt`, `type`, `colspan`, `rowspan`, `action`, `method`, and any other element-specific field.

`src/fold/algebras/links.ts:28-32` — three `as string` casts in the `tag` callback for `href`, `target`, `rel`.

`src/fold/algebras/aria-describe.ts:33-41` — accesses `attrs.alt`, `attrs.type` as `unknown`; `attrs.alt` is used directly in template literal coercion (implicit `toString()`, fails silently if a non-string value is stored).

`src/fold/algebras/render.ts:23-30` — iterates `Object.entries(attrs)` to emit element-specific attrs, but skips the known keys manually. The open index signature means any non-string value that slipped in through `extractAttrs` is stringified as `"[object Object]"` or similar without a type error.

## Why it matters

Every author of a custom algebra must write `attrs.href as string` instead of getting a typed field. This violates the library's "type-safety first" guardrail (§11.4) for the fold API surface. A future element subclass that stores a numeric attr (e.g. `colspan: 3` as a `number`) would silently produce `"3"` in some paths and a runtime error in others, depending on which cast path is reached. Three of the five shipped algebras already contain unsafe casts because of this design.

## Rough idea (not a design)

Options for Wave 2 to evaluate:

1. **Typed accessor on `TagAttrs`** — add `getAttr(key: string): string | undefined` that reads from either the index signature or `attributes`, with a typed return; algebras call `attrs.getAttr('href')` and get `string | undefined` without a cast.
2. **Element-specific `TagAttrs` subtypes** — `AnchorAttrs extends TagAttrs { href?: string; target?: string; rel?: string }`, etc.; algebras narrow via `element === 'a'` then cast the whole `attrs` to `AnchorAttrs`. More type-safe but verbose.
3. **Remove the index signature; move extra fields into `attributes: Record<string, string>`** — then the `attributes` map is always `string`-valued and `extractAttrs` coerces to string on the way in. Simpler typing; loses the distinction between schema-key attrs and custom attrs.
