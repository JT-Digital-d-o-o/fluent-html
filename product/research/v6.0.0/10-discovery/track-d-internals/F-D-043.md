# `linksAlgebra` uses `[linkInfo, ...childLinks]` spread per anchor — O(n²) accumulation

## Problem

`linksAlgebra` collects all `<a>` links from a `View` tree. Its `tag` callback prepends each found link with a spread:

```ts
// src/fold/algebras/links.ts:28-38
tag: (element, attrs: TagAttrs, childLinks) => {
  if (element === 'a' && attrs.href) {
    const linkInfo: LinkInfo = {
      href: attrs.href as string,
    };
    if (attrs.target) linkInfo.target = attrs.target as string;
    if (attrs.rel) linkInfo.rel = attrs.rel as string;
    return [linkInfo, ...childLinks];   // ← O(n) spread per found link
  }
  return childLinks;
},
list: (linkArrays) => linkArrays.flat(),  // ← O(n) flat per list node
```

Each `[linkInfo, ...childLinks]` spread copies the entire `childLinks` array into a new array. For a tree with `L` links, the total work is O(1 + 2 + ... + L) = **O(L²)** array copying, plus `linkArrays.flat()` does another O(n) copy at every list node. In a nav with 50 links this is ~1250 element-copies instead of 50.

## Evidence

`src/fold/algebras/links.ts:34` — `return [linkInfo, ...childLinks]` is called for every `<a>` element. On a page with a main nav (20 links), footer (15 links), and sidebar (10 links), a single `foldView(linksAlgebra, page)` performs ~(20²+15²+10²)/2 ≈ ~462 element copies instead of 45.

`src/fold/algebras/links.ts:38` — `linkArrays.flat()` also allocates a new array for every array node in the tree, compounding the allocation count.

## Why it matters

`linksAlgebra` is an exported public API, intended for accessibility auditing and link extraction over full-page views. The quadratic behavior is invisible until the page grows. A navigation-heavy SSR page (e.g. a site with breadcrumbs + nav + footer) easily has 50–100 links. The correct pattern — a single mutable accumulator array threaded through the fold — is O(L) with one final allocation.

This also sets a bad example for users writing custom algebras by copying the existing ones.

## Rough idea (not a design)

Use a shared accumulator instead of per-link spreading:

```ts
// Collect into a shared array via the list callback
export const linksAlgebra: ViewAlgebra<LinkInfo[]> = {
  text: () => [],
  raw: () => [],
  tag: (element, attrs, childLinks) => {
    if (element === 'a' && attrs.href) {
      // push into the already-accumulated child array instead of prepending
      childLinks.push({ href: attrs.href as string });
      return childLinks;
    }
    return childLinks;
  },
  list: (linkArrays) => {
    // merge multiple arrays into the first to avoid O(n) flat allocation
    if (linkArrays.length === 0) return [];
    const result = linkArrays[0]!;
    for (let i = 1; i < linkArrays.length; i++) {
      for (const link of linkArrays[i]!) result.push(link);
    }
    return result;
  },
};
```

Note: this changes the order from DFS pre-order to DFS post-order for found links; if order matters, document it or preserve it with a different strategy.
