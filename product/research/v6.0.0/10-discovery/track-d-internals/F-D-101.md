# applyNonce permanently mutates Tag objects — subsequent render() calls emit stale nonce attributes

## Problem

`renderWithNonce` calls `applyNonce(view, nonce)` before rendering. `applyNonce` mutates every matching `<script>` and `<style>` tag in-place by calling `tag.setNonce(nonce)`, which writes `this.attributes['nonce'] = nonce` onto the Tag instance. The mutation is permanent — the Tag object is modified and never restored.

```ts
// src/render/render.ts:49-66
export function renderWithNonce(nonce: string, ...views: View[]): string {
  const view = views.length === 1 ? views[0]! : views;
  applyNonce(view, nonce);          // ← mutates view tree in place
  return renderImpl(view, false);
}

function applyNonce(view: View, nonce: string): void {
  if (isTag(view)) {
    if (NONCE_ELEMENTS.has(view.el)) {
      view.setNonce(nonce);         // ← permanently writes to view.attributes['nonce']
    }
    applyNonce(view.child, nonce);
  } else if (Array.isArray(view)) {
    for (let i = 0; i < view.length; i++) {
      applyNonce(view[i]!, nonce);
    }
  }
}
```

And `setNonce` (tag.ts:157-163):

```ts
setNonce(nonce: string): this {
  if (this.attributes === EMPTY_ATTRS) {
    this.attributes = Object.create(null) as Record<string, string>;
  }
  this.attributes['nonce'] = nonce;   // ← permanent write, no restore
  return this;
}
```

## Evidence

Any view tree passed to `renderWithNonce` will have its `<script>` and `<style>` tags permanently mutated. If that view tree is then passed to `render()` (or rendered again through any path), the nonce attribute will appear in the output even though no nonce was requested:

```ts
const page = Div(Script("console.log('hi')"), P("body"));
renderWithNonce("nonce-abc", page);
// page's Script tag now has attributes['nonce'] = 'nonce-abc' permanently

render(page);
// emits: <div><script nonce="nonce-abc">console.log('hi')</script>\n<p>body</p></div>
// ^^^ nonce appears in plain render() — WRONG
```

Calling `renderWithNonce` twice with different nonces on the same view results in the second nonce overwriting the first in the tag's attributes, but the first render output already captured the first nonce correctly. Any third call to `render()` emits the second nonce.

The planned `Frozen`/static-subtree hoisting API (tracked in existing findings) makes this worse: a static subtree containing `<script>` tags would be corrupted by the first `renderWithNonce` call across all subsequent renders.

## Why it matters

`renderWithNonce` is the library's only CSP support. Any application that:
- builds a layout/wrapper view once and reuses it across requests (the natural SSR pattern),
- or constructs a view tree for testing and then renders it multiple times,
- or applies nonces per-request to a shared partial,

will emit nonce attributes on every subsequent `render()` call after the first `renderWithNonce`. This is a security correctness bug: `render()` is supposed to produce deterministic output from the view tree, but the tree is now secretly stateful.

## Rough idea (not a design)

Thread the nonce as a parameter through `renderImpl` instead of pre-mutating the tree. When `renderImpl` emits a `<script>` or `<style>` tag, check if a nonce is present in the context and inject it into the attribute string at render time, without touching the Tag. This makes nonce application stateless and safe for shared views.
