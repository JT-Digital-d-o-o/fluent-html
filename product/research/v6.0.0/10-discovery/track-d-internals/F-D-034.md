# `renderToStream` is non-variadic — asymmetric API vs `render()` that accepts `...views` for multi-swap responses

## Problem

`render()` is variadic, accepting one or more `View` arguments. The multi-view case is used for HTMX partial / multi-swap responses (multiple `Partial()` elements):

```ts
// src/render/render.ts:33-35
export function render(...views: View[]): string {
  return renderImpl(views.length === 1 ? views[0]! : views, false);
}
```

`renderToStream()` accepts a single `View`:

```ts
// src/render/stream.ts:111-118
export function renderToStream(view: View): Readable {
  return new Readable({
    read() {
      streamImpl(this, view, false);
      this.push(null);
    },
  });
}
```

To use multi-swap streaming a caller must manually wrap the views in an array:

```ts
// Caller workaround required today:
renderToStream([
  Partial(ids.list, UserList(users)),
  Partial(ids.count, Span(`${users.length}`)),
])

// vs. render() which accepts them directly:
render(
  Partial(ids.list, UserList(users)),
  Partial(ids.count, Span(`${users.length}`)),
)
```

The workaround works because `View = Tag | string | RawString | View[]`, so a `View[]` is a valid `View`. But the call-site asymmetry is a DX friction point: developers who know `render()` is variadic and try `renderToStream(a, b)` get a TypeScript error because `renderToStream` only accepts one argument.

## Evidence

`src/render/render.ts:33-35` — variadic `...views: View[]` with `views.length === 1 ? views[0]! : views` normalization.

`src/render/stream.ts:111-118` — single `view: View` parameter, no normalization.

`src/index.ts:23-24` — both exported; the type signatures are visible to callers and the mismatch is part of the public API contract.

The HTMX multi-swap pattern (`render(Partial(...), Partial(...))`) is a first-class documented pattern (CLAUDE.md: "Multi-swap response"). Any developer migrating an existing multi-swap handler from `render()` to `renderToStream()` discovers the API difference only when TypeScript rejects the call.

## Why it matters

The inconsistency creates a stumbling block when porting handlers from string-based to streaming responses. It is also a sign of the underlying structural issue flagged in the seed backlog: `stream.ts` is a manual copy of `render.ts`, and both evolve independently. When `render()` was updated to be variadic, `renderToStream()` was not. The same drift risk applies to any future change to `render()`'s entry-point behavior.

This is a low-complexity fix (one-liner normalization matching what `render()` already does) but its value is in removing an observable asymmetry in the public API surface.

## Rough idea (not a design)

```ts
export function renderToStream(...views: View[]): Readable {
  const view = views.length === 1 ? views[0]! : views;
  return new Readable({
    read() {
      streamImpl(this, view, false);
      this.push(null);
    },
  });
}
```

This is a backward-compatible change (callers passing a single argument are unaffected).
