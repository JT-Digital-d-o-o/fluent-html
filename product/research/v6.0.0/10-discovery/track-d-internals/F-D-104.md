# behavior("toggleClass") injects opts.class into inline JS without escapeJs — JS injection if class name is user-controlled

## Problem

The `toggleClass` behavior renderer concatenates `opts.class` directly into a JavaScript string without calling `escapeJs`. If `opts.class` is derived from user input or dynamic data, a single quote (`'`) or backslash in the value breaks out of the JS string context and injects arbitrary code.

```ts
// src/core/behavior-methods.ts:51-54
toggleClass: (opts) => [
  "click",
  `${el(opts.target)}.classList.toggle('${String(opts.class)}')`,
  //                                      ^^^^^^^^^^^^^^^^  ← NOT escaped via escapeJs!
],
```

Compare with `clipboard`, which correctly calls `escapeJs`:

```ts
// src/core/behavior-methods.ts:59-62
clipboard: (opts) => [
  "click",
  `navigator.clipboard.writeText('${escapeJs(String(opts.value))}')`,
  //                                ^^^^^^^^^^^                   ← correctly escaped
],
```

The `escapeJs` function exists in the same file and handles exactly this case:

```ts
// src/core/behavior-methods.ts:85-87
function escapeJs(str: string): string {
  return str.replace(/\\/g, "\\\\").replace(/'/g, "\\'");
}
```

## Evidence

```ts
// Server-side: class name comes from a user-editable config or DB
const dynamicClass = "my-class'; alert(document.cookie); 'pwned";
Button("Toggle theme").behavior("toggleClass", {
  target: ids.panel,
  class: dynamicClass,   // ← class is string, not validated
});
// Renders hx-on:click attribute value:
//   document.getElementById('panel').classList.toggle('my-class'; alert(document.cookie); 'pwned')
//                                                                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//   JS injection — alert() fires on click
```

The `toggle`, `remove`, `focus`, and `scrollTo` behaviors use `el(opts.target)` which also lacks `escapeJs`:

```ts
// src/core/behavior-methods.ts:42-44
function el(value: unknown): string {
  return `document.getElementById('${resolveId(value)}')`;
  //                                 ^^^^^^^^^^^^^^^^  ← no escapeJs
}
```

However, `target` is typed as `Id` in `BehaviorMap` and `Id` values are produced by `defineIds`/`createId` from compile-time string literals, so in practice ID values are safe. `class` in `toggleClass` is typed as plain `string`, making it higher risk.

## Why it matters

Guardrail §11.3 requires escape-by-default with no XSS regressions. The `behavior()` system emits inline JavaScript via `hx-on:*` attributes. The library already has `escapeJs` for this purpose and uses it correctly in `clipboard`, but inconsistently omits it in `toggleClass`. Any application that derives the class name from external data (URL param, DB value, user preference label) is vulnerable to JS injection delivered via a trusted HTMX event handler. This bypasses the HTML-level XSS protection entirely.

## Rough idea (not a design)

Apply `escapeJs(String(opts.class))` in the `toggleClass` renderer. Audit every `renderers` entry for strings concatenated into backtick JS templates and ensure `escapeJs` is called on every user-controlled value. Add a test asserting that `behavior("toggleClass", { target: ids.x, class: "'; alert(1); '" })` does NOT produce executable JS in the rendered attribute.
