# Verdict: RFC-B-08 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's entire compatibility story rests on one sentence — *"Additive — nothing breaks."* — and on the `declare module "fastify"` block in the Proposed API. Both are false in a way the RFC does not mark.

- **Breaking failure mode 1 — the augmentation collision (killer).** The library does not own the `renderView` decorator. It is declared *per app*, in app-side code: `glimm/src/core/server.ts:122-127`, `storysell-ai/src/core/server.ts:149-153`, and every other app decorate their own `reply.renderView`/`renderStreamView` and ship their own `declare module "fastify" { interface FastifyReply { renderView(view?: View): FastifyReply } }`. TypeScript module augmentation **merges interface members across declarations**. If the library now also ships `declare module "fastify" { interface FastifyReply { renderView(view?: View, opts?: RenderViewOptions): FastifyReply } }` (which the Proposed API block literally writes, and the Open Question is "leaning exported helper" — i.e. shipping it), then any app that still has its old single-arg declaration gets **two incompatible declarations of the same property** in the merged `FastifyReply` — a `TS2717 Subsequent property declarations must have the same type` error. That is not additive; it is compile-time breakage with no codemod, triggered merely by upgrading the lib. The RFC's frontmatter says `breaking: additive` and the body says "No `breaking-changes.md` entry needed." Both are wrong under the leaning resolution of its own Open Question.

- **Breaking failure mode 2 — the manual augmentation edit is unmarked breakage even in the documentation-only path.** Suppose the lib stays documentation-only (the safer resolution). Then the *feature itself is unreachable* until each app hand-edits its existing augmentation from `renderView(view?: View)` to `renderView(view?: View, opts?: RenderViewOptions)`. That edit is not codemod-able (it lives in arbitrary app boilerplate, not at call sites) and is a precondition for every `{ code, reswap }` call site to typecheck. An app that runs the optional call-site codemod *before* updating its augmentation gets a wall of `TS2554 Expected 1 arguments, but got 2`. The RFC frames the augmentation change as a one-line freebie ("The decorator augmentation gains an optional 2nd param") and never lists it as a required migration step. This is the classic "guardrail drift — a breaking API sneaks in as additive" failure (ALGORITHM §13).

- **Breaking failure mode 3 — type narrowing breaks the advertised codemod.** The raw path being replaced accepts `string`: `reply.header("HX-Reswap", X)` and `hxResponse().reswap(strategy: HxSwapStyle | string)` (src/patterns.ts:289) both tolerate a runtime string. The replacement `RenderViewOptions.reswap?: HxSwap` does not. The RFC says the codemod is "Pure AST shape match; safe to auto-apply." It is not: any of the ~20 fleet sites where the swap value is a variable, a ternary, or a non-literal rewrites to non-compiling code. "Safe to auto-apply" is a false guarantee for a tool that can emit type errors.

- **Breaking failure mode 4 — internal type contradictions that void the advertised migrations.** Two of the RFC's own signatures don't match the source they cite: (a) `retarget: HxTarget` cannot accept an `Id` (src/htmx.ts:82 — `HxTarget` is string-only), yet the headline worked example passes `layoutIds.mainContent`; (b) `Deferred`'s `route.resolve: (query?) => string` excludes parameterized routes whose real resolve is `(params, query?) => string` (src/routes.ts:132-134). These aren't breaking to *existing* code, but they mean the advertised before→after migrations — the evidence that justifies the RFC — do not compile as written. The "win" is illusory until the types are fixed.

## Does it survive?

**survives-with-changes.** None of the four findings is an unfixable design flaw — the *direction* (typed HX-* options on `renderView`, the `.applyTo` bridge, an htmx-native `Deferred`) is sound and additive at the value level. But the RFC's central compatibility claim ("Additive — nothing breaks") is materially false because it ignores that `renderView` is an app-owned augmentation, and the proposed lib-shipped `declare module "fastify"` block would break every existing app on upgrade with a hard TS2717. The breakage is real but bounded and fixable by (1) keeping the augmentation app-side / documentation-only, (2) honestly marking the required manual augmentation edit, and (3) demoting the codemod and fixing the two contradictory option types. With those changes folded back, the RFC is honestly additive and ships. Without changes 1+2 it is a mis-marked breaking change and must be rejected under the default-reject rule.

## Guardrail check (§11.5 backward-compat — this lens owns it)

**Fails as written, passes with required changes.** §11.5 demands breaking changes be (a) codemod-able where possible, (b) bundled into one migration in `breaking-changes.md`, (c) justified. The RFC asserts §11.5 "pass — additive" in its own guardrail table; that assessment is incorrect given the app-owned augmentation. The augmentation edit is *not* codemod-able (req. change 2), so it must be written into `breaking-changes.md` rather than waved off with "No `breaking-changes.md` entry needed." Once the lib ships no `fastify` augmentation and the per-app edit is documented as a migration step, the change is honestly additive at the library boundary and §11.5 is satisfied.
