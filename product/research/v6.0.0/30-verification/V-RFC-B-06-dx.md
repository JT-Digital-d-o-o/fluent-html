# Verdict: RFC-B-06 — dx lens

> You are an ADVERSARY. Your job is to KILL this RFC through the dx lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC resolves a real, well-evidenced cluster (F-B-011..014), and the `TableState` single-source genuinely closes the F-B-013 silent-reset bug class — the load-bearing insight is correct. It is worth the surface area: the four primitives already exist, mis-typed, in 5+ apps, so this is net surface *reduction*, the rare case where a new API shrinks total boilerplate. So the attack is not "cut it." It is "the design is mis-typed against the library's own route system, and the teaching surface is not self-contained."

- **dx failure mode 1 — the `route` type breaks on the most common real route shape (killer).** The whole pitch is "pass `route` + `state`; links are built internally; no `renderPageLink`/`buildHtmx` callback" (lines 297, 391). But `route` is typed `(options?: RouteHxOptions) => HTMX` (lines 95, 122, 130). Per `src/routes.ts:145-150`, that structural shape is ONLY the **param-less** route callable. A route with a `:param` segment has the *different* callable signature `(params, options?) => HTMX` (`routes.ts:147`). Analytics/event tables live under nested resources constantly (`/projects/:id/events`, `/users/:id/sessions`); their route refs will NOT assign to `route`. The author's only escape is `route: (o) => analyticsRoutes.events({ id }, o)` — a wrapper lambda per table, which is exactly the per-call-site closure the RFC says it eliminates (Alternatives, line 391). The headline DX win silently regresses on the nested-route case, with no compile error pointing at the fix. For a library whose entire idiom is `defineRoutes` single-sourcing, mistyping against its own route callable is a first-order DX defect.

- **dx failure mode 2 — `state` is an optional that everything secretly requires (hard-to-misuse failure).** `TableOptions.state?` (line 97) is optional, yet (a) `totalPages` cannot render a pager without it and (b) every `sortBy` column cannot build a sort link without it. The type-safety story explicitly sells "discriminated absence, not optional bags" (line 255). But the dependency between `sortBy`/`totalPages` and `state` is undiscriminated: a column with `sortBy: "event"` and a forgotten `state` compiles and yields either a dead non-sortable header or a runtime throw. This is precisely the "bag of optionals" the project's TypeScript guideline forbids. The RFC asserts misuse is impossible ("Forgetting a filter is impossible", line 256) — true for filter-forwarding, false for the `state` wiring itself.

- **dx failure mode 3 — the taught example is not self-contained (adoption / §11.8 failure).** The canonical fluent-html.md and CLAUDE.md examples render `cell: e => Badge(e.category)` (lines 290, 321). `Badge` is not in this RFC's `api_surface`; it is a separate RFC's symbol. The single most-copied snippet — the one an LLM reader pastes — does not compile unless an unrelated RFC also ships. A flagship teaching example depending on an un-shipped symbol is an adoption failure by the guardrail's own logic (§11.8: an un-taught/un-compilable API is an un-adopted API).

- **dx failure mode 4 — competing idiom left standing.** `web-development/README.md:1679` already documents a generic `DataTable<T>(columns)` component. The new guideline section neither references nor retires it, leaving the LLM reader two table idioms with no ✗ steering it to the new one. Under-utilization (the `Match` 18:1 problem the algorithm explicitly flags) is the predicted outcome.

- **Naming / consistency (survives this sub-attack):** `Table.of(...)` as a static on the element function mirrors house idiom and leaves the element form untouched — good. `tableState`/`TableState<T>` factory+type split matches `formFor`/context conventions. `ThCell`/`TdCell`/`SortHeader`/`Pagination` are discoverable. `.withPage`/`.withSort` immutable-builder naming is idiomatic. The `TableThemeCtx.scope({...})` theming usage matches the verified `Context.scope(value): Disposable` signature (`src/control/context.ts:42`). No naming change required.

## Does it survive?

**survives-with-changes.** The concept is worth the surface area (a consolidation of existing mis-typed boilerplate — the rare case where new API reduces net surface), and naming/discoverability are right. But it ships two concrete DX defects — a `route` type that rejects the most common real route shape, and a `state` optional that everything covertly requires — plus a non-self-contained teaching surface. Under the default-reject posture I weighed rejecting on the route-type defect alone; it stays alive only because it is a type-signature correction, not a design rethink, and folds cleanly back into the RFC. The six `required_changes` are the exact edits.
