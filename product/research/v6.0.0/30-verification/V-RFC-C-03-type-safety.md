# Verdict: RFC-C-03 — type-safety lens

> ADVERSARY. Goal: kill RFC-C-03 through the type-safety failure mode. Default to reject under uncertainty.

## Attack

The RFC stakes its type-safety credibility on one sentence: *"`outlineHidden()` over `.outline("none")` … Removing `"none"`'s ambiguity is the type-level fix to a semantic trap."* I verified the proposed types against the live source. The claim does not hold, and the pattern of failure repeats across the whole surface.

- **Type-safety failure 1 — the headline fix is self-contradicted.** Current `TailwindOutline = "none" | "dashed" | "dotted" | "double"` (`tailwind-types.ts:165`). The RFC's proposed type is `"none" | "hidden" | "dashed" | "dotted" | "double"` (RFC line 103). It *keeps* `"none"` — so `.outline("none")`, the dangerous a11y-regressing call the entire RFC is built to eliminate, **still compiles**; it is caught only by ESLint, i.e. not "the type-level fix" the RFC advertises. Worse, it *adds* `"hidden"`, so `.outline("hidden")` now compiles too — the exact `outline("hidden")` overload the RFC's own Alternatives section says it rejected in favor of `outlineHidden()`. The result is two compilable ways to express v4-hidden plus the live trap, the opposite of "removing ambiguity." This is a credible killer on guardrail §11.4 (the RFC's claimed type-safety win is not delivered by the types it proposes).

- **Type-safety failure 2 — new slots are valid under the wrong target, ungated by type OR emit.** The RFC's central design decision is "additive at the type level … v4-only narrowing is enforced at emit time" (line 97, 203). But emit time does *not* enforce it. Under target `v3`, `.shadow("xs")` falls through `SHADOW_V4`-less path and emits `shadow-xs` — a class that does not exist in v3 → dead CSS, no warning. The RFC exists to kill silent dead classes (Problem §1); its own new slots reintroduce them, merely flipping the direction (v3→dead instead of v4→dead). A wrong call compiles *and* emits silently. The type system genuinely cannot express "valid only under target v4" with a process-global runtime flag — which is an argument the global-target design is itself in tension with type-safety, not a point in its favor.

- **Type-safety failure 3 — `(string & {})` neuters the literal unions the RFC leans on.** `TailwindGradientDirection` (proposed, line 105-108) keeps `(string & {})`. Adding `"45"|"90"|"135"|"180"` to a union already containing `(string & {})` collapses every literal into `string`: `.gradientTo("to-rrr")`, `.gradientTo("99")`, `.gradientTo("bogus")` all compile and all render dead. The typo'd-direction case is literally finding F-C-001. The type catches none of it. Same structural defect: `TailwindShadow` (`:81`) and `TailwindRingWidth` (`:144`) already contain `(string & {})`, so the RFC's claims that users "can't opt into the new scale without `(string & {})`" (line 38) and that `TailwindRingWidth` "lacks `3`" (line 46) as *type* problems are false — `.shadow("xs")` and `.ring("3")` already type-check today. The real (modest) benefit is autocomplete + an ESLint anchor, which the RFC overstates as a correctness gain.

- **Type-safety failure 4 — untyped cross-package target plumb.** Guardrail §11.7 requires all three packages to share the vocabulary; the RFC adds `ExtractorOptions.target` and an ESLint `settings` key. The ESLint plugin has *no* typed settings layer today (grep over `fluent-html-eslint-plugin/src` returned nothing). A bare `settings: { "@fluent-html/tailwind": { target: ... } }` is an `unknown` bag — `target: "v5"` or a typo is accepted silently, and the three packages can disagree without a single type or runtime error. That is a class-string-contract divergence the type system is supposed to prevent.

## Does it survive?

It survives **with changes**, not on a coin flip but because the underlying *engineering* (target switch + remap tables + dedicated `outlineHidden()` method) is sound and addresses real shipped breakage. What fails is the **type-safety story as written** — it claims wins the proposed types do not deliver, and it re-opens the silent-dead-class hole it set out to close. None of these are fatal to the approach; all are fixable by tightening the types and adding emit-time warnings. The six required changes above are the exact edits; the first two are non-negotiable (they are the difference between the RFC's stated goal and its proposed mechanism). If the authors decline to drop `"none"`/`"hidden"` from `TailwindOutline` and decline emit-time gating of the new slots, downgrade to **reject** — at that point the RFC ships a type-safety narrative it does not back, which under default-reject is worse than not shipping.

## Guardrail check (§11.4 type-safety)

Not cleanly passed as the RFC asserts (frontmatter `§11.4: pass`). Three concrete defects: (a) the headline `outline` fix is compilable-around, (b) new literal slots are valid under the wrong target with no type or emit guard, (c) `(string & {})` members make the "literal union" claims non-load-bearing for the gradient-direction typo case that motivates the RFC. Reclassify to **pass-with-required-changes**; fold the six changes back into the RFC and re-assert §11.4 only after `TailwindOutline` loses `"none"`/`"hidden"` and the emit branch warns on wrong-target slots.
