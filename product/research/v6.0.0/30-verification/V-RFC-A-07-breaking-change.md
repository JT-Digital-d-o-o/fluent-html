# Verdict: RFC-A-07 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

I hunted for hidden breakage: changed signatures, renamed/removed symbols, behavioral output changes, and anything that slips a break past the `additive` frontmatter. The most load-bearing sentence in the RFC is the Wave-4 merge note on line 151:

> "the emitted class strings … are all standard Tailwind utilities already in the extractor/eslint vocabulary … No new vocabulary; no Track-C change."

That sentence is false, and its falsity is the breaking change the RFC fails to mark.

- **Breaking-change failure mode 1 — the lib fix silently desyncs from the extractor (the killer).** The Tailwind extractor scans *source*, not rendered HTML, and builds the safelist by string-interpolating method args. Its transform handlers (`fluent-html-tailwind-extractor/src/index.ts:349-362`) carry the **identical broken interpolation** the RFC removes from the lib:

  ```js
  { methodName: "rotate",    generateClass: a => [`rotate-${a[0]}`] },              // .rotate("-45")        → "rotate--45"     ✗
  { methodName: "translate", generateClass: a => [`translate-${a[0]}-${a[1]}`] },   // .translate("y","-1")  → "translate-y--1"  ✗
  { methodName: "skewX",     generateClass: a => [`skew-x-${a[0]}`] },              // .skewX("-6")          → "skew-x--6"      ✗
  { methodName: "skewY",     generateClass: a => [`skew-y-${a[0]}`] },
  ```

  Today the runtime class (`translate-y--1`) and the safelisted class (`translate-y--1`) **agree** — both invalid, both no-op, but *consistent*. After a lib-only fix the runtime emits `-translate-y-1` while the extractor still safelists `translate-y--1`. They **diverge**. Tailwind generates CSS only for what the extractor outputs, so `-translate-y-1` gets **no rule** and the transform still renders nothing — only now the failure is split across two packages and harder to diagnose. The victims are real and live: `jt-cut/src/projects/views/projects.render.view.ts` (lines 268, 1322, 1384), `v2.components.ts:245`, `v2.export.view.ts` (202, 366), `home.pricing.view.ts` (283, 416), `home.use-cases.view.ts:80`, `home.hero.view.ts:660`, `rideshare/src/rides/views/create.view.ts:357` — all call `.translate("y", "-0.5"|"-px")` *today*. Shipping the lib fix without the lockstep extractor patch regresses every one, and **no codemod can fix it** because it is cross-package version coupling, not a call-site rewrite. This is exactly the guardrail-§11.7 violation §8 escalates past majority ("any un-rebutted guardrail killer").

- **Breaking-change failure mode 2 — the new surface is invisible to the toolchain.** The eleven zero-arg shortcuts (`absolute`, `fixed`, `inlineFlex`, `contents`, …) and `.neg(cls)` have **zero** extractor handlers (verified: grep for each name in `index.ts` returns nothing). An app that adopts `.fixed()` or `.neg("inset-px")` emits a valid runtime class the extractor never sees → never safelists → no CSS in a content-scanned build. The RFC sells these as "purely additive … no migration." They are additive to the *runtime* and silently broken in the *build*. The eslint rule `no-known-modifiers-in-setclass` (`fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:321-323`) keys on the *positive* patterns `translate-x-`/`translate-y-`/`rotate-`, so it cannot match the negative `-translate-y-1` it is meant to redirect — the very adoption push fails on the negative case.

- **Breaking-change failure mode 3 — undeclared type-surface change masquerading as "impl-only."** The RFC insists "signatures unchanged," "implementation-only," "no call-site re-types." For `translate` that holds — but only because `TailwindSpacing` ends in `(string & {})` (`tailwind-types.ts:16-19`), which admits any string (a separate type-safety hole). For `rotate`/`skew` it is **false**: `TailwindRotate` (`:148`) and `TailwindSkew` (`:234`) contain no negative members and no `(string & {})`, so `.rotate("-45")`/`.skewX("-6")` are compile errors today; the only path to `-45` is the `[${string}]` escape, and `"[-45]"` emits `rotate-[-45]` (signNeg leaves the `[`-leading value alone). To make the headline examples compile, the unions **must** be widened — an additive public type-surface change the RFC neither performs nor declares, and actively contradicts. A "fix" that does not type-check for half its target methods cannot ship under a `breaking: additive` label that claims the contract is unchanged.

- **Probed, NOT breaking — symbol collisions / renames.** Every proposed name (`absolute`, `relative`, `fixed`, `sticky`, `static`, `block`, `inline`, `inlineBlock`, `inlineFlex`, `inlineGrid`, `contents`) checked against `tag.ts`, `types.ts`, `tailwind-methods.ts`: no existing Tag method shadows any. `position()`/`display()` retained (`tailwind-methods.ts:459,469`) — no rename/removal. `.neg()` already exists (`:663`), only documented. `static` as a prototype/interface method name is legal (reserved-word restriction is class-body only). Genuinely additive on the symbol axis.

- **Probed, NOT breaking — arbitrary-value corruption & snapshot churn.** `.rotate("[-45deg]").startsWith("-")` is `false`, so signNeg passes it through unchanged — the `[`-guard holds. Existing transform tests all use positive values, so none change. No snapshot asserts a buggy `--` string. (Worth a pinned regression test — see required changes.)

## Does it survive?

**survives-with-changes.** I do not reject outright: the underlying defect is real and already shipped, the runtime fix is sound, `position()`/`display()` are correctly *kept*, and there is no source-level hard break (no rename, no removal, no signature *narrowing*). The breakage is not in the API contract — it is in the **build-pipeline coupling the RFC explicitly denies** (§11.7), plus an undeclared type-union widening. Both are fixable, both are mandatory, and both fold back cleanly into a single bundled lib+extractor+eslint migration. But shipped as written — lib-only, "additive, no Track-C change" — it is a net regression for ~13 live call-sites and an adoption trap for all new shortcut/`.neg()` callers. The additive claim does not stand on its own.

## Guardrail check (breaking-change owns §11.5; this attack turns on §11.7)

- **§11.5 backward-compat:** pass *only conditional on the required changes*. Source-level it is additive. But the blanket "nothing breaks / no breaking-changes.md entry" is wrong: one real behavioral output change (`translate` negative path), one undeclared type widening (`rotate`/`skew`), and one cross-package coupling break — all must be stated and migrated, not denied.
- **§11.7 class-string contract (the killer):** **fail as written.** The lib fix breaks string parity with the extractor for every negative transform, and the new shortcuts/`.neg()` are absent from the extractor entirely. The prior breaking-change pass asserted "no extractor/eslint change" without opening the extractor source; that is incorrect. Compliance requires the extractor + eslint patches to ship in the same migration (per §6 cross-track collision detection and the Wave-4 `_merge.md` `api_surface` scan). With those folded in, §11.7 passes — `-translate-y-1`, `inline-flex`, `contents` are standard utilities once *both* packages emit them.
