# Verdict: RFC-A-06 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

I verified every type claim in the RFC against the real source (`src/elements/document.ts`, `src/core/raw-string.ts`, `src/render/render.ts`, `src/core/tailwind-types.ts`). Four type failures, one of them a killer that targets the RFC's own raison d'être.

- **type-safety failure 1 — the central invariant is unenforced (KILLER).** The RFC's headline type-safety claim is that `Document()` returns `DocumentTag extends HtmlTag` so the root "stays chainable" *and* the doctype is guaranteed. But the proposed class is `export class DocumentTag extends HtmlTag {}` — an **empty** subclass. The existing `HtmlTag` (`document.ts:5-26`) has members `lang`/`dir`/`setLang`/`setDir`; `DocumentTag` adds nothing. Under TypeScript's structural typing two classes with identical public shape are **mutually assignable**. Concretely: `function Layout(): DocumentTag { return HTML(Head(), Body()).setLang("en"); }` compiles with no error, because `HTML()` returns `HtmlTag` which structurally satisfies `DocumentTag`. The doctype, however, is gated at runtime on the prototype `_doc` brand (the RFC's own design: "discriminated by `el === "html"` + an internal `_doc` brand on the prototype, same pattern as `_sk`"). `HtmlTag.prototype` has no `_doc`, so render emits `<html>` with **no `<!DOCTYPE html>`** — silently, with a green build. That is exactly the quirks-mode correctness bug F-A-041 exists to kill, now reachable through a type the RFC advertises as the fix. A wrong call compiles.

- **type-safety failure 2 — `StructuredData(data: Record<string, unknown>)` types in a runtime crash.** `unknown` values are not JSON-LD-serializable in general. `JSON.stringify` on a `BigInt` throws `TypeError`; on a circular object throws; `Date` serializes to an opaque ISO string (usually wrong for `@type`); functions and `undefined` are silently dropped, producing invalid structured data that fails Google's validator with no error anywhere. The render-side `sanitizeRawContent` (`render.ts:174-176`) only string-replaces `</script` — it does nothing about un-serializable input. The type promises "any object is fine"; the contract is "a JSON value." A type that admits inputs guaranteed to throw or silently corrupt is a type that fails to prevent misuse.

- **type-safety failure 3 — `Doctype(): RawString` is an untyped escape hatch wearing a trusted name.** `RawString` (`raw-string.ts:5-9`) is precisely `Raw()`'s return — the documented XSS bypass. The RFC asserts "no new type leaks; it is the library-trusted constant, not a user escape hatch," but the type system gives **zero** such guarantee: a `RawString` from `Doctype()` is indistinguishable from `Raw(userInput)`. Worse, returning a bare `View`-compatible `RawString` means nothing in the types stops `Document(Doctype(), Head(), Body())` (two doctypes emitted) or a stray `Doctype()` inside `Body()`. The "trusted constant" framing is prose, not type.

- **type-safety failure 4 — overstated `og:type` guarantee + over-wide shared props.** The `(string & {})` pattern (confirmed convention, `tailwind-types.ts:9`, `htmx.ts:150`) collapses the `type` union to `string` for any non-literal: `const t: string = req.query.type; SeoHead({ title, type: t })` compiles, so the "typos are compile errors" claim only holds for inline literals. Separately, one `SeoProps` feeds three functions that each read a different subset (`OgMeta` never reads `card`; `TwitterCard` never reads `canonical`/`type`/`siteName`), so callers can pass irrelevant typed fields with no signal — weak cohesion the types don't catch.

## Does it survive?

The killer (failure 1) is real and strikes the RFC's core promise, but it is **fixable with a one-line brand**, not a design dead-end — the rest of the design (literal unions for `card`, concrete `*Tag` returns, `setProperty` over `addAttribute`) is sound and genuinely improves type-safety over the 6-app copy-paste status quo. This is a `survives-with-changes`, not a reject: the API shape is correct, but three of its type signatures (`DocumentTag`, `StructuredData`, `Doctype`) must be tightened before they ship, or each lets a wrong call compile. The required changes above are exact and fold straight back into the Proposed-API and Type-safety-story sections.
