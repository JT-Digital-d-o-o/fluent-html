# Verdict: RFC-A-08 — breaking-change lens

> Adversary brief: kill RFC-A-08 by finding hidden breakage — changed signatures, renamed/removed symbols, behavioral output changes — that the RFC's `breaking: additive` / "nothing breaks" framing conceals.

## Attack

The RFC's migration section is one sentence repeated three ways: "Additive — nothing breaks", "No codemod required", "`breaking-changes.md`: no entry — additive." Two of the three coordinated changes do not honor that claim.

- **Breaking-change failure mode 1 — `escapeJs` is an output-affecting change to a tested public contract, mislabeled "internal no-op."** The RFC argues (line 193): *"The fix only adds escapes — any value that rendered correctly before still does."* This is false in two ways.
  1. `escapeJs` feeds `.behavior("clipboard", { value })` (`behavior-methods.ts:61`) and is the same family of rendering as `toggleClass`. `clipboard` values are explicitly user/db-derived (the RFC's own index example: `behavior("clipboard", { value: apiKey })`). A new `.replace(/</g, "\\x3C")` rewrites the **rendered byte output** for any clipboard value containing `<` (e.g. an API key, a code snippet, an XML token). The RFC's claim that the chain is "byte-stable except for the newly-handled chars" is self-contradicting: `<` *is* a newly-handled char, so output is NOT byte-stable for it. Existing apps that snapshot-test or diff their HTML output will see a diff.
  2. The library's own test pins the exact emitted string: `test/behavior.test.ts:31` asserts `hx-on:click="navigator.clipboard.writeText(&#39;sk-abc123&#39;)"`. Any value flowing through the new escaper that contains the affected chars changes this contract. The RFC ships a render-output change with **zero** acknowledgment that the existing behavior test suite encodes the old contract and must be updated in lockstep. "No call-site changes" is true; "nothing changes" is not — the *output* changes, which for an SSR library IS the product.

- **Breaking-change failure mode 2 — the `\x3C` escape is dead code that only causes drift.** `hx-on:*` attribute values are rendered through `escapeAttr` (`src/render/escape.ts:37`), which already escapes `<` → `&lt;`. There is no raw/unescaped sink for behavior JS in the render path. So the stated justification — *"neutralize `</script>` breakout in raw contexts"* (line 127) — describes a context that does not exist for this code. The line buys no safety and only mutates previously-stable output. A change whose sole effect is an unannounced output diff is the textbook hidden breakage this lens hunts.

- **Breaking-change failure mode 3 — silent functional regression from the event-separator guess.** The two new behaviors emit kebab `htmx:after-swap` (lines 102, 105). Every piece of cited real-world evidence uses the **colon** form: `rideshare/src/settings/settings.view.ts:260` and `:337` both use `hx-on:htmx:after:swap`. The RFC flags this in Open Questions and hand-waves it as "non-breaking, only autocomplete-affecting" because of `(string & {})`. That reasoning applies to `.hxOn` (where the user supplies the event), **not** to the behaviors (where the *library hard-codes* the separator). If htmx-4 canonical is colon and the library emits kebab, `formResetOnSwap` produces an `hx-on:htmx:after-swap` handler htmx never fires — a **silent no-op**. The "after" migration (line 145) would then be a regression versus the working `addAttribute` "before" it replaces. A behavior that renders but never executes is worse than the raw string it replaced, and `(string & {})` gives no compile-time or test-time protection against the wrong guess. This is unverified at design time and must be pinned before lock.

- **Breaking-change failure mode 4 — undeclared guideline-policy flip.** `htmx.md` rung 3 (line 252) reclassifies `addAttribute("hx-on:…", js)` from the index's prior "last resort, allowed" to "✗ do not use." By the RFC's own count, 127 call-sites across 12+ apps instantly become guideline/lint violations, and the migrating codemod is explicitly deferred to Wave-4 as "nice-to-have, optional" (line 195). So the rule flips to "violated everywhere" *before* the mechanical fix exists. That is a real (soft) breaking policy transition dressed as "additive."

## Does it survive?

**Survives-with-changes.** None of the four findings is fatal to the *idea* — `.hxOn` itself is genuinely additive (new method, new type, no renamed/removed symbol; I confirmed no existing `hxOn` symbol and no `htmx-on-*` files exist, so no collision). The `BehaviorMap` additions are additive (two new keys; `BehaviorMap` is publicly exported at `src/index.ts:332`, but adding union members to an object-type export does not break consumers). The breakage is concentrated in (a) an output-affecting "bug fix" sold as a no-op, (b) a dead escape that only causes drift, and (c) an unverified separator that can ship a silent no-op. All are fixable by honest labeling + one verification, so the RFC clears the bar — but only after the required changes fold back in. Default-reject is overridden because the core surface is sound and the defects are correctable without redesign.

The decisive correction is failure mode 1: the `escapeJs` change must be reclassified as behavioral/output-affecting and bundled with its test update and a `breaking-changes.md` note, not waved through. An SSR library's rendered string IS its contract; changing it silently is exactly the "behavioral change not codemod-able" this lens exists to catch.

## Guardrail check (§11.5 backward-compat)

- **API surface:** additive — verified no removed/renamed symbol; `.hxOn`, `HxOnEvent`, two `BehaviorMap` keys are all new. ✓
- **Output contract:** NOT preserved — `escapeJs` alters rendered bytes for `<`/`\n`/`\r`/U+2028/U+2029-bearing values flowing through `clipboard`/`toggleClass`. The RFC's "no entry — additive" verdict on `breaking-changes.md` is **wrong**; this is an output-behavioral change and must be recorded. ✗ until required change 1 applied.
- **Codemod/bundling (§11.5b):** the guideline policy flip (addAttribute → ✗) is not codemod-complete at ship; codemod deferred. Must be marked an accepted staged transition, not silent. ✗ until required change 4 applied.
