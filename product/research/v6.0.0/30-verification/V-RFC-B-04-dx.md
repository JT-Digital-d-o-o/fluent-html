# Verdict: RFC-B-04 — dx lens

> Adversary brief: kill this through the dx failure mode — is it worth the surface area, discoverable, consistent with idioms, hard to misuse, correctly taught?

## Attack

This RFC bundles SIX primitives (`Document`, `Container`/`.container`, `Shell`+`createLayoutContext`, `NavItem`/`SidebarNav`/`TabNav`, `LoadingBar`/`HtmxIndicatorStyles`/`.htmxIndicator`) into one L-effort change. The strongest two — `Document` and `.htmxIndicator()` — are clearly worth it and well-evidenced (13 hand-rolled doctypes, byte-identical copy-paste). But the bundle smuggles in two designs that are not hard-to-misuse — they are hard-to-use-CORRECTLY, and the RFC's own examples demonstrate the misuse.

- **dx failure mode 1 — NavItem fights the route-callable contract (the killer).** The library's `defineRoutes` ref is `(options?: RouteHxOptions) => HTMX` (`src/routes.ts:147`), where `target`, `swap`, and `pushUrl` are passed *into* the call: `rideRoutes.list({ target: ids.mainContent, swap: "outerMorph", pushUrl: true })`. The established, guideline-taught idiom (CLAUDE.md "Full layout navigation") is `A(...).setHtmx(route({ swap, target, pushUrl }))`. RFC-B-04's `NavItem` instead declares `route: () => HTMX` (a *zero-arg* thunk) **plus a parallel `target: Id` field**. This is internally incoherent: a `RouteCallable` invoked with no args returns a fully-built `HTMX` with no target — and NavItem has no way to retro-inject `target` into an already-constructed HTMX object. The worked example `route: () => hx(item.href)` (line 230) compounds it: `hx()` exists (`src/htmx.ts:292`) and takes options, so the natural call is `hx(href, { target })` — the thunk silently discards the `target` prop sitting right next to it. An app author reaching for the headline "stop reinventing nav items" primitive immediately hits an API that contradicts the one route-wiring pattern they already know. That is the opposite of discoverable-and-hard-to-misuse.

- **dx failure mode 2 — the Shell context example teaches a runtime-broken pattern.** Context scopes in this library are a synchronous stack disposed at block exit (`src/control/context.ts:35-42,77-85`; `using _ = ctx.scope(value)` releases when the enclosing function returns). Worked example #5 opens the scope `// in the app.preHandler` with the comment `// survives the sync render below`. It does not survive: the preHandler returns, the `using` disposes, and the later route handler's `Shell()` chrome read throws (`createRequiredContext` throws outside a scope — confirmed). The RFC's §5.5 note *admits* this and defers the real fix to RFC-B-06, yet leaves the broken example and ships the feature anyway. An LLM reader (the stated audience, §0.7) will copy the preHandler version because it is the concrete one. A primitive whose flagship example throws at runtime is an adoption failure, not a convenience.

- **dx failure mode 3 — redundant alias inflates surface.** `createLayoutContext<T>(name)` is openly "a thin alias for `createRequiredContext`" (Open Question #2). CLAUDE.md already teaches `createRequiredContext(name)` for "auth, request data" — exactly shell state. Two names for one function is precisely the "idea inflation / is this worth the surface area" failure §13 warns the dx lens to catch.

- **dx failure mode 4 — guideline edit drifts from house style and misses symbols.** The CLAUDE.md insert crams five concepts into one 14-line block (vs. the file's strict one-bold-rule-per-concept rhythm). `HtmxIndicatorStyles()` and `TabNav()` are in `api_surface` but get no ✓/✗ rule — §11.8 requires every added symbol be taught. The `Container` overload ✓/✗ and `Document`/`.htmxIndicator` rules ARE good and house-style-correct; the rot is concentrated in the Shell/Nav/index portions.

What survives cleanly: `Document` (real, repeated pain; F-B-104 lang fix is genuinely valuable and the `setLang("en")` guideline correction at fluent-html.md:177 is verified accurate), `Container`/`.container()` (the `projects-template` extraction is the strongest promote-to-builtin signal), `.htmxIndicator()` + `HtmxIndicatorStyles()` (kills a verified copy-paste and the exact `setClass("htmx-indicator")` anti-pattern), `LoadingBar`. These four would survive on their own.

## Does it survive?

**survives-with-changes.** The core value (Document/Container/indicator/LoadingBar) is real, well-evidenced, idiom-consistent, and correctly taught — too strong to reject outright. But two sub-designs (NavItem htmx wiring; Shell/context) ship APIs that the RFC's own examples misuse, and the guideline edit under-covers two symbols and over-stuffs the index. None of these is fatal to the cluster, but each is a concrete adoption landmine that must fold back before this is mergeable. The required changes above are the exact cuts: realign NavItem to the route-callable contract, fix-or-defer the Shell context story, drop the redundant alias, and bring the guideline edit to house style with full symbol coverage.

Confidence 0.74: high on the NavItem and Shell-example defects (verified against source), moderate that the right resolution is "amend" rather than "split the RFC and defer Shell" — a reviewer could reasonably push the Shell/context half to RFC-B-06 wholesale, which I offer as required-change 2b.

## Guardrail check (dx owns §11.8)

§11.8 guideline-sync: **fails as written.** `HtmxIndicatorStyles()` and `TabNav()` are in `api_surface` without a ✓/✗ rule; the CLAUDE.md index block violates the succinct-one-rule-per-concept house style; and the fluent-html.md Shell snippet, while textually correct ("in the render handler"), directly contradicts worked-example #5's broken preHandler version — a contradictory do/don't the §13 'orphaned API' mitigation is meant to prevent. Resolvable via required-changes 2/4/5; until then the guideline edit is not minimal, not fully covering, and not internally consistent.
