# Verdict: RFC-B-08 — perf lens

> ADVERSARY: kill this RFC through the perf lens. Default to reject under uncertainty.

## Attack

The RFC splits cleanly: **Part 1/2 (renderView opts + applyTo) are perf-inert; Part 3 (Deferred + renderStreamView) is perf-fraudulent as written.** I attack Part 3.

- **Perf failure mode 1 — the headline benefit does not exist against the shipping code.** Part 3 sells `renderStreamView` as "the shell flushes immediately while the deferred region resolves in a 2nd request" (RFC lines 95, 109, 172). But the shipping `renderToStream` (`src/render/stream.ts:111-117`) is **eager**: `read()` calls `streamImpl(this, view, false)` which walks the *entire* tree synchronously, `push`-ing every chunk into the Readable's internal buffer in one tick, then immediately `this.push(null)`. Recon confirms this verbatim (04 §1.4: "The entire tree is walked synchronously inside one `read()` call... not backpressure-aware and not incremental: it materializes all chunks eagerly... No async children, no await, no flush points tied to I/O readiness"). Consequence: `renderStreamView(DashboardPage({ statsSlot: Deferred(...) }))` has **byte-for-byte identical flush timing to `renderView`** — the shell does NOT reach the socket any earlier. The *only* real saving is that `prisma.heavyAggregate()` moves to a second HTTP round-trip — a *round-trip-deferral* win that is fully available under plain synchronous `renderView`. The "streaming" framing markets a capability that needs Track-D's unbuilt incremental-streaming RFC. Shipping a feature whose named benefit depends on non-existent work is exactly the false-positive the quorum rule (§8) and guardrail §11.2 exist to stop.

- **Perf failure mode 2 — it entrenches a divergent, slower serializer before de-dup.** `streamImpl` (`stream.ts:120-194`) is a near-verbatim copy of `renderImpl` (recon 04 §1.4, Track-D's "dedupe render/stream into shared emitter" finding, ~70-line copy). Today `renderStreamView` has **zero call sites** (the RFC's own F-B-074), so the divergent copy is dead and harmless. Part 3 deliberately resurrects it ("give renderStreamView a reason to exist"). That re-activates a second serializer on the perf-critical path — one that the per-tick eager-push pattern makes *strictly worse* than `renderView` for the common case (Readable buffering overhead, no `+=` accumulation) — and locks in the duplication right before Track-D wants to collapse it. We would be adding adoption pressure to the slower of two divergent emitters at the exact moment we should be retiring one.

- **Perf non-issue (cleared) — Part 1/2 and the synchronous hot path.** `applyHxOptions` early-returns on `!opts` (`fastify-helpers.ts`, RFC line 70), so the 80% `renderView(view)` call pays nothing. The opts branch is a handful of `header()` string writes — synchronous, no allocation beyond strings the raw-header path already wrote. `Deferred()` emits a single static placeholder Tag built from a `route.resolve()` string — no async, no per-render closure, no new Tag field, no construction-allocation regression (it does not touch the `_variantPrefix`/monomorphic-shape concerns from Track-D #4). `JSON.stringify(trigger)` runs only when a `trigger` object is passed. None of this enters the synchronous render loop. Guardrail §11.2's letter is met for Parts 1/2 — but the invariant must be written down (see required changes).

## Does it survive?

**survives-with-changes.** The perf risk is concentrated entirely in Part 3's *framing*, not its mechanism. The mechanism (a 2nd-round-trip lazy slot emitting a static placeholder) is genuinely cheap and hot-path-safe. The defect is that the RFC dresses a round-trip-deferral primitive as early-flush streaming and pins it to a dead, eager, divergent `renderStreamView` whose perf benefit is vaporware until a separate Track-D RFC lands. Required fixes: (1) drop the early-flush claim, reframe Deferred as round-trip deferral; (2) decouple Deferred from renderStreamView so it works under plain `renderView` (eliminating the dead-export dependency); (3) add `depends_on` on the Track-D incremental-streaming RFC if the streaming claim is kept at all; (4) write the zero-cost-when-opts-absent invariant explicitly; (5) keep Deferred Promise-free and fully-materialized; (6) gate renderStreamView resurrection behind the render/stream de-dup so we don't entrench the slower divergent emitter. With these, Part 3 carries no hot-path risk and makes no false perf promise. Below the kill bar only because Parts 1/2 are clean and the Part-3 mechanism is salvageable by reframing — not by rebuilding.

## Guardrail check (perf owns §11.2)

- **Synchronous hot path untouched (Parts 1/2):** PASS in mechanism. `renderView(view)` with no opts is byte-identical; `applyHxOptions` early-returns; no new Tag field or per-request allocation; nothing enters the render loop. Must be stated as an explicit invariant in the RFC.
- **Async is opt-in:** PASS. `Deferred()` is synchronous (static placeholder); no Promise enters the View union or the render walk. The rejected "Suspense-that-awaits-in-render" alternative (RFC line 304) was correctly cut for this exact reason.
- **"Track D owns the proof" (RFC §11.2 self-check, line 292):** FAILS as written. The RFC offloads the streaming perf proof to Track D while simultaneously *asserting* the streaming benefit in its worked examples. §11.2 requires the async/streaming benefit to be real and proven, not borrowed from unbuilt work. This is the core required change: either prove it (depend on the incremental-streaming RFC) or stop claiming it (round-trip-deferral framing).
