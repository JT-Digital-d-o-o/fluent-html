# Verdict: RFC-A-05 — dx lens

> Adversary brief: kill RFC-A-05 through the dx failure mode. Is it worth the surface area? Discoverable, idiom-consistent, hard to misuse? Would an app author reach for it? Is the naming right? Audit the Guidelines impact for §11.8 completeness and house style.

## Attack

The underlying *problem* is real and I verified it against source: `src/control/context.ts:77-85` and `:121-129` are both bare `stack.push(value)` / `stack.pop()`, and the error string at `:116` is exactly the leak-steering message the RFC quotes — `Wrap the call in ${name}.scope(value)` with no `using`. The unsafe `onRequest`-scope / `onResponse`-dispose pattern, the template propagation, and every before/after line citation check out. So this is not a "not worth the surface" kill. The dx kill is sharper and narrower: **the surface is right in spirit but mis-shaped at its single most-used entry point, half-undecided, and under-taught against its own api_surface.**

- **dx failure mode 1 — the flagship signature fights the library's own #1 idiom.** `renderWithScopes(bindings: readonly ScopeBinding[], ...views: View[])` leads with an array immediately in front of variadic children. CLAUDE.md rule one is "Variadic children — never wrap in arrays: `Div(H1(), P())` ✓ / `Div([H1(), P()])` ✗." A `View` is itself allowed to be an array (`render(...views: View[])` plus the `Array.isArray(view)` branch — confirmed `render/render.ts:34,61`). So a reader who internalized the idiom reads the leading bindings array as a wrapped child — the exact anti-pattern. Hard-to-misuse failure: `renderWithScopes([], Page())` is pure noise for the no-context case, and `renderWithScopes([Page()])` (forgot bindings, passed the view as the bindings array) is a plausible typo. This is the symbol apps will touch most, and it's the weakest point on the surface.

- **dx failure mode 2 — `update()` ships undecided.** The RFC's own Open Questions ask whether `update()` on a `createContext` with only the default frame is legal — a public method's runtime semantics left open. Per §8/§11 (default-reject under uncertainty; "a good API cut is cheaper than a bad API shipped"), a symbol whose behavior the author cannot state cannot ship. An app author calling `LocaleCtx.update(x)` at the wrong moment gets either a silent default mutation or a throw, and the RFC won't say which.

- **dx failure mode 3 — redundant test helper with a timing footgun.** `withContext(ctx, value)` and `withScopes(bindings)` are the same job. `withContext(ctx, v)` === `withScopes(() => [ctx.bind(v)])`. Worse, they evaluate differently: `withScopes` takes a lazy thunk (re-evaluated per test, correct) while `withContext` takes an eagerly-captured value — a stale-across-test capture trap for whoever reaches for the "simpler" singular form. Two helpers for one job with inconsistent laziness is what §11.6 (one safe combinator, discourage variants) exists to prevent; the ergonomic delta is `[Ctx.bind(v)]` vs `(Ctx, v)`, negligible.

- **dx failure mode 4 — three entry shapes, three files, no single taught path; api_surface ⊋ taught surface (§11.8).** CLAUDE.md teaches `renderWithScopes` as primary; fluent-html.md shows `renderWithScopes` + `renderWithNonceAndScopes` + `scopeAll`; fastify.md shows a `renderView` override. For the LLM reader (the §11.8 audience) "which do I reach for?" is unanswered — the same discoverability gap that produced the original mess. And the index covers only 3 of 8 api_surface symbols: `renderWithNonceAndScopes` has no index presence, `bind` is never named as a concept (only glue inside `renderWithScopes([...])`), and `withContext` has zero ✓ examples anywhere. By this project's own §0.7 / §11.8, an un-taught symbol is an un-adopted symbol. The RFC's §11.8 self-check claiming it covers "every symbol in api_surface" is overstated.

## Does it survive?

**Survives-with-changes.** The problem is real, evidence checks out against source, and the core earns its keep: the pop-by-identity hardening (`lastIndexOf(frame)` + idempotent dispose) is a genuine correctness win with an unchanged external contract; `scopeAll`, `bind`→`ScopeBinding<T>` type re-association, and the fixed error message are clean, idiomatic, hard-to-misuse wins an app author would reach for; and `renderWithScopes` makes scoping across an `await` physically impossible — the central safety payoff. It deletes the `_i18nDispose` module-augmentation dance from the template and 5 apps. So it is not a reject.

But it cannot ship as written: the flagship call shape fights the library's own array idiom, `update()` is semantically undecided, `withContext` is redundant-with-a-footgun, the fastify.md snippet breaks the file's augmentation idiom, and the guideline under-covers its own api_surface with no single canonical path. All are mechanical, all fold back into the RFC — see required_changes.

## Guardrail check (§11.8 — guideline-sync, owned by this lens)

**Fails as written; pass is achievable with the required changes.** The Guidelines impact section is well-structured, broadly house-style (✓/✗, code-first, LLM-reader), patches the correct three target files, and its line citations verify exactly (CLAUDE.md:145-147, fluent-html.md:146/166, fastify.md renderView guidance at 35/62/127). But it does not cover every api_surface symbol — `renderWithNonceAndScopes`, `bind`, and `withContext` lack addressable ✓ teaching — it teaches three different entry shapes with no canonical path, the fastify.md snippet diverges from the established augmentation idiom, and it teaches `update()` whose semantics are unresolved. Required changes 1–5 close all of this; once done, the edit is complete, minimal, and in voice.
