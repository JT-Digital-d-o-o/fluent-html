# Verdict: RFC-C-05 — dx lens

> You are an ADVERSARY. Your job is to KILL this RFC through the dx lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's premise — "one declarative table, three consumers derive their copies" — is checkable against the live code it cites, and the live code does not match the model. I read all three cited files.

- **dx failure mode 1 — the modelled table is a fiction; the real reverse map is 2.4× bigger, hand-curated, and order-sensitive.** The RFC frames the three lists as symmetric copies of one `(method → emit)` table, generated in both directions. The forward extractor (`fluent-html-tailwind-extractor/src/index.ts`) is indeed ~120 rows. But the ESLint reverse map (`no-known-modifiers-in-setclass.ts`) is **283 entries, 169 of them `exactMatch: true`**, and the file's own comment says *"Order matters: more specific patterns should come first."* The reason is structural, not sloppiness: `textColor`, `textSize`, and `textAlign` **all** emit `text-*` in the forward direction (extractor lines 95/117/121). To reverse `text-left` → `textAlign` but `text-xs` → `textSize` but `text-blue-500` → `textColor`, you need an ordered exact-match list that the forward table does not contain and cannot generate. The RFC's entire reverse-direction mechanism is one optional field, `fixPrefix?: string | string[]`, "defaulting to the emit prefix." That field cannot produce 169 exactMatch rows or any ordering. So the claim "ESLint auto-fix map … generated from it" is false for the majority of the ESLint map. The promised CI drift test — "the three derived tables are byte-identical to a freshly generated copy" — therefore cannot pass on day one (Migration claims it proves byte-identical output on first commit). It would either red-CI forever or be quietly weakened to skip exactMatch rows, which **reintroduces exactly the hand-maintained divergence the RFC was created to eliminate**, now with extra package machinery on top.

- **dx failure mode 2 — `EmitShape` does not cover the shapes that exist, so the "≈120 rows" collapse is overstated and `kind:"custom"` is the common case, not the escape hatch.** Concrete forward shapes in the live extractor that none of the six `EmitShape` kinds express: two-arg suffix joins `gap-${a}-${b}`, `overflow-${a}-${b}`, `rounded-${a}-${b}`, `translate-${a}-${b}`; `border`'s 0/1/2-arg logic with a `dirMap` lookup AND a raw fallback; bare-value emit `[args[0]]` for `display` and `position`. The Open Questions section waves this away as "a handful (`position`, `display`)" — but a quick pass over the 120 rows shows the two-arg and mixed-fallback shapes alone are more than a handful. Every one that falls to `kind:"custom"` is "hand-written in all 3" by the RFC's own definition — i.e. precisely the triple-edit the RFC promises to abolish, preserved for an unquantified fraction of the table. An author reaching for this table cannot tell from the RFC how much of it is actually single-sourced.

- **dx failure mode 3 — shared-prefix methods break the one-line-rename story.** The lib import path is `prefixOf("gradientTo")`. But `prefixOf` is keyed by method, and `textColor`/`textSize`/`textAlign` share the prefix `text`; `background` vs `borderColor` disambiguate by arg arity, not prefix. The clean `gradientTo` example works only because `bg-gradient` is unique. The RFC never addresses what a v4 rename does when it touches one of N methods sharing a prefix — the headline "one edit, not three" is demonstrated on the one case where it's true and is silent on the cases where it isn't.

- **dx failure mode 4 — surface-area-vs-payoff, the §13 "is this worth it" bar.** The app-author-visible API surface added by this RFC is **zero new methods**. The entire payoff is internal maintenance ergonomics: turning a mechanical, grep-able 3-line find-replace (done once per Tailwind major) into a new workspace package, a six-variant discriminated-union DSL, an `emitClasses` interpreter, a `defineUtility` helper, codegen wired into three `prebuild`s, generated checked-in files, and a drift test. For a v3→v4 prefix rename, the actual recurring cost the RFC removes is ~2 redundant edits. That is a real bug (silent drift), but the RFC reaches for a DSL where a flat `Record<method, { v3: string; v4: string }>` of renamable prefixes — single-sourcing just the strings that actually rename — would close the silent-drift hole with a fraction of the surface. `defineUtility()` in particular is dead API: it appears once, identity-returns its argument, and is used in zero examples.

## Does it survive?

**Survives-with-changes.** The underlying finding (F-C-042) is real and verified at every cited line, and the failure mode it names — silent cross-package drift on a rename — genuinely exists and genuinely is enforced today only by human diligence (guardrail §11.7). Killing the RFC outright would leave that hole open, and a narrower version of this RFC clearly closes it. So I do not reject.

But it cannot ship as written: the model of the problem is wrong in a way that breaks its own central proof (the byte-identical drift test), its data structure doesn't cover the data, and it over-builds relative to the dx payoff. The required changes above either (a) make the model match the live code (cover all `EmitShape` kinds, make the reverse/ESLint direction a first-class ordered spec, resolve shared-prefix renames) or (b) downscope to single-sourcing the renamable prefix strings only — which I'd weakly prefer on the dx surface-area bar. Either path is acceptable; both must also fix the guideline edit (it teaches a contested, not-owned gradient name) and name the maintainer README as a real deliverable so the maintainer-only symbols in `api_surface` are actually taught (§11.8 for the audience that uses this package).
