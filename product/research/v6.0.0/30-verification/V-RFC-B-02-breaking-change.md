# Verdict: RFC-B-02 — breaking-change lens

> Adversary. Goal: kill RFC-B-02 on hidden/unmarked breakage. Default reject under uncertainty.

## Attack

The RFC's entire back-compat story is "additive — nothing breaks," resting on three load-bearing claims: (1) new exports don't collide, (2) `BehaviorMap` only gains keys + optional options with today's defaults, and (3) no codemod needed. I went to the source.

**1. The new-export claim holds — this is the RFC's strongest ground.** No library export named `Modal`/`Drawer`/`ToastContainer`/`Toast` exists in `fluent-html/src` (grep clean). `HxResponse.toast()` is genuinely new; `trigger()` is untouched (src/patterns.ts:202). `openOverlay`/`closeOverlay`/`resetOnSuccess` are not used as behavior names in any app today. So the symbol-collision surface is real and clean. Credit where due.

**2. The `BehaviorMap` back-compat claim is asserted, not verified — and it has a live consumer the RFC never saw.** `BehaviorMap` is a **public exported type** (`src/index.ts:332 export type { BehaviorMap }`; published as `export type BehaviorMap = {...}` in dist). Exactly one app already depends on this surface: `ttl/src/core/fluent-html.augment.ts` does `declare module "fluent-html" { interface BehaviorMap { ... } }`, re-declaring the full map. Two problems the RFC is blind to:
   - You **cannot interface-merge into a `type` alias**. ttl's augment is therefore silently inert today — it only fails to error because ttl sets `skipLibCheck: true`. The RFC's BehaviorMap rewrite walks straight past this latent footgun. If anyone ever flips the export to `interface` (a natural way to *support* augmentation), or another app copies ttl's pattern without skipLibCheck, the widened map collides. The RFC must take an explicit position on the export kind; "additive" is meaningless without it.
   - The RFC's BehaviorMap (lines 157-176) shows `toggle: { target; event?; force? }` under the comment "existing (unchanged renderers, options widened where noted)." Widening an exported type's member shape is additive *only* if every new field is optional — which it is here — but the RFC never checks that an augmenting app (ttl) re-declaring the **old** shape won't conflict with the **new** shape under declaration merging. With a real augmenter in the fleet this is not hypothetical.

**3. "No codemod required / find-replace is sufficient" understates adopter test breakage.** `planet-positive-sport/tests/.../submission-modal.test.ts:67-86` pins the *exact on-the-wire inline-JS string* of its modal close handlers — `classList.add('hidden')` x3, `classList.remove('flex')` x3 — and adds a **negative assertion** that `classList.toggle('hidden')` must NOT appear. Migrating that modal to the built-in `Modal`/`closeOverlay` (the RFC's headline worked example) changes which elements emit the string and the counts, breaking these tests. That's exactly the "behavioral change not codemod-able" the lens hunts for. It's adopter-side and opt-in, so not a library break — but the RFC's migration section claims a find-replace suffices and is silent on string-pinned tests. That's an unmarked migration cost.

**4. `remove` + `animateOut` is a behavioral change gated on an option — fine, but unstated.** ~10 existing `behavior("remove", { target })` sites (jt-cut/gif-export, jt-draw) emit synchronous `.remove()`. The RFC adds `animateOut` that switches the emit to an async `animationend`-awaiting form. Gated correctly (default unchanged), so existing sites are safe — but the RFC must *say* the default path is byte-identical, not leave it to inference.

**5. Citation drift weakens trust in the additive audit.** The RFC's quoted `BehaviorMap` already contains `event?`/`force?` while labeling the block "existing … unchanged renderers." Those options do not exist in `src/core/behavior-methods.ts` today (verified: `toggle: { target: Id }`, nothing more). The framing risks a reader treating the widened map as the current contract.

## Does it survive?

**Survives with changes.** The core breakage vectors are honest-additive once forced into the open: no symbol collisions (verified), `trigger()` untouched (verified), new options optional with today's defaults (verified against the renderer source). No *library*-breaking change is hidden here. But the RFC's "additive — nothing breaks" is under-audited on two real fronts the lens exists to catch: the **published `BehaviorMap` export kind + the live ttl augmentation**, and the **adopter test/string-pin breakage** that its own headline migration triggers. These are folded into required_changes; none rises to a guardrail killer (§11.5 backward-compat is *additive at the library boundary* — true; the gaps are documentation/migration-completeness, not an actual broken public contract). Hence survives-with-changes, not reject.

## Guardrail check (§11.5 backward-compat, this lens owns it)

Library public surface is additive: new exports (no collision), new optional options (today's defaults), new method (`toast`) alongside untouched `trigger`. PASS at the boundary. The required changes are about (a) declaring the `BehaviorMap` export-kind contract so the latent ttl augmentation footgun is governed, and (b) marking the adopter-side migration costs (string-pinned tests, `force` semantics shift) so the Wave-4 breaking-changes.md / migration note is honest — per §11.5(b) "bundled into one migration" and §0.6 "must carry an explicit migration."
