# Verdict: RFC-C-06 — breaking-change lens

> Adversary. Job: kill RFC-C-06 through the breaking-change failure mode. Default reject under uncertainty.

## Attack

I verified the RFC against the actual `src/core/tailwind-types.ts` and `src/core/tailwind-methods.ts`. The structural citations are accurate: `TailwindState` at `:179-189` (28 members, no `not-*`/`print`/`starting`), `TailwindBreakpoint` at `:191` (`"sm".."2xl"`, no `@`), `withVariant` at `:86-92` (prepends prefix verbatim — runtime genuinely is target-agnostic), and `p.on`/`p.at` at `:326-332` typed `string` internally but surfaced as the unions via declaration merge at `:107-108`. The "runtime already correct, only the type blocks the call" premise is true.

**Breaking-change failure mode 1 — the headline label is half-true and the dangerous half is buried.** The RFC frontmatter says `breaking: additive`; §Migration says "Additive — nothing breaks" and "`breaking-changes.md`: no entry required (additive)." That is correct *for this RFC's own API delta* (union widening in argument position is contravariantly safe; new methods are pure addition; I confirmed `TailwindState`/`TailwindBreakpoint` are public via the `./core` subpath export in package.json but no app in the workspace consumes them, so the exported-type-widening vector has zero real blast radius). **But the RFC simultaneously documents a real behavioral regression** — v4 gates `hover:` behind `@media (hover:hover)`, so `.on("hover", …)` stops firing on touch devices. I confirmed the cited call-sites exist verbatim (`ttl/src/auth/auth.view.ts:78` `.on("hover", t => t.underline())`, `:392` `.on("hover", t => t.background("accent-light"))`) and that ttl/src has **57** `.on("hover"` call-sites, more than the RFC's "20+." This break is: (a) runtime-only, (b) invisible to the type checker (the string is valid in both majors), (c) invisible to ESLint, (d) **not codemod-able** (you cannot mechanically know which hovers are decorative vs. interactive). That is the exact profile guardrail §11.5 forces into the bundled migration guide — yet the RFC explicitly downgrades it to "a one-line upgrade note" and "no entry required." A 57-site silent touch regression is not a footnote.

**Breaking-change failure mode 2 — orphaned attribution.** The regression is honestly *not caused by this RFC* (it rides the v4 target flip, which RFC-C-02's `TW_TARGET_DEFAULT = "v4"` actually triggers). But that is an argument for *bundling and attributing* it, not for omitting it. As written, the only place a migrating app is warned is a prose guideline edit. If a team applies RFC-C-02 (target→v4) without reading the RFC-C-06 guideline note, they ship the regression. Guardrail §11.5b ("bundled into one migration in breaking-changes.md") is precisely the mechanism that prevents this orphaning.

**Breaking-change failure mode 3 — `onPointerHover` is a latent hidden break under v3.** The helper emits `[@media(hover:hover)]:hover:` unconditionally. The RFC's own Open Question 1 admits it does not know whether the v3 extractor accepts that syntax. If it does not, a v3 app that adopts `.onPointerHover()` gets a silently dropped class — no CSS, no error — which is itself a (small) hidden behavioral break introduced *by this RFC*. Shipping an API whose correctness under one supported target is an open question is a breaking-change risk, not an open question to resolve later.

(Cross-lens flag, not my kill: the `not-${TailwindBaseState | TailwindMediaState}` distribution generates invalid members — `not-before`, `not-after`, `not-marker`, `not-placeholder` (pseudo-elements, non-negatable) and `not-starting`/`not-open`/`not-inert` (questionable). That is the type-safety lens's concern; it is inert from a breaking-change view since offering extra invalid members breaks no existing code.)

## Does it survive?

**Survives-with-changes.** The type/method additions are genuinely backward-compatible — I verified no downstream consumer of the widened types and confirmed widening is argument-position-safe. The RFC does not introduce a hard break in its own surface. It is killed *as written* only on honesty/marking: it acknowledges a real, widespread, non-codemod-able behavioral regression and then declines to bundle it into the migration guide, which violates guardrail §11.5's bundling requirement and the algorithm's §13 "guardrail drift — a breaking API sneaks into a minor" failure mode. That is fixable by the three required changes above without redesigning any API. Once the hover regression is properly entered in `breaking-changes.md` with an audit procedure and attributed to the v4 target flip, and Open Question 1 is resolved (gate `onPointerHover` on TW_TARGET or mark it v4-only), the breaking-change story is honest and complete.

## Guardrail check (this lens owns §11.5 backward-compat)

- §11.5 additive-by-default: the API delta passes. The *documented v4 hover behavior* is a breaking behavioral change that the RFC currently leaves out of `breaking-changes.md` — **fails as written**, fixable via required change 1 & 2.
- §11.5 codemod-able-where-possible: the hover regression is explicitly NOT codemod-able; that strengthens the case for a migration-guide entry with a manual audit procedure, not weakens it.
- §11.5 bundled-into-one-migration: currently orphaned in a guideline note; required change 2 folds it into the v4 migration bundle alongside RFC-C-02.
