# Verdict: RFC-D-03 — security/escape lens

> You are an ADVERSARY. Your job is to KILL this RFC through the security/escape lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's headline security selling point is that the shared `emit()` lets `renderAlgebra` "close the script/style XSS gap" (F-D-003/F-D-083), with §Worked-examples #3 promising `Script(userControlled)` now emits a sanitized `<\/script>`. I attack precisely this claim, because if the security improvement the RFC advertises is unachievable in the proposed shape, the RFC ships under a false guardrail-§11.3 "pass."

- **security/escape failure mode 1 — the fold cannot thread render context, so the advertised script-sanitization fix is structurally impossible at the leaves.** `renderAlgebra` is constrained to `ViewAlgebra<string>` (the RFC explicitly preserves this shape for `foldView`/`hyloView` compat). `foldView` (`src/fold/fold.ts:65`) is a *bottom-up catamorphism*: `const foldedChildren = foldView(alg, view.child)` runs and produces a finished string **before** `alg.tag(view.el, attrs, foldedChildren)` ever sees that the element is `<script>`. The algebra's leaf cases are `text: (s: string) => A` and `raw: (html: string) => A` — context-blind *by type*. The RFC's own proposed leaves bake in a fixed mode: `text: (s) => emit(k, s, 'escape')` and `raw: (html) => html`. Now consider the documented danger input `Script(Raw(userJs))` where `userJs = "</script><img src=x onerror=alert(document.cookie)>"`. The `raw` leaf fires first and returns the string **verbatim** (no `sanitizeRawContent`, because the fold has no idea it's inside a script). By the time `tag('script', …, childHtml)` runs, `childHtml` is already the un-neutralized breakout string; splicing it between `<script>…</script>` yields a live DOM-injection. This is **F-D-003 still open** — the very finding the RFC lists as resolved. The canonical `render()` avoids this only because it threads `childCtx` *downward* (`render.ts:239`), a mechanism the bottom-up fold cannot replicate.

- **security/escape failure mode 2 — the parity test as specified does not pin the hole.** The RFC's mitigation is "a property/fuzz test asserting `foldView(renderAlgebra, v) === render(v)` over generated trees that include void elements, Script/Style, and every HTMX attr." A generator that inserts `Script("plain text")` will *pass* even with the bug, because plain text under `'escape'` happens to also be safe-ish (over-escaped, but no breakout). The breakout only manifests for `Raw(...)` nested **under** Script/Style — a structurally specific shape the stated generator need not produce. So the RFC's safety net would go green while the XSS gap remains. A guardrail invariant (escape-by-default, §11.3) protected only by a test that can't see the failure is not protected.

- **security/escape failure mode 3 — reconstructing the open tag from `TagAttrs` re-opens attribute injection.** The new `emitOpenTag(element, attrs)` must rebuild markup from the fold's `TagAttrs` (`src/fold/types.ts:7`), which is a loose bag: `attributes: Record<string, string>` plus an index signature `[key: string]: unknown` for element-specific props. The *current* `renderAlgebra.buildAttributes` (`render.ts:16-31`) already double-iterates this bag (`Object.entries(attrs)` twice). Any rewrite that reconstructs the tag from this bag must guarantee every value is `escapeAttr(String(v))`'d and that **attribute names** themselves are never attacker-derived raw. The RFC does not spell out `emitOpenTag`'s escaping contract — it's hand-waved as "shared: VOID_ELEMENTS + buildHtmx + escape." Under default-reject, an unspecified escaping contract on a new markup-emitting helper is a hazard, not a pass.

## Does it survive?

**survives-with-changes.** The *direction* is a genuine net-security improvement: collapsing three serializers into one `emit()` with a typed `RenderCtx` literal union (`'escape'|'raw'|'script'|'style'`) is strictly better than the tri-typed `boolean|string` flag, and the canonical `render()`/`renderToStream()` paths (which thread context downward) genuinely become a single audited sanitizer — that closes the real-world XSS surface, since apps render responses via `reply.renderView`/`render`/`renderToStream`, never via `foldView(renderAlgebra, …)` (the RFC itself adds a guideline steer to that effect).

But the RFC **overclaims**: it lists F-D-003/F-D-083 as *resolved by the renderAlgebra wrapper*, and ships a §11.3 "pass — net improvement; renderAlgebra now goes through the canonical sanitizer." That is false as written — a bottom-up fold cannot route script/style context to its leaves, so `renderAlgebra` cannot sanitize `Raw`-in-`Script` no matter how thin the `tag` wrapper is. Shipping a guardrail "pass" on an unachieved sanitization is exactly the false-positive the §8 quorum rule is built to stop.

It does not reach `reject` because the defect is **confined to the secondary `renderAlgebra` path** and is fixable two ways without touching the production hot path:
- **(a) Make `renderAlgebra.tag` re-walk its own `child` through `emit()`** for script/style elements (discarding the bottom-up `childHtml` for those elements) — then sanitization is real and the F-D-003 claim becomes true. This is slightly awkward (the fold's `childHtml` is thrown away for raw-text elements) but correct.
- **(b) Drop the F-D-003/083 "resolved" claim for `renderAlgebra`**, keep/strengthen the "not for output, not script-safe" warning, and rely on the guideline steer + the (legitimately-fixed) `render`/`stream` paths for the actual security win.

Either is fine; both fold back as the required changes above. Without one of them, the RFC ships a guardrail invariant marked "pass" that is not.

## Guardrail check (security/escape — this lens owns §11.3)

- **render() / renderToStream():** PASS. Both remain context-threading top-down serializers routed through the single `emit()`; `'escape'` is the default ctx; `<script>`/`<style>` children correctly get `'script'`/`'style'` sanitization via the downward `childCtx`. Deduping them is a real reduction in the XSS-drift surface (today's `stream.ts:24` `v as string` drift confirms the risk the RFC removes). No new public symbol is exported (`emit`/`Sink`/etc. stay internal to `src/render/`), so no new attacker-reachable markup API.
- **renderAlgebra:** **CONDITIONAL FAIL as written.** The claimed F-D-003/083 closure is not achievable by a thin bottom-up wrapper; `Raw(...)` nested under `Script()`/`Style()` still breaks out. Must be fixed via required-change (a) or the claim withdrawn via (b). The §11.3 self-check must be downgraded from an unconditional "pass" to an explicit per-input statement.
- **escapeAttr coverage:** `escapeAttr` aliases `escapeHtml` (`escape.ts:37`) and escapes `& < > " '` — adequate **only** for the double-quoted attributes the renderer always emits (correctly noted in the escape.ts comment). The new `emitOpenTag` must preserve that double-quoted invariant and never introduce an unquoted/single-quoted attribute path; confirm in the rewrite.
