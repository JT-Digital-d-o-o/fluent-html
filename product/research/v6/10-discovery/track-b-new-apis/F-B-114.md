# Per-app `inputStyle` apply-fn is the de-facto input-variant token

## Problem

`formFor<T>()` generates typed `InputTag` instances but provides no way to set a default appearance. The library has no concept of an "input theme" — the base style (border, padding, radius, focus ring) that every input in the app shares. The ecosystem solution is a hand-written `inputStyle` apply-fn in every app's shared components file. These functions are structurally identical: same fluent method chain, differing only in brand-color tokens.

## Evidence

All four implementations follow the same pattern:

glimm:
```ts
// glimm/src/shared/components/ui.form.components.ts:26-33
export const inputStyle = (t: InputTag) => t
  .w("full").padding("x","4").padding("y","3")
  .border("2").borderColor("sand-2").rounded("lg")
  .transition("colors").on("focus", tt => tt.borderColor("primary").outline("none"));
```

storysell-ai (near-verbatim copy, different color tokens):
```ts
// storysell-ai/src/shared/components/ui.form.components.ts:26-33
export const inputStyle = (t: InputTag) => t
  .w("full").padding("x","4").padding("y","3")
  .border().borderColor("gray-300").rounded("lg")
  .transition("colors").on("focus", tt => tt.borderColor("brand-500").ring("1").ringColor("brand-500/20").outline("none"));
```

rideshare (named `styledInputStyle`, otherwise identical structure):
```ts
// rideshare/src/shared/components/form.view.ts:16-23
export const styledInputStyle = <T extends Tag>(t: T): T => t
  .w("full").padding("x","4").padding("y","3")
  .border("2").borderColor("site-border").rounded("lg")
  .transition("colors").on("focus", t => t.borderColor("leaf").outline("none")) as T;
```

planet-positive-sport:
```ts
// planet-positive-sport/src/shared/components/forms/form.ts:46-55
export const inputStyle = <T extends Tag>(t: T): T =>
  t.w("full").padding("x","4").padding("y","3")
   .border().borderColor("border-ui").rounded("lg")
   .background("white")
   .transition("colors").on("focus", tt => tt.borderColor("primary").ring("1").ringColor("primary/20").outline("none")) as T;
```

Additionally, glimm has a **second** input theme in its huluma brand layer:
```ts
// glimm/src/shared/components/huluma/form.components.ts:11-25
export function hulumaInput(t: InputTag): InputTag {
  return t.w("full").background("foam").border().borderColor("sand-2")
    .rounded("full")  // ← pill shape, different from ui.form.components.ts "lg"
    .padding("x","5").padding("y","3").textSize("[15px]")
    .transition("colors").on("focus", tt => tt.borderColor("coral").outline("none").ring("2").ringColor("coral/30"));
}
```

Exactly like buttons (see F-B-113), glimm ended up with two input styles: the generic `inputStyle` and the brand-specific `hulumaInput`.

## Why it matters

The `inputStyle` function is the input equivalent of the button wrapper. It is independently typed, defined, and tested in 4 apps. Callers write `.apply(inputStyle)` rather than anything semantic. When the brand updates (e.g. focus ring changes from none to `ring-1`), every app updates its closure individually.

The root cause is the same as the button-variant gap: no library-level concept of a configurable style token for a form element. A `createInputTheme(tokens)` factory would let apps supply `{ borderWidth, borderColor, focusBorderColor, focusRing, radius, padding }` once and have all inputs in the app automatically styled without per-app apply-fn boilerplate. This also unblocks the `FormField` RFC (F-B-002): a built-in `FormField` component needs to know what a "styled input" looks like — currently it cannot, because the input style is always an external apply-fn.

## Rough idea (not a design)

A `createInputTheme(tokens)` factory returns an `InputThemeCtx` context. The app's Fastify setup (or layout root) enters the context with the brand tokens. The built-in `FormField` and raw `Input()` calls can then resolve the app's input theme without callers passing an `apply(inputStyle)` argument. This composes cleanly with the button-variant-token RFC.
