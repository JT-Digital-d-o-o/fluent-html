# File-upload forms require dual redundant encoding attributes — no fluent API for the `setEnctype` + `hx-encoding` pair

## Problem

HTMX 4 ignores a form's native `enctype` attribute when submitting via AJAX — callers must also set `hx-encoding="multipart/form-data"` (or the `encoding` option in `setHtmx()`). This means every file-upload form must set both `setEnctype("multipart/form-data")` **and** pass `encoding: "multipart/form-data"` in the htmx options — two separate calls for one logical requirement. There is no fluent API that handles both at once, and the relationship is not explained in the guidelines.

Additionally, `Input().setType("file")` has no typed method for the `capture` attribute (which requests the device camera on mobile), forcing `addAttribute("capture", "environment")` at every call site.

## Evidence

```ts
// rideshare/src/settings/settings.view.ts:137-143
Form(/* ... */)
  .setEnctype("multipart/form-data")                     // ← native HTML
  .setHtmx(settingsRoutes.uploadAvatar({
    target: layoutIds.page,
    swap: "outerMorph scroll:top",
    encoding: "multipart/form-data",                     // ← HTMX also needs it
  })),
```

```ts
// glimm/src/protect/views/protect.components.ts:63-72
.setEnctype("multipart/form-data")
.setHtmx(protectRoutes.upload({
  // htmx 4 ignores the form's enctype — hx-encoding is what makes it send FormData.
  encoding: "multipart/form-data",   // ← comment documents the pain
}))
```

```ts
// planet-positive-sport/src/loc/suppliers/views/contributors-card.view.ts:330-331
.setEnctype("multipart/form-data")
.addAttribute("hx-encoding", "multipart/form-data")   // ← raw addAttribute (bypasses setHtmx)
```

```ts
// planet-positive-sport/src/admin/questionnaires/picker/picker.view.ts:302-304
.setEnctype("multipart/form-data")
.addAttribute("hx-encoding", "multipart/form-data")   // ← same pattern, 4+ times in pps
```

```ts
// glimm/src/protect/views/protect.components.ts:59  — capture via addAttribute
Input().setType("file").when(capture, (t) => t.addAttribute("capture", "environment"))
```

The `pps` pattern reaches for raw `addAttribute("hx-encoding", …)` rather than the `setHtmx(…encoding…)` option — suggesting devs are unaware of (or can't use) the structured path. The glimm comment explicitly documents the counterintuitive htmx-4 behaviour, showing the knowledge isn't obvious.

## Why it matters

At least 7 file-upload forms across 4 apps repeat this dual-attribute pattern. Every new developer discovering file uploads must re-learn that HTMX 4 requires its own encoding attribute independently of the HTML form attribute. The `addAttribute("hx-encoding", …)` bypass in pps skips the typed `setHtmx()` path entirely. The `capture` attribute gap forces a third `addAttribute` call on top.

## Rough idea (not a design)

Add `.multipart()` on `FormTag` that calls `setEnctype("multipart/form-data")` and records a flag so that `setHtmx()` (or the htmx serializer) automatically emits `hx-encoding="multipart/form-data"` without a separate caller argument. Separately, add `InputTag.setCapture(value: "user" | "environment")` as a typed setter alongside the existing `setAccept()` and `setMultiple()`.
