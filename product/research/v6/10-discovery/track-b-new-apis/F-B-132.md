# htmx.md 'Shorthand vs setHtmx' section shows raw string endpoints, contradicting defineRoutes mandate

## Problem

The `htmx.md` guideline contains two rules that contradict each other:

1. **"Type-safe routes with defineRoutes"** (htmx.md §): _"Never hardcode endpoint strings … NEVER: `const url = route.resolve() + ?page=${page}` — use `resolve({ page })`"_
2. **"Shorthand vs setHtmx"** (htmx.md §, line 83): Shows `Button("Load").hxGet("/api/items")` with a raw string endpoint as the canonical shorthand usage.

Because `hxGet(endpoint: string, ...)` accepts a raw string (unlike `setHtmx(route.method())` which is typed), the shorthand section creates a legitimate-looking loophole. Apps — specifically mngmt — adopted this pattern and extended it to manual template-literal query string concatenation, the exact anti-pattern the defineRoutes rule forbids.

## Evidence

**htmx.md shorthand section (the source of the confusion):**

```ts
// guidelines/web-development/htmx.md:83 — shows raw strings as acceptable shorthand
Button("Load").hxGet("/api/items")
Button("Save").hxPost("/api/save", { target: ids.result })
```

**mngmt uses hxGet with template-literal query concatenation — the forbidden pattern:**

```ts
// mngmt/src/analytics/analytics.view.ts:89
A(preset.label)
  .hxGet(`${analyticsRoutes.dashboard.path}?range=${preset.value}`, {
    target: ids.analyticsDashboard,
    swap: "outerMorph scroll:top",
  })

// mngmt/src/analytics/analytics.view.ts:494
.hxGet(`${analyticsRoutes.events.path}?page=${props.filters.page - 1}`, {

// mngmt/src/analytics/analytics.view.ts:337
.hxGet(`${analyticsRoutes.cohorts.path}?period=${period}&range=${props.activeRange}`, {
```

The `.path` property gives the route template path (e.g. `/analytics/events`) without resolving params. Appending `?page=${n}` bypasses the typed `resolve({ page: n })` method — no compile-time check that `page` is a valid query key for that route, no encoding guarantee.

**mngmt's navLink helper also passes a raw `href: string` to hxGet:**

```ts
// mngmt/src/shared/components/layout.view.ts:41
export const navLink = (href: string) => (t: ReturnType<typeof A>) =>
  t.cursor("pointer").hxGet(href, {
    target: layoutIds.pageContent,
    swap: "outerMorph scroll:top",
    pushUrl: true,
    indicator: layoutIds.pageLoadingBar,
  });
```

**rideshare uses hxGet correctly with .resolve() — inconsistent patterns in the same codebase:**

```ts
// rideshare/src/rides/views/browse.view.ts:122 — correct pattern
.hxGet(rideRoutes.browse.resolve({ event: event.id }), { ... })
```

## Why it matters

The `hxGet`/`hxPost` shorthand methods accept `string` (not a typed route reference), which means any typo in the path or query key is a silent runtime failure. The defineRoutes section explicitly outlaws this but the shorthand section contradicts it by showing raw strings as the canonical usage. mngmt has 6 template-literal `hxGet()` calls using `.path + ?key=value` that are invisible to TypeScript. Affects approx 6 apps that use hxGet (rideshare 25, mngmt 9 calls).

Pain: high — silent type-safety regression that bypasses the core `defineRoutes` value proposition.

## Rough idea (not a design)

Rewrite the "Shorthand vs setHtmx" htmx.md section: change the examples to show `Button("Load").hxGet(userRoutes.list.resolve())` and add an explicit ✗ for raw strings and template-literal concatenation. No API change required — `hxGet/hxPost` already accept the string returned by `.resolve()`, so this is a pure guideline patch.
