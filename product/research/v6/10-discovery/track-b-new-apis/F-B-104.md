# No locale-aware document root — `lang` attribute is hardcoded or omitted across apps

## Problem

Even apps with a full i18n stack (pps: 4 context vars, 125 view files importing `t()`) fail to connect the runtime locale to the HTML document's `lang` attribute. The `lang` attribute is required for screen readers to switch pronunciation correctly and for search engines to serve language-appropriate results. When a Slovenian user loads jt-cut, the document still says `lang="en"` (or nothing), degrading accessibility and SEO.

The root cause is a guideline gap: `fluent-html.md` shows `HTML(Head(), Body()).setLang("en")` with a hardcoded string. Nothing teaches the idiomatic connection `HTML().setLang(i18nLocale.current)`. Apps either copy the hardcoded "en" or rely on the browser default.

## Evidence

```ts
// planet-positive-sport/src/core/i18n/i18n.ts:9
export const i18nLocale = createContext("en");
// ↑ The locale IS available at render time via i18nLocale.current...
```

But in all four pps layout files, `.setLang` receives a hardcoded string:

```ts
// planet-positive-sport/src/shared/components/layouts/app-layout.view.ts:92
HTML(head, body).setLang("en"),  // ← hardcoded "en" despite full i18n stack

// planet-positive-sport/src/shared/components/layouts/auth-layout.view.ts:71
HTML(head, body).setLang("en"),  // ← same

// planet-positive-sport/src/shared/components/layout.view.ts:72
).setLang("en"),                 // ← same

// planet-positive-sport/src/loc/reports/category-report.view.ts:103
).setLang("en"),                 // ← same
```

rideshare also hardcodes:

```ts
// rideshare/src/shared/components/layout.view.ts:165
HTML(Head(...headChildren), body).setLang("en"),
```

The fluent-html guideline example reinforces the bad pattern:

```ts
// guidelines/web-development/fluent-html.md (Rendering section)
HTML(Head(), Body()).setLang("en")   // ← hardcoded string in the guidelines example
```

## Why it matters

A screen reader encountering `lang="en"` on a Slovenian page will mispronounce content. Search engines may not surface the page in Slovenian results. This is a correctness issue for any app supporting more than one locale. The fix in any individual app is a one-liner (`HTML().setLang(i18nLocale.current)`), but the guideline example actively teaches the wrong pattern, so four apps with dynamic locale resolution still hardcode "en".

This is primarily a **guidelines adoption gap** — the API (`setLang`) exists; the teaching is wrong. But it also points to a missing convenience: an i18n companion that ships a `LocaleAwareHTML()` or a `Document({ lang: i18nLocale.current, ... })` helper that wires it automatically.

## Rough idea (not a design)

1. Fix the guideline example immediately: replace `HTML(Head(), Body()).setLang("en")` with `HTML(Head(), Body()).setLang(i18nLocale.current)` and add a ✓/✗ do-don't pair.
2. In the library i18n companion (F-B-101 proposed API), expose `LocaleAwareHTML()` or make `Document()` (if shipped, see seed backlog item 9) read `i18nLocale.current` for `lang` by default.
