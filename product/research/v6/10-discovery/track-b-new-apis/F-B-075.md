# Cross-request shared data prop-drilled through every controller call; no request-context injection for layout data

## Problem

Every authenticated page in rideshare passes `navCounts: request.navCounts` through every `Layout()` call, which means every controller must (1) fetch navCounts in a preHandler, (2) receive it on `request`, and (3) pass it to the view function explicitly. The prop-drill reaches 50+ sites in `settings.controller.ts` alone. storysell-ai used AsyncLocalStorage to avoid this (F-B-071), but that violates the guideline. Neither pattern is idiomatic.

## Evidence

```ts
// rideshare/src/core/server.ts:72-75
// Populate navCounts for authenticated users (runs after auth sets request.user)
server.addHook("preHandler", async (request) => {
  if (request.user) {
    request.navCounts = await getNavCounts(server.prisma, request.user.id);
  }
});
```

```ts
// rideshare/src/settings/settings.controller.ts:57  (one of 50+ identical lines)
reply.renderView(SettingsPage({ user: request.user, navCounts: request.navCounts, ... }));

// settings.controller.ts:82
reply.renderView(SettingsPage({ ..., navCounts: request.navCounts, ... }));
// ... 48 more sites in settings.controller.ts alone ...
```

```ts
// rideshare/src/shared/nav-counts.ts:46-66
async function getUserCounts(prisma, userId) {
  const [reservationCount, myRideRequestCount, eventMemberCount] = await Promise.all([
    prisma.reservation.count({ where: { passengerId: userId, status: { in: ["PENDING","CONFIRMED"] }, ... } }),
    prisma.reservation.count({ where: { status: "PENDING", ride: { driverId: userId, ... } } }),
    prisma.eventMember.count({ where: { userId } }),
  ]);
  return { reservationCount, myRideRequestCount, hasEvents: eventMemberCount > 0 };
}
```

The NavCounts type is imported into `settings.view.ts` (line 18), making it a prop on every view function signature. The same data is also threaded as a prop into `layout.view.ts`. The problem repeats in any app that has shared layout data — glimm and mngmt have equivalent `navLink` patterns that implicitly embed indicator IDs in every nav link.

## Why it matters

This is the other side of F-B-071: rideshare chose prop-drilling, storysell chose AsyncLocalStorage. Both choices are workarounds for the same missing primitive — a way to inject request-level context data into the render without threading it through every function signature. The prop-drill approach produces dozens of `navCounts: request.navCounts` sites that are pure boilerplate: they carry no information, they just satisfy TypeScript.

The root cause is that `reply.renderView(view)` takes a pre-built view, not a factory + data. There is no `reply.renderView(view, { contexts: [[NavCountsContext, request.navCounts]] })` that temporarily enters context scopes around the render.

Five apps have this pattern in some form: rideshare (navCounts), storysell (sidebarContext / ALS), glimm (indicator IDs in nav links), mngmt (indicator IDs in nav links), planet-positive-sport (i18n contexts threaded through layout).

## Rough idea (not a design)

Two complementary solutions: (1) `reply.renderView(view, { contexts: [[Ctx1, val1], [Ctx2, val2]] })` — the render internally calls `scope(Ctx1, val1, () => scope(Ctx2, val2, () => render(view)))`, so view functions can read `Ctx1.use()` without receiving the value as a prop. (2) A Fastify integration helper `seedRequestContext(server, MyContext, async (request) => loadValue(request))` that registers a preHandler hook and makes the value available to `renderView` automatically — apps call this once during server setup and never touch navCounts again in any controller or view.
