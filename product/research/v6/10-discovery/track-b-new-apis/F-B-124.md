# `reply.renderView()` and `hxResponse()` are incompatible — HTMX response headers must be set via raw `reply.header()` strings

## Problem

The library provides two separate, incompatible APIs for HTMX responses: `hxResponse(view).reswap(…).trigger(…).build()` (a builder that returns `{ html, headers }`) and `reply.renderView(view)` (the Fastify decorator). There is no way to use `hxResponse`'s typed builder together with `reply.renderView()` — the controller must either use `hxResponse` and manually spread its headers, or fall back to raw `reply.header("HX-Reswap", "outerMorph")` string calls before calling `reply.renderView()`. Apps uniformly choose the raw-header path because it chains cleanly with `reply`.

This is the dominant pattern for every 422 validation response in rideshare: `reply.header("HX-Reswap", "outerMorph").code(422).renderView(view)` — 12 identical occurrences in a single controller file.

## Evidence

```ts
// rideshare/src/settings/settings.controller.ts:110  — one of 12 identical occurrences
reply.header("HX-Reswap", "outerMorph").code(422).renderView(
  SettingsSection({ ... })
);
```

```ts
// planet-positive-sport/src/admin/admin.guards.ts:33-34 — retarget + reswap as raw strings
reply.header("HX-Retarget", layoutIds.mainContent.selector);
reply.header("HX-Reswap", "outerHTML");
```

```ts
// planet-positive-sport/src/expert/action-scoring/action-scoring.controller.ts:203
reply.header("HX-Retarget", layoutIds.mainContent.selector);
// (followed by reply.renderView)
```

The `hxResponse` builder exists and has typed `.reswap()`, `.retarget()`, `.trigger()`, etc. (`fluent-html/src/patterns.ts:279-302`). But using it requires:

```ts
// what a dev must write to use hxResponse with Fastify (awkward)
const { html, headers } = hxResponse(view).reswap("outerMorph").build();
Object.entries(headers).forEach(([k, v]) => reply.header(k, v));
reply.code(422).type("text/html").send(html);
```

No app does this. All 6+ apps use raw `reply.header(…)` strings instead — because `reply.renderView()` has no mechanism to accept HTMX header instructions.

Counts of raw `reply.header("HX-…")` calls: rideshare 12, planet-positive-sport 4, glimm 3, jt-cut 1 — approx 20 total across the fleet.

## Why it matters

`reply.header("HX-Reswap", "outerMorph")` is an untyped string — a typo silently produces a broken HTMX response. The htmx 4 swap name is `outerMorph` (not `outerHTML`, `outermorph`, etc.) and there is no compile-time guard. The `hxResponse` builder already has a typed `HxSwapStyle` union for `.reswap()` — but it's unreachable from the idiomatic `reply.renderView()` path. The guidelines document `reply.renderView()` as the correct way to render but do not mention that HTMX response headers must be set separately via raw strings.

The rideshare settings controller has 12 identical `reply.header("HX-Reswap", "outerMorph")` calls — a clear signal that 422-with-reswap is a high-frequency pattern with no idiomatic library support.

## Rough idea (not a design)

Extend the `reply.renderView()` decorator to accept an optional second argument — either an `HxResponse` builder instance or a plain options object `{ reswap?, retarget?, trigger?, code? }` — so the common case becomes:

```ts
// proposed
reply.renderView(view, { code: 422, reswap: "outerMorph" });

// or with the builder
reply.renderView(view, hxResponse().reswap("outerMorph").trigger("formError"));
```

This keeps the typed HTMX API and the Fastify reply decorator on the same call site. Zero-deps guardrail risk: the Fastify integration is already app-side boilerplate (see F-B-121); adding HTMX header support to the decorator adds no new library dependencies.
