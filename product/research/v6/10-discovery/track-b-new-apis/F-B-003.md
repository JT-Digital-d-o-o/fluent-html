# No `behavior('resetOnSuccess')` — form reset after successful swap is wired via raw `hx-on:htmx:after:swap` JS string

## Problem

A common pattern is: submit a form, and if the server returns success (no error element present in the swapped content), reset the form to empty. The only way to do this today is via a raw `hx-on:htmx:after:swap` attribute containing an inline JS expression. The guideline says "never raw inline JS" and prescribes `.behavior()`, but `.behavior()` has no `reset` variant, forcing devs to reach for `addAttribute` with a JS string.

## Evidence

**rideshare** — two forms with the identical conditional-reset pattern:

```ts
// rideshare/src/settings/settings.view.ts:255-260
Form(
  ...
).setHtmx(
  settingsRoutes.changePassword({ target: layoutIds.page, swap: "outerMorph scroll:top" })
).addAttribute(
  "hx-on:htmx:after:swap",
  `if(!document.getElementById('${ids.passwordError.id}'))this.reset()`
),
```

```ts
// rideshare/src/settings/settings.view.ts:332-337
Form(
  ...
).setHtmx(
  settingsRoutes.changeEmail({ target: layoutIds.page, swap: "outerMorph scroll:top" })
).addAttribute(
  "hx-on:htmx:after:swap",
  `if(!document.getElementById('${ids.emailError.id}'))this.reset()`
),
```

Both generate dynamic strings using template literals with `ids.passwordError.id` / `ids.emailError.id` — an error element whose presence signals a 422 was re-rendered. The JS expression detects absence of the error and resets the form.

**mngmt** — same need, handled with a full Script() block containing 9 lines of getElementById/addEventListener:

```ts
// mngmt/src/comments/comments.components.ts:216-224
Script(`(function(){
  var t=document.getElementById('${toggleId}');
  t.addEventListener('click',function(){
    var f=document.getElementById('${formId}');
    f.classList.toggle('hidden');
    f.querySelector('textarea')?.focus();
  });
})();`)
```

While this specific case is a toggle (not a reset), it illustrates the same root: `.behavior()` doesn't cover the form-lifecycle event hooks that htmx provides via `hx-on:htmx:*` events, so devs fall back to `Script()` or `addAttribute`.

## Why it matters

The guideline in `web-development/htmx.md` says to use `.behavior()` for all client-side interactions and never raw inline JS. Yet `.behavior()` covers `toggle`, `clipboard`, `disable`, `focus`, `back`, `scrollTo`, `selectAll` — not "reset form after a successful swap". The gap forces an `addAttribute("hx-on:htmx:after:swap", js_string)` pattern that: (a) violates the guideline, (b) uses dynamic template literal strings for element IDs (fragile if the id changes), and (c) is invisible to TypeScript.

The fix is not just a docs note — the behavior library needs a new entry.

## Rough idea (not a design)

Add `behavior("resetOnSuccess", { errorSelector? })` to the built-in behavior set. When `errorSelector` is provided (e.g. `#password-error`), the reset fires only if the element is absent after the swap — matching the current JS logic. Without `errorSelector`, the form resets unconditionally after every swap. This covers the two rideshare cases and keeps the guideline "no raw JS" rule enforceable.
