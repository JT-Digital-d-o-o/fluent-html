# Global loading bar (htmx-indicator) reimplemented identically in every app; no .htmxIndicator() fluent method

## Problem

fluent-html has no `.htmxIndicator()` fluent method and no built-in global loading bar component. As a result:

1. Every app that shows an HTMX loading indicator must call `.setClass("htmx-indicator")` — the raw class string — instead of a fluent method.
2. Every layout file also inlines the same CSS snippet (`opacity: 0; transition: opacity 200ms ease-in; .htmx-request .htmx-indicator { opacity: 1 }`) because there's no built-in way to inject it.
3. Many apps define a private `LoadingBar()` function with the same implementation.

## Evidence

Two separate apps (storysell-ai, glimm) define a `LoadingBar()` function with near-identical bodies:

```ts
// storysell-ai/src/shared/components/layout.view.ts:51-57
export function LoadingBar() {
  return Div(
    Div("").w("full").h("1").background("primary").animate("pulse"),
  )
    .setId(layoutIds.globalLoading)
    .setClass("htmx-indicator")        // ← raw class string, not fluent
    .position("fixed").top("0").left("0").right("0").zIndex("50");
}
```

```ts
// glimm/src/shared/components/layout.view.ts:40-46
export function LoadingBar() {
  return Div(
    Div("").w("full").h("1").background("primary").animate("pulse"),
  )
    .setId(layoutIds.globalLoading)
    .setClass("htmx-indicator")        // ← same raw class string
    .position("fixed").top("0").left("0").right("0").zIndex("50");
}
```

Glimm duplicates this a third time in `screen.view.ts:134` (the alternative full-screen layout shell).

In jt-cut, inline indicators use `addClass` without a dedicated component:
```ts
// jt-cut/src/projects/views/projects.render.view.ts:258
Span("Starting…").addClass("htmx-indicator")
```

Every layout's `<Style>` block repeats the same 3-line CSS:
```ts
// glimm/src/shared/components/layout.view.ts:74-75
.htmx-indicator { opacity: 0; transition: opacity 200ms ease-in; }
.htmx-request .htmx-indicator, .htmx-request.htmx-indicator { opacity: 1; }
```
This identical block appears in glimm `layout.view.ts:74`, `screen.view.ts:109`, `landing.shell.ts:119`, and storysell `layout.view.ts:97`. Rideshare and mngmt each manage loading differently (rideshare delegates to a JS-driven bar; mngmt uses a custom progress element).

## Why it matters

The guidelines explicitly state `.Skeleton()` + `.htmxIndicator()` as a proposed first-class method (recon §3.10) but the method does not exist. Apps working around this use `.setClass("htmx-indicator")` which is the exact anti-pattern the guidelines prohibit ("use fluent methods, not setClass"). Additionally, the inline CSS duplication means the animation keyframes and show/hide rules can diverge between apps.

## Rough idea (not a design)

Two small additions: (1) a `.htmxIndicator()` fluent method on `Tag` that sets the `htmx-indicator` class (same as `.toggle("htmx-indicator")` but semantically named); (2) a `HtmxLoadingBar({ id })` built-in component that renders the fixed top bar and injects the required CSS exactly once into the document (or as a `<style>` child in the component itself so it's scoped). This would let apps replace 10+ lines of `LoadingBar()` definition with a single import.
