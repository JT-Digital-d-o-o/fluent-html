# `SortableThCell`/`SortHeader` reimplemented in 3 apps with incompatible `buildHtmx` signatures

## Problem

Three apps independently implement a sortable table header cell (`SortableThCell` in jt-cut, `SortHeader` in glimm, and a positional variant in rideshare). All three solve the same problem — flip sort direction on click, pass current sort column, emit an HTMX link — but use different prop shapes and incompatible `buildHtmx` callback signatures. The result is that the pattern is not portable across apps, and each view that uses sorted tables must bring its own sort-header component.

## Evidence

### jt-cut — `buildHtmx(column: string, dir: SortDir) => HTMX`

```ts
// jt-cut/src/shared/components/ui.components.ts:139
type SortableThCellProps = {
  text: string;
  column: string;
  currentSort: string;
  currentDir: SortDir;
  buildHtmx: (sort: string, dir: SortDir) => HTMX;   // positional (column, dir)
  align?: "left" | "right" | "center";
};
export function SortableThCell({ text, column, currentSort, currentDir, buildHtmx, align = "left" }: SortableThCellProps) {
  const isActive = column === currentSort;
  const nextDir: SortDir = isActive && currentDir === "desc" ? "asc" : "desc";
  ...
  return Th(A(text + indicator).setHtmx(buildHtmx(column, nextDir)).cursor("pointer")...)
}
```

### glimm — `buildHtmx({ sort, dir }) => HTMX` (named-property object)

```ts
// glimm/src/analytics/views/analytics.components.ts:5
type SortHeaderProps = {
  label: string;
  field: string;
  currentSort?: string;
  currentDir?: SortDirection;
  align?: "left" | "right";
  buildHtmx: (vals: { sort: string; dir: SortDirection }) => HTMX;  // named object
};
export function SortHeader({ label, field, currentSort, currentDir, align = "left", buildHtmx }: SortHeaderProps) { ... }
```

The two signatures are incompatible: jt-cut's callback is `(string, SortDir) => HTMX` while glimm's is `({ sort, dir }) => HTMX`. A developer copying one app's sort headers into the other would need to adapt the callback shape.

### Call-site boilerplate required in every view

Both approaches require the view to define a `buildSortHtmx` helper that closes over the current route and forwards active filter params (itself a separate pain point, see [[F-B-013]]):

```ts
// jt-cut/src/analytics/views/dashboard.view.ts:399 (approx)
const sortProps = { currentSort: sort, currentDir: dir, buildHtmx };
// ... then spread into every SortableThCell call:
SortableThCell({ text: "Path", column: "path", ...sortProps }),
SortableThCell({ text: "Views", column: "views", align: "right", ...sortProps }),
SortableThCell({ text: "Unique Users", column: "uniqueUsers", align: "right", ...sortProps }),
```

The `...sortProps` spread is a workaround for prop-drilling `currentSort`/`currentDir`/`buildHtmx` into every column header.

## Why it matters

Three separate, mutually incompatible implementations of a standard UI pattern. The inconsistency in `buildHtmx` callback signatures means the helpers are not cross-app portable. The prop-drilling of `currentSort`/`currentDir`/`buildHtmx` into every sortable column header call is repetitive (typically 3–8 columns per table, 2–5 tables per analytics view). Total estimated boilerplate: approx 80–120 lines of sort-infrastructure code that could be shared across all three apps with a single built-in primitive.

## Rough idea

A built-in `SortableThCell({ label, field, state: TableState, route })` that reads sort state from a shared `TableState` object (see [[F-B-013]]) and emits the HTMX link internally — removing both the `buildHtmx` callback and the `...sortProps` spread pattern entirely. The unification also forces a single `buildHtmx` signature convention, ending the incompatibility.
