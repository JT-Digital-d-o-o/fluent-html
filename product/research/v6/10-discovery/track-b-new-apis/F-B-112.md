# No typography-scale API — every app independently defines heading/body wrappers

## Problem

Apps with a design system need a consistent type scale: a small set of named roles (display title, screen title, section headline, body, caption, micro-label) each mapping to specific font-family, size, weight, line-height, and color values. fluent-html has no API for this. Every app defines its own set of wrapper functions, each hard-coding arbitrary `textSize("[Npx]")` escape values, duplicating the concept with incompatible names and signatures.

## Evidence

glimm/huluma defines 8 typed text wrappers (60+ usage sites across the app):
```ts
// glimm/src/shared/components/huluma/text.components.ts:9-87
export function DisplayTitle(...children: Parameters<typeof H1>) {
  return H1(...children)
    .fontFamily("display").fontWeight("semibold").textSize("[42px]").leading("[1.05]").textColor("deep");
}
export function ScreenTitle(...children: Parameters<typeof H1>) {
  return H1(...children)
    .fontFamily("display").fontWeight("semibold").textSize("3xl").leading("[1.12]").textColor("deep");
}
export function SectionHeadline(...children: Parameters<typeof H2>) {
  return H2(...children)
    .fontFamily("display").fontWeight("medium").textSize("2xl").leading("[1.2]").textColor("deep");
}
export function CardTitle(...children: Parameters<typeof H3>) {
  return H3(...children)
    .fontWeight("extrabold").textSize("[19px]").leading("[1.3]").textColor("deep");
}
export function Lead(...children: Parameters<typeof P>) {
  return P(...children).textSize("[17px]").leading("[1.55]").textColor("deep");
}
export function BodyText(...children: Parameters<typeof P>) {
  return P(...children).textSize("[15px]").leading("[1.6]").textColor("deep");
}
export function Caption(...children: Parameters<typeof Span>) {
  return Span(...children).fontWeight("semibold").textSize("[13px]").leading("[1.4]").textColor("deep-soft");
}
export function Micro(...children: Parameters<typeof Span>) {
  return Span(...children).fontWeight("bold").textSize("[11px]").leading("[1.3]")
    .tracking("[0.06em]").uppercase().textColor("coral-deep");
}
```

All 8 are re-exported as the huluma design kit (`glimm/src/shared/components/huluma/index.ts:6-13`) and used 60+ times across glimm.

storysell-ai independently defines a `SectionHeader` wrapper:
```ts
// storysell-ai/src/shared/components/molecules/ui.molecules.cards.ts:146-165
type SectionHeaderProps = { title: string; description?: string };
export function SectionHeader({ title, description }: SectionHeaderProps) {
  return Div(
    H2(title).textSize("2xl").fontWeight("bold").textColor("gray-900"),
    IfThen(description, d => P(d).textSize("base").textColor("gray-600").margin("t", "1")),
  );
}
```

The key pain points:
1. **Arbitrary-value proliferation**: `[42px]`, `[19px]`, `[17px]`, `[15px]`, `[13px]`, `[11px]` — none of these appear in Tailwind's built-in scale, and each is hand-picked per app with no coordination.
2. **No named scale**: glimm calls its heading "ScreenTitle"; storysell calls the equivalent component "SectionHeader". The semantic role is the same; the name, element, and styles differ.
3. **Per-app duplication**: each app that needs a type scale starts from scratch. The wrapper functions have 5–10 lines of fluent chain each, totalling 80+ lines in glimm alone.

## Why it matters

Any app reaching design-system maturity hits this wall. glimm's huluma layer is effectively a per-app design-system workaround with 8 components, exported as a mini-library. If fluent-html provided a `createTypographyScale(tokens)` API (or equivalent context-injected theme), apps could configure roles once and call `TypographyToken("display", "My Headline")` instead of scattering arbitrary-value calls.

## Rough idea (not a design)

A `createTypographyScale(roles)` factory (analogous to `createContext`) that maps named roles to `(tag, children) => Tag` factories. The Wave-2 RFC would decide the exact shape — options include a context-injected lookup, a `Text.role("display", ...)` method on the library's `H1`/`H2`/`P` etc., or simply a typed `defineTextScale(...)` helper that generates the wrapper functions with a unified interface.
