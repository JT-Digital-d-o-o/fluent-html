# createContext() cannot survive an await — AsyncLocalStorage workaround

## Problem

`createContext()` (fluent-html's synchronous scoped-context API) requires an explicit `scope.run(() => render())` call that wraps the render synchronously. This works perfectly when the render happens in the same synchronous tick as the context setup. It breaks when:

1. A `preHandler` hook runs asynchronously (DB query), seeds some cross-cutting chrome data, and
2. A later `preHandler` (or the handler itself) awaits another DB query, then
3. Wants to read the first context during the synchronous render.

The CLAUDE.md guideline says "**Never use `AsyncLocalStorage`** for render-time data." storysell-ai violated this explicitly because `createContext` had no answer:

```ts
// storysell-ai/src/core/view-context.ts:20
export const sidebarContext = new AsyncLocalStorage<SidebarContext>();

// The comment explains exactly why createContext wasn't enough:
// "AsyncLocalStorage.enterWith does NOT reliably propagate when called after an await,
//  so a fresh store set here (post-DB-query) would be invisible to the synchronous render."
```

```ts
// storysell-ai/src/core/server.ts:164-170  (the workaround)
server.addHook("preHandler", async (request) => {
  const store: SidebarContext = { brands: [], activeId: null, mode: "default" };
  sidebarContext.enterWith(store);   // ← must call BEFORE first await
  const user = request.user;
  if (!user) return;
  // ... then mutates the store object after the DB query (can't enterWith again)
});
```

The developer had to use a mutable-store trick: `enterWith` synchronously (before the first `await`) then mutate the same object reference after the `await`, because a second `enterWith` post-await would be invisible to the render.

## Evidence

- `storysell-ai/src/core/view-context.ts:20`: `export const sidebarContext = new AsyncLocalStorage<SidebarContext>();`
- `storysell-ai/src/core/view-context.ts:31-34`: extensive comment explaining why `createContext` was insufficient
- `storysell-ai/src/core/view-context.ts:36-39`: `setSidebarContext` that mutates the store rather than `enterWith` again
- `storysell-ai/src/core/server.ts:164-184`: `preHandler` hook pattern: `enterWith` before first await, then mutate after DB query

This is the single most concrete "the library forced me off the happy path" example in the recon doc (`02-app-patterns.md:260-270`).

## Why it matters

The `AsyncLocalStorage` workaround works, but it violates the documented guideline, creates a subtle ordering dependency (the `enterWith` must happen before any `await` in the hook), and requires a mutable-store trick that is easy to get wrong. Any app that needs to seed cross-cutting chrome data (sidebar, nav counts, tenant context) from a `preHandler` — a natural Fastify pattern — hits this wall. `rideshare` avoids it by threading `navCounts` as a prop on every `renderView` call (27+ occurrences of `navCounts: request.navCounts`), which is the prop-drilling alternative to context. Both workarounds are worse than a first-class solution.

The guideline in `fastify.md` says "Auth via preHandler" but gives no guidance on how to make context-seeded-in-preHandler visible to the render — the two patterns conflict.

## Rough idea (not a design)

A `reply.renderView(view, { context: { [key]: value } })` overload (or `reply.withContext(ctx, () => reply.renderView(view))`) that accepts an explicit context bag. The Fastify integration runs `scope.run(contexts, () => render(view))` at reply time, bridging the gap between async preHandler setup and synchronous render. This is zero-dep (the context mechanism already exists), additive, and eliminates both the `AsyncLocalStorage` workaround and the `navCounts`-everywhere prop-drilling pattern.
