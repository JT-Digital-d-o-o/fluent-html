# `ErrorPage` + `setErrorHandler`/`setNotFoundHandler` boilerplate copy-pasted across all apps with diverging prop signatures

## Problem

Every fluent-html app independently reimplements two things: (1) a local `ErrorPage` component, and (2) a `setErrorHandler` + `setNotFoundHandler` block in `server.ts`. The `ErrorPage` component has diverging prop signatures — rideshare passes `user` and `navCounts` for the authenticated nav chrome, mngmt passes neither, pps receives `status` from the guard and localizes the message. The `setErrorHandler` bodies are structurally identical (validation-400, operational-4xx, 500-hide-in-prod) but not shared.

## Evidence

```ts
// rideshare/src/shared/components/error.view.ts:6-11
type ErrorPageProps = {
  status: number;
  message: string;
  user?: AuthUser | null;     // ← rideshare-specific
  navCounts?: NavCounts;      // ← rideshare-specific
};
```

```ts
// mngmt/src/shared/components/error.view.ts:4-7  — simpler, no auth props
type ErrorPageProps = {
  status: number;
  message: string;
};
```

```ts
// rideshare/src/core/server.ts:121-157  — standard three-branch error handler
server.setErrorHandler((error, request, reply) => {
  const statusCode = error.statusCode ?? 500;
  if (error.validation) {
    reply.status(400);
    return reply.renderView(ErrorPage({ status: 400, message: error.message, user, navCounts }));
  }
  if (statusCode < 500) {
    reply.status(statusCode);
    return reply.renderView(ErrorPage({ status: statusCode, message: error.message, user, navCounts }));
  }
  const message = process.env.NODE_ENV === "production" ? "Internal Server Error" : error.message;
  reply.status(500);
  return reply.renderView(ErrorPage({ status: 500, message, user, navCounts }));
});
```

The three-branch logic (validation-400 / operational-4xx / 500-hide-in-prod) appears identically in rideshare (`server.ts:121-157`), mngmt (`index.ts:8-41`), pps (`server.ts:147-183`), storysell (`server.ts:237-273`), glimm (`server.ts:147-185`), jt-cut (`server.ts:148-198`). The `setNotFoundHandler` is a one-liner in every app:

```ts
// mngmt/src/index.ts:52-54 — identical shape in all 6 apps
server.setNotFoundHandler(async (_request, reply) => {
  reply.status(404);
  reply.renderView(ErrorPage({ status: 404, message: "Page not found" }));
});
```

## Why it matters

Six apps maintain independent implementations of the same three-branch `setErrorHandler` body. A bug in the 500-hide-in-prod branch (e.g. leaking stack traces) must be fixed in all six. The divergent `ErrorPage` prop signatures mean the apps can never share even the component — every future fluent-html app starts by deciding how many auth-chrome props to thread into the error page. The guidelines document `setErrorHandler` patterns but don't provide a reusable helper.

## Rough idea (not a design)

Provide (a) a built-in `ErrorPage({ status, message, shell? })` component that accepts an optional `shell` prop (a `(children: View) => View` wrapper) for apps that need auth chrome, and (b) a `registerErrorHandlers(server, { shell?, hideDetailsInProd? })` helper that installs the standard three-branch `setErrorHandler` + `setNotFoundHandler`. Apps that need custom chrome pass their layout as a `shell` callback; apps that don't pass nothing. This reduces both the component copy and the handler body to a single import.

Zero-deps risk: same as F-B-121 — this would live in a Fastify integration entry point.
