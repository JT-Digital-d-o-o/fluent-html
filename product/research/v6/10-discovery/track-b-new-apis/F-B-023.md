# hxResponse.trigger('showToast') fires a dead event in 4 apps — no built-in toast container or HX-Trigger listener

## Problem

Four apps — rideshare, storysell-ai, mngmt, and planet-positive-sport — use `hxResponse(…).trigger("showToast", { message })` in their controllers. `HX-Trigger` is the correct HTMX mechanism to fire a client-side event after a response. However, none of these apps has a client-side listener that handles `showToast`. The event is fired and silently dropped. Users get no confirmation that the action (file upload, file delete) succeeded.

The storysell products.js even has a comment acknowledging this:

```js
// storysell-ai/public/js/products.js:39-42
// ── Inline note (no toast system in this app) ────────────────────────────
//
// where the prototype called toast(). Kept deliberately minimal.
```

Rideshare has a partial workaround — a manually-built copy-paste toast element in the view, wired with bespoke JS in `public/js/main.js` — but it only covers a single specific "Link copied!" use case, not the `showToast` trigger:

```ts
// rideshare/src/rides/views/browse.view.ts:261-273
Div("Link copied!")
  .setId(ids.copyToast)
  .position("fixed")
  .opacity("0").bottom("6").right("6").transition("opacity").duration("300").pointerEvents("none")
  .background("forest")
  .textColor("white")
  ...
  .zIndex("50"),
```

```ts
// rideshare/src/files/files.controller.ts:63
const { html, headers } = hxResponse(Empty())
  .trigger("showToast", { message: "File uploaded successfully" })
  .build();
```

The `hxResponse.trigger` API is correct and idiomatic. What's missing is the receiver: a built-in `ToastContainer()` component and the associated `htmx:showToast` listener JS.

## Evidence

All four apps use the identical pattern:

```ts
// rideshare/src/files/files.controller.ts:63
hxResponse(Empty()).trigger("showToast", { message: "File uploaded successfully" })

// storysell-ai/src/files/files.controller.ts:104
hxResponse(Empty()).trigger("showToast", { message: "File uploaded successfully" })

// mngmt/src/files/files.controller.ts:63
hxResponse(Empty()).trigger("showToast", { message: "File uploaded successfully" })

// planet-positive-sport/src/files/files.controller.ts:28
hxResponse(Empty()).trigger("showToast", { message, type: "error" })
```

pps is the only app that passes a `type` field, suggesting developers have independently evolved the payload shape — evidence of convergent need without a shared contract.

Searching all public JS directories in all four apps for a `showToast` event listener returns zero results. The event is dead in every app.

## Why it matters

Toasts/snackbars are the canonical success-feedback pattern for HTMX actions (file upload, save, delete). The `hxResponse.trigger()` API is exactly the right tool — but without a built-in container in the layout, the pattern fails silently. Four apps have adopted the server-side half and omitted the client-side half, meaning they have broken UX today. Frequency × pain is high: every action that should confirm success is silent.

## Rough idea (not a design)

A `ToastContainer()` component, meant to be included once in the shared layout, that contains a small inline `<script>` listening for `htmx:show-toast` (or `document.addEventListener('showToast', ...)`) and dynamically appending styled, auto-dismissing toast elements. The container is SSR-friendly (no initial state, pure JS-driven). The `hxResponse.trigger("showToast", { message, variant? })` payload shape gets a typed helper — e.g. `hxResponse(content).toast(message, "success")` — with a defined schema so all apps converge on the same payload. The script stays small (no deps, no external lib).
