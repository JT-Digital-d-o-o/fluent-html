# No behavior for conditional show/hide on input/change events; devs hand-write hx-on:change classList expressions

## Problem

The `.behavior()` system hardcodes the event type per behavior (e.g. `toggle` always emits `hx-on:click`). Developers who need to show/hide an element conditionally based on a `change` or `input` event have no built-in option and reach for `addAttribute("hx-on:change", ...)` directly.

The most common case is a checkbox or select controlling the visibility of a related section:

```ts
// planet-positive-sport/src/loc/sdg/sdg.view.ts:74
Input()
  .setType("checkbox")
  ...
  .addAttribute("hx-on:change", `document.getElementById('${textareaId}-wrap').classList.toggle('hidden', !this.checked)`),
```

This expression is richer than the simple `classList.toggle('hidden')` that `.behavior("toggle")` emits — it uses the `force` parameter (`toggle('hidden', !this.checked)`) to synchronize the element's visibility with the checkbox state rather than blindly flipping it.

A second pattern is the inline dismiss animation for toast/alert elements:

```ts
// planet-positive-sport/src/shared/components/display/display.ts:35
.addAttribute("hx-on:click", "const el=this.closest('[role=alert]');el.classList.add('animate-fade-out');el.addEventListener('animationend',()=>el.remove())")
```

This isn't a simple `remove()` (which `.behavior("remove")` covers) — it needs to add a CSS animation class first and wait for the animation to finish before removing. `.behavior("remove")` doesn't support an exit animation.

A third pattern is toggle-hidden bound to a specific id that's simpler but still forces `addAttribute`:

```ts
// planet-positive-sport/src/admin/organizations/organizations.detail.view.ts:66
function toggleHidden(id: string) {
  return `document.getElementById('${id}').classList.toggle('hidden')`;
}
// ...
.addAttribute("hx-on:click", toggleHidden(rejectModalId)),
```

Note: this is a click-based toggle just like `.behavior("toggle")` but the dev doesn't use `.behavior("toggle")` — likely because they're already in a context where `addAttribute` is the established pattern for JS strings on this element.

- `planet-positive-sport/src/loc/sdg/sdg.view.ts:74` — `hx-on:change` with `classList.toggle(class, force)` binding checkbox state to a section's visibility
- `planet-positive-sport/src/shared/components/display/display.ts:35` — dismiss button with CSS animation before DOM removal
- `planet-positive-sport/src/admin/organizations/organizations.detail.view.ts:66` — `toggleHidden` string helper bypassing `.behavior("toggle")`
- `planet-positive-sport/src/admin/organizations/organizations.view.ts:72` — second independent `toggleHidden` string helper
- Pattern documented in `emission-factors.utils.ts:100`: "One-shot expressions — bound to `hx-on:input` / `hx-on:change` / `hx-on:click`"

## Why it matters

The `.behavior()` system's hardcoded `click` event type is the root constraint. Developers who need a behavior on a non-click event must abandon `.behavior()` entirely and use `addAttribute`. Once they're in `addAttribute` mode, they also bypass `.behavior()` for adjacent click behaviors on the same element, because mixing the two APIs on a single element is awkward.

The checkbox→section-visibility pattern is extremely common in forms and is entirely expressible as a typed behavior if the event type were a parameter. The animated dismiss is less common but represents a class of "behavior with a guard condition or transition" that the current system can't express.

## Rough idea (not a design)

Two extensions: (1) Allow `.behavior()` to accept an optional `event` parameter to override the default event type (`"change"`, `"input"`, `"focus"`, etc.) — this covers the checkbox show/hide case. (2) Add `behavior("dismissAnimated", { animationClass })` that applies a CSS animation class and removes the element on `animationend` — covering the toast/alert dismiss case without raw JS.
