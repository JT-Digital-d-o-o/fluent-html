# CSS-var paren syntax `bg-(--brand)` not expressible through the type system

## Problem

Tailwind v4 changed the CSS-variable arbitrary-value syntax from square brackets `bg-[--brand]` to
parentheses `bg-(--brand)`. fluent-html's type escape hatches use **only** the bracket form
`` `[${string}]` ``. An app author wanting to reference a CSS custom property with v4's paren
syntax has no typed way to express it — they must fall through to the `(string & {})` widening
on `TailwindColor`, losing all compile-time checking.

## Evidence

The escape-hatch comment in `tailwind-types.ts` explicitly documents only the bracket form:

```ts
// fluent-html/src/core/tailwind-types.ts:9-12
// Escape hatches:
//   (string & {})   — accepts any string while preserving autocomplete.
//                      Used where custom theme tokens are common (colors, spacing).
//   `[${string}]`   — bracket-only escape hatch for arbitrary CSS values.
//                      Stricter: forces explicit bracket syntax like "[13px]".
```

`TailwindColor` provides only `string & {}` as the fallback for non-standard values:

```ts
// fluent-html/src/core/tailwind-types.ts:59-62
export type TailwindColor =
  | "inherit" | "current" | "transparent" | "black" | "white"
  | `${TailwindColorName}-${TailwindShade}`
  | (string & {});   // ← can accept "(--brand)" but also accepts "typo-color"
```

Types with `[${string}]` bracket escapes (not `string & {}`) — e.g. `TailwindTextSize`, `TailwindBlur`,
`TailwindAnimate` — have no path at all for paren-syntax CSS vars. A user typing
`.textSize("(--font-size-custom)")` gets a TypeScript error.

The v4 recon documents this as a minor gap:

```
// 00-recon/03-tailwind4.md:155-159
| CSS var arbitrary value | `bg-[--brand]` | `bg-(--brand)` (**parens**) |
```

## Why it matters

With v4's `@theme { --color-brand: oklch(…); }`, referencing a token via CSS var is the canonical
v4 pattern for values that don't map to Tailwind's utility scale (dynamic or computed colors,
semantic tokens not in the standard palette). Apps will encounter this for any `@theme` color
they define. The type system offers no ergonomic path: users must either use `string & {}` widening
(no typo detection) or reach for `addClass("bg-(--brand)")` raw strings (bypassing fluent methods
entirely).

Pain is medium rather than high because the `string & {}` fallback still works at runtime;
the cost is purely compile-time safety.

## Rough idea (not a design)

Extend the bracket escape-hatch pattern to also admit `(--${string})` (CSS-var paren form) on
`TailwindColor` and other types where it makes sense. The template-literal type
`` | `(--${string})` `` is narrow enough to reject `(anything)` while permitting `(--brand)`.
Combined with `defineTheme()` (F-C-051), this would let the generated token types flow directly
into fluent method arguments without any `string & {}` escape.
