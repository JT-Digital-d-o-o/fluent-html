# Bare `.border()` default color changes from `gray-200` to `currentColor` in Tailwind v4

## Problem

In Tailwind v3, a bare `border` class (no color argument) renders a `1px solid` border in **`gray-200`** (the theme default). In Tailwind v4, the same `border` class renders in **`currentColor`** — the element's current text color.

The fluent-html `.border()` method emits bare `border`:

```ts
// fluent-html/src/core/tailwind-methods.ts:425-427
p.border = function (directionOrValue?: string | number, value?: string | number) {
  if (directionOrValue === undefined) return this.addClass("border");
  ...
```

There is no type-system warning, no lint rule, and no migration note. Every site that calls `.border()` without an explicit `.borderColor(...)` will silently render borders in the text color instead of a neutral gray, which in dark-text contexts means black or near-black borders everywhere.

## Evidence

The ttl app has 64+ bare `.border()` calls (no `borderColor` chained), including layout-critical elements:

```ts
// ttl/src/settings/settings.view.ts:55 — card border
.border()

// ttl/src/home/views/landing.components.ts:146 — section separator
.border()

// ttl/src/home/views/landing.components.ts:174 — card border
.border()

// ttl/src/home/views/landing.components.ts:215 — card border
.border()
```

These all expect a subtle gray-200 border (the v3 default). After a v4 upgrade, they render in the text color instead, turning subtle card outlines into high-contrast borders.

Searching the ttl src directory:

```
$ grep -rn "\.border(" ttl/src --include="*.ts" | grep -v "borderColor\|borderStyle\|borderWidth" | wc -l
64
```

## Why it matters

This is a **pervasive, silent visual regression** — the same class name, the same method call, a completely different rendered appearance. It affects cards, form inputs, separators, and other components that rely on subtle neutral borders. The frequency (64+ sites in one app) and the visual impact (border color changing from subtle gray to text color) make this high-pain. Like the ring default change (F-C-004), there is no compile error and no lint warning to catch it.

## Rough idea (not a design)

Add a migration note to `TAILWIND-SETUP.md` listing the border default color change alongside ring and outline. For the ESLint plugin, when `tailwindTarget: 'v4'` is configured (per F-C-024's dual-target mechanism), flag bare `.border()` calls (without a `.borderColor(...)` in the same chain) with a message: "In Tailwind v4, bare `border` renders in `currentColor`, not `gray-200` — add explicit `.borderColor('gray-200')` to preserve v3 appearance." This is autofix-safe.
