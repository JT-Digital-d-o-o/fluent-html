# Three independent copies of class-generation logic with no shared codegen

## Problem

Every fluent method that maps to a Tailwind class name is implemented **three times**, independently:

1. **`fluent-html/src/core/tailwind-methods.ts`** — the runtime `p.gradientTo = function(direction) { return this.addClass(\`bg-gradient-\${direction}\`) }` (L576)
2. **`fluent-html-tailwind-extractor/src/index.ts`** — `METHOD_PATTERNS` entry `{ methodName: "gradientTo", generateClass: (args) => [\`bg-gradient-\${args[0]}\`] }` (L391)
3. **`fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts`** — `FIXABLE_PATTERNS` entry `{ pattern: "bg-gradient-", methodName: "gradientTo" }` (L384)

```ts
// fluent-html/src/core/tailwind-methods.ts:576
p.gradientTo = function (direction: string) { return this.addClass(`bg-gradient-${direction}`); };

// fluent-html-tailwind-extractor/src/index.ts:391
{
  methodName: "gradientTo",
  generateClass: (args) => args.length === 1 ? [`bg-gradient-${args[0]}`] : [],
},

// fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384
{ pattern: "bg-gradient-", methodName: "gradientTo" },
```

All three use `bg-gradient-*` — the v3 class prefix. In v4 this must become `bg-linear-*`. That means **three separate edits across three packages**, with no compile-time guarantee that all three agree. The shadow scale shift (`shadow`/`shadow-sm`/`shadow-xs`), the ring default change, and every other v4 rename present the same triple-edit problem.

## Evidence

- `fluent-html/src/core/tailwind-methods.ts:576` — runtime emit of `bg-gradient-${direction}`
- `fluent-html-tailwind-extractor/src/index.ts:391` — extractor emit of `bg-gradient-${args[0]}`
- `fluent-html-eslint-plugin/src/rules/no-known-modifiers-in-setclass.ts:384` — ESLint fix pattern `bg-gradient-`

The recon doc (§4, "Cross-cutting decisions to encode") explicitly identifies this: *"Three copies of the generation logic (methods, extractor, eslint map) must agree on the target."*

Additional triple-edit sites:
- `shadow` / `shadow-${value}` (methods L451; extractor L289; eslint L222–231)
- `rounded` / `rounded-${value}` (methods L442; extractor L266; eslint L212–220)
- `blur` / `blur-${value}` (methods L596; extractor L415; eslint — via prefix `blur-`)
- `ring` / `ring-${value}` (methods L533; extractor L297; eslint L285–290)
- `outline-${value}` (methods L568; extractor L283; eslint L343)

Each v4 migration item hits all three simultaneously with no shared type that would cause a compile error if they disagree.

## Why it matters

This is the root structural reason Track C work is expensive and brittle. The v4 migration surface (gradient rename, shadow scale shift, outline split, ring default change) requires 3× the edits of what would be needed with a shared source of truth. More importantly, it is easy to update one or two of the three and miss the third — yielding a state where the lib emits `bg-linear-*` but the ESLint plugin still suggests `bg-gradient-*`, or the extractor still generates `bg-gradient-*` classes for Tailwind's scanner. These inconsistencies are silent: no TypeScript error crosses package boundaries.

## Rough idea (not a design)

Create a single `packages/class-map/` module (or a JSON/TS file within the lib) that maps each fluent method name to its class-template and version-specific variants. A lightweight codegen script (run as a build step) derives:
- The extractor's `METHOD_PATTERNS` array
- The ESLint plugin's `FIXABLE_PATTERNS` array

The `tailwind-methods.ts` runtime calls remain hand-written (they are trivial one-liners), but the template string (e.g. `"bg-gradient-"` vs `"bg-linear-"`) could be imported from the shared map so a v4 toggle in one place propagates everywhere.
