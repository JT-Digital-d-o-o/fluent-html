# `.outline("none")` becomes a real a11y regression on Tailwind v4

## Problem

In Tailwind v3, `outline-none` set `outline: 2px solid transparent; outline-offset: 2px` — it kept the outline present in the DOM for accessibility/keyboard tools, just made it visually invisible. This was the canonical pattern for custom focus ring styling (`.on("focus", t => t.borderColor("blue").outline("none"))`).

In Tailwind v4, the semantics split into **two** utilities:

| v4 class | CSS | a11y |
|---|---|---|
| `outline-hidden` | Same as v3 `outline-none` — invisible but present | Safe |
| `outline-none` | `outline-style: none` (real none) | **Removes outline entirely** |

`.outline("none")` still emits `outline-none`, which now does `outline-style: none`. Any element using `.outline("none")` for focus ring suppression will have its outline **completely removed** on v4 — an accessibility regression with no compile error or visual difference in the non-focused state.

The current type and method:

```ts
// fluent-html/src/core/tailwind-types.ts:165
export type TailwindOutline = "none" | "dashed" | "dotted" | "double";

// fluent-html/src/core/tailwind-methods.ts:568
p.outline = function (value: string) { return this.addClass(`outline-${value}`); };
```

There is no `"hidden"` in `TailwindOutline`, so there is currently no type-safe way to emit `outline-hidden` at all — users would need `addClass("outline-hidden")` directly.

The extractor correctly generates `outline-none`:

```ts
// fluent-html-tailwind-extractor/src/index.ts:282-284
{
  methodName: "outline",
  generateClass: (args) => args.length === 0 ? ["outline"] : [`outline-${args[0]}`],
},
```

## Evidence

The rideshare app uses `.outline("none")` in 5 distinct places as the standard focus-style suppression pattern:

```ts
// rideshare/src/rides/views/browse.view.ts:184
.outline("none").cursor("pointer")

// rideshare/src/rides/views/create.view.ts:63
.outline("none")

// rideshare/src/rides/views/create.view.ts:340
.transition("colors").on("focus", t => t.borderColor("leaf").outline("none"))

// rideshare/src/auth/auth.components.ts:31
.outline("none").transition("colors")
```

Every one of these is using the v3 "safe" pattern. On v4 they all become `outline-style: none`, meaning keyboard users get no focus indicator.

## Why it matters

This is an accessibility regression that is invisible to sighted users and to automated style checks. It affects every input, button, and interactive element where `.outline("none")` is used for focus ring customization — i.e., essentially all of them. No compile error, no runtime warning, no visual change until a keyboard user tries to navigate.

## Rough idea (not a design)

Under the v4 target:
- Add `"hidden"` to `TailwindOutline` (or add a dedicated `.outlineHidden()` method that emits `outline-hidden`)
- Deprecate or ESLint-flag `.outline("none")` with a suggestion to use `.outlineHidden()` / `outline-hidden`
- Update the extractor to emit `outline-hidden` when the v4 target is active and value is `"none"` (or add a separate `outlineHidden` pattern)
- Update `no-known-modifiers-in-setclass` to flag `outline-none` in `setClass()` with an auto-fix to `outline-hidden`
