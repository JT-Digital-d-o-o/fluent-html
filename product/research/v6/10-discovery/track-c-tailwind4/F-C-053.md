# Extractor regex silently drops dynamic custom-token calls; v4 `@source inline()` makes this more critical

## Problem

The `fluent-html-tailwind-extractor` regex can only extract class names when method arguments are
**string literals** in source. If an argument is a variable, ternary, or computed expression, the
extractor produces zero classes — it does fire a warning, but the warning is opt-in (`onWarning`
callback), and the missed class silently becomes unstyled at runtime.

Under Tailwind v3 this is a nuisance: the `content.extract` hook runs on file content and the JIT
scanner sees the live Tailwind config with full color definitions, so statically-known colors
typically still generate CSS. Under Tailwind v4 the extractor is being redesigned to emit a
`@source inline("class list")` block — in that model, any class the extractor misses is **100%
absent from the stylesheet**, with no fallback.

## Evidence

`extractMethodArgs` in the extractor matches only literal string arguments:

```ts
// fluent-html-tailwind-extractor/src/index.ts:549-564
function extractMethodArgs(content: string, methodName: string): string[][] {
  const regex = new RegExp(
    `\\.${methodName}\\s*\\(\\s*` +
    `(?:` +
      `(?:` +
        `"([^"]*)"` +          // ← double-quoted literal only
        `|` +
        `'([^']*)'` +          // ← single-quoted literal only
      `)` +
      // ... no path for variables, template literals, or expressions
    `)?` +
    `\\s*\\)`,
    "g"
  );
  // ...
}
```

The warn path exists but is opt-in and unlogged by default:

```ts
// fluent-html-tailwind-extractor/src/index.ts:726-735
if (warn) {
  for (const pattern of METHOD_PATTERNS) {
    const callRegex = new RegExp(`\\.${pattern.methodName}\\s*\\(`, "g");
    const callMatches = [...stripped.matchAll(callRegex)];
    const extracted = extractMethodArgs(stripped, pattern.methodName);
    if (callMatches.length > extracted.length) {
      const unresolved = callMatches.length - extracted.length;
      warn(`${unresolved} unresolved .${pattern.methodName}() call(s) — arguments may use variables or expressions`);
    }
  }
}
```

In `rideshare`, the 11 custom colors (456 call-sites) are **always** used as inline literals
(`".background("forest")`), so the regex happens to work today. But this is fragile: as soon
as a component abstracts a color into a variable — `const btnColor = condition ? "leaf" : "moss"` —
and calls `.background(btnColor)`, both `leaf` and `moss` are dropped silently.

The rideshare `tailwind.config.js` defines a combined extractor that appends a raw `defaultExtractor`
regex as a workaround:

```js
// rideshare/tailwind.config.js:3-11
const defaultExtractor = (content) => {
  return content.match(/[a-zA-Z0-9_\-:\/]+(?:\[[^\]]+\])?[a-zA-Z0-9_\-]*/g) || [];
};
const combinedExtractor = (content) => {
  const lambdaClasses = fluentHtmlExtractor(content);
  const twClasses = defaultExtractor(content);
  return [...lambdaClasses, ...twClasses];
};
```

This workaround leaks ALL identifiers in source to Tailwind (polluting the safelist with
non-class strings) and only works under v3's `content.extract` hook — it disappears entirely
in v4.

## Why it matters

Under v4's `@source inline()` redesign (the planned resolution of blocker B-1 from the recon),
every class the extractor fails to emit becomes genuinely absent from the stylesheet. The dynamic
argument miss goes from "annoying but often workable" to a hard correctness bug. Apps with
custom `@theme` tokens — exactly the apps that will benefit most from v4 — are most exposed,
because those tokens are not in Tailwind's standard vocabulary and won't be rescued by automatic
detection.

Both production apps (rideshare, ttl) use custom color tokens heavily (456 and 92 call-sites
respectively), and both have already adopted the workaround `combinedExtractor` pattern — a signal
that the base extractor is known to be insufficient.

## Rough idea (not a design)

The correct v4 story is a **static class manifest**: a build step that resolves all theme tokens
at build time (from `defineTheme()` output, F-C-051) and emits `@source inline("bg-forest
text-leaf …")` covering all permissible combinations. This is fundamentally more reliable than
regex-on-source for any method whose argument set is finite and known from the theme definition.
Dynamic arguments (variables) would still be a gap, but the manifest would cover the entire
token vocabulary by construction. The warning path should become a hard error (or at minimum a
CI-visible log line) when building for v4.
