# ESLint `no-conflicting-classes-in-setclass` has no gradient conflict group

## Problem

The `no-conflicting-classes-in-setclass` rule catches mutually-exclusive Tailwind classes via two data structures: `CONFLICT_GROUPS` (exact-match groups, line 4) and `PREFIX_CONFLICTS` (prefix-based, line 102). Neither includes gradient-related classes:

```ts
// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:102-140
const PREFIX_CONFLICTS: string[] = [
  "p-", "px-", /* ... spacing ... */
  "rounded-", "border-",
  "ring-",
  "blur-", /* ... filters ... */
  "backdrop-blur-", /* ... backdrop filters ... */
  "transition-", "duration-", "animate-",
  "scale-", "rotate-", "translate-x-", "translate-y-",
  // ↑ No "bg-gradient-", "bg-linear-", "bg-radial-", "bg-conic-" anywhere
];
```

This means ESLint will not detect:
- `setClass("bg-gradient-to-r bg-gradient-to-l")` — two v3 directions on the same element
- `setClass("bg-linear-to-r bg-linear-to-b")` — two v4 directions
- `setClass("bg-gradient-to-r bg-linear-to-l")` — mixing v3 and v4 class names (a v3→v4 migration artifact)
- `setClass("bg-linear-to-r bg-radial-at-center")` — mixing gradient types in v4

## Evidence

The `CONFLICT_GROUPS` array (lines 4–99) and `PREFIX_CONFLICTS` array (lines 102–140) cover every major utility family — spacing, color, typography, flexbox, transforms, filters, backdrop filters, ring — but omit the gradient family entirely. A search for `gradient`, `linear`, `radial`, `conic` in the file returns zero results:

```ts
// fluent-html-eslint-plugin/src/rules/no-conflicting-classes-in-setclass.ts:4-99
const CONFLICT_GROUPS: string[][] = [
  // Display, Position, Flex, Justify, Align... but no gradient family
];
```

The `bg-` prefix IS in `PREFIX_CONFLICTS` indirectly — no, it is not; `bg-` is only in `FIXABLE_PATTERNS` (the auto-fix map in `no-known-modifiers-in-setclass.ts`). The conflict rule has no coverage for background-image utilities at all.

This gap exists in v3 too (a user could write `bg-gradient-to-r bg-gradient-to-l` and the plugin would not catch it), but the problem becomes more acute in v4 because there are now three competing gradient family prefixes (`bg-linear-`, `bg-radial-`, `bg-conic-`) that all override each other, plus the legacy `bg-gradient-` that v3 users might mix in.

## Why it matters

The gradient conflict gap is currently low-frequency in raw `setClass()` usage (most gradient use goes through `.gradientTo()` fluent method), but becomes relevant:
1. During a v3→v4 migration, when both `bg-gradient-to-r` (old) and `bg-linear-to-r` (new) might appear in the same string during an incremental migration
2. For any user who uses `setClass()` or `addClass()` to apply gradient classes directly (e.g. custom theme utility strings, or Tailwind plugin-generated classes)
3. As v4 new features (radial, conic) see adoption

The fix is purely additive (adding prefixes to `PREFIX_CONFLICTS`) and has zero breaking-change risk.

## Rough idea (not a design)

Add the following to `PREFIX_CONFLICTS` in `no-conflicting-classes-in-setclass.ts`:

```ts
"bg-gradient-",   // v3 linear gradient direction (conflicts with other bg-gradient- directions)
"bg-linear-",     // v4 linear gradient (conflicts with bg-radial-, bg-conic-, other bg-linear-)
"bg-radial-",     // v4 radial gradient
"bg-conic-",      // v4 conic gradient
```

Because these are different prefix strings, the current prefix-based logic will group them separately (not as a single conflict group across family types). To catch cross-family conflicts (`bg-linear-to-r bg-radial-at-center`), a CONFLICT_GROUPS entry listing all four families as a single group would be needed — that is the more correct fix.
