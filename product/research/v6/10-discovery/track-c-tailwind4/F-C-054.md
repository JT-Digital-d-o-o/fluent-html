# Both apps duplicate a `combinedExtractor` workaround because the package doesn't export one

## Problem

Both `rideshare` and `ttl` define an identical workaround in their `tailwind.config.js`: a
`combinedExtractor` that calls `fluentHtmlExtractor` plus a raw regex fallback
(`content.match(/[a-zA-Z0-9_\-:\/]+…/g)`). The reason: `fluentHtmlExtractor` alone misses
standard Tailwind classes in HTML `class=""` attributes and template literals that aren't
fluent method calls. The package's internal `extractDefaultClasses` function covers this, but
it is not exported.

## Evidence

`rideshare/tailwind.config.js:1-11`:

```js
const { fluentHtmlExtractor } = require("fluent-html-tailwind-extractor");

const defaultExtractor = (content) => {
  return content.match(/[a-zA-Z0-9_\-:\/]+(?:\[[^\]]+\])?[a-zA-Z0-9_\-]*/g) || [];
};

const combinedExtractor = (content) => {
  const lambdaClasses = fluentHtmlExtractor(content);
  const twClasses = defaultExtractor(content);
  return [...lambdaClasses, ...twClasses];
};
```

`ttl/tailwind.config.js:1-11` is structurally identical (same regex, same wrapper pattern).

The extractor already has this internally:

```ts
// fluent-html-tailwind-extractor/src/index.ts:688-691
function extractDefaultClasses(content: string): string[] {
  const matches = content.match(/[:\w\-/.@#[\]]+(?:\([^)]*\))?/g);
  return matches || [];
}
```

And it is called inside `fluentHtmlExtractor` (line 706-708). So the combined behavior is
**already the default** — but users don't know that, and the README doesn't clearly state it.
They cargo-culted the workaround because the documentation shows `content.extract: { ts: fluentHtmlExtractor }` without explaining that the default-candidate pass is built in.

The two hand-rolled regexes are subtly different from `extractDefaultClasses` (character class
width, presence/absence of `@#` chars, paren handling) — creating an inconsistency between what
apps extract and what the package actually does internally.

## Why it matters

Two independent apps arrived at the same workaround independently. That is a DX signal. In v4,
when `content.extract` is removed, this workaround evaporates silently — apps must update their
config — but there is no documented guidance. The inconsistency between the hand-rolled regex and
the internal one also means apps may be extracting slightly different class sets than intended.

## Rough idea (not a design)

1. Clarify the README: state explicitly that `fluentHtmlExtractor` already includes default
   candidate extraction — apps don't need the workaround.
2. Remove the workaround from both app configs.
3. For v4: export a `createFluentHtmlPlugin()` (Vite/PostCSS plugin) that encapsulates the
   `@source inline()` emission, so the migration is a one-line change in each app's config.
