# No `.containerQuery()` fluent method to emit the `@container` marker class

## Problem

Tailwind v4 ships container queries as a first-class built-in feature. The responsive pattern requires two cooperating pieces:

1. A **parent element** marked with `@container` (or `@container/name` for named scopes) — this element becomes the sizing reference.
2. **Child elements** that use `@sm:`, `@md:`, `@max-lg:` etc. variants (covered separately in F-C-043 for the `.at()` type gap).

There is no fluent method in fluent-html to emit the `@container` marker. The only path today is:

```ts
// fluent-html/src/core/tailwind-methods.ts — no containerQuery() anywhere
Div().addClass("@container")              // forced addClass escape hatch
Div().addClass("@container/sidebar")     // named scope — no fluent equivalent
```

The extractor's `METHOD_PATTERNS` array (index.ts:56–540) has no entry for `containerQuery`, so even if a user calls `addClass("@container")`, that class is only picked up by the fallback `extractDefaultClasses` regex — not explicit method-level extraction.

## Evidence

```ts
// fluent-html/src/core/tailwind-types.ts:191
export type TailwindBreakpoint = "sm" | "md" | "lg" | "xl" | "2xl";
// ↑ no @container marker support anywhere in the type system

// fluent-html-tailwind-extractor/src/index.ts:56–540
const METHOD_PATTERNS: MethodPattern[] = [
  // ... 80+ entries for padding, margin, bg, text, ring, shadow, blur, etc.
  // ↑ no "containerQuery" entry — @container must be discovered by fallback regex
];
```

The `.at()` method's `withVariant` would correctly prepend `@sm:` as a CSS class prefix (F-C-043 covers the type constraint on that side). But the `@container` marker on the parent — which enables the scoping — has no first-class API path at all.

## Why it matters

Container queries are the primary responsive-design feature of Tailwind v4, replacing many `md:` viewport breakpoint patterns for reusable component grids, card layouts, and sidebars. Developers who adopt v4 and want to use container queries must bypass the fluent API for the parent element (`Div().addClass("@container")`), which:
- Is not type-safe (any typo in the string is silently wrong)
- Is not in the extractor's explicit `METHOD_PATTERNS` (relying on fallback detection)
- Creates a `addClass` dependency at every container root — visible friction in a codebase that otherwise avoids `addClass`
- Named containers (`@container/sidebar`) add a scope that child `.at("@sm/sidebar", ...)` would use, making the parent marker even more important to get right

## Rough idea (not a design)

Add a `.containerQuery(name?: string)` method to `tailwind-methods.ts` that emits `@container` or `@container/${name}`. Add a corresponding `METHOD_PATTERNS` entry in the extractor. The RFC can decide whether this merges with F-C-043 (type gap for `.at("@sm",...)`) into a single "container query support" RFC or ships separately. These two changes are tightly coupled — a container query scoping method without typed child variants is half a feature.
