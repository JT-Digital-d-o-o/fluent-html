# Responsive breakpoint callbacks (.at()) under-taught for gridCols

## Problem

The guidelines teach `.at("md", t => t.padding("x", "8").textSize("lg"))` — an example using padding and text size — but never show `.at()` being used to change `gridCols`. Developers learning from these examples understand `.at()` for typography/spacing but not for layout mutations. Five call-sites across the ttl app escape to raw `addClass("sm:grid-cols-N")` strings instead of the equivalent `.at("sm", t => t.gridCols("N"))` fluent path.

## Evidence

```ts
// ttl/src/time-entry/views/time-entry.view.ts:134 — escape hatch for responsive grid
.grid().gridCols("1").addClass("sm:grid-cols-2")
// ✓ Correct fluent form:
.grid().gridCols("1").at("sm", t => t.gridCols("2"))

// ttl/src/time-entry/views/time-entry.view.ts:178 — same pattern
.grid().gridCols("1").addClass("sm:grid-cols-3")
// ✓ .grid().gridCols("1").at("sm", t => t.gridCols("3"))

// ttl/src/dashboard/views/dashboard.view.ts:108 — two breakpoints in one addClass string
.grid().gridCols("1").addClass("md:grid-cols-2 lg:grid-cols-3")
// ✓ .grid().gridCols("1").at("md", t => t.gridCols("2")).at("lg", t => t.gridCols("3"))

// ttl/src/dashboard/views/dashboard.components.ts:206
.addClass("sm:grid-cols-4")
// ✓ .at("sm", t => t.gridCols("4"))

// ttl/src/admin/views/project-detail.view.ts:261
.addClass("sm:grid-cols-5")
// ✓ .at("sm", t => t.gridCols("5"))
```

The guideline's `.at()` example (CLAUDE.md line ~155, fluent-html.md) only shows:
```ts
Button("Save").at("md", t => t.padding("x", "8").textSize("lg"))
```

No layout methods (`gridCols`, `flexDirection`, `display`) appear in any `.at()` example.

## Why it matters

The raw string `addClass("sm:grid-cols-2")` is type-unsafe and bypasses the extractor's pattern-matching (the extractor has a pattern for `gridCols` method calls, not for arbitrary `sm:grid-cols-N` strings in `addClass`). Under Tailwind v4's automatic Oxide detection, the class string in `addClass()` IS visible to the scanner — but under the v3 extractor setup, such classes go through the `extractDirectClasses` fallback regex rather than the typed `gridCols` pattern. More importantly, this silently teaches developers that `.at()` is only for spacing/typography, reinforcing the escape-to-addClass habit for any responsive layout change.

Additionally, line 108 in dashboard.view.ts packs two breakpoints into a single `addClass` string (`"md:grid-cols-2 lg:grid-cols-3"`), which is harder to read and impossible for the ESLint conflict-detection rule to analyze (it can't detect that these are complementary, not conflicting, classes).

Frequency: 5 call-sites in ttl, 0 in rideshare (rideshare uses responsive grid via `.at()` correctly for other properties but has fewer responsive-grid patterns). The pattern is likely more widespread in apps with data-grid UI.

## Rough idea (not a design)

Add a grid layout example to the `.at()` section of `guidelines/web-development/fluent-html.md`:

```ts
// ✓ responsive layout via .at()
Div().grid().gridCols("1").gap("4")
  .at("sm", t => t.gridCols("2"))
  .at("lg", t => t.gridCols("3"))

// ✗ escape-hatch raw string — bypasses type-safety and extractor
Div().grid().gridCols("1").gap("4").addClass("sm:grid-cols-2 lg:grid-cols-3")
```

No code change needed.
