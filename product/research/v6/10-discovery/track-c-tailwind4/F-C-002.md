# shadow/rounded/blur scale shift in Tailwind v4 causes silent visual regressions

## Problem

Tailwind v4 shifted the named scale for shadows, border-radius, and blur by one slot:

| v3 class | v4 class | CSS value |
|---|---|---|
| `shadow` | `shadow-sm` | was `shadow-sm` |
| `shadow-sm` | `shadow-xs` | was `shadow` |
| `rounded` | `rounded-sm` | was `rounded-sm` |
| `rounded-sm` | `rounded-xs` | — new slot |
| `blur` | `blur-sm` | — |
| `blur-sm` | `blur-xs` | — |

fluent-html's type tables do NOT include the new `xs` slot:

```ts
// fluent-html/src/core/tailwind-types.ts:77
export type TailwindRounded = "none" | "sm" | "md" | "lg" | "xl" | "2xl" | "3xl" | "full" | `[${string}]`;
//                                     ^^^^  no "xs"

// fluent-html/src/core/tailwind-types.ts:81
export type TailwindShadow = "sm" | "md" | "lg" | "xl" | "2xl" | "inner" | "none" | (string & {});
//                            ^^^^  no "xs"

// fluent-html/src/core/tailwind-types.ts:205
export type TailwindBlur = "none" | "sm" | "md" | "lg" | "xl" | "2xl" | "3xl" | `[${string}]`;
//                                   ^^^^  no "xs"
```

The methods themselves pass the value through verbatim:

```ts
// fluent-html/src/core/tailwind-methods.ts:451-453
p.shadow = function (value?: string) {
  return value === undefined ? this.addClass("shadow") : this.addClass(`shadow-${value}`);
};

// fluent-html/src/core/tailwind-methods.ts:442-450
p.rounded = function (cornerOrValue?: string, value?: string) {
  if (cornerOrValue === undefined) return this.addClass("rounded");
  ...
  return this.addClass(`rounded-${cornerOrValue}`);
};

// fluent-html/src/core/tailwind-methods.ts:596-598
p.blur = function (value?: string) {
  return value === undefined ? this.addClass("blur") : this.addClass(`blur-${value}`);
};
```

## Evidence

Because the class names themselves are unchanged (`.shadow("sm")` still emits `shadow-sm`, which is still a valid v4 class), there is no build error and no type error. But on v4 `shadow-sm` renders as a *smaller* shadow than it did on v3 — every card, button, and input that uses `.shadow("sm")` will look visually different after a v4 upgrade.

The extractor mirrors the same bare-strings-through pattern (L266 for rounded, L289 for shadow), so it will happily emit `shadow-sm` for CSS generation — Tailwind will compile it, but to the wrong visual weight.

Observed in shipped apps:
- `ttl/src/analytics/analytics.view.ts:150,517,687` — `.shadow("sm")` on stat cards
- `ttl/src/settings/settings.view.ts:415` — `.shadow("sm")` on settings panel
- `rideshare/src/settings/settings.view.ts:57,79,497` — `.shadow("sm")` on profile sections
- `rideshare/src/rides/views/browse.view.ts:272`, `rides.components.ts:266` — `.shadow("lg")` on ride cards

## Why it matters

This is the canonical "same class name, different rendered value" silent regression. Every shipped app using `.shadow("sm")` will have its shadows shrink on v4 with no warning. Frequency is high (approx 29 `.shadow()` call-sites across two apps alone); pain is high because the visual change is subtle enough to escape casual testing.

## Rough idea (not a design)

Add `"xs"` to `TailwindShadow`, `TailwindRounded`, and `TailwindBlur`. The RFC must answer the key question: does `.shadow("sm")` on v4 continue to emit `shadow-sm` (honest pass-through, new visual) or emit `shadow-xs` (backward-visual-compat shim)? The recon doc recommends pass-through + migration note (§5 open question 5). Either way, the type tables need `xs` so users can opt in to the new scale.
