# Extractor exports only the v3 `content.extract` callback shape — no v4-compatible safelist-emitter API exists

## Problem

The extractor's sole public export is `fluentHtmlExtractor(content: string): string[]` — a per-file content callback that fits squarely into Tailwind v3's `content.extract` hook shape. Tailwind v4 removed `content.extract` entirely (the Oxide engine auto-detects content). The v4 replacement for classes that can't be auto-detected is `@source inline("class1 class2 …")` in a CSS file, but no function in the package produces that output.

Fixing the dual-target strategy therefore requires two distinct output APIs:
- v3: the existing per-file callback (`(content) => string[]`) wired into `tailwind.config.js`
- v4: a file-scanner that accumulates all classes across the project and emits a single `@source inline("…")` block to be placed in the user's CSS

Neither the package's exports nor its type signatures expose anything suitable for v4.

## Evidence

```ts
// fluent-html-tailwind-extractor/src/index.ts:698-749
export function fluentHtmlExtractor(content: string, options?: ExtractorOptions): string[] {
  // ... per-file scanning logic, returns string[]
}

// Default export for CommonJS
module.exports = fluentHtmlExtractor;
module.exports.fluentHtmlExtractor = fluentHtmlExtractor;
```

The README documents only the v3 wiring:

```js
// fluent-html-tailwind-extractor/README.md:37
extract: {
  ts: fluentHtmlExtractor,
  tsx: fluentHtmlExtractor,
```

The `peerDependencies` constraint reflects this:

```json
// fluent-html-tailwind-extractor/package.json:39-41
"peerDependencies": {
  "tailwindcss": ">=3.0.0"
}
```

There is no exported function with a signature like:

```ts
// This does NOT exist:
export function generateFluentSafelist(
  files: string[],
  options?: ExtractorOptions
): string; // → '@source inline("bg-red-500 p-4 rounded-lg …")'
```

## Why it matters

The v3→v4 migration path for extractor consumers is completely blocked at the API level — not just at the class-string level. Even if every class name in `METHOD_PATTERNS` is updated to v4 names, users cannot wire the extractor into v4 because the output shape (per-file `string[]`) has no consumer on the v4 side. This makes the extractor a v3-only package regardless of any class-string updates made elsewhere, and the dual-target strategy (F-C-024) cannot be implemented without this new output API.

## Rough idea (not a design)

Add a companion named export `generateFluentSafelist(files: string[], options?: ExtractorOptions): string` that (1) reads each file from the filesystem, (2) calls the existing per-file scanning logic on each, (3) deduplicates the resulting class list, and (4) returns the string `@source inline("class1 class2 …")` ready to be written into the user's CSS file. Keep the existing callback export unchanged for v3 consumers.
