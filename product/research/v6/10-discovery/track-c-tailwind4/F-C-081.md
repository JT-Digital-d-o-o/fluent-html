# TailwindTransition includes "transform" which silently breaks hover animations of translate/scale/rotate in Tailwind v4

## Problem

`TailwindTransition` at `src/core/tailwind-types.ts:139` includes `"transform"` as a valid value:

```ts
// fluent-html/src/core/tailwind-types.ts:139
export type TailwindTransition = "none" | "all" | "colors" | "opacity" | "shadow" | "transform";
```

Calling `.transition("transform")` emits the class `transition-transform`, which in Tailwind v3 correctly animated `translate-*`, `scale-*`, and `rotate-*` utilities because they all composed into the CSS `transform` property.

In Tailwind v4, these utilities were **decomposed into individual CSS properties** (`translate`, `scale`, `rotate`). The CSS `transform` property is no longer used for these effects. As a result, `transition-transform` targets a property that is no longer written, so hover animations using `-translate-y-*`, `scale-*`, or `rotate-*` **stop animating on Tailwind v4** — the element jumps immediately instead of transitioning.

The extractor mirrors the same broken class name:

```ts
// fluent-html-tailwind-extractor/src/index.ts:331-332
methodName: "transition",
generateClass: (args) => args.length === 0 ? ["transition"] : [`transition-${args[0]}`],
```

So `.transition("transform")` → extractor emits `transition-transform` → that CSS property no longer targets the right properties in v4.

## Evidence

Multiple call-sites in production apps use `.transition("all")` combined with `-translate-y-*` applied via `addClass` in the hover callback. While `transition-all` still works correctly (it now includes `translate`, `scale`, `rotate` as individual properties in v4), the `"transform"` slot in `TailwindTransition` is the misleading culprit: any developer who reaches for `.transition("transform")` — a natural choice when animating movement — gets silently broken hover effects.

```ts
// rideshare/src/landing/views/landing.view.ts:108
.transition("all").noUnderline().on("hover", t =>
  t.background("sage").addClass("-translate-y-0.5").shadow("lg"))

// rideshare/src/landing/landing.components.ts:42 (same pattern)
.transition("all").on("hover", t =>
  t.background("sage").addClass("-translate-y-0.5").shadow("lg"))

// rideshare/src/landing/views/browse-rides.view.ts:188
.on("hover", t => t.addClass("-translate-y-1").shadow("xl"));
// (parent card uses .transition("all") at line 186)

// rideshare/src/auth/auth.components.ts:42
.on("hover", t => t.background("sage").addClass("-translate-y-0.5").shadow("lg"))
```

These apps currently use `transition("all")` (not `"transform"`) for these patterns, which happens to still work in v4. But the `TailwindTransition` type actively advertises `"transform"` as a valid choice, and any developer switching to the more targeted `.transition("transform")` for performance reasons will hit broken animations silently.

Additionally, in Tailwind v4, the correct values to target individual transform properties are `transition-[translate]`, `transition-[scale]`, `transition-[rotate]`, or `transition-transform` for backward compatibility when also using the `transform` property directly. The type table provides no path to express these v4-idiomatic transitions.

## Why it matters

Frequency: 6 call-sites in rideshare alone using `.transition("all")` + `translate`-based hover effects; additional sites in ttl. The type `"transform"` is actively in the type table and misleads developers. The regression is completely silent — the CSS is emitted, no error, the animation just jumps instead of easing. This is especially bad for landing-page CTAs and cards where hover lift animations (`-translate-y-0.5`, `-translate-y-1`) are the primary interactive signal.

## Rough idea (not a design)

1. Remove `"transform"` from `TailwindTransition` in `tailwind-types.ts` (breaking for v4 users, additive for v3 compat).
2. Add `"[translate]"`, `"[scale]"`, `"[rotate]"` to the type as bracket-escape entries so v4 users can express targeted transitions.
3. Alternatively, if a v3/v4 target flag is adopted (see related findings), gate the `"transform"` slot on the v3 target.
4. Document in migration that `.transition("transform")` must become `.transition("[translate,scale,rotate]")` or `.transition("all")` under v4.
