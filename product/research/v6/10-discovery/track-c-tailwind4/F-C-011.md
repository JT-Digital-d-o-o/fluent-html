# Extractor uses `content.extract` hook removed in Tailwind v4; fluent classes become invisible to Oxide

## Problem

`fluent-html-tailwind-extractor` is wired into Tailwind via the `content.extract` API — a v3-only mechanism. Tailwind v4 replaced configurable content extractors with the Oxide engine's automatic content detection; there is no `extract` hook to register. Because fluent-html methods never write `bg-red-500` into source files (`.background("red-500")` → class only appended at runtime), v4's automatic scanner **cannot see any fluent-generated class names** — those utilities get no CSS generated at all. Entire pages render unstyled with no error.

## Evidence

`fluent-html-tailwind-extractor/README.md` lines 37–42 — the documented integration:
```javascript
// fluent-html-tailwind-extractor/README.md:37
content: {
  files: ['./src/**/*.{ts,tsx,js,jsx}'],
  extract: {
    ts: fluentHtmlExtractor,   // v3-only key; does not exist in v4 config
    tsx: fluentHtmlExtractor,
  },
},
```

The extractor's exported function `fluentHtmlExtractor` (index.ts line 698) is designed specifically for this callback contract. v4 has no equivalent registration point.

`package.json` line 40 (peerDependencies): `"tailwindcss": ">=3.0.0"` — no v4 range.

`fluent-html/TAILWIND-SETUP.md` lines 39–44 repeat the same `content.extract` pattern as the authoritative user-facing setup guide.

## Why it matters

This is the existential blocker for v4 support. All three packages have documented and tested workflows built around `content.extract`. A user upgrading to Tailwind v4 following any fluent-html doc gets a silently broken build — no CSS for any fluent-styled element, no error, no warning. It affects every fluent-html consumer that wants to adopt v4.

## Rough idea (not a design)

Repurpose the extractor: instead of registering a content-extractor callback, it runs at build time and writes a `.css` file containing `@source inline("bg-red-500 p-4 rounded-lg …");` (all discovered class names). The user `@imports` this file alongside `@import "tailwindcss"`. The regex logic in `METHOD_PATTERNS` is reusable; only the output format and the wiring change. Alternatively, a first-party `@tailwindcss/vite` plugin wrapping the same logic would be the most integrated solution.
