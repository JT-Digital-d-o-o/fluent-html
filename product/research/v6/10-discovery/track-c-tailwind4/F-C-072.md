# Extractor devDependency pins `tailwindcss: "^3.0.0"` — no CI test coverage for v4 class-string output

## Problem

The extractor's `devDependencies` hardcodes `"tailwindcss": "^3.0.0"`. This means every test run installs Tailwind v3 and the test suite only validates that the extractor emits v3 class names. There is no mechanism to:

1. Run the test suite against Tailwind v4
2. Assert that updated `METHOD_PATTERNS` (for the gradient rename, scale-shift, etc.) produce the correct v4 output
3. Catch regressions where a v4 update to one pattern inadvertently changes the v3 output

When the dual-target strategy (F-C-024) is implemented, each `METHOD_PATTERNS` entry will need to branch on a `target: "v3" | "v4"` option. Without a dual-version CI matrix, there is no way to verify that v3 output is preserved while v4 output produces the new class names.

## Evidence

The pinned devDependency:

```json
// fluent-html-tailwind-extractor/package.json:44
"devDependencies": {
  "tailwindcss": "^3.0.0",
```

The patterns that need to branch for v4:

```ts
// fluent-html-tailwind-extractor/src/index.ts:390-392
{
  methodName: "gradientTo",
  generateClass: (args) => args.length === 1 ? [`bg-gradient-${args[0]}`] : [],  // v3 only
},

// fluent-html-tailwind-extractor/src/index.ts:288-290
{
  methodName: "shadow",
  generateClass: (args) => args.length === 0 ? ["shadow"] : [`shadow-${args[0]}`],  // v3 scale
},

// fluent-html-tailwind-extractor/src/index.ts:265-270
{
  methodName: "rounded",
  generateClass: (args) => {
    if (args.length === 0) return ["rounded"];       // v3: 0.25rem; v4: 0.125rem (old rounded-sm)
    if (args.length === 1) return [`rounded-${args[0]}`];
    ...
  },
},
```

There is no test file that asserts `gradientTo("to-r")` → `"bg-linear-to-r"` (v4) or `shadow("sm")` → `"shadow-xs"` (v4 equivalent of v3 visual).

## Why it matters

Without CI coverage for v4 class output, any v4 migration in the extractor is untested. The three-way divergence problem (lib, extractor, ESLint — F-C-024) will be hard to catch because the extractor has no test harness that would reveal when its output disagrees with the lib's method output on a v4 target. This is also the path most likely to cause a silent regression: a developer implements the v4 class names in the lib but forgets to update or test the extractor's `METHOD_PATTERNS`, and v4 CSS simply stops generating for affected utilities.

## Rough idea (not a design)

Add a vitest workspace configuration that installs both `tailwindcss@3` and `tailwindcss@4` as optional dev deps under different workspace aliases, then runs the extractor test suite twice with a `TAILWIND_TARGET=v3|v4` environment variable. Test fixtures should assert the expected class name per target. This is a test-infrastructure change only — no production code change needed — and can land as a first step before the actual `METHOD_PATTERNS` v4 migration.
