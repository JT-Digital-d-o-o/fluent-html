# ForEach(count, fn) adoption gap — Array.from workaround instead of built-in overload

## Problem

`ForEach` has a built-in count overload: `ForEach(n, (i) => …)` renders `n` items with index `0..n-1`. Three independent apps instead write `ForEach(Array.from({ length: n }, (_, i) => i), (i) => …)` — a verbose and allocation-heavy workaround — because the guidelines only mention the count overload in a short code comment, with no ✗ anti-pattern to teach what to replace.

## Evidence

`glimm/src/auth/views/auth.onboarding.view.ts:87`:

```ts
ForEach(Array.from({ length: count }, (_, i) => i), (i) =>
  Div("").w("2")…
)
```

`gzs/inovacije/src/views/library/library.view.ts:886`:

```ts
ForEach(Array.from({ length: 4 }, (_, i) => i), (i) =>
  …
)
```

`rideshare/src/analytics/views/cohorts.view.ts:75`:

```ts
ForEach(Array.from({ length: maxPeriods }, (_, i) => i), (i) =>
  ThCell(`${periodLabel} ${i}`, "center")
)
```

All three should be:

```ts
ForEach(count, (i) => Div("").w("2")…)
ForEach(4, (i) => …)
ForEach(maxPeriods, (i) => ThCell(`${periodLabel} ${i}`, "center"))
```

The `Array.from` form allocates an intermediate array of length `n` on every render. For small `n` this is harmless, but the pattern establishes a precedent that spreads across the codebase.

## Why it matters

3 apps, each independently reinventing the same workaround. The `ForEach(n, fn)` overload already exists and handles this exactly, but the guideline presents it as a comment (`// 0..n`) without an explicit negative example. Because LLMs and developers see `Array.from` as the standard "generate a range of indices" idiom in JavaScript, the built-in overload is invisible.

## Rough idea (not a design)

Add a ✗/✓ pair in `guidelines/web-development/fluent-html.md` under the ForEach section:

```ts
// ✗ Array.from workaround — allocates, verbose
ForEach(Array.from({ length: count }, (_, i) => i), (i) => Item(i))

// ✓ built-in count overload
ForEach(count, (i) => Item(i))
```

No code change needed. Pure guidelines fix.
