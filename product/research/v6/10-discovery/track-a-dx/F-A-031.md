# Context.scope() dispose is order-sensitive; concurrent Fastify requests corrupt the stack

## Problem

`Context.scope(value)` pushes `value` onto a module-global stack and returns a `Disposable` whose `[Symbol.dispose]()` always calls `stack.pop()` — it pops whatever is currently on top, not the specific item it pushed:

```ts
// fluent-html/src/control/context.ts:78-83
scope(value: T): Disposable {
  stack.push(value);
  return {
    [Symbol.dispose]() {
      stack.pop();   // ← pops TOP, not the pushed value
    },
  };
},
```

This is correct when `scope` lifetimes are strictly LIFO (which `using` guarantees inside a synchronous block). But every app that scopes context inside Fastify lifecycle hooks (`onRequest`/`preHandler`) and disposes in `onResponse` violates LIFO under concurrent requests.

Fastify processes multiple requests concurrently. Between the moment a sync `onRequest` hook calls `done()` and the moment that request's handler runs, Fastify's event loop can execute another request's `onRequest`. Result:

```
req A onRequest: stack = [default, A_value]
req B onRequest: stack = [default, A_value, B_value]
req A handler:   ctx.current === B_value  ← WRONG
req A onResponse: disposes A's Disposable → stack.pop() removes B_value → stack = [default, A_value]
req B handler:   ctx.current === A_value  ← WRONG
req B onResponse: disposes B's Disposable → stack = [default]
```

The stack is permanently corrupted mid-request-pair. Any subsequent request reads a stale value until the server is restarted or the stack happens to recover.

## Evidence

The pattern is in the **project template** (copied to every new app):

```ts
// projects-template/templates/full-stack/src/core/i18n/i18n.plugin.ts:34-45
fastify.addHook("onRequest", (request, _reply, done) => {
  request._i18nDispose = [
    i18nTranslation.scope(tFn),   // ← pushes to global stack
    i18nLocale.scope(locale),     // ← pushes to global stack
  ];
  done();
});

fastify.addHook("onResponse", (request, _reply, done) => {
  for (const d of request._i18nDispose) d[Symbol.dispose](); // ← pops in onResponse
  done();
});
```

The same pattern is independently reproduced in:
- `glimm/src/core/i18n/i18n.plugin.ts:42-45, 57-71`
- `jt-i18n/src/core/i18n/i18n.plugin.ts:42-45, 57-71`
- `redaction-renderbox/src/core/i18n/i18n.plugin.ts:42-45, 57-71`
- `planet-positive-sport/src/auth/auth.plugin.ts:83,87`
- `planet-positive-sport/src/federation/federation.plugin.ts:159`

**The safe pattern** (`jt-vault-cloud/src/core/server.ts:101-108`) scopes in `renderView` (which is synchronous and uninterruptible) and disposes before the call returns — no concurrent interleaving possible:

```ts
// jt-vault-cloud/src/core/server.ts:101-108
function renderView(this: FastifyReply, ...views: View[]) {
  using _ = OrgCtx.scope({ active: this.request.orgContext, userOrgs: ... });
  using _nav = NavCtx.scope({ pendingApprovalCount: ... });
  this.type("text/html").send(render(...views));  // synchronous
}
```

## Why it matters

5 production apps and the canonical project template use the unsafe hook-lifecycle pattern. The bug is latent under low load but manifests under concurrent traffic: wrong locale, wrong user, wrong auth data silently served to users. The library gives no warning and the `Context` type surface provides no safe alternative pattern — no `renderWith`, no scoped-render helper.

## Rough idea (not a design)

Add `renderWithScopes(scopes: [Context<unknown>, unknown][], ...views: View[]): string` (or a `scopeForRender(scopes, fn)` helper) that scopes all provided contexts, calls the function/renders, and disposes — all in one synchronous block. This makes it physically impossible to scope across an `await` boundary. Wave 2 should also decide whether the `stack.pop()` in `Disposable` should pop a specific index (for robustness against mis-ordering), though the safer fix is API design rather than implementation hacking.
