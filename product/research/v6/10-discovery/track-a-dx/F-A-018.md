# No typed API for HTMX lifecycle event handlers (`hx-on:htmx:after:swap`, `hx-on:keydown`) — forces raw `addAttribute` with unescaped JS strings

## Problem

HTMX 4's `hx-on:*` syntax allows attaching inline JS handlers to htmx lifecycle events (e.g., `htmx:after:swap`, `htmx:before:request`) and DOM events (e.g., `keydown`). These are needed for form-reset-on-swap, escape-key dismissal, and similar patterns.

The `.behavior()` system handles the common cases (click→toggle, click→clipboard, etc.) but its built-in event map is fixed and doesn't include htmx lifecycle events or arbitrary DOM events:

```ts
// fluent-html/src/core/behavior-methods.ts:11
export type BehaviorMap = {
  toggle:     { target: Id };
  toggleClass:{ target: Id; class: string };
  remove:     { target: Id };
  clipboard:  { value: string };
  disable:    void;
  focus:      { target: Id };
  scrollTo:   { target: Id };
  selectAll:  void;
  back:       void;
  // ← no 'htmxEvent', no 'keydown', no 'formReset'
};
```

And there is no public `hxOn()` method or equivalent. So apps fall back to `addAttribute`:

```ts
// rideshare/src/settings/settings.view.ts:260
Form(/* fields */)
  .hxPost(settingsRoutes.changePassword.resolve(), { target: ids.result, swap: "outerMorph" })
  .addAttribute(
    "hx-on:htmx:after:swap",
    `if(!document.getElementById('${ids.passwordError.id}'))this.reset()`,  // ✗ unescaped JS string
  )

// rideshare/src/settings/settings.view.ts:337
.addAttribute(
  "hx-on:htmx:after:swap",
  `if(!document.getElementById('${ids.emailError.id}'))this.reset()`,      // ✗ same pattern
)

// ttl/src/time-entry/views/time-entry.view.ts:679
Div(/* ... */)
  .addAttribute(
    "hx-on:keydown",
    "if(event.key==='Escape'){this.querySelector('[type=button]').click()}",  // ✗
  )
```

## Evidence

The `addAttribute` path in `tag.ts:141` validates keys (no `on*` attributes allowed — see `EVENT_HANDLER_RE`) but crucially `hx-on:htmx:after:swap` passes this check because it starts with `hx-`, not `on`. There is no JS-level escaping of the value string. The interpolation in rideshare:

```ts
`if(!document.getElementById('${ids.passwordError.id}'))this.reset()`
```

works in practice because `Id.id` values are controlled strings, but the pattern is structurally fragile: any dynamic content interpolated into the JS string is unescaped.

The `behavior-methods.ts` already has a private `escapeJs` function (line 85) and the infrastructure to emit `hx-on:<event>` attributes (line 97). The gap is purely in the public surface — there is no extension point for custom event names or lifecycle events.

## Why it matters

The "form reset on successful swap" pattern (used in rideshare's settings forms) is one of the most common HTMX lifecycle hooks — enough to have its own htmx docs page. So is the "dismiss-on-Escape" pattern for modal-like overlays (used in ttl). Both require raw `addAttribute` with inline JS strings today:

1. The JS string is unescaped — any user-controlled value interpolated into it creates XSS.
2. The pattern is inconsistent with the library's philosophy that `.behavior()` owns the inline JS story.
3. `addAttribute` on `hx-on:` attributes cannot be chained safely — calling `addAttribute("hx-on:keydown", js1)` then `addAttribute("hx-on:keydown", js2)` would overwrite, not append (unlike `.behavior()` which concatenates with `;`).

## Rough idea (not a design)

Option A: **Extend `BehaviorMap`** with htmx lifecycle behaviors:
```ts
formResetOnSwap: void;  // emits hx-on:htmx:after:swap → "this.reset()"
```
This covers the two known patterns without exposing raw JS strings.

Option B: **Add `.hxOn(event, js)` escape hatch** that emits `hx-on:<event>` via the same concatenation logic as `.behavior()`, using the existing `escapeJs` for the JS value. This is more flexible but accepts raw JS — should be documented as "last resort, ensure no user content is interpolated."

Option A is safer (no XSS surface); Option B is more flexible for one-off patterns. Both can coexist.
