# `hx-confirm` is a typed `HTMX` option but guidelines only show it via `addAttribute` — 5 app call-sites use the escape hatch

## Problem

The `HTMX` interface has a typed `confirm?: string` field:

```ts
// fluent-html/src/htmx.ts:217
export interface HTMX {
  // ...
  validate?: boolean;
  confirm?: string;   // ← exists and is serialized correctly
  // ...
}
```

This means the following is fully valid:

```ts
// ✓ correct — typed, part of setHtmx options
Button("Delete").hxDelete(deleteRoute.resolve({ id }), {
  target: ids.mainContent,
  swap: "outerMorph",
  confirm: "Are you sure you want to delete this?",
})
```

But the guidelines only document `hx-confirm` via a raw `addAttribute` in an inheritance example, never as part of the typed options object:

```ts
// guidelines/web-development/htmx.md:182  — the only mention of hx-confirm
Div(
  Button("Delete 1").hxDelete("/item/1"),
  Button("Delete 2").hxDelete("/item/2"),
).addAttribute("hx-confirm:inherited", "Are you sure?")   // ← not the same as hx-confirm on the button itself
```

As a result, every app discovers `addAttribute("hx-confirm", ...)` as the way to add confirmation:

```ts
// rideshare/src/rides/views/detail.view.ts:185
.hxPost(rideRoutes.toggleFull.resolve({ id: ride.id }), { target: layoutIds.page, swap: "outerMorph scroll:top" })
.when(!ride.isFull && pendingReservations.length > 0, (t) =>
  t.addAttribute("hx-confirm", markFullConfirmMessage(pendingReservations.length)),   // ✗ escape hatch
)

// rideshare/src/reservations/reservations.view.ts:115
Button("Remove passenger")
  .addAttribute("hx-confirm", "Are you sure you want to remove this passenger?")   // ✗
  .hxPost(reservationRoutes.driverRemove.resolve({ id: reservation.id }), { ... })

// rideshare/src/admin/views/admin.dashboard.view.ts:83
.addAttribute("hx-confirm", "Are you sure you want to delete this event? ...")   // ✗
```

## Evidence

The `confirm` field IS serialized correctly by `render.ts` (line 118 in the `HTMX_ATTRS` table), so there is zero code change needed — the fix is purely a guideline update. The typed API already works:

```ts
// ✓ type-safe version
Button("Delete").hxDelete(route.resolve({ id }), {
  target: ids.page,
  swap: "outerMorph",
  confirm: "Are you sure?",   // ← fully typed, rendered as hx-confirm="..."
})
```

The `addAttribute("hx-confirm", ...)` pattern has a subtle difference: it writes to the `attributes` bag and renders independently from the `htmx` field. Both are serialized to the output, so functionally they are equivalent when `hxPost`/`hxDelete` is also called on the same element. But the `addAttribute` pattern forces the developer to manage two parallel call chains, inviting ordering bugs and obscuring that `confirm` is a first-class HTMX concept.

## Why it matters

`hx-confirm` is one of the most commonly needed HTMX features for destructive actions. Five call-sites across two production apps all chose `addAttribute` because the guidelines don't surface the typed option. This is a pure guideline bug — no code change is needed, only documentation.

## Rough idea (not a design)

Edit `guidelines/web-development/htmx.md` to add a "Confirmation dialogs" section showing:

```ts
// ✓ typed confirm option — part of hxPost/hxDelete options object
Button("Delete").hxDelete(route.resolve({ id }), {
  target: ids.mainContent,
  swap: "outerMorph",
  confirm: "Are you sure you want to delete this?",
})
```

Mark the `addAttribute("hx-confirm", ...)` pattern as an anti-pattern (should only be used with `:inherited` modifier for parent-level confirmation, as shown in the existing example).
