# IfThen chains on string-discriminant fields instead of Match

## Problem

Apps across the codebase replace `Match` with repetitive `IfThen(x.field === "VALUE", ...)` chains when dispatching on a string-discriminant field. The guidelines teach `Match` (including the discriminated-union overload) but never show the anti-pattern to avoid — so LLMs and developers keep writing the chain.

## Evidence

`rideshare/src/reservations/reservations.view.ts` switches on `reservation.status` three times in separate `IfThen` calls:

```ts
// rideshare/src/reservations/reservations.view.ts:86
IfThen(reservation.status === "PENDING", () =>
  Div(Button("Confirm")…, Button("Decline")…).flex().gap("2"),
),

// rideshare/src/reservations/reservations.view.ts:109
IfThen(reservation.status === "CONFIRMED", () =>
  Button("Remove passenger")…,
),
```

A second, separate location switches on `res.status` three more times (lines 351, 361, 365):

```ts
// rideshare/src/reservations/reservations.view.ts:351
IfThen(res.status === "PENDING" && !eventPast, () =>
  Button("Cancel reservation")…,
),
// rideshare/src/reservations/reservations.view.ts:361
IfThen(res.status === "DECLINED", () =>
  P("Driver couldn't accommodate…"),
),
// rideshare/src/reservations/reservations.view.ts:365
IfThen(res.status === "CANCELLED", () =>
  P("You cancelled this reservation…"),
),
```

`buzzin/src/views/admin/editor.view.ts` chains four `IfThen` calls on `quiz.status` ("SCHEDULED", "ACTIVE", "ACTIVE" again, "COMPLETED"). `pregled-nepremicnin-dashboard` chains three on `invoice.status` ("DRAFT", "SENT", "DRAFT||SENT"). `glimm` on `payment.status`. In total, 63 `IfThen(…status ===)` call-sites across 6+ apps, versus only 6 `Match(…, "status", …)` uses in the same codebase.

The correct idiom is `Match` with the discriminant-key overload, which:
- provides per-variant narrowing (the callback receives the narrowed type)
- produces a compile error when a new variant is added and the switch is not updated (exhaustive form)
- reads as a single intent rather than scattered boolean conditions

```ts
// ✓ intended pattern
Match(reservation, "status", {
  PENDING:   (r) => Div(Button("Confirm")…, Button("Decline")…),
  CONFIRMED: (r) => Button("Remove passenger")…,
}, () => Empty())
```

## Why it matters

63 misuse sites across 6 apps. Each chain is non-exhaustive (a new status variant is silently unhandled), duplicates the field access, and blocks TypeScript narrowing — so `.message` or other variant-specific properties require manual casts inside the callback. `Match` would catch new variants at compile time. This is the exact scenario the discriminated-union overload was designed for.

## Rough idea (not a design)

No code change needed. The fix is a one-liner ✗ example in `guidelines/web-development/fluent-html.md` (and the CLAUDE.md index) showing the chain as the anti-pattern and `Match` as the replacement:

```ts
// ✗ chained IfThen on discriminant — non-exhaustive, no narrowing
IfThen(x.status === "PENDING", () => ...)
IfThen(x.status === "DONE",    () => ...)

// ✓ Match with discriminant key — exhaustive, each branch is narrowed
Match(x, "status", {
  PENDING: (s) => …,
  DONE:    (s) => …,
})
```
