# No Context.update() — changing a scoped value mid-request requires dispose + re-scope boilerplate

## Problem

A common real-world pattern needs to upgrade a context value after auth resolves: first set locale from `Accept-Language` header in `onRequest` (before auth), then upgrade to the user's preferred locale in `preHandler` (after auth). The library provides no way to mutate the top-of-stack in place, so apps must manually dispose the old scope and push a new one:

```ts
// glimm/src/core/i18n/i18n.plugin.ts:50-65
fastify.addHook("preHandler", (request, _reply, done) => {
  const userLocale = request.user?.preferredLocale;
  if (userLocale && userLocale !== request.locale) {
    // No ctx.update() — must dispose old scope and push new one:
    if (request._i18nDispose) {
      for (const d of request._i18nDispose) d[Symbol.dispose]();
    }
    request._i18nDispose = [
      i18nTranslation.scope(tFn),
      i18nLocale.scope(userLocale),
    ];
  }
  done();
});
```

This dispose+re-scope pattern appears in **every app with i18n and auth** (5 apps + the project template). It forces the app to track `Disposable[]` arrays, manage disposal order, and repeat the boilerplate.

## Why it matters

5 apps and the template all copy this exact boilerplate because `Context<T>` has no mutation API. The workaround is verbose, error-prone (forgetting to dispose before re-scoping causes stack growth), and couples the app to internals of how the stack works. With `ctx.update(value)` the preHandler hook would be 3 lines instead of 8.

## Rough idea (not a design)

Add `ctx.update(newValue: T): void` that replaces `stack[stack.length - 1]` in place (no push, no pop). Only valid inside an active scope — throws or no-ops if stack is empty. The existing `Disposable` from the original `scope()` call would still pop the stack on disposal. This eliminates the dispose+re-scope dance entirely.
