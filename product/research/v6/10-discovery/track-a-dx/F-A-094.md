# 15+ type-only exports (`OverlayPosition`, `HTMX`, `HxSwap`, …) in value-position `export {}` blocks — breaks consumers using `verbatimModuleSyntax` / `isolatedModules`

## Problem

`src/index.ts` exports 15+ type-only declarations (interfaces, type aliases) in non-`export type` blocks, mixed together with genuine runtime values (functions, classes). Under `isolatedModules: true` or `verbatimModuleSyntax: true` TypeScript requires type-only exports to use `export type {}`. Consumers using either flag — common in monorepos, Next.js apps, Vite, Deno — get a compile error when they re-export any of these.

The library is inconsistent with itself: `Context`, `BehaviorMap`, `RouteHxOptions`, `QueryParams` are correctly exported with `export type`, but the HTMX types and `OverlayPosition` are not.

## Evidence

`OverlayPosition` is a plain type alias:
```ts
// fluent-html/src/control/overlay.ts:4
export type OverlayPosition = 'top' | 'bottom' | 'top-left' | ...;
```

But re-exported without `type` keyword alongside the `Overlay` function:
```ts
// fluent-html/src/index.ts:249-252
export {
  Overlay,
  OverlayPosition,   // ← type-only, no 'type' keyword
} from './control/index.js';
```

`HTMX` is an interface (type-only):
```ts
// fluent-html/src/htmx.ts:191
export interface HTMX { ... }
```

Exported without `type` keyword alongside `hx` (a function):
```ts
// fluent-html/src/index.ts:268-289
export {
  hx,               // ← runtime value
  resolveSelector,  // ← runtime value
  HTMX,             // ← type-only (interface)
  HxSwap,           // ← type-only
  HxSwapStyle,      // ← type-only
  HxTrigger,        // ← type-only
  HxEncoding,       // ← type-only
  HxHttpMethod,     // ← type-only
  HxSync,           // ← type-only
  HxOptions,        // ← type-only
  HxConfig,         // ← type-only
  HxStatusConfig,   // ← type-only
  ...
} from './htmx.js';
```

Similarly in the patterns block:
```ts
// fluent-html/src/index.ts:292-306
export {
  HtmxConfig,          // ← runtime function (OK)
  HtmxGlobalConfig,    // ← type-only
  hxResponse,          // ← runtime function (OK)
  HxResponse,          // ← runtime class (OK)
  HxResponseResult,    // ← type-only (interface)
  HxLocationConfig,    // ← type-only (interface)
} from './patterns.js';
```

The library already demonstrates the correct pattern for some exports:
```ts
// fluent-html/src/index.ts:265
export type { Context } from './control/index.js';   // ← correct
// fluent-html/src/index.ts:332
export type { BehaviorMap } from './core/behavior-methods.js';  // ← correct
```

## Why it matters

Any consumer app or monorepo package that has `"verbatimModuleSyntax": true` (the default in modern TypeScript 5.x projects and in all Vite + Next.js scaffolds) and tries to re-export `HTMX` or `HxSwap` from `fluent-html` receives:

```
TS1205: Re-exporting a type when 'verbatimModuleSyntax' is enabled requires using 'export type'.
```

This is a silent breakage vector when upgrading consumer projects to newer TypeScript configs. The fix is purely mechanical and non-breaking (splitting the export blocks), but the current state creates real friction for any consumer in a modern monorepo.

Additionally, the pattern is inconsistent within the same file: `Context`, `BehaviorMap`, and `RouteHxOptions` are correctly `export type`, while the far more commonly used `HTMX` and `HxSwap` are not.

## Rough idea (not a design)

Split each mixed `export { }` block into separate `export { }` (values) and `export type { }` (types) blocks. This is a purely mechanical, non-breaking refactor:

```ts
// Before (line 268)
export { hx, resolveSelector, HTMX, HxSwap, ... } from './htmx.js';

// After
export { hx, resolveSelector } from './htmx.js';
export type { HTMX, HxSwap, HxSwapStyle, HxTrigger, HxEncoding, HxHttpMethod, HxSync, HxOptions, HxConfig, HxStatusConfig } from './htmx.js';
```

No runtime change; no consumer API change. Pure compile-time correctness fix.
