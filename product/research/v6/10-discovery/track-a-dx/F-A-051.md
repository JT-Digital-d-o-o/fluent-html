# No `.setRole()` fluent method — WAI-ARIA role always set via `addAttribute("role", "...")`

## Problem

The library's core idiom is "never use `addAttribute` for standard HTML properties — use typed fluent setters instead." The `role` attribute is one of the most common HTML attributes (used to communicate semantic meaning to AT), yet there is no `.setRole()` method on `Tag`. Every call site in every app uses the raw escape hatch:

```typescript
// rideshare/src/shared/components/tooltip.view.ts:40
Div(...).addAttribute("role", "tooltip")

// rideshare/src/shared/components/layout.view.ts:463
Div(...).addAttribute("role", "dialog")

// glimm/src/shared/components/huluma/control.components.ts:98
Div(...).addAttribute("role", "switch")

// planet-positive-sport/src/loc/onboarding/onboarding.view.ts:54
Div(...).addAttribute("role", "progressbar")

// planet-positive-sport/src/shared/components/display/display.ts:50
Div(...).addAttribute("role", "alert")
```

This pattern appears 17+ times across 5 distinct apps (rideshare, glimm, jt-draw, filmplast-landing-page, planet-positive-sport), and in every case the same element also uses `setAria({...})` or other fluent methods — making the mixed style unavoidable as long as `.setRole()` is absent.

```typescript
// glimm/src/shared/components/huluma/control.components.ts:98-99
// Role set via addAttribute, aria attrs via setAria — inconsistent on the same element
.addAttribute("role", "switch")
.setAria({ checked: on ? "true" : "false", label: on ? "On" : "Off" });
```

## Why it matters

- **Guideline violation.** The idiom "never use `addAttribute` for standard HTML props" is broken for one of the most important accessibility attributes — specifically an attribute with a well-defined, finite vocabulary (WAI-ARIA 1.2 defines ~90 roles).
- **No typo detection.** `.addAttribute("role", "tooptip")` compiles and renders silently. A typed union would catch this.
- **Mixed call chains.** The same element uses `setAria({...})` for aria attributes and `addAttribute("role", ...)` for role — forcing an inconsistent hybrid style for any element that needs both.
- **High frequency.** 17+ call sites across 5 apps and the pattern will recur on every new accessible component (dialog, tooltip, alert, progressbar, tablist, etc.).

## Rough idea

Add `.setRole(role: AriaRole): this` to `Tag`, with a typed union for the full WAI-ARIA 1.2 role vocabulary (landmark: `"banner"`, `"navigation"`, `"main"`, `"region"`, etc.; widget: `"button"`, `"checkbox"`, `"dialog"`, `"menu"`, `"switch"`, `"tab"`, `"tablist"`, `"tooltip"`, etc.; live region: `"alert"`, `"status"`, `"log"`, etc.; document structure: `"img"`, `"list"`, `"progressbar"`, etc.; plus `(string & {})` escape hatch). Method writes `this.attributes["role"] = role`. Add to `_sk` if subclasses need it, or handle in the generic `attributes` bag.
