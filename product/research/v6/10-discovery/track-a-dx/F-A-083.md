# `fluent-html.md` teaches `.setName()` before `formFor<T>()` with no preference signal, causing `formFor<T>()` to be ignored even when schemas exist

## Problem

`guidelines/web-development/fluent-html.md` presents `.setName()` at the top of the "Tag Methods" section as the canonical way to set form field names:

```ts
// guidelines/web-development/fluent-html.md:22–26
Input().setType("email").setPlaceholder("you@example.com").setName("email")  // InputTag (generic)
// ...
Textarea().setPlaceholder("Message").setName("msg").setRows(5)         // TextareaTag
Select(Option("A").setValue("1"), Option("B").setValue("2")).setName("x") // SelectTag
```

The `formFor<T>()` section appears later (line 63) with the note "Untyped `.setName()` still works for one-off elements outside a schema" (line 87) — but this framing makes `.setName()` sound equally valid for typed forms.

`CLAUDE.md` has the correct rule (`"never untyped .setName() when a schema exists"`), but `fluent-html.md` — the detail reference that LLM agents read when building forms — contradicts this by showing `.setName()` prominently and without a `// ✗` marker.

## Evidence

TTL (a full-stack app with well-structured schema files) uses 41 `.setName()` calls and zero `formFor<T>()` despite having matching schema types:

```ts
// ttl/src/auth/auth.view.ts:58
Input().setType("email").setPlaceholder("Email").setName("email")

// ttl/src/auth/auth.view.ts:68
Input().setType("password").setPlaceholder("Password").setName("password")

// ttl/src/settings/settings.view.ts:74
Input().setType("text").setName("name")
```

The schema types that `formFor<T>()` could leverage already exist:

```ts
// ttl/src/core/types.ts:5
export type SignInReq = { email: string; password: string; };

// ttl/src/settings/settings.schema.ts:11
export type UpdateProfileReq = { name: string; ... };
export type ChangePasswordReq = { currentPassword: string; newPassword: string; passwordConfirm: string; };
```

The fields at `auth.view.ts:58–68` exactly match `SignInReq` — a perfect `formFor<SignInReq>()` opportunity that is missed because the guideline doesn't flag the `.setName()` path as suboptimal.

The `fluent-html.md` "Tag Methods" section (lines 22–26) is the first place a developer — or an LLM reading the guidelines — looks when building forms. It shows `.setName()` without any note about `formFor<T>()`. The `formFor<T>()` section is a separate heading later in the document, so it is often not reached.

## Why it matters

`formFor<T>()` exists specifically to catch typos in field names at compile time. When `.setName("email")` is used instead, a rename of the schema field (`email` → `emailAddress`) does not produce a TypeScript error in the view — the mismatch is only caught at runtime by a 422 response. The guideline inconsistency defeats the entire type-safety guarantee. This is a straight-forward fix: one annotation and one ✗ example prevents N future undetected name mismatches.

## Rough idea (not a design)

Edit `guidelines/web-development/fluent-html.md` to:
1. Mark the `.setName()` lines in the "Tag Methods" section with `// for one-off use outside a schema` comments.
2. Add a ✗ example to the `formFor<T>()` section:

```typescript
// ✗ when a schema type exists — use formFor<T>() instead:
Input().setType("email").setName("email")           // typos compile silently

// ✓ type-safe — compile error on misspelling:
const f = formFor<SignInReq>();
f.input("email", "email")
f.input("nmae", "password")  // ✗ compile error — not a key of SignInReq
```

No library code change is needed.
