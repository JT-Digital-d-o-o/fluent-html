# Two competing boolean-attribute APIs — typed `setDisabled()`/`setChecked()` vs `.toggle()`

## Problem

The library offers two distinct mechanisms for HTML boolean attributes:

1. **Typed setters on `*Tag` subclasses** — `InputTag.setChecked(bool)`, `ButtonTag.setDisabled(bool)`, `SelectTag.setMultiple(bool)`, `TextareaTag.setReadonly(bool)`, etc. (15+ methods across 8+ element classes). These store a JS `boolean` in a `_sk` field.

2. **`.toggle(name, condition?)`** on the base `Tag` — appends the attribute name to the `toggles` array; rendered as bare attribute name (e.g., `disabled`) when present.

These two paths have **opposite semantics for `false`** (see F-A-001), but more importantly, they receive **conflicting guidance**:

- The **guidelines** (`guidelines/web-development/fluent-html.md:47`) say:
  ```
  **Boolean attributes** — `.toggle()` only:
  Input().toggle("required")
  Input().toggle("required", isRequired)
  Option(city).toggle("selected", city === current)
  ```

- The **ESLint `prefer-set-method` rule** (`fluent-html-eslint-plugin/src/rules/prefer-set-method.ts:87-95`) lists boolean attrs as standard attributes and auto-fixes `addAttribute("disabled", ...)` → `setDisabled(...)`:
  ```ts
  // Boolean attributes with dedicated setters
  disabled: "setDisabled",
  readonly: "setReadonly",
  checked: "setChecked",
  autofocus: "setAutofocus",
  multiple: "setMultiple",
  novalidate: "setNovalidate",
  selected: "setSelected",
  open: "setOpen",
  ```

The ESLint plugin is recommended (`recommended: true`) and has an auto-fixer — so it actively drives code toward the buggy path when `addAttribute("disabled", "true")` is encountered.

## Evidence

**`prefer-set-method.ts:87-95`** — Boolean attrs listed alongside safe string attrs, pointing to setters that have the false-value bug:

```ts
// fluent-html-eslint-plugin/src/rules/prefer-set-method.ts:87-95
// Boolean attributes with dedicated setters
disabled: "setDisabled",
readonly: "setReadonly",
checked: "setChecked",
autofocus: "setAutofocus",
multiple: "setMultiple",
novalidate: "setNovalidate",
selected: "setSelected",
open: "setOpen",
```

**`fluent-html.md:47-53`** — guidelines say toggle-only:

```
**Boolean attributes** — `.toggle()` only:
Input().toggle("required")                        // always on
Input().toggle("required", isRequired)            // conditional
Option(city).toggle("selected", city === current) // expression
```

**App-level evidence**: 41 apps counted using `addAttribute(..., "required")` / `addAttribute(..., "disabled")` (175 total call sites). When these are auto-fixed by ESLint, they go to `setRequired()`/`setDisabled()` — which do not exist on `InputTag` (only `setChecked`, `setDisabled`, `setReadonly`, etc. are present), so some fixes would compile-error, others would silently emit the wrong HTML.

## Why it matters

The two competing APIs confuse new app authors. The ESLint auto-fixer reinforces the wrong path. Even experienced developers (as evidenced by the `ttl` and `gym-crm` codebases) use both paths inconsistently. The guidelines are the authoritative source of truth, but the tooling contradicts them — the LLM-facing guidelines win for newly written code, but the ESLint fixer corrupts existing `addAttribute` calls into the buggy `set*` path. Fix in either code or ESLint.

## Rough idea (not a design)

Option A (recommended): remove the typed boolean setters and their `_sk` entries; `.toggle(name, cond?)` becomes the single path. ESLint `prefer-set-method` drops the boolean-attr entries; add `prefer-toggle` rule that reports `addAttribute("disabled", ...)` and auto-fixes to `.toggle("disabled")`. Breaking change requiring a codemod.

Option B: keep the setters but fix the render path (see F-A-001) so `false` skips emission. The API duplication remains but at least the semantics converge.
