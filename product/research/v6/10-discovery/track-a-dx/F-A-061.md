# `.translate(direction, value)` generates invalid Tailwind class for negative values

## Problem

`Tag.prototype.translate` is implemented as:

```ts
// fluent-html/src/core/tailwind-methods.ts:542
p.translate = function (direction: string, value: string) {
  return this.addClass(`translate-${direction}-${value}`);
};
```

When a caller passes a negative value like `"-1"` or `"-0.5"`, the result is:

```
translate-y--1      // invalid — Tailwind ignores it; CSS receives no transform
translate-y--0.5    // invalid
```

The correct Tailwind class is `-translate-y-1` (the `-` prefix goes in front of the utility name, not in front of the value). This is a **silent bug**: the element renders without the intended transform; there is no error, no TypeScript complaint, and no visual hint that the class is malformed.

## Evidence

The library's own test suite documents the breakage:

```ts
// rideshare/tests/view/browse-rides.view.test.ts:258
// Regression: previously used .translate("y", "-1") which emitted the
// invalid class `hover:translate-y--1`. The correct Tailwind class is
// `hover:-translate-y-1`.
expect(html).toContain("hover:-translate-y-1");
expect(html).not.toContain("hover:translate-y--1");
```

Apps uniformly work around the bug by falling back to `.addClass("-translate-y-…")` — bypassing the typed API entirely:

```ts
// rideshare/src/landing/landing.components.ts:42
.on("hover", t => t.background("sage").addClass("-translate-y-0.5").shadow("lg"))

// rideshare/src/landing/views/browse-rides.view.ts:188
.on("hover", t => t.addClass("-translate-y-1").shadow("xl"));

// rideshare/src/landing/views/landing.view.ts:299
.on("hover", t => t.background("white").shadow("lg").addClass("-translate-y-1"))

// rideshare/src/auth/auth.components.ts:42
.on("hover", t => t.background("sage").addClass("-translate-y-0.5").shadow("lg")) as T;

// jt-cut/src/home/views/home.hero.view.ts:597
.addClass("-translate-x-1/2")

// jt-cut/src/projects/views/projects.list.view.ts:304
.addClass("-translate-y-1")

// jt-cut/src/shared/components/layout.view.ts:273
.opacity("0").addClass("-translate-x-1")
```

The same issue applies to `.rotate()` and `.skewX()`/`.skewY()` which use the same pattern — but translate is the primary pain point because negative lift animations (`-translate-y-1`) are the most common use case.

## Why it matters

9 call-sites across 2 apps are forced off the typed path. The bug causes **silent broken animations** in production (a hover-lift that does nothing). Every developer who tries `.translate("y", "-1")` discovers the bug by breakage, then learns to use `.addClass()` instead — permanently lowering trust in the typed transform API.

## Rough idea (not a design)

Detect a leading `-` in `value` inside the `translate`, `rotate`, `skewX`, `skewY` implementations and emit the correct negative-utility class:

```ts
p.translate = function (direction: string, value: string) {
  if (value.startsWith("-")) {
    return this.addClass(`-translate-${direction}-${value.slice(1)}`);
  }
  return this.addClass(`translate-${direction}-${value}`);
};
```

Same fix for `rotate(-45)` → `-rotate-45`, etc. Alternatively, accept a number parameter and apply the sign prefix there; or provide a dedicated `.neg(cls)` call (already exists but undocumented).
