# Guidelines teach context in isolation but never show Fastify request-lifecycle integration — apps invent two incompatible patterns

## Problem

`guidelines/web-development/fluent-html.md` teaches `createContext` / `createRequiredContext` with a handler-function example:

```ts
function handler(user: User) {
  using _t = ThemeCtx.scope("dark");
  using _a = AuthCtx.scope(user);
  return Page();
}
```

And `guidelines/web-development/fastify.md` mentions context **zero times**. The guidelines never answer: *"How should I scope a per-request context in a Fastify app?"*

As a result, 6 apps independently invented two distinct patterns:

**Pattern 1 — scope in lifecycle hooks, dispose in `onResponse`** (glimm, jt-i18n, redaction-renderbox, planet-positive-sport, projects-template):

```ts
// glimm/src/core/i18n/i18n.plugin.ts:42-45
fastify.addHook("onRequest", (request, _reply, done) => {
  request._i18nDispose = [
    i18nTranslation.scope(tFn),
    i18nLocale.scope(locale),
  ];
  done();
});
fastify.addHook("onResponse", (request, _reply, done) => {
  for (const d of request._i18nDispose) d[Symbol.dispose]();
  done();
});
```

**Pattern 2 — scope inside `renderView`, disposed synchronously** (jt-vault-cloud):

```ts
// jt-vault-cloud/src/core/server.ts:101-108
server.decorateReply("renderView", function (this: FastifyReply, ...views: View[]) {
  using _ = OrgCtx.scope({ active: this.request.orgContext, userOrgs: ... });
  using _nav = NavCtx.scope({ ... });
  this.type("text/html").send(render(...views));
});
```

Pattern 1 is concurrency-unsafe (see F-A-031). Pattern 2 is safe. The guidelines endorse neither; apps chose at random.

## Evidence

`fastify.md` has no mention of `createContext`, `scope`, or context at all:

```
$ grep -n "context\|createContext\|scope\|Ctx\|render-time" guidelines/web-development/fastify.md
35: reply.renderView(FeatureListView());   ← only uses
62: interface FastifyReply { renderView(view?: View): void; }
127: return reply.code(422).renderView(...)
```

`fluent-html.md` (line 148) only says: "**Never use `AsyncLocalStorage`** — `createContext` is sufficient for synchronous rendering." It does not show how to wire context into a Fastify request lifecycle.

6 apps (glimm, jt-i18n, redaction-renderbox, planet-positive-sport, jt-vault-cloud, projects-template) all had to solve this independently, arriving at two different patterns — one of which is latently buggy under concurrent traffic.

## Why it matters

The project template (`projects-template/templates/full-stack/`) uses the unsafe hook-lifecycle pattern. Every new project started from the template inherits the concurrency bug. Fixing the guideline would: (a) standardize on Pattern 2, (b) give apps a clear migration path, and (c) document *why* the scope-in-renderView approach is correct.

## Rough idea (not a design)

Add a **"Scoping context per request"** section to `fastify.md` with:
- The endorsed pattern: scope inside `renderView` decorator using `using`
- Why the hook-lifecycle pattern is unsafe (concurrent requests, LIFO violation)
- A worked example for i18n + auth context

Also add a one-liner to `CLAUDE.md` context rule: "Scope in `renderView` — not in preHandler/onResponse hooks."
