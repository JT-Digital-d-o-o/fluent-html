# `position()` and `display()` take full Tailwind class names, violating the `method(value) → prefix-value` convention

## Problem

Every Tailwind fluent method follows the convention: `method(value)` emits `prefix-value`. For example:

```ts
.padding("4")      → "p-4"
.background("red-500") → "bg-red-500"
.textColor("white") → "text-white"
.rounded("lg")     → "rounded-lg"
```

But `position()` and `display()` break this: they take the full Tailwind class name as their argument and just call `addClass(value)` directly:

```ts
// fluent-html/src/core/tailwind-methods.ts:459
p.position = function (value: string) { return this.addClass(value); };
// fluent-html/src/core/tailwind-methods.ts:469
p.display = function (value: string) { return this.addClass(value); };
```

The type constraints confirm this — the values ARE the full class names, not suffixes:

```ts
// tailwind-types.ts:168
export type TailwindPosition = "static" | "fixed" | "absolute" | "relative" | "sticky";
// tailwind-types.ts:118-121
export type TailwindDisplay =
  | "block" | "inline-block" | "inline" | "flex" | "inline-flex"
  | "table" | "inline-table" | "table-cell" | "table-row" | "flow-root"
  | "grid" | "inline-grid" | "contents" | "list-item" | "hidden";
```

There is no `position-` or `display-` prefix in Tailwind — these ARE bare class names. This makes the methods semantically different from all their neighbors: you call `.position("fixed")` to add the class `fixed`, not `position-fixed`.

This is further confusing because:
1. `.flex()` already exists as a separate method (no-arg to add `flex`, optional arg for `flex-{value}`). So `display("flex")` and `.flex()` do the same thing.
2. `display("hidden")` adds the class `hidden` — but there is no visual separation between "I want to hide this" and "I want to set display".

## Evidence

App usage shows developers call these correctly (`position("fixed")`, `position("relative")`) but a newcomer reading the API surface would expect `position("fixed")` to emit `position-fixed` (which doesn't exist in Tailwind but would be the natural inference from the convention):

```ts
// glimm/src/landing/views/landing.shell.ts:140
.position("fixed")

// glimm/src/protect/views/protect.review.view.ts:104
.position("relative")
```

Usage across all apps: ~1,907 calls to `.position()` / `.display()` — these are very high-frequency methods. The inconsistency is well-established in practice but creates API surface confusion for new learners and mis-fires in IDE autocomplete (seeing `position("fixed")` where nothing has a `position-` Tailwind prefix).

## Why it matters

The inconsistency is low-severity in isolation (no correctness bug, just a naming oddity), but it:
- Confuses new developers learning the fluent API
- Makes the type signatures surprising (`TailwindPosition` contains full class names, unlike every other `Tailwind*` type)
- Creates redundancy with more specific named methods (`.flex()`, and potentially others)

At 1,907 call-sites it is deeply entrenched — any rename is a significant breaking change and would need a codemod.

## Rough idea (not a design)

Two options:
- **Keep as-is with clarified documentation**: explicitly call out in guidelines that `position()` and `display()` are pass-through class name adders, not prefix methods.
- **Deprecate in favor of per-value methods**: add `.absolute()`, `.relative()`, `.fixed()`, `.sticky()` shorthands (same as `.flex()`) and `.block()`, `.inlineFlex()`, `.inlineBlock()`, `.grid()`, `.inlineGrid()`, `.hidden()`, `.contents()` etc. Then `position()` and `display()` become deprecated aliases.
