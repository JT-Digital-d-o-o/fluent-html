# `OptionTag.setValue()` requires a non-optional `string` — inconsistent with all other `*Tag` setters

## Problem

Every setter method on every `*Tag` subclass accepts an optional argument (matching `undefined` to mean "remove / don't emit the attribute"). The `_sk` renderer correctly skips `undefined` values:

```ts
// fluent-html/src/render/render.ts:212
if (value !== undefined && value !== null) {
  attrs += ' ' + sk[i]! + '="' + ...
}
```

So `InputTag.setValue(value?: string)` and `ButtonTag.setValue(value?: string)` are both optional. But `OptionTag.setValue` has a **required** non-optional argument:

```ts
// fluent-html/src/elements/forms.ts:407
setValue(value: string): this {   // ← required, not optional
  this.value = value;
  return this;
}
```

vs. the parallel setters on neighboring form elements:

```ts
// fluent-html/src/elements/forms.ts:47  (InputTag)
setValue(value?: string): this {   // ← optional

// fluent-html/src/elements/forms.ts:265  (ButtonTag)
setValue(value?: string): this {   // ← optional
```

## Evidence

The inconsistency is visible by inspection across three `setValue` implementations in the same file:

```ts
// forms.ts:47 — InputTag
setValue(value?: string): this { this.value = value; return this; }

// forms.ts:265 — ButtonTag
setValue(value?: string): this { this.value = value; return this; }

// forms.ts:407 — OptionTag  ← different signature
setValue(value: string): this { this.value = value; return this; }
```

**Practical impact**: code that conditionally sets a value via `.setValue(maybeUndefined)` compiles fine on `Input()` and `Button()` but produces a TypeScript error on `Option()`. Developers must either cast (`setValue(value!)`) or restructure their code.

The requirement is presumably intentional — `<option>` without a value attribute submits the element's text content as the value, so passing `undefined` to `.setValue()` and omitting the attribute might be a valid use case. But the inconsistency with the pattern is still surprising.

## Why it matters

Low frequency (3 affected sites), low pain (compile error, not runtime bug). But it violates the "principle of least surprise" for a common building block. Anyone who learns `setValue` is optional on `Input()` and tries the same on `Option()` gets a confusing type error. Reachable in any app that renders a dynamic select list where the option value might not exist.

## Rough idea (not a design)

Make `OptionTag.setValue(value?: string)` consistent. If there is a legitimate HTML reason for the distinction (empty `value` vs absent `value`), document it in a JSDoc comment on the method. The `_sk` renderer already handles `undefined` gracefully.
