# `.apply()` is documented with `setClass("raw tailwind")` — the JSDoc teaches what the guidelines prohibit

## Problem

The project has a clear rule in `CLAUDE.md` (line 112):

> **Fluent methods** — not `setClass` with Tailwind strings (fluent methods provide type safety + IDE autocomplete).

But the `.apply()` JSDoc in `core/tag.ts` — the canonical inline documentation — uses `setClass` with a raw Tailwind string as its primary example:

```ts
// fluent-html/src/core/tag.ts:208
/**
 * Apply one or more modifier functions to this tag.
 *
 * @example
 * const card = (t: Tag) => t.setClass("rounded shadow p-4 bg-white");  // ← anti-pattern
 * const danger = (t: Tag) => t.addClass("border-red-500 text-red-700"); // ← anti-pattern
 *
 * Div("Warning").apply(card, danger)
 */
```

An LLM reading the JSDoc (or a developer using IDE hover-docs) sees this as the idiomatic way to write modifier functions, then replicates it — bypassing the fluent API.

## Evidence

The same anti-pattern appears twice more in the README:

```ts
// fluent-html/README.md:153 — "Modifier Functions" section
const card = (t: Tag) => t.setClass("rounded shadow p-4 bg-white");
const danger = (t: Tag) => t.addClass("border-red-500 text-red-700");
Div("Warning").apply(card, danger)
```

And a ternary variant in the README "Table" section (lines 1706–1707):

```ts
// fluent-html/README.md:1706
.addClass(options?.hoverable ? 'hover:bg-gray-50' : '')
.addClass(options?.striped && index % 2 ? 'bg-gray-50' : '')
```

The second snippet also contains `.on()`-bypass (raw `hover:` prefix inside `addClass`) and a ternary inside `addClass` — two patterns the ESLint plugin's `no-ternary-in-view-builder` rule is intended to catch but cannot, because the ternary is in the attribute argument, not in the element children.

Meanwhile `guidelines/web-development/fluent-html.md` correctly shows the fluent version (line 98):

```ts
const card = (t: Tag) => t.padding("6").background("white").rounded("lg").shadow("md");
```

So the JSDoc and the README are inconsistent with both `CLAUDE.md` and `fluent-html.md`.

## Why it matters

JSDoc is read at the point of use — when a developer hovers `.apply()` in their IDE. It is often the only documentation they see. Showing the anti-pattern here teaches it even to developers who have read the guidelines, because the JSDoc appears to be the authoritative example for the method. Every LLM agent generating code also reads JSDoc as primary API documentation.

The README examples are also consumed by LLM context in this project (the CLAUDE.md system) — stale examples there propagate directly into generated app code.

## Rough idea (not a design)

Replace the JSDoc and README example with fluent versions:

```ts
// tag.ts JSDoc — corrected
* const card  = (t: Tag) => t.padding("6").background("white").rounded("lg").shadow("md");
* const hover = (t: Tag) => t.transition().on("hover", t => t.shadow("lg"));
*
* Div("Content").apply(card, hover)
```

And in the README "Table" section, replace the ternary-in-addClass lines with `.when()`:

```ts
.when(options?.hoverable, t => t.on("hover", t => t.background("gray-50")))
.when(options?.striped && index % 2 === 1, t => t.background("gray-50"))
```

This is a documentation-only fix (JSDoc + README).
