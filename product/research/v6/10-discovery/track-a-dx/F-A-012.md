# `MetaTag._sk` uses `'httpEquiv'` (camelCase) but the HTML attribute is `http-equiv` — wrong output, no test

## Problem

`MetaTag` stores its `http-equiv` value under the camelCase property `httpEquiv` and includes that string literal in `_sk`. The renderer at `render.ts:213` emits the `_sk` key directly as the HTML attribute name:

```ts
// fluent-html/src/render/render.ts:213
attrs += ' ' + sk[i]! + '="' + escapeAttr(...) + '"';
```

So `Meta().setHttpEquiv("content-security-policy")` renders:

```html
<meta httpEquiv="content-security-policy">
```

instead of the correct:

```html
<meta http-equiv="content-security-policy">
```

Browsers will not recognize `httpEquiv` as a valid meta attribute. The element silently does nothing.

## Evidence

```ts
// fluent-html/src/elements/document.ts:75
(MetaTag.prototype as any)._sk = ['name', 'charset', 'httpEquiv', 'property', 'content'];
//                                                      ^^^^^^^^^^
//                                                      emitted verbatim as HTML attribute name
```

```ts
// fluent-html/src/elements/document.ts:44
export class MetaTag extends Tag {
  httpEquiv?: string;        // stored as camelCase JS property
  // ...
  setHttpEquiv(httpEquiv?: string): this {
    this.httpEquiv = httpEquiv;
    return this;
  }
}
```

The test suite has three `Meta` tests (`elements.test.ts:460–464`) — `charset`, `viewport`, and `og:title` — but none for `setHttpEquiv`. The bug is untested and invisible.

No app in the monorepo calls `setHttpEquiv` (confirmed by grep), which means the bug has gone unreported because production code either avoids this setter or falls back to `Meta().addAttribute("http-equiv", value)`.

## Why it matters

`http-equiv` is important for CSP delivery, refresh/redirect, and compatibility headers. Any app that tries to emit CSP via `<meta http-equiv="content-security-policy">` using `setHttpEquiv` gets a silently broken element. This is a correctness bug.

The root cause is a pattern gap in the `_sk` design: `_sk` assumes the property name matches the HTML attribute name, which is true for all lowercase names (`src`, `href`, `charset`) and hyphenated ones explicitly stored with hyphens (`stroke-width`, `fill-rule`), but breaks for any camelCase JS property that maps to a hyphenated attribute.

## Rough idea (not a design)

The simplest fix is to rename the JS property to `'http-equiv'` (using a quoted key) and update `_sk` correspondingly — matching how `SvgShapeTag` handles `'stroke-width'` and `PathTag` handles `'fill-rule'`. The getter would be `tag['http-equiv']` internally, which is valid JS (just not a valid identifier as a bare name). Alternatively, extend the `_sk` scheme to support `[propName, attrName]` tuples.
