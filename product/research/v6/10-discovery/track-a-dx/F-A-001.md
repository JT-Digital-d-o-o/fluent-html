# `_sk` boolean fields serialize as `="true"`/`="false"` instead of HTML boolean attributes

## Problem

Every `*Tag` subclass exposes typed boolean setters (`setDisabled`, `setChecked`, `setReadonly`, `setMultiple`, `setSelected`, `setAutofocus`, `setControls`, `setAutoplay`, `setLoop`, `setMuted`, `setDefer`, `setAsync`, `setNomodule`, `setNovalidate`, `setOpen`, `setDefault`). These store a JS `boolean` field, and the `_sk` loop in `renderImpl` serializes it via `String(value)`:

```ts
// fluent-html/src/render/render.ts:213
attrs += ' ' + sk[i]! + '="' + escapeAttr(typeof value === 'string' ? value : String(value)) + '"';
```

`String(true)` → `"true"`, `String(false)` → `"false"`. Both are emitted as quoted attribute values.

**Two problems:**

1. `setDisabled()` / `setControls(true)` renders `disabled="true"` / `controls="true"`. While browsers treat *any* present value as truthy (so this is technically correct), it is non-standard and produces noisy HTML. The idiomatic HTML for a boolean attribute is either bare (`disabled`) or empty-string-quoted (`disabled=""`).

2. **`setDisabled(false)` renders `disabled="false"` — which browsers still treat as the attribute being present (truthy).** This is a real correctness bug. Any conditional usage of a boolean setter with `false` activates the attribute when it should be absent.

The test suite codifies the wrong behavior:

```ts
// fluent-html/test/forms.test.ts:177
render(Button("Disabled").setDisabled()), `<button disabled="true">Disabled</button>`
// fluent-html/test/elements.test.ts:271
render(Video().setSrc("video.mp4").setControls().setWidth(640).setHeight(360)),
  `<video src="video.mp4" controls="true" width="640" height="360"></video>`
// fluent-html/test/elements.test.ts:292
`<video src="video.mp4" controls="true" autoplay="true" loop="true" muted="true" ...></video>`
```

## Evidence

**Real app conditional breakage (`ttl/src/shared/components/ui.components.ts:76`):**

```ts
Input()
  .setType("checkbox")
  .setName(name)
  .setChecked(checked)   // if checked=false → <input checked="false"> → browser sees checked!
```

**Another app explicitly works around the bug (`gym-crm/src/scenes/videoChat/videoChatUi.ts:109`):**

```ts
Video()
  .setSrc(correctFilePath(video.file_name))
  .setControls(false)   // → <video controls="false"> — controls are STILL active in browsers
```

**The planet-positive-sport app has a comment documenting the bug** (`planet-positive-sport/src/loc/assessment/questionnaire.view.ts:203`):

```ts
// `setDisabled(false)` would still emit `disabled="false"` (browsers treat any
// presence of the boolean attribute as disabled). `.toggle()` only adds the
// attribute when the condition is true.
.toggle("disabled", isLocked)
```

## Why it matters

Any component that conditionally passes `false` to a boolean setter gets a broken HTML attribute that permanently activates the feature. The `.toggle(name, condition)` API on the same `Tag` class works correctly (skips emission when `condition=false`). Having two mechanisms with different semantics is a high-pain correctness trap.

Affected sites: every app that passes a variable (not a literal `true`) to a boolean setter. Confirmed in at least 3 apps. The `_sk` path is shared by ~18 boolean fields across 12+ element subclasses.

## Rough idea (not a design)

In the `_sk` loop inside `renderImpl`, branch on `typeof value === 'boolean'`: if `true`, emit the bare attribute name; if `false`, skip it entirely. This mirrors how `.toggle()` works and fixes all conditional boolean setter usages without any API change. The test expectations will change (e.g., `disabled="true"` → `disabled`) but the HTML semantics become correct.
