# `hxResponse` builder absent from CLAUDE.md index — 23 controllers set `reply.header("HX-*")` manually

## Problem

`fluent-html` exports an `hxResponse` builder that wraps the full set of HTMX response headers (HX-Redirect, HX-Push-Url, HX-Trigger, HX-Reswap, HX-Retarget, HX-Location, HX-Refresh) into a typed, chainable API. Despite this, 23 controller files across the codebase bypass it and write `reply.header("HX-*", ...)` directly.

The root cause is a guideline gap: `guidelines/web-development/CLAUDE.md` — the LLM-facing index that is loaded for every task — has no entry for `hxResponse`. The only reference is a 4-line section buried at the bottom of `htmx.md` with no ✗ anti-pattern shown. An LLM following the guidelines sees no reason to prefer the builder.

## Evidence

`mngmt` uses `hxResponse` in its `files.controller.ts` (copied from the project template) but then manually sets headers in its other controllers:

```ts
// mngmt/src/bugs/bugs.controller.ts:300
reply.header("HX-Redirect", dashboardRoutes.projectTab.resolve({ repoName, tab: "bugs" }));

// mngmt/src/dashboard/dashboard.controller.ts:554
reply.header("HX-Redirect", dashboardRoutes.taskDetail.resolve({ repoName, fingerprint }));
```

`rideshare` sets `HX-Reswap` manually on every 422 response (5 call-sites):

```ts
// rideshare/src/settings/settings.controller.ts:110
reply.header("HX-Reswap", "outerMorph").code(422).renderView(...)
```

`buzzin` has 10+ manual `reply.header("HX-Redirect", ...)` calls across admin and auth controllers. `jt-cut`, `planet-positive-sport`, `vabilo30`, `rideshare`, `pokemon`, `cms`, and `idea-hub` all do the same.

The builder form that should replace these:

```ts
// ✓ intended pattern — typed, chainable, all headers in one place
const { html, headers } = hxResponse(content)
  .redirect("/users")
  .trigger("showToast", { message: "Saved!" })
  .build();
reply.headers(headers);
reply.renderView(html);

// ✗ anti-pattern — manual, untyped, scattered
reply.header("HX-Redirect", "/users");
reply.header("HX-Trigger", JSON.stringify({ showToast: { message: "Saved!" } }));
reply.renderView(content);
```

The `htmx.md` section for `hxResponse` (line 211) exists but shows only one example and has no ✗ rule. `CLAUDE.md` does not mention `hxResponse` at all — it shows `reply.redirect("/path")` as an SSR pattern (line 284) but never connects it to `hxResponse` for cases requiring HTMX headers alongside a rendered view.

## Why it matters

23 controller files across 9+ apps set HX-* headers manually. Each instance is untyped (a typo in "HX-Redirect" silently does nothing), bypasses the builder's header-merging logic (multi-trigger composition), and splits header logic from view rendering across multiple lines. The fix is a guideline edit, not a code change — `hxResponse` already exists and is correct.

## Rough idea (not a design)

Add to `CLAUDE.md` HTMX section:

```ts
// ✓ hxResponse — typed builder for HTMX response headers
const { html, headers } = hxResponse(UserList(users))
  .pushUrl(userRoutes.list.resolve())
  .trigger("usersUpdated")
  .build();
reply.headers(headers).renderView(html);

// ✗ manual header strings — untyped, verbose
reply.header("HX-Push-Url", "/users").header("HX-Trigger", "{\"usersUpdated\":true}");
```

Expand the `htmx.md` section to cover all builder methods (`.redirect()`, `.pushUrl()`, `.trigger()`, `.location()`, `.retarget()`, `.reswap()`) with a worked example for each common case.
