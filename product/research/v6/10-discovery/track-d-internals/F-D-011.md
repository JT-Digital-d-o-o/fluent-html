# renderToStream ignores push() backpressure return value — entire tree eagerly buffered in one read() tick

## Problem

`renderToStream` creates a `Readable` whose `read()` handler calls `streamImpl`, which recursively traverses the entire view tree and calls `stream.push()` for every chunk — open tag, text, close tag — without ever checking whether `push()` returned `false` (the signal that the internal highWaterMark buffer is full and downstream is not consuming fast enough). After walking the whole tree, `this.push(null)` is called immediately, ending the stream.

```ts
// src/render/stream.ts:113-117
export function renderToStream(view: View): Readable {
  return new Readable({
    read() {
      streamImpl(this, view, false);
      this.push(null);
    },
  });
}
```

Inside `streamImpl` every `stream.push(...)` call at lines 122-125, 129-130, 176, 181, 183, 189 returns a boolean that is **silently discarded**:

```ts
// src/render/stream.ts:181-183
stream.push('<' + el + attrs + '>');
streamImpl(stream, tag.child, childCtx);   // recurses immediately regardless of backpressure
stream.push('</' + el + '>');
```

The Node.js `Readable` contract says: when `push()` returns `false`, stop pushing and wait for the next `read()` call. The current code never pauses, so the stream's internal buffer absorbs the entire rendered page in one event-loop tick.

## Evidence

`src/render/stream.ts:113-117` — `read()` is a single synchronous call to `streamImpl` + `push(null)`. The entire tree is walked before `read()` returns. There is no state saved for resuming mid-tree.

`src/render/stream.ts:181-183` — open-tag, recurse into children, close-tag: all three happen without checking the return value of `push()`, making partial-flush semantically impossible.

The JSDoc comment on `renderToStream` (line 104-110) says _"Chunks are yielded at tag boundaries"_ and _"This enables flushing early bytes to the client for large SSR responses."_ — this claim is architecturally false today. Early flushing requires the HTTP layer to receive chunks before the full render finishes, but since everything is pushed in one tick the TCP send buffer cannot flush until the event loop yields.

## Why it matters

For large SSR pages (full document renders, large `ForEach` lists, paginated tables) the memory behavior is identical to calling `render()` and sending the resulting string — there is no streaming advantage. The `bench/render.ts` shows the realistic-page render allocates ~55 KB and the flat-1000 render ~104 KB per call; all of that lands in the stream's internal buffer at once before the first byte leaves the socket. Real streaming would let Fastify/Node begin flushing TCP chunks mid-render, reducing time-to-first-byte (TTFB) for large pages and bounding memory under backpressure.

## Rough idea (not a design)

Convert `streamImpl` to a generator function that `yield`s string fragments instead of calling `stream.push` directly. The `Readable`'s `read()` method drives the generator, calling `.next()` only while `push()` returns `true`. When `push()` returns `false` (highWaterMark hit), `read()` exits and the generator is suspended mid-tree. The next `read()` call resumes it. This is compatible with the existing `render()` synchronous path — the generator approach is opt-in via `renderToStream`.
