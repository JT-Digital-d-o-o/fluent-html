# `setStyles()` unconditionally overwrites `this.style`, silently clobbering any prior `setStyle()` call in the same chain

## Problem

`Tag.setStyles(styles)` builds a style string from the provided object and assigns it directly to `this.style`, replacing any value already set by `setStyle(s)` or a previous `setStyles()` call. This is an unannounced destructive mutation: any style set before `setStyles` in a fluent chain is silently dropped.

## Evidence

```ts
// src/core/tag.ts:249-258
setStyles(styles: Record<string, string | number>): this {
  const styleString = Object.entries(styles)
    .map(([key, value]) => {
      const kebabKey = key.replace(/[A-Z]/g, letter => `-${letter.toLowerCase()}`);
      return `${kebabKey}: ${value}`;
    })
    .join("; ");
  this.style = styleString;  // ← unconditional overwrite, no merge
  return this;
}
```

A concrete silent failure:

```ts
Div().setStyle("position: relative").setStyles({ width: "100px" })
// Expected style: "position: relative; width: 100px"
// Actual style:   "width: 100px"   ← "position: relative" lost
```

The library's fluent API is designed for chaining. Every other multi-setter in the library (`addClass`, `setDataAttrs`, `setAria`) accumulates rather than replaces. `setStyles` is the only setter that silently clobbers a previously-set attribute:

- `addClass` appends to `this.class` (`tag.ts:108-113`)
- `setDataAttrs` merges into `this.attributes` (`tag.ts:276-282`)
- `setAria` merges into `this.attributes` (`tag.ts:299-304`)
- `setStyle` sets `this.style` (a replacement setter, but documented as such and named `set`)
- `setStyles` sets `this.style` — same destructive behaviour as `setStyle`, but callers expect batch-setting to compose

The same bug applies to calling `setStyles` twice:

```ts
Div().setStyles({ color: "red" }).setStyles({ background: "blue" })
// Expected: "color: red; background: blue"
// Actual:   "background: blue"
```

## Why it matters

The expected idiom is to layer `setStyle`/`setStyles` in a chain or across component-composition steps. A base component might call `.setStyle("position: relative")` and a consumer might add `.setStyles({ width: "100px" })`. The silent overwrite breaks the composition contract and produces incorrect CSS without any error. The bug is hard to notice because both calls succeed and the output is valid (just incomplete) CSS.

Frequency is approx 2 places in apps (construction-time composition patterns), but the blast radius is large because the library advertises both `setStyle` and `setStyles` as complementary APIs.

## Rough idea (not a design)

Append the generated style string to `this.style` (e.g. `this.style = this.style ? this.style + '; ' + styleString : styleString`) rather than overwriting. This makes `setStyles` consistent with how `addClass` accumulates onto `this.class`. If a full-replace variant is genuinely needed, expose it as `replaceStyle(obj)` (explicit name).
