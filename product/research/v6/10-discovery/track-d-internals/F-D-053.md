# `hx-status:` attribute key is concatenated unvalidated into the HTML attribute name

## Problem

`buildHtmx` in both `render.ts` and `stream.ts` iterates `Object.keys(htmx.status)` and concatenates each key directly into the attribute name string without any escaping or validation:

```ts
// src/render/render.ts:147-152
if (htmx.status) {
  for (const code of Object.keys(htmx.status)) {
    const cfg = htmx.status[code]!;
    const value = typeof cfg === 'string' ? cfg : buildStatusConfig(cfg);
    result += ' hx-status:' + code + '="' + escapeAttr(value) + '"';
    //                        ^^^^ unvalidated, unsanitized key injected into attribute name
  }
}
```

The attribute _value_ is correctly passed through `escapeAttr`, but the attribute _name_ — `hx-status:<code>` — concatenates `code` directly. The TypeScript type for `htmx.status` is `Record<string, string | HxStatusConfig>` (htmx.ts:245), which means `code` is an arbitrary `string`.

A status-code key containing `>`, `"`, `/`, space, or other HTML-special characters would produce a malformed attribute name in the rendered output:

```ts
// An adversarial or mistyped key
A("link").setHtmx("/path", {
  status: { '422 onfocus=alert(1) x': 'target:#err' }
})
// Rendered: <a hx-get="/path" hx-status:422 onfocus=alert(1) x="target:#err">
```

This creates an injectable attribute name. The existing `addAttribute` API defends against this with `validateAttributeKey` (tag.ts:19-29), but `htmx.status` keys bypass that defence entirely.

## Evidence

```ts
// src/render/render.ts:148-151
for (const code of Object.keys(htmx.status)) {

```

```ts
// src/render/stream.ts:68-72 (verbatim copy)
for (const code of Object.keys(htmx.status)) {
  const cfg = htmx.status[code]!;
  const value = typeof cfg === 'string' ? cfg : buildStatusConfig(cfg);
  result += ' hx-status:' + code + '="' + escapeAttr(value) + '"';
}
```

Compare with `addAttribute` (tag.ts:141-148), which validates every key through `validateAttributeKey`:

```ts
// src/core/tag.ts:19-29
const VALID_ATTR_KEY = /^[a-zA-Z_][a-zA-Z0-9\-_:.]*$/;
const EVENT_HANDLER_RE = /^on[a-z]/i;
const PROTO_KEYS = new Set(['__proto__', 'constructor', 'prototype']);

function validateAttributeKey(key: string): void {
  if (PROTO_KEYS.has(key)) throw new Error(`...prototype pollution`);
  if (!VALID_ATTR_KEY.test(key)) throw new Error(`Invalid attribute key: "${key}"`);
  if (EVENT_HANDLER_RE.test(key)) throw new Error(`Event handler attribute "${key}" is blocked`);
}
```

The `hx-status:` path has none of this protection. HTTP status codes are strictly 3-digit numbers (`[1-9][0-9]{2}`); any key that doesn't match that pattern should be rejected.

## Why it matters

The `escape-by-default` guardrail (§11.3) applies not just to attribute _values_ but to attribute _names_. The renderer already validates custom attribute keys via `addAttribute` → `validateAttributeKey`. The `hx-status:` path creates a gap in that defence where a HTMX status-code key could inject into the attribute namespace.

In practice, all callers set status codes from literal numbers (`404`, `422`) or the route type system, so the risk is low in well-typed apps. However, the lack of runtime validation means a test bypass, a log-derived status code, or an integration that passes status codes as strings would be silently unsafe. This is an inconsistency in the escaping posture of `buildHtmx` (values escaped, keys not) versus `addAttribute` (both validated/escaped).

The bug exists in two places because `buildHtmx` is verbatim-duplicated between `render.ts` and `stream.ts` (F-D-012).

## Rough idea (not a design)

Validate the status-code key at serialization time (or earlier, at `hx()` construction):

```ts
// Option A: validate in buildHtmx (defensive, catches any path)
for (const code of Object.keys(htmx.status)) {
  if (!/^[1-9][0-9]{2}$/.test(code)) throw new Error(`Invalid hx-status key: "${code}"`);
  // ...
}

// Option B: validate in htmx.ts hx() constructor when status is set (fail fast)
```

Option B is preferred (fail-fast at construction matches the `addAttribute` model) and can carry a TypeScript type like `type HttpStatusCode = \`${1|2|3|4|5}${number}${number}\`` to surface the constraint at compile time.
