# Bench suite not wired into CI — perf regressions in ops/sec are invisible

## Problem

The benchmark suite (`bench/render.ts`) measures throughput for 7 render workloads and 2 fold/context workloads. It is runnable only via `npm run bench` / `npm run bench:mem` — it is NOT included in `npm test` or `npm run test:coverage`. This means a code change that regresses render throughput by 2× will pass CI undetected.

## Evidence

```json
// package.json:51-52
"bench": "npm run build && node dist/bench/render.js",
"bench:mem": "npm run build && node --expose-gc dist/bench/render.js",
```

```json
// package.json:47 (the test script — bench is absent)
"test": "npm run build && node --test dist/test/elements.test.js dist/test/attributes.test.js ... dist/test/form-for.test.js"
```

The bench outputs only human-readable console text:
```ts
// bench/render.ts:35-39
function printResult(name, result): void {
  const pad = 40 - name.length;
  console.log(
    `  ${name}${" ".repeat(pad)}${formatOps(result.opsPerSec).padStart(10)} ops/sec ...`
  );
}
```

There is no assertion, no exit-code-1 on regression, no machine-readable baseline. The recon explicitly flagged this:

> "bench is not wired into `npm test` so regressions in ops/sec are invisible."
> — `00-recon/04-performance.md:131`

The recon also established concrete baselines (e.g. Flat page 6.4K ops/s, Realistic page 23.6K ops/s, Large ForEach 1.1K ops/s) — these numbers exist but are not enforced anywhere.

## Why it matters

Track D's goal is to improve render perf (de-recursion, allocation reduction, static hoisting). Every RFC in that track needs a performance gate to:
1. Confirm the RFC actually improves things.
2. Prevent a future cleanup from accidentally regressing the achieved numbers.

Without a CI gate, the benchmarks are advisory notes, not guardrails. The recon measured that "obvious" optimizations (array-join, regex prefilter) are actually regressions — but those conclusions rest on a manual bench run. If someone "simplifies" the renderer using array-join in a future PR, CI will not catch the 2.5× throughput drop.

## Rough idea (not a design)

Add a lightweight `test/perf-smoke.test.ts` that:
1. Runs each benchmark for a small number of iterations (e.g. 200).
2. Asserts `ms/op < ceiling` per benchmark (ceilings set generously at ~3× the measured baseline to tolerate CI machine variance, but still catch gross regressions).
3. Is included in `npm test`.

Example ceilings from recon baselines (×3 guard):
- Flat page (1000 divs): `< 0.47 ms` (baseline 0.156 ms)
- Realistic page: `< 0.13 ms` (baseline 0.043 ms)
- Large ForEach (5000 items): `< 2.7 ms` (baseline 0.886 ms)

The ceilings should be committed as a checked-in constant so they can be tightened as performance improves.
