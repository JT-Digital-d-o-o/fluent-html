# countAlgebra.list uses reduce with a closure callback — inconsistent with the codebase's zero-overhead loop style

## Problem

`countAlgebra.list` sums an array of child counts via a functional `reduce`:

```ts
// src/fold/algebras/count.ts:14
list: (counts) => counts.reduce((a, b) => a + b, 0),
```

The callback `(a, b) => a + b` is a **new closure object allocated on every call to `list`**. In a tree with many array nodes, this adds up.

## Evidence

The render core (`render.ts:248-251`) deliberately uses `+=` concatenation in an explicit `for` loop rather than `array.join()` or `array.reduce()` — the recon (§2, §5) documents this as a deliberate micro-optimisation decision validated by bench. The `countAlgebra` does the opposite without a measured reason.

```ts
// src/render/render.ts:248-251 — the codebase's established style
let result = renderImpl(view[0]!, isRawContext);
for (let i = 1; i < len; i++) {
  result += '\n' + renderImpl(view[i]!, isRawContext);
}
```

For `countAlgebra` specifically, the `list` case is called for every array node in the tree. A 200-node page with 50 array nodes allocates 50 closures per `foldView(countAlgebra, view)` call. Each closure is ephemeral but forces GC work.

## Why it matters

`countAlgebra` is the benchmark target for fold-layer performance (recon bench: "foldView count (realistic page) — 25K ops/s"). Any allocation saved there directly improves the reference number used to evaluate fold overhead vs render overhead. It is also library example code that teaches the algebra pattern — a functional `reduce` callback in an otherwise imperative codebase sends mixed signals to contributors.

## Rough idea (not a design)

```ts
list: (counts) => {
  let sum = 0;
  for (let i = 0; i < counts.length; i++) sum += counts[i]!;
  return sum;
},
```

Zero allocations, consistent style, no behavior change.
