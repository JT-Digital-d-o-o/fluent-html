# unfoldView constructs plain new Tag() — silently drops _sk schema keys just like createTransformAlgebra

## Problem

`unfoldView` reconstructs tag nodes by calling `new Tag(layer.element, ...children)` directly. `Tag` is the base class; specialized elements (`ATag`, `InputTag`, `ImgTag`, etc.) carry their element-specific attribute names on `_sk` as a prototype field. A plain `new Tag('a', ...)` has no `_sk`, so `href`, `src`, `type`, `alt`, `colspan`, `rowspan`, and every other schema-key attribute are silently omitted from `render()` output.

The SEEN list already documents this for `createTransformAlgebra`. `unfoldView` has the identical defect but is a separate exported function called by any code that uses the anamorphism pattern.

## Evidence

```ts
// src/fold/unfold.ts:29-30
const children = layer.children.map(s => unfoldView(coalg, s));
const tag = new Tag(layer.element, ...children);
// tag._sk is undefined — element-specific attrs will never render
```

The `linkedTocCoalgebra` works around this by putting `href` in `attrs.attributes` rather than relying on `_sk`:

```ts
// src/fold/algebras/toc.ts:103-106
case "link":
  return {
    type: "tag",
    element: "a",
    attrs: { attributes: { href: seed.href } },   // ← escapes via extraAttrs path
    children: [{ type: "text" as const, value: seed.text }],
  };
```

This workaround works only because the `toc` coalgebra was hand-coded to avoid `_sk`. Any coalgebra that naively emits `element: "a"` with `attrs: { href: '/foo' }` (using the direct `TagAttrs.href` field from the index signature) will silently drop the href — the extra field lands in `attrs.href` but `tag._sk` is undefined, so the renderer never writes it.

```ts
// test/recursion-schemes.ts:216-224 — the passing test only checks href via attributes{}
const view = unfoldView(linkedTocCoalgebra, { type: "list" as const, entries: headings });
const html = render(view);
assert.ok(html.includes('href="#intro"'));   // passes — but only because toc uses attributes{} workaround
```

## Why it matters

The bug is invisible during development because the library's own coalgebra (`linkedTocCoalgebra`) accidentally avoids it. Any new coalgebra written against the documented `TagAttrs` type that sets element-specific fields like `attrs.href`, `attrs.src`, or `attrs.type` directly will silently emit elements missing those attributes. This is a correctness trap for every anamorphism user. `hyloView` has the same problem when combined with an algebra that reconstructs Tag objects.

## Rough idea (not a design)

Maintain a module-level `Map<string, readonly string[]>` from element name → `_sk` keys (populated when each element subclass registers itself), and after `new Tag(element, ...)` apply the matching `_sk` — or change `ViewLayer` to carry an optional `schemaKeys` field. Either way, this should be fixed in parallel with the same fix to `createTransformAlgebra`.
