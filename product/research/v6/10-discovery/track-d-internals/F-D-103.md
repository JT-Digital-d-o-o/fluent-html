# unfoldView / hyloView / createTransformAlgebra bypass addAttribute XSS validation — event-handler keys and prototype-pollution keys pass through unchecked

## Problem

`addAttribute` validates attribute keys via `validateAttributeKey`, blocking event-handler attributes (`onclick`, `onload`, etc.) and prototype-pollution keys (`__proto__`, `constructor`, `prototype`). However, three fold-layer functions bypass this check entirely by directly assigning to `tag.attributes`:

```ts
// src/fold/unfold.ts:36
if (attrs.attributes) tag.attributes = { ...attrs.attributes };   // ← no validation

// src/fold/algebras/transform.ts:41
if (finalAttrs.attributes) tag.attributes = { ...finalAttrs.attributes };  // ← no validation

// src/fold/hylo.ts:30-33
const attrs = {
  attributes: {} as Record<string, string>,
  ...layer.attrs,
};
return alg.tag(layer.element, attrs, foldedChildren);
// attrs.attributes flows into the algebra's tag() as-is — no validation
```

`addAttribute`, the intended path, does validate:

```ts
// src/core/tag.ts:19-28
function validateAttributeKey(key: string): void {
  if (PROTO_KEYS.has(key)) {
    throw new Error(`Attribute key "${key}" is blocked (prototype pollution)`);
  }
  if (!VALID_ATTR_KEY.test(key)) {
    throw new Error(`Invalid attribute key: "${key}"`);
  }
  if (EVENT_HANDLER_RE.test(key)) {
    throw new Error(`Event handler attribute "${key}" is blocked — use client-side JS or HTMX instead`);
  }
}
```

The render path trusts that keys in `tag.attributes` are valid and emits them unescaped:

```ts
// src/render/render.ts:220-226
const extraKeys = Object.keys(extraAttrs);
for (let i = 0; i < extraKeys.length; i++) {
  const key = extraKeys[i]!;
  const value = extraAttrs[key];
  if (value !== undefined && value !== null) {
    attrs += ' ' + key + '="' + escapeAttr(String(value)) + '"';
    //            ^^^  key is interpolated directly — no escaping of the key itself
  }
}
```

## Evidence

A coalgebra that injects an event-handler key:

```ts
const maliciousCoalgebra: ViewCoalgebra<string> = (text) => ({
  type: "tag",
  element: "div",
  attrs: {
    attributes: { onclick: "alert(1)" },  // ← blocked by addAttribute but not by unfoldView
  },
  children: [{ type: "text", value: text }],
});

const view = unfoldView(maliciousCoalgebra, "hello");
render(view);
// produces: <div onclick="alert(1)">hello</div>
// ^^^ XSS — onclick attribute was not blocked
```

The same applies to `hyloView` when `renderAlgebra` (or any algebra that reconstructs Tags via `unfoldView`) passes attributes through `attrs.attributes`, and to `createTransformAlgebra` / `addClassToMatching` when a transform returns modified attrs containing attacker-controlled keys.

The attribute value IS escaped via `escapeAttr`, but the key is not. Attribute keys that contain `"` or `>` can break out of the attribute context.

## Why it matters

This is a security breach in the fold/unfold layer's public API that contradicts guardrail §11.3 (escape-by-default, no XSS regressions). The library's tag-construction path enforces key validation; the coalgebra/transform path does not. Any user-supplied data that flows into `ViewLayer.attrs.attributes` keys is emitted unvalidated and unescaped into the HTML output. A developer building a `ViewCoalgebra` from user-provided data has no warning that attribute keys are unsafe.

## Rough idea (not a design)

Apply `validateAttributeKey` to every key when directly assigning to `tag.attributes` in `unfoldView`, `hyloView`, and `createTransformAlgebra`. Alternatively, route the assignment through `addAttribute` which already has the validation. Add a test that asserts `unfoldView` with an `onclick` attribute key throws the same error `addAttribute` does.
