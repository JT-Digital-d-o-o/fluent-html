# `renderWithNonce` does a full extra recursive tree traversal before rendering

## Problem

`renderWithNonce` is the correct API for CSP nonce injection (every script and style tag needs `nonce="..."` in a CSP-protected app). Its implementation walks the entire view tree *twice*: once with `applyNonce` to mutate nonce attributes onto matching tags, then once again with `renderImpl` to serialize to HTML.

```ts
// src/render/render.ts:49-66
export function renderWithNonce(nonce: string, ...views: View[]): string {
  const view = views.length === 1 ? views[0]! : views;
  applyNonce(view, nonce);     // ← full recursive traversal #1 (mutates tags)
  return renderImpl(view, false);  // ← full recursive traversal #2 (serializes)
}

function applyNonce(view: View, nonce: string): void {
  if (isTag(view)) {
    if (NONCE_ELEMENTS.has(view.el)) {
      view.setNonce(nonce);    // allocates attributes object if not already present
    }
    applyNonce(view.child, nonce);   // recurse
  } else if (Array.isArray(view)) {
    for (let i = 0; i < view.length; i++) {
      applyNonce(view[i]!, nonce);   // recurse
    }
  }
}
```

Every node in the tree is visited twice. `applyNonce` also *mutates* the tree (calls `setNonce`, which can trigger `Object.create(null)` for the `attributes` map if the tag had none), leaving side-effects on shared Tag instances — a latent hazard if Tag reuse is introduced.

## Evidence

The render pipeline in `renderImpl` (`render.ts:184-256`) already distinguishes `script`/`style` elements for raw-context switching:

```ts
// src/render/render.ts:239
const childCtx = el === 'script' ? 'script' : el === 'style' ? 'style' : isRawContext;
```

The nonce emission point could be placed here — when `el` is `script` or `style` and a nonce is available, emit ` nonce="<nonce>"` inline, with zero additional tree traversal. The `NONCE_ELEMENTS` set (`render.ts:37`) already exists.

For a realistic page with ~200 tags (the bench's "Realistic page" workload at 23.6K ops/s), a second traversal adds proportional cost and makes `renderWithNonce` approximately twice as slow as `render` for the same tree, even when no `<script>` or `<style>` tags are present.

The mutation side-effect is also concerning: `applyNonce` calls `view.setNonce(nonce)` which calls `addAttribute` which writes to `this.attributes` (breaking the frozen `EMPTY_ATTRS` identity check used in `render.ts:219` for the fast-path). Tags modified by `applyNonce` thus exit the render with a non-`EMPTY_ATTRS` attributes object, allocating even for tags whose attributes were otherwise empty.

## Why it matters

CSP nonce usage is mandatory in security-conscious deployments, meaning `renderWithNonce` is the production render path for any app with a Content Security Policy. It is not an edge-case API — in hardened apps it replaces `render` entirely. Doubling traversal cost for all such apps is a perf regression that scales with page size.

## Rough idea (not a design)

Add an optional `nonce?: string` parameter to `renderImpl`. When present and `el` is `'script'` or `'style'`, append ` nonce="${nonce}"` to the attrs string inline — no separate traversal, no mutation, no extra allocation. Remove `applyNonce` entirely. `renderWithNonce` becomes:

```ts
export function renderWithNonce(nonce: string, ...views: View[]): string {
  const view = views.length === 1 ? views[0]! : views;
  return renderImpl(view, false, nonce);  // single-pass, non-mutating
}
```

The same nonce parameter would need to be threaded through `streamImpl` in `stream.ts` for parity.
