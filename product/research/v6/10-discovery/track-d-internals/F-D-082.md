# stream.test.ts tests output equality only — no test verifies backpressure or incremental flushing

## Problem

Every test in `stream.test.ts` is an output-equality check: collect all chunks, join, compare against `render()`. None of them test the streaming *contract* — specifically that the stream respects backpressure and flushes chunks incrementally.

The implementation is known to be eager: `renderToStream` walks the entire tree synchronously inside one `read()` call, pushing all chunks before returning. This means:

- The stream's internal buffer is fully loaded in one tick — no memory advantage for large pages.
- `push()` returning `false` (backpressure signal from the consumer) is never observed; the implementation does not check it.
- There is no test that would fail if a future change accidentally collapsed all chunks into a single push.

## Evidence

```ts
// src/render/stream.ts:111-117
export function renderToStream(view: View): Readable {
  return new Readable({
    read() {
      streamImpl(this, view, false);  // entire tree, synchronously
      this.push(null);
    },
  });
}
```

The recon noted:
> "The entire tree is walked synchronously inside one `read()` call — every chunk is `push`ed in one tick, then EOF. So this is not backpressure-aware streaming and not incremental."
> — `00-recon/04-performance.md:41`

The test helper:
```ts
// test/stream.test.ts:16-23
function streamToString(view): Promise<string> {
  return new Promise((resolve, reject) => {
    const chunks: string[] = [];
    const stream = renderToStream(view);
    stream.on("data", (chunk) => chunks.push(chunk.toString()));
    stream.on("end", () => resolve(chunks.join("")));
    stream.on("error", reject);
  });
}
```

Every single test calls `streamToString` and asserts the joined output equals `render()`. There is one test that counts chunks (`stream.test.ts:347`), but it only asserts `chunks.length >= 3` — it doesn't assert memory bounds or that the stream pauses on backpressure.

## Why it matters

Without a backpressure test:
1. The eagerness bug (full tree in one tick) is invisible to the test suite — the suite passes even though the behavior is wrong.
2. When the backpressure-aware streaming RFC lands (Track D, complementary to de-recursion), there is no CI gate to confirm the new behavior is actually incremental.
3. Large SSR pages (1000+ nodes) defeat the purpose of using a stream entirely — they load the full response into the Readable buffer before any bytes reach the socket.

## Rough idea (not a design)

Add a test that creates a stream with `highWaterMark: 1` (one byte), renders a large tree (e.g. `ForEach(200, ...)`), and asserts that at some point `stream.push(...)` returns `false`, and that all data is still received correctly after resuming. This test would fail with the current eager implementation and pass only when true incremental streaming is in place.
