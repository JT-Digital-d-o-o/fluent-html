# context scope() allocates a new Disposable object per call — no singleton or push/pop escape hatch for hot loops

## Problem

Every call to `ctx.scope(value)` creates a fresh `{ [Symbol.dispose]() { stack.pop(); } }` object. The object is discarded once the `using` block exits. For a page that composes many scoped components (i18n, auth, nonce, theme) the GC pressure accumulates.

```ts
// src/control/context.ts:77-84
scope(value: T): Disposable {
  stack.push(value);
  return {
    [Symbol.dispose]() {
      stack.pop();
    },
  };
}
```

The identical pattern appears twice — in `createContext` (`:77`) and `createRequiredContext` (`:121`).

## Evidence

The bench measures "Context scope/read (1000 scopes)" at **4.2K ops/s = 0.237 ms per 1000 scopes** (recon §2). That is 237 ns per scope, dominated by the Disposable object allocation and GC — the actual stack push/pop is O(1) with no heap allocation.

```ts
// bench/render.ts:218-224
printResult("Context scope/read (1000 scopes)", measure("context", () => {
  for (let i = 0; i < 1000; i++) {
    using _s = ThemeCtx.scope("dark");
    void ThemeCtx.current;
  }
}, ITERATIONS));
```

A page that uses 3 contexts (theme, locale, auth) and renders 200 components calls `scope()` at least 3 times per request — small total, but every allocation counts at SSR throughput. For components that call a context inside a loop (e.g. `ForEach(rows, row => { using _ = RowCtx.scope(row); return RowView(); })`), the cost is paid per row.

## Why it matters

SSR rebuilds the whole tree per request. Allocations in hot paths (anything touched per node or per row) directly raise GC frequency. The context API is specifically recommended for cross-cutting per-request values (auth, nonce, i18n), meaning it is called early and often. A reusable singleton disposable or a non-`using` `push/pop` pair would cut the allocation to zero for callers that need the extra speed.

## Rough idea (not a design)

Option A — singleton Disposable: create one `disposable` object per `createContext` call (closed over the stack), reset it each time `scope()` is called, and return the same reference. Safe as long as a single `scope()` is never shared across threads (not possible in Node single-threaded sync render).

Option B — expose `ctx.push(value)` / `ctx.pop()` as a low-level escape hatch; let callers own the cleanup. `using _ = ctx.scope(value)` becomes syntactic sugar over push/pop.
