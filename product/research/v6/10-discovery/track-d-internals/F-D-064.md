# hyloView allocates a fresh `{}` object as default attributes on every tag node

## Problem

`hyloView` normalises `TagAttrs` by ensuring `attributes` is always present:

```ts
// src/fold/hylo.ts:30-33
const attrs = {
  attributes: {} as Record<string, string>,
  ...layer.attrs,
};
```

The spread `{ attributes: {}, ...layer.attrs }` unconditionally allocates a new `{}` object for `attributes` on every `"tag"` case, then immediately overwrites it if `layer.attrs.attributes` exists (spread order: last-key wins). So when a well-formed coalgebra returns `layer.attrs` with `attributes` already set, the `{}` is allocated and immediately abandoned.

## Evidence

Every `"tag"` node in a `hyloView` traversal executes this path. For a 200-node page built via `hyloView`, that is 200 redundant empty-object allocations per render cycle. The `TagAttrs` type in `fold/types.ts` already has `attributes` as a required field, so any correct coalgebra must provide it — meaning the defensive `attributes: {}` default fires for every tag but is only meaningful for malformed coalgebras.

## Why it matters

`hyloView` is positioned as the zero-intermediate-tree renderer (a fused unfold+fold for data→HTML without materialising a `View` tree). Its performance advantage over `foldView` is undermined if it allocates extra objects per node. For large data-driven pages (tables, lists) the allocation count is proportional to row count.

## Rough idea (not a design)

Either (a) check for the key before spreading — `layer.attrs.attributes ?? {}` merged as a fallback — or (b) require coalgebras to always provide `attributes` (already implied by the type) and remove the defensive default, trusting the type contract. Option (b) is zero-cost with no observable behavior change for correct callers.
