# Bench has no static-subtree hoisting measurement — the throughput gain is unquantified

## Problem

The bench suite (bench/render.ts) measures rendering of pre-built static view trees (`flatPage`, `realisticPage`, etc.) — but always by calling `render(tree)` at full cost every iteration. There is no measurement of the *counterfactual*: how fast would the same output be if the subtree had been pre-compiled to a cached `RawString`?

```ts
// bench/render.ts:190-208 — all benchmarks call render() on a frozen tree at full cost every iteration
const flatPage = benchFlatPage();
printResult("Flat page (1000 divs)", measure("flat", () => render(flatPage), ITERATIONS));
// 6.4K ops/sec — but what if flatPage were a pre-rendered RawString?

const realisticPage = benchRealisticPage();
printResult("Realistic page (~200 tags)", measure("realistic", () => render(realisticPage), ITERATIONS));
// 23.6K ops/sec — but the static chrome (header, nav, footer) could be a memcpy
```

A `Frozen()` stub that renders once and caches the result would look like:

```ts
// hypothetical bench case — not yet in bench/render.ts
function benchWithStaticHoisting(): void {
  // Simulate: nav is static across all requests
  const frozenNav = Raw(render(benchNavView()));  // pre-rendered once
  const page = Div(frozenNav, MainContent());     // Main rebuilt per request
  return page;
}
// Expected: ops/sec roughly = 1/cost(render(MainContent())) instead of 1/cost(render(fullPage))
```

Without this measurement, the decision to invest in a `Frozen()` API (F-D-091) rests on the recon's theoretical claim ("turns repeated 200-tag renders into a memcpy") rather than measured data.

The bench already demonstrates the *construction* cost separately (`bench/render.ts:231-234`):

```ts
measureMemory("Flat page construction (1000 divs)", () => benchFlatPage(), 100);  // 14.5 KB/render
measureMemory("Realistic page construction",         () => benchRealisticPage(), 100); // 65 KB/render
```

But these only measure heap allocation — not the total time saved by skipping render of a pre-compiled subtree.

## Why it matters

The recon ranked static-subtree hoisting as performance opportunity #3, behind de-recursion and true streaming. But without quantified throughput gain, Wave 2 designers and Wave 3 verifiers cannot make an evidence-based argument for where it sits in the roadmap. A 2× throughput gain justifies a new public API; a 5% gain does not. The bench is the gate.

Additionally, the existing bench already simulates the use case (same pre-built tree, rendered 1000×) — adding a "hoisted" variant is a two-line addition that provides the missing comparison.

## Rough idea (not a design)

Add two bench cases to bench/render.ts:

1. **Static subtree cost breakdown**: render only the static chrome (header+nav+footer from `benchRealisticPage`) in isolation, then render only the dynamic body — establishing a baseline per-part cost.

2. **Manual hoisting simulation**: pre-call `render(staticChrome)` once, wrap in `Raw(...)`, then bench `render(Div(frozenChrome, dynamicBody))` vs `render(fullPage)` — the ratio is the theoretical `Frozen()` speedup.

This is a bench-only change (no lib code); no API surface, no guardrail risks.
