# `createTransformAlgebra` silently drops all element-specific `_sk` attributes (href, src, type, alt, …) when reconstructing tags

## Problem

`createTransformAlgebra` (and the derived `addClassToMatching`) reconstructs the transformed view as a plain `new Tag(finalEl, children)`. It then copies only the six base `TagAttrs` fields (`id`, `class`, `style`, `attributes`, `htmx`, `toggles`) back onto the tag. It does not restore any of the element-specific `_sk` fields — `href`, `src`, `alt`, `type`, `target`, `rel`, `name`, `value`, `checked`, `disabled`, `rows`, `colspan`, and dozens of others — even though `extractAttrs` correctly gathered all of them into the `attrs` object via `Object.keys(tag)`.

The result: transforming any view that contains anchors, images, inputs, selects, form elements, SVG shapes, or media elements will silently discard every specialized attribute. The output HTML renders with no `href`, no `src`, no `type`, etc.

## Evidence

`extractAttrs` in `fold.ts` gathers the missing fields correctly:

```ts
// src/fold/fold.ts:19-25
for (const key of Object.keys(tag)) {
  if (!(key in attrs) && key !== '_t' && key !== 'el' && key !== 'child') {
    (attrs as Record<string, unknown>)[key] = (tag as unknown as Record<string, unknown>)[key];
  }
}
```

`createTransformAlgebra` reconstructs but only writes back the six base fields:

```ts
// src/fold/algebras/transform.ts:37-43
const tag = new Tag(finalEl, children);
if (finalAttrs.id) tag.id = finalAttrs.id;
if (finalAttrs.class) tag.class = finalAttrs.class;
if (finalAttrs.style) tag.style = finalAttrs.style;
if (finalAttrs.attributes) tag.attributes = { ...finalAttrs.attributes };
if (finalAttrs.htmx) tag.htmx = finalAttrs.htmx;
if (finalAttrs.toggles) tag.toggles = finalAttrs.toggles;
// href, src, alt, type, target, rel, name, value, ... — all lost
return tag;
```

An `AnchorTag` stores `href`, `target`, `rel`, `download`, `type`, `referrerpolicy` as own instance fields registered in `_sk`:

```ts
// src/elements/links.ts:12-53
export class AnchorTag extends Tag {
  href?: string;
  target?: BrowsingContext;
  rel?: LinkRel;
  // ...
}
(AnchorTag.prototype as any)._sk = ['href', 'target', 'rel', 'download', 'type', 'referrerpolicy'];
```

A concrete failing case:

```ts
const noop = addClassToMatching(() => false, "x");
const view = A("Home").setHref("/dashboard").setTarget("_blank");
const result = foldView(noop, view);
render(result);
// Expected: <a href="/dashboard" target="_blank">Home</a>
// Actual:   <a>Home</a>   ← href, target silently dropped
```

## Why it matters

`createTransformAlgebra` and `addClassToMatching` are exported public API specifically intended for bulk tree rewrites (e.g. "add a class to all paragraphs", "inject data-attributes", "wrap links"). Any such transform applied to a realistic view tree containing anchors, inputs, images, or form fields will silently produce invalid HTML — links without `href`, images without `src`, inputs without `name` — while appearing to succeed. No error is thrown; the drop is invisible.

The fold layer is already used for production purposes (nonce injection via `renderWithNonce` uses a tree walk; `linksAlgebra` depends on `extractAttrs` faithfully copying `href`). Adding transforms to the same pipeline raises the stakes.

## Rough idea (not a design)

Two options: (a) in `createTransformAlgebra`, after writing back the six base fields, iterate `Object.keys(finalAttrs)` minus those base fields and assign the extras directly onto the reconstructed tag — this requires no API change; or (b) accept an optional `factory: (el: string) => Tag` argument so the correct subclass is instantiated and its setter methods are available. Option (a) is simpler but still produces a base `Tag` (losing `_sk`-driven render path for specialized attrs); option (b) preserves full render correctness.
