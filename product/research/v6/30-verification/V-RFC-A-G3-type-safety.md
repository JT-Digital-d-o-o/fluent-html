# Verdict: RFC-A-G3 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

I attacked every claim in the RFC's "Type-safety story" against the actual source: `src/htmx.ts:191-260`, `src/routes.ts:104-150,262-289`, `src/core/htmx-methods.ts:14-22`, `src/patterns.ts:184-360`, and the real reply decorator at `rideshare/src/core/server.ts:87`.

- **The strongest claim survives — route objects ARE typed `HTMX`.** `RouteCallable` (routes.ts:147) returns `HTMX`; `setHtmx(htmx?: HTMX)` (htmx-methods.ts:16) consumes it; `method` is welded from `Def['method']` (routes.ts:262). `setHtmx(rideRoutes.browse({event}, {...}))` is genuinely method-safe and `hxGet(route.resolve(...))` genuinely collapses to `string`. F-A-074 framing is type-accurate. No kill there.

- **My first attack collapsed under inspection.** I expected the `include`/`trigger`/`vals` examples (RFC 146-147) to fail because `RouteHxOptions` does `Omit<HTMX,...'include'>`. It does — but then **re-adds** `include?: string | Id` (routes.ts:109), the same omit-then-widen trick as `HxOptions` (htmx.ts:253). So `voiceoverRoutes.update({ trigger, include })` type-checks. The typed-options story (F-A-016 `confirm?: string`, F-A-062 `vals`/`trigger`/`include`) is sound — real `HTMX` fields validated at the call site, strictly better than `addAttribute("hx-*", string)`. Survives — but the invariant is load-bearing and undocumented (required change 4).

- **type-safety failure mode 1 — the 'Type-safety story' overclaims value safety.** The final bullet promises "No bare `string` where a union fits." But the builder methods the RFC promotes are bare `string`: `redirect(url: string)`, `pushUrl(url: string)`, `retarget(selector: string)`, `reselect(selector: string)`, and `reswap(strategy: HxSwapStyle | string)` where `| string` collapses the union. The headline F-A-101 "after" `hxResponse(...).reswap("outerMorph")` is **no safer at the value level** than `reply.header("HX-Reswap","outerMorph")`: `reswap("outerMrph")` compiles identically. The genuine win is narrow — the method NAME removes the `"HX-Redrect"` header-KEY typo class — but the RFC lists `reswap` as a value-level type-safe win it does not deliver.

- **type-safety failure mode 2 (killer) — `HxReplyLike` is structurally underspecified and lets `applyTo` silently diverge.** `HxReplyLike = { header; type; send(string) }`. The real decorator (`rideshare/src/core/server.ts:87`) is `renderView = this.type("text/html").send(render(...views))`, so for rideshare `applyTo` happens to be equivalent — by luck, not by type enforcement. `applyTo` calls `this.build()` (renders the View itself) then `reply.type().send(html)`, **re-implementing `renderView` inside the library and routing around the host's decorator.** Any host whose `renderView` injects a CSP nonce, doctype, charset, or compression hint gets a compile-clean `applyTo(reply)` that silently drops it — the structural type cannot express "use this host's render pipeline." This is the ONE new public type in the RFC, and it makes the divergence invisible.

- **type-safety failure mode 3 — the primary worked example uses an off-type method.** `applyTo(reply.code(422))` (RFC 181, guideline 324) needs `.code()` to return `this`. `.code` is not on `HxReplyLike`. It compiles only because `reply.code(422)` is evaluated in the host's type before widening to the parameter. So the "framework-agnostic, satisfied by Express `Response`" claim (RFC 199) is untested by the type — Express has no `.code()` (it's `.status()`) — and Open Question #2 openly leaves the status contract unresolved. Shipping an adapter whose copy-paste example relies on an unresolved, off-type status method is a type-safety defect.

## Does it survive?

**survives-with-changes (confidence 0.72).** The core — typed route objects (F-A-074), typed `confirm`/`vals`/`trigger`/`include` (F-A-016/F-A-062), the doc-only `set*`/`hx*` zone rule (F-A-073), and the deferred `setCrossorigin` (F-A-072, owned by RFC-A-F044) — is type-sound. I tried to find a wrong call that compiles on the route/options path; the omit-then-readd trick defeats it. It is not a kill: the proposal is ~90% guideline over an already-typed surface.

But the ~10% of *new code* — `applyTo` / `HxReplyLike` — is the only new type, and it is the weakest link: an underspecified structural type that (a) silently bypasses `renderView`, (b) leans on an off-type `.code()` in its headline example, and (c) ships with a "Type-safety story" overclaiming value-level narrowing the builder methods don't provide. The four required changes fold these back; with them, it ships.

## Guardrail check (§11.4 type-safety)

Conditional PASS. The route-object and typed-options surface honors §11.4 (no bare `string` where a union fits, no `any`, no inference break). The new `HxReplyLike`/`applyTo` surface does **not** fully clear §11.4 as written: bare-`string` value methods are promoted as type-safe, and the structural type admits a silent `renderView` bypass plus an off-type `.code()` dependency. Required changes 1-3 bring the new surface into §11.4 compliance; change 4 hardens the invariant the typed-options examples silently rely on.
