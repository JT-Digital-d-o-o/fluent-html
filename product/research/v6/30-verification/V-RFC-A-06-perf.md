# Verdict: RFC-A-06 — perf lens

> You are an ADVERSARY. Your job is to KILL this RFC through the perf lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's perf self-assessment (§11.2) is one sentence: *"`DocumentTag` adds one `el === "html"` branch in `renderImpl`, no hot-path cost for non-document nodes."* Three things are wrong or unproven about that claim.

- **perf failure mode 1 — the branch only exists in one of three serializers, so the "fast path" claim hides a correctness regression on the perf-critical path.** The library ships three independent tag serializers: `renderImpl` (render.ts:196), `streamImpl` (stream.ts:134), and the fold render algebra (src/fold/algebras/render.ts). They are verbatim-divergent copies — the Track-D recon explicitly flags *"Dedupe render/stream into shared emitter — verbatim ~70-line copy."* The RFC patches **only `renderImpl`**. `renderToStream` is a **public export** (render/index.ts:2, index.ts:24). The streaming path is precisely the one you reach for on *large* pages — the case where DOCTYPE-bearing full documents live. So `renderToStream(Document(Head(), Body()))` walks the `isTag` branch, sees `el === 'html'`, emits `<html>` and never emits `<!DOCTYPE html>`. The page renders in quirks mode — the exact correctness bug the RFC exists to fix — on the streaming hot path, silently. The RFC's "no hot-path cost" framing is technically true only because it forgot the hot path that matters. Closing the hole means duplicating the branch into `streamImpl` (and the fold algebra), which (a) the effort estimate (M) does not budget and (b) widens the render/stream divergence the Track-D recon is trying to eliminate — a perf/maintainability regression in the opposite direction.

- **perf failure mode 2 — "one branch in renderImpl" is under-specified and the naive reading taxes every node.** `renderImpl`'s `isTag` block runs once per element — thousands of times per request. The RFC describes discrimination as *"`el === "html"` + an internal `_doc` brand on the prototype."* Read literally as an added top-of-block test (`if (tag._doc) ...`), that is an **unconditional per-tag property load + branch** added to the single hottest loop in the library, paid by every `Div`/`Span`/`P` to serve a feature that fires **once per page**. That is the textbook guardrail §11.2 violation: *the common case paying for a rare feature.* It is salvageable — if and only if the test is nested behind the `el === 'html'` string-compare that already happens for the script/style `childCtx` decision (render.ts:239), so non-`html` nodes short-circuit before any `_doc` read. But the RFC does not say that; it must, or the implementer will reach for the cheap-looking top-of-block guard.

- **perf failure mode 3 — DocumentTag must not perturb the monomorphic Tag shape, and the RFC never proves it.** The Track-D recon's headline perf goal is *"Cut construction allocation — monomorphic Tag shape … ~14.5KB/1000 divs paid per request."* The render hot path does megamorphic property reads (`tag.id`, `tag.class`, `tag._sk`, `tag.attributes`) across all Tag subclasses; keeping subclasses field-shape-compatible matters for inline-cache stability. `DocumentTag extends HtmlTag` is fine *only if* it adds zero instance fields and brands via the prototype (like `_t`/`_sk`/`HtmlTag._sk`). The RFC says "`_doc` brand on the prototype" for the discriminant — good — but never commits that `DocumentTag` adds no instance state, and the `Doctype()` "node insertion" framing (a `RawString` child) risks an extra array slot + extra recursion frame per page if `Document()` renders the doctype by nesting a node rather than prepending a hoisted constant string.

## Does it survive?

**survives-with-changes.** The feature is genuinely cheap *in principle* — DOCTYPE is a constant string, SEO helpers are pure synchronous string-building with zero async and zero new deps, and the common (non-document) node pays nothing **if** the discrimination is gated correctly. There is no inherent per-request allocation or async contamination of the sync path. This is not a reject: the perf cost of a correct implementation is approximately zero.

But the RFC's "one-line branch in renderImpl" is both **under-specified** (invites a per-node tax) and **incomplete** (ignores the streaming and fold serializers, producing a silent DOCTYPE drop on the streaming hot path). Those are not nitpicks — failure mode 1 is a shippable correctness regression on the perf-relevant path, and failure mode 2 is a literal §11.2 violation under the naive reading. The four required changes above fold the fix in: render in all three serializers, gate behind `el === 'html'`, prototype brand only (no instance fields), and prepend a hoisted constant rather than nesting a Doctype() node.

## Guardrail check (§11.2 — sync hot path)

The perf lens owns §11.2. Verdict: **conditionally pass.**

- **Async:** none introduced. SEO helpers and Document() are fully synchronous string builders. No `await`, no ALS, no opt-in async needed. Clean.
- **Per-request allocation:** SEO helpers allocate the same Meta/Link/Script tags the hand-rolled per-app `seo.ts` already allocates today — net-neutral, arguably a wash. No new per-request allocation in the renderer itself **provided** the doctype is a hoisted constant, not a per-render `Raw("<!DOCTYPE html>")` node (required change #4).
- **Common-case cost:** passes **only** with required change #2 (gate behind `el === 'html'`). As written, the §11.2 invariant ("common case must not pay for a rare feature") is at risk.
- **Hot-path completeness:** fails as written — the streaming hot path (`streamImpl`) is unpatched (required change #1). This is the load-bearing objection.
