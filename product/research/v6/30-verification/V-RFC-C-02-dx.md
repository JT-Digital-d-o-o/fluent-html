# Verdict: RFC-C-02 — dx lens

> You are an ADVERSARY. Your job is to KILL this RFC through the dx lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's *mechanism* (one `CLASS_VOCAB` table, three readers, a literal-union target) is sound and idiomatic — it mirrors `defineRoutes`/`defineIds` single-sourcing. The dx failure is not the idea; it is that **the surface as written is internally contradictory and the guideline edit teaches a different API than the one the RFC ships.** An app author who does exactly what the guideline says hits a wall.

- **dx failure mode 1 — the documented function does not exist (three names, one function).** `api_surface` declares `emitSafelistCss()`. The body declares `emitSafelistCss()` (lines 101–106). The depended-upon RFC-C-01 declares the identical function as `generateFluentSafelist(files, options?)` and never mentions `emitSafelistCss`. The C-02 guideline edit teaches *neither* — it tells the author to run a CLI `fluent-html-extractor --target v4 --out ./fluent-safelist.css` (lines 164, 255). So the public surface has three disjoint names for one capability. A developer who reads `fluent-html.md`, then reaches for the documented function, finds no exported `emitSafelistCss` (C-01 shipped `generateFluentSafelist`) and an unconfirmed CLI binary name (C-01 open-question #4: "CLI name … cosmetic; defer"). This is the canonical "hard to use correctly" defect: the happy path in the docs does not type-check.

- **dx failure mode 2 — the same option has two opposite defaults across coupled RFCs.** `ExtractorOptions.target` defaults to `"v4"` here (lines 93, 203: "omitting it on a v3 project is the only action needed to opt back") but to `"v3"` in RFC-C-01 ("Default \"v3\" for backward-compat"). These two RFCs are mutually `depends_on`. An author cannot know whether omitting `target` yields v3 or v4 output — and the C-02 migration prose is actively wrong if C-01's `"v3"` default wins. A default you cannot predict is worse than no default.

- **dx failure mode 3 — circular dependency = the cut is wrong.** `RFC-C-02.depends_on: [RFC-C-01]` and `RFC-C-01.depends_on: [RFC-C-02]`. A dependency cycle is unschedulable in Wave-4 roadmap ordering and is a tell that the responsibilities were never cleanly separated: C-02 claims to "define" `CLASS_VOCAB` (line 80, "RFC-C-01 fills CLASS_VOCAB; this RFC defines it") yet also re-declares C-01's `ExtractorOptions`/safelist surface. Two RFCs editing the same `src/index.ts` symbols with contradictory signatures is a merge collision, not a clean dual-target.

- **dx failure mode 4 — the guideline edit teaches the wrong layer (§11.8 audit).** Guardrail §11.8 requires the guideline edit to cover **every symbol in api_surface**. The api_surface is six symbols: `TW_TARGET`, `TailwindTarget`, `defineTailwindTarget()`, `ExtractorOptions.target`, the ESLint setting, `emitSafelistCss()`. The proposed `fluent-html.md` section teaches: `@import "tailwindcss"`, `@tailwindcss/postcss`, `@source inline()`, `@theme`, a CLI flag, and the ESLint setting. That is *one* of six symbols (`ExtractorOptions.target`, shown as `target: "v4"`). `defineTailwindTarget()` — the one helper an app author would actually call to pin a target — is never shown. `TW_TARGET` and `CLASS_VOCAB` are never named. An LLM reader (the guideline's actual audience per §0.7) will not learn the API from this; it will learn a pipeline. The pipeline content is good and necessary, but it is *not* the api_surface, so §11.8 is not satisfied.

- **dx failure mode 5 (minor) — would an app author reach for this at all?** Five of six api_surface symbols are cross-package plumbing (`CLASS_VOCAB`, `ClassVocab`, `TW_TARGET`, the vocab `Record`) that an app author should never import. The genuinely app-facing surface is two things: `target?: "v3"|"v4"` on two option objects, and maybe `defineTailwindTarget`. Shipping six public symbols where two are app-facing inflates the surface and makes the guideline harder to write — it must either teach internals or silently omit half the api_surface, and it chose to omit, which is exactly how §11.8 broke. The internals should be marked non-public so the discoverable surface equals the app-facing surface.

## Does it survive?

**survives-with-changes.** The core design is idiomatic and resolves a real, well-evidenced drift (F-C-024) and a real broken-pipeline doc (F-C-012). It is not a reject: the mechanism is correct and the guardrail-§11.7 cross-package consistency test is genuinely valuable — it makes the class-string contract mechanical instead of manual. But it cannot ship as written, because (a) the documented function name does not exist under that name in the package that ships it, (b) the headline option has two contradictory defaults, (c) the two RFCs form a dependency cycle, and (d) the guideline edit — which §11.8/the dx lens explicitly owns — teaches a CLI and CSS syntax while omitting every TypeScript symbol in api_surface, including the one helper (`defineTailwindTarget`) an app author would call. Each is a concrete, falsifiable defect with a concrete fix; folded back, the RFC is shippable. The required changes are listed in frontmatter.

## Guardrail check (dx owns §11.8)

§11.8 guideline-sync: **fail as written.** The RFC's self-check (line 288) claims the guideline "covers `TW_TARGET`/`TailwindTarget`/`defineTailwindTarget`, `ExtractorOptions.target`, the ESLint setting, `emitSafelistCss`." This is inaccurate: searching the two proposed guideline blocks, none of `TW_TARGET`, `defineTailwindTarget`, or `emitSafelistCss` appears as a taught symbol — only `ExtractorOptions.target` (as `target: "v4"`) and the ESLint setting do. The self-check is aspirational, not actual. Required changes #4 + #5 bring the edit into compliance (teach `defineTailwindTarget`, use the real `generateFluentSafelist` call instead of the unconfirmed CLI name, and explicitly scope the internal symbols out of the app-facing teaching surface). The house *voice* of the prose that is present (✓/✗, code-first, LLM-reader) is correct — the defect is coverage, not style.
