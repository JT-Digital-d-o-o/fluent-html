# Verdict: RFC-A-01 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's correctness premise (boolean attrs render bare / are absent when false) is sound. The type-safety *delivery* fails in three places — and the RFC's own "Type-safety story" asserts the opposite of the truth on the central one.

- **Failure mode 1 — convergence onto a structurally-`string` parameter (the killer).** The RFC deprecates ~15 typed boolean setters and routes the fleet onto `.toggle(name: BooleanAttribute, …)`. But `BooleanAttribute` (`src/elements/html-types.ts:40-45`) ends in `| (string & {})`, which admits **every** string. `.toggle("diabled")`, `.toggle("requried")`, `.toggle("onclick")`, `.toggle("href")` all compile. The RFC claims (line 162) typos "are caught by the `(string & {})` tail only as a last resort" — backwards: `(string & {})` catches *nothing*; it only preserves literal autocomplete on the union members while still accepting any string. The deprecated setters had **no** name-typo surface — the attribute name was the method identifier, compiler-checked. Net effect on the typo axis: the migration is a regression, and it lands exactly on the rule §11.4 names ("No bare `string` where a literal union fits"). A wrong call compiles — *more easily* after this RFC than before.

- **Failure mode 2 — render branch is value-typed; the HTML contract is field-typed (Open Question 3, unresolved).** The new branch (`render.ts:210-215`, duplicated in `stream.ts` and `fold/algebras/render.ts`) is `if (typeof value === 'boolean') { if (value) bare(); continue }`, running over `_sk` arrays that interleave string/number and boolean fields: `InputTag._sk` (`forms.ts:125`) has `'name','placeholder','value',…` AND `'checked','disabled','multiple'`; `OptionTag._sk` (`forms.ts:430`) has `'value','label'` AND `'selected','disabled'`; `MeterTag._sk` is all-numeric. The setters for those fields (`setValue(value?: string)`, `Meter.setValue(value?: number)`) are typed, but TS cannot stop a runtime `boolean` from reaching them — `setValue(data.flag)` with `data: any`/`unknown`/a Prisma `Json` scalar is the daily SSR case. Today that yields `value="true"` (wrong, visible). After this RFC it yields `<input value>` — a *bare* attribute that silently drops the value. Unpreventable by types, because the render path keys on the runtime `typeof` of the VALUE with no binding to whether the FIELD is a boolean attribute. The RFC dismisses the field-level fix (`_skBool`) as "over-engineering," but `typeof` is exact for values and *unsound for the field contract* HTML's boolean model requires — an `any`-leak manufactured by the fix.

- **Failure mode 3 — an auto-fix that mutates types/semantics (Open Question 2).** `prefer-toggle` ships `recommended` + auto-fixable and rewrites `.setChecked(expr)` → `.toggle("checked", expr)`. `toggle`'s second param is `boolean` (`tag.ts:173`); the RFC explicitly floats auto-coercing to `.toggle("checked", !!expr)` and leaves it "flag for the ESLint author." A `recommended` auto-fixer that either leaves a type error or silently inserts `!!` coercion the developer never wrote is a type-safety defect distributed as tooling — it changes the program's typing/semantics under `--fix`.

## Does it survive?

`survives-with-changes`. The render-correctness core is right and worth shipping; failure modes 2 and 3 are fixable mechanically. But failure mode 1 is a genuine §11.4 hit the RFC actively misdescribes, so it cannot ship as written. The required changes fold back: close the union for the `.toggle()` convergence path (or carry an explicit ESLint guard + honest admission), make the render branch field-typed via a boolean-attribute registry rather than a value `typeof`, and constrain the codemod's narrowing. With those, the type story is *better* than today; without the union fix, the RFC ships a `string`-typed boolean API to the whole fleet under a "type-safety: pass" banner — the precise false-positive the quorum rule (§8: cut a good idea over shipping a bad API) exists to stop. Confidence is held below 0.8 because the `(string & {})` tail may be a deliberate source-compat choice for existing `.toggle()` callers — but the RFC must *say* so and mitigate, not claim safety it lacks.

## Guardrail check (this lens owns §11.4)

§11.4 (type-safety first) — **FAIL as written, repairable.** The convergence target `.toggle(name)` is bare-`string` via `| (string & {})`, the canonical §11.4 violation; the render branch introduces a value-typed→field-typed unsoundness (a new path for `any`-origin booleans to corrupt string/number attributes); the bundled auto-fix can insert coercions or type errors. None are intrinsic — all three close under the required changes — but the RFC's frontmatter `guardrails_checked` and its Type-safety story currently assert §11.4 "pass," which is unsupportable until `.toggle()`'s union is closed (or lint-guarded) and the render branch is field-gated.
