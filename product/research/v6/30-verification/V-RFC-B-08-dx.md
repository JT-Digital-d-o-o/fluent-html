# Verdict: RFC-B-08 — dx lens

> ADVERSARY. Killing RFC-B-08 through the dx failure mode: worth the surface area? discoverable, consistent, hard to misuse, named right? And is the Guidelines impact correct, minimal, house-style, and complete over `api_surface`?

## Attack

This RFC bundles **three** distinct API additions (typed renderView opts, a builder→reply bridge, a deferred-slot streaming primitive) behind one `impact: high` banner. The DX problem is that the strongest part (Part 1) carries the weakest two, and the type story that justifies the whole RFC does not actually compile against the library it cites.

- **dx failure mode 1 — the headline ergonomic is a type error.** The RFC's core selling line is "pass the Id, not Id.selector" (`{ retarget: layoutIds.mainContent }`, lines 146 and 255). But `RenderViewOptions.retarget` is typed `HxTarget`, and `HxTarget = StandardCSSSelector | ExtendedCSSSelector` (src/htmx.ts:82) — a **string-only** union. The library widens to `Id` only in `RouteHxOptions` and `HxAttributesInput` (`target?: HxTarget | Id`, src/routes.ts:106, src/htmx.ts:255), *never* in `HxTarget` itself. So the RFC as specified rejects the exact call it advertises. Worse, the broken snippet is copy-pasted into the proposed `fastify.md` edit, so the guideline would teach an LLM a non-compiling pattern — the precise "orphaned/mis-taught API" failure §13 warns about. This alone clears the bar for not-survives-as-written.

- **dx failure mode 2 — "typed" is leaky on the very path sold as typed.** Part 2's `.applyTo(reply)` is pitched as the typed escape from raw header spreading. But it routes through the *existing* `HxResponse` whose `.retarget(selector: string)` and `.reswap(strategy: HxSwapStyle | string)` (src/patterns.ts:280,289) accept bare strings — the `| string` escape hatch means `hxResponse(v).reswap("outermorph").applyTo(reply)` still compiles to a broken swap. The RFC claims `.applyTo` kills the F-B-124 typo class; it does not, on the multi-header path it exists to serve. Two doors to the same room, one still unlocked.

- **dx failure mode 3 — Part 3 is a different RFC wearing Part 1's coat.** `Deferred()` + streaming is a genuinely larger design (it depends on `Skeleton` from another RFC, on `renderToStream` being non-eager — which it is NOT today: `streamImpl` walks the whole tree in one `read()` tick and pushes `null`, src/render/stream.ts:111-117, the Track-D "eager stream" finding — so the "shell flushes immediately" claim is unproven against the current engine), and it ships with a route-type that only fits param-less GET endpoints (failure mode below). Bundling it inflates `impact: high` and risks the verifier rubber-stamping the streaming primitive on the strength of Part 1. §13 idea-inflation: the `dx` lens is supposed to ask "is this worth the surface area?" — for Parts 2+3, jointly, the answer under the current engine is "not yet."

- **dx failure mode 4 — `Deferred` route type excludes the common case.** `route: { method: "GET"; resolve: (query?: QueryParams) => string }` structurally matches only param-LESS routes; a `:param` route's `resolve` is `(params, query?) => string` (src/routes.ts:130-132). Deferred fragments are routinely per-entity (`/orders/:id/timeline`), so the primitive silently rejects its most natural use and the one worked example (`/stats`) hides it. A primitive that doesn't typecheck for the obvious case is a discoverability trap.

- **dx failure mode 5 — guideline anchors are fabricated/stale.** `fluent-html.md` has no streaming section at all (grep empty), yet the RFC says "augment the streaming reference (~line 170)." `renderStreamView` (in `api_surface`) is taught in NO web-development/** file. The CLAUDE.md SSR block is at 280-286, not ~278. `renderView` is documented as returning `void` (fastify.md:62), contradicting the chaining the opts API needs. A reviewer trusting the Guidelines-impact section would apply edits against anchors that don't exist — guardrail §11.8 is not actually satisfied despite the §11.8 self-check claiming "pass."

## Does it survive?

**survives-with-changes.** Part 1 (typed `renderView` opts) is the real win: it kills ~20 raw `HX-*` header sites (F-B-124, frequency 19), it is discoverable (opts object on the call devs already make), idiomatic (mirrors `defineIds`/`Id` single-sourcing), and additive. That core is worth shipping. But it does **not** survive *as written*: the central Id ergonomic is a compile error, the "typed" guarantee leaks through the builder, the streaming primitive is unproven against an eager engine and mistyped for param routes, and the Guidelines impact — which the `dx` lens specifically owns — cites non-existent anchors and leaves `renderStreamView` untaught. These are concrete, mechanical fixes (listed above), so this is `survives-with-changes`, not `reject`. The confidence is held below 0.8 because if Part 3 cannot be made non-eager by Track D, `Deferred` should be split out into its own RFC rather than amended in place — a scope call the synthesis wave must make.

## Guardrail check (dx owns §11.8 guideline-sync)

§11.8 is **NOT** satisfied as claimed. The self-check (line 298) asserts every `api_surface` symbol is covered, but: `renderStreamView` appears in no topic ref; the `fluent-html.md` streaming anchor it targets does not exist; the `fastify.md:62` `renderView(): void` augmentation it must change is untouched; and the proposed `fastify.md`/`CLAUDE.md` snippets embed the non-compiling `{ retarget: Id }` form. House style (✓/✗, code-first, LLM-reader) is correct in shape, but correctness and completeness fail. Required-changes item 5 and 6 fold these back. With them applied, §11.8 passes.
