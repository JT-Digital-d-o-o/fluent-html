# Verdict: RFC-B-06 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

This RFC stamps itself `breaking: additive` across the board (`§11.5 backward-compat: pass — additive`). Verified against the real source, that stamp is over-confident: the design hides at least one latent signature that **must break to become correct**, and one **behavioral** wire-format change that is not codemod-trivial. Default-reject posture applies; I downgrade to `survives-with-changes` only because the breakage is fixable inside the RFC before any code ships.

- **breaking failure mode 1 — the `route` type is wrong and will force a future breaking signature change (killer).** `TableOptions.route`, `SortHeader.route`, and `Pagination.route` are all typed `(options?: RouteHxOptions) => HTMX`. That is exactly the *parameter-less* branch of `RouteCallable` (src/routes.ts:145-150). A `defineRoutes` route with a `:param` segment — e.g. the canonical `detail: { path: "/:id", params: { id: "number" } }` from the project guidelines — resolves to `(params, options?) => HTMX` and is **not assignable** to the RFC's `route` type. So Table.of works for `events` (param-less) but a table whose row-links or scoped route carries a path param cannot be wired without a cast. The instant someone needs that (and analytics drill-downs routinely do), the fix is to widen `route` — i.e. change a *shipped public signature*. That is the textbook unmarked breaking change §11.5/§13 "guardrail drift" exists to catch: it sneaks in under `additive` and detonates in a later minor.

- **breaking failure mode 2 — `vals` → `query` is a behavioral wire-format change, not pure addition.** The "before" code forwards filters via `vals: { ...extraVals, sort, dir }`. `vals` is real (HTMX.vals, src/htmx.ts:210; serialized via `jsonOrStr('vals')` in render.ts:113 / stream.ts:50) and emits `hx-vals` — a JS-evaluated/body bag. The "after" routes everything through `state.toQuery()` → `RouteHxOptions.query` → `buildQueryString` (routes.ts:170) → a URL `?key=value` string. For an app that today relies on `hx-vals` semantics (e.g. POST bodies, non-string values, server reading body vs querystring), swapping to `Table.of` silently moves the data from one transport to another. That is observable at the network layer and at the Fastify handler (querystring schema vs body schema). The RFC calls adoption "a one-line call-site change" and "no codemod required" — false for any `vals`-based table. It must be flagged as a behavioral migration.

- **breaking failure mode 3 — name collisions on adoption.** The RFC exports `SortDir`, `ThCell`, `TdCell`, `Pagination`, `SortHeader` as new top-level symbols. Cited apps already define `ThCell`/`TdCell`/`Pagination` locally and a `SortDirection`/`SortDir` type (RFC line 152 even uses `SortDirection`). On `import { ThCell } from "fluent-html"`, every app with a local `ThCell` gets a redeclaration/shadow conflict in its barrel and must delete the local one in the same change. That is a small but real, per-app, non-additive edit — fine if bundled into one migration note, but the RFC currently frames it as drop-in.

- **breaking failure mode 4 — open questions encode future behavioral breaks.** `withSort` toggle policy (desc-first? two- vs three-state) and page-window rendering are left "leaning". Whatever ships first becomes the contract for every generated sort/page link; changing it later alters every adopter's URLs and sort order — a behavioral break. These must be decided pre-ship, not deferred.

## Does it survive?

**survives-with-changes.** None of the four findings is a guardrail *killer* in the §11.3 (escape) or §11.1 (deps) sense — the escape path and zero-deps claims hold, and the *element* form `Table(...)` genuinely is preserved at the call level. The defects are: (1) a wrong central type that is presented as additive but is a future breaking change, (2) a behavioral wire-format shift mislabeled as drop-in, and (3) two adoption-time renames/collisions that belong in the single migration. All are correctable within the RFC. Per the default-reject rule I would reject an RFC that left finding 1 unaddressed — a shipped public type that must break to be usable is exactly the false-positive §8 warns against. Because the fix is a type widening that can land before code, I gate rather than kill: the five `required_changes` above must fold back into the RFC, and the frontmatter `breaking:` field must change from `additive` to `additive (with one behavioral migration: vals→query)` with a `breaking-changes.md` entry for the `vals` transport change and the per-app symbol renames.

## Guardrail check (§11.5 backward-compat — this lens owns it)

- `Table(...)` element call form: preserved (✓), but the `typeof Table` shape changes function→intersection — must use `Object.assign` and confirm no reflection consumers (low risk, note it).
- `route` type: **fails** for parameterized routes as written — REQUIRED widening (above).
- `vals`→`query`: **behavioral change** — not pure-additive; needs a `breaking-changes.md` line and an explicit "this changes the transport" callout.
- New symbol collisions (`ThCell`/`TdCell`/`Pagination`/`SortDir`): adoption-time, non-additive per app — bundle into the one migration.
- The `breaking: additive` frontmatter is **not honestly marked** as-is; it must acknowledge the `vals` behavioral migration and the route-signature limitation before this is roadmap-eligible.
