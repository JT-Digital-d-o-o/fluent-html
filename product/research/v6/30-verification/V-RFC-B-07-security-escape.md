# Verdict: RFC-B-07 — security/escape lens

> You are an ADVERSARY. Your job is to KILL this RFC through the security/escape lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's §11.3 self-check asserts PASS: *"`ErrorPage`/`AuthShell`/`OAuthButtons` emit via the standard escaping `render`; error `message` is text content, never `Raw`. `OAuthProvider.icon` is a caller-supplied `View` (their responsibility, same as today)."* This conflates **HTML-context escaping** with **URL-scheme safety**, and it under-specifies the one security primitive the RFC ships. Three concrete failure modes:

- **security/escape failure mode 1 — `javascript:` URI XSS through `OAuthButtons.href`; renderer escaping does not save you.** The renderer's `escapeAttr` (`src/render/escape.ts:37`) is literally `escapeHtml` — it replaces only `& < > " '` (verified: `src/render/escape.ts:11-28`). It does **not** neutralize a URL scheme. An anchor rendered with `href="javascript:alert(document.cookie)"` escapes to *exactly* that string and **fires on click**. `OAuthButtons({ providers: [{ href }] })` takes a bare `href: string`, and the RFC explicitly declines to validate it. But the RFC's own worked example is `href: oauthRoutes.authorize.resolve({ provider: "google" })` — and `provider` is a request-derived route param in the shipped apps. A `provider` segment that resolves into a `javascript:`/`data:text/html,...` scheme (mis-config, or an open `:provider` route) lands an executable href the library happily renders. This is a *new, first-class auth-view primitive the library owns* whose entire job is rendering IdP links; "same as today" is not an acceptable security posture for it. The RFC never states the load-bearing fact that escaping ≠ scheme-validation, so an LLM reading the matching guideline edit will assume `OAuthButtons` is href-safe — exactly the adoption-of-a-vuln failure §11.8 is meant to prevent.

- **security/escape failure mode 2 — `safeReturnTo` spec is weaker than its only proven implementation → reintroduced open redirect, standardized to 4-6 apps.** The RFC's signature comment is *"Open-redirect guard: same-origin absolute path only, else null."* The battle-tested implementation it cites (`rideshare/src/auth/auth.return-to.ts:9`) rejects `//host` **and** the backslash variant `/\host` — both of which browsers treat as host-changing protocol-relative URLs despite "starting with `/`". "Same-origin absolute path only" does not encode the `/\` trap; the obvious from-prose reimplementation `raw.startsWith("/")` is an open redirect against `/\evil.com`. The RFC's entire migration pitch is *"glimm/mngmt/storysell gain returnTo preservation they were silently missing"* — i.e. it propagates **one canonical guard to 4-6 apps**. If that guard's spec is under-defined, the RFC standardizes the vulnerability instead of the fix. A shared security primitive must ship with its reject-list and test vectors pinned, not a one-line gloss.

- **security/escape failure mode 3 — returnTo carried unsigned weakens the guard the RFC claims to bundle.** The reference `consumeReturnTo` carries returnTo across the OAuth round-trip in a **signed, httpOnly, short-lived** cookie and re-validates with `safeReturnTo` on read. The RFC's `loginRedirect: (returnTo) => authRoutes.login.resolve({ returnTo })` drops returnTo into a **query string** with no signing and shows `safeReturnTo` only at produce time, not at consume time. The value is fully attacker-controllable on the way back, so the guard must re-run on consumption — which the RFC never states. The RFC asserts `safeReturnTo` is "built in," but the worked example bypasses the signed-cookie discipline that makes the rideshare version actually safe.

**Secondary / cleared.** `renderHx` header injection (CRLF in `HX-Trigger`/`HX-Redirect` from un-sanitized strings, `src/patterns.ts:202-264`) is a *pre-existing* property of `hxResponse(...).build()`, not introduced here — `renderHx` is a thin `reply.headers(headers); reply.renderView(html)` wrapper, and Node's http layer rejects CR/LF in header values. No new surface; noted, not blocking. `ErrorPage` message rendering is text-context (escaped via `render`), so stored/reflected XSS there is low — but the prod-hide must cover the 4xx branch and requireUser's 401 message must stay static (required change 4).

## Does it survive?

`survives-with-changes`. The RFC does not *regress* HTML escaping — it routes through the same escaping renderer, and its highest-frequency changes (`requireUser` retiring 261 `request.user!`, single-sourcing `safeReturnTo`, returnTo preservation) are net security *improvements*. But it ships a security primitive (`safeReturnTo`) under-specified relative to its own reference, and a markup-emitting URL primitive (`OAuthButtons`) with an explicit "we don't validate the href" stance that is wrong on a renderer whose escaping provably does not stop `javascript:`. Under default-reject these are credible killers — but they are closable by *tightening the contract*, not by cutting the API. Hence conditional survival with the four required changes folded back into the RFC body and its §Guidelines-impact edit (the LLM reader must be told escaping ≠ scheme-safety).

## Guardrail check (§11.3 escape-by-default)

The renderer escapes by default for HTML text and attribute-*value* context (`src/render/render.ts:202-225`, `src/render/escape.ts:11-39`) — confirmed, no `Raw` is introduced by this RFC. **But the RFC's §11.3 PASS is incomplete:** escape-by-default does not extend to URL-scheme safety, and the RFC's two new URL-bearing surfaces (`OAuthButtons.href`, `loginRedirect`/`safeReturnTo`) sit exactly where that gap bites. Mark §11.3 **PASS-with-caveats**: the escaping the guardrail owns is intact, but it is not a sufficient proof of "no XSS / no open-redirect regression" for this RFC. The scheme-validation + `safeReturnTo` reject-list + signed-cookie changes are required before it folds into v6.
