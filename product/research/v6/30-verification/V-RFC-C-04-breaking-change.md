# Verdict: RFC-C-04 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC frames itself as cleanly additive ("v3 apps: no action. Lint output is byte-for-byte identical"). Under the breaking-change lens the real risk is the opposite of conventional breakage: **the regen ships entries that silently don't fire, and the only way to make them fire is an unstated behavioral change to v3.** I read the actual plugin source (`fluent-html-eslint-plugin/src/rules/`) and the central mechanism contradicts the RFC.

- **breaking-change failure mode 1 — the proposed v4 table entries are dead code as written.** `matchClass()` (no-known-modifiers-in-setclass.ts) iterates `FIXABLE_PATTERNS` and returns on the **first** `startsWith` match. The broad `{ pattern: "bg-", methodName: "background" }` lives at **line 39**. The RFC places `bg-linear-`/`bg-radial-`/`bg-conic-` in the "Gradients" block (~line 384, after `bg-`). I reproduced it: `bg-linear-to-r` matches `bg-` first and would auto-fix to `.background("linear-to-r")` — never `.gradientTo("to-r")`. The RFC's Example 1 "after" output is unreachable with the table it specifies. The fix is real (reorder ahead of `bg-`), but the RFC neither states it nor accounts for it — and it is exactly the kind of ordering subtlety the codebase already handles deliberately ("Padding - directional first (more specific)", "specific colors before generic text-").

- **breaking-change failure mode 2 — the RFC's premise misdescribes current behavior, so its "before/after" contract is wrong.** Because `bg-` shadows `bg-gradient-` (line 384) today, `setClass("bg-gradient-to-r")` already auto-fixes to `.background("gradient-to-r")`, NOT to `.gradientTo("to-r")` as the RFC's F-C-023 narrative repeatedly claims ("auto-fixes to .gradientTo(...)... Fix made it worse"). The v3 gradient fixable is *already dead*. This matters for breaking-change accounting: making the gradient entries live (by reordering) **changes v3 behavior** — `bg-gradient-to-r` would start fixing to `.gradientTo(...)`. That is desirable, but it is a v3 behavioral change, which directly falsifies the RFC's "byte-for-byte identical" / `breaking: additive` claim. An honest migration note is required; right now the breakage is hidden behind an incorrect baseline.

- **breaking-change failure mode 3 — the documented per-rule `{ target: 4 }` path hard-fails on current schemas.** `no-conflicting-classes-in-setclass.ts` has `schema: []` (no options at all); `no-known-modifiers-in-setclass.ts` has `additionalProperties: false`. Passing `{ target: 4 }` to either before widening the schema is an ESLint validation error, not a silent fallback. The RFC documents `"fluent-html/no-known-modifiers-in-setclass": ["warn", { target: 4 }]` as a supported alternative to the preset; it would throw. Codemod-ability isn't the issue — runnability is.

- **breaking-change failure mode 4 — config-format mismatch makes the migration snippet itself non-loading.** The shipped configs are **legacy** `.eslintrc` objects (`plugins: ["fluent-html"]`, string-keyed rules). The guideline examples (`export default [fluentHtml.configs.recommendedV4]`) are **flat config**. Spreading a legacy config object into a flat-config array is malformed; the "one-line config edit" migration the RFC sells as the entire cost would not load. This is a guideline-edit defect (the dx lens also owns it) but it is load-bearing for the migration story.

- **Not-breaking, correctly handled (credit where due):** the `minTarget`/`maxTarget` gating, the new `no-removed-v4-utilities` rule (inert on v3), the `recommendedV4` opt-in preset, and the dependency-pinning of `methodName` to RFC-C-01/C-02 lib methods (so the fix can't suggest a non-existent method) are all genuinely additive and well-marked. The message-only decision for `*-opacity-*` (no autofix because the companion color is unknown) is correct and avoids a far worse silent-breakage autofix.

## Does it survive?

**Survives-with-changes.** None of these defects is fatal to the *idea* — target-aware vocabulary is the right design and the alternatives (flat regen, twin packages, auto-detect) are correctly rejected. But the RFC as written would ship a regen whose headline v4 entries never fire, justified by a "before" state that doesn't match the code, under a `breaking: additive` flag that is false for the v3 reorder, with a per-rule option path and a migration snippet that both fail to load. Those are concrete, mechanical defects that fold straight back into the table edits, the schema, the frontmatter, and the guideline snippet — see required_changes. With them applied the RFC is sound; without #1–#3 it ships a no-op dressed as a fix.

Confidence 0.72 (not higher): the matching-order and schema defects are verified against source and decisive; I'm slightly less certain the maintainers haven't already intended the reorder implicitly, and the config-format fix has two valid resolutions rather than one forced answer.

## Guardrail check (breaking-change owns §11.5)

§11.5 backward-compat is **mis-asserted PASS** in the RFC. The data-only additions (xs slot, no-removed-v4-utilities, preset) are additive, but the gradient fix is unimplementable without reordering FIXABLE_PATTERNS, which changes v3 match precedence for `bg-gradient-*`. The RFC must either (a) gate the reordered gradient entries so v3 output is truly unchanged and accept that F-C-023 stays unfixed on v3, or (b) reclassify the v3 gradient behavior change as an intentional fix and record it in breaking-changes.md. "No action for v3 apps / byte-for-byte identical" cannot stand as written.
