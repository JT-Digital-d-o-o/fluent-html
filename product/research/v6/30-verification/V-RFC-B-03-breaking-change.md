# Verdict: RFC-B-03 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty.

## Attack

The RFC frontmatter says `breaking: additive` and the Migration section closes with "**Nothing for `breaking-changes.md`.**" At the symbol level this is mostly honest — I verified no `Alert`/`Badge`/`Card`/`Skeleton`/`Callout`/`StatCard` is currently exported from `src/index.ts`, and no `.variant()`/`.size()`/`.gradient()` exists on the Tag prototype. New symbols, no signature changes. But "additive" is being used to wave past three concrete breakage vectors:

- **breaking-change failure mode 1 — the `.w()` overload is fake-new and a real hazard.** The RFC adds `w(fraction: TailwindWidth): this` to the Tag augmentation and lists it in `api_surface`, claiming "this RFC guarantees fraction keys." This is false. `src/core/tailwind-types.ts:22-26` already enumerates every fraction (`1/2`, `1/3`, … `11/12`) in `TailwindWidth`, and `src/core/tailwind-methods.ts:139` already declares `w(value: TailwindWidth): this`. The proposed overload has a signature **identical** to the existing one. Declaring the same overload twice doesn't "guarantee" anything new — it either resolves to a no-op or, if someone implements it as a separate runtime branch, introduces an overload-resolution ambiguity against the existing `w(unit, amount)` numeric overload. An RFC that lists a no-op as net-new surface is hiding a change it doesn't understand; under the default-reject rule that alone is disqualifying for that line item.

- **breaking-change failure mode 2 — `.gradient()` ships with an UNDECIDED output class.** Open Q #3 says the emit is `bg-linear-to-*` (v4) "if v3 dual-target is kept… the method needs a target-aware emit — defer to the Track-C dual-target decision." So the method's actual emitted class string is *unresolved*, yet it appears in `api_surface` with `depends_on: []`. Meanwhile the existing `gradientTo()` emits v3 `bg-gradient-${direction}` (src/core/tailwind-methods.ts:576). Shipping `.gradient()` now means: on a v3 target it emits `bg-linear-to-r` which the v3 runtime and the current extractor don't recognize → the gradient silently doesn't render. That is a behavioral regression (visual break) reachable with zero TS errors — the worst kind, because it's invisible to the compiler and to `breaking-changes.md`. "Additive symbol, broken output" is still broken.

- **breaking-change failure mode 3 — §11.7 is self-downgraded from blocker to footnote.** The guardrail check admits `.gradient()` and the semantic palettes "emit new class strings… Wave-4 `_merge.md` must reflect them in the Track-C extractor + ESLint vocab" then concludes "Noted, not blocking." This is exactly the class-string contract guardrail (§11.7) the algorithm calls non-negotiable. If the extractor vocab update doesn't ship in the *same* milestone, every app that adopts `Alert`/`Badge`/`StatCard` with the default theme renders with missing CSS — the status colors (`green-50`, `red-200`, …) and gradients won't be in the generated stylesheet. No signature changed; the app is still broken at runtime. The RFC marks this honestly but then under-rates its severity and doesn't bundle it into a single migration as §11.5(b) requires.

The one thing the RFC gets RIGHT: the app-level import collision (local `Alert` vs imported `Alert`, ~88 Badge sites) is genuinely opt-in — apps "keep their hand-rolled copies until they choose to migrate." So this is not forced breakage. But the migration vehicle (the "optional codemod") is hand-waved as "left to Wave-4 to scope, not required for adoption," which leaves the duplicate-identifier step unstated.

## Does it survive?

**survives-with-changes.** None of the three vectors is a forced, fleet-wide compile break, so this isn't a hard `reject` — the additive-at-the-symbol-boundary claim holds. But the RFC mislabels a no-op as new surface (`.w()`), ships a method with an undecided output class (`.gradient()`), and downgrades the class-vocabulary contract that its own components depend on at render time. Each is a real defect the breaking-change lens must force back into the RFC before it can be called honestly additive. The four `required_changes` above are exact and fold back cleanly: drop the phantom `.w()` overload, pin or gate `.gradient()`'s emit (add the Track-C `depends_on`), promote §11.7 to a same-milestone bundle, and state the codemod's rename step as the migration path for adopters.

## Guardrail check (breaking-change owns §11.5)

§11.5 backward-compat: **PASS with conditions.** Additive at the public-symbol boundary (verified: no current export/prototype-method collisions in `src/index.ts` or the Tag prototype). FAILS the spirit of §11.5(b)/§11.7 on two counts until amended: (1) `.gradient()` can emit a class the active target can't resolve (undecided output = un-codemodable behavioral change), and (2) the new class vocabulary (status palette + `bg-linear-to-*`) is a §11.7 cross-package contract change that must be bundled into the same migration, not deferred as "noted, not blocking."
