# Verdict: RFC-C-05 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's entire value proposition is a type-safety claim: *"No TypeScript error crosses the package boundary because there is no shared type"* (Problem), fixed by *"one type that fails to compile if the copies disagree."* I attack that claim on its own terms — and on the ground truth of the three files it cites.

- **type-safety failure mode 1 — the lib seam is stringly-typed, so the loop never closes.** The one place the lib touches the vocab is `prefixOf("gradientTo")` (Proposed API line 100). As written, `prefixOf` takes a bare `string`. Delete or rename the `gradientTo` row in `vocab.ts` and *the lib call site still compiles* — `prefixOf` returns `undefined` (or throws) at runtime. That is precisely the silent cross-package drift the RFC was written to abolish, reintroduced at the lib boundary. The drift test (a runtime assertion) becomes the *only* guard, which contradicts the headline "a type that fails to compile." A verifier defaulting to reject cannot accept an RFC whose central type-safety claim is unmet at its own example call site.

- **type-safety failure mode 2 — `as const satisfies` does not enforce key uniqueness.** `classVocab` is an *array* of structs. `satisfies readonly UtilityDef[]` checks each element's *shape*; it cannot reject two rows whose `method` is `"shadow"`. Duplicate or near-duplicate rows (trivially produced by the "one-time mechanical port" of three existing lists, Migration §Codemod) compile cleanly, and `emitClasses`/`prefixOf`/`buildMethodPatterns` then resolve to whichever the linear scan hits first — a divergence the type system is advertised to make impossible. The "single source of truth" is not even single-valued in the type.

- **type-safety failure mode 3 — `EmitShape` underfits the real surface, dumping renamable methods into `kind:"custom"`.** I read the three cited files. The live extractor uses opaque `(args) => string[]` closures including whitelist branches (`rounded` gates on `ROUNDED_CORNERS`, `shadow`/`divideX`/`grow` are bare-or-prefix). The live eslint map (`no-known-modifiers-in-setclass.ts`) carries fields the RFC's `UtilityDef` has no slot for — `exactMatch`, `fixedValue` (e.g. `font-sans`→`fontFamily("sans")`), and **order-dependent** prefix matching with explicit "must come after" comments (`ring-` after exact ring widths, `shadow-` after shadow exacts). The six `EmitShape` variants model none of exactMatch / fixedValue / ordered-prefix / whitelisted-directional. Every such row falls to `kind:"custom"` = "hand-written in all 3" (line 58) — i.e. the per-package triple-edit *survives untyped* under a `custom` label, for a non-trivial fraction of the ~120 rows. The RFC never bounds that fraction. If it's large (the eslint file alone shows exactMatch/fixedValue/ordering across many rows), the RFC delivers single-sourcing for the easy rows and leaves the hard, drift-prone ones exactly as they are today — while *claiming* §11.7 is now mechanized.

- **type-safety failure mode 4 — `TARGET`, `fixPrefix`, `skip` are bare strings at exactly the boundaries that go silently wrong.** `TARGET` is a build-env read; if it isn't validated to `TailwindTarget` at the boundary, `emit[TARGET]` indexes with a bad literal → `undefined` → empty class array → no CSS, silently. `fixPrefix?: string | string[]` is a bare string a typo can rot (dead eslint match, no error). `skip: Array<"extractor"|"eslint">` strings are not tied to the codegen's consumer set. These are §11.4 ("no bare `string` where a literal union fits") violations in the very RFC that claims a §11.4 pass.

## Does it survive?

**survives-with-changes.** The RFC is directionally correct and the discriminated-union *idea* is sound — but as specified it does not deliver the compile-time guarantee it is sold on, and it under-models the real extractor/eslint surface badly enough that the divergence it targets can survive untyped. None of the holes are fatal to the design; each has a concrete, mechanical fix that folds back into the RFC. A wrong call *can* compile today (rename a row, lib still builds; duplicate a method, lookup silently picks one; typo a `fixPrefix`/`TARGET`, dead output). That is disqualifying for a *type-safety* RFC unless the changes below are made mandatory — hence not a clean `survives`. It is not `reject` because the fixes are additive type tightenings, not a redesign.

Required changes are listed in frontmatter; the load-bearing two: (1) type the lib's vocab accessor over the derived method-name union so a removed/renamed row is a compile error at the lib call site, and (2) expand `EmitShape` (or explicitly enumerate and bound the `kind:"custom"` rows) to cover the exactMatch/fixedValue/ordered-prefix/whitelisted shapes the live eslint and extractor files actually use — otherwise §11.7 is mechanized only for the rows that were never the problem.

## Guardrail check (§11.4 type-safety — this lens owns it)

**Not a clean pass as written.** The RFC claims §11.4 pass on four grounds (discriminated `EmitShape`, `as const satisfies`, required `v3`, literal `TailwindTarget`). Three of the four are real; but `as const satisfies` does not enforce method-key uniqueness, the `EmitShape` union does not cover the real surface (forcing untyped `custom`), and the cross-package seams (`prefixOf`, `TARGET`, `fixPrefix`, `skip`) carry bare `string` exactly where §11.4 forbids it. §11.4 is conditionally satisfied only after the frontmatter changes; until then the RFC overclaims its own headline guardrail.
