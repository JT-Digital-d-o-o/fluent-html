# Verdict: RFC-A-01 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC sells `breaking: breaking` as "honestly marked, codemod-able end-to-end, behaviorally uniform." Two of those three claims do not survive contact with the source.

- **Breaking-change failure mode 1 — the fix misses a render path, so the behavioral change is NON-uniform.** §1 of the RFC asserts: *"The three `_sk` loops branch on `typeof value === 'boolean'`"* and names `src/render/render.ts`, `src/render/stream.ts`, **and `src/fold/algebras/render.ts`** as the three. The first two are genuinely `_sk` loops (render.ts:208-215, stream.ts:146-153). **`src/fold/algebras/render.ts` is not.** It has no `_sk` reference at all — it serializes a flat `TagAttrs` plain-object via `Object.entries(attrs)` with `String(value)` (lines 16-20 and 23-30). Boolean setter fields reach it because `extractAttrs` (fold.ts:21-25) blindly copies every own key of the tag (`checked`, `defer`, `disabled`, `selected`, …) into `TagAttrs`. A maintainer applying the RFC patch literally will search `fold/algebras/render.ts` for an `_sk` loop, not find one, and either (a) skip the file — leaving `foldView(renderAlgebra)` emitting `<script defer="true">` and `<input checked="false">` forever, i.e. the F-A-001 footgun survives on a shipped public render path — or (b) graft the branch onto the generic loop, which the RFC never specifies and which also governs custom-attribute serialization (a different blast radius). Worse, there is a **second** undocumented copy of `extractAttrs` in `src/fold/para.ts` (para.ts:9) feeding the same algebra. The RFC's "three loops" is really "two `_sk` loops plus a structurally different generic loop reached through two duplicate extractors." A breaking change that is inconsistent across render backends is *worse* than the current uniform bug: now the same tag renders differently depending on whether you call `render()` or fold through `renderAlgebra`.

- **Breaking-change failure mode 2 — the migration is not closed over the actual symbol set.** The RFC promises codemods that "pay off the 186 legacy call-sites" and a deprecation that "bundles into one migration." But the deprecation list and `api_surface` are drawn from memory, not the code. Ground truth: the codebase has 17 boolean setters; the RFC omits `setSelected`, `setNovalidate`, `setAllowfullscreen`, `setPlaysinline`, and lists a phantom `setDefault` that does not exist. Each omitted setter is a live API whose *behavior* changes under the render fix (e.g. `setSelected(false)` flips `selected="false"` → omitted) but which gets **no `@deprecated` tag, no guideline ✗-line, and no `prefer-toggle` rewrite**. That is the precise F-A-003 failure the RFC claims to be curing: a boolean attribute whose behavior shifts with no migration path. And `setPlaysinline` is a trap door — `'playsinline'` is absent from the `BooleanAttribute` union (html-types.ts:40), so the prescribed codemod `setPlaysinline()` → `.toggle("playsinline")` compiles only through the `(string & {})` fallback, silently demoting the very type-safety the RFC's "Type-safety story" advertises. The migration, as written, is neither complete nor cleanly codemod-able for the full surface.

- **Secondary (non-fatal):** Open Question 3 ("does any string `_sk` field ever hold `true`/`false`?") is the right question but is left open while the fix it gates ships anyway. The audit actually comes out *in the RFC's favor* — `aria-*`, `contenteditable`, `draggable`, `spellcheck` (legitimate string `"true"`/`"false"`) all route through `attributes`, not `_sk`, so the `typeof === 'boolean'` branch never touches them — but "open question, shipped anyway" is not an acceptable resolution for a §11.5 breaking change. State the audit result.

## Does it survive?

**survives-with-changes.** The core intent is sound and genuinely a bug-fix; I cannot reject it on the merits, and the deprecate-now/remove-in-v7 staging is the correct lesson from F-A-003. But under the breaking-change lens the RFC currently **under-declares its own blast radius**: it misidentifies a render path (leaving the bug live there), and it draws its deprecation/codemod set from an inaccurate symbol list (leaving four real setters behaviorally changed with no migration, one of them type-unsafe to migrate). Those are the exact "hidden breakage, not codemod-able, not bundled into one migration" failures this lens exists to catch. They are fixable without redesign, so the verdict is survives-with-changes, not reject. The five required changes above must fold back into the RFC before it can honestly claim "codemod-able end to end."

## Guardrail check (§11.5 backward-compat — this lens owns it)

- **Is the breaking honestly marked?** Partially. `breaking: breaking` is set, but the *scope* is wrong: it omits the fold render path and four setters. Honest marking requires the corrected render-path list and the complete 17-setter list.
- **Codemod-able where possible (§11.5a)?** Not as written — `setSelected`/`setNovalidate`/`setAllowfullscreen`/`setPlaysinline` have no codemod, and `setPlaysinline`'s codemod target is not in the type union.
- **Bundled into one migration (§11.5b)?** The `breaking-changes.md` note covers only the named setters; it must enumerate all 17 and the cross-render-path behavior change.
- **Justified by impact (§11.5c)?** Yes — the `checked="false"` → browser-sees-checked bug is a real correctness defect with confirmed app evidence (ttl, gym-crm). Impact justifies the break; the break just has to be declared completely and fixed on *every* path it claims to fix.
