# Verdict: RFC-D-04 — breaking-change lens

> Adversary. Goal: kill RFC-D-04 through hidden/under-marked breakage.

## Attack

I verified every signature and behavioral claim against `src/render/render.ts`, `src/render/stream.ts`, `src/core/tag.ts:157-163`, `src/index.ts:23-24`, and `test/security.ts:248-285`. The public-signature story holds up — but the *behavioral* story does not, and the frontmatter `breaking: additive` is doing work it hasn't earned.

- **Breaking failure mode 1 — silent precedence REVERSAL, mislabeled additive (killer).** Today's path is `renderWithNonce` → `applyNonce` → `view.setNonce(nonce)` (render.ts:51,58), and `setNonce` does `this.attributes['nonce'] = nonce` (tag.ts:160) — an **unconditional overwrite**. So the *current, shipped* behavior is **render-time nonce wins over an author-set `.setNonce()`**:
  ```ts
  renderWithNonce("rt", Script("x").setNonce("author")) // today → <script nonce="rt">
  ```
  RFC-D-04's stated precedence is the **opposite**: "author-set `.setNonce(...)` wins over the render-time nonce" (RFC §Proposed API, precedence rule). So the same call would emit `nonce="author"` after the change. That is a behavioral change in emitted HTML, dependent on runtime values, hence **not codemod-able** and **not detectable by grep**. The RFC nonetheless stamps `breaking: additive` and downgrades the whole thing to a "Bug fixes" *note* with "no entry" in `breaking-changes.md`. Worse, the RFC's own **Open Question #1** admits the precedence direction is *undecided* ("Decision for a human"). An RFC cannot simultaneously (a) declare a precedence rule, (b) admit it's unresolved, and (c) claim additive/non-breaking. One of those three is false. Under the §8 default-reject-under-uncertainty rule, an unresolved behavioral reversal labeled additive is exactly the "breaking API sneaks in under a minor" failure mode (§13 guardrail-drift row).

- **Breaking failure mode 2 — ambiguous removal of a public method.** The internal contract says "`applyNonce()` and the `setNonce()` pre-pass are deleted from the render path." `applyNonce` is private and fine to delete. But `Tag.setNonce()` is a **public method** (tag.ts:157), exported via the `Tag` class, and covered by exact-match tests (test/security.ts:248-258, `assert.strictEqual` on `<script nonce="abc123">`). The phrase "the `setNonce()` pre-pass" is the *caller* `applyNonce`, but a careless implementer reads "delete setNonce" — and `Tag.setNonce` isn't in `api_surface`, so its retention is unstated. If `setNonce` were removed or changed to stop writing the attributes bag, the strictEqual tests break and the public surface shrinks — a breaking change not marked anywhere. The author-wins precedence rule actually *requires* `setNonce` to keep writing the bag so the renderer can detect "author already set one." This needs to be said.

- **Breaking failure mode 3 — output-byte ordering shift.** An author `setNonce` lands the nonce in the `extraAttrs` bag and serializes in the extra-attr loop (render.ts:218-228), positioned *after* id/class/style/`_sk`. The RFC's render-time nonce is appended inline at the script/style branch (render.ts:239) — a different string position. For any `<script>`/`<style>` carrying other extra attributes, the emitted attribute *order* differs between the old (`applyNonce`) path and the new inline path. The RFC's "passes as-is" claim survives only because the three `renderWithNonce` tests use `.includes()`/regex-count; it is **not** byte-identical, contradicting the "output is **identical**" assertion in Migration & compatibility. Apps doing HTML snapshot/golden comparisons (common in SSR test suites) would see a diff. Honest marking: "attribute order may change; semantics identical."

- **Breaking failure mode 4 — undeclared dependency on the `RawCtx` refactor.** `depends_on: []`, yet the type-safety story and internal contract both lean on replacing the `boolean | string` ctx flag with a `RawCtx` literal union "adopted from recon §4" — a change to `renderImpl`/`streamImpl` signatures in *both* files. If that refactor is a separate RFC, this RFC's internals don't compile standalone, and the §11.5(b) "bundle into one migration" guarantee is unmet. Either declare the dep or own the ctx change here.

## Does it survive?

**Survives-with-changes.** The core idea — thread nonce as a render-time param instead of mutating the tree — is correct and genuinely fixes a real reuse-corruption bug (F-D-101, which I confirmed: `setNonce` mutates the live instance and never restores). The public *signatures* are honestly additive (overloaded `render`, optional second stream arg, new `renderToStreamWithNonce`/`RenderOptions`). It is not a reject: nothing here is unfixable, and cutting the RFC would leave the confirmed stale-nonce bug shipped.

But it cannot ship as `breaking: additive` while it (1) reverses an existing precedence, (2) leaves that reversal explicitly undecided, (3) is ambiguous about whether a public method is removed, and (4) changes output byte ordering it claims is "identical." Those are the five `required_changes` above. Folded back, they either (a) preserve today's render-time-wins semantics — restoring true additivity — or (b) honestly reclassify as `breaking` with a resolved decision, a `breaking-changes.md` entry, and byte-exact tests. Both are acceptable; the current "additive + open question" middle is not.

## Guardrail check (breaking-change owns §11.5)

§11.5 backward-compat: **FAILS as currently marked.** Additivity requires "existing signatures and outputs preserved." Signatures: preserved (verified). Outputs: **not** preserved for the `setNonce`-present and extra-attr-present cases (precedence reversal + ordering shift). The RFC's §11.5 self-check ("the only behavior delta is removal of a bug") is incorrect — the precedence flip is a *second* behavior delta, and it is a feature change, not a bug removal. Required-change #1 must land before this passes §11.5.
