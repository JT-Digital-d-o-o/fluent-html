# Verdict: RFC-B-03 — type-safety lens

> Adversarial review. The job is to kill the RFC through the type-safety lens. Default to reject under uncertainty.

## Attack

The RFC's "Type-safety story" (lines 261-268) makes five concrete promises. Three of them are false against the actual library types, and one worked example does not compile. Verified against `src/core/tailwind-types.ts`, `src/core/tailwind-methods.ts`, and `src/control/context.ts`.

- **Failure mode 1 — the "no raw class strings / extractor-safe" promise is hollow (killer).** Line 265: *"Color positions take `TailwindColor` / `TailwindGradientStop` … so every emitted class is visible to the Tailwind v4 extractor (closes the F-B-063/F-B-111 extractor hole)."* But `TailwindColor` is defined (src/core/tailwind-types.ts:59-62) as:
  ```ts
  export type TailwindColor =
    | "inherit" | "current" | "transparent" | "black" | "white"
    | `${TailwindColorName}-${TailwindShade}`
    | (string & {});      // ← accepts ANY string
  ```
  `TailwindGradientStop = TailwindColor` (:202) and `TailwindGradientDirection` ends in `| (string & {})` (:197-199). The `(string & {})` member exists deliberately to let custom theme colors through — which means every new color slot this RFC adds (`.gradient(from, to, dir)`, `Badge.of`'s `{ bg, text }`, `SemanticThemeCtx` palettes, `StatusColorSet`, `ButtonTokens`) silently accepts garbage. `Span(l).gradient("from-brnad-500", "too-brand", "rihgt")` compiles. `Badge.of(s, { active: { bg: "bg-emerald-500/10", text: "txet-emerald-400" } })` — the EXACT raw-class-string shape from the `mngmt` before-example (lines 180-189) — compiles and is invisible to the extractor. The RFC reuses the very leaky types whose leak it claims to plug. This is the central justification of the whole RFC (F-B-063 is "the type-safe bridge that's missing") and it does not hold.

- **Failure mode 2 — `Badge.of` exhaustiveness is conditional, not guaranteed.** Line 264: *"a missing key or a typo'd key is a compile error."* The signature `of<V extends string>(value: V, map: Record<V, …>)` enforces exhaustiveness ONLY when `V` infers to the literal union of `value`. There is no `const` modifier. If `value` is typed `string` (a bare DB column, a freeform status — common in the cited apps), `V` widens to `string`, `map` becomes `Record<string, …>`, and `{}` / any partial map type-checks with zero errors. The promise holds for the `ProjectStatus` union in the worked example and breaks the moment someone passes a `string`-typed value — with no diagnostic. A type-safety claim that silently degrades to "no checking at all" on a common input is a trap.

- **Failure mode 3 — `defineTypographyScale`'s own worked example doesn't compile.** The signature (line 150) types the element factory as `el?: () => Tag`. The worked example (line 254) and the guideline snippet (line 368) pass `el: H1` and `el: H2`. `H1`/`H2` are variadic tag constructors `(...children: View[]) => Tag` — assignable to `() => Tag` only if calling with zero args is allowed, but the declared parameter type is `() => Tag`, so passing `H1` is structurally fine for *assignment* yet the factory is then invoked as `el()` with no children, discarding the role's text — or, if `el` is meant to receive children, the type is wrong. Either way the type and the example disagree. The type must be `el?: (...children: View[]) => Tag` (or `typeof H1`).

- **Failure mode 4 — `.variant()` / `.size()` pollute every Tag and collide with HTML semantics.** The RFC adds `variant(name: ButtonVariant)` and `size(name: ButtonSize)` to the global `Tag` interface (lines 127-132). These land on `Div`, `Span`, `Input`, `Select`, etc. `Input().size("sm")` compiles but `size` is a real HTML attribute on inputs/selects — a reader cannot tell whether `.size()` sets the attribute or the button token. `variant`/`size` are also the two most likely identifiers for an app to declaration-merge itself, producing silent shadowing. Button-scoped methods bolted onto the universal Tag with no constraint is a type-safety smell (a wrong call — `Div().variant("ghost")` — is meaningless yet compiles).

- **Failure mode 5 — `.gradient()` direction is type-incompatible with the type it cites.** The signature names `dir?: TailwindGradientDirection`, defaults it to `"r"` (lines 137, 220), and an example passes `"br"` (line 221). But `TailwindGradientDirection` (tailwind-types.ts:197-199) is `"to-t" | "to-tr" | "to-r" | "to-br" | …` — `"r"` and `"br"` are NOT members; they only slip through via the `(string & {})` arm (failure mode 1 again). So either the RFC silently introduces a new undocumented short-form direction union, or every gradient example fails to typecheck against the type it names. A spec a reviewer cannot resolve is itself a defect.

- **Failure mode 6 (minor) — `.w()` overload is a no-op masquerading as new safety.** Tag already has `w(value: TailwindWidth)` (tailwind-methods.ts:139) and `TailwindWidth` already lists every fraction (`"1/2"…"11/12"`, tailwind-types.ts:24-25). The RFC's `w(fraction: TailwindWidth)` (line 138-139, "this RFC guarantees fraction keys") re-declares an existing overload and guarantees nothing new — and `TailwindWidth` itself carries `(string & {})`, so `w("9/9")` compiles. It implies a safety win that does not exist.

- **Failure mode 7 (minor) — theme override is checked, but only as deep as the leaky leaves.** Line 268 claims a mistyped theme override fails at the `scope()` call site. True for *structure* (`Record<StatusVariant, StatusColorSet>` forces all five variants and all four fields) — that part is genuinely good. But every leaf is `TailwindColor`, so the values inside are unchecked (see failure mode 1). The structural guarantee is real; the value guarantee is not.

## Does it survive?

**survives-with-changes.** The RFC is not fatally unsound — the component shapes, the context-single-sourcing, the structural exhaustiveness of `SemanticTheme`, and the literal unions `StatusVariant`/`ButtonVariant`/`ButtonSize` (which are genuinely closed and DO make `.variant("primry")` a compile error, as claimed on line 263) are all correct and valuable. What fails is the RFC's *overstated* type-safety story: it claims closed-world guarantees that the reused `(string & {})` types cannot deliver, ships a `Badge.of` whose headline exhaustiveness silently evaporates on `string` input, and includes a `defineTypographyScale` example that contradicts its own signature.

These are fixable without redesign: introduce a strict color type for the new surface (or honestly downgrade the claim), add `const` to `Badge.of`'s type parameter plus a stated literal-union precondition, fix the `el` factory type, and constrain or rename `.variant()`/`.size()`. With those five changes folded back, the RFC delivers what it promises. Without them, it ships an API that advertises type-safety it does not enforce — which is worse than no claim, because apps will trust it and stop reviewing color strings.

## Guardrail check (§11.4 type-safety — this lens owns it)

**Fails as written, passes with required changes.** The frontmatter asserts `§11.4 type-safety: pass — … no bare string for colors/variants`. That is incorrect: `TailwindColor`/`TailwindGradientStop`/`TailwindGradientDirection` are `(string & {})` (bare string with a no-op intersection), which §11.4 ("No bare `string` where a literal union fits") specifically targets. The variant/size/role unions DO pass §11.4. The guardrail line in the RFC must be re-marked `needs-mitigation` until the strict-color change lands, mirroring how §11.7 was already flagged.
