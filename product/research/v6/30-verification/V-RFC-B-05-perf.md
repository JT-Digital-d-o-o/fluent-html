# Verdict: RFC-B-05 — perf lens

> You are an ADVERSARY. Your job is to KILL this RFC through the perf lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's perf story rests on a single sentence (§11.2): *"`Icon` is synchronous tag construction on the existing render path; no async."* True, but it answers the wrong question. The guardrail §11.2 is "the **synchronous render path stays fast**," and this RFC measurably *slows it for the common case* while only self-certifying the absence of async. The danger here is not suspense — it is allocation churn on the hottest primitive in the codebase, justified by recon's own numbers: 170+ icon sites, many of them *per-row* (`mngmt` `TaskStatusIcon` is invoked once per task; rideshare's 14 icons live in layout/list chrome rendered on every navigation).

- **perf failure mode 1 — Icon() is strictly more per-call allocation than the baseline it replaces.** The current `Raw("<svg>…")` constants (rideshare `layout.view.ts:171`, mngmt `dashboard.components.ts:25`) are built **once at module load**: a single `RawString` holding a pre-escaped string. Render of a `RawString` is a memcpy into the output buffer — zero per-call object allocation, zero attribute serialization. `Icon("search")` replaces that with a **per-invocation factory**: it allocates one `SvgTag`, then for each path calls `Path()` (a `new Tag`, src/core/utils.ts:9) and `.setD(d)`. Confirmed against the real construction model: `Tag` lazily allocates its attribute map (`this.attributes = EMPTY_ATTRS` until first write, src/core/tag.ts:315; first `addAttribute`/setter does `Object.create(null)`, :143-145). The RFC says Icon "sets `viewBox`, `fill`, `stroke`, `stroke-width`, `stroke-linecap`, `stroke-linejoin`" on the root — that is one `Object.create(null)` plus six string writes **per Icon call**, plus a fresh `Path` tag (with its own potential attribute map) per path, plus the `child` flattening in the `Tag` constructor (:61). For a 100-row list with one icon per row this is 100× the allocation that `Raw`-constant baseline pays exactly once. This is precisely the "common case pays for the construction every render" regression Track-D exists to prevent, and the RFC offers no allocation count and no benchmark against the baseline.

- **perf failure mode 2 — the same icon is re-serialized on every render.** A registered icon is immutable path data. Yet `Icon("name")` rebuilds the entire `SvgTag` + `Path[]` subtree on every call, so identical icons across 100 rows produce 100 identical-but-distinct object graphs that the renderer must each walk and serialize. The cheap, correct design — build the frozen Path-child subtree once per registered name and share it, mutating only the outer wrapper for caller chaining — is *not specified*. As written, Icon trades the baseline's "serialize once, copy many" for "construct many, serialize many."

- **perf failure mode 3 — bundle/module-init cost of the builtin table is unspecified.** §11.1 says builtins are "a small bundled `Record<string, string[]>`." If that is one eager module-level object literal, every app that imports `Icon` for three names pays the parse + allocation of all ~24 entries at module init and ships the dead path data in its bundle (no tree-shaking of object-literal values). The RFC's "Open questions" defers the icon-set *scope* but never addresses its *bundling shape* — a perf concern, not a curation one.

- **What does NOT fail (concede honestly):** The layers 2 and 3 of the RFC — the `SvgTag`/`SvgShapeTag` stroke setters and the typed gradient/clip/filter tags — are perf-neutral. They are thin typed wrappers over the exact same `addAttribute` writes apps already perform (e.g. `setStrokeLinecap("round")` compiles to one attribute write, identical cost to the `addAttribute("stroke-linecap","round")` it replaces). They add no allocation and no async. The attack is confined to **Layer 1, `Icon` + the registry.**

## Does it survive?

**survives-with-changes.** The RFC does not violate §11.2 in the strict (async) sense, and two of its three layers are perf-clean. But Layer 1 replaces a zero-per-call-allocation baseline with a per-call, per-render factory on the single highest-fanout primitive in the apps, and self-certifies that regression away with one sentence. Under "default to reject under uncertainty," I do not reject outright only because the fix is mechanical and well-scoped: memoize the immutable path subtree, pre-build the default root attribute object, and require a Track-D allocation/render proof. With those, Icon can match or beat the `Raw`-constant baseline (it gains escape-safety and extractor-visibility at parity cost). Without them, Icon is a per-request allocation regression dressed as an ergonomics win, and ships unmeasured.

The required changes (frontmatter) fold back as: (1) a Track-D benchmark gate vs the baseline; (2) memoized/frozen per-icon child subtree; (3) single-shot default root-attribute initialization, not six sequential lazy-map writes; (4) a stated, tree-shakeable bundling strategy for the builtin table; (5) an explicit "no async in the Icon/registry path" clause so the thenable return never introduces a microtask.

## Guardrail check (perf owns §11.2)

§11.2 "SSR-only, synchronous render path stays fast": **conditional pass.** No async is introduced (the literal sub-clause holds). But "stays fast" is **not demonstrated** — the RFC measures nothing and replaces a zero-allocation baseline with a per-call factory. Track-D owns the proof per §11.2's parenthetical; this RFC must carry or cite that proof before it can claim the guardrail. The §11.2 self-check in the RFC frontmatter is currently a non-sequitur (it answers async, not speed) and must be rewritten to reference the benchmark in required-change #1.
