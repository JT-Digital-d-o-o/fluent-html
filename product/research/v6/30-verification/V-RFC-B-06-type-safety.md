# Verdict: RFC-B-06 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's "Type-safety story" (lines 251–258) is the load-bearing justification for the whole feature — its claim is that `TableState` makes "forgetting a filter impossible" and that wrong calls fail to compile. Under inspection, several of those guarantees are not actually expressible with the proposed signatures.

- **type-safety failure mode 1 — `route` is typed to reject half the route registry.** `TableOptions.route`, `SortHeader.route`, and `Pagination.route` are all `(options?: RouteHxOptions) => HTMX`. But the real route system (`src/routes.ts:145`) defines `RouteCallable<Def>` as a *conditional*: routes whose path has a `:param` are `(params, options?) => HTMX`; only param-less routes are `(options?) => HTMX`. So `Table.of({ route: userRoutes.detail })` (path `/:id`) is a **compile error** under the narrow type, and the only way to make it pass is to widen `route` toward `Function`/`any`, at which point required params vanish at runtime. The RFC says "Reuses the typed route system" (line 257) but does not reuse the system's actual callable type — it re-declares a strictly narrower one. A concrete inference/overload-collision bug, not a hypothetical.

- **type-safety failure mode 2 — `toQuery(): QueryParams` is unsound by construction.** `T extends Record<string, unknown>` (lines 53, 60, 80, 92, 118, 127). `QueryParamValue` (verified at `src/routes.ts:119`) is `string | number | boolean | undefined | null`. Nothing forces `T`'s *values* into that set. A perfectly ordinary filter type — `{ since?: Date; tags?: string[]; range?: { from: number } }` — satisfies `Record<string, unknown>`, compiles everywhere, and then `toQuery()` (contract: "Serialize all non-empty fields to a query bag", line 65) hits `buildQueryString`'s `String(value)` (`src/routes.ts:174`) and emits `since=Mon+Jun+22+2026...`, `tags=a%2Cb`, or `range=%5Bobject+Object%5D`. The type system green-lights silent data corruption in exactly the serialization layer the RFC says it owns. The fix is trivial (`T extends Record<string, QueryParamValue>`) but its absence falsifies the headline claim.

- **type-safety failure mode 3 — `sortBy` is checked against the wrong type.** `sortBy: keyof T & string` (line 88) constrains the sort key to the *filter* shape, while `cell: (row: R) => …` reads the *row* shape. These are independent generics. So a column can display one field and sort by a completely unrelated key, and it compiles. The RFC ships this bug in its own canonical example: line 200's "When" column renders `formatTime(e.at)` but declares `sortBy: "userId"`. A reviewer can't tell from types whether that's intentional or a copy-paste slip — precisely the F-B-014 class of "sort column and data drift apart" the RFC claims to structurally fix. "Literal-union sort keys" (line 254) prevents typos against `T`, but not the more dangerous semantic mismatch between sort key and rendered column.

- **type-safety failure mode 4 — the escape hatch reopens the hole.** `toQuery(overrides?: QueryParams)` (line 66) takes a bare untyped bag — the same `Record<string, string>` shape the RFC spends its Problem section (lines 26–36) eliminating. `state.toQuery({ evnet: x })` — typo and all — compiles, and `state.toQuery({ page: "9" })` silently overrides the typed page. The single-source guarantee is only as strong as the unconstrained override surface allows: not at all.

- **type-safety failure mode 5 — representable illegal states + a no-op default.** `sort?` and `dir?` are independent optionals (lines 56–57, 62–63), so `{ sort: "event" }` with no `dir` and `{ dir: "asc" }` with no `sort` are both well-typed but meaningless — the "bag of optionals" the project's TypeScript guideline explicitly forbids. And the `T = Record<string, never>` default (lines 73, 108) makes `keyof T & string = never`, so omitting the type param doesn't error — it silently turns `sortBy`/`field` into an unsettable `never`, disabling the feature's whole type story with no diagnostic.

## Does it survive?

**survives-with-changes.** The core shape — const-generic row type `R`, a `TableState<T>` single source, literal-union sort keys, `defineRoutes`/`defineIds` reuse — is sound in concept and consistent with house idiom. None of the failures are fatal to the design; each is a fixable signature defect. But three of them (modes 1, 2, 4) directly falsify claims the RFC makes in its own "Type-safety story," and one (mode 3) is demonstrated as a live bug in the RFC's flagship example. Under §11.4 ("No bare `string` where a literal union fits; … full types, not `any`") and the project's "no bags of optionals" rule, this cannot ship as written — the `toQuery` unsoundness in particular is a serialization-correctness hole the type system is supposed to close. The six required changes fold back into the RFC; with them, the type-safety story becomes true rather than aspirational.

## Guardrail check (§11.4 type-safety)

Fails as written: `T extends Record<string, unknown>` admits non-serializable values into a `QueryParams`-producing method (unsound); the `route` type does not match the real `RouteCallable` (forces widening toward `any` for parameterized routes); `sortBy` is keyed to the wrong type; and `toQuery(overrides)` reintroduces an untyped string bag. All repairable; none require cutting the feature. Conditional pass *after* the six required changes.
