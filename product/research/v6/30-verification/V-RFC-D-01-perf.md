# Verdict: RFC-D-01 — perf lens

> You are an ADVERSARY. Your job is to KILL this RFC through the perf lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC bundles a genuine win (`Frozen`, a near-free per-render memcpy after first render) with a risky internal rewrite (work-stack de-recursion + `Sink` abstraction) that touches the single hottest code path in the library. The perf danger is concentrated entirely in the rewrite, and the recon's own measurements arm the attack.

- **Perf failure mode 1 — polymorphic `Sink.emit()` defeats inlining on the per-node hot path.** Today `renderImpl` is a monomorphic, return-by-value recursion: `'<'+el+attrs+'>'+renderImpl(child,ctx)+'</'+el+'>'` (`render.ts:240`). V8 inlines this aggressively and there is no virtual dispatch. The RFC introduces `interface Sink { emit(s: string): void }` (`serialize.ts`) shared by the string renderer (`out += s`) and the stream renderer (`stream.push(s)`). The moment one `serialize()` function is called with two different sink implementations, the `emit` call site becomes polymorphic/megamorphic and V8 stops inlining it. The recon clocked the flat-1000 and ForEach-5000 workloads at **~156 ns/node**, dominated by per-node cost × node count (`04-performance.md §2`). Adding an un-inlinable interface call *per emitted fragment* (open tag, each attr-group, each child separator, close tag — several per node) on a path that runs thousands of times per request is exactly the "make the common case pay" regression the perf lens exists to block. Recon item #5 explicitly rates the sink extraction as **"No raw speed"** — the RFC promotes that mechanical dedup onto the hot path and *assumes* it stays neutral.

- **Perf failure mode 2 — work-stack converts zero-alloc control flow into O(nodes) per-request heap churn.** Native recursion uses the call stack: zero heap allocation for control flow. An explicit work-stack must (a) allocate and grow a stack array, and (b) remember to emit each element's closing tag *and restore the script/style raw-context* after its children are done — which means pushing a synthetic "close" node or a deferred-close record **per open element**. If implemented naively that is O(nodes) fresh allocations per request, stacked on top of the already-measured ~104 KB/render GC pressure for flat-1000 (`§2 memory`). Guardrail §11.2 protects the sync path from exactly this. The RFC's "throughput neutral" assertion (§Guardrail check, §11.2) is unbacked.

- **Perf failure mode 3 — cons-string rope shape is not preserved by assumption.** The current nested concat builds a balanced rope that V8 flattens cheaply; recon measured `+=` beating array-join 2.5x and the charCode escape fast path beating regex (`§2 micro-table`) — i.e. the existing shape is finely tuned. A left-to-right flat work-stack emitting into one accumulator changes that shape. Maybe it is still fine; maybe deep trees regress. The RFC does not say, and the deep-tree case (124K ops/s today) is precisely where the rope structure differs most.

- **Perf failure mode 4 — no proof, against an explicit guardrail mandate.** §11.2 says any internals change "must not slow the synchronous hot path (Track D owns the proof)." F-D-094 already flagged that the Frozen throughput gain "was unmeasured." The RFC then *adds* the de-recursion regression risk and still presents **no before/after numbers** — the bench (`bench/render.ts`) has no Frozen case and no recursive-vs-work-stack comparison. An internals RFC whose entire justification is performance, shipping without the measurement its own guardrail demands, cannot be waved through.

## Does it survive?

**survives-with-changes.** It survives because (1) the correctness payload is real and not perf-negative — the ~3.5k-depth stack overflow (`04-performance.md §2`, binary-searched 3468→3500) is a genuine production crash, and fixing it cannot be done *without* removing native recursion, so the de-recursion is load-bearing, not gratuitous; and (2) `Frozen` is, post-first-render, an unambiguous win (one branch + one append vs re-walking a static subtree). Recon ranked de-recursion #1 and rated it "throughput neutral **if the loop is kept tight**" — survivable, conditional on proof and on not introducing the two taxes above.

It does **not** survive as written, because it asserts hot-path neutrality without measuring it and proposes a `Sink` abstraction + work-stack whose obvious implementations regress the path the recon proved is already optimal. The required changes (above) fold the guardrail proof into the merge gate and constrain the implementation so the common case keeps paying nothing: monomorphic string emitter, O(maxDepth)-not-O(nodes) control-flow allocation, and a measured ±5% neutrality gate covering the per-node-dominated and deep-tree cases plus the new Frozen case. With those, the perf risk is bounded and verifiable; without them it is an unmeasured rewrite of the hottest path and should be **reject**ed.

## Guardrail check (perf owns §11.2)

§11.2 (SSR-only, synchronous render path stays fast): **CONDITIONAL PASS — only after the required bench gate is added.** As written the RFC claims the de-recursion is "throughput-neutral" and bench-gated but supplies no numbers and proposes abstractions (shared polymorphic `Sink`, work-stack with per-node close bookkeeping) that the recon's measurements predict will regress the hot path. The async/stream concern is satisfied (render stays synchronous; no async touches the sync path; `Frozen` adds only a synchronous branch). The gate must prove neutrality on Flat-1000, ForEach-5000, deep-tree, and realistic-page within recon's ±5% noise band, and quantify the Frozen speedup, before merge.
