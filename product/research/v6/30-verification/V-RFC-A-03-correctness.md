# Verdict: RFC-A-03 — correctness lens

> You are an ADVERSARY. Your job is to KILL this RFC through the correctness lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's enabling mechanism (the `_sk` tuple form) is mechanically sound and matches the cited code in `render.ts:208-216` and `stream.ts:146-154` exactly. The bugs it claims are **real and reproduced**: `MetaTag.prototype._sk = ['name','charset','httpEquiv','property','content']` (`document.ts:75`) does emit the camelCase `httpEquiv` attribute, and `OptionTag.setValue(value: string)` (`forms.ts:407`) is required while `Input`/`Button` are optional. But the RFC overclaims its own completeness and contradicts itself, and three of those overclaims are correctness defects.

- **Correctness failure 1 — the http-equiv fix is incomplete; "fix once / zero blast radius" is false.** The RFC states (Problem §, Migration §, Dedup note): "the `_sk` loop is copy-pasted in `render.ts:208` and `stream.ts:146`. This RFC must patch **both**," and treats the tuple as the single enabling change that "unblocks the whole cluster cleanly." There is a **third** HTML-emitting path the RFC never mentions: the fold subsystem. `src/fold/algebras/render.ts` `buildAttributes()` (lines 23-31) walks `Object.entries(attrs)` and emits `${key}="..."` by **JS property name**, never reading `_sk`. The attrs come from `extractAttrs()` (`src/fold/fold.ts:9`, duplicated in `src/fold/para.ts:9`), which copies own-enumerable props via `Object.keys(tag)` — so `Meta().setHttpEquiv("…")` arrives under key `httpEquiv` and renders `httpEquiv="…"`, the exact broken output the RFC claims to eliminate. `foldView(renderAlgebra, view)` / `paraView(...)` are public API. The tuple `_sk` scheme **cannot** fix this path because the path doesn't consult `_sk`. So "blast radius is zero" and "fixing it once unblocks the whole cluster cleanly" are wrong for the general correctness claim; the fix is `render()`/`stream()`-only.

- **Correctness failure 2 — crossorigin/referrerpolicy split-brain reintroduces F-A-071's own defect.** `ImgTag` (`media.ts:20,62`) carries `crossorigin?: 'anonymous'|'use-credentials'` + `setCrossorigin`; `AnchorTag` (`links.ts:18,45`) carries `setReferrerpolicy`. The RFC renames + widens crossorigin only on Link/Script (§3, §4) and renames referrerpolicy only on Iframe (§4). After this RFC, `Link().setCrossOrigin("")` exists but `Img().setCrossOrigin` does not — the guideline edit (CLAUDE.md block) teaches `setCrossOrigin` unqualified, and the eslint `prefer-set-method` map (`prefer-set-method.ts:40` `crossorigin → setCrossorigin`), which the RFC says to update to the camelCase target, will then autofix `<img crossorigin>` to a method that doesn't exist → compile error. The RFC's stated goal (F-A-071: eliminate the camelCase/lowercase split that pushes devs to `addAttribute`) is partially self-defeated.

- **Correctness failure 3 — the F-A-071 worked example is internally contradictory.** The `gym-crm/.../qrUI.ts:361` example presents `Input().setReadOnly()` as the correct replacement for `addAttribute("readonly", "true")`, with the inline jab "also wrong: `readonly="true"` is truthy noise." But `setReadonly(true)` → `this.readonly = true` (`forms.ts:107-108`), and the `_sk` loop emits `String(true)` → `readonly="true"` (`render.ts:213`). The "fixed" call produces byte-identical broken output to the call it mocks. The boolean-truthy bug is out of scope (a separate finding/RFC), but the RFC actively asserts its rename fixes it.

- **What does NOT kill it.** The tuple renderer is correct — `typeof entry === 'string' ? entry : entry[0]/entry[1]` is exhaustive over `SchemaKey = string | readonly [string, string]`, and the `value !== undefined && value !== null` guard (`render.ts:212`) is preserved. `OptionTag.setValue(value?)` is sound: the `_sk` loop already skips `undefined`, so the looser type matches runtime. The SVG opacity/filter move is output-identical on the main path. The `''` `CrossOrigin` member escapes correctly through the same `escapeAttr`. The mechanism is right; the *coverage and the prose claims* are wrong.

## Does it survive?

**survives-with-changes.** None of the three defects invalidate the core design — the tuple `_sk` form is the right primitive and the bugs it directly targets are real. But shipping as written would (a) leave `httpEquiv` broken on the fold render path while the RFC documents it as globally fixed, (b) reintroduce the camelCase split it set out to kill on `<img>`/`<a>` and break the eslint autofix there, and (c) ship a worked example that misrepresents its own output. These are correctness defects in the deliverable, not polish — they fold back as the required changes above. The most important is #1: the RFC must either extend the fix to `extractAttrs`/fold `renderAlgebra` or explicitly down-scope its correctness claim to `render()`/`stream()` and reaffirm the fold path as non-production. With those changes the RFC is correct.
