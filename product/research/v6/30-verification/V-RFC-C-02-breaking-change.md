# Verdict: RFC-C-02 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's central deception is its frontmatter: `breaking: additive`, with a §11.5 self-check of "pass," and the word "additive" repeated through the Migration section. But the same RFC sets `TW_TARGET_DEFAULT = "v4"` and ships it as the v6 default. Those two facts are mutually exclusive, and the seam between them is exactly where a real adopter gets a silently broken page.

- **Failure mode 1 — the default-flip is a behavioral break on unchanged source, smuggled past the bundle.** Worked Example B states it plainly: after this RFC, `p.gradientTo = (dir) => this.addClass(\`${CLASS_VOCAB[TW_TARGET].gradientLinearPrefix}-${dir}\`)`. With `TW_TARGET` defaulting to `"v4"`, the *identical* app expression `Div().gradientTo("to-r")` — verified present in `ttl/` and `rideshare/` — stops emitting `bg-gradient-to-r` (confirmed current behavior at `src/core/tailwind-methods.ts:576`) and starts emitting `bg-linear-to-r`. Same for `.shadow()` and outline. The RFC concedes this ("the resolved class string changes only because v6 ships on v4") then disowns it: "that visual change is RFC-C-01's breaking note, **not this RFC's**. This RFC is the mechanism, additive." That is the exact move guardrails §13 ("a breaking API sneaks into a minor") and the Wave-4 "rejects unmarked breakage" rule exist to stop. The *mechanism* (the CLASS_VOCAB table, the flag, the helper) is genuinely additive — but this RFC does not ship the mechanism set to a no-op; it ships it with `TW_TARGET_DEFAULT = "v4"`, i.e. it ships the flip. You cannot both *define* the default and *disclaim* its effect. And the break is non-codemod-able in app source: the app code is correct and unchanged, so there is nothing to rewrite — it can only be *disclosed*, and the `additive` label actively hides it from the disclosure bundle.

- **Failure mode 2 — a shipped public signature with an undeclared fate.** The current public surface is `fluentHtmlExtractor(content: string, options?: ExtractorOptions): string[]` (confirmed `fluent-html-tailwind-extractor/src/index.ts:698`). It is *the* documented v3 integration point, wired into `ttl/tailwind.config.js` and `rideshare/tailwind.config.js` via `content.extract`. The RFC introduces `emitSafelistCss(sources, outFile, options): Promise<void>` — different name, arity, sync->async — as the v4 primary, and adds `target?` to the *shared* `ExtractorOptions` whose `target` defaults to `"v4"`. It never states whether `fluentHtmlExtractor` is retained, deprecated, or removed, nor whether *its* output flips to v4 vocabulary when the shared option defaults to v4. If it does, that is a behavioral break to a shipped signature, undeclared. A breaking-change RFC silent on the disposition of the symbol it is replacing has not done the accounting its frontmatter claims.

- **Failure mode 3 — the new tooling->lib value dependency is an unmarked compatibility constraint.** Today the extractor's `peerDependencies` is `{ tailwindcss: ">=3.0.0" }` (confirmed `package.json:40`) — no `fluent-html` edge. The RFC's methods/extractor/eslint and the cross-package test import `CLASS_VOCAB`/`TW_TARGET` as *values*, not just types, from `fluent-html`. That creates a hard version coupling: an extractor published against v6 lib values will not resolve against a v5 lib. The RFC widens the `tailwindcss` peerDep (good) but adds no `fluent-html` peer constraint, so the three packages can be installed at incompatible versions and fail at import/build time with no install-time guard. Open Question #1 is exactly this; deferring it means shipping the coupling without deciding its compat story.

- **Failure mode 4 — `TW_TARGET` as a mutable module global breaks the dual-target promise it sells.** `export const TW_TARGET: TailwindTarget; // resolved value (env/config override of default)`, read as `CLASS_VOCAB[TW_TARGET]` at call time inside prototype methods, makes the target process-global. The Alternatives section rejects separate majors specifically to avoid "strand[ing] in-monorepo consumers (`ttl`, `rideshare`) on an island during migration." But those two apps (both confirmed present, both still on `tailwind.config.js` = v3) share one hoisted `fluent-html` install. A single env-resolved global cannot serve ttl-on-v3 and rideshare-on-v4 in the same process or shared install. The flag's headline benefit — a gradual per-app migration window — is unreachable under the proposed mechanism. The compat claim contradicts the implementation sketch.

## Does it survive?

**survives-with-changes.** The core idea — single-source the class vocabulary and gate v3/v4 on a typed literal target, with a cross-package consistency test — is sound and is the right shape for the §11.7 class-string contract. But on the one axis this lens owns, the RFC is **mis-labeled and under-specified**: it ships a v4-default behavioral break under an `additive` flag, leaves a shipped public signature's fate unstated, defers a packaging-coupling decision with compat consequences, and proposes a global-resolution mechanism that defeats its own migration story.

None of these is fatal to the design. Each is fixable by (a) honestly re-labeling `breaking` and routing the default-flip into the Wave-4 bundle, or (b) defaulting the target to `"v3"` here and letting RFC-C-01 own the flip — plus the four narrower specifications above. I stop short of `reject` only because the break is real-but-disclosable and the mechanism itself is additive; the mislabeling is correctable without redesign. Confidence 0.75: the §11.5 "pass" self-assessment is demonstrably wrong (strong), but a reasonable reviewer could argue the v4 flip is "morally RFC-C-01's" and this RFC is a pure mechanism *if* `TW_TARGET_DEFAULT` were moved — which is precisely required-change #1.

## Guardrail check (breaking-change owns §11.5)

§11.5 self-check **fails as written.** The RFC asserts "§11.5 backward-compat: **pass** — additive; every new option defaults to `"v4"`." Defaulting a new option to v4 is additive only if v4 == prior behavior; it does not — prior behavior is v3 for every shipped app (ttl/rideshare confirmed on v3 config and v3 class vocabulary). Defaulting the resolved `TW_TARGET` to v4 changes the output of unchanged code, the definition of a backward-incompatible change. It is permitted in a major (v6 is a major) but §11.5 requires it be (a) codemod-able where possible — here it is not codemod-able in app source, only disclosable — (b) bundled into the one `breaking-changes.md` migration, and (c) marked `breaking` in frontmatter. As drafted it satisfies none of (a)/(b)/(c) for the default-flip. Fix: mark `breaking`, route into the bundle, and either default to v3 here or move the flip to RFC-C-01.
