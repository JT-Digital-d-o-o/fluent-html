# Verdict: RFC-C-05 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's headline guarantee is **`breaking: false` / "additive / emitted class strings are byte-identical to today / no `breaking-changes.md` entry"** (§Migration). The drift test is supposed to prove this on first commit. I verified the three cited source sites against the real code; the file:line citations are accurate. But the RFC's *data model* is a lossy projection of two of the three lists it claims to single-source, and "byte-identical" silently fails on the eslint surface.

- **breaking-change failure mode 1 — the eslint fix model is lossy, so regeneration is not byte-identical.** The RFC models a utility as `emit` shapes plus `fixPrefix?: string | string[]` that "defaults to the emit prefix." The real `FIXABLE_PATTERNS` (`no-known-modifiers-in-setclass.ts`) is **283 patterns across 92 methods**, consumed by `matchClass()` as a **flat, ordered, first-match** loop. `ringColor` alone owns **26 patterns** (lines 293–317, 376). They are NOT derivable from the emit prefix `ring`:
  - they enumerate specific color families (`ring-slate-`, `ring-red-`, … 22 of them) plus exact-match singletons (`ring-white`/`ring-black`/`ring-transparent` carry `exactMatch:true, fixedValue:"white"`),
  - they are **ordered after** the `ring` *width* patterns (`ring-2` → `methodName:"ring"`, lines 285–290) and **before** the catch-all `ring-` (line 376),
  - `matchClass` returns the **first** `startsWith`/exact hit, so the ordering is the disambiguation logic: `ring-2` must resolve to `.ring("2")`, `ring-slate-500` to `.ringColor("slate-500")`.
  Regenerating `fixPrefix` as the emit prefix collapses all 26 into one `ring-` row, **deletes the width/color disambiguation and the `fixedValue` exacts**, and changes the auto-fix output adopters get. That is a behavioral breaking change in a published ESLint rule, hidden under `breaking:false`. The RFC's own drift test would not catch it — it only checks forward `emitClasses` vs `liveEmit` (lib/extractor), never asserts the generated `FIXABLE_PATTERNS` equals today's array in order.

- **breaking-change failure mode 2 — the three lists are not 1:1 today, and the single `skip` flag must reproduce three different sets.** Measured coverage: lib **120** methods, extractor **117** (excludes the `on`/`at`/`neg` variant-modifiers, which emit nothing), eslint **92** (excludes 28: every `backdrop*`, `brightness`/`contrast`/`saturate`/`grayscale`/`invert`/`sepia`/`hueRotate`, `skewX/Y`, `gridAuto*`, `place*`, `order`, `overscroll`, `willChange`). The RFC presents one `classVocab` table with a single `skip?: Array<"extractor"|"eslint">`. Getting any one of the 28+3 exclusions wrong **adds or removes coverage** — e.g. forgetting `skip:["eslint"]` on `brightness` makes the fixer start rewriting `brightness-50` toward a method it previously ignored (new fixes = behavior change), or skipping a method that *was* extracted drops CSS generation for it (silent missing-class regression). The "byte-identical" claim is asserted, never enumerated; with 31 deliberate divergences it is a non-trivial proof obligation, not a freebie.

- **breaking-change failure mode 3 — `kind:"custom"` re-imports the divergence it claims to kill, at unquantified scale.** Several extractor closures don't fit the 6 emit shapes: `gap` (3-branch unit/dual/single closure), `borderColor` (directional + color overload), `display`/`position` (emit the bare arg), `w/h/...` (`arbitraryOrStandard`). Each falls to `kind:"custom"`, whose definition is "hand-written in all 3" (the EmitShape comment). For every custom row, the table is a registry, not a source of truth — the actual logic still triples. The RFC never says how many of ~120 rows are custom; if it's 15–25, the central claim ("three lists → one table") is materially overstated for exactly the methods most likely to be touched by a v4 migration (`gap`, sizing, borders).

- **breaking-change failure mode 4 — the `TARGET="v4"` default is itself the break.** Open Q2 floats defaulting codegen to `v4`. If it does, the *first* regenerated build emits `bg-linear-*`, `shadow-xs`, etc. — by construction **not** byte-identical to today. The "additive, proven byte-identical day one" story holds only under `TARGET="v3"`. The RFC wants it both ways: be the additive prerequisite AND default to v4. It must pick one; a v4 default belongs in C-01..C-04's bundled breaking migration, not in a `breaking:false` refactor.

## Does it survive?

**survives-with-changes.** The breaking is real but it is *latent in the model*, not in the concept. The forward-emit half (lib + extractor prefixes) genuinely can be single-sourced additively, and a properly-scoped drift test pinned to `TARGET="v3"` *can* prove byte-identical lib/extractor output. What does NOT survive as written is the claim that the eslint fixer is covered by the same model and is byte-identical — `fixPrefix` defaulting to the emit prefix demonstrably changes fixer output. Under the lens's "default to reject under uncertainty" rule this would be a reject, but the defect is precisely localizable and the fixes fold back cleanly into the table schema (encode the eslint match-list fields + ordering, snapshot-test the generated array, enumerate skips, count customs, pin the day-one target to v3). With those five required changes the RFC is honest about its surface and its `breaking:false` label becomes defensible.

The single most important non-negotiable: **add an ordered deep-equal snapshot of the generated `FIXABLE_PATTERNS` against today's 283-row array before the hand-written list is deleted, and extend `UtilityDef` to carry `exactMatch`/`fixedValue`/`direction` and an explicit ordering**, otherwise the RFC ships a silent ESLint auto-fix regression under an `additive` banner.

## Guardrail check (§11.5 backward-compat — this lens owns it)

- §11.5 requires breaking changes be (a) codemod-able, (b) bundled into one `breaking-changes.md` migration, (c) justified. The RFC claims exemption ("additive"). For the lib/extractor emit surface under `TARGET="v3"`, the additive claim is **plausible and provable** (drift test). For the **eslint-fix surface and the `TARGET="v4"` default**, the additive claim is **false as written** — fixer output changes — so §11.5 is currently **violated by mislabeling**: a behavioral change is present with no breaking-changes.md entry. The required changes restore compliance by either (i) proving byte-identical eslint output via the schema additions + snapshot test (keeping it additive), or (ii) routing any non-identical output into the C-01..C-04 bundled migration with an explicit entry. Until one of those lands, §11.5 = **fail**.
