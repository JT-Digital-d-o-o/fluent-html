# Verdict: RFC-B-01 — type-safety lens

> You are an ADVERSARY. Your job is to KILL this RFC through the type-safety lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's "Type-safety story" (lines 265-272) is its load-bearing claim — five new symbols are justified on the premise that "the typed path is the short path." I checked every claim against the actual codebase. Three are **false as written**, two more leak through type erasure, and one references a method that does not exist.

- **type-safety failure mode 1 — the headline claim is false (`InputThemeTokens` are not typo-proof).** Line 269: *"`InputThemeTokens` fields are the existing literal-union scale types (`TailwindColor`, `TailwindSpacing`, …) — no bare `string`; a typo like `borderColor: "site-bordr"` fails to compile."* This is the single strongest selling point of `createInputTheme` over the per-app `inputStyle` apply-fn it replaces. It is wrong. In `src/core/tailwind-types.ts`, `TailwindColor` is `"inherit" | "current" | … | \`${TailwindColorName}-${TailwindShade}\` | (string & {})` (lines 59-62) and `TailwindSpacing` is `"0" | "px" | … | (string & {})` (lines 16-19). `(string & {})` is the **bare-string escape hatch** the file's own comment (lines 8-9) documents as "accepts any string while preserving autocomplete." So `createInputTheme({ borderColor: "site-bordr", paddingX: "fortytwo" })` type-checks cleanly. The RFC's §11.4 guardrail self-attestation — *"PASS … no bare `string`, no `any` in the public surface"* (line 415) — is contradicted by the very types it cites. Under ALGORITHM §11.4 a false PASS is exactly what the adversarial lens exists to catch.

- **type-safety failure mode 2 — `resetOnSuccess: … | void` makes the option *required*, breaking the RFC's own examples.** The existing `behavior` overload (`src/core/behavior-methods.ts:28-31`) is `...args: BehaviorMap[K] extends void ? [] : [options: BehaviorMap[K]]`. The RFC declares `resetOnSuccess: { selfOnly?: boolean } | void` (line 125). A union `{…} | void` does **not** satisfy `extends void`, so the conditional picks the `[options: BehaviorMap[K]]` branch → the options arg is required (you must pass `undefined` explicitly). Every bare call in the RFC — worked example E `.behavior("resetOnSuccess")` (line 262), guideline index (line 322), htmx ref (line 387) — **fails to compile**. The `| void` idiom only erases the arg for entries that are *exactly* `void` (like `disable`, `back`); it does not work for "optional options bag." A concrete, reproducible compile break in the RFC's primary usage.

- **type-safety failure mode 3 — `replaceWith` does not exist.** The fluent-html.md edit the RFC ships (line 335) demonstrates the input override as `input: base => base.replaceWith(Textarea().apply(/*…*/))`. Grep across `src/` returns zero definitions of `replaceWith` on `Tag`/`InputTag`. The canonical "render a textarea instead" example — the whole point of the `input?` escape hatch — does not type-check. The RFC ships a guideline teaching a nonexistent method.

- **type-safety failure mode 4 — the `input?` override silently drops form binding with no type error.** `input?: (base: InputTag) => Tag` (line 92) returns an arbitrary `Tag`. The RFC promises the override keeps "name/value/theme" (fluent-html.md line 339), but nothing in the type forces the returned Tag to carry them. An app that returns a fresh `Textarea()` (the documented case) produces a control with no `name` — it won't submit — and the compiler is silent. A type-checked program yields a broken form.

- **type-safety failure mode 5 — `FormErrors`/`FormErrorsCtx` is type-erased; the schema link is a runtime contract, not a checked one.** `FormErrorsCtx: Context<ErrorBag>` where `ErrorBag = Record<string, string>` (line 118) — the published context is **untyped**. The `FormErrors<T>` generic constrains only the *argument* at the call site; once stored in the context Symbol the `T` is gone. `f.field({name: K extends keyof T})` reads its error out of the untyped bag. There is no compile-time guarantee the bag's `T` and the field's `T` agree — the RFC's claim "errors keyed to the same schema, so a stray `errors.deparrtureCity` is a type error" (line 268) holds only at the literal `FormErrors(errors, …)` construction, not across the field reads it governs. Compounded by inference loss: in the dominant render path `errors` is `undefined`, `T` defaults to `{}`, and the linkage is vacuous.

These are not stylistic nits — three (FM1, FM2, FM3) are outright compile-falsity in the RFC's stated examples and guardrail attestation; the lens's mandate is to refuse a false type-safety story even when the runtime behavior would be fine.

## Does it survive?

**survives-with-changes.** The *shape* of the design is sound and the `formFor<T>().field({ name })` name-check (line 267) is genuinely correct — it inherits the verified `keyof T & string` guarantee from the existing `formFor` (form.ts:28-40), so the core ergonomic win stands. But the RFC over-claims: its Type-safety story asserts guarantees the underlying types do not provide (FM1), its flagship behavior example does not compile (FM2), and it teaches a nonexistent method (FM3). None is fatal to the concept; each is a precise, mechanical fix. Per ALGORITHM §8 the lens does not `reject` when a credible amended form exists and no guardrail is irreparably violated — §11.4 is *repairable* by correcting the claims and the overload. The six `required_changes` (above) are the exact edits that fold back into the RFC; with them applied the type-safety story becomes true rather than aspirational.

Confidence 0.82: high that FM1/FM2/FM3 are real (verified against source); slightly reserved on whether maintainers prefer to *weaken the claim* vs *strengthen the types* for FM1 — both are valid resolutions, which is why this is changes-not-reject.

## Guardrail check (type-safety, §11.4)

**FAIL as written, PASS after required changes.** §11.4 forbids bare `string` where a literal union fits and forbids `any` in new public surface. The RFC's `InputThemeTokens` inherit `(string & {})` from `TailwindColor`/`TailwindSpacing` — functionally bare `string` for typo-detection — while the RFC attests "no bare `string`" (line 415). That attestation must be corrected (required change 1). The `behavior` overload + `replaceWith` issues are type *correctness* breaks the lens owns. No `any` leaks into the public signatures themselves (the `as any` prototype write in behavior-methods.ts:91 is pre-existing internal, out of scope). With changes 1-6 applied, §11.4 is satisfied honestly.
