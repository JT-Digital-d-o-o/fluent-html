# Verdict: RFC-A-08 — dx lens

> You are an ADVERSARY. Your job is to KILL this RFC through the dx lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

This RFC is well-grounded — every evidence claim I spot-checked is accurate: `addAttribute("hx-on:htmx:after:swap", …)` at rideshare/src/settings/settings.view.ts:260 and :337; exactly **127** `addAttribute("hx-on:click", …)` call-sites (grep-confirmed); the incomplete `escapeJs` at behavior-methods.ts:85-87 missing `\n`/`\r`/`<`; the private `renderers` map (behavior-methods.ts:46) with no public extension point; the 9 built-in behaviors matching BehaviorMap exactly. The `(string & {})` literal-union pattern it copies is the genuine library idiom (htmx.ts:150,168). So the attack is not "is the problem real" — it is. The attack is on the *details that decide adoption*.

- **dx failure mode 1 — autocomplete that lies (the killer).** The runtime renders `this.attributes["hx-on:" + event] = js`. With `HxOnEvent` containing `"htmx:after-swap"`, autocompleting that value produces the attribute `hx-on:htmx:after-swap`. But every shipped app emits `hx-on:htmx:after:swap` (colon — verified at settings.view.ts:260, :337). The RFC's own Open Question admits it does not know which htmx-4 canonical form is right, then *ships the literal union and two behavior renderers built on the guess anyway*, hand-waving the risk as "non-breaking, only autocomplete-affecting." That is wrong twice. (a) For `.hxOn`, autocomplete is the entire value proposition over `addAttribute`; if it suggests the wrong separator, the typed escape hatch is strictly worse than the untyped one it replaces — it lends a false air of correctness to a broken string. (b) For `formResetOnSwap`/`dismissOnEscape`, the event string is not autocomplete — it is *emitted into shipped HTML*. A wrong separator means `formResetOnSwap` binds `hx-on:htmx:after-swap`, htmx-4 never fires it, and the form silently fails to reset. That is a functional regression masquerading as additive convenience. An escape hatch and two behaviors whose correctness hinges on an unresolved Open Question must not ship until that question is closed.

- **dx failure mode 2 — the one footgun the type system does not catch.** `.hxOn` mirrors `.behavior()`'s concat-on-same-event semantics (RFC line 83, matching behavior-methods.ts:97-99). That means `.behavior("toggle", { target })` (emits `hx-on:click`) followed by `.hxOn("click", "foo()")` chains *both* into one `hx-on:click="…toggle…;foo()"`. This is arguably correct, but it is invisible: an author reaching for `.hxOn("click")` on an element that already carries a click behavior gets surprising compound JS with no warning. The JSDoc documents concat *within* `.hxOn` but not the cross-`.behavior()` interaction — the exact case the ladder ("no built-in fits → drop to `.hxOn`") makes likely. Documentation gap, not an API flaw, but it is the real sharp edge.

- **dx failure mode 3 — naming and surface area, where it holds up.** I tried to kill `.hxOn` as redundant surface. It survives: 127 call-sites across 12+ apps is overwhelming reach; the built-in-only Alternative A is correctly rejected as unable to cover the one-off tail (`switchTab(this,'rbx')`, conditional key guards); and `.hxOn` is honestly typed as a "raw JS escape hatch" rather than pretending to be type-safe — the right altitude for a documented last resort. Naming: `.hxOn` is consistent with the `hx`-prefix family (`setHtmx`, `hxResponse`) and reads as "the hx-on attribute," so it is discoverable. I cannot reject on surface-area grounds.

## Does it survive?

**survives-with-changes.** The problem is real, the evidence accurate, the API shape and naming right, and the guardrail story clean. But the RFC ships *running code* (two behavior renderers + a literal union) on top of an unresolved separator question it mischaracterizes as cosmetic. That makes it `survives-with-changes`, not `survives`: the separator must be resolved pre-merge (change 1) and the cross-`.behavior()` concat footgun documented (change 2). The two guideline-hygiene items (stale CLAUDE.md:25, per-row-Id migration cost) round it out. None of these is a guardrail killer, so the RFC is not rejected — but all four fold back before it ships.

## Guidelines impact audit (this lens owns it — guardrail §11.8)

Mostly strong, one gap:

- **Coverage of `api_surface`:** `.hxOn` — taught in both CLAUDE.md and htmx.md (✓). `formResetOnSwap`/`dismissOnEscape` — added to the built-in list and shown with examples in both files (✓). `HxOnEvent` — covered as an autocomplete note rather than a named export, which is correct (it is a parameter type, not user-facing surface) (✓). `escapeJs` — internal, not exported, correctly left untaught (✓). All four symbols accounted for; the frontmatter §11.8 claim is honest.
- **House style:** the three-rung ladder (`.behavior()` → `.hxOn()` → never `addAttribute`) is exactly the succinct ✓/✗ code-first LLM-reader style the algorithm demands. The `✗ Button(label).hxOn("click", \`track('${userInput}')\`)` XSS counter-example is the right teaching — it shows the failure, not merely states the rule.
- **The gap (change 3):** the edit patches the §HTMX block at CLAUDE.md:201-208 but ignores the *index summary* rule at CLAUDE.md:25 ("`.behavior()` for pure-client interactions … never inline `<script>` / `onclick`"). After this RFC that one-liner is stale — it implies `.behavior()` is the sole path when the RFC's whole thesis is that a sanctioned `.hxOn` rung now exists. An LLM reader hitting line 25 first never learns about `.hxOn`. The index must stay internally consistent.
- **Append point:** "after `## hxResponse` (end of file)" — confirmed `## hxResponse` (htmx.md:211) is the final section, so the append is correctly placed.

A great API with a guideline edit that leaves the index self-contradictory is an adoption failure — which is precisely why this lands `survives-with-changes`, not `survives`.
