# Verdict: RFC-C-06 — correctness lens

> You are an ADVERSARY. Your job is to KILL this RFC through the correctness lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC's central correctness claim is that this is "pure type-table widening (zero runtime change)" and that "the extractor already handles every `.on`/`.at` prefix generically — no extractor change." Both halves of that claim are false for the two new *methods* it introduces, and the type-safety story oversells the container surface. The type unions are largely fine; the methods and the parity claims are where it breaks.

- **correctness failure mode 1 — `onPointerHover` is extractor-invisible (dead CSS).** The extractor's variant scanner is a single regex: `/\.(on|at)\s*\(\s*["']([^"']+)["']\s*,/g` (`fluent-html-tailwind-extractor/src/index.ts:640`). It matches **only** method names `on` and `at`. `onPointerHover(t => …)` is neither, so its callback body is never recursed into, no `METHOD_PATTERNS` are run against it, and the classes inside (`shadow-lg` in the RFC's own `Card().onPointerHover(t => t.shadow("lg"))`) are never added to the candidate set. Under TW4's no-content-extract model that means **no CSS is generated** and the shadow silently never renders. The RFC teaches `onPointerHover` as the recommended "pointer-only intent" pattern in BOTH guideline edits (lines 248, 294) — so the recommended path ships broken. This is precisely the extractor-blindness that Track C exists to eliminate, reintroduced by an "additive, low-risk" helper. §11.7 ("extractor already handles all `.on`/`.at` prefixes generically — no change") is contradicted by the cited code.

- **correctness failure mode 2 — the helper's own emitted string is an unresolved Open Question.** `onPointerHover` emits `withVariant(this, "[@media(hover:hover)]:hover", fn)` (line 127). Open Question 1 admits the RFC does not know whether the v3 extractor/Tailwind accepts `[@media(hover:hover)]:` and punts the decision "for a human." A method whose runtime output may not be parseable on a target it claims to support (Migration §217 says these are "valid under both Tailwind majors") is not a verified design — it is a hypothesis. Shipping a *recommended* API with an open correctness question violates the §8 default-reject posture.

- **correctness failure mode 3 — unproven runtime/extractor prefix-join parity.** Two independent code paths build the variant prefix by string-joining with `:`: the runtime (`tag.ts:103-107`) and the extractor (`index.ts:645` and `:663`). The RFC adds arbitrary members whose inner text contains `:`, `[`, `]`, `(`, `)` (`supports-[display:grid]`, `@[480px]`, `[&>svg]`, `[@media(hover:hover)]`). For the output to be correct, both joiners must produce a byte-identical string AND Tailwind v4 must parse the bracket-balanced result. The RFC asserts parity ("extractor already handles … generically") but cites zero test for the arbitrary/nested cases. The runtime path I verified is generic; the *risk* is divergence the RFC never tests for — a single mismatch is silent missing CSS, the worst correctness outcome (no error, no warning, just an unstyled element in production).

- **correctness failure mode 4 — the type-safety story is overstated for containers, and an example is wrong.** (a) `TailwindContainerBreakpoint` includes `@${string}/${string}`, which makes `.at("@anything/anything", …)` typecheck — so the §205 claim "misspellings (`.at('@smm', …)`) stay compile errors" is only true for the non-arbitrary members; `.at('@smm/x', …)` compiles. The §11.4 self-check ("pass — no bare string … misspellings stay compile errors") is therefore inaccurate as written. (b) Worked example 2 (lines 152-164) places `.containerQuery()` / `@container` on `Div("Title")`, a **sibling** of the `@sm`/`@max-lg`-styled `Div("Body")`. Container queries resolve against the nearest **ancestor** `@container`, not a sibling — as the topic-ref example at lines 283-289 correctly shows (`Div(Card().at("@md", …)).containerQuery()`). The example as printed produces a query that never matches: a broken before→after demonstration of the headline feature.

## Does it survive?

**Survives with changes.** The load-bearing premise — that the three *type-union* widenings (`not-*`, media states, `@`-container breakpoints, arbitrary members) are inert, additive, and already correctly emitted by `withVariant` — is **verified true**: `tag.ts:103-107` composes any prefix string generically, `tailwind-methods.ts:326-332` passes the string straight through, and the existing `TailwindState`/`TailwindBreakpoint` at `tailwind-types.ts:179-191` match the RFC's quotes exactly. The union half of this RFC is correct and valuable. It does not reach `reject`.

But it does not reach `survives` either, because the two new *methods* it bundles in are not correct as specified: `onPointerHover` emits CSS the extractor cannot see (failure 1) using a string the RFC itself flags as unverified (failure 2), and the parity/type claims are overstated with at least one outright-broken example (failures 3-4). These are mechanical, in-scope fixes — they fold back into the RFC without redesign — so the correct verdict is `survives-with-changes` with the six required changes above. The single change that gates everything is #1: until the extractor learns `onPointerHover`/`containerQuery`, those two methods are non-functional and must not ship as recommended surface.

## Guardrail check (correctness owns the runtime-behavior invariant)

- **Runtime emission (verified):** `.on`/`.at` with any new union member emits a correct class string via the unchanged `withVariant`/`addClass` path. PASS for the union widenings.
- **§11.7 class-string contract (FAIL as written):** the RFC claims no extractor change, but `onPointerHover` and the `@container` marker from `containerQuery` are not in `METHOD_PATTERNS` and `onPointerHover` is not matched by the variant regex (`index.ts:640`). The three packages are NOT in sync for the new methods until required-change #1 lands. This is the guardrail this lens escalates.
- **Type-safety §11.4 (overstated):** PASS for `not-*`/media/`supports-[…]` (template-literal distribution is sound), but the container-breakpoint members admit nonsense (`@x/y`), so the blanket "misspellings stay compile errors" claim must be scoped (required-change #4).
