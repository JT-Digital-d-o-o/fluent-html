# Verdict: RFC-A-03 — breaking-change lens

> You are an ADVERSARY. Your job is to KILL this RFC through the breaking-change lens.
> Default to `reject` under uncertainty — a good API cut is cheaper than a bad API shipped.

## Attack

The RFC is mostly honest about its breakage ledger — renames keep `@deprecated` aliases, `crossorigin` is a union widen, `OptionTag.setValue` is a param loosen, all genuinely additive. But it is built on one load-bearing false premise about the codebase, and that premise hides two real, un-codemod-able behavior changes.

- **Breaking failure mode 1 — the "two render paths" premise is false; the http-equiv fix is half-applied.** §Migration ("Dedup note") states: *"the `_sk` loop is copy-pasted in `render.ts:208` and `stream.ts:146`. This RFC must patch **both**."* It must patch **more**. There is a third, **public** render path: `renderAlgebra` (`src/fold/algebras/render.ts`), exported from `src/index.ts:343` and `src/fold/index.ts:15`, driven by the also-public `foldView`/`paraView`. Its `buildAttributes` emits element attributes by iterating `Object.entries(attrs)` (render.ts fold algebra lines 23-31) keyed by the **JS property name** and **never reads `_sk`**. The `attrs` it receives come from `extractAttrs` (`src/fold/fold.ts:9`, duplicated `src/fold/para.ts:9`), which flat-copies every own-enumerable tag key. Consequence: `foldView(renderAlgebra, Meta().setHttpEquiv("content-security-policy"))` STILL renders `httpEquiv="…"` — the exact silently-broken element F-A-012 claims to fix. The RFC's frontmatter marks the change `# bug fix: emits http-equiv (was httpEquiv)` unconditionally; it is only true on render/stream, false on the documented alternate path. A bug "fixed" on one of two public render paths is not fixed.

- **Breaking failure mode 2 — SVG opacity/filter "output identical" is wrong under mixed usage.** §Migration claims for F-A-015: *"output is identical (`opacity=\"…\"` either way); only the internal path changes (`attributes` bag → `_sk`)."* True only for pure call sites. Today `setOpacity` routes through `addAttribute` (svg.ts:46,61), so `opacity` lives in the keyed `attributes` bag — and the bag deduplicates by object key. After the change `opacity`/`filter` become own-enumerable instance fields emitted by the `_sk` loop (render.ts:213), which runs **before** the `attributes`-bag loop (render.ts:225). Any call site that mixes the new typed setter with a leftover `addAttribute('opacity', …)` — precisely the escape-hatch these apps used pre-migration — now emits the attribute **twice** (`opacity="x" opacity="y"`), one from each loop, where today it deduped to one. That is observable, browser-affecting, and not codemod-able from the signature alone. `setOpacity`/`setFilter` are live in `planet-positive-sport` and `fluent-svg`, so the surface is non-hypothetical.

- **Breaking failure mode 3 — the rename surface is incomplete, so it is two migrations, not one.** §3/§4 and `api_surface` enumerate `crossorigin` only on Link/Script. But `ImgTag.setCrossorigin` (`src/elements/media.ts:62`) exists, is typed to the narrow `'anonymous' | 'use-credentials'`, and `ImgTag._sk` carries `'crossorigin'`. It is left un-widened and un-renamed — so `Img().setCrossOrigin("")` is still a type error and Img still forces the F-A-044 `addAttribute("crossorigin","")` bypass. Likewise `AnchorTag.setReferrerpolicy` (`src/elements/links.ts:45`) is a second referrerpolicy setter the RFC's Iframe-only rename misses. Guardrail §11.5(b) requires breaking changes be "bundled into one migration." Leaving sibling setters un-renamed guarantees a *second* rename pass (and a second v7 alias-removal line) over the same method family — the opposite of one bundled migration.

## Does it survive?

**survives-with-changes.** None of the three failure modes is a guardrail-killer that should sink the cluster — the enabling `_sk` tuple design is sound, the renames-with-aliases are correctly additive, and the genuinely scary claim (http-equiv has zero app call sites) checks out (the only grep hit, `pregled-nepremicnin-dashboard/.../webhook.controller.ts:558`, is a raw `<meta http-equiv="refresh">` HTML literal, not a `setHttpEquiv()` call; zero real callers confirmed). So the render/stream behavior changes land on empty or pure surface and are safe to treat as bug fixes *there*.

But the RFC ships an inaccurate breakage map: it claims two render paths when there are three (plus two `extractAttrs` copies), which makes the http-equiv fix half-true and the SVG change mismarked as inert. Under the breaking-change lens, mismarked breakage is the failure — guardrail §13 "guardrail drift: a breaking API sneaks into a minor." The required changes above make the ledger honest (fix or scope the third path; reclassify SVG as a marked behavior change with the double-emit hazard guarded; complete the crossorigin/referrerpolicy rename so it's one migration). With those folded in, it survives.

## Guardrail check (breaking-change owns §11.5)

- **§11.5(a) codemod-able:** the renames are pure-rename codemods — pass. The http-equiv and SVG changes are NOT app-side codemods (they're internal), which is fine **iff** the behavior truly doesn't change; failure modes 1–2 show it does change on the fold path / under mixed usage, so those must be either fixed or explicitly documented as behavior changes (required-changes #1, #2).
- **§11.5(b) one bundled migration:** currently violated by the incomplete crossorigin/referrerpolicy surface (required-change #3) — fixing it restores the invariant.
- **§11.5(c) justified by impact:** pass — 25 documented `addAttribute` bypasses + a silently-broken CSP meta tag is real, cited pain.
- Net: additive-by-default holds for the public setter surface; the breakage that exists is internal/zero-call-site, but the RFC under-counts the render paths it touches. Honest re-marking required, not rejection.
